## 1. 三种"保活"的准确定义

| | **心跳 Noop** | **UDP 信令保活** | **TCP Keepalive** |
|---|---|---|---|
| 传输 | TCP 长连（同 socket） | **独立 UDP socket** | TCP 协议栈 |
| cmdid | **6** | **243** | 无 |
| seq | `0xFFFFFFFF` | UDP 路径 = 0 | — |
| body | 空 | 空 | — |
| 间隔 | **3.5 ~ 10 分钟**（智能自适应） | **固定 5 秒** | 系统默认 2 小时 |
| 超时 | 8 秒（active 5 秒）→ **断链** | 20 秒无流量则停止 | 无感 |
| 期待回包 | **是**（`longlink_noop_isresp` 校验） | **否**（`send_only = true`） | — |
| 目的 | 探测链路存活、测 RTT、校准心跳间隔 | 穿透 NAT、保持 NAT 映射、探跨网可达 | 探测 TCP 连接是否还在 |
| Mars 是否启用 | ✅ | ✅ | ❌ **全仓无 `SO_KEEPALIVE`** |

> **结论**：Mars 完全不依赖 TCP Keepalive，链路存活判断 100% 在应用层。

### 2.5 ★ 关键：有业务流量就不发心跳

`longlink.cc:939-946`（写路径）：


> **这是 Mars 心跳设计的重要细节**：
> **只要往 socket 写了数据，心跳定时器就被重置。**
> 也就是说：**有消息在发的时候，完全不需要额外的心跳包**。
> 只有链路空闲时才发 noop 保活。
>
> **IM 价值**：高频消息场景下**零心跳开销**；
> 空闲场景下心跳间隔自动拉长到最长 10 分钟。

> **这是"服务端 IM 网关扛不住流量"的典型表现。**

## 3. 智能心跳（SmartHeartbeat）

`mars/stn/src/smart_heartbeat.cc`（465 行）。

### 3.1 目标（源码注释）

```
Manage the heartbeat frequecy by Adaptive Computing for the current active network.
The purpose is to decrease the heartbeat frequecy when our app in inactive state,
And meanwhile keep the TCP alive as far as possible.
```

> **两个目标**：① App 不活跃时**降低心跳频率**省电省流量；
> ② **尽可能保持 TCP 存活**（避免每次重连都要重新握手 + 重新鉴权）。

### 3.2 常量

`mars/stn/config.h:34-45`：

```cpp
#define MinHeartInterval (3 * 60 * 1000 + 30 * 1000)  // 3.5 分钟 = 210s（最小）
#define MaxHeartInterval (10 * 60 * 1000)             // 10 分钟 = 600s（最大）

#define HeartStep (60 * 1000)     // 每次成功后 +60s
#define SuccessStep (20 * 1000)   // 达标后 -20s

#define MaxHeartFailCount (2)     // 连续失败 2 次 → 降档
#define BaseSuccCount (5)         // 连续成功 5 次 → 升档
#define NetStableTestCount (3)    // 用 MinHeartInterval 测试 3 次后判定网络稳定
```

### 3.4 `GetNextHeartbeatInterval` —— 决策入口

`smart_heartbeat.cc:271-301`：

```cpp
unsigned int SmartHeartbeat::GetNextHeartbeatInterval() {
    // ① 外部强制指定优先
    if (outer_setted_heart_ != -1 && outer_setted_heart_ >= 0) {
        last_heart_ = outer_setted_heart_;
        return outer_setted_heart_;
    }

    // ② App 活跃 → 最小间隔
    if (ActiveLogic::Instance()->IsActive()) {
        last_heart_ = MinHeartInterval;
        return MinHeartInterval;
    }

    // ③ 还没稳定 / 没有网络信息 → 最小间隔
    if (success_heart_count_ < NetStableTestCount ||
        current_net_heart_info_.net_detail_.empty()) {
        last_heart_ = MinHeartInterval;
        return MinHeartInterval;
    }

    // ④ 用学习到的值
    last_heart_ = current_net_heart_info_.cur_heart_;
    xassert2((last_heart_ < MaxHeartInterval && last_heart_ >= MinHeartInterval),
             "heart value invalid");

    // ⑤ Doze 模式下强制最小
    if (__IsDozeStyle() && current_net_heart_info_.heart_type_ != kDozeModeHeart
        && last_heart_ != (MaxHeartInterval - SuccessStep)) {
        current_net_heart_info_.cur_heart_ = last_heart_ = MinHeartInterval;
    }
    // ⑥ 越界修正
    if (last_heart_ >= MaxHeartInterval || last_heart_ < MinHeartInterval) {
        current_net_heart_info_.cur_heart_ = last_heart_ = MinHeartInterval;
    }
    return last_heart_;
}
```

> **重要**：`ActiveLogic::IsActive()` 为 true（App 在前台活跃）时，
> **心跳间隔固定为 3.5 分钟**，不用学习值。
> 学习值只在 **App 不活跃（后台）** 时才生效 —— 这正是省电的目的。

### 3.5 `OnHeartResult` —— 学习算法

`smart_heartbeat.cc:111-245`。核心逻辑：

```
收到心跳结果（成功/失败）
  │
  ├─ 阶段 1：累计 success_heart_count_ <= NetStableTestCount(3)
  │     → 只记录 min_heart_fail_count_，返回（还在探测期）
  │     → min_heart_fail_count_ >= 6 且有网 → 上报 kActionBadNetwork（弱网）
  │
  ├─ 阶段 2：网络已稳定 → 调整 cur_heart_
  │     │
  │     ├─ 成功 && last_heart_ == pre_heart_ → succ_heart_count_++
  │     │     否则失败 → succ_heart_count_ = 0, fail_heart_count_++
  │     │
  │     ├─ 成功 && is_stable_:
  │     │     ├─ cur_heart_ >= MaxHeartInterval - SuccessStep → 已是最大，不再加
  │     │     └─ 距上次修改 >= 7 天 → 探测更大的心跳（+SuccessStep=20s）
  │     │        （源码注释："probe bigger heart on Wednesday"）
  │     │     → 7 天才探一次，避免频繁扰动
  │     │
  │     ├─ 成功 && succ_heart_count_ >= BaseSuccCount(5):
  │     │     ├─ cur_heart_ >= MaxHeartInterval - SuccessStep
  │     │     │     → cur_heart_ = MaxHeartInterval - SuccessStep (580s)
  │     │     │     → is_stable_ = true ★ 标记"已收敛"
  │     │     │     → heart_type_ = Doze 或 SmartHeartBeat
  │     │     └─ 否则 cur_heart_ += HeartStep(60s)，上限 580s
  │     │
  │     └─ 失败 && fail_heart_count_ >= MaxHeartFailCount(2):
  │           ├─ is_stable_ → cur_heart_ = MinHeartInterval，重置计数
  │           └─ 否则 cur_heart_ -= (HeartStep + SuccessStep) = 80s，下限 MinHeartInterval
  │
  └─ __SaveINI()   持久化
```

**收敛上限是 `MaxHeartInterval - SuccessStep = 600s - 20s = 580s`（9 分 40 秒）**，不是整整 10 分钟。

> **为什么留 20s 的余量**？因为 `SuccessStep` 用于"探测更大心跳"和"降档"的对称性。

### 3.6 Doze 模式识别

`smart_heartbeat.cc:249-269`：

```cpp
void SmartHeartbeat::JudgeDozeStyle() {
    if (ActiveLogic::Instance()->IsActive()) return;
    if (!noop_start_tick_.isValid()) return;
    if (kMobile != ::getNetInfo()) return;      // 只在移动网络下判断

    if (std::abs(noop_start_tick_.gettickspan() - last_heart_) >= 20 * 1000) {
        doze_mode_count_++;                       // 实际间隔远大于预期 → doze
        normal_mode_count_ = std::max(normal_mode_count_ - 1, 0);
    } else {
        normal_mode_count_++;
        doze_mode_count_ = std::max(doze_mode_count_ - 1, 0);
    }
    noop_start_tick_ = tickcount_t(false);
}

bool SmartHeartbeat::__IsDozeStyle() {
    return doze_mode_count_ >= 2 && doze_mode_count_ > (2 * normal_mode_count_);
}
```

> **Doze 模式判定**：移动网络下，实际心跳间隔比预期大 20 秒以上 → 说明 Android 把 CPU 挂起了。
> Doze 模式下直接用最大心跳间隔（580s），因为**这种状态下发多密的包也没用，CPU 根本不跑**。

### 4.3 ★ 重排逻辑：有流量就推迟信令

`signalling_keeper.cc:72-91`：

```cpp
void SignallingKeeper::OnNetWorkDataChanged(const char*, ssize_t, ssize_t) {
    if (!keeping_) return;
    uint64_t now = ::gettickcount();
    xassert2(now >= last_touch_time_);

    if (now < last_touch_time_ || now - last_touch_time_ > g_keepTime) {
        keeping_ = false;    // ★ 超过 keepTime 没流量 → 放弃保活
        return;
    }
    if (postid_ != MessageQueue::KNullPost) {
        MessageQueue::CancelMessage(postid_);      // ★ 取消已排的下一次
    }
    postid_ = MessageQueue::AsyncInvokeAfter(g_period,
        boost::bind(&SignallingKeeper::__OnTimeOut, this),
        msgreg_.Get(), "SignallingKeeper::__OnTimeOut");
}
```

**逻辑**：
1. 每 5 秒发一次 UDP 信令包
2. **只要长连上有流量（收或发），就取消下一次定时，重新计时**
3. **20 秒内完全没有流量 → 停止保活**（`keeping_ = false`）

> **IM 价值**：
> - **有消息在传的时候不需要信令保活** → 省流量
> - **长时间空闲时才用 UDP 探活** → 保持 NAT 映射，防止长连被中间设备回收
> - **NAT 映射保持的价值**：移动网络下 NAT 映射通常有超时（几分钟），
> 保持映射可以让下一次 TCP 连接更快建立（省掉一次握手）

```
1. 客户端在上层生成"校验 buffer" + "hash buffer"，cmdid 由上层给定
2. 客户端发一个 cmdid=上层cmdid, seq=0xFFFFFFFE 的帧，body = 校验 buffer
3. 服务端回包必须 seq 回显 0xFFFFFFFE
   （longlink_identify_isresp 判 _sent_seq == _recv_seq && 0 != _sent_seq）
4. 客户端把回包 body 交给 OnLonglinkIdentifyResponse() 校验
5. 清空 taskid_（longlink_identify_checker.cc:90-99）
```

**三种模式**：
- `kCheckNow`：立刻校验（本次心跳就发校验包）
- `kCheckNext`：下一次心跳再校验
- `kCheckNever`：**永不校验**（sample 的 Android 端就是这个，`MarsServiceStub.java:188-193`）

### 5.3 为什么复用心跳通道

```cpp
// longlink.cc:364-368
if (identifychecker_.GetIdentifyBuffer(buffer, req_cmdid)) {
    Task task(Task::kLongLinkIdentifyCheckerTaskID);
    task.cmdid = req_cmdid;
    suc = Send(buffer, KNullAtuoBuffer, task);
```

> **省一次往返**：校验包兼做心跳包，一次 RTT 完成两件事。
> 这是很典型的"协议复用"技巧。

### 5.4 IM 落地建议

长连接建立后做一次身份校验，防止：
- **伪造客户端**（拿到 IP 就连）
- **中间人劫持长连接**（除非用 TLS）
- **账号串号**（把账号绑定到连接上，服务端可以踢掉其他设备的连接）

服务端需要：
- 为 cmdid 提供一个专门的校验接口
- **回包 seq 必须回显 `0xFFFFFFFE`**
- 校验失败要主动断链

## 6. 心跳相关的时间线总览

```
t=0        长连建立成功（kConnected）
t=0        启动心跳间隔 alarm（3.5~10 分钟）
           │
           ├─ 如果有业务数据写入 → ★ 重置心跳间隔 alarm
           │                        （长连接.cc:939-946）
           │                        → 心跳被无限推迟
           │
t=T        心跳间隔到 → __NoopReq
           ├─ 优先发信令校验包（如果还没校验过）
           └─ 否则发普通 noop 包（cmdid=6, seq=0xFFFFFFFF）
           │
           ├─ 同时启动超时 alarm（8s，active 时 5s）
           │
t=T+δ      收到心跳回包 → __NoopResp
           ├─ is_noop = true
           ├─ _nooping = false
           ├─ 取消超时 alarm
           └─ __NotifySmartHeartbeatHeartResult(true, ...) → SmartHeartbeat 学习
           │
t=T+8s     没收到回包 → alarmnooptimeout_ 触发
           └─ _errtype = kEctSocket, _errcode = kEctSocketRecvErr
              → goto End → ★ 断开长连 → 触发重连流程
```

**并行进行**：
```
每 5 秒      UDP 信令保活（cmdid=243）
             └─ 有流量就推迟；20 秒无流量则停止
```

## 7. IM 服务端实现要求汇总

| 项 | 要求 | 不满足的后果 |
|---|---|---|
| **心跳回包** | cmdid=6 的包，**原样回显 seq=0xFFFFFFFF**，body 可空 | 客户端 8 秒后断链 → 无限重连 |
| **心跳响应延迟** | 必须 < 8 秒（active 模式 < 5 秒） | 同上 |
| **心跳频率** | 客户端最密 3.5 分钟一次，最疏 9 分 40 秒一次 | — |
| **UDP 信令** | 收到 cmdid=243 的 UDP 包，**不需要响应**（UDP 本身不可靠） | — |
| **信令校验** | 若启用，seq 必须回显 `0xFFFFFFFE` | 校验永远失败 |
| **主动断开** | 服务端主动关闭 TCP → 客户端 `recv==0` → `kEctSocketShutdown(-10090)` → 触发重连 | — |
| **服务端心跳** | 服务端也可以主动发心跳包（seq 用业务自定义） | 客户端会当成"找不到的任务"丢弃 |

> **最后一条很关键**：
> **服务端不能主动发心跳包**（seq 不能是 `0xFFFFFFFF` 以外的值且期望客户端响应），
> 因为客户端只认 `seq == 0xFFFFFFFF && cmdid == 6` 为心跳。
> 如果服务端要用"服务端主动 ping"，必须**复用 cmdid=6 + seq=0xFFFFFFFF**，
> 客户端会把它当心跳响应处理（`__NoopResp` 会清 `isnooping_`）——
> 但这会让客户端误以为自己的心跳被响应了。**设计上应该由客户端发起心跳。**

## 2. TCP 粘包/拆包的处理机制

### 2.1 核心工具：`AutoBuffer::Move`

`mars/comm/autobuffer.cc:157-174`：

```cpp
off_t AutoBuffer::Move(off_t _move_len) {
    if (_move_len > 0) {
        // 头部插入空洞
        memmove(parray_ + _move_len, parray_, Length());
        memset(parray_, 0, _move_len);
        Length(Pos() + _move_len, Length() + _move_len);
    } else if (_move_len < 0) {
        // 消费掉头部 _move_len 字节（无 memcpy！）
        Length(move_len < Pos() ? Pos() - move_len : 0, Length() + move_len);
    }
    return Length();
}
```

**负数 = 消费**：`memmove` 前移剩余数据，缩短 `Length()`，**读指针 `Pos()` 保持不变**。

> **这就是零成本的"消费式拆包"**：
> 收到 100 字节、消耗了 20 字节的帧 → `Move(-20)` →
> 剩余 80 字节前移到头部，`Length()` 变成 80，`Pos()` 仍为 0 → 下一轮循环直接继续解。

### 2.2 三种 TCP 边界情况

| 情况 | 现象 | Mars 的处理 |
|---|---|---|
| **半包** | 一次 recv 只收到 10 字节（头都没收全） | `__unpack_test` 返回 `LONGLINK_UNPACK_CONTINUE` → `break` → 等下次 recv |
| **粘包** | 一次 recv 收到 3 帧（100 字节） | while 循环解 3 次，每次 `Move(-packlen)` |
| **包内粘包** | 一次 recv 收到 1.5 帧 | 第 1 次解出整帧 `Move(-packlen)`，第 2 次 `CONTINUE` → `break` |

### 2.3 接收缓冲的按需扩容

`mars/comm/socket/tcpclient_fsm.cc:364-366`：

```cpp
if (recv_buf_.Capacity() - recv_buf_.Length() < 8KB) {
    recv_buf_.AddCapacity(16KB);
}
```

长连接侧（`longlink.cc:1000`）：每次 recv 前 `bufrecv.AllocWrite(64 * 1024, false)`。

> `AllocWrite(n, false)` 的第二个参数 `changelength=false` 表示**只扩容量不改长度**，
> 这样 `bufrecv.Length()` 仍然是"已收到的真实数据长度"。

## 4. 序列号（seq）管理

### 4.1 核心事实：线上的 `seq` 就是 Mars 的 `taskid`

```cpp
// mars/stn/src/longlink.cc:221
Encoder().longlink_pack(_task.cmdid, _task.taskid, _body, _extension, ...);
```

taskid 生成：

```cpp
// mars/stn/stn.cc:32-34
static uint32_t gs_taskid = 1;
Task::Task() : Task(atomic_inc32(&gs_taskid)) {}
```

```cpp
// mars/stn/stn_manager.cc:421-427
uint32_t StnManager::GenTaskID() {
    if (BOOST_UNLIKELY(atomic_read32(&gs_taskid) >= kReservedTaskIDStart)) {
        atomic_write32(&gs_taskid, 1);
    }
    return atomic_inc32(&gs_taskid);
```

`kReservedTaskIDStart = 0xFFFFFFF0` —— 从这里起保留给内部任务。

|---|---|---|
| `0xFFFFFFFF` (`kNoopTaskID`) | 心跳请求 | `longlink.cc:261` |
| `0xFFFFFFFE` (`kLongLinkIdentifyCheckerTaskID`) | 信令校验请求 | `longlink.cc:365-368` |

## 5. 客户端如何"跟踪期望的 server seq"

**没有期望计数器**。Mars 是**按 taskid 精确匹配**的：

`mars/stn/src/longlink_task_manager.cc:925-934`：

```cpp
std::list<TaskProfile>::iterator LongLinkTaskManager::__Locate(uint32_t _taskid) {
    if (Task::kInvalidTaskID == _taskid)
        return lst_cmd_.end();

    find_task find_functor;
    find_functor.taskid = _taskid;
    std::list<TaskProfile>::iterator it =
        std::find_if(lst_cmd_.begin(), lst_cmd_.end(), find_functor);
    return it;
}
```

### 5.1 不匹配时的行为

`longlink_task_manager.cc:966-999`：

```cpp
if (kEctOK == _error_type &&
    longlink->Encoder().longlink_ispush(_cmdid, _taskid, body, extension)) {
    // :966  seq == 0 → 视为 push，直接回调 OnPush，return
    fun_on_push_(_name, _cmdid, _taskid, body, extension);
    return;
}

std::list<TaskProfile>::iterator it = __Locate(_taskid);
...
if (lst_cmd_.end() == it) {
    xwarn2_if(Task::kInvalidTaskID != _taskid,
              TSF "task no found task:%0, cmdid:%1, ect:%2, errcode:%3", ...);  // :992
    return;      // :998 ★ 静默丢弃
}
```

**关键结论**：
> **回包 seq 在待发列表里找不到 → 打 warn 日志后丢弃，不重连、不重试。**

**为什么这样设计是对的**：
- 任务已超时被删除，响应姗姗来迟 → 丢弃是正确的
- 不需要维护"期望 seq 窗口"（像 TCP 那样）→ 乱序响应天然支持

### 5.2 性能代价

`__Locate` 是 **`find_if` 全表扫描** → **O(n)**。

| 场景 | n | 影响 |
|---|---|---|
| 正常聊天 | 10~50 个在途 | 可忽略 |
| IM 高峰 / 消息轰炸 | 1000+ | **可观的 CPU 消耗**（每次回包扫 1000 次） |

> **优化方向**（如果你要改造）：
> 把 `std::list<TaskProfile> lst_cmd_` 拆成
> `std::list<TaskProfile> lst_cmd_`（保持 FIFO 顺序）
> + `std::unordered_map<uint32_t, iterator> taskid_map_`（O(1) 定位）。
> **但要小心**：list 节点在排序（`sort`）后迭代器会失效，
> 需要在 `sort` 后重建 map。

## 9. 心跳包的识别

```cpp
// longlink_packer.cc:150-153
longlink_noop_isresp =
    [](uint32_t _taskid, uint32_t _cmdid, uint32_t _recv_seq,
       const AutoBuffer& _body, const AutoBuffer& _extend) {
        return Task::kNoopTaskID == _taskid && NOOP_CMDID == _cmdid;

```

**两个条件同时满足**：`taskid == 0xFFFFFFFF` 且 `cmdid == 6`。

> **IM 服务端要求**：必须对 cmdid=6 的心跳包**原样回显**（seq 也要回显 `0xFFFFFFFF`）。
> 如果服务端把 seq 改成别的值，客户端会认为心跳失败 → 8 秒后断链 → 无限重连。
> **这是 IM 服务端最容易写错的地方。**

## 12. 服务端的两个协议缺陷

### 缺陷 1：Netty pipeline 缺少帧解码器

```java
// samples/Server/server/src/main/java/com/tencent/mars/proxy/ProxyServer.java:108-115
@Override protected void initChannel(T channel) throws Exception {
    channel.pipeline().addLast(new NetMsgHeaderHandler());   // ← 只有这一个
}
```

**没有 `LengthFieldBasedFrameDecoder`**。

TCP 是字节流：
- 一次 `channelRead` 只拿到半帧 → `readInt` 抛 EOF → `decode` 返回 false → `if(!ret) return;` → **静默丢包**（`NetMsgHeaderHandler.java:87-90`）
- 一次 `channelRead` 拿到多帧 → 只解析第一帧 → **其余丢失**

**正确做法**：
```java
channel.pipeline().addLast(
    new LengthFieldBasedFrameDecoder(1024*1024, 16, 4, 0, 0));  // lengthOffset=16, lengthFieldLength=4
channel.pipeline().addLast(new NetMsgHeaderHandler());
```
（`head_length` 在 offset 0..3，`body_length` 在 offset 16..19，所以 lengthOffset=16、lengthFieldLength=4、
lengthAdjustment=0 表示"整包长度 = body_length"，需要再减去 20 的头长 → 实际要用
`LengthFieldBasedFrameDecoder(maxLen, 16, 4, -20, 0)` 或自定义 decoder。）

### 缺陷 2：`InvalidHeaderException` 未被捕获

```java
// NetMsgHeader.java:65 声明 throws InvalidHeaderException
// :99 只 catch (IOException)
```

→ 异常冒泡到 `channelRead` 的 `catch(Exception)`（`:158-160`）→ 只 `printStackTrace()`，
**不给客户端任何错误帧**，客户端只能等到超时。

> **真实服务端必须**：捕获异常 → 回一个错误帧（cmdid 原样、seq 原样、body 带错误码）。

## 13. IM 服务端协议实现清单（对照检查）

| 检查项 | 要求 |
|---|---|
| 帧定界 | 必须有 `LengthFieldBasedFrameDecoder` 或等价实现 |
| `client_version` | 与客户端一致（200 或双版本兼容） |
| 响应 `cmdid` / `seq` | **原样回显** |
| 心跳（cmdid=6） | **必须回显 seq = 0xFFFFFFFF**，body 可为空 |
| 推送（push） | **seq 填 0**，cmdid 用业务约定的值（如 10001） |
| 异常处理 | 解包失败也要回错误帧，不能静默丢 |
| 顺序 | **不要求**按请求顺序响应（客户端用 taskid 匹配） |
| 幂等 | 重试的请求（seq 相同）必须去重 |
| body 大小 | ≤ 1MiB（客户端硬限制） |
| 背压 | 慢客户端要限速，否则服务端内存爆 |

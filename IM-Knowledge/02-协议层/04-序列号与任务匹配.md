# 04 · 序列号、命令号与业务接入契约

> 这一篇把"协议层"和"业务层"的接缝讲清楚 —— **面试和实战中最容易出错的地方**。

---

## 1. cmdid 体系

### 1.1 框架内建 cmdid（只有 3 个）

`mars/stn/proto/longlink_packer.cc:96-98`：

```cpp
#define NOOP_CMDID 6
#define SIGNALKEEP_CMDID 243
#define PUSH_DATA_TASKID 0
```

| cmdid | 常量 | 含义 | 备注 |
|---|---|---|---|
| **6** | `NOOP_CMDID` | **心跳 ping / pong 共用** | 请求 seq = `0xFFFFFFFF`；回包 seq 必须回显 `0xFFFFFFFF` |
| **243** | `SIGNALKEEP_CMDID` | **UDP 信令保活** | seq = 0（UDP 路径） |
| 业务自定义 | — | 应用命令 | 由业务方定义 |
| `0xFF000000 \| x` | `Task::kMinorLonglinkCmdMask` | 副长连的 identify cmdid | `mars/stn/stn.h:93` |

### 1.2 业务 cmdid（sample 示例）

`samples/Server/server/src/main/proto/main.proto:4-14` 与
`samples/android/marsSampleChat/app/src/main/proto/main.proto:5-14`：

```protobuf
enum CmdID {
    CMD_ID_INVALID           = -1;
    CMD_ID_UNKNOWN           = 0;
    CMD_ID_HELLO             = 1;
    CMD_ID_AUTH              = 2;
    CMD_ID_SEND_MESSAGE      = 3;
    CMD_ID_CONVERSATION_LIST = 4;
    CMD_ID_JOINTOPIC         = 5;
    CMD_ID_LEFTTOPIC         = 7;
    CMD_ID_HELLO2            = 8;   // 仅 Server 侧 main.proto 有
}
```

> ⚠️ **注意 cmdid = 6 被 `NOOP_CMDID` 占用，所以枚举里跳过了 6**（5 → 7）。
> **这是一个真实的协议设计陷阱**：业务 cmdid 必须避开 6 和 243。

## 2. ⚠️ 开源版 vs 微信内部版的 cmdid 差异（**必须知道**）

以下符号**在开源 Mars 中完全不存在**，它们是微信内网 STNetMsgXp 的私有体系：

| 微信内部版 | 开源版对应 |
|---|---|
| `cmdInnerPing` / `cmdInnerPong` | `cmdid = 6`（`NOOP_CMDID`），ping/pong 同 cmdid，靠 `seq=0xFFFFFFFF` + `taskid` 区分 |
| `cmdOuterPing` / `cmdOuterPong` | 同上（TCP 长连上的心跳） |
| `cmdAuth` | **无协议层 cmdid**。`Task::need_authed` + `Callback::MakesureAuthed()` 是**本地鉴权门控**，不产生网络包 |
| `cmdInnerStart` | 无；最接近的是 `Task::kLongLinkIdentifyCheckerTaskID`（信令校验首包） |
| `cmdInnerReport` | 无；上报走 `reportTaskProfile` / `onPush` 通道 |
| `cmdSignalling` | `SIGNALKEEP_CMDID = 243`（UDP 信令保活） |

**面试时如果说错，会暴露"没真读过代码"。**

## 3. 业务接入契约

### 3.1 `Req2Buf` —— 编码

```cpp
virtual bool Req2Buf(uint32_t _taskid, void* const _user_context,
                     const std::string& _user_id,
                     AutoBuffer& outbuffer, AutoBuffer& extend,
                     int& error_code, const int channel_select,
                     const std::string& host,
                     const unsigned short client_sequence_id) = 0;
```

| 参数 | 用途 | IM 用法 |
|---|---|---|
| `_taskid` | 区分是哪个任务 | 用于查表拿消息对象 |
| `_user_context` | **业务上下文原样返回** | 放 `MessageEntity*` |
| `_user_id` | 多用户标识 | 传 uin |
| `outbuffer` | **输出**，写业务 body | protobuf `toByteArray()` |
| `extend` | 扩展通道（默认编码器不用） | 留空 |
| `error_code` | 出错时填 | — |
| `channel_select` | 当前通道（长连/短连） | 短连可能需要不同的 body |
| `host` | 目标 host | 短连时可能需要放 token |
| `client_sequence_id` | 16 位 trace id | **可放进 body 做端到端对账** |

**返回 `false` 的后果**（`longlink_task_manager.cc:511-517`）：
```
OnTaskEnd(kEctEnDecode, error_code, kTaskFailHandleTaskEnd)
```
→ 任务**直接结束，不重试**。

### 3.2 `Buf2Resp` —— 解码

```cpp
virtual int Buf2Resp(uint32_t _taskid, void* const _user_context,
                     const std::string& _user_id,
                     const AutoBuffer& _inbuffer, const AutoBuffer& _extend,
                     int& _error_code, uint64_t& _flags,
                     const int channel_select,
                     unsigned short& server_sequence_id) = 0;
```

**返回值语义（最关键）**：

| 返回值 | 语义 | IM 用法 |
|---|---|---|
| `0` (`kTaskFailHandleNormal`) | 成功 | 正常收到服务端 ACK |
| `-1` (`kTaskFailHandleDefault`) | 默认处理（出错） | 业务错误码 → 走错误分支，**可以重试**（如果 `remain_retry_count > 0`） |
| `-12` (`kTaskFailHandleRetryAllTasks`) | 该用户所有任务全部重做 | 服务端说"你的数据全乱了，重新拉" |
| `-13` (`kTaskFailHandleSessionTimeout`) | **会话超时 → 立即重试 + 重新鉴权** | **登录态失效的典型处理** |
| `-14` (`kTaskFailHandleTaskEnd`) | 直接结束，不重试 | 消息已被服务端拒绝（如内容违规） |
| `-15` (`kTaskFailHandleTaskTimeout`) | 超时结束 | — |
| `-16` (`kTaskSlientHandleTaskEnd`) | **静默删除，不回调上层** | 用户已退出聊天页 |

> **IM 黄金规则**：
> **服务端返回"业务错误"时，要区分"可重试"和"不可重试"。**
> - 网络类错误、限流 → 返回 `-1`，让它重试
> - 参数错误、内容违规、账号被封 → 返回 `-14`，别浪费重试
> - 登录态失效 → 返回 `-13`

**副作用参数**：
- `_error_code`（引用）→ 传给 `OnTaskEnd` 的 `errCode`
- `_flags`（引用）→ 协议内部用
- `server_sequence_id`（引用）→ **上层从响应体里解析出来回填**，用于与后台对账

### 3.3 `OnTaskEnd` —— 任务结束

```cpp
virtual int OnTaskEnd(uint32_t _taskid, void* const _user_context,
                      const std::string& _user_id,
                      int _error_type, int _error_code,
                      const CgiProfile& _profile) = 0;
```

- **返回值会覆盖 err_code**（`stn.h:503` 注释）
- `_profile` 是完整性能画像（见 `01-公开API与数据结构.md` §4）
- **在 STN 线程上被调用** → 切主线程更新 UI

### 3.4 `OnPush` —— 服务端推送

```cpp
virtual void OnPush(const std::string& _channel_id, uint32_t _cmdid, uint32_t _taskid,
                    const AutoBuffer& _body, const AutoBuffer& _extend) = 0;
```

- `_taskid` 恒为 **0**（push 的定义）
- `_cmdid` 是业务约定的 push cmdid（如 10001）
- **在 LongLink I/O 线程上被调用**（不是 STN 线程）→ 同样要切线程

> **IM 落地**：这是服务端主动下发消息（对方发来的消息、离线同步、系统通知）的入口。
> **必须做**：解析 → 落库 → 通知 UI → 发送 ACK。

## 5. taskid ↔ 业务对象的映射维护

### 5.1 sample 的做法

```java
// MarsServiceStub.java:104
TASK_ID_TO_WRAPPER.put(_task.taskID, taskWrapper);
```

```java
// MarsServiceStub.java:120-124 —— 取消
StnLogic.stopTask(taskID);
TASK_ID_TO_WRAPPER.remove(taskID);
```

```java
// MarsServiceStub.java:216-232 —— onTaskEnd
MarsTaskWrapper taskWrapper = TASK_ID_TO_WRAPPER.get(taskID);
if (taskWrapper != null) {
    taskWrapper.onTaskEnd(errType, errCode);
}
```

### 5.2 必须自己清理

> ⚠️ **STN 不会帮你删除 map 里的条目**。
> 如果 `onTaskEnd` 不移除，map 会**无限增长 → 内存泄漏**。

**正确做法**：
```java
@Override public void onTaskEnd(int errType, int errCode) {
    MarsTaskWrapper w = TASK_ID_TO_WRAPPER.remove(taskID);
    if (w != null) w.onTaskEnd(errType, errCode);
}
```

### 5.3 更好的方案：直接用 `userContext`

C++ 侧 `Task::user_context` 是 `void*`，会原样传回 `Req2Buf` / `Buf2Resp` / `OnTaskEnd`。

**Java 侧没有直接暴露 `userContext` 的传递**，所以 sample 用了 `TASK_ID_TO_WRAPPER` map。
如果你在做 Java 层的 IM 框架，可以：
- 用 `userContext`（如果 SDK 暴露了）直接传对象引用
- 或者用 `WeakHashMap` 避免泄漏
- 或者用 `client_sequence_id` 做业务消息 ID（更可靠）

## 6. 多用户 / 多账号

`Task::user_id`（`stn.h:126`）：

> `// use for identify multi users`

配合 `Callback::MakesureAuthed(host, user_id)`：
不同 `user_id` 的任务**鉴权状态相互独立**。

`kTaskFailHandleRetryAllTasks(-12)` 的语义是"**该用户**所有任务全部重做" ——
所以 `user_id` 是重做范围的划分依据。

> **IM 场景**：账号切换时，需要把旧账号的任务清理掉、新账号的任务重新鉴权。
> `user_id` 就是这个隔离维度。

## 7. 消息顺序性

### 7.1 Mars 不保证顺序

- 任务队列是 `std::list` + **按 priority 排序**（**不是按创建时间**）
- 响应匹配用 `find_if`，**乱序响应完全正常**

> **IM 关键结论**：
> **如果你要保证消息顺序，必须在业务层实现。**
>
> 例如：同一会话的消息携带自增 `seq`（业务层），
> 收到时按 seq 排序后再上屏。或者**串行化发送**（同一会话的消息排队发）。

### 7.2 优先级排序带来的顺序破坏

```cpp
lst_cmd_.push_back(task);
lst_cmd_.sort(__CompareTask);      // 按 priority 排序
```

**如果同一会话的消息 priority 相同** → 稳定排序 → FIFO → 顺序保持。
**如果 priority 不同** → 顺序会被打乱。

> **IM 建议**：**同一会话内的消息用同一优先级**，
> 不同重要性的消息（VIP 消息 vs 普通消息）才用不同优先级，且要接受乱序。

### 7.3 `std::list::sort` 的复杂度

`std::list::sort` 是 **O(n log n)**，每次 `StartTask` 都调一次 → **O(n log n) 的插入成本**。

IM 高峰（1000 个在途任务）时，每加一个任务都要重排 1000 个元素。
**这是一个真实的性能瓶颈点**（虽然实践中 n 通常不大）。

> **优化方向**（如果你要改）：
> - 维护多个 priority 的子队列（0~5 共 6 个 list），插入 O(1)
> - 或者用插入排序优化（因为新任务优先级通常相邻）

## 8. 一份完整的 IM 接入检查清单

### 协议层
- [ ] cmdid 不与 6 / 243 冲突
- [ ] `client_version` 三端一致
- [ ] 服务端回包原样回显 cmdid + seq
- [ ] 服务端心跳回包 seq = 0xFFFFFFFF
- [ ] push 的 seq = 0
- [ ] body ≤ 1MiB
- [ ] 服务端有帧解码器（处理粘包拆包）

### 客户端层
- [ ] `Req2Buf` / `Buf2Resp` 不阻塞（< 1ms）
- [ ] `Req2Buf` 失败返回 `false`（不是空包）
- [ ] `Buf2Resp` 按错误类型返回正确的 `TaskFailHandleType`
- [ ] `OnTaskEnd` 移除 taskid 映射（防泄漏）
- [ ] `OnPush` 正确处理并回 ACK
- [ ] 消息有业务级唯一 ID（幂等键），**不用 taskid**
- [ ] 同一会话消息用同一 priority
- [ ] UI 更新切主线程

### 运维层
- [ ] 实现 `ReportTaskLimited`（用户提示"网络繁忙"）
- [ ] 实现 `ReportConnectStatus`（驱动连接状态 UI）
- [ ] 实现 `ReportTaskProfile`（性能监控）
- [ ] 实现 `TrafficData`（流量统计）
- [ ] Xlog 初始化 + 日志分级

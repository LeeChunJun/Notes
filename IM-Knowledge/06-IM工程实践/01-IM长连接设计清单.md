## 2. 通道设计

| 业务 | 通道 | 理由 |
|---|---|---|
| **聊天消息收发** | `kChannelLong`（纯长连） | 必须实时；长连不可用时任务留在队列等待，**不降级** |
| **消息 ACK / 已读回执** | `kChannelLong` | 低优先级（`priority=1~2`），可与消息合批 |
| **送达回执** | `kChannelLong` | 同上 |
| **拉取历史消息** | `kChannelShort` | 可缓存、可重试、可 CDN 化 |
| **同步会话列表** | `kChannelShort` | 同上 |
| **图片/文件上传下载** | `kChannelShort` | 大流量，不占用长连带宽 |
| **埋点 / 统计上报** | `kChannelShort`，`retry_count=0` | 失败就丢，不要浪费资源 |

> **不要用 `kChannelBoth` 做 IM 消息** ——
> 降级发生在"选路时刻"而非"发送时刻"，
> 长连刚好在那一瞬间连上也会被分到短连，延迟劣化且行为不可预测。

## 3. 优先级设计

```cpp
// 建议
消息发送        priority = 0   (ETASK_PRIORITY_HIGHEST)
消息 ACK        priority = 1
送达/已读回执   priority = 2
会话同步        priority = 3   (NORMAL)
历史消息拉取    priority = 4
埋点上报        priority = 5   (LOWEST)
```

> ★ **同一会话内的消息必须用同一优先级** ——
> 因为任务队列是按 priority 排序的，不同 priority 会打乱顺序。

## 4. 消息信封（Message Envelope）

### 4.1 推荐结构

```protobuf
message Envelope {
    // ── 路由 ──
    uint64 msg_id = 1;           // ★ 业务级唯一 ID（幂等键）
    uint64 conv_id = 2;          // 会话 ID
    uint32 sender = 3;
    uint32 receiver = 4;         // 单聊=对方；群聊=群 ID
    uint32 msg_type = 5;         // 文本/图片/语音/系统通知

    // ── 内容 ──
    bytes  payload = 6;          // 具体内容（可再嵌套 protobuf）
    uint32 client_seq = 7;       // ★ 客户端递增序号（会话内排序）

    // ── 时间与状态 ──
    uint64 client_time = 8;      // 客户端时间戳
    uint64 server_time = 9;      // 服务端时间戳（服务端填）
    uint32 ack_code = 10;        // 服务端应答码

    // ── 鉴权与路由 ──
    string session_id = 11;      // 登录会话
    uint32 device_id = 12;
    string trace_id = 13;        // 端到端 trace（可复用 client_sequence_id）
}
```

### 4.2 ★ `msg_id` 为什么必须用业务 ID 而不是 taskid

| | taskid | 业务 msg_id |
|---|---|---|
| 生成者 | Mars 客户端 | 业务层 |
| 唯一范围 | 单进程内递增，32 位会回绕 | **全局唯一**（雪花 ID / UUID / 时间戳+设备+序号） |
| 跨设备一致 | ❌ | ✅ |
| 重试时不变 | ❌ **每次重试都是新 taskid** | ✅ |
| 可做幂等键 | ❌ | ✅ |
| 服务端可识别重复 | ❌ | ✅ |

> **重试时 taskid 会变吗？**
> 会。重试是**同一个 Task 对象**重新发送，`task.taskid` 不变 —— 但**服务端视角**
> 如果做的是"记录所有 taskid"，重试会看到同一个 taskid 出现两次。
> 但如果你在客户端每次重试都新建 Task（更常见的做法），taskid 就变了。
>
> **结论：幂等键必须用业务 msg_id。**

## 5. 消息状态机

```
   用户点击发送
        │
        ▼
   ┌─────────┐
   │ sending │  ← 已入队（乐观上屏，图标"发送中"）
   └────┬────┘
        │  Req2Buf 成功 + 写入 socket
        ▼
   ┌─────────┐
   │ sent    │  ← 已发出（图标"已发送"，单勾）
   └────┬────┘
        │  收到服务端 ACK（响应包）
        ▼
   ┌────────────┐
   │ delivered  │  ← 对方已收到（双勾）
   └────┬───────┘
        │  收到已读回执
        ▼
   ┌────────┐
   │  read  │  ← 对方已读（变色双勾）
   └────────┘

   任意状态 → failed（可重试 → 回到 sending）
```

> **必须在本地持久化这个状态机**。
> App 被杀后重启，要能从数据库恢复"哪些消息还没发出去"。

## 6. 握手与鉴权

### 6.1 鉴权握手

```
1. 长连建立（TCP + TLS）
2. 客户端发送 CMD_ID_AUTH
   body: { token, device_id, device_type, client_version, app_version, push_token }
3. 服务端校验
   ├─ 成功 → 回 { session_id, server_time, push_token, config }
   └─ 失败 → 回 { err_code } （如 TOKEN_EXPIRED / DEVICE_KICKED / BANNED）
4. 客户端把 session_id 存入，后续业务包带上
```

### 6.2 `MakesureAuthed` 的实现

```java
@Override public boolean makesureAuthed(String host) {
    if (SessionManager.isLogined()) return true;
    // 触发登录流程，登录成功后 StnLogic.touchTasks() 唤醒挂起的任务
    LoginManager.startLogin();
    return false;
}
```

> ★ **返回 false 时，任务会留在队列里，每秒轮询一次**（`longlink_task_manager.cc:471-483`）。
> 登录成功后调 `StnLogic.touchTasks()` 可以立即唤醒。

### 6.3 会话失效的处理

```java
@Override public int buf2Resp(int taskid, Object userContext, int channelSelect,
                              byte[] data, int[] serverSequenceId) {
    Response resp = Response.parseFrom(data);
    serverSequenceId[0] = resp.traceId;
    switch (resp.errCode) {
        case 0:      return StnLogic.RESP_FAIL_HANDLE_NORMAL;
        case 10001:  return StnLogic.RESP_FAIL_HANDLE_SESSION_TIMEOUT;  // ★ 立即重试 + 重新鉴权
        case 10002:  return StnLogic.RESP_FAIL_HANDLE_TASK_END;         // 内容违规，不重试
        case 10003:  return StnLogic.RESP_FAIL_HANDLE_DEFAULT;         // 通用错误，可重试
        default:     return StnLogic.RESP_FAIL_HANDLE_TASK_END;
    }
}
```

> **`RESP_FAIL_HANDLE_SESSION_TIMEOUT` 是 IM 最重要的一个返回值**：
> STN 会立即重试该任务并触发重新鉴权流程
> （`longlink_task_manager.cc:829-906` 会 `__Disconnect` + `retry_interval_ = 0`）。

## 7. 消息顺序

### 7.1 Mars 不保证顺序

- 任务队列按 priority 排序 → 不同 priority 打乱顺序
- 响应按 taskid 匹配 → 乱序响应完全正常

### 7.2 业务层保证顺序的做法

| 方案 | 说明 |
|---|---|
| **客户端递增序号** | 每条消息带 `client_seq`（会话内递增），接收端按 seq 排序 |
| **串行发送** | 同一会话的消息用队列串行化（一个 in-flight） |
| **服务端排序** | 服务端按 `server_time` + `msg_id` 排序后下发 |

> **推荐组合**：
> - **发送侧**：同一会话串行发送（最多 N 个 in-flight，N=3~5）
> - **接收侧**：用 `client_seq` 做"乱序到达"的检测和重排缓冲

### 7.3 串行发送的实现

```java
class ConvSender {
    private final Deque<Message> queue = new ArrayDeque<>();
    private int inFlight = 0;
    private static final int MAX_INFLIGHT = 3;

    void send(Message m) {
        queue.add(m);
        pump();
    }
    private void pump() {
        while (inFlight < MAX_INFLIGHT && !queue.isEmpty()) {
            Message m = queue.poll();
            inFlight++;
            mars.send(m, () -> {          // onTaskEnd
                inFlight--;
                pump();
            });
        }
    }
}
```

> **注意**：不要完全串行（in-flight=1），那会让 RTT 成为吞吐瓶颈。
> **滑动窗口（3~5）** 是平衡点。

## 9. 服务端设计要求

### 9.1 协议层

- [ ] **帧解码器**（`LengthFieldBasedFrameDecoder` 或自写）
- [ ] `client_version` 三端一致，且支持多版本共存
- [ ] 回包原样回显 `cmdid` + `seq`
- [ ] **心跳（cmdid=6）回包 seq = 0xFFFFFFFF，body 可空**
- [ ] **推送（push）seq = 0**
- [ ] 解包失败也要回错误帧
- [ ] body ≤ 1MiB

### 9.2 业务层

- [ ] **鉴权**：`CMD_ID_AUTH` 校验 token
- [ ] **会话管理**：session_id ↔ 连接 ↔ 用户
- [ ] **幂等去重**：按 `msg_id` 去重（Redis SETNX / 本地 LRU）
- [ ] **消息持久化**：先落库再投递
- [ ] **离线消息**：用户不在线时存队列，上线时推送
- [ ] **多端同步**：同一账号多端登录，消息同步
- [ ] **推送路由**：按 user_id 找到在线连接
- [ ] **背压**：慢客户端限速
- [ ] **连接数限流 + 退避拒绝**

### 9.3 运维层

- [ ] 连接建立监控（成功率/耗时）
- [ ] 消息延迟监控（P50/P90/P99）
- [ ] 失败归因分布（`GetFailStep`）
- [ ] 心跳失败率
- [ ] 雪崩拦截数

## 11. 与其他 IM 方案的对比

| 方案 | 优点 | 缺点 | 适用 |
|---|---|---|---|
| **Mars STN** | 生产级、微信验证过、全套容灾 | C++、学习成本高、协议要自己定 | 大型 IM、需要精细控制 |
| **OkHttp + WebSocket** | 简单、Java 原生 | 没有任务队列/退避/雪崩/弱网识别 | 中小型 IM |
| **Netty** | 服务端首选 | 客户端要自己写很多 | 服务端 |
| **MQTT** | 协议标准、Broker 成熟 | 要额外部署 Broker | IoT / 简单推送 |
| **自研 UDP/QUIC** | 可控 | 成本极高 | 特殊场景 |
| **gRPC / HTTP2** | 多路复用、标准 | 长连接保活要自己做 | RPC 场景 |

> **面试话术**：
> "我们用 Mars STN 而不是 WebSocket，核心原因是**它把'网络不可靠'这件事完全内化了**：
> 任务排队与优先级、多 IP 竞速建连、自适应重连退避、动态超时、雪崩防护、
> 弱网识别、流量与频次控制 —— 这些在 WebSocket 上都要自己重写一遍，
> 而且很容易漏掉边界情况。代价是要吃透它的 Task/Callback 模型和协议约束。"

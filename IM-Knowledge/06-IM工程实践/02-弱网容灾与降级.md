## 2. 弱网的三种表现与对策

| 表现 | 检测方式 | Mars 的应对 | 业务层应对 |
|---|---|---|---|
| **高延迟** | RTT > 阈值 | `WeakNetworkLogic` 判定弱网 → 放宽超时 | 提示用户、降低发送频率 |
| **丢包** | 心跳失败、首包超时 | 心跳超时断链重建；任务超时重试 | 消息本地重试队列 |
| **首选 IP 不通** | `ip_index > 0` | 多 IP 竞速自动绕开 | 提示"网络不稳定" |
| **NAT 超时（假死）** | 心跳超时 | 8 秒超时断链；UDP 信令保活维持映射 | — |
| **DNS 慢/失败** | `conn_profile.dns_time` | BackupIP 兜底、DebugIP | 预热 DNS |

## 3. 降级策略设计

### 3.1 降级层级

```
Level 0  ★ 正常
    长连 + 短连都可用，所有消息走长连

Level 1  长连可用但不稳定（RTT 高 / 频繁重连）
    → 消息仍走长连，但：
    · 降低发送频率（合并消息）
    · 大文件改走短连
    · 提示用户"网络较差"

Level 2  长连不可用（连接中 / 重连退避中）
    → 消息：
    · 小消息：留在长连队列等待（kChannelLong）
    · 或降级到短连（kChannelBoth / 显式切换）
    · 大文件：走短连

Level 3  完全无网
    → 消息进本地队列，标记"待发送"
    → 网络恢复后按序重发

Level 4  服务端故障（雪崩拦截）
    → 不重试，等冷却
    → 提示"服务繁忙"
```

### 3.2 如何感知当前处于哪一级

| 信号 | 来源 |
|---|---|
| 连接状态 | `Callback::ReportConnectStatus(status, longlinkStatus)` |
| 长连状态变化 | `Callback::OnLongLinkStatusChange(status)` |
| 是否弱网 | `WeakNetworkLogic::IsCurrentNetworkWeak()`（C++）/ 上层自研（Java） |
| 任务失败原因 | `OnTaskEnd` 的 `errType/errCode` |
| 限流命中 | `Callback::ReportTaskLimited(checkType, task, param)` |

> ★ **上层不要自己维护 `isConnected` 布尔值** ——
> 必须用 `ReportConnectStatus` 驱动，否则必然和真实状态不同步。

## 4. 降级到短连的正确做法

### 4.1 不要用 `kChannelBoth` 的自动降级

理由（见 `01-STN框架/02-任务生命周期与状态机.md` §2）：
- 降级发生在"选路时刻"，行为不可预测
- 长连恢复后，任务不会自动回到长连

### 4.2 推荐：显式决策

```java
void sendMessage(Message m) {
    int channel = mars.isLongLinkHealthy() ? StnLogic.Task.ELong
                                            : StnLogic.Task.EShort;
    // ★ isLongLinkHealthy 由 ReportConnectStatus 驱动
    mars.startTask(buildTask(m, channel));
}
```

### 4.3 降级时的协议差异

**长短连的协议是同一套吗？**

| | 长连接 | 短连接 |
|---|---|---|
| 帧格式 | Mars 20B 头 + body | HTTP/1.1 POST |
| cmdid | 有 | **没有** |
| 路由 | 服务端按 cmdid 路由 | 服务端按 CGI path 路由 |
| 鉴权 | body 里带 session_id | HTTP Header 带 token |
| 推送 | 有 | 无 |

> ★ **所以降级到短连需要服务端同时暴露 HTTP 接口**。
> 真实 IM 通常这样设计：
> ```
> 长连接：cmdid = CMD_ID_SEND_MESSAGE，body = SendMessageRequest
> 短连接：POST /cgi/sendmessage，body = 同一个 SendMessageRequest
> ```
> **业务 payload 完全复用**，只是外层信封不同。

## 5. 消息可靠性保障

### 5.1 三层保障

```
┌─ 第 3 层：服务端持久化 ────────────────────────────┐
│  服务端收到 → 落库 → 返回 ACK                       │
│  （客户端收到 ACK 才认为"已送达"）                    │
├─ 第 2 层：客户端本地队列 ───────────────────────────┤
│  发送失败 → 落本地库（状态 sending）→ 定时/网络恢复重试 │
├─ 第 1 层：Mars 的任务重试 ──────────────────────────┤
│  retry_count=1，1 秒间隔重试（指数退避可自己加）        │
└─────────────────────────────────────────────────────┘
```

### 5.2 为什么不能只靠 Mars 的重试

| 问题 | 说明 |
|---|---|
| **App 被杀** | 进程死了，任务队列就没了 |
| **重试次数有限** | 默认只重试 1 次 |
| **不区分错误类型** | 服务端返回"内容违规"也会重试（浪费） |
| **无持久化** | 进程重启后丢失 |

> **必须自己做本地队列。**

### 5.3 本地队列设计

```java
// 消息表
CREATE TABLE message (
    msg_id      TEXT PRIMARY KEY,   -- 业务唯一 ID（幂等键）
    conv_id     TEXT,
    sender      INTEGER,
    payload     BLOB,
    client_seq  INTEGER,           -- 会话内递增（排序用）
    client_time INTEGER,
    status      INTEGER,           -- 0=sending 1=sent 2=delivered 3=read 4=failed
    retry_count INTEGER DEFAULT 0,
    next_retry_time INTEGER DEFAULT 0
);
CREATE INDEX idx_msg_status ON message(status, next_retry_time);
```

```
发送流程：
  1. 写库（status=sending）
  2. 乐观上屏
  3. 调 mars.startTask
  4. onTaskEnd:
     成功 → 更新 status=sent，记录 server_time
     失败 → retry_count++，算 next_retry_time，更新 status
  5. 定时器扫 status in (sending, failed) and next_retry_time <= now → 重发
  6. 网络恢复事件 → 立即扫一遍重发
```

### 5.4 重试退避（业务层）

```java
long calcNextRetry(int retryCount) {
    long base = 5_000;                          // 5 秒
    long max  = 5 * 60_000;                     // 5 分钟
    long delay = Math.min(base * (1L << Math.min(retryCount, 6)), max);
    long jitter = ThreadLocalRandom.current().nextLong(0, 1000);  // 抖动
    return delay + jitter;
}
```

> ★ **必须有抖动** —— 否则大量客户端同时失败、同时重试 → 惊群。

## 6. 雪崩防护的理解

### 6.1 防的是什么

> **服务端出故障时，客户端全部疯狂重试 → 重试流量压垮本已故障的服务端 → 故障扩大。**

这是典型的**重试风暴（retry storm）**。

### 6.2 Mars 的两个机制

| 机制 | 位置 | 作用 |
|---|---|---|
| `AntiAvalanche` | `anti_avalanche.h/.cc` | 按 cmdid/user 统计失败次数，超阈值直接拒绝 |
| `FrequencyLimit` | `frequency_limit.cc` | 频率限制 |
| `FlowLimit` | `flow_limit.cc` | 流量漏斗 |
| `TaskIntercept` | `task_intercept.cc` | 命中时走伪回包，不发网络 |

### 6.3 上层必须配合

```java
@Override public void reportTaskLimited(int checkType, Task task, int[] param) {
    // checkType: 1 = kFrequencyLimit, 2 = kFlowLimit
    showToast("网络繁忙，请稍后重试");
    // ★ 不要立即重试！把 next_retry_time 往后推
}
```

> **不实现 `ReportTaskLimited` 的后果**：
> 用户看到"发送失败"，不知道为什么，也不知道要等多久 → 反复点击 → 加重负担。

## 7. 服务端侧的容灾

### 7.1 客户端保护服务端

| 机制 | 位置 |
|---|---|
| 重连退避（最多 10 分钟） | `longlink_connect_monitor.cc` |
| 随机抖动 | `__Interval` 里的 `rand() % 20` |
| 雪崩拦截 | `anti_avalanche.cc` |
| 频次/流量限制 | `frequency_limit.cc` / `flow_limit.cc` |

### 7.2 服务端保护自己

| 机制 | 建议 |
|---|---|
| **连接数上限** | 单用户 / 单 IP / 全局三级 |
| **拒绝要快** | 超限时**立即关闭**而不是拖住（拖住会占资源） |
| **退避拒绝** | 对同一 IP 的频繁连接请求，间隔限制 |
| **优雅关闭** | 服务端要下线时，发一个"即将重启"的帧，让客户端退避 |
| **过载保护** | 消息队列积压时主动拒绝新消息（返回明确的 errcode，让客户端知道是"稍后重试"而不是"失败"） |

> **关键**：服务端返回的错误码要**区分"永久失败"和"临时失败"**。
> 客户端才能正确决定是否重试。

## 8. 弱网场景的专项优化

### 8.1 消息合并（batching）

弱网时不要一条消息一个包，攒 3~5 条合并成一个（protobuf 数组）。

```java
// 弱网时启用聚合
if (mars.isWeakNetwork() && pendingMessages.size() < 5) {
    pendingMessages.add(m);
    scheduleFlush(200);     // 200ms 后发
    return;
}
```

> **代价**：单条消息延迟增加 200ms。**弱网时这个交易是划算的**（网络开销远大于 200ms）。

### 8.2 消息压缩

| 方案 | 效果 |
|---|---|
| protobuf 本身紧凑 | 已经省掉了很多 JSON 的冗余 |
| 文本消息 gzip | 对长文本有效（> 1KB 时收益才明显） |
| **不要压缩小包** | 压缩 + 延迟可能得不偿失 |

> **开源版 Mars 帧层没有压缩** —— 要压缩得自己实现（在 `Req2Buf` 里压，或替换 `LongLinkEncoder`）。

### 8.3 大文件单独走短连

- 长连带宽被大文件占满 → 聊天消息延迟飙升
- **大文件走短连（甚至专门的 CDN）**，长连只传控制消息

## 9. 容灾演练清单

| 场景 | 演练方式 | 期望表现 |
|---|---|---|
| **服务端进程重启** | kill 服务端 | 客户端 30 秒内自动重连，消息自动重发 |
| **服务端只回错误帧** | 改服务端逻辑 | 客户端收到明确 errcode，不无限重试 |
| **DNS 不可用** | 改 resolv.conf | 走 BackupIP 或明确失败提示 |
| **网络断开** | 飞行模式 | 消息进本地队列，提示"网络不可用" |
| **网络切换** | WiFi ↔ 4G | 立即重连，消息不丢（`retry_count >= 1`） |
| **弱网** | tc netem 限速 | 超时放宽，失败率可接受 |
| **服务端限流** | 人为限速 | 客户端提示"网络繁忙"，不无限重试 |
| **App 被杀** | 划掉 App | 重启后从本地队列恢复发送 |
| **版本不一致** | 改 client_version | 明确失败，不是无限重连 |

## 10. 一句话总结

> **Mars 的容灾哲学是"客户端永远不放弃，但也永远不失控"**：
> - 不放弃：重连退避 + 心跳保活 + UDP 信令 + 多 IP 竞速 + 任务重试
> - 不失控：随机抖动 + 阶梯退避 + 雪崩防护 + 频次流量限制 + 弱网降级
>
> **这是 IM 客户端最核心的工程能力**，也是面试中最能体现深度的部分。

# 05 · 性能优化与监控

---

## 1. 性能预算

### 1.1 端到端延迟分解

```
用户点击发送
   │  0~50ms    UI 交互 + 乐观上屏
   ├─ 0~1000ms  ★ 等待 STN 1 秒 tick 调度（首条消息最坏 1 秒）
   │  <1ms       Req2Buf 编码
   │  <1ms       写入 socket（writev）
   │  RTT        网络往返（WiFi 20~80ms，4G 50~200ms）
   │  <1ms       Buf2Resp 解码
   │  0~50ms    切主线程 + UI 刷新
   ▼
用户看到"已发送"
```

**关键预算**：

| 环节 | 预算 | 说明 |
|---|---|---|
| **STN tick 延迟** | **0~1000ms** | ★ **最大的可控项** |
| Req2Buf | < 1ms | 纯内存操作 |
| RTT | 20~200ms | 物理限制 |
| Buf2Resp | < 1ms | 纯内存操作 |
| UI 刷新 | < 16ms | 一帧 |

### 1.2 ★ 如何优化 STN tick 延迟

`DEF_TASK_RUN_LOOP_TIMING = 1 * 1000`（`mars/stn/config.h:31`）。

| 方案 | 效果 | 代价 |
|---|---|---|
| **改小常量**（如 100ms） | tick 延迟降到 0~100ms | CPU 唤醒频率 ×10 |
| **首次任务立即触发** | ★ 首条消息几乎无延迟 | 改 Mars 源码 |
| **消息聚合** | 多条消息合并成一帧 | 单条延迟 +batch 窗口 |
| **主动 push 唤醒** | 长连线程收到 push 时触发 `__RunLoop` | 改 Mars 源码 |

> **最实用的是"消息聚合"**：
> 用户连发 5 条消息时，攒 200ms 打包成一个请求发出去。
> **吞吐提升 5 倍，首条延迟只多 200ms** —— 在 IM 里这个交易非常划算。

## 2. 性能优化手段

### 2.1 协议层

| 手段 | 说明 | 收益 |
|---|---|---|
| **protobuf-lite** | 替代 full protobuf | 体积 ↓ 序列化快 |
| **紧凑字段编号** | 1~15 用 1 字节 | 体积 ↓ |
| **不传空字段** | proto3 默认行为 | 体积 ↓ |
| **批量发送** | 多条消息一个包 | **吞吐 ↑↑** |
| **文本压缩** | 长文本 gzip | 体积 ↓ 50%+ |
| **去掉冗余字段** | 时间戳用相对值 | 体积 ↓ |

### 2.2 编码器层（Mars）

| 手段 | 说明 |
|---|---|
| **TCP_NODELAY** | 已默认开启（长连） |
| **writev 批量写** | 已默认（`longlink.cc:905-927`） |
| **AutoBuffer 零拷贝** | 已默认 |
| **SO_SNDBUF 预留** | ⚠️ 工具函数存在但无调用点，可自己加 |
| **MSM 1400** | 已默认（Wi-Fi） |

### 2.3 线程层

| 风险 | 后果 | 对策 |
|---|---|---|
| **`Req2Buf` 阻塞** | 整条 STN 队列卡住 | 预编码 |
| **`Buf2Resp` 阻塞** | 同上 | 纯反序列化 |
| **`OnPush` 阻塞** | ★ 整条长连接卡住 | 立刻返回 + 投递业务线程 |
| **UI 线程做 IO** | ANR | 全部下沉 |
| **日志过多** | IO 抢占 | 降级别 |

> ★ **`OnPush` 在 LongLink I/O 线程上** ——
> 这是最容易出事的回调。业务在这里做 DB 写入 = **整个长连接的收发全停**。

### 2.4 资源层

| 风险 | 后果 | 对策 |
|---|---|---|
| **`TASK_ID_TO_WRAPPER` 不清理** | 内存泄漏 | `onTaskEnd` 里 remove |
| **消息不落库** | 内存无限增长 | 持久化 + 分页 |
| **AutoBuffer 不复用** | GC 压力 | 对象池 |
| **日志不轮转** | 磁盘满 | 配 `max_file_size` + `max_alive_duration` |
| **AIDL 序列化** | CPU 浪费 | 独立进程方案的固有成本 |

### 2.5 服务端

| 手段 | 说明 |
|---|---|
| **异步 IO（Netty）** | 避免阻塞 EventLoop（★ sample 踩了这个坑） |
| **业务逻辑丢线程池** | 不在 EventLoop 上做重活 |
| **批量写** | 聚合多个客户端的响应 |
| **连接池 / 内存缓存** | 会话、在线状态 |
| **背压** | 慢客户端限速 |
| **分库分表** | 消息存储 |

## 3. 监控体系

### 3.1 四层指标

```
┌─ L4 业务指标 ────────────────────────────────────┐
│  消息端到端延迟 P50/P90/P99                       │
│  消息发送成功率 / 失败率（按 errCode 分类）         │
│  在线用户数 / 长连数                               │
├─ L3 STN 指标（Mars 提供）─────────────────────────┤
│  长连建立成功率 / 平均耗时                         │
│  首选 IP 命中率                                    │
│  心跳失败率                                        │
│  重连间隔分布                                       │
│  失败归因分布（GetFailStep）                        │
│  任务画像（CgiProfile 时间线）                      │
├─ L2 连接指标（Mars 提供）─────────────────────────┤
│  DNS 耗时 / 成功率                                  │
│  TCP 握手耗时 / RTT                                │
│  命中 IP 分布                                       │
├─ L1 原始日志（Xlog）───────────────────────────────┤
│  STN 内部日志 + 业务日志                             │
└───────────────────────────────────────────────────┘
```

### 3.2 必接的回调

| 回调 | 数据 | 优先级 |
|---|---|---|
| `ReportTaskProfile` | 任务时间线 → 端到端延迟 | ★★★ |
| `ReportConnectStatus` | 连接状态 → 掉线率 | ★★★ |
| `ReportTaskLimited` | 限流 → 服务端过载信号 | ★★★ |
| `ReportDnsProfile` | DNS 画像 | ★★ |
| `TrafficData` | 流量 | ★★ |
| `OnLongLinkStatusChange` | 长连状态迁移 | ★★ |

### 3.3 核心指标定义

```sql
-- 消息端到端延迟
SELECT percentile_cont(0.99) WITHIN GROUP (ORDER BY latency_ms)
FROM task_profile
WHERE cmd_id = 3 AND err_type = 0 AND ts > now() - interval '5 minutes';

-- 长连建立成功率
SELECT count(*) FILTER (WHERE success) * 1.0 / count(*)
FROM connect_profile
WHERE ts > now() - interval '5 minutes';

-- 失败归因分布
SELECT fail_step, count(*)
FROM task_profile
WHERE err_type != 0 AND ts > now() - interval '10 minutes'
GROUP BY fail_step;

-- 重连间隔分布
SELECT percentile_cont(0.5), percentile_cont(0.9)
FROM (SELECT interval_s FROM reconnect_log WHERE ts > now() - interval '1 hour');
```

### 3.4 告警规则

| 告警 | 阈值 | 排查方向 |
|---|---|---|
| 长连建立成功率 < 90% | 5min | 网络 / 服务端 |
| 消息端到端 P99 > 3s | 5min | 服务端慢 / 排队 |
| 消息失败率 > 5% | 5min | 服务端错误 / 版本不兼容 |
| 心跳失败率 > 10% | 10min | 链路质量 |
| 首包超时占比 > 20% | 10min | 服务端处理慢 |
| 雪崩拦截数突增 | 5min | 服务端故障 |
| 重连间隔 P50 > 60s | 30min | 弱网用户占比高 |
| 首选 IP 命中率 < 80% | 1h | DNS / 机房问题 |
| 消息 sending 状态停留 > 1min | 10min | 客户端卡住 / 重试失效 |

## 4. 压测方案

### 4.1 客户端压测（验证 Mars 侧）

| 场景 | 方法 |
|---|---|
| **大量消息** | 脚本模拟 1000 msg/s，观察 STN 队列长度、`__RunLoop` 间隔 |
| **大消息** | 发 900KB 的消息，验证接近 1MiB 限制时的表现 |
| **弱网** | `tc netem` 限速 / 丢包 / 延迟 |
| **切网** | 脚本切换网络接口 |
| **内存** | 长时间运行观察 RSS（找泄漏） |
| **CPU** | 观察 `Req2Buf`/`Buf2Resp` 的耗时占比 |

### 4.2 服务端压测（sample 提供的工具）

`samples/Server/server/src/main/java/com/tencent/mars/webserver/HelloCgi.java`：

> 支持 `"64KB"/"128KB"` 文本返回等量随机 dump，**用于压测大包**。

`CMD_ID_HELLO2 = 8` → `/mars/hello2`。

### 4.3 压测客户端

`samples/Server/server/src/test/java/com/tencent/mars/proxy/EchoCgiTest.java:63-81`：
Netty 客户端直连 8081 发 hello，可作为压测客户端的起点。

> **注意**：sample server **没有帧解码器**，压测时会丢帧 ——
> 必须先修好（加 `LengthFieldBasedFrameDecoder`）再压测，否则数据不可信。

## 5. 性能优化的优先级

| 优先级 | 优化项 | 理由 |
|---|---|---|
| **P0** | `OnPush` 不阻塞 | 一行改动，避免整条长连接卡死 |
| **P0** | `Req2Buf`/`Buf2Resp` 不阻塞 | 避免 STN 队列卡住 |
| **P0** | 清理 taskid 映射 | 避免内存泄漏 |
| **P1** | 消息聚合 | 吞吐提升最大 |
| **P1** | 降低日志级别 | 减少 IO |
| **P2** | 减小 STN tick | 影响 CPU 唤醒频率 |
| **P2** | protobuf 字段优化 | 收益有限 |
| **P3** | AutoBuffer 池化 | 收益有限（GC 压力不大时） |

## 6. 一个真实的性能案例（参考思路）

**场景**：IM 消息发送，弱网（4G，RTT 200ms，丢包 2%）。

**问题**：单条消息 P99 延迟 2.5 秒。

**分析**（用 `CgiProfile` 时间线拆解）：

| 阶段 | 耗时 |
|---|---|
| 排队等 tick | 0~1000ms（平均 500ms）★ |
| 编码 | 0.5ms |
| 网络 RTT | 200ms |
| **首次失败重试** | 200ms + 1s 退避 ★★ |
| 二次成功 | 200ms |

→ 发现 **重试占了 1.2 秒**。

**优化**：
1. **减小 tick**（1s → 200ms）→ 省 400ms
2. **区分错误类型**：网络错误立即重试（不隔 1 秒）→ 省 1 秒
3. **消息聚合** → 批量发送，吞吐翻倍

**结果**：P99 从 2.5s → 700ms。

> **方法论**：
> **先用 `CgiProfile` 把延迟拆到阶段，再针对性优化。**
> 不要凭感觉优化。

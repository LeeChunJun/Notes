# 03 · 可靠性：重试、幂等与顺序

---

## 1. 三个核心问题

| 问题 | 本质 | 解法 |
|---|---|---|
| **重试** | 网络会失败，失败了怎么办 | 退避重试 + 本地持久化队列 |
| **幂等** | 重试会不会导致重复发送 | 业务级唯一 ID + 服务端去重 |
| **顺序** | 消息会不会乱序到达 | 客户端序号 + 服务端排序 + 滑动窗口 |

---

## 2. 重试

### 2.1 三层重试

```
┌─ Layer 1：Mars 任务重试（进程内）────────────────────────┐
│  Task.retry_count（默认 1）                                │
│  重试间隔：DEF_TASK_RETRY_INTERNAL = 1 秒                  │
│  批量错误后统一 1 秒（避免惊群）                            │
└───────────────────────────────────────────────────────────┘
┌─ Layer 2：业务本地队列重试（持久化）───────────────────────┐
│  进程被杀也不丢                                            │
│  指数退避 + 抖动                                            │
│  按错误类型决定是否重试                                     │
└───────────────────────────────────────────────────────────┘
┌─ Layer 3：服务端重试（幂等去重后）─────────────────────────┐
│  服务端内部重试下游（DB/缓存）                              │
└───────────────────────────────────────────────────────────┘
```

### 2.2 `retry_count` 的语义

`mars/stn/config.h:29`：
```cpp
#define DEF_TASK_RETRY_COUNT (1)
```

`Task::retry_count` 默认 `-1` → 实际是 **1** → **总共尝试 2 次**（1 次原始 + 1 次重试）。

| 设置 | 效果 |
|---|---|
| `-1`（默认） | 尝试 2 次 |
| `0` | 只尝试 1 次，失败即结束 |
| `1` | 尝试 2 次 |
| `2` | 尝试 3 次 |
| `> 30` | 视为非法参数（`net_core.cc:259`） |

### 2.3 终止判定

`shortlink_task_manager.cc:1131-1132` / `longlink_task_manager.cc:696-697`：

```cpp
if (_it->force_no_retry || 0 >= _it->remain_retry_count || kEctOK == _err_type
    || kTaskFailHandleTaskEnd == _fail_handle
    || kTaskFailHandleTaskTimeout == _fail_handle) {
    // → 结束
}
```

**四种不重试的情况**：
1. `force_no_retry`（内部标记）
2. `remain_retry_count` 耗尽
3. 成功
4. `Buf2Resp` 返回了 `kTaskFailHandleTaskEnd(-14)` 或 `kTaskFailHandleTaskTimeout(-15)`

> ★ **第 4 条是业务能控制的** ——
> **在 `Buf2Resp` 里返回 `-14` 可以明确表示"这个错误重试也没用，别浪费"**。

### 2.4 重试门控

`longlink_task_manager.cc:431-443`：

```cpp
bool canretry = curtime - lastbatcherrortime_ >= retry_interval_;
if (first->task.retry_count > first->remain_retry_count && !canretry) {
    // 不满足重试条件 → 跳过
}
```

`retry_interval_` 在**批量错误**时被设为 1 秒（`longlink_task_manager.cc:829-906`），
在**会话超时**时被设为 0（立即允许重试）。

### 2.5 哪些错误该重试

| 错误 | 该重试？ | 理由 |
|---|---|---|
| 网络断开、socket 错误 | ✅ | 瞬时故障 |
| DNS 错误 | ✅ | 瞬时（但要配合 BackupIP） |
| 首包/包间超时 | ✅ | 可能是服务端慢 |
| 服务端 5xx | ✅ | 服务端问题 |
| 服务端 4xx（参数错） | ❌ | 重试也没用 |
| 内容违规 | ❌ | 重试会重复触发风控 |
| 账号被封 | ❌ | 重试是骚扰 |
| 会话失效 | ✅ **用 `-13`** | 会自动触发重新鉴权 |
| 客户端编码失败 | ❌ | 本地 bug |
| 雪崩拦截 | ❌ **要等冷却** | 重试会加剧雪崩 |

## 3. 幂等

### 3.1 为什么必须幂等

重试场景：

```
客户端发送 msg_id=12345
  → 网络抖动，服务端可能已经处理了，但 ACK 丢了
  → 客户端 1 秒后重试 msg_id=12345
  → 服务端如果不去重 → 用户收到两条一样的消息
```

### 3.2 幂等键的选择

| 候选 | 唯一性 | 重试时是否变 | 结论 |
|---|---|---|---|
| `taskid` | 单进程内唯一，32 位会回绕 | 同 Task 重试不变；新 Task 会变 | ❌ 不可靠 |
| `client_sequence_id` | 16 位，短窗口内会重复 | 首次编码时生成，重试不变 | ⚠️ 只能做短窗口对账 |
| **业务 `msg_id`** | **全局唯一** | **永远不变** | ✅ **正确选择** |

> ★ **服务端必须按 `msg_id` 去重。**

### 3.3 服务端去重实现

```
去重键：user_id + msg_id
TTL：消息有效期（通常 24h~7d）

方案 A：Redis SETNX
    SETNX dedup:{user_id}:{msg_id} 1 EX 86400
    返回 0 → 已处理过 → 直接返回上次的结果（幂等返回）

方案 B：本地 LRU + 定时清理（单机部署）
    ConcurrentHashMap<String, Long> dedup

方案 C：DB 唯一索引
    UNIQUE KEY (user_id, msg_id)
```

> ★ **幂等返回很重要**：重复请求要返回**和第一次一样的响应**，而不是报错。
> 否则客户端会以为失败而继续重试。

### 3.4 客户端的幂等职责

| 事项 | 做法 |
|---|---|
| **msg_id 生成** | 服务端下发或客户端用雪花 ID（保证不重复） |
| **本地去重** | 收到 push 时按 msg_id 检查本地是否已有 |
| **重发不换 id** | ★ 重试时 msg_id 必须保持不变 |

### 3.5 群聊的特殊性

群聊里"消息已读"是**按成员记录**的，需要额外的幂等：

```
read_receipt 表：(conv_id, msg_id, user_id) UNIQUE
```

## 4. 顺序

### 4.1 Mars 不保证顺序

| 环节 | 是否保序 |
|---|---|
| 任务入队 | ❌ 按 priority 排序，不同 priority 会乱 |
| 同 priority 入队 | ✅ 稳定排序，FIFO |
| TCP 传输 | ✅ 字节流有序 |
| 响应匹配 | ✅ 按 taskid 精确匹配，**允许乱序响应** |
| 客户端处理 | ❌ 取决于业务 |

### 4.2 顺序被破坏的两个地方

**① 优先级排序**

```cpp
lst_cmd_.push_back(task);
lst_cmd_.sort(__CompareTask);      // 按 priority
```

**不同 priority 的任务会被重排**。

**② 发送后重试**

```
t=0    发送 msg_A（网络慢，丢包）
t=1s   重试 msg_A
t=1.2s 服务端收到 msg_A
t=1.5s 发送 msg_B（正常）
t=1.6s 服务端收到 msg_B
```
→ 服务端看到 B 在 A 之后，但 A 是后到的。

### 4.3 业务层保证顺序的三种方案

#### 方案 A：客户端序号 + 重排缓冲（推荐）

```protobuf
message Envelope {
    uint64 conv_id = 1;
    uint32 client_seq = 2;      // ★ 会话内单调递增
    ...
}
```

接收端：
```java
class ReorderBuffer {
    private long expectedSeq;
    private TreeMap<Long, Message> pending;

    void offer(Message m) {
        pending.put(m.clientSeq, m);
        while (pending.containsKey(expectedSeq)) {
            deliver(pending.remove(expectedSeq));
            expectedSeq++;
        }
    }
}
```

> **代价**：一条消息丢了会导致后续全部卡住 → 需要**超时跳过**机制。

#### 方案 B：串行发送（滑动窗口 = 1）

最简单、最可靠，但吞吐受 RTT 限制。

```java
// 只允许一个 in-flight
if (inFlight > 0) { queue.add(m); return; }
```

**RTT 200ms 时，吞吐上限 5 msg/s** —— 对 IM 来说通常够用，但群聊爆发时不够。

#### 方案 C：服务端排序（最可靠）

服务端收到消息后按 `(client_time, client_seq, server_seq)` 排序后再下发。
客户端不需要处理乱序。

> **推荐组合**：
> - **发送侧**：滑动窗口 3~5（吞吐 + 顺序的平衡）
> - **接收侧**：轻量重排缓冲 + 超时跳过
> - **服务端**：按 server_seq 兜底排序

### 4.4 优先级与顺序的冲突

> **同一会话内的消息必须用同一 priority。**
>
> 如果要区分"VIP 消息"和"普通消息"，接受乱序 —— 反正 VIP 消息本来就该插队。
> 但**普通消息之间必须同优先级**。

## 5. 端到端的消息状态追踪

### 5.1 状态机（客户端）

```
        ┌──────────┐
        │ CREATED  │  本地创建
        └────┬─────┘
             │ 调 startTask
             ▼
        ┌──────────┐
        │ SENDING  │  已入队
        └────┬─────┘
             │ Req2Buf 成功 + 写入 socket
             ▼
        ┌──────────┐
        │  SENT    │  已发出
        └────┬─────┘
             │ 收到服务端 ACK
             ▼
        ┌────────────┐
        │ DELIVERED  │  对方已收到
        └────┬───────┘
             │ 收到已读回执
             ▼
        ┌──────────┐
        │   READ   │  对方已读
        └──────────┘

   任意状态 ──失败──► FAILED ──可重试──► SENDING
                          └──不可重试──► FAILED（展示感叹号）
```

### 5.2 状态回传

服务端需要在响应里回传足够的信息让客户端更新状态：

```protobuf
message SendMessageResponse {
    uint64 msg_id = 1;
    uint64 server_seq = 2;      // 服务端排序号
    uint64 server_time = 3;     // 服务端时间
    uint32 err_code = 4;
}
```

### 5.3 多端同步

同一账号在多端登录：

| 场景 | 处理 |
|---|---|
| A 端发送，B 端收到 | 服务端把消息同时推给所有在线端 |
| A 端已读，B 端同步 | 已读回执广播给所有端 |
| A 端发送中，B 端也发 | 各自的 msg_id 独立，靠服务端排序 |
| 端级 seq 冲突 | 用 `(device_id, client_seq)` 或直接用服务端 `server_seq` |

> **建议**：客户端展示顺序**以服务端 `server_seq` 为准**，
> 客户端 `client_seq` 只用于"发送中的乐观消息"排序和本地重排。

## 6. 消息去重（接收侧）

服务端可能因为网络重传或服务端自身重试而推送重复消息。

```java
// 客户端：按 msg_id 去重
private final LruCache<String, Boolean> receivedIds = LruCache.create(1000);

void onPush(int cmdid, int taskid, byte[] data) {
    MessagePush push = MessagePush.parseFrom(data);
    for (Message m : push.messages) {
        if (receivedIds.get(m.msgId) != null) continue;   // ★ 已收到，跳过
        receivedIds.put(m.msgId, true);
        deliver(m);
    }
}
```

> **服务端也要去重**（推给多个端时，一个端失败重推会导致该端收到两次）。

## 7. 检查清单

### 客户端

- [ ] msg_id 全局唯一（雪花/UUID/服务端下发）
- [ ] 重试时 msg_id 不变
- [ ] 本地持久化消息 + 状态机
- [ ] 接收侧按 msg_id 去重
- [ ] 会话内同优先级
- [ ] 滑动窗口控制 in-flight
- [ ] 重试退避 + 抖动
- [ ] 按错误类型决定是否重试

### 服务端

- [ ] 按 `(user_id, msg_id)` 去重
- [ ] **幂等返回**（返回和第一次一样的响应）
- [ ] 消息持久化
- [ ] 服务端排序号 `server_seq`
- [ ] 多端广播 + 去重
- [ ] 离线消息队列

### 监控

- [ ] 重试次数分布
- [ ] 幂等命中率（重复请求被拦截的比例）
- [ ] 乱序消息比例（客户端 seq 跳变）
- [ ] 消息各状态停留时长（sending 卡住的比例）

## 2. 三种"保活"机制（最容易混）

这是面试高频混淆点，三者完全不同：

| | **心跳 Noop** | **UDP 信令保活** | **TCP Keepalive** |
|---|---|---|---|
| 传输 | TCP 长连（同 socket） | **独立 UDP socket** | TCP 协议栈 |
| cmdid | **6** | **243** | 无（协议层） |
| seq | `0xFFFFFFFF` | UDP 路径 = 0 | — |
| 间隔 | **3.5 ~ 10 分钟**（自适应） | **固定 5 秒** | 系统默认 2 小时 |
| 目的 | 探测链路存活、测 RTT | 穿透 NAT、保持 NAT 映射、探跨网可达 | 探测 TCP 连接是否还在 |
| 超时后果 | **8 秒不回 → 断链重连** | 20 秒无流量则停止保活 | 无感 |
| Mars 是否启用 | ✅ | ✅ | ❌ **全仓无 SO_KEEPALIVE** |

> **结论**：Mars 完全不依赖 TCP Keepalive，链路存活判断 100% 在应用层。

另有一个易混项：**信令校验（IdentifyChecker）**
- 不是保活，是**长连建立后的一次性身份握手**（`seq = 0xFFFFFFFE`）。
- 它**复用**了心跳的发送通道：`LongLink::__NoopReq` 里优先发校验包（`longlink.cc:364-368`）。
- 目的：让服务端确认"这条连接确实是合法客户端"，防伪造。

## 3. IM 客户端的三个主要通道

```
                 ┌──────────────────────────────┐
   App 业务 ───► │  长连接 (LongLink)           │ ───► IM 消息 / push
                 │  cmdid 路由，seq=taskid 配对 │
                 └──────────────────────────────┘
                 ┌──────────────────────────────┐
   App 业务 ───► │  短连接 (ShortLink)          │ ───► HTTP CGI
                 │  标准 HTTP/1.1 POST          │     拉历史/配置
                 └──────────────────────────────┘
                 ┌──────────────────────────────┐
   Mars 内部 ──► │  UDP 信令 (SignallingKeeper)│ ───► NAT 保活 + 路径探测
                 └──────────────────────────────┘
```

**为什么 IM 需要短连？**
- 消息拉取（历史消息、同步会话列表）走 HTTP 更合适：可缓存、可重试、可 CDN 化。
- 长连只承载"低延迟、必须实时"的业务。

**为什么 IM 需要副长连（MinorLong）？**
- 主长连连的是"核心机房"，某个租户/某类消息需要连另一个机房时，用副长连。
- `kChannelMinorLong = 0x4`，`LonglinkConfig::link_type` 可设为它（`stn.h:66,204`）。
- 副长连的 cmdid 会 OR 上 `kMinorLonglinkCmdMask = 0xFF000000`（`stn.h:93`）以便服务端区分。
- **注意**：`is_keep_alive=false` 的副长连**不会自动重连**，只能靠任务触发。

## 4. Task 的四个正交维度

理解 `Task` 的关键 —— 它不是"一个类型"，而是**四个正交维度的组合**：

### 维度 1：通道类型 `channel_select`（位掩码）

```
kChannelShort     0x1   纯短连
kChannelLong      0x2   纯长连
kChannelBoth      0x3   长连优先，未连上降级短连
kChannelMinorLong 0x4   副长连
kChannelNormal    0x5   副长连 > 短连（不含主长连）
kChannelAll       0x7   副长连 > 主长连 > 短连
```

### 维度 2：传输协议 `transport_protocol`

```
kTransportProtocolDefault  0   （默认 TCP）
kTransportProtocolTCP      1
kTransportProtocolQUIC     2   （开源版只有枚举）
kTransportProtocolMixed    3   TCP 或 QUIC
```

### 维度 3：选路策略 `channel_strategy`

```
kChannelNormalStrategy            0   常规
kChannelFastStrategy              1   快速（长连任务数受限时降级短连）
kChannelDisasterRecoveryStategy   2   容灾
```

> **Fast 策略的特殊逻辑**（`net_core.cc:302-306`）：只有当长连上的任务数 `<= kFastSendUseLonglinkTaskCntLimit`（`config.h:99` 默认 **0**）时才允许用长连。
> 即：默认配置下 Fast 策略永远走短连 —— 因为它本意就是"长连拥堵时快速降级"。

### 维度 4：优先级 `priority`（队列排序键）

```
kTaskPriorityHighest 0
kTaskPriorityNormal  3   ← 默认
kTaskPriorityLowest  5
```

排序实现（`mars/stn/src/task_profile.cc:75-77`）：

```cpp
bool __CompareTask(const TaskProfile& _first, const TaskProfile& _second) {
    return _first.task.priority < _second.task.priority;
}
```

`std::list::sort` 是**稳定排序**，所以同优先级保持 FIFO。

> **IM 落地建议**：
> - 消息发送 = 最高优先级（0）
> - 消息 ACK / 已读回执 = 1~2
> - 心跳相关 = 内部，不走 Task
> - 历史消息拉取 = 3~4
> - 埋点上报 / 统计 = 5

## 5. 一次任务的"身份"体系

一个 IM 任务在系统里有 **4 个不同的 ID**，别搞混：

| ID | 位宽 | 生成者 | 作用 | 生命周期 |
|---|---|---|---|---|
| **taskid** | 32 位 | `atomic_inc32(&gs_taskid)`（`stn.cc:32-34`） | 引擎内部任务标识，**也是线上帧的 seq** | 任务创建 → 结束 |
| **cmdid** | 32 位 | 业务定义 | 业务命令号 | 常量 |
| **client_sequence_id** | 16 位 | `GenSequenceId()` = Mersenne Twister 随机（`stn_manager.cc:429-433`） | 与后台上报系统对齐的 trace id，**不在协议线上** | 任务创建 → 结束 |
| **server_sequence_id** | 16 位 | 服务端在响应体里返回，上层解析后回填 | 与客户端 trace id 对账 | 任务结束 |

**`client_sequence_id` 的生成时机很讲究**（`longlink_task_manager.cc:498-501`）：

```cpp
if (!first->antiavalanche_checked) {
    // client_sequence_id 在 buf2resp 这里生成，防止重试 sequence_id 一样
    first->task.client_sequence_id = context_->GetManager<StnManager>()->GenSequenceId();
```

在**首次编码前**生成 → 任务重试时**不重新生成** → 保证重试链路可对账。

## 6. 任务状态（本仓库用 6 组枚举/码族共同表达）

开源版没有单一的 `TaskStatus` 枚举，而是分层表达：

| 维度 | 枚举/码族 | 位置 | 取值 |
|---|---|---|---|
| 错误类型（粗） | `ErrCmdType` | `stn.h:245-257` | OK/False/Dial/Dns/Socket/Http/NetMsgXP/EnDecode/Server/Local/Canceld |
| 错误码（细） | 本地 `-1..-16` | `stn.h:260-275` | TaskTimeout/TaskRetry/StartTaskFail/AntiAvalanche/ChannelSelect/NoNet/Cancel/Clear/Reset/TaskParam/CgiFrequencyLimit/ChannelID/LongLinkReleased/LongLinkUnAvailable |
| 错误码（细） | 长连/HTTP `-500..-503` | `stn.h:278-292` | FirstPkgTimeout/PkgPkgTimeout/ReadWriteTimeout/TaskTimeout |
| 错误码（细） | Socket `-10086..-10606` | `stn.h:295-314` | NetworkChange/RecvErr/SendErr/Shutdown/UserBreak/MakeSocketPrepared… |
| 失败处理策略 | `TaskFailHandleType` | `stn.h:231-242` | Normal(0)/Default(-1)/RetryAllTasks(-12)/SessionTimeout(-13)/TaskEnd(-14)/TaskTimeout(-15)/SlientHandleTaskEnd(-16) |
| 连接状态 | `NetStatus` | `stn.h:316-324` | Unknown(-1)/Unavailable(0)/GateWayFailed(1)/ServerFailed(2)/Connecting(3)/Connected(4)/ServerDown(5) |
| 长连通道状态 | `LongLink::TLongLinkStatus` | `src/longlink.h:77-83` | ConnectIdle(0)/Connecting(1)/Connected(2)/DisConnected(3)/ConnectFailed(4) |
| 失败阶段归因 | `TaskProfile::TaskFailStep` | `task_profile.h:358-368` | Succ/Dns/Connect/FirstPkg/PkgPkg/Decode/Other/Timeout/Server |

**`TaskFailHandleType` 是业务最需要关注的**（`Buf2Resp` 的返回值）：

| 值 | 宏 | 语义 |
|---|---|---|
| 0 | `kTaskFailHandleNormal` | 成功 |
| -1 | `kTaskFailHandleDefault` | 默认处理（出错，走错误分支） |
| -12 | `kTaskFailHandleRetryAllTasks` | **该用户所有任务全部重做** |
| -13 | `kTaskFailHandleSessionTimeout` | **会话超时 → 立即重试并触发重新鉴权** |
| -14 | `kTaskFailHandleTaskEnd` | 任务直接结束（不重试） |
| -15 | `kTaskFailHandleTaskTimeout` | 任务超时结束 |
| -16 | `kTaskSlientHandleTaskEnd` | **静默结束（不回调上层）** |

> **IM 典型用法**：收到服务端"登录态失效"错误码 → `Buf2Resp` 返回 `kTaskFailHandleSessionTimeout(-13)`
> → STN 会立即重试该任务，并触发重新鉴权流程（`longlink_task_manager.cc:829-906`）。

## 7. 完整生命周期图

```
StartTask(task)
     │
     ▼
┌────────────────────────────────────────────────────────────┐
│ S0  QUEUED   在 lst_cmd_ 中，running_id == 0                │
│              排序键 = task.priority（稳定排序，同级 FIFO）  │
└────────────────────────────────────────────────────────────┘
   │      │      │      │       │
   │      │      │      │       └─[MakesureAuthed()==false]──┐
   │      │      │      │                                 │  留在 S0，1s 后重试
   │      │      │      └─[Req2Buf 失败]───────────────────┐
   │      │      └─[AntiAvalanche 拦截]──────────────────┐ │
   │      │                                          │    │
   │      │                                          ▼    ▼
   │      │   ┌───────────────────────────────────────────────┐
   │      │   │ S1  SENDING   running_id != 0                │
   │      │   │  长连: running_id = channel->Send(...)       │
   │      │   │  短连: running_id = (ShortLinkInterface*)wkr │
   │      │   └───────────────────────────────────────────────┘
   │      │        │        │         │
   │      │        │        │         └─[StopTask/Clear/网络变化]──┐
   │      │        │        │                                 │    │
   │      ▼        ▼        ▼                                  ▼    ▼
┌──────────────────────────────────────────────────────────────────────┐
│ S2  TERMINATED                                                      │
│  Buf2Resp 返回值决定：                                               │
│    0  → 成功结束                                                    │
│   -1  → 错误结束（走重试逻辑 if remain_retry_count>0）             │
│  -12  → 全部任务重做                                                 │
│  -13  → 会话超时，立即重试 + 重新鉴权                               │
│  -14  → 直接结束不重试                                               │
│  -15  → 超时结束                                                     │
│  -16  → 静默删除，不回调上层                                         │
│                                                                      │
│  终止判定（shortlink_task_manager.cc:1131-1132）：                   │
│  if (force_no_retry || 0 >= remain_retry_count || kEctOK==err_type │
│      || kTaskFailHandleTaskEnd==fail || kTaskFailHandleTaskTimeout==fail) │
│      → 结束；从 lst_cmd_ 删除；回调 OnTaskEnd                        │
│                                                                      │
│  未终止且可重试：                                                     │
│    remain_retry_count--; PushHistory(); InitSendParam();            │
│    retry_start_time = now; retry_time_interval = DEF_TASK_RETRY_INTERNAL(1s)│
└──────────────────────────────────────────────────────────────────────┘
```

**注意 `DEF_TASK_RETRY_INTERNAL = 1 * 1000`**（`config.h:30`）：重试间隔 1 秒，由 `LongLinkTaskManager::__RunLoop` 的 1s tick 驱动。

## 8. 心智模型：把 Mars 当成"IM 的操作系统"

```
┌───────────────────────────────────────────────────────────────┐
│  你的 IM 业务                                                │
│  - 消息发送 / 接收 / ACK / 拉历史                              │
├───────────────────────────────────────────────────────────────┤
│  你的协议层                                                  │
│  - cmdid 路由、protobuf 编解码、业务错误码                       │
├───────────────────────────────────────────────────────────────┤
│  Mars STN  ← 你在这里接入                                     │
│  - 任务排队 / 优先级 / 选路 / 重试 / 超时 / 雪崩防护              │
├───────────────────────────────────────────────────────────────┤
│  Mars LongLink                                               │
│  - 建连 / 心跳 / 断链重连 / 弱网退避                             │
├───────────────────────────────────────────────────────────────┤
│  TCP / TLS / UDP                                             │
└───────────────────────────────────────────────────────────────┘
```

**STN 的核心价值 = 让你的业务代码永远不需要处理"网络不可靠"这件事**。
它把连接失败、超时、重试、雪崩、优先级、限流全部内化成了任务状态机的行为。

**代价 = 你必须遵守它的约定**：
1. `Req2Buf` / `Buf2Resp` 必须快（跑在 STN 线程上）。
2. 必须实现 `Buf2Resp` 的返回值语义（决定重试与否）。
3. 长连接上必须实现心跳响应（cmdid=6）。
4. 不要在业务层自己维护"连接是否可用"的全局状态（STN 已有 `ReportConnectStatus`）。

## 9. 常见误解澄清

| 误解 | 真相 |
|---|---|
| "STN 就是个 HTTP 库" | 它是 IM 通道框架，长连接才是主角 |
| "taskid 就是请求序号" | 是的，线上帧的 seq 就是 taskid |
| "心跳超时只是打个日志" | **直接断链重连**，所有在途任务批量失败并重试 |
| "重连就是固定间隔 5 秒" | 是**多维度自适应的**：活跃态 / 前台态 / 无网 / 无账号 / 退避阶梯 |
| "TCP 有 keepalive 就够了" | Mars 完全不用它，靠应用层 noop |
| "长连断了消息就丢了" | 任务会进 `lst_cmd_` 或 zombie，链路恢复后重做（取决于 `retry_count`） |
| "短连接也有 Mars 帧头" | 没有，短连是标准 HTTP/1.1 |
| "长连加密是 Mars 做的" | 开源版**没有**加密层，靠 TLS；私有加密要自己替换 `LongLinkEncoder` |

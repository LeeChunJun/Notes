# 02 · 项目经历话术

> 目标：把"读过 Mars"这件事**讲成一个有深度、有主线、有个人判断的项目经历**，
> 而不是"我看过一个开源库"。

---

## 一、通用原则

### 1.1 面试官真正想知道的

| 他们问 | 他们想听到 |
|---|---|
| "你负责什么？" | **边界清晰**（哪部分是你做的，哪部分是现成的） |
| "遇到什么难题？" | **真实的技术难点**（不是"我加了日志"） |
| "怎么解决的？" | **有取舍的方案**（为什么不用另一种） |
| "有什么效果？" | **可量化的结果** |
| "你觉得有什么不足？" | **有自己的判断**（不是复述文档） |

### 1.2 三条禁忌

| 禁忌 | 为什么 | 替代说法 |
|---|---|---|
| ❌ "我基于 Mars 做了 IM" | 听起来像"我用了个库" | "我在 Mars 的 STN 框架上承载 IM 业务，**我负责的是业务接入层和服务端协议对接**" |
| ❌ 背源码细节 | 面试官会追问细节，背不住就露馅 | 讲**为什么这样设计**，细节留到被问 |
| ❌ 说"开源版有 XX 功能" | 会暴露没读懂 | 明确区分"开源版有"和"我们线上有" |

### 1.3 数字要说准

记住这 10 个数字（见 `README.md` §4）：**20 / 200 / 6 / 243 / 0 / 3.5min / 10min / 10s·2.5s·3 / 5s·20s / 1MiB**。

## 二、三种版本的经历描述（按你的实际角色选）

### 版本 A：你主要做业务接入层（最常见）

> "我们 IM 用的是腾讯开源的 Mars 里的 **STN 信令网络框架**，在它上面做长连接消息通道。
>
> **我主要负责三块**：
>
> **第一是业务接入层**。STN 的接入方式是实现 `Req2Buf`/`Buf2Resp` 两个回调，
> 我们封装了一套 `TaskWrapper` + AIDL 的抽象层，把网络栈放到 `:marsservice` 独立进程，
> UI 进程通过 Binder 通信。这样 UI 卡死或被系统回收都不影响长连接收消息。
>
> **第二是消息可靠性**。这块 STN 只做到进程内的任务重试，
> 进程一杀就没了。所以我加了一层**本地持久化队列**：
> 消息先落库再发送，用业务 `msg_id` 做幂等键（不能用 STN 的 taskid，
> 那个是进程内递增会回绕的），配指数退避 + 随机抖动防惊群。
>
> **第三是协议对接**。包括和服务端约定 cmdid 划分（注意 6 号被心跳占了要避开）、
> push 的 seq 必须是 0 这个隐式约定、心跳回包必须原样回显 seq 这些坑。
>
> 最有价值的收获是搞清楚了 **STN 的 `Buf2Resp` 返回值语义** ——
> 它直接决定任务是否重试。比如登录态失效要返回 -13 让框架触发重新鉴权，
> 内容违规要返回 -14 表示别重试了。这个设计挺巧的。"

**面试官可能追问**：
- "为什么要放独立进程？" → 见 `04-Android/02-初始化与进程模型.md` §1.1
- "幂等怎么做？" → 见 `06-IM工程实践/03-可靠性-重试幂等顺序.md` §3
- "为什么不能用 taskid？" → 进程内递增 + 32 位回绕 + 新建 Task 就变

### 版本 B：你主要做长连接稳定性

> "我们 IM 的核心痛点是**弱网下的消息送达率**，
> 所以我重点研究了 Mars STN 的连接容灾体系。
>
> Mars 的重连策略是我见过最完整的客户端实现，**五个维度叠加**：
> ① 按 App 活跃态分级（前台 1 分钟内 30 秒、前台 10 分钟内 120 秒、不活跃 600 秒）；
> ② 不活跃态走**阶梯退避** `{0,60,120,240,360,480,600}` 秒，
> 而且是**自适应升降档** —— 距上次尝试不足 10 分钟就升档等更久，超过 10 分钟就降档更快恢复；
> ③ 无网络时间隔 ×3 + 600 秒；没有账号信息且不活跃直接退到 **7 天**；
> ④ 每次加 0~20 秒**随机抖动**；
> ⑤ 网络切换时无视活跃态立即重连。
>
> ★ 我认为**第 4 点最关键**：几百万台手机同时断网恢复，
> 没有抖动就是瞬间百万次重连，服务端直接被打挂。这是典型的重试惊群。
>
> 另外我把 Mars 的**弱网识别**机制也吃透了：它不是靠主动探测，
> 而是看**建连时命中的是不是首选 IP**（`ip_index > 0`）和 RTT。
> 因为 IP 排序会把上次连成功的排第一，所以首选 IP 这次不通，本身就是弱网信号。
> 这个设计挺巧的 —— 用历史成功经验做异常检测，零额外开销。
>
> 我基于这些做了监控埋点，把**重连间隔分布**和**首选 IP 命中率**作为核心指标。"

**面试官可能追问**：
- "阶梯退避为什么要自适应升降档？" → 见 `03-长连接/03-重连退避算法.md` §7.3
- "7 天间隔是不是有问题？" → 未登录用户不该占长连接资源；但**退出登录必须清理长连**
- "随机抖动怎么实现的？" → `interval += rand() % 20`（`longlink_connect_monitor.cc:163`）

### 版本 C：你主要做服务端 / 协议

> "我们服务端是 Netty，客户端用 Mars STN。
> **协议对齐是我做的**，踩了不少坑。
>
> Mars 的帧格式是固定 20 字节头 + body，5 个 uint32 全大端。
> 看着简单，但有几个必须注意的点：
>
> ① **心跳回包必须原样回显 seq = 0xFFFFFFFF**。
> 客户端判定心跳的条件是 `taskid == 0xFFFFFFFF && cmdid == 6`，
> seq 改了就识别不出来，客户端 8 秒后判定心跳超时**直接断链**，
> 表现就是"连上就断，连上就断"，很难查。
>
> ② **服务端主动 push 的帧 seq 必须是 0**。
> 这是 Mars 的隐式约定 —— 客户端靠 `seq == 0` 判断这是推送而不是某个请求的响应，
> 不用额外的 flag 字段，设计很简洁。
>
> ③ **cmdid 6 被心跳占了**、243 是信令保活，业务 cmdid 要避开。
>
> ④ **帧定界要做对**。TCP 是字节流，
> 我们一开始没装 `LengthFieldBasedFrameDecoder`，一次 read 拿到半帧就 `readFully` 阻塞，
> 拿到多帧就只解第一帧 —— 表现为随机丢消息。
> 正确做法是按 `head_length + body_length` 定界。
>
> 另外还做了**幂等**：客户端重试时 taskid 可能变，
> 所以我们在业务层加了 `msg_id`，服务端按 `(user_id, msg_id)` 去重，
> 而且**重复请求要返回和第一次一样的响应**，否则客户端会一直重试。"

**面试官可能追问**：
- "为什么 push 的 seq 用 0 这么巧？" → 见 `07-面试准备/01-核心问答.md` Q32
- "幂等返回具体怎么实现？" → Redis SETNX + 缓存首次响应
- "心跳超时是多久？" → 8 秒（active 模式 5 秒）

## 三、把"读过源码"讲成"有判断"

### 3.1 讲优点时给数字

| 别说 | 说 |
|---|---|
| "它的重连策略很完善" | "它的重连策略是五维叠加：活跃态分级 + 阶梯退避 + 场景加盐 + 随机抖动 + 切网立即重连" |
| "心跳做得很智能" | "心跳间隔在 3.5 到 10 分钟之间自适应，而且学到的结果按网络类型持久化到 INI 文件，下次直接用" |
| "支持多 IP" | "是 Happy Eyeballs 的实现，2.5 秒错峰并发 3 个，谁先握手成功用谁" |

### 3.2 讲不足时给判断

| 别说 | 说 |
|---|---|
| "有些地方不够完善" | "我觉得最大的问题是 **1 秒的调度 tick**：IM 首条消息最坏要等 1 秒才发出去，这是首包延迟的主要来源。我们后来用消息聚合绕过了" |
| "性能有待优化" | "`__Locate` 是 `std::find_if` 全表扫描，IM 高峰 1000 个在途任务时每次回包都扫一遍，理论上可以加个 `unordered_map<taskid, iterator>` 索引" |
| "加密不太完善" | "开源版的帧层是明文的，20 字节头里没有加密位也没有压缩标志位。`LongLinkEncoder` 留了扩展点可以自己实现，但我们线上是靠 TLS" |

### 3.3 展示"读到什么深度"

这三个细节能证明你真读过：

1. **帧头 20 字节**（`#pragma pack(1)` 的 5 个 uint32，全大端）
2. **seq 就是 taskid**，服务端原样回显，客户端 `find_if` 匹配（所以支持乱序响应）
3. **心跳超时 8 秒直接断链**，active 模式 5 秒

## 四、STAR 结构模板

### 模板 1：弱网消息丢失

```
【S 情境】
我们的 IM 在地铁/电梯等弱网环境下消息丢失率高，用户投诉多。

【T 任务】
我负责定位原因并提升弱网下的消息送达率。

【A 行动】
1. 先用 Mars 的 CgiProfile 把延迟拆解到阶段
   （排队 / 建连 / 编码 / RTT / 解码），发现两个问题：
   a) 排队等待平均 500ms —— STN 是 1 秒 tick 调度
   b) 首次失败后要等 1 秒才重试（DEF_TASK_RETRY_INTERNAL）
2. 针对 b)：把错误分类 —— 网络类错误立即重试，不隔退避；
   业务类错误直接终止。靠 Buf2Resp 的返回值语义区分。
3. 针对 a)：引入消息聚合，把用户连发的多条消息攒 200ms 合成一个包。
   吞吐提升 5 倍，首条延迟只多 200ms。
4. 补上本地持久化队列，因为 Mars 的任务重试是进程内的，App 一杀就没了。

【R 结果】
弱网场景消息送达率从 XX% 提升到 XX%，
P99 端到端延迟从 2.5s 降到 700ms。
```

### 模板 2：长连频繁重连

```
【S 情境】
线上监控发现长连重连次数异常，周末尤其严重。

【T 任务】定位重连风暴的根因。

【A 行动】
1. 拉出重连间隔分布和断开原因码，发现两个聚集：
   - 大量 kRemoteClosed（服务端主动关）
   - 大量 kNoopTimeout（心跳超时）
2. 查服务端日志，发现心跳响应延迟 P99 到了 6 秒 ——
   客户端心跳超时是 8 秒，已经贴脸了。
   根因是服务端的 EventLoop 上做了同步阻塞的 HTTP 调用（业务 CGI），
   一个慢请求阻塞了整个 EventLoop 上的所有连接。
3. 把业务 CGI 挪到独立的业务线程池，EventLoop 只做 IO。
4. 客户端侧也加了兜底：把心跳响应从业务链路里摘出来，
   在 Netty pipeline 的第一层就处理，不排队。

【R 结果】
心跳超时占比从 XX% 降到 XX%，重连次数下降 XX%。
```

### 模板 3：版本发布事故

```
【S 情境】
客户端发版后大批用户反馈"消息发不出去"。

【T 任务】快速定位并止损。

【A 行动】
1. 看日志，定位到 "unpack error" + "connect status to: kDisConnected"，
   且是"连上立刻断"。
2. 想到 client_version 不匹配会直接返回 LONGLINK_UNPACK_FALSE 断链。
3. 对比发现客户端把 productID 从 200 改成了 201，服务端没同步。
4. 止损：客户端紧急发版回滚 / 或服务端加版本兼容分支。
5. 复盘：在协议里引入"版本协商"，
   服务端维护支持版本列表，客户端带自己的版本，
   服务端回一个"我支持哪些版本"的帧，而不是直接断链。
```

## 五、可能被问到的"你到底做了什么"的澄清

面试官会分不清"用框架"和"做框架"。准备好这个回答：

> "我**没有修改 Mars 的 C++ 源码**，主要是在 Java 侧做业务接入和服务端协议对接。
> 但我把 STN 的调度模型、任务状态机、重连退避、协议帧格式都读透了，
> 这让我能准确定位问题出在哪一层。
>
> 有一次 STN 的 `__Locate` 全表扫描导致高峰期 CPU 飙高，
> 我是通过读 `longlink_task_manager.cc` 定位到 `std::find_if` 那行的，
> 然后在业务侧做了限流规避。"

> **诚实 + 有深度**，比夸大更好。

## 七、一页速记卡

```
【项目】基于腾讯 Mars STN 的 Android IM 长连接

【技术栈】Mars STN / Netty / protobuf-lite / AIDL / 多进程

【我做的】
  ① 业务接入层：TaskWrapper + AIDL 抽象，网络栈放 :marsservice 独立进程
  ② 消息可靠性：本地持久化队列 + 业务 msg_id 幂等 + 指数退避抖动
  ③ 协议对接：cmdid 规划、push seq=0 约定、心跳回包原样回显

【协议关键】
  20B 头（head_length|client_version|cmdid|seq|body_length，全大端）
  seq = taskid；seq = 0 表示 push；cmdid 6 = 心跳；243 = UDP 信令
  心跳 3.5~10min 自适应，超时 8s 断链

【重连策略】
  活跃态分级 + 阶梯退避 + 场景加盐 + 随机抖动 + 切网立即重连

【踩过的坑】
  ① cmdid 忘了赋值 → 被静默降级到短连（延迟从 ms 变 100ms）
  ② client_version 不匹配 → 连上就断
  ③ 服务端没装帧解码器 → 随机丢帧
  ④ EventLoop 上同步做 HTTP → 阻塞所有连接
  ⑤ OnPush 里做 DB 写入 → 整条长连接卡住
  ⑥ taskid 映射不清理 → 内存泄漏
```

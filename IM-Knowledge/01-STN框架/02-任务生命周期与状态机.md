### 1.1 `__ValidAndInitDefault` 的校验规则

`net_core.cc:253-294`：

| 校验 | 规则 | 违规处理 |
|---|---|---|
| `retry_count` | `> 30` 视为非法 | 拒绝 |
| `server_process_cost` | `> 120000` 视为非法 | 拒绝 |
| `total_timeout` | `> 600000` 视为非法 | 拒绝 |
| `cmdid` | 走长连时不能为 0 | **自动摘除 `kChannelLong`**（`net_core.cc:269-274`） |
| `cgi` | 走短连时必填 | **自动摘除 `kChannelShort`**（`net_core.cc:276-282`） |
| `channel_select` | 不能为 0 | 失败 |

> **IM 落地**：如果你的消息 cmdid 忘了赋值，Mars **不会报错**，而是悄悄把你的任务从长连降级到短连 —— 延迟从毫秒级变成百毫秒级。
> **这是一个非常隐蔽的坑，务必在自测时检查 cmdid != 0。**

## 2. 通道选路 `__ChooseChannel`

`net_core.cc:296-324`：

**真实实现**（`net_core.cc:296-324`）：

```cpp
int NetCore::__ChooseChannel(const Task& _task,
                             std::shared_ptr<LongLinkMetaData> _longlink,
                             std::shared_ptr<LongLinkMetaData> _minorLong) {
    bool longlinkOk = (_longlink != nullptr);
    longlinkOk = longlinkOk && LongLink::kConnected == _longlink->Channel()->ConnectStatus();

    if (longlinkOk && _task.channel_strategy == Task::kChannelFastStrategy) {
        longlinkOk = longlinkOk
                     && (longlink_task_manager_->GetTaskCount(_task.channel_name)
                         <= kFastSendUseLonglinkTaskCntLimit);
    }

    bool minorOk = _task.minorlong_host_list.empty()
                 ? false : longlink_task_manager_->IsMinorAvailable(_task);

    int channel = _task.channel_select;
    switch (_task.channel_select) {
        case Task::kChannelAll:
            channel = minorOk ? Task::kChannelMinorLong
                              : (longlinkOk ? Task::kChannelLong : Task::kChannelShort);
            break;
        case Task::kChannelNormal:
            channel = minorOk ? Task::kChannelMinorLong : Task::kChannelShort;
            break;
        case Task::kChannelBoth:
            channel = longlinkOk ? Task::kChannelLong : Task::kChannelShort;
            break;
        default:
            break;   // kChannelShort / kChannelLong / kChannelMinorLong 原样返回
    }
    return channel;
}
```

**优先级总结**：副长连 > 主长连 > 短连。

### Fast 策略的特殊逻辑

`net_core.cc:302-306`（见上）：

```cpp
if (longlinkOk && _task.channel_strategy == Task::kChannelFastStrategy) {
    longlinkOk = longlinkOk && (GetTaskCount(channel_name) <= kFastSendUseLonglinkTaskCntLimit);
}
```

`kFastSendUseLonglinkTaskCntLimit = 0`（`config.h:99`）。

> **含义**：默认配置下 Fast 策略**永远走短连**。这个策略本意是"长连拥堵时快速降级到短连"，
> 阈值 0 意味着"只要长连上有任何一个任务在飞，就走短连"。
> 如果你要用 Fast 策略，必须先调大这个常量。

### `kChannelBoth` 的降级时机

注意：**降级发生在"选路时刻"，不是"发送时刻"**（`net_core.cc:317-319`）。

即：`kChannelBoth` 的任务在 `StartTask` 那一刻如果长连还没连上，就会被分到短连任务管理器，
**即使 200ms 后长连连上了，它也不会改走长连**。

> **IM 建议**：IM 消息用 `kChannelLong`（纯长连）。长连未连上时任务会留在队列里等
> （`longlink_task_manager.cc:535-546`），不会丢，也不会降级到短连（延迟劣化）。
> 降级策略应由业务显式控制，而不是隐式。

### 3.2 调度循环 `__RunLoop`（1 秒 tick）

`longlink_task_manager.cc:271-317`：

```cpp
void LongLinkTaskManager::__RunLoop() {
    if (lst_cmd_.empty()) {
#ifdef ANDROID
        wakeup_lock_->Lock(kLongLinkWakeupLockEmptyCMD, 500);   // 500ms
#endif
        return;
    }

    __RunOnTimeout();     // ① 处理超时
    __RunOnStartTask();   // ② 发起新任务

    if (!lst_cmd_.empty()) {
        MessageQueue::FasterMessage(asyncreg_.Get(),
            MessageQueue::Message((MessageQueue::MessageTitle_t)this,
                                  boost::bind(&LongLinkTaskManager::__RunLoop, this),
                                  "LongLinkTaskManager::__RunLoop"),
            MessageQueue::MessageTiming(1000));      // ★ 1 秒后再跑一次
    }
}
```

**关键点**：
1. **1 秒节拍**（`DEF_TASK_RUN_LOOP_TIMING = 1*1000`，`config.h:31`）。
2. 用 `FasterMessage` 而不是 `PostMessage` —— **去重 + "更早者胜"**：
   如果网络变化、任务下发等多处同时触发调度，只保留一个待执行消息，且执行时间取最早到期的那个。
3. Android 上用 `WakeUpLock` 防止 CPU 进入 doze。

> **IM 延迟分析**：任务入队后最坏要等 **1 秒**才会被第一次调度。
> 高频 IM 场景（比如连发 10 条消息）不会每条都等 1 秒 —— 因为 `__RunLoop` 一次会**批量**发。
> 但首条消息的调度延迟可能是 0~1000ms 的随机值。**这是 IM 首包延迟的重要来源之一。**
>
> **优化手段**：业务侧自己做"发送聚合/节流"，或者调低 `DEF_TASK_RUN_LOOP_TIMING`。

## 4. `__RunOnStartTask` —— 真正的发送逻辑

`longlink_task_manager.cc:425-661`。这是长连任务的核心调度函数。

```
while (队列非空):
  ├─ first->running_id != 0 ? → 已在途，跳过
  ├─ 是重试任务 && 未到重试时间 ? → 跳过（canretry 门控）
  ├─ get_real_host_ → 解析真实 host
  ├─ need_authed → MakesureAuthed(host, user_id)
  │      false → 留在队列，跳过（等下一轮）              [longlink_task_manager.cc:471-483]
  ├─ 首次发送（!antiavalanche_checked）:
  │    ├─ 生成 client_sequence_id                       [:498-501]
  │    ├─ Req2Buf(...) → 失败则 kEctEnDecode + TaskEnd  [:511-517]
  │    └─ AntiAvalanche::Check → 失败则 kEctLocalAntiAvalanche  [:521-528]
  ├─ TaskIntercept → 命中则走伪回包路径                  [:589-616]
  ├─ longlink->Send(body, ext, task)
  │      → running_id = channel->Send(...)               [:627]
  └─ 移到队列尾部（或保持 FIFO）
```

### 4.1 鉴权门控（IM 关键）

`longlink_task_manager.cc:471-483`：

```cpp

    bool ismakesureauthsuccess =
        context_->GetManager<StnManager>()->MakesureAuthed(host, first->task.user_id);
    if (!ismakesureauthsuccess) {
        first = next;   // 留在队列，下一轮再来

```

> **IM 语义**：`MakesureAuthed` 返回 false 表示"当前还没登录/鉴权还没过"。
> 任务**不会丢**，只是原地等待，每秒轮询一次。
> 登录成功后（上层调用 `TouchTasks()` 或鉴权回调触发），任务自动继续。
>
> **重要**：`need_authed` 默认为 **false**（C++）/ **true**（Java）—— 不一致！
> 见 `01-公开API与数据结构.md` §2.2。

### 4.2 雪崩防护（AntiAvalanche）

`longlink_task_manager.cc:521-528`。命中时：

```
OnTaskEnd(kEctLocal, kEctLocalAntiAvalanche)   // 错误码 -4
```

`mars/stn/src/anti_avalanche.h` 的机制：
- 按 `(cmdid, user_id)` 维度统计**失败次数**和**时间窗口**
- 连续失败超过阈值 → 拒绝新任务，返回 `kEctLocalAntiAvalanche`
- 有时间窗衰减，避免永久封禁

> **IM 价值**：当 IM 服务端（长连入口）挂了，客户端不会变成"几千个客户端一起疯狂重连"的 DDoS 源。
> 这是**客户端侧保护服务端**的经典设计。

`ReportTaskLimited(_check_type, _task, _param)` 的 `_check_type`：
- `kFrequencyLimit = 1`（`frequency_limit.cc`）
- `kFlowLimit = 2`（`flow_limit.cc`）

### 4.3 任务截流（TaskIntercept）

`longlink_task_manager.cc:589-616`。命中时**不走真实网络**，而是构造一个伪回包直接走 `Buf2Resp`。

> **IM 场景**：比如"服务端说这个用户被禁言"，就本地直接返回错误，不需要真的发出去再等超时。

## 5. 超时体系

长连任务的超时由 `__RunOnTimeout` 处理（`longlink_task_manager.cc:330-390`）：

| 超时类型 | 错误码 | 触发条件 | 位置 |
|---|---|---|---|
| **首包超时** | `kEctLongFirstPkgTimeout (-500)` | 发出请求后 `first_pkg_timeout` 内没收到**任何**响应 | `:336-346` |
| **包间超时** | `kEctLongPkgPkgTimeout (-501)` | 收到上一个包后，`pkg_pkg_timeout` 内没收到下一个 | `:348-358` |
| **读写超时** | `kEctLongReadWriteTimeout (-502)` | socket 层读写超时 | `:360-368` |
| **任务总超时** | `kEctLocalTaskTimeout (-1)` | `total_timeout` 内任务未结束 | `:371-389` |

首包/包间超时由 **`DynamicTimeout`（动态超时）** 计算，不是固定值。

### 5.1 动态超时（DynamicTimeout）

`mars/stn/src/dynamic_timeout.h/.cc`。根据 **包大小 + 网络类型** 计算超时。

相关常量（`mars/stn/config.h:66-87`）：

```cpp

kDynTimeMiddlePackageLen = 10 * 1024;     // < 10KB
kDynTimeBigPackageLen    = 30 * 1024;     // < 30KB
kDynTimeBiggerPackageLen = ...            // > 30KB

// Wi-Fi 下的期望耗时
kDynTimeSmallPackageWifiCosttime    = 500;
kDynTimeMiddlePackageWifiCosttime   = 2 * 1000;
kDynTimeBigPackageWifiCosttime      = 4 * 1000;
kDynTimeBiggerPackageWifiCosttime   = 6 * 1000;

// GPRS 下的期望耗时
kDynTimeSmallPackageGPRSCosttime    = 1 * 1000;
kDynTimeMiddlePackageGPRSCosttime   = 3 * 1000;
kDynTimeBigPackageGPRSCosttime      = 5 * 1000;
kDynTimeBiggerPackageGPRSCosttime   = 7 * 1000;

// 首包超时
kDynTimeFirstPackageWifiTimeout = 7 * 1000;
kDynTimeFirstPackageGPRSTimeout  = 10 * 1000;

// 额外余量
kDynTimeExtraWifiTimeout = 10 * 1000;
kDynTimeExtraGPRSTimeout = 15 * 1000;
```

**核心思想**：小消息在 4G 上期待 1 秒，大消息期待 7 秒。超时 = 期望耗时 + 余量。

状态机（`dynamic_timeout.h:27`）：
```cpp
enum DynamicTimeoutStatus { kEValuating = 1, kExcellent = 2, kBad = 3 };
```

- `kEValuating`：正在评估当前网络质量
- `kExcellent`：网络好 → 用"期望耗时 + 小余量"
- `kBad`：网络差 → 用"期望耗时 + 大余量"

还有几个"达标"标签（`config.h:91-96`）：
```cpp
kDynTimeTaskNormalTag            = 0;
kDynTimeTaskMeetExpectTag        = 1;   // 达标
kDynTimeTaskMidPkgMeetExpectTag  = 2;
kDynTimeTaskBigPkgMeetExpectTag  = 3;
kDynTimeTaskBiggerPkgMeetExpectTag = 4;
```

连续 10 次达标（`kDynTimeMaxContinuousExcellentCount = 10`）且至少 6 个包（`kDynTimeMinNormalPkgCount = 6`）→
判定网络优秀 → 收紧超时。5 分钟（`kDynTimeCountExpireTime`）后过期重算。

> **IM 价值**：**超时不是拍脑袋定的**。大图片/文件消息在弱网下需要更长的超时，
> 小文本消息则可以快速失败让用户重试。动态超时能同时优化"成功率"和"用户感知延迟"。

### 6.1 `__Locate` 的关键特性

`longlink_task_manager.cc:925-934`：

```cpp
std::list<TaskProfile>::iterator LongLinkTaskManager::__Locate(uint32_t _taskid) {
    if (Task::kInvalidTaskID == _taskid)
        return lst_cmd_.end();

    find_task find_functor;
    find_functor.taskid = _taskid;
    std::list<TaskProfile>::iterator it =
        std::find_if(lst_cmd_.begin(), lst_cmd_.end(), find_functor);
    return it;
}
```

**用 `find_if` 全表扫描，不是 map 查找**。

- ✅ **乱序回包能正确匹配**（不要求响应顺序与请求顺序一致）
- ❌ **O(n) 复杂度**：任务多时（IM 高峰 1000+ 在途）会有性能问题
- ❌ **seq 冲突风险**：如果 taskid 回绕（32 位），旧任务可能匹配到新任务

### 6.2 匹配失败 = 静默丢弃

`longlink_task_manager.cc:992-998`：

```cpp
if (lst_cmd_.end() == it) {
    xwarn2_if(Task::kInvalidTaskID != _taskid,
              TSF "task no found task:%0, cmdid:%1, ect:%2, errcode:%3", ...);
    return;      // 静默丢弃，不重连、不重试
}
```

> **IM 常见现象排查**：客户端日志出现大量 "task no found"，
> 通常是**任务已超时被删除，但服务端响应姗姗来迟**。这是正常的（网络抖动），
> 但如果频繁出现，说明首包超时设置过短或网络确实差。

```cpp
InitSendParam();      // 重置发送参数
retry_start_time = now;

```

### 7.3 重试的门控

`longlink_task_manager.cc:431-443`：

```cpp
bool canretry = curtime - lastbatcherrortime_ >= retry_interval_;
...
if (first->task.retry_count > first->remain_retry_count && !canretry) {
    // 不满足重试条件 → 跳过，等下一轮
    first = next; continue;

```

`retry_interval_` 在**批量错误**时被重置为 1 秒（`longlink_task_manager.cc:829-906`）：

```cpp
if (kEctLocal != _err_type && !lst_cmd_.empty())
    retry_interval_ = DEF_TASK_RETRY_INTERNAL;     // 1s
```

> **IM 含义**：长连断开瞬间，所有在途任务批量失败，然后统一等 1 秒再重试。
> 避免"每个任务各自立刻重连"造成惊群。

### 7.4 `retry_count` 语义

- 默认 `-1` → 实际为 `DEF_TASK_RETRY_COUNT = 1`（`config.h:29`）→ **总共尝试 2 次**（1 次原始 + 1 次重试）
- 设置 `retry_count = 0` → 只发一次，不重试
- `> 30` 视为非法

> **IM 建议**：
> - 发送消息这类"用户主动操作"：`retry_count = 1`（重试 1 次），并且**必须做幂等**（见 `06-IM工程实践/03-可靠性-重试幂等顺序.md`）
> - 拉历史消息：`retry_count = 2~3`
> - 埋点上报：`retry_count = 0`（失败就丢）

```cpp
}
```

**关键逻辑**：
- `kEctSocket` / `kEctDns` / `kEctCanceld` **不再额外断链** —— socket 本来就已经死了
- `kEctNetMsgXP`（协议解析错误）→ **主动断链**（协议错乱必须重建）
- `kTaskFailHandleSessionTimeout(-13)` / `RetryAllTasks(-12)` → 断链 + 取消重连定时消息 + `retry_interval_ = 0`（立即允许重试）

> **IM 含义**：
> - **协议错误必断链** —— 因为流已经错位了，继续用会一直出错。
> - **会话超时必须重连** —— 因为鉴权态没了。
> - **网络错误不额外断** —— 断链动作由 LongLink 自己完成，这里避免重复。

## 9. 僵尸任务（ZombieTask）

`mars/stn/src/zombie_task_manager.cc`。

场景：长连断开时，任务被批量失败并从 `lst_cmd_` 删除，但用户希望**恢复连接后自动重发**。

```cpp
// net_core.cc:795-818
// zombie_task_manager.h:49
```

**流程**：
```
长连断开
  → 任务进入 ZombieTaskManager 暂存
  → 长连重连成功
  → __RedoTasks(channel_name) 把 zombie 任务放回 lst_cmd_
  → 重新发送
```

对比 `RedoTasks()` 全局 API（`stn_logic.cc:289`）：重连长连并重做**所有**任务。

> **IM 场景**：用户在地铁里（断网）发的消息，进了 zombie；
> 出站连上后自动重发 —— 用户体感是"消息自己发出去了"。
> 但**必须服务端幂等**，否则会重复发消息。

## 10. 网络变化时的任务处理

`mars/stn/src/net_core.cc:581-644`（`OnNetworkChange`）：

```
网络变化（WiFi ↔ 4G）
  │
  ├─ longlink_task_manager_->OnNetworkChange()
  │     ├─ 每个 channel: Monitor()->NetworkChange()
  │     │     ├─ longlink_.Disconnect(kNetworkChange)     ← 先断
  │     │     └─ __IntervalConnect(kNetworkChangeConnect) ← 再按网络切换策略重连
  │     └─ 重连成功后 __RedoTasks(channel, false)          [:1226-1233]
  │
  └─ 正在飞行的任务 → kEctLocal/kEctLocalCancel → 重新排队
```

`longlink_task_manager.cc:239-246` / `shortlink_task_manager.cc:998-1006`：
任务被置为"未在途"，重新入队等待重发。

> **IM 关键行为**：网络切换时**不会丢任务**。
> 前提是 `retry_count` 足够（默认 1 次重试）。
> 如果 `retry_count = 0`，切网瞬间在途的消息就真的丢了。

## 12. `TaskProfile` —— 运行时画像

`mars/stn/task_profile.h`。这是排查问题的**核心数据结构**。

包含：
- `task`：原始 `Task` 副本
- `taskid` / `cmdid` / `cgi`
- `start_time` / `end_time`
- `err_code` / `err_type`
- `dyntime_status`：动态超时状态
- `channel_select` / `link_type`
- `history`：重试链（每次重试的快照）
- `ConnectProfile`：DNS 时间、连接时间、命中 IP、端口、RTT、断连原因

`TaskProfile::GetFailStep()`（`task_profile.h:447-465`）的归因优先级：

```
成功 → DNS → Connect（ip_index == -1）→ FirstPkg（last_receive_pkg_time == 0）
     → Decode（kEctEnDecode）→ PkgPkg（Socket/Http/NetMsgXP）
     → Timeout（kEctLocalTaskTimeout）→ Server → Other
```

> **IM 排查价值**：拿到一个失败任务的 `TaskProfile`，
> 直接能看出是"DNS 慢"还是"TCP 连不上"还是"服务端慢"还是"本地解包失败"。
> 这是线上 IM 质量分析的核心依据。

```
App 线程            STN 线程                      LongLink 线程        服务端
   │                   │                              │                │
   ├─ startTask ──────►│                              │                │
   │                   ├─ StartTask → 入 lst_cmd_     │                │
   │                   │  (sort by priority)          │                │
   │                   │                              │                │
   │                   ├─ [1s tick] __RunLoop         │                │
   │                   │   ├─ __RunOnTimeout          │                │
   │                   │   └─ __RunOnStartTask        │                │
   │                   │      ├─ MakesureAuthed ──────►│                │
   │                   │      ├─ Req2Buf（业务编码）   │                │
   │                   │      ├─ AntiAvalanche::Check │                │
   │                   │      └─ longlink->Send ─────►│                │
   │                   │         (打包 20B 头+body)   │                │
   │                   │                              ├─ writev ─────►│
   │                   │                              │                │
   │                   │                              │◄──────────────┤ 响应
   │                   │                              ├─ recv         │

```

**关键耗时点**：
1. **入队 → 首次调度**：0 ~ 1000ms（1s tick）
2. `Req2Buf` / `Buf2Resp`：**跑在 STN 线程**，必须 < 几毫秒
3. `Send` → 实际 write：几乎立即（`readwritebreak_.Break()` 唤醒 select）
4. 服务端 RTT
5. **回包 → `__OnResponse`**：几乎立即（同一 LongLink 线程直接回调）

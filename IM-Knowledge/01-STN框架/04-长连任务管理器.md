# 04 · 长连任务管理器

> 主要源码：`mars/stn/src/longlink_task_manager.h`（202 行）、`longlink_task_manager.cc`（1439 行）

## 1. 职责

`LongLinkTaskManager` 是 **STN 调度引擎与物理长连接之间的中介**：

- 维护长连任务队列 `lst_cmd_`
- 每个 tick 决定：谁该发、谁超时了、谁该重试
- 把响应对应回任务（按 taskid）
- 管理多条长连接（主长连 / 副长连 / 业务线长连）
- 长连断开时批量失败在途任务

## 5. 调度循环 `__RunLoop`

`longlink_task_manager.cc:271-317`：

```cpp
void LongLinkTaskManager::__RunLoop() {
    if (lst_cmd_.empty()) {
#ifdef ANDROID
        wakeup_lock_->Lock(kLongLinkWakeupLockEmptyCMD, kLongLinkWakeupLockEmptyCMD);  // 500ms
#endif
        return;
    }

    __RunOnTimeout();     // ① 超时处理
    __RunOnStartTask();   // ② 发起新任务

    if (!lst_cmd_.empty()) {
        MessageQueue::FasterMessage(asyncreg_.Get(),
            MessageQueue::Message((MessageQueue::MessageTitle_t)this,
                                  boost::bind(&LongLinkTaskManager::__RunLoop, this),
                                  "LongLinkTaskManager::__RunLoop"),
            MessageQueue::MessageTiming(1000));
    }
}
```

**Android WakeUpLock 的作用**：
防止 CPU 进入 doze 模式导致 1 秒 tick 变成几分钟一次。
`kLongLinkWakeupLockEmptyCMD = 500`（队列空时 500ms 保活）
`kLongLinkWakeupLockRunCMD = 30 * 1000`（有任务时 30s）

## 6. `__RunOnStartTask` —— 发送决策

`longlink_task_manager.cc:425-661`。完整流程：

```
curtime = gettickcount()
canretry = (curtime - lastbatcherrortime_ >= retry_interval_)
sent_count = 0

while (first != last):
  ├─ first->running_id != 0 → 已在途，跳过，sent_count++
  │
  ├─ 是重试任务 && !canretry → 跳过（等 retry_interval_ 到期）
  │
  ├─ get_real_host_(task.user_id, task.longlink_host_list, false, task.extra_info)
  │      → 解析/刷新真实 host（可能触发 host 重定向）
  │
  ├─ need_authed → MakesureAuthed(host, user_id)
  │      false → 跳过（留在队列）
  │
  ├─ 首次发送（!antiavalanche_checked）:
  │    ├─ client_sequence_id = GenSequenceId()
  │    ├─ Req2Buf(...) → 失败：kEctEnDecode + kTaskFailHandleTaskEnd
  │    └─ AntiAvalanche::Check → 失败：kEctLocal + kEctLocalAntiAvalanche
  │
  ├─ TaskIntercept::Check → 命中：构造伪回包，走 Buf2Resp
  │
  ├─ longlink->Send(bufreq, buffer_extension, task)
  │      → running_id = channel->Send(...)
  │
  └─ 移到队尾（保持 FIFO）或原地
```

### 6.1 `get_real_host_` —— 动态 host 解析

这是 IM 特有的能力：**服务端可以下发"你该连哪个 host"**。

```cpp
if (get_real_host_) {
    get_real_host_(task.user_id, task.longlink_host_list, /*_strict_match=*/false, task.extra_info);
}
```

配合 `Task::redirect_type`（`HostRedirectType`）：
```cpp
kFull  = 0   完全匹配
kFuzzy = 1   模糊匹配
kPrefix = 2  前缀匹配（注释标注"很可能已废弃"）
kOther = 3
```

> **IM 落地**：微信的"就近接入 / 机房切换 / 故障转移"就是靠这个。
> 服务端在 `Buf2Resp` 里返回新的 host，上层更新 `longlink_host_list`，下次任务就用新 host。

## 7. `__RunOnTimeout` —— 超时处理

`longlink_task_manager.cc:330-390`。

```
遍历 lst_cmd_ 中 running_id != 0 的任务:
  ├─ 首包超时: 发出后 first_pkg_timeout 内没收到响应
  │      → kEctLongFirstPkgTimeout(-500)
  ├─ 包间超时: 收到上个包后 pkg_pkg_timeout 内没收到下一个
  │      → kEctLongPkgPkgTimeout(-501)
  ├─ 读写超时: socket 层
  │      → kEctLongReadWriteTimeout(-502)
  └─ 任务总超时: total_timeout 内任务未结束
         → kEctLocal + kEctLocalTaskTimeout(-1) + kTaskFailHandleTaskTimeout(-15)
```

超时时长由 `DynamicTimeout` 计算（见 `02-任务生命周期与状态机.md` §5）。

## 8. 响应分发 `__OnResponse`

`longlink_task_manager.cc:936-1101`。核心流程见 `02-任务生命周期与状态机.md` §6。

### 8.1 Push 判定优先于任务匹配

```cpp
// longlink_task_manager.cc:966-974
if (kEctOK == _error_type &&
    longlink->Encoder().longlink_ispush(_cmdid, _taskid, body, extension)) {
    fun_on_push_(_name, _cmdid, _taskid, body, extension);
    return;
}
```

`longlink_ispush` 的默认实现（`longlink_packer.cc:175-177`）：
```cpp
longlink_ispush = [](uint32_t _cmdid, uint32_t _taskid,
                     const AutoBuffer& _body, const AutoBuffer& _extend) {
    return PUSH_DATA_TASKID == _taskid;      // taskid == 0
};
```

> **IM 核心机制**：服务端主动推送的帧，`seq` 填 **0**。
> 客户端一看 seq=0 就知道"这不是某个请求的响应，是推送"。
> **这是一个非常简洁但强大的设计** —— 不需要额外的 flag 字段。

### 8.2 找到任务后调用 `Buf2Resp`

```cpp
// longlink_task_manager.cc:1007-1022
int handle_type = context_->GetManager<StnManager>()->Buf2Resp(
        _taskid, _it->task.user_context, _it->task.user_id,
        _body, _extension, _err_code, _flags, _channel_select, _server_sequence_id);
```

`Buf2Resp` 的返回值 → `handle_type`，决定后续。

### 8.3 静默结束

`longlink_task_manager.cc:1072-1084`：`kTaskSlientHandleTaskEnd(-16)` → 从队列删除但**不回调上层 `OnTaskEnd`**。

> **IM 用途**：消息已发送成功，但用户已经退出聊天页 → 不必再回调 UI。

## 11. `RedoTasks` —— 重做所有任务

`longlink_task_manager.cc:203`（`RedoTasks`）与 `__RedoTasks`：

```cpp
void LongLinkTaskManager::RedoTasks() {
    MetaScopedLock lock(meta_mutex_);
    for (auto& item : longlink_metas_) {
        __RedoTasks(item.first, false);
    }
}
```

`__RedoTasks(channel_name, is_user_cancel)` 的效果：
1. 把在途任务重新置为"未在途"
2. 断链
3. 触发重连
4. 连上后重发

> **IM 典型场景**：服务端下发"你的服务器地址变了"→ 调用 `RedoTasks()`，
> 所有消息重新走新链路。这是**机房切换 / 灰度切流**的标准做法。

## 13. `StopTask`

`longlink_task_manager.cc:124-149`：

```cpp
void LongLinkTaskManager::StopTask(uint32_t _taskid) {
    // 找到任务
    // 1. 如果在途 → longlink->Stop(taskid)（从发送队列删除）
    // 2. 从 lst_cmd_ 删除
    // 3. 回调 OnTaskEnd(kEctLocal, kEctLocalCancel)
}
```

`LongLink::Stop(taskid)`（`longlink.cc:264-275`）只删除**尚未开始写**的任务（`Pos() == 0`）：

```cpp
bool LongLink::Stop(uint32_t _taskid) {
    for (auto it = lstsenddata_.begin(); it != lstsenddata_.end(); ++it) {
        if (it->first.taskid == _taskid && it->second->Pos() == 0) {
            lstsenddata_.erase(it);
            return true;
        }
    }
    return false;
}
```

> **限制**：已经写到 socket 里的包撤不回来。
> **IM 含义**：用户点"取消发送"时，如果消息已经上网络了，就撤不掉了 ——
> 这就是为什么 IM 消息必须有**服务端幂等**和**发送状态机**（sending → sent → delivered → read）。

## 16. IM 场景的队列调优建议

| 场景 | 建议 |
|---|---|
| 消息发送 | `priority = 0`（最高），`retry_count = 1`，`need_authed = true` |
| 消息 ACK / 已读 | `priority = 1` |
| 拉历史消息 | `priority = 3`，`channel_select = kChannelShort` |
| 会话列表 | `priority = 3`，`channel_select = kChannelShort` |
| 埋点 / 统计上报 | `priority = 5`，`retry_count = 0`，`limit_flow = false` |
| 批量发消息 | **不要**用一个 Task 塞 N 条消息 —— 每个 Task 一个消息，否则优先级失效、超时粒度不对 |
| 离线消息同步 | `priority = 2`，`retry_count = 2`，注意幂等 |

> **一个 Task 只能对应一次请求-响应**。批量场景要在 `Req2Buf` 里聚合，
> 在 `Buf2Resp` 里拆分 —— 但那样就没有逐条的状态回调了。
> **更好的做法**：单条一个 Task，靠优先级区分重要性。

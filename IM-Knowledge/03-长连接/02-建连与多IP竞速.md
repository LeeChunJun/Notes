## 1. 为什么需要多 IP 竞速

IM 服务的现实：
- 一个域名解析出多个 IP（不同机房 / 不同网段）
- 部分 IP 在某些运营商网络下**不可达**（这是国内运营商的常态）
- 单 IP 串行尝试 = 最坏 10s 超时 × N 个 IP = **用户感知 30 秒以上**

**Happy Eyeballs 思想**：不等第一个失败，隔一小段时间就并发试下一个，谁先通用谁。

Mars 的实现叫 **`ComplexConnect::ConnectImpatient`**（"Impatient" = 不耐烦）。

### 3.2 Step 1：时间轴调度主循环

`:648-834`

```
laststart_connecttime = curtime - max(interval_, error_interval_)     // :638

do {
    SocketSelect sel(_breaker); sel.PreSelect();                     // :651-652

    // 下一个 IP 应该多久后发起
    next_connect_timeout = (lasterror == 0 ? interval_ : error_interval_)
                          - (curtime - laststart_connecttime)          // :654-655

    timeout = timeout_;                                                // :659
    running_count = count_if(FSM 仍在连接中)                            // :660-661

    // ① 还没轮到下一个 IP，但 select 最多等到那一刻
    if (index < size && next_connect_timeout > 0 && running_count < max_connect_)
        timeout = min(timeout, next_connect_timeout);                  // :663-665

    // ② 到点了，且并发未超限 → 发起第 index 个 connect
    if (index < size && next_connect_timeout <= 0 && running_count < max_connect_) {
        if (running_count + 1 < max_connect_) timeout = min(timeout, interval_);
        laststart_connecttime = gettickcount();
        lasterror = 0;
        trycount_ = index + 1;  ++index;                               // :668-683
    }

    // ③ 所有在跑的 FSM 注册到 select，并收集各自的超时
    for (i < index) {
        fsm[i]->PreSelect(sel, group);
        timeout = min(timeout, fsm[i]->Timeout());                     // :685-694
    }

    ret = sel.Select(timeout);                                         // :706
    if (ret < 0)          { errcode_ = sel.Errno(); break; }           // :710-714
    if (sel.IsException()) break;                                      // :717-720
    if (sel.IsBreak())    { is_interrupted_ = true; break; }           // :722-726

    // ④ 处理各 FSM 状态
    for (i < index) {
        fsm[i]->AfterSelect(sel, group);
        if (status == EEnd)                    → 失败，OnFinished(err)，删除 FSM，lasterror = -1  // :743-760
        if (status == EReadWrite && check == ECheckFail) → 校验失败                                     // :762-781
        if (status == EReadWrite && check == ECheckOK)   → ★ 成功！retsocket = fsm[i]->Socket()        // :783-812
    }

    if (all_invalid || retsocket != INVALID_SOCKET) break;              // :825-826
    loop_count++;
    if (loop_count > 30) break;      // kMaxConnectingLoopCount 防死循环   // :828-832
} while (true);
```

### 3.3 参数语义

| 参数 | 语义 |
|---|---|
| `timeout_` | **单次 connect 的绝对超时**（从该 FSM `start_connecttime_` 起算） |
| `interval_` | **正常情况下**两个 IP 之间的发起间隔（错峰） |
| `error_interval_` | **上一个 IP 失败后**到下一个 IP 的间隔（通常更短，fail-fast） |
| `max_connect_` | **最大并发连接数**（默认 3） |

> **长链的 `error_interval == interval == 2.5s`**（`longlink.cc:668`），
> 也就是说**不管上一个 IP 失败没失败，都是 2.5 秒后试下一个**。

### 3.4 时序示意（3 个 IP）

```
t=0.0s   发起 connect(IP1)                      [running=1]
t=0.0s   select 等待，timeout = min(10s, 2.5s) = 2.5s
t=2.5s   发起 connect(IP2)  ← 错峰 2.5s        [running=2]
t=2.5s   select 等待，timeout = min(10s, 2.5s) = 2.5s
t=5.0s   发起 connect(IP3)                      [running=3]
t=5.0s   select 等待，timeout = 10s
         ├─ 若 IP2 在 t=3.1s 握手成功 → 立即返回 IP2，耗时 3.1s ★
         ├─ 若 IP1 在 t=6.0s 握手成功 → 返回 IP1，耗时 6.0s
         └─ 若全部失败 → 最多耗到 t=15s（3 个 IP 各 10s，错峰 2.5s）
```

> **最坏情况耗时 ≈ timeout + (N-1) × interval = 10s + 2×2.5s = 15s**。
> 这是 IM 长连接建立延迟的上限。

### 4.4 超时计算

`complexconnect.cc:227-239`：

```cpp
virtual int ConnectTimeout() const {
    return start_connecttime_ + ConnectAbsTimeout() - gettickcount();
}
virtual int ReadWriteTimeout() const {
    return end_connecttime_ + ReadWriteAbsTimeout() - gettickcount();
}
virtual int ConnectAbsTimeout() const { return connect_timeout_; }
virtual int ReadWriteAbsTimeout() const {
    return std::max(3000, std::min(6 * Rtt(), ConnectAbsTimeout() - Rtt()));  // 至少 3s
}
```

> **读写超时 = clamp(6×RTT, 3s, connect_timeout − RTT)** ——
> RTT 越小超时越短，弱网下自动放宽。**这是一个很漂亮的自适应设计。**

## 5. 长连的"业务层连通性校验"

**TCP 握手成功 ≠ 业务通道可用。**

`mars/stn/src/longlink.cc` 的 `LongLinkConnectObserver`：

```cpp
virtual bool OnShouldVerify(...) {
    return longlink_.Encoder().longlink_complexconnect_need_verify();
}
virtual bool OnVerifySend(...)   { /* 打包一个 noop 包 */ }
virtual bool OnVerifyRecv(...)   { /* 解析 noop 响应，校验 cmdid/seq */ }
```

`longlink_complexconnect_need_verify` 默认返回 `false`（`longlink_packer.cc:171-173`），
即**默认不做业务层校验**。

> **IM 场景**：
> 某些机房会在 TCP 层面完成握手后立刻发 RST（安全设备策略），
> 或者需要先发一个探测包才能确认通道可用。
> 这时打开 `longlink_complexconnect_need_verify`，
> Mars 会在 TCP 连上后先发一个 noop 包验证，确认后才交给上层使用。
>
> **代价**：多一个 RTT 的建连延迟。**默认关闭是对的。**

## 7. socket 选项实际生效情况

| 选项 | 是否启用 | 位置 / 条件 |
|---|---|---|
| **`TCP_NODELAY`** | ✅ **仅长链**（`nagle=1` 即禁用） | `longlink.cc:753-757`。短连不设 |
| **`SO_KEEPALIVE`** | ❌ **全仓库无任何 setsockopt(SO_KEEPALIVE)** | 靠应用层 noop 心跳 |
| **`SO_LINGER`** | ❌ **被注释掉** | `longlink.cc:759-764`、`shortlink.cc:559-568` |
| **`SO_SNDBUF`/`SO_RCVBUF`** | ⚠️ 工具函数存在但**调用点为 0** | `socket_reserve_sendbuf`（`unix_socket.cc:380`）无调用 |
| **`TCP_MAXSEG` (MSS)** | ✅ **Wi-Fi 下强制 1400** | `tcpclient_fsm.cc:184-188`、`block_socket.cc:58-62` |
| **`IPV6_V6ONLY = 0`** | ✅ 仅 Windows | `tcpclient_fsm.cc:190-194`、`block_socket.cc:46-50` |
| **`O_NONBLOCK`** | ✅ 全部 | `tcpclient_fsm.cc:196`、`block_socket.cc:52` |

### 7.1 为什么 Wi-Fi 下强制 MSS = 1400

```cpp
// tcpclient_fsm.cc:184-188
if (getNetInfo() == kWifi && socket_fix_tcp_mss(sock_) < 0) { ... }
```

`socket_fix_tcp_mss`（`unix_socket.cc:350-352`）：
```cpp
int socket_fix_tcp_mss(int sockfd) {
    return socket_set_tcp_mss(sockfd, 1400);
}
```

> **原因**：某些运营商/AP 设备有 PMTU（路径 MTU）黑洞 ——
> 小包能通、大包被静默丢弃。强制把 MSS 降到 1400 可以绕过。
>
> **IM 价值**：这是典型的"在真实网络里踩过坑才会加的代码"。
> 面试时讲这个比讲架构更能体现工程经验。

### 7.2 `socket_reserve_sendbuf` 的"只增不减"逻辑

`unix_socket.cc:380-388`：

```cpp
// 读 SO_SNDBUF，仅当当前值 < 目标值才 setsockopt
```

> **原因**：Linux 会把 `setsockopt(SO_SNDBUF, n)` 的值翻倍作为内部缓冲，
> 且**不能调小于内核默认值**。如果强行设置反而可能被内核加倍变大。
> 所以必须"先读再判断"。

## 10. `SocketBreaker` —— 打断机制

`mars/comm/unix/socket/socketbreaker.h:28-58` / `.cc`。

### 10.1 原理

Linux `pipe()` 造一对 fd，都设为 `O_NONBLOCK`（`.cc:69-70`）。
写端 fd 被注册进 `poll()` 的事件集合；
`Break()` 往管道写 1 字节 → `poll` 立即返回 → 阻塞中的 `Select()` 被唤醒。

### 10.2 API

```cpp
// unix/socket/socketbreaker.h:33-45
bool IsCreateSuc() const;
bool ReCreate();                       // 重建管道
void Close();
bool Break();                          // 写 1 字节打断
bool Break(int reason);                // 带原因码
bool Clear();                          // 读空管道，复位
bool PreciseBreak(uint32_t cookie);   // 写 4 字节 cookie（精确唤醒特定等待者）
bool PreciseClear(uint32_t* cookie);
bool IsBreak() const;
int  BreakerFD() const;               // 读端 fd，注册进 poll
int  BreakReason() const;
```

| 实现 | 位置 |
|---|---|
| `ReCreate()` | `.cc:52-80` |
| `Break()` | `.cc:82-99`（幂等：`breaked_` 已置位则直接 true） |
| `Clear()` | `.cc:110-146`（循环 read 到 EWOULDBLOCK） |
| `PreciseBreak/Clear` | `.cc:148-179`（4 字节 `uint32_t cookie`） |

### 10.3 在 `SocketSelect` 中的角色

`mars/comm/unix/socket/socketselect.h:67-100`：

```cpp
bool SocketSelect::IsBreak()    { return socket_poll_.BreakerIsBreak(); }
bool SocketSelect::IsException(){ return socket_poll_.BreakerIsError(); }
```

`SocketSelect` 内部包 `SocketPoll`（`unix/socket/socketpoll.h`），
把 breaker 的读端 fd 加入 poll 集合；`Select(_msec)`（`.cc:194-196`）转发到 `socket_poll_.Poll(_msec)`。

> macOS 上曾用 kqueue 实现（`.cc:20-179` 的 `#if 0` 死代码保留），现统一为 poll。

### 10.4 STN 中的 breaker 归属

| 对象 | breaker |
|---|---|
| `LongLink` | `connectbreak_`（打断 connect）+ `readwritebreak_`（打断 select） |
| `TcpSocketOperator` | `sBreaker_`（静态，`tcp_socket_operator.h:65`），通过 `TcpBreaker` 适配到 `OPBreaker` 抽象（`tcp_socket_operator.cc:34-47`） |

`ComplexConnect::ConnectImpatient` 里 `sel.IsBreak()` → `is_interrupted_ = true; break;`（`:722-726`）。
**这是让上层"取消 connect"能立即生效的关键。**

## 11. IM 建连优化的实践建议

| 优化 | 做法 | 预期收益 |
|---|---|---|
| **DNS 预热** | App 启动时提前解析长连 host（`Callback::OnNewDns` 提前填 host 列表） | 省掉首次建连的 DNS 时间（可能 1~5s） |
| **多 IP 排序** | 确保 `SimpleIPPortSort` 能学到"上次成功的 IP" | 命中率大幅提升 |
| **备用 IP** | `SetBackupIPs(host, ips)` 兜底 DNS 失败 | 抗 DNS 故障 |
| **调试 IP** | `SetDebugIP` 直连指定 IP（灰度/自测） | 绕开 DNS |
| **降低 connect 超时** | `kLonglinkConnTimeout` 从 10s 降到 3~5s | 失败时更快切换 |
| **提高并发数** | `kLonglinkConnMax` 从 3 提到 4~5 | 弱网下更快命中（但服务端压力↑） |
| **TCP_NODELAY** | 已默认开启 | 小消息不延迟 |
| **MSS 1400** | 已默认（Wi-Fi） | 绕开 PMTU 黑洞 |
| **连接复用** | 长连本身就是这个目的 | 避免重复握手 |

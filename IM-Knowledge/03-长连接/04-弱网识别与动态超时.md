# 04 · 弱网识别与动态超时

> 主要源码：`mars/stn/src/weak_network_logic.h/.cc`、`mars/stn/src/dynamic_timeout.h/.cc`、
> `mars/stn/src/timing_sync.h/.cc`

---

## 1. 为什么需要弱网识别

IM 客户端面对的网络是**高度动态**的：

- WiFi ↔ 4G 切换
- 地铁 / 电梯 / 地下室 → 信号弱、RTT 高、丢包
- 运营商限速 / 拥塞
- NAT 超时导致"看起来还连着，其实已断"

**如果不做弱网识别**，会发生：
1. 超时设得太短 → 消息频繁失败，用户体验差
2. 超时设得太长 → 用户等太久才收到失败反馈
3. 弱网下继续高频发消息 → 加剧拥塞，越发越慢

## 2. `WeakNetworkLogic` —— 弱网识别

`mars/stn/src/weak_network_logic.h/.cc`。

### 2.1 核心接口

```cpp
bool IsCurrentNetworkWeak();       // 当前网络是否弱
bool IsLastValidConnectFail();     // 上次有效连接是否失败
```

### 2.2 判定逻辑

`weak_network_logic.cc:124-172`：

```cpp
void WeakNetworkLogic::OnConnectEvent(bool _is_suc, unsigned int _rtt, int _index) {
    if (!_is_suc) {
        // 连接失败
        last_connect_fail_ = true;
        ...
        return;
    }

    // 连接成功
    last_connect_fail_ = false;

    if (_index > 0) {
        // ★ 命中的不是首选 IP → 说明首选 IP 不通 → 弱网
        scene_ = kSceneIndex;
    } else if (_rtt > rtt_threshold) {
        // ★ RTT 超过阈值 → 弱网
        scene_ = kSceneRtt;
    } else {
        scene_ = kSceneNormal;
    }
}
```

**两个判定维度**：

| 场景 | 含义 | 依据 |
|---|---|---|
| `kSceneIndex` | **命中 IP 序号 > 0** | 首选 IP（上次连成功的）这次不通了 → 网络路径变了/被限 |
| `kSceneRtt` | **RTT > 阈值** | 连得上但很慢 → 拥塞/信号差 |
| `kSceneNormal` | 正常 | — |

### 2.3 ★ `ip_index > 0` 是最强的弱网信号

**为什么？**

`SimpleIPPortSort` 会把**上次连接成功的 IP 排到第一位**。
如果这次连上的不是第一个，说明：
- 第一个 IP 完全不通（被限流/被墙/机房故障）
- 或者网络切换了（原来 WiFi 的排序在新网络下不适用）

> **这是一个"用历史成功经验做异常检测"的经典设计** ——
> 不需要额外的探针，连接行为本身就携带了信号。

### 2.4 弱网后的行为

| 行为 | 位置 |
|---|---|
| **放宽超时** | `DynamicTimeout` 根据弱网状态调整 |
| **降低消息发送频率** | 上层通过 `IsCurrentNetworkWeak()` 自行决定 |
| **给用户提示** | 上层通过 `ReportConnectStatus` / 自己的逻辑 |
| **上报** | `kActionBadNetwork` 等事件（`smart_heartbeat.cc:133-136`） |

> `smart_heartbeat.cc:133-136`：
> ```cpp
> if (report_smart_heart_ && current_net_heart_info_.min_heart_fail_count_ >= 6 && ::isNetworkConnected()) {
>     report_smart_heart_(context_, kActionBadNetwork, current_net_heart_info_, false);
>     current_net_heart_info_.min_heart_fail_count_ = 0;
> }
> ```
> **连续 6 次心跳失败 + 网络是连着的 → 上报"弱网"事件。**

## 3. `DynamicTimeout` —— 动态超时

`mars/stn/src/dynamic_timeout.h/.cc`。

### 3.1 核心思想

> **超时时间不应该是一个固定值，而应该是"包大小 × 网络类型 × 网络质量"的函数。**

小文本消息在 4G 上期待 1 秒，大图片消息期待 7 秒。
如果都设成 10 秒：
- 小消息失败时要白等 10 秒 → 用户体验差
- 大消息可能本来就超过 10 秒 → 假失败

### 3.2 常量表

`mars/stn/config.h:66-87`：

**包大小分档**：
```cpp
kDynTimeSmallPackageLen  = 3 * 1024;    // 小
kDynTimeMiddlePackageLen = 10 * 1024;   // 中
kDynTimeBigPackageLen    = 30 * 1024;   // 大
// 更大 → BiggerPackage
```

**Wi-Fi 期望耗时**：
```cpp
kDynTimeSmallPackageWifiCosttime    = 500;
kDynTimeMiddlePackageWifiCosttime   = 2 * 1000;
kDynTimeBigPackageWifiCosttime      = 4 * 1000;
kDynTimeBiggerPackageWifiCosttime   = 6 * 1000;
```

**GPRS 期望耗时**：
```cpp
kDynTimeSmallPackageGPRSCosttime    = 1 * 1000;
kDynTimeMiddlePackageGPRSCosttime   = 3 * 1000;
kDynTimeBigPackageGPRSCosttime      = 5 * 1000;
kDynTimeBiggerPackageGPRSCosttime   = 7 * 1000;
```

**首包超时**：
```cpp

```

**额外余量**：
```cpp

```

### 3.3 状态机

`mars/stn/src/dynamic_timeout.h:27`：

```cpp
enum DynamicTimeoutStatus {
    kEValuating = 1,     // 正在评估网络质量
    kExcellent = 2,      // 网络优秀 → 收紧超时
    kBad = 3,            // 网络差 → 放宽超时
};
```

### 3.4 质量评估

```cpp
kDynTimeMaxContinuousExcellentCount = 10;   // 连续 10 次达标
kDynTimeMinNormalPkgCount = 6;               // 至少 6 个包样本
kDynTimeCountExpireTime = 5 * 60 * 1000;     // 5 分钟后过期重算
```

**"达标"标签**（`config.h:91-96`）：
```cpp
kDynTimeTaskNormalTag              = 0;
kDynTimeTaskMeetExpectTag          = 1;   // 小包达标
kDynTimeTaskMidPkgMeetExpectTag    = 2;   // 中包达标
kDynTimeTaskBigPkgMeetExpectTag    = 3;   // 大包达标
kDynTimeTaskBiggerPkgMeetExpectTag = 4;   // 特大包达标
kDynTimeTaskFailedPkgLen = 0xffffffff;    // 失败标记
kDynTimeTaskFailedTag = -1;
```

**判定逻辑**：
```
每个任务结束后：
  实际耗时 <= 期望耗时 → 记为 "MeetExpect"（按包大小分档）
  失败                  → 记为 Failed

累计：
  连续达标次数 >= 10 且样本数 >= 6 → kExcellent（收紧超时）
  失败率上升                        → kBad（放宽超时）
  5 分钟没有新样本                   → 过期，回到 kEValuating
```

### 3.5 超时的计算

```
首包超时 = (包大小期望耗时) + (网络类型余量) + (质量调整)
包间超时 = 同上，但通常更短（因为已经在传输中了）
```

**质量调整**：
- `kExcellent` → 减小余量（快速失败）
- `kBad` → 增大余量（给弱网更多机会）

### 3.6 IM 落地价值

| 场景 | 效果 |
|---|---|
| **小消息（< 3KB）** | Wi-Fi 超时约 0.5 + 余量 = **快速失败**，用户立刻知道要重试 |
| **大消息（图片/文件）** | Wi-Fi 超时约 4~6 秒 + 余量 = **不会假失败** |
| **4G 下的小消息** | 约 1 秒 + 余量 |
| **弱网** | 额外放宽，避免"本来能成功却超时" |

> **这也是为什么 `Task::server_process_cost` 存在** ——
> 上层可以告诉 STN "这个 CGI 服务端要处理 3 秒"，
> 动态超时会把服务端的处理时间算进去。

## 4. `TimingSync` —— 时间校准

`mars/stn/src/timing_sync.h/.cc`。

**用途**：估计客户端与服务端的时间差。

**IM 场景**：
1. **消息时间戳排序** —— 客户端本地时间不准（用户手动改时间）
2. **服务端下发"绝对时间"的业务** —— 例如"消息将在 X 时刻过期"
3. **跨端一致性** —— 消息列表在多端展示的时间一致

**实现**（推断）：
- 记录长连往返时间（RTT）
- 用 `SignalConnection` 感知连接建立/断开
- 在连接稳定后定期做一次时间探测

## 5. `LongLinkSpeedTest` —— 链路测速

`mars/stn/src/longlink_speed_test.h/.cc`。

**用途**：测量长连接的实际吞吐能力。

**IM 场景**：
- 判断"当前网络能不能传大文件"（比如发图）
- 自适应选择传输方式（长连直传 vs 短连上传）
- 端到端带宽调度

> 这是一个"按需触发"的辅助能力，需要上层主动调用。

## 6. `LongLinkIdentifyChecker` —— 长连身份校验

已在 `02-协议层/03-心跳保活与信令.md` §5 详述。这里补充与弱网的关系：

| 场景 | 行为 |
|---|---|
| `kCheckNow` | 立刻校验（当前心跳就带校验包） |
| `kCheckNext` | 下次心跳校验 |
| `kCheckNever` | 不校验（sample Android 的默认） |

> **弱网下的额外成本**：校验包复用心跳通道，**不多花 RTT**。
> 这是 Mars 协议设计的一个亮点。

## 7. 弱网相关的可观测指标

| 指标 | 数据来源 | 用途 |
|---|---|---|
| 长连建立成功率 | `ConnectProfile` 聚合 | 核心 SLO |
| 平均建连耗时 | `conn_cost` | 网络质量 |
| 首选 IP 命中率 | `ip_index == 0` 的比例 | DNS 质量 / 机房健康度 |
| 建连 RTT | `conn_rtt` | 网络延迟 |
| 心跳失败率 | `SmartHeartbeat` 的 `fail_heart_count_` | 链路稳定性 |
| 任务失败阶段分布 | `TaskProfile::GetFailStep()` | 定位问题在 DNS/连接/服务端/本地 |
| 首包超时率 | `kEctLongFirstPkgTimeout` 占比 | 服务端健康度 |
| 消息端到端延迟 | `CgiProfile` 各时间戳差值 | 用户体验核心指标 |

> **`TaskProfile::GetFailStep()` 的归因优先级**（`task_profile.h:447-465`）：
> ```
> 成功 → DNS → Connect（ip_index == -1）→ FirstPkg（last_receive_pkg_time == 0）
>      → Decode（kEctEnDecode）→ PkgPkg（Socket/Http/NetMsgXP）
>      → Timeout（kEctLocalTaskTimeout）→ Server → Other
> ```
> **这张归因表是线上 IM 质量分析的起点** ——
> 拿到失败任务就能知道该找谁（DNS 服务？网关？业务服务端？客户端？）。

## 8. IM 弱网优化的完整清单

| 层级 | 手段 | 效果 |
|---|---|---|
| **协议** | 消息分级（大图 vs 文本） | 不同消息用不同超时 |
| **超时** | 用 `DynamicTimeout`（默认已启用） | 失败更快速 / 更少假失败 |
| **重试** | `retry_count` 按消息重要性设置 | VIP 消息多试几次，埋点不试 |
| **退避** | 依赖 Mars 的 `LongLinkConnectMonitor` | 弱网不疯狂重连 |
| **降级** | 长连不可用时业务降级到短连 | 至少能发出去 |
| **提示** | `ReportConnectStatus` + `IsCurrentNetworkWeak` | 用户知道"网络差"而不是"失败" |
| **限流** | `limit_flow` / `limit_frequency` | 弱网时不加剧拥塞 |
| **雪崩** | `AntiAvalanche` | 服务端故障时不打死服务端 |
| **上报** | `ReportTaskProfile` | 拿到失败归因 |
| **兜底** | 消息本地落库 + 恢复后重发 | 不丢消息 |

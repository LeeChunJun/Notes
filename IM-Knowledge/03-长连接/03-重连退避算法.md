# 03 · 重连退避算法 ★

> 这是 Mars 长连接最有工程含量的部分，也是**面试最能体现"你真的读过代码"的地方**。
> 主要源码：`mars/stn/src/longlink_connect_monitor.h`（109 行）、`longlink_connect_monitor.cc`（537 行）

---

## 1. 角色定位

`LongLinkConnectMonitor` 是**重连调度的唯一决策中枢**，负责：

1. 依据 **ActiveLogic（前台/后台/活跃/不活跃）** 决定重连节奏
2. 依据**失败/成功次数**做**阶梯式退避**
3. 监听 `LongLink::SignalConnection` 状态变化
4. 处理网络切换（`NetworkChange()`）
5. iOS 上额外做"移动网络下 DNS 恢复探测"

> **设计原则**：**客户端重连必须比服务端恢复更快，同时不能形成惊群。**
> 退避 + 抖动 + 活跃态区分 就是为了同时满足这两点。

```cpp
static int __CurActiveState(const ActiveLogic& _activeLogic) {
    if (!_activeLogic.IsActive())   return kInactive;
    if (!_activeLogic.IsForeground()) return kBackgroundActive;
    if (10 * 60 * 1000 <= ::gettickcount() - _activeLogic.LastForegroundChangeTime()) return kForgroundActive;
    if (60 * 1000 <= ::gettickcount() - _activeLogic.LastForegroundChangeTime()) return kForgroundTenMinute;
    return kForgroundOneMinute;
}
```

```
                     ┌─ App 不活跃（后台被杀/无心跳）    → kInactive
                     │
   ActiveLogic ──────┼─ 后台但活跃                       → kBackgroundActive
   (前台? 活跃?)     │
                     └─ 前台
                        ├─ 切换到前台 < 1 分钟           → kForgroundOneMinute
                        ├─ 切换到前台 < 10 分钟          → kForgroundTenMinute
                        └─ 切换到前台 > 10 分钟          → kForgroundActive
```

## 4. 间隔表

`longlink_connect_monitor.cc:77-85`：

```cpp
//                     后台活跃 前台1分内  前台10分内 前台>10分  不活跃
static unsigned long const sg_interval[][5] = {
    {5,   10,   20,   30,   300},     // [0] kTaskConnect          （秒）
    {15,  30,   120,  300,  600},     // [1] kLongLinkConnect      （秒）
    {0,   0,    0,    0,    0},       // [2] kNetworkChangeConnect （秒）
};

static int const reconnect_interval[7] = {0, 60, 120, 240, 360, 480, 600};  // 不活跃态退避阶梯（秒）
static int const kInternalMaxIndex = 6;
```

### 4.1 表格解读

**`kTaskConnect`（有任务要发）**：

| 活跃态 | 间隔 |
|---|---|
| 后台活跃 | **5 秒** |
| 前台 1 分钟内 | **10 秒** |
| 前台 10 分钟内 | **20 秒** |
| 前台 > 10 分钟 | **30 秒** |
| 不活跃 | **300 秒**（5 分钟） |

**`kLongLinkConnect`（自动重连）**：

| 活跃态 | 间隔 |
|---|---|
| 后台活跃 | **15 秒** |
| 前台 1 分钟内 | **30 秒** |
| 前台 10 分钟内 | **120 秒** |
| 前台 > 10 分钟 | **300 秒** |
| 不活跃 | **600 秒**（10 分钟） |

**`kNetworkChangeConnect`（网络切换）**：全是 0 → **无视活跃态，立即重连**。

### 4.2 不活跃态的退避阶梯

`reconnect_interval[7] = {0, 60, 120, 240, 360, 480, 600}` 秒

```
index:   0     1     2     3     4     5     6
间隔:    0s   60s   120s  240s  360s  480s  600s
```

> **0 秒在 index 0** —— 意味着**第一次不活跃时是立即重连**的，
> 之后才逐步退避到 60s / 120s / ... / 600s。

## 5. 间隔计算 `__Interval`

`longlink_connect_monitor.cc:138-165`：

```cpp
static unsigned long __Interval(mars::boot::Context* _context, int _type, const ActiveLogic& _activelogic) {
    unsigned long interval = sg_interval[_type][__CurActiveState(_activelogic)];

    if (kLongLinkConnect != _type)
        return interval;                       // ★ 只有自动重连路径才做加盐

    if (__CurActiveState(_activelogic) == kInactive || __CurActiveState(_activelogic) == kForgroundActive) {
        if (!_activelogic.IsActive() && _context->GetManager<AppManager>()->GetAccountInfo().username.empty()) {
            interval = kNoAccountInfoInactiveInterval;          // 不活跃 + 无账号 → 7 天
            xwarn2(TSF "no account info and inactive, interval:%_", interval);
        } else if (kNoNet == getNetInfo()) {
            interval = interval * kNoNetSaltRate + kNoNetSaltRise;   // 无网 → ×3 + 600
            xinfo2(TSF "no net, interval:%0", interval);
        } else if (_context->GetManager<AppManager>()->GetAccountInfo().username.empty()) {
            interval = interval * kNoAccountInfoSaltRate + kNoAccountInfoSaltRise;  // ×2 + 300
            xinfo2(TSF "no account info, interval:%0", interval);
        } else {
            interval += rand() % (20);          // ★ 抖动，避免多客户端同时重连打崩服务器
        }
    }
    return interval;
}
```

### 5.1 "加盐"（salt）的三种情形

| 情形 | 计算 | 例子（不活跃，600s） |
|---|---|---|
| **不活跃 + 无账号信息** | 直接 = **7 天** | 604800s |
| **无网络** | `interval × 3 + 600` | 600×3+600 = **2400s**（40 分钟） |
| **有网但无账号** | `interval × 2 + 300` | 600×2+300 = **1500s**（25 分钟） |
| **正常** | `interval + rand()%20` | 600 + [0,20) |

### 5.2 ★ 抖动（jitter）的意义

```cpp
interval += rand() % (20);
```

> **这是防止惊群（thundering herd）的关键**。
> 如果 100 万台手机在同一个机房断网、同时恢复，
> 全部按 600s 间隔重连 → 服务端瞬间被 100 万连接打爆。
> 加 0~20 秒随机抖动 → 重连请求被摊平到 20 秒的窗口里。
>
> **这是分布式系统里"重试抖动"（retry jitter）的经典应用，
> 在客户端 IM 里同样重要。**

### 5.3 "无账号信息 → 7 天"的逻辑

```cpp
if (!_activelogic.IsActive() && accountInfo.username.empty()) {
    interval = kNoAccountInfoInactiveInterval;   // 7 天
}
```

> **场景**：App 被杀、用户在后台、还没登录（或者登录态已清）——
> 这时候维护长连接**纯属浪费服务端资源**。
> 所以退到 **7 天一次**（实际上就是"不连了"）。
>
> **IM 落地意义**：**未登录用户不应该占用 IM 长连接。**
> 登录成功后才建立长连。

## 6. 核心：`__IntervalConnect()` —— 重连决策

`longlink_connect_monitor.cc:267-341`：

```cpp
uint64_t LongLinkConnectMonitor::__IntervalConnect(int _type) {
    if (longlink_.IsSvrTrigOff()) { xinfo2(TSF "server trig off"); return 0; }
    if (LongLink::kConnecting == longlink_.ConnectStatus() ||
        LongLink::kConnected == longlink_.ConnectStatus())
        return 0;                                    // ★ 已在连接/已连接 → 不重复发起

    uint64_t interval = __Interval(context_, _type, activelogic_) * 1000ULL;
    uint64_t posttime = gettickcount() - longlink_.Profile().dns_time;   // 距上次 DNS/连接尝试的时间
    uint64_t buffer = activelogic_.IsActive() ? 0 : kInactiveBuffer;     // in case doze mode

    xinfo_trace(TSF "longlink_progress next connect interval: %_, process active state: %_, process foreground: %_",
                interval, activelogic_.IsActive(), activelogic_.IsForeground());

    /* ── 路径 A：活跃态 或 网络切换触发 ── */
    if (activelogic_.IsActive() || _type == kNetworkChangeConnect) {
        current_interval_index_ = 0;
        if ((posttime + buffer) >= interval) {
            bool newone = false;
            bool ret = longlink_.MakeSureConnected(&newone);       // ★ 立即重连
            xinfo2(TSF "process active made interval connect interval:%0, posttime:%_, newone:%_, connectstatus:%_, ret:%_",
                   interval, posttime, newone, longlink_.ConnectStatus(), ret);
            return 0;
        } else {
            uint64_t inter = interval - posttime;
            xinfo2(TSF "final interval %_", inter);
            return inter;
        }
    }

    /* ── 路径 B：不活跃态（后台/doze）── */
    if (rebuild_longlink_) { // 被 alarm 强制要求立刻重建
        rebuild_longlink_ = false;
        bool newone = false;
        longlink_.MakeSureConnected(&newone);
        xinfo2(TSF "rebuild now");
        return 0;
    }
    rebuild_longlink_ = false;

    // ★ 退避阶梯升降
    if (posttime < kUpOrDownThreshold) {                 // 距上次尝试 < 10min → 升档（更保守）
        current_interval_index_++;
        current_interval_index_ = std::min(current_interval_index_, kInternalMaxIndex);
    } else { // 距上次尝试 ≥ 10min → 降档（更激进）
        current_interval_index_--;
        current_interval_index_ = std::max(current_interval_index_, 0);
    }
    int time_interval = reconnect_interval[current_interval_index_];   // 0,60,120,240,360,480,600 (s)
    int interval_final = time_interval * 1000 - posttime;
    xinfo2(TSF "after select interval_final %_ ", interval_final);
    interval_final = std::max(interval_final, 0);
    interval_final = std::min(interval_final, (int)kUpOrDownThreshold); // 上限 10min
    xinfo2(TSF "index %_ posttime %_, interval_final %_", current_interval_index_, posttime, interval_final);

    if (interval_final == 0) {
        bool newone = false;
        bool ret = longlink_.MakeSureConnected(&newone);
        xinfo2(TSF "rebuild now, connect interval:%0, posttime:%_, newone:%_, connectstatus:%_, ret:%_",
               interval, posttime, newone, longlink_.ConnectStatus(), ret);
        return 0;
    } else {
        return (uint64_t)interval_final;
    }
}
```

## 7. 退避算法详解

### 7.1 路径 A（活跃态 / 网络切换）

```
current_interval_index_ = 0                       // 重置退避档位
if (posttime + buffer >= interval) → 立即重连
else → 等待 (interval - posttime) 毫秒
```

**`posttime` 的含义**：`gettickcount() - longlink_.Profile().dns_time`，
即"距上次发起 DNS/连接尝试过了多久"。

> **`dns_time` 初始为 0**（`conn_profile_.Reset()`），
> 此时 `posttime` 是个巨大值 → **首次连接必然立即发起**。✓

**`buffer = kInactiveBuffer(30s)`**：不活跃时额外等 30 秒，"in case doze mode" ——
因为 Doze 模式下 CPU 可能不调度，30 秒缓冲给系统一点余量。

### 7.2 路径 B（不活跃态）

```
① 如果 rebuild_longlink_（alarm 强制）→ 立即重连，清标志
② 退避档位升降：
     posttime < 10min  → current_interval_index_++   （退避更久）
     posttime >= 10min → current_interval_index_--   （恢复更快）
     钳制在 [0, 6]
③ interval_final = reconnect_interval[index] * 1000 - posttime
     钳制到 [0, 10min]
④ interval_final == 0 → 立即重连
```

### 7.3 ★ 升降档的语义（这是最巧妙的部分）

```
                  距上次尝试 < 10min          距上次尝试 >= 10min
                  （刚刚失败过）                （已经很久了）
   index++  ← 升档（更保守，等待更久）    index--  ← 降档（更激进，尽快恢复）
```

**为什么要这样？**

- **连续失败时**（每次尝试间隔都 < 10min）→ `index` 不断增大 →
  等待时间从 60s → 120s → 240s → 360s → 480s → 600s →
  **既避免反复打服务端，又在服务端恢复后能较快恢复**。
- **长时间没有尝试**（说明之前的失败可能是网络问题，现在可能好了）→ `index` 减小 →
  更快地尝试恢复。

> **这是一个"自适应退避"（adaptive backoff）**，
> 比纯指数退避更聪明：它考虑了"最近一次尝试距今多久"这个信息。

### 7.4 完整退避时序（不活跃态）

```
t=0s      断链，wake_alarm 500ms
t=0.5s    __IntervalConnect(kLongLinkConnect)
          → 活跃态 = kInactive
          → 走路径 B
          → posttime = 巨大（首次）→ index++ → 1
          → interval = 60s
t=0.5s    rebuild_alarm_.Start(60000)

t=60.5s   alarm 触发 → rebuild_longlink_ = true
          → __IntervalConnect → rebuild_longlink_ → ★ 立即重连
          → 失败
          → posttime = 60s < 10min → index++ → 2 → interval = 120s

t=180.5s  重连 → 失败 → index=3 → 240s

t=420.5s  重连 → 失败 → index=4 → 360s

t=780.5s  重连 → 失败 → index=5 → 480s

t=1260.5s 重连 → 失败 → index=6 → 600s

t=1860.5s 重连 → 失败 → index 保持 6（min(7,6)）→ 600s
          ★ 稳定在 10 分钟一次
```

## 8. `MakeSureConnected` 与 `NetworkChange`

### 8.1 `MakeSureConnected`（任务触发）

`longlink_connect_monitor.cc:228-265`：

```cpp
bool LongLinkConnectMonitor::MakeSureConnected() {
    xdebug_function();
    if (longlink_.IsSvrTrigOff()) { xinfo2(TSF "server trig off"); return false; }
    __IntervalConnect(kTaskConnect);
    return LongLink::kConnected == longlink_.ConnectStatus();
}
```

> **注意**：这里调的是 `__IntervalConnect(kTaskConnect)`，
> 走的是 `sg_interval[0]` = {5, 10, 20, 30, 300} 秒。
> **但由于 `activelogic_.IsActive()` 为真时走路径 A，
> 条件是 `posttime + buffer >= interval`** ——
> 意味着**距离上次尝试已经超过 5~30 秒就会立即连接**。
> 如果刚刚尝试过（posttime < interval），会返回"还需要等 N 秒"，
> **但这个等待不会被执行！** —— 因为 `MakeSureConnected` 直接返回了。

> ⚠️ **这是一个可以质疑的实现细节**：
> `MakeSureConnected` 在"距上次尝试太近"的情况下返回 false，
> 任务会一直等到下一个 `__RunLoop`（1 秒 tick）再试。
> **实际影响很小**（因为 `__RunLoop` 每秒都会调 `__RunOnStartTask` → `Monitor()->MakeSureConnected()`）。

### 8.2 `NetworkChange`（网络切换）

`longlink_connect_monitor.cc:246-265`：

```cpp
bool LongLinkConnectMonitor::NetworkChange() {
    xinfo_function();
#ifdef __APPLE__
    __StopTimer();
    do {
        if (LongLink::kConnected != status_ || (::gettickcount() - last_connect_time_) <= 10 * 1000) break;
        if (kMobile != last_connect_net_type_) break;
        int netifo = getNetInfo();
        if (kNoNet == netifo) break;
        if (__StartTimer()) return false;      // iOS：启动 DNS 探测线程，暂不立刻重连
    } while (false);
#endif
    longlink_.Disconnect(LongLinkErrCode::kNetworkChange);      // ← 先断
    xinfo_trace(TSF "longlink_progress network change time: %_", gettickcount());
    return 0 == __IntervalConnect(kNetworkChangeConnect);        // ← 再按网络切换策略重连
}
```

**iOS 专属逻辑**：网络切换时，如果当前连着且是移动网 → 不立刻重连，
而是启动后台 DNS 探测线程（`__StartTimer`），每 10 秒探一次移动网络的 DNS 是否恢复，
**连续 3 次成功才 `__ReConnect()`**。

> **原因**：iOS 切网后系统 DNS 还没恢复，立刻重连会用旧 DNS 结果连到不可达的 IP。
> 等 DNS 恢复再连更可靠。

`NetworkChange()` 由 `LongLinkTaskManager::OnNetworkChange()` 逐个 channel 调用
（`longlink_task_manager.cc:1226-1233`）：

```cpp
void LongLinkTaskManager::OnNetworkChange() {
    MetaScopedLock lock(meta_mutex_);
    for (auto& item : longlink_metas_) {
        if (item.second->Monitor()->NetworkChange()) {
            __RedoTasks(item.first, false);     // 重连成功后，把该 channel 上的任务全部重做
        }
    }
}
```

| alarm | 绑定 | 行为 |
|---|---|---|

| `wake_alarm_` | `__OnAlarm(false)` | `rebuild_longlink_ = false`；在 `kConnectFailed`/`kDisConnected` 时 **500ms** 启动 |

**三个触发 `__AutoIntervalConnect()` 的入口**：
1. `__OnSignalForeground(bool)` — `:368-399`（前台切换）
2. `__OnSignalActive(bool)` — `:401-414`（活跃态切换）
3. `__OnAlarm(bool)` — `:449-459`（定时器）

### 9.1 前台恢复时的特殊处理（iOS）

`longlink_connect_monitor.cc:379-396`：
前台恢复时，若 `ConnectStatus() == kConnected` 且 `now - lastrecvtime_ > 4.5min`，
主动 `__ReConnect()`（"sock long time no send data, close it"）。

> **原因**：iOS 挂起后，TCP 连接可能已被系统静默回收，
> 但客户端还以为是连着的 → 消息发出去石沉大海。
> **主动断开重建比"以为还连着"更可靠。**
>
> **这是移动端 IM 的经典问题**，值得记住。

### 9.2 `__Run`（iOS 周期探测线程）

`longlink_connect_monitor.cc:499-521`：
每 10 秒检查一次；条件为"当前连着 + 上次连接 > 12s + 上次是移动网 + 现在不是移动网"，
则用 `socket_gethostbyname` 探活，**连续 3 次成功才 `__ReConnect()`**。

## 12. IM 场景的重连策略调优

| 场景 | 建议 | 理由 |
|---|---|---|
| **普通 IM 消息** | 保持默认（活跃态 15~120s 退避） | 平衡体验与服务器压力 |
| **用户刚发消息但连不上** | 走 `kTaskConnect` 路径（5~30s） | 用户在等，不能等 10 分钟 |
| **推送通道（独立长连）** | 建议 `is_keep_alive = true` | 推送必须随时可达 |
| **副长连（租户专属）** | `is_keep_alive = false` | 服务端关闭是有意为之 |
| **未登录用户** | `accountInfo.username` 留空 → 自动退到 7 天 | 不浪费服务端资源 |
| **服务端大促/故障** | 依赖 Mars 自带的雪崩防护 | 客户端保护服务端 |

> **一个容易被忽略的点**：
> `kNoAccountInfoInactiveInterval = 7 天` 意味着**登录态清空后，长连几乎不再重连**。
> 如果你的 App 有"退出登录"逻辑，**记得同时清掉长连**（`ClearTasks()` + `Reset()`），
> 否则会残留一条僵尸长连。

## 13. 一句话总结

> **Mars 的重连策略 = 活跃态感知（快慢有别）× 阶梯退避（失败越多等越久）× 时间自适应（久了就恢复快）× 随机抖动（防惊群）× 特殊场景加盐（无网/无账号）。**
>
> 五个维度叠加，才是一个生产级的客户端重连策略。

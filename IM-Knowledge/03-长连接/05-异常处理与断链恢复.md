# 05 · 异常处理与断链恢复

> 汇总 Mars 长连接在各种异常场景下的处理策略。这篇是**排查线上问题的对照表**。

---

## 1. 异常来源总览

           ┌───────────────────┬───┴───────┬──────────────────┐

## 4. 关键异常的深度分析

### 4.1 协议错误必断链

```cpp
// longlink_task_manager.cc（__BatchErrorRespHandle）
if (kEctNetMsgXP == _err_type) {
    __Disconnect(_name, LongLinkErrCode::kTaskTimeout);
    ...
}
```

> **为什么协议错误必须断链？**
> 因为 TCP 是字节流，一旦解析错位，**后续所有数据都是错的**。
> 不断链只会一直错下去，而且会污染任务匹配（taskid 错位 → 响应张冠李戴）。
>
> **这是协议实现中的一条铁律：解析失败必须重置流状态。**

### 4.2 Socket 错误不额外断链

```cpp
if (kTaskFailHandleDefault == _fail_handle) {
    if (kEctDns != _err_type && kEctSocket != _err_type && kEctCanceld != _err_type) {
        __Disconnect(_name, LongLinkErrCode::kDecodeErr);
    }
    MessageQueue::CancelMessage(asyncreg_.Get(), longlink_id_[_name]);
}
```

> `kEctSocket` / `kEctDns` / `kEctCanceld` 时**不重复调 `__Disconnect`** ——
> 因为 socket 本来就已经死了，或者本来就是用户主动断的。

### 4.3 会话超时的特殊处理

```cpp
if (kTaskFailHandleSessionTimeout == _fail_handle || kTaskFailHandleRetryAllTasks == _fail_handle) {
    __Disconnect(_name, LongLinkErrCode::kDecodeErr);
    MessageQueue::CancelMessage(asyncreg_.Get(), longlink_id_[_name]);
    retry_interval_ = 0;      // ★ 立即允许重试（不等 1 秒）
}
```

> **`retry_interval_ = 0`** —— 鉴权失效后要尽快重连重新鉴权，不能等。

### 4.4 心跳超时的双重判定

```cpp
// longlink.cc:893-903
if (isnooping_ && alarmnooptimeout_.Status() == Alarm::kOnAlarm) {
    _errtype = kEctSocket;
    _errcode = kEctSocketRecvErr;
    goto End;
}
```

**`isnooping_` 的生命周期**：
```
__NoopReq 成功 → isnooping_ = true
__NoopResp 收到 → isnooping_ = false, 取消超时 alarm
超时 alarm 触发 → isnooping_ 仍为 true → 断链
```

> **注意**：如果 `__NoopReq` **发送失败**（`suc == false`），
> `isnooping_` 不会被置 true → 超时 alarm 不会断链。
> 这避免了"发送失败就断链"的过激行为。

### 4.5 网络切换时的任务重排队

`net_core.cc:581-644`：

```
网络变化
  → LongLinkTaskManager::OnNetworkChange()
      ├─ 每个 channel: Monitor()->NetworkChange()
      │     ├─ longlink_.Disconnect(kNetworkChange)
      │     └─ __IntervalConnect(kNetworkChangeConnect)  ← 立即重连
      └─ 重连成功 → __RedoTasks(channel, false)
```

**在途任务的处理**（`longlink_task_manager.cc:239-246`）：
任务被置为"未在途"，重新入队等待重发。

> **IM 关键前提**：`retry_count` 必须 ≥ 1，否则切网时消息就真丢了。

## 5. 断链后的恢复路径

```
断链
  │
  ├─ ① 长连线程退出（__Run 返回）
  │     ├─ __ConnectStatus(kDisConnected)
  │     └─ __RunResponseError(errtype, errcode, profile)
  │
  ├─ ② 在途任务批量失败
  │     ├─ __BatchErrorRespHandle
  │     ├─ lastbatcherrortime_ = now
  │     ├─ retry_interval_ = 1s
  │     └─ 任务从 running 状态回到 pending（remain_retry_count 未耗尽时）
  │
  ├─ ③ 重连调度
  │     ├─ wake_alarm_.Start(500)
  │     └─ 500ms 后 __AutoIntervalConnect()
  │           ├─ __IntervalConnect(kLongLinkConnect)
  │           │     ├─ 活跃态 → 路径 A（15~120s 间隔）
  │           │     └─ 不活跃 → 路径 B（阶梯退避）
  │           └─ rebuild_alarm_.Start(remain)
  │
  ├─ ④ 重连
  │     ├─ MakeSureConnected() → thread_.start()
  │     ├─ __RunConnect()
  │     │     ├─ DNS → IP 列表
  │     │     ├─ ComplexConnect::ConnectImpatient（多 IP 竞速）
  │     │     └─ TCP_NODELAY
  │     └─ __ConnectStatus(kConnected)
  │
  ├─ ⑤ 连上后冲刷积压任务
  │     └─ LongLinkTaskManager::__SignalConnection → __RunLoop()
  │           └─ __RunOnStartTask → 重新发送所有 pending 任务
  │
  └─ ⑥ 恢复统计
        ├─ SmartHeartbeat::OnLongLinkEstablished() → __LoadINI()
        └─ WeakNetworkLogic 状态更新
```

## 6. "假死"的处理

**NAT 超时导致的假死**：TCP 连接在客户端看来还在（没收到 RST），但中间的 NAT 已经把映射表项删了。
表现：**发送成功但收不到任何响应**。

**Mars 的应对**：

| 机制 | 效果 |
|---|---|
| **心跳超时** | 8 秒无心跳响应 → 主动断链重建 |
| **首包超时** | 每个任务有独立的首包超时（动态） |
| **有流量就重置心跳** | 有消息在发时不发心跳，但那些消息也会各自超时 |
| **UDP 信令保活** | 5 秒一次 UDP 包，**独立于 TCP** → 提前发现 NAT 失效 |
| **iOS 前台恢复检测** | 前台恢复时若 4.5 分钟无数据 → 主动重连 |

> **UDP 信令保活在"假死"场景下特别有价值**：
> TCP 可能还"看起来正常"，但 UDP 包发出去收不到回包
> （服务端不回 UDP，但 NAT 会因为收到外发包而刷新映射…）
> 实际上 UDP 保活的作用是**保持 NAT 映射不过期**，从源头避免假死。

## 7. IM 服务端的对应职责

| 客户端异常 | 服务端应该做什么 |
|---|---|
| **心跳超时（客户端断链）** | 服务端会看到连接关闭。**不要立刻清理会话** —— 客户端马上会重连，会话应该保持 |
| **大量重连（服务端过载）** | **限流**：单 IP/单用户连接数上限；拒绝时**主动关闭**而不是拖住 |
| **`recv == 0`（客户端主动关）** | 正常清理，**不要立刻让用户重连失败**（要允许重新鉴权） |
| **协议错误（客户端版本不符）** | **回一个错误帧**（带正确的错误码），让客户端知道原因，而不是静默丢包 |
| **鉴权失败** | 回一个明确的业务错误码，客户端才能触发重新登录 |
| **客户端重连风暴** | 服务端也要做**连接数限流 + 退避拒绝**（保护自己） |

## 8. 线上问题排查手册

### 症状 → 排查路径

| 症状 | 优先看 | 关键日志/指标 |
|---|---|---|
| **消息发不出去，一直失败** | `OnTaskEnd` 的 `errType/errCode` | `kEctLocalAntiAvalanche(-4)` = 被雪崩拦截；`kEctLocalNoNet(-6)` = 无网 |
| **消息偶尔丢** | 是否 `retry_count` 够 | `kEctLocalCancel(-7)` = 网络变化/被取消；`kEctLocalTaskTimeout(-1)` = 超时 |
| **频繁重连** | `LongLink::GetDisconnectReasonText()` | `kNoopTimeout` = 心跳超时；`kRemoteClosed` = 服务端主动关；`kNetworkChange` = 切网 |
| **重连很慢** | `ConnectProfile.conn_cost` / `ip_index` | `ip_index > 0` = 首选 IP 不通；`conn_cost` 大 = DNS 慢或 TCP 慢 |
| **长连连上但没消息** | `sent_taskids` / 服务端日志 | 客户端 `task no found` warn 日志 → 服务端回包 taskid 不对 |
| **心跳超时频繁** | 服务端心跳响应延迟 | 服务端 event loop 阻塞（sample 的 `doHttpRequest` 就是同步阻塞！） |
| **服务端看到大量 seq=0** | 服务端日志 | 那是 push 帧，正常 |
| **客户端日志 "task no found" 很多** | 正常现象 | 任务已超时删除，响应姗姗来迟。频繁出现说明首包超时太短 |
| **首次消息特别慢** | STN 队列 | 1 秒 tick 延迟 + DNS 耗时 |
| **消息乱序** | 优先级设置 | 不同 priority 的任务会被排序打乱 |

### 关键日志关键字（Xlog）

```
"longlink lifetime"          → 连接总时长
"connect status from:%0 to:%1" → 状态迁移
"task socket close sock"     → 断链
"noop timeout"               → 心跳超时
"task no found task"         → 响应匹配失败
"process active made interval connect"  → 活跃态重连
"rebuild now"                → 强制重建
"longlink_progress next connect interval" → 退避决策
"start noop taskid"          → 心跳发送
"smoke" / "smart heartbeat"  → 智能心跳学习
```

## 9. 改进建议（如果你要在这基础上做 IM）

| 改进 | 描述 |
|---|---|
| **消息落库 + 状态机** | sending → sent → delivered → read；App 重启后可恢复 |
| **业务幂等键** | 用业务消息 ID 而非 taskid 做去重 |
| **本地重试队列** | 失败消息进本地队列，网络恢复后重发 |
| **重连策略可配** | 把 `sg_interval` 暴露成配置，不同业务线不同策略 |
| **多长连** | 推送通道独立长连，避免和消息通道互相影响 |
| **心跳参数可配** | `Encoder().longlink_noop_interval()` 可强制固定心跳间隔 |
| **服务端主动 ping** | 目前客户端只认 seq=0xFFFFFFFF 的心跳，服务端主动 ping 需要约定新 cmdid |

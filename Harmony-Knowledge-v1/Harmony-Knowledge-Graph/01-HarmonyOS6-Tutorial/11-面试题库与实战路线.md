# 第一部分：高频面试题（按模块，带标准答案）

## 一、架构与工程体系（8 题）

**Q1. HarmonyOS 6 的 API Level 是多少？它和之前的版本有什么本质区别？**

> API Level 20。HarmonyOS 5.0（NEXT）起彻底移除了 AOSP 兼容层，是纯血鸿蒙，只能用 ArkTS/ArkUI 原生开发，不再支持 Android APK。开发模型上全面转向 Stage 模型，FA 模型已废弃。

**Q2. 介绍一下 Stage 模型和 FA 模型的区别。**

> FA 模型中 Ability 直接绑定 UI，Ability 销毁即页面销毁，没有窗口抽象。
> Stage 模型引入了 WindowStage 作为中间层：Ability → WindowStage → Window → 页面。这让 **Ability 生命周期与 UI 生命周期解耦**——Ability 可以在无 UI 时继续存活（后台播放），也为跨端流转和后台任务打下基础。同时 Ability 形态也细分为 UIAbility（有界面）和 ExtensionAbility（无界面，Service/Form/DataShare/InputMethod 等）。

**Q3. HAP、HSP、HAR 有什么区别？**

> - **HAP**（Harmony Ability Package）：应用的原子能力包，含 Ability、页面、资源，可独立安装。一个应用可以有主 HAP + 多个 Feature HAP。
> - **HSP**（Harmony Shared Package）：应用内多个 HAP 之间共享代码和资源的动态共享包，避免重复打包。
> - **HAR**（Harmony Archive）：编译期链接的静态库，适合纯逻辑模块（不依赖 Ability 上下文）。
>
> 选型：页面级共享用 HSP，纯工具/算法用 HAR。

**Q4. `module.json5`、`app.json5`、`build-profile.json5` 分别配置什么？**

> - `AppScope/app.json5`：应用级 —— bundleName、版本号、图标、应用名。
> - `module.json5`：模块级 —— Ability 列表、权限声明、页面路由（`$profile:main_pages`）、deviceTypes、skills、metadata。
> - `build-profile.json5`：构建配置 —— products（产品形态）、signingConfigs（签名）、buildModeSet、modules。

**Q5. 鸿蒙的分布式能力底层是什么？**

> **分布式软总线**。它屏蔽底层传输差异（Wi-Fi/蓝牙/星闪/NFC），把设备抽象成虚拟终端，上层用统一 API 做设备发现与数据传输。HarmonyOS 6 引入了**星闪（NearLink）2.0**，2.4GHz 频段，相比蓝牙功耗更低、带宽更高，支撑了"碰一碰"这种端到端本地的高速传输。

## 二、ArkTS 语言（8 题）

**Q6. ArkTS 和 TypeScript 的主要区别是什么？为什么这么设计？**

> ArkTS 是 TS 的**子集 + 约束**，不是超集。主要限制：
> ① 禁用 `any` / `unknown`；② 禁用命名空间；③ 禁用索引签名（用 `Record<K,V>` 替代）；④ 禁用 `delete`、`Symbol`；⑤ 不支持运算符重载；⑥ 运行时反射受限；⑦ 对象字面量需显式类型。
>
> **根本原因**：让方舟编译器（Ark Compiler）能做彻底的静态检查和 **AOT 预编译**，去掉运行期动态解析，从而提升启动速度和运行性能。这是"为编译优化让路"的设计取舍，不是单纯的语法限制。

**Q7. `TaskPool` 和 `Worker` 有什么区别？什么时候用哪个？**

> - **TaskPool**：任务池，复用线程，有**真正的并行**（可同时跑多个任务），通过返回值通信。适合一批彼此独立的计算任务（图片批处理、数据计算）。任务函数要加 `@Concurrent`，参数和返回值必须**可跨线程传递（Sendable）**，用完**必须 `taskpool.release(task)`**。
> - **Worker**：独立线程 + 独立 VM，一个 Worker 一个线程，通过 `postMessage` 通信。适合单个长耗时任务或需要持续双向通信的任务，用完必须 `terminate()`。
>
> 一句话：**多个独立计算任务 → TaskPool；单个长耗时/频繁通信 → Worker。**

**Q8. 什么是 Sendable？为什么跨线程要限制？**

> Sendable 是可安全跨线程传递的类型：基础类型（number/string/boolean/bigint）、Sendable 类实例、ArrayBuffer/TypedArray/DataView、元素均为 Sendable 的 Map/Set/Array、`@Sendable` 函数。
> 限制原因：跨线程共享对象需要加锁或深拷贝，会严重影响性能且容易出竞态。ArkTS 限制为**值传递或只读共享**，换取 AOT 下的性能和安全。

**Q9. ArkTS 支持哪些装饰器？**

> ArkTS **只保留状态管理相关的装饰器**，不支持属性装饰器、类装饰器、方法装饰器的通用用法。
> V1：`@State`、`@Link`、`@Prop`、`@Provide`、`@Consume`、`@Observed`、`@ObjectLink`、`@Watch`、`@StorageLink`、`@StorageProp`、`@LocalStorageLink`。
> V2：`@Local`、`@Param`、`@ParamOnce`、`@Event`、`@ProvideV2`、`@ConsumeV2`、`@ObservedV2`、`@Trace`、`@Monitor`、`@Computed`、`@Require`、`@StorageLinkV2`。
> 还有 `@Builder`、`@BuilderParam`、`@Preview`、`@Concurrent`、`@Sendable`、`@Entry`、`@Component`。

**Q10. 鸿蒙的 HTTP 请求为什么必须指定 `expectDataType`？**

> 它决定响应体的解析方式：`STRING`（返回字符串）/ `OBJECT`（自动 JSON 解析）/ `ARRAY_BUFFER`（二进制）。显式声明避免隐式解析的歧义和运行时开销，是 AOT 优化的要求。这是从 Android 迁移过来最容易踩的第一个坑。

**Q11. 鸿蒙需要申请网络权限吗？**

> **不需要。** 网络访问是默认开放的能力，HarmonyOS 没有 `INTERNET` 权限。只有涉及个人信息的权限（位置、相机、麦克风、通讯录、媒体等）才需要动态申请。这个细节能答出来说明真的了解鸿蒙的权限模型。

## 三、ArkUI 与状态管理（12 题）

**Q12. 声明式 UI 的本质是什么？**

> `UI = f(state)`。命令式是"一步步操作控件"，声明式是"描述 UI 应该是什么样子"，状态变化时框架重新描述并通过 diff 算法**只更新变化的节点**。好处是数据流单一、可预测、易维护。

**Q13. ArkUI 的两阶段渲染是什么？为什么 build() 里不能写副作用？**

> 首次渲染执行 `build()` 生成完整节点树；后续状态变更走 **update 阶段**，不再执行 build()，而是只更新受影响节点的属性。
> build() 里写副作用（打印日志、发请求、做计算）会导致：① 首屏变慢；② 每次节点重建时重复执行，产生意外行为。副作用应该放在 `aboutToAppear` 或事件回调里。

**Q14. `@State`、`@Link`、`@Prop`、`@Provide`/`@Consume`、`@ObjectLink` 各自的语义？**

> - `@State`：组件内部状态，是本地变量 + Proxy 拦截。
> - `@Link`：父子**双向**绑定，**引用传递**，子可直接改父的值。传参时**不要写 `$`**。
> - `@Prop`：父子**单向**同步，**值传递（副本）**，子不能改；**只同步一层**，嵌套对象属性变化不会同步（这是 V1 最大痛点）。
> - `@Provide`/`@Consume`：祖先→后代跨层通信，靠 key 匹配，中间层无需声明；`@Provide` 可被后代直接改。
> - `@ObjectLink`：观察 `@Observed` 标注的类实例的**任意深度**属性变化；不能整体替换父传的对象。

**Q15. V1 的 `@Observed + @ObjectLink` 与 V2 的 `@ObservedV2 + @Trace + @Param` 有什么区别？**

> **观察粒度不同**：
> - V1 是**类级粗粒度**：`@Observed` 标注类，类内**所有**属性自动可观察，配合 `@ObjectLink` 使用。
> - V2 是**属性级细粒度**：`@ObservedV2` 标注类，但**只有标了 `@Trace` 的属性**被观察，配合 `@Param` 使用。
>
> 传递方式不同：V1 用 `@ObjectLink`（引用观察，不能整体替换）；V2 用 `@Param`（父传子，可观察被观察对象的 `@Trace` 属性）。
> V2 的优势：粒度更细可控、装饰器语义统一（`@Param` + `@Event` 形成单向数据流）、支持 `@Monitor`/`@Computed`。

**Q16. V2 的 `@Param` 为什么不能被组件内部修改？用什么替代？**

> `@Param` 设计为**单向**，防止子组件破坏父组件的数据源，保持"单一数据源"。替代方案是 `@Event` —— 子组件通过事件回调**通知**父组件，由父组件修改状态，再回流到子。这构成了 **单向数据流**：数据自上而下，事件自下而上。优势是数据流可预测、可追踪、易于测试，避免双向绑定的隐式更新带来的调试困难。

**Q17. V1 和 V2 的状态装饰器能混用吗？**

> **不能。** 具体规则：
> ① 同一属性上不能同时用 V1 和 V2 装饰器；
> ② 同一条数据链路上（如父 `@State` → 子 `@Link`）不能混用；
> ③ `@Provide`/`@Consume` 与 `@ProvideV2`/`@ConsumeV2` 不能并存于同一链路；
> ④ `@Observed` 类不能传给 `@Param`，`@ObservedV2` 类不能传给 `@ObjectLink`。
>
> 最佳实践：**整项目统一到一套**，新项目直接上 V2。

**Q18. AppStorage、PersistentStorage、LocalStorage、Preferences、RDB 的定位区别？**

> - **AppStorage**：应用级**内存**全局状态，页面/组件都能用。
> - **PersistentStorage**：把 AppStorage 的指定键**持久化**到磁盘（API 12 起被 `PersistentStorageV2` 取代）。
> - **LocalStorage**：**组件内部**的存储，与 `@State` 关联，用 `@LocalStorageLink`（双向）/`@LocalStorageProp`（单向）访问。
> - **Preferences（首选项）**：**轻量 KV 持久化**到磁盘（XML），适合配置、开关、token。单 key ≤ 8KB，总 ≤ 1MB。
> - **RDB（关系型数据库）**：**结构化业务数据**，SQLite 兼容，支持事务、复杂查询、分级保护（SecurityLevel S1~S4）。

**Q19. `aboutToAppear` 和 `onAppear` 有什么区别？`onPageShow` 呢？**

> - `aboutToAppear`：组件创建时、**build() 之前**。此时组件还没渲染，**拿不到尺寸**。适合做数据初始化、订阅。
> - `onAppear`：组件**挂载到渲染树后**。此时已渲染，可以获取真实尺寸、启动动画。
> - `onPageShow`：**页面级**回调（`@Entry` 组件），页面每次显示触发（含从后台返回）。适合刷新数据。
>
> 关键点：`aboutToAppear` 在 build 之前，不能调 `getUIContext()` 拿尺寸。

**Q20. 长列表要做哪些性能优化？**

> ① `ForEach` 必须提供**稳定唯一的 keyGenerator**（不要用数组索引，增删会错位）；
> ② 开启 **`lazyForEach(true)`** 懒加载 + 合理 `cachedCount`；
> ③ 简化 item 组件层级（减少嵌套 Row/Column），必要时用 `GridRow`；
> ④ 用 `@Reuse` 让复用节点保留状态；
> ⑤ 图片必须指定宽高（触发解码优化）并使用异步加载；
> ⑥ 避免在 item 内做复杂计算（挪到 TaskPool 或预计算）。

## 四、路由与页面（4 题）

**Q21. `router` 和 `Navigation` 的区别？推荐哪个？**

> `router` 用字符串路径、参数是无类型的 Object、转场单一、缺少完整拦截（要 monkey-patch `router.pushUrl` 很脆弱）。
> `Navigation` + `NavDestination` 用 Builder 强类型、参数可泛型约束、转场丰富（`NavigationTransition`、`sharedTransition` 共享元素）、拦截齐全（`onWillShow`/`onHidden`/`onBackPressed`）、内置导航栏、NavDestination 有独立生命周期。
> **新项目推荐 `Navigation`**，router 保留用于兼容存量代码。注意**不要两套混用**。

**Q22. `NavPathStack` 是什么？`NavDestination` 有哪些生命周期？**

> `NavPathStack` 是导航路径栈，管理所有 NavDestination 的层级、参数、转场状态，通过 `Navigation(pageStack)` 传入作为路由容器。
> NavDestination 的四个回调：`onWillShow`（显示前，可拦截）、`onShown`（已显示，开启动画/埋点）、`onWillHide`（隐藏前，保存数据）、`onHidden`（已隐藏，释放资源）。另外还有 `onBackPressed` 可拦截返回。

**Q23. 什么是共享元素转场？怎么实现？**

> 列表滑到详情页时，图片位置平滑移动、视觉上"无缝"的动画。实现：列表项和详情页的组件使用**相同的 `sharedTransition` key**，且必须在**同一个 Navigation 容器**内。系统会对相同 key 的组件在页面切换时做位置/尺寸插值。这是 HarmonyOS 6 的重点视觉能力。

**Q24. `getUIContext()` 相比直接用全局 `router` 有什么优势？**

> `UIContext` 绑定组件所在的窗口/Ability 上下文，能正确处理**多窗口、多实例**场景，避免全局单例的隐式耦合，便于测试和 mock。同时它还统一提供弹窗（`showAlertDialog`/`showActionSheet`）、Toast（`getPromptAction`）等 UI 能力。这是 HarmonyOS 6 的 API 演进方向。

## 五、应用模型与生命周期（6 题）

**Q25. `onBackground` 和 `onDestroy` 有什么区别？**

> `onBackground` 只表示**切到后台**，Ability 实例**还活着**，状态保留，可以被拉回前台。适合：保存易失状态、释放占用资源、停止动画。
> `onDestroy` 才是实例**真正销毁**，之后重建就是全新的。适合：彻底释放资源、注销全局监听、释放后台任务。
> 这是 Stage 模型面试的必考对比。

**Q26. `onNewWant` 什么时候触发？解决什么问题？**

> 应用已在运行（singleton 模式）时**再次被拉起**触发。解决"热启动带新请求"的场景 —— 比如用户从推送消息点击进入应用，应用已在前台，此时需要用新的参数更新 UI 而**不是**重建整个 Ability。

**Q27. Want 的显式和隐式写法？隐式匹配依赖什么？**

> - 显式：`{ bundleName, abilityName }`。
> - 隐式：`{ action, entities, uri }`。
> 隐式匹配依赖 module.json5 中对应 Ability 的 **`skills` 声明**（entities + actions 组合匹配）。

**Q28. Want 的 parameters 支持哪些类型？有什么限制？为什么？**

> 支持 `number`、`string`、`boolean`、`object`、`array`、`null`、`undefined`。**嵌套层数有限制（API 12 起最多 9 层）**，对象内不能含函数或类实例。
> 原因：跨进程传递大对象性能差、易出安全问题。大数据应该走**文件路径或数据库**。

**Q29. 冷启动和热启动的流程差异？**

> 冷启动（进程不存在）：`onCreate` → `onWindowStageCreate` → `loadContent` → `onForeground`，全流程。
> 热启动（进程和实例都在）：只走 `onNewWant` → `onForeground`。
> 第三种（进程在但 Ability 被回收）：重建 `onCreate` → `onWindowStageCreate` → `onForeground`。
> 启动优化要重点关注冷启动的 `onCreate`。

**Q30. `loadContent` 为什么放在 `onWindowStageCreate` 而不是 `onCreate`？**

> `onCreate` 时 WindowStage 还不存在，没有窗口容器可以加载内容。`onWindowStageCreate` 表示窗口舞台已就绪，此时才能 `windowStage.loadContent('pages/Index')` 把页面组件树挂上去。

## 六、数据与网络（8 题）

**Q31. 首选项的 `put` 和 `flush` 有什么区别？容量上限？**

> 首选项是**内存缓存 + 异步落盘**模型。`put` 只修改内存，**必须 `flush()` 才写到磁盘**，否则进程被杀会丢数据。规范做法是在仓库层统一封装，写方法内部一律 await flush。
> 容量：**单 key ≤ 8KB，单文件 ≤ 1MB**。超限要把大数据移到文件或 RDB。

**Q32. RDB 的 `ResultSet` 为什么必须 close？数据库升级怎么做？**

> `ResultSet` 持有底层游标资源，不关闭会导致句柄泄漏、内存持续增长。
> 升级流程：调高 `StoreConfig.version`，在 `onUpgrade` 回调里按版本号**增量**执行 `ALTER TABLE` / `CREATE TABLE`。**忘记改 version 会导致升级回调不执行**，表结构与代码不匹配，运行时报错。

**Q33. DistributedKVStore 的一致性模型是什么？什么业务不适合用？**

> **最终一致**（非强一致），依赖同账号 + 软总线/云端中继，同步有延迟。适合剪贴板、收藏、最近浏览这类弱一致场景；**不适合**余额、库存锁、分布式锁等强一致业务。

**Q34. 鸿蒙如何访问用户文件？和 Android 有什么不同？**

> 鸿蒙**没有粗粒度的存储权限**。应用只能访问自己沙箱（`context.filesDir` 等）。要访问用户设备上的文件，必须通过**系统 Picker**（`DocumentViewPicker`、`PhotoViewPicker`）让用户主动选择并授权具体的文件/目录。这是隐私保护的设计，也是与 Android READ_EXTERNAL_STORAGE 模型的本质区别。

**Q35. 首选项、RDB、KV Store、文件怎么选？**

> 看数据形态与需求：少量配置/开关/token → **首选项**（简单但有容量限制）；结构化业务数据、需要查询排序事务 → **RDB**；高性能本地缓存、二进制数据 → **KV Store**；图片视频大文件 → **文件 + fs**；跨设备同步 → **DistributedKVStore**；跨应用共享 → **DataShare**。

**Q36. 三类后台任务怎么区分？WorkScheduler 保证准时执行吗？**

> - **短时任务**：申请后立即获得几秒~几分钟的后台执行权。
> - **长时任务**：声明类型（audioPlayback/location/dataSync 等）持续后台运行，**用户可见**（如控制中心显示"正在播放"）。
> - **延迟任务（WorkScheduler）**：**系统按条件调度，不保证准时**，只保证最终会执行（受电量、网络、用户习惯影响）。适合夜间同步。
> - **代理提醒（ReminderAgent）**：定时且用户可见，等同闹钟。
>
> WorkScheduler 的 `conditions` 支持 network、charging、deviceIdle 等触发条件。

**Q37. 如何防止搜索场景的请求竞态？**

> 用 key 维护 pending 请求 Map，同 key 发起新请求前先 `destroy()` 掉旧请求（或用取消令牌）。否则旧响应晚到会覆盖新响应，导致显示错误结果。

**Q38. `http.Http` 对象为什么要 destroy？**

> 它持有底层网络连接资源，不释放会持续占用，最终导致连接耗尽和内存增长。正确做法是 `try/finally` 中 `request.destroy()`。

## 七、权限与安全（6 题）

**Q39. 鸿蒙的权限模型与 Android 有哪三个关键差异？**

> ① **系统不再替应用弹授权框**，而是由应用自己实现说明弹窗（用户同意后系统记录授权状态）。
> ② **用户拒绝后系统永久记住**，不再询问，必须引导用户去设置手动开启。
> ③ **权限粒度更细**，没有粗粒度存储权限，文件访问靠 Picker 用户授权。

**Q40. 用户永久拒绝了权限，代码里怎么检测和处理？**

> 用 `atManager.checkPermissionsFromUser(context, permissions)` 查询状态，若为 **`PERMANENTLY_DENIED`** 则无法再弹出系统框。此时应弹自定义对话框，引导用户跳转到应用设置页（`bundleName: 'com.huawei.hmos.settings'`，`uri: 'package://application'`）。
> 检测顺序：全部 GRANTED → 直接用；有 PERMANENTLY_DENIED → 引导设置；否则 → 先弹自定义说明 → 再 `requestPermissionsFromUser` → 处理 `authResults`（GRANTED / DENIED / CANCELLED）。

**Q41. 权限的 `reason` 字段有什么作用？**

> 是申请理由的文本资源，会展示给用户。**上架审核会核对 reason 与实际 API 调用是否一致** —— 空洞的"需要相机权限"或与实际不符会被驳回。规范写法要说明"用于什么具体功能"。

**Q42. `usedScene.when` 的 `inuse` 和 `always` 有什么区别？**

> `inuse` = 使用该功能时申请（绝大多数场景，推荐）；`always` = 始终需要（如后台导航定位）。选 `always` 会让用户更谨慎、审核更关注。

**Q43. 隐私弹窗应该在什么时机展示？常见的不合规做法？**

> 应在**首次获取个人信息之前**展示，用户主动勾选同意后才能继续。
> 不合规做法：① 启动就弹隐私协议（但还没索取个人信息）；② 用完才弹；③ 隐私政策链接打不开或内容不完整；④ 用户不同意就强制退出（未给"不使用该功能"的合理路径）；⑤ 隐私政策内容与实际采集的数据不符。

**Q44. 敏感数据（如 token）应该怎么存？**

> 用 **HUKS**（`@kit.UniversalKeystoreKit`）生成密钥，对敏感数据加密后再存入首选项/数据库；或用系统 KeyStore 保护。**绝不明文存储**，也不要把 token 打到日志里（用 `hilog` 的 `%{public}` 规则控制）。

## 八、性能与工程化（4 题）

**Q45. ArkUI 性能优化的核心手段有哪些？**

> ① **状态下沉** —— 状态放到真正需要的最小作用域，缩小刷新范围。
> ② **列表优化** —— ForEach + 稳定 key + lazyForEach + cachedCount + 简化 item 层级。
> ③ **计算卸载** —— 重计算放 TaskPool，别阻塞 UI 线程。
> ④ **减少 build() 逻辑** —— build() 只做 UI 描述，副作用放回调。
> ⑤ **图片规范** —— 必设宽高触发解码优化、异步加载、必要时压缩。

**Q46. 冷启动优化有哪些手段？**

> 冷启动 = 进程创建 + `onCreate` + WindowStage 创建 + loadContent + 首帧渲染。
> ① `onCreate` 只做必要初始化，非关键服务延迟/异步；
> ② **本地优先**渲染，先出骨架再填数据；
> ③ 减少首屏组件层级；
> ④ AppStorage 预热全局状态；
> ⑤ 重计算挪到 TaskPool。

**Q47. HarmonyOS 的签名四件套是什么？**

> `.cer`（证书，开发者身份）、`.p12`（私钥，PKCS#12）、`.p7b`（Profile，把证书 + bundleName + 设备 UDID 绑定的授权文件）、`.keystore`（密钥库）。调试用自动生成的调试签名，发布需向 AppGallery Connect 申请发布证书。

**Q48. HarmonyOS 6 的新特性有哪些？（开放题）**

> ① **Ark Agent Framework** —— 感知/决策/执行三层；端侧 Skills 随应用上架、云端 Skills 动态下发；**生成式 UI** 让大模型输出直接呈现为可交互原生 UI。
> ② **空间感** —— 沉浸光感（1 行代码实现光影分层）、智感握姿、平行视界新分屏比例。
> ③ **多设备适配** —— 一套代码适配直板/折叠/平板/2in1，配套多设备开发 Skill。
> ④ **性能** —— 方舟引擎热点代码优化（内联/向量化）、智能预加载、120Hz 自适应刷新率、百米扫码。
> ⑤ **工具链** —— DevEco Code（懂鸿蒙的编程智能体，含多设备适配 Skill、问题定位 Skill 做根因定位+自修复）、DevEco CLI（面向编程 Agent 的命令行工具链，2000 多万字文档转化为 Agent 可调用知识）。
> ⑥ **跨端** —— KMP/CMP 框架 Beta，一套代码三端运行，复用率 90%。
> ⑦ **生态** —— 星闪协议栈开源、仓颉语言开源、3 万+ 原生应用、98% 升级率。

# 第三部分：面试临场话术模板

## 1. 自我介绍里的技术定位（30 秒版）

> "我做过 HarmonyOS 6（API 20）的原生开发，用 ArkTS + ArkUI 的声明式范式，Stage 模型。技术上比较熟的一块是**状态管理**，我用的是 V2 体系——`@ObservedV2` + `@Trace` 做属性级深度观察，`@Param` + `@Event` 做单向数据流，`@Computed` 处理派生数据。工程上我遵循 MVVM 分层，数据层用关系型数据库 + 仓库模式做本地优先，网络层做了统一封装和请求竞态处理。性能上关注列表懒加载、状态下沉和启动优化。"

## 2. 回答"你遇到的最大坑"

> "最典型的坑是 `@Prop` 传对象时嵌套属性不更新。`@Prop` 是值传递且只同步一层，子组件里改嵌套对象父组件完全感知不到。我后来在 V2 里统一用 `@ObservedV2` + `@Trace` + `@Param` 解决，观察粒度从对象级细化到属性级，任意深度的嵌套变化都能触发刷新。这也让我意识到状态管理的选型不只是 API 差异，而是直接影响数据流的正确性。"

## 3. 回答"你怎么保证性能"

> "我分三层做。**渲染层**：状态尽量下沉到最小作用域，列表用 ForEach + 稳定 key + lazyForEach + cachedCount，item 组件层级尽量扁平。**计算层**：重计算放 TaskPool，避免阻塞 UI 线程。**启动层**：onCreate 只做必要初始化，首屏数据本地优先先渲染骨架，AppStorage 预热。另外我会用 SmartPerf 和 ArkTS Profiler 做实测，而不是凭感觉优化。"

## 4. 回答"你关注 HarmonyOS 6 的哪些新特性"

> "我比较关注两个方向。一是 **Ark Agent Framework** —— 端侧 Skills 可以随应用上架，意图框架让业务能力能被系统智能体编排调用，这改变了 AI 能力的接入方式，从自己接大模型变成把能力标准化后交给系统编排。二是**工具链的 Agent 化** —— DevEco Code 的多设备适配 Skill 和问题定位 Skill，以及 DevEco CLI 把整套开发链路做成 Agent 可调用，这说明鸿蒙开发范式本身在往 Agentic 工程走。"

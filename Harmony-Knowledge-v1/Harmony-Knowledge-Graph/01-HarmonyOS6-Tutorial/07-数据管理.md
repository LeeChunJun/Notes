## 一、数据存储体系全景

```
应用沙箱（每个应用独立）
│
├── files/                    私有文件目录（fs 模块）
├── cache/                    缓存目录（系统可清理）
├── temp/                     临时目录
├── preferences/              首选项（轻量 KV）
├── database/                 关系型数据库文件
├── distributedfiles/         分布式文件
└── el2/ ...                  各用户（userId）隔离的目录
```

**存储方案选型表（面试必背）**：

| 方案 | 类型 | 适用场景 | 大小限制 | 并发 |
|---|---|---|---|---|
| **Preferences（首选项）** | KV 内存 + 磁盘 | 少量配置、开关、token | **单 key ≤ 8KB**，总 **≤ 1MB** | 单实例 |
| **关系型数据库 RDB** | SQLite 兼容 | 结构化业务数据、列表、离线缓存 | 视设备（通常 GB 级） | 支持事务、多线程 |
| **KV Store** | 键值数据库 | 高性能 KV、大量小数据 | 较大 | 高性能 |
| **Distributed KVStore** | 分布式 KV | 跨设备同步 | 受限 | 自动同步 |
| **文件（fs）** | 二进制 | 图片、视频、大文件 | 设备容量 | 需自行管理并发 |
| **DataShare** | 跨应用数据共享 | 供其他应用查询 | 受限 | URI 授权 |

> **面试话术**："存储选型的第一原则是看数据形态。少量配置用首选项，结构化、需要查询和事务的业务数据用关系型数据库，大文件走文件系统，跨设备共享用分布式 KVStore。首选项有明确的容量上限——单 key 8KB、总量 1MB，这是我在实际项目里踩过的坑，超限会静默失败。"

## 二、首选项 Preferences

### 2.1 基本用法

```ts
import { preferences } from '@kit.ArkData';
import { common } from '@kit.AbilityKit';
import { BusinessError } from '@kit.BasicServicesKit';

class PrefsService {
  private store: preferences.Preferences | undefined = undefined;

  // 1. 获取实例
  async init(context: common.UIAbilityContext): Promise<void> {
    try {
      this.store = await preferences.getPreferences(context, {
        name: 'my_prefs'          // ★ 文件名，会生成 my_prefs.xml
        // dataGroupId: 'group1'  // 可选：数据分组（API 10+）
      });
    } catch (err) {
      console.error(`Preferences 获取失败: ${(err as BusinessError).code}`);
    }
  }

  // 2. 写
  async put(): Promise<void> {
    await this.store?.put('token', 'abc123');
    await this.store?.put('count', 10);
    await this.store?.put('user', { id: 1, name: 'Tom' } as preferences.ValueType);
    await this.store?.flush();     // ★ 手动落盘
  }

  // 3. 读
  async get(): Promise<preferences.ValueType | undefined> {
    const token = await this.store?.get('token', 'default');
    const count = await this.store?.get('count', 0);
    return token;
  }

  // 4. 删
  async remove(): Promise<void> {
    await this.store?.delete('token');
    await this.store?.clear();
  }

  // 5. 订阅变化
  subscribe(): void {
    this.store?.on('change', (preferences: preferences.Preferences) => {
      console.info('prefs changed');
    });
  }
}
```

### 2.2 内存实例与磁盘实例的区别（重要）

```ts
// 磁盘实例：会持久化到文件
const diskStore = await preferences.getPreferences(context, { name: 'disk' });

// 内存实例：不落盘（API 10+）
const memStore = await preferences.getPreferences(context, { name: 'mem', dataType: preferences.DataType.MEMORY });
```

### 2.3 首选项的缓存机制（高频面试题）

**首选项在内存中有一份缓存**，`put` 只是改内存，`flush` 才写盘。

```ts
// 写入
await store.put('key', 'value');
await store.flush();     // 落盘

// 或者
await store.put('key', 'value', flush);   // flush = true 时立即落盘
```

**读取时**：
- `get()` 读的是**内存缓存**。
- `getSync()` / `getPreferencesSync()` 同理。
- 若需要确保读到磁盘最新值，先 `flush`。

**多实例并发**：
- 同一个 `name` 的 Preferences **建议全应用只创建一个实例**，避免多实例各自持有缓存导致数据不一致。
- 不同实例写同一文件会有覆盖风险。

> **面试话术**："首选项是内存缓存 + 异步落盘的模型，put 不保证立刻写到磁盘，必须 flush。所以遇到'杀进程后数据丢了'的问题，首先检查有没有 flush。规范做法是在仓库层统一封装，暴露的写方法内部一律 await flush。"

### 2.4 容量限制

- **单个 value ≤ 8KB**
- **单个文件 ≤ 1MB**

超限会抛异常或静默失败。实际项目对策：**大 JSON 放文件或数据库，首选项只存索引/开关**。

## 三、关系型数据库 RDB

### 3.1 核心概念

HarmonyOS 的 RDB 基于 **SQLite**，使用 **关系型数据库 (RelationalStore)** API。

**三要素**：
1. **RdbStore**：数据库实例
2. **Table**：表
3. **RdbPredicates**：查询条件（SQL WHERE 的对象化封装）

### 3.2 完整示例

```ts
import { relationalStore } from '@kit.ArkData';
import { common } from '@kit.AbilityKit';
import { BusinessError } from '@kit.BasicServicesKit';

export class DBService {
  private store: relationalStore.RdbStore | undefined = undefined;

  async init(context: common.UIAbilityContext): Promise<void> {
    try {
      this.store = await relationalStore.getRdbStore(context, {
        name: 'app.db',
        securityLevel: relationalStore.SecurityLevel.S1   // ★ 数据分级
      });
      await this.createTables();
    } catch (err) {
      console.error(`RDB 初始化失败: ${(err as BusinessError).code}`);
    }
  }

  private async createTables(): Promise<void> {
    if (!this.store) return;
    const db = this.store;

    // 建表
    await db.executeSql(`CREATE TABLE IF NOT EXISTS todo (
      id INTEGER PRIMARY KEY AUTOINCREMENT,
      title TEXT NOT NULL,
      done INTEGER DEFAULT 0,
      createdAt INTEGER
    )`);

    // 索引
    await db.executeSql('CREATE INDEX IF NOT EXISTS idx_todo_done ON todo(done)');
  }

  // 插入
  async insert(todo: Todo): Promise<number> {
    const db = this.store;
    if (!db) return -1;

    const values: relationalStore.ValuesBucket = {
      title: todo.title,
      done: todo.done ? 1 : 0,
      createdAt: Date.now()
    };
    return db.insert('todo', values);
  }

  // 查询
  async query(done: boolean): Promise<Todo[]> {
    const db = this.store;
    if (!db) return [];

    const predicates = new relationalStore.RdbPredicates('todo');
    predicates.equalTo('done', done ? 1 : 0);
    predicates.orderByDesc('createdAt');

    const result = await db.query(predicates, ['id', 'title', 'done', 'createdAt']);
    // result 是 ResultSet，需要逐行读取
    const todos: Todo[] = [];
    if (result.goToFirstRow()) {
      do {
        todos.push({
          id: result.getLong(result.getColumnIndex('id')),
          title: result.getString(result.getColumnIndex('title')),
          done: result.getLong(result.getColumnIndex('done')) === 1,
          createdAt: result.getLong(result.getColumnIndex('createdAt'))
        });
      } while (result.goToNextRow());
    }
    result.close();     // ★ 必须关闭
    return todos;
  }

  // 更新
  async update(id: number, done: boolean): Promise<number> {
    const db = this.store;
    if (!db) return 0;

    const predicates = new relationalStore.RdbPredicates('todo');
    predicates.equalTo('id', id);

    const values: relationalStore.ValuesBucket = { done: done ? 1 : 0 };
    return db.update(values, predicates);
  }

  // 删除
  async delete(id: number): Promise<number> {
    const db = this.store;
    if (!db) return 0;
    const predicates = new relationalStore.RdbPredicates('todo');
    predicates.equalTo('id', id);
    return db.delete(predicates);
  }

  // 事务
  async batchInsert(todos: Todo[]): Promise<void> {
    const db = this.store;
    if (!db) return;

    db.beginTransaction();
    try {
      for (const t of todos) {
        await this.insert(t);
      }
      db.commit();
    } catch (e) {
      db.rollBack();
      throw e;
    }
  }
}
```

### 3.3 RdbPredicates 条件构造

```ts

p.equalTo('age', 18);

p.greaterThanOrEqualTo('age', 18);
```

### 3.4 安全级别（SecurityLevel）—— 面试加分

HarmonyOS 按数据敏感度分级，不同级别有不同保护：

| 级别 | 名称 | 适用 | 保护强度 |
|---|---|---|---|
| **S1** | 普通 | 公开数据 | 低 |
| **S2** | 进阶 | 内部数据 | 中 |
| **S3** | 高阶 | 敏感数据 | 高 |
| **S4** | 核心 | 核心数据（如支付） | 最高 |

> **面试话术**："HarmonyOS 有数据分级保护机制，数据库可以按 SecurityLevel 划分，不同级别在设备锁定、账户切换等场景下的保护策略不同。涉及支付、身份信息的核心数据应该用 S4，开发和业务系统配合已有的分级规范落地。"

### 3.5 事务

```ts
// 方式 1：显式

  await db.insert('t', values);

  db.rollBack();

// 方式 2：API 12+ 的事务回调形式（更安全，自动提交/回滚）
```

```ts
import { kvManager } from '@kit.ArkData';
```

**与 Preferences 的区别**：
- KV Store 性能更高（原生 C++ 实现），支持更大数据量。
- 不需要 XML 序列化，值可以是 ArrayBuffer（存图片/二进制）。
- 更适合做**本地缓存**。

### 5.1 DistributedKVStore

```ts
// 监听同步变化

  console.info(`远端变更: ${event.keys}`);

```

### 5.2 分布式数据同步的机制

- 需要**同一华为账号**登录。
- 需要设备在**同一局域网**或通过云端中继。
- 同步是**最终一致**的，不是强一致。
- 冲突解决策略由系统处理（最后写入优先）。

> **面试话术**："分布式数据是'最终一致'模型，不是分布式事务。跨设备同步靠软总线+云端中继，同步有延迟，所以设计上适合'剪贴板、收藏、最近浏览'这类弱一致场景，不适合做锁、余额等强一致业务。"

## 八、实际项目的数据层设计（面试项目经验）

### 8.1 Repository 模式

```ts
// 仓库接口
export interface TodoRepository {
  getTodos(): Promise<Todo[]>;
  addTodo(todo: Todo): Promise<void>;
  updateTodo(todo: Todo): Promise<void>;
  deleteTodo(id: number): Promise<void>;
  sync(): Promise<void>;
}

// 实现：本地优先 + 网络同步
export class TodoRepositoryImpl implements TodoRepository {
  private db: DBService;
  private api: ApiService;

  constructor(db: DBService, api: ApiService) {
    this.db = db;
    this.api = api;
  }

  // ★ 本地优先（Local-First）：先读本地，立即返回
  async getTodos(): Promise<Todo[]> {
    return this.db.query(false);
  }

  // 写：先本地，后台同步
  async addTodo(todo: Todo): Promise<void> {
    await this.db.insert(todo);
    this.sync();          // 不 await，避免阻塞 UI
  }

  // 同步：拉取服务端数据并合并
  async sync(): Promise<void> {
    try {
      const remote = await this.api.fetchTodos();
      await this.db.batchInsert(remote);
    } catch (e) {
      console.error('同步失败，使用本地缓存');
    }
  }
}
```

### 8.2 三层数据策略

| 层级 | 技术 | 内容 | 生命周期 |
|---|---|---|---|
| **内存** | `@Local` / `@State` / AppStorage | UI 展示数据 | 页面/应用 |
| **本地持久化** | RDB / Preferences / 文件 | 业务数据、缓存 | 应用生命周期 |
| **远端** | HTTP / 云端 DB | 权威数据源 | — |

### 8.3 缓存策略

```ts
// 缓存 + 过期时间
interface CacheEntry<T> {
  data: T;
  timestamp: number;
  ttl: number;
}

async function getWithCache<T>(
  key: string,
  fetcher: () => Promise<T>,
  store: preferences.Preferences
): Promise<T> {
  const raw = await store.get(key, '');
  if (raw) {
    const entry = JSON.parse(raw as string) as CacheEntry<T>;
    if (Date.now() - entry.timestamp < entry.ttl) {
      return entry.data;      // 命中缓存
    }
  }
  const data = await fetcher();
  const entry: CacheEntry<T> = { data, timestamp: Date.now(), ttl: 5 * 60 * 1000 };
  await store.put(key, JSON.stringify(entry));
  await store.flush();
  return data;
}
```

## 九、数据管理常见坑

| 坑 | 现象 | 原因 | 解决 |
|---|---|---|---|
| Preferences 数据丢失 | 杀进程后没了 | 没 `flush()` | 写完 flush / 统一封装仓库 |
| 首选项超限 | 写入失败无提示 | 单 key >8KB / 总 >1MB | 大数据放文件或 RDB |
| 首选项多实例不一致 | 读到旧值 | 多实例各持缓存 | 全局单实例 |
| RDB 查询内存泄漏 | 内存持续涨 | ResultSet 没 close | `result.close()` |
| 数据库升级丢数据 | 升级后表结构错 | 忘了改 version + onUpgrade | 版本号与 ALTER 同步 |
| 多实例 RDB 写入冲突 | 数据覆盖 | 未用事务/锁 | 用事务；或单例 store |
| 沙箱路径不对 | 找不到文件 | 用错目录 API | `context.filesDir` 等 |
| 存储权限申请被拒 | 用不了外部存储 | 鸿蒙无外部存储权限概念 | 用 Picker / UserFile |
| JSON 序列化循环引用 | 报错 | 对象有环 | 用 WeakMap 或精简对象 |

## 十一、参考答案要点

1. 首选项：少量配置/KV，单 key 8KB、总 1MB；RDB：结构化业务数据、支持事务与查询；KV Store：高性能本地缓存、支持二进制；文件：大文件/媒体。选型看数据形态和是否需要查询/事务。
2. put 只修改内存缓存，flush 才写磁盘。首选项是"内存缓存 + 异步落盘"模型，不 flush 会在进程被杀时丢失。
3. 单 key ≤ 8KB，单文件 ≤ 1MB。超限应把大数据移到文件或 RDB，首选项只存索引/开关。
4. RdbPredicates 是 SQL WHERE 条件的对象化封装。常用：equalTo、notEqualTo、greaterThan、between、like、isNull、in、orderByAsc/Desc、limitAs/offsetAs、beginGroup/endGroup。
5. ResultSet 持有底层游标资源，不关闭会导致句柄泄漏、内存持续增长。
6. 提高 StoreConfig.version，在 onUpgrade 中按版本号增量执行 ALTER TABLE / CREATE TABLE。忘记改 version 会导致升级回调不执行，表结构与代码不匹配，运行时报错。
7. S1 普通（公开数据）、S2 进阶（内部数据）、S3 高阶（敏感数据）、S4 核心（核心敏感数据如支付）。保护策略随设备锁定、账号切换等场景变化。
8. 最终一致（非强一致）。适用于剪贴板、收藏、最近浏览等弱一致场景；不适合余额、锁等强一致业务。
9. 通过系统 Picker（DocumentViewPicker、PhotoViewPicker）让用户主动选择并授权具体文件/目录；沙箱外的文件必须经此路径访问。鸿蒙没有粗粒度的"存储权限"概念。
10. DataShare 用于跨应用共享数据查询。需要在 module.json5 的 extensionAbilities 中声明 type: "dataShare" 和 uri（如 datashare://bundleName/path），并配置相应权限。
11. 本地优先 = 先读本地立即渲染，后台同步远端。优点是启动快、离线可用、交互跟手；现代 App 普遍采用（Instagram/Notion 等）。

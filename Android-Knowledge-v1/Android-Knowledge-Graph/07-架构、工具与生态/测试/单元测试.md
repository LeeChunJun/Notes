# 单元测试

## 一句话定义

单元测试是对**最小可测单元**（纯逻辑类、函数、ViewModel）做自动化验证；Android 上它应当**跑在 JVM 上、不依赖模拟器、毫秒级返回**，是保障重构安全与 CI 质量的第一道防线。

## 核心原理

### 1. 测试金字塔与成本

```text
        △
        │  E2E / UI 测试        （少而精，覆盖关键链路）
       ╱ ╲    慢（分钟级）、脆弱、维护贵
      ╱   ╲
     ╱ 集成测试 ╲                （适中，验证模块间协作）
    ╱           ╲
   ╱  单元测试    ╲              （多而快，覆盖业务逻辑）
  ╱               ╲
```

| 类型 | 运行环境 | 速度 | 稳定性 | 覆盖目标 |
| --- | --- | --- | --- | --- |
| 单元测试 | JVM（纯） | **毫秒~秒** | 高 | 业务逻辑、ViewModel、Reducer、工具类 |
| 集成测试 | JVM + Robolectric | 秒级 | 中高 | 涉及 Android 框架 API 的逻辑 |
| 组件测试（Instrumented） | 模拟器/真机 | 分钟级 | 中 | Activity/Fragment 交互 |
| UI 测试（Espresso/Compose） | 模拟器/真机 | 分钟级 | 中低 | 界面行为、端到端流程 |

> **原则**：能在 JVM 上测的，绝不上模拟器。这是 CI 速度与稳定性的生命线。

### 2. Android 单元测试的分类

```text
src/test/          ← 本地单元测试（JVM，无 Android 依赖）
    └── 只能访问纯 JVM API；调用 android.* 会抛 "not mocked" 异常
        └─ 例外：android.jar 里未被 mock 的方法会返回默认值或抛异常
                 → 用 Robolectric 或 testOptions.unitTests.isReturnDefaultValues = true

src/androidTest/   ← 仪器测试（模拟器/真机上运行）
    └── 可以访问真实 Android 框架
```

`build.gradle.kts` 中的关键配置：

```kotlin
android {
    testOptions {
        unitTests {
            isIncludeAndroidResources = true   // 允许 Robolectric 读取资源
            isReturnDefaultValues = true       // 未 mock 的 android 方法返回默认值而非抛异常
        }
    }
}
```

### 3. 三大要素：Arrange-Act-Assert

```kotlin
@Test
fun `given valid user when login then returns token`() {
    // Arrange（准备）
    val repo = FakeUserRepository(token = "abc")
    val vm = LoginViewModel(repo)

    // Act（执行）
    vm.login("tom", "123456")

    // Assert（断言）
    assertEquals("abc", vm.uiState.value.token)
}
```

### 4. 常用测试框架与工具

| 工具 | 用途 | 特点 |
| --- | --- | --- |
| **JUnit4 / JUnit5** | 测试框架 | JUnit4 是 Android 默认；JUnit5 需 `useJUnitPlatform()` + `junit5` 插件 |
| **kotlin.test** | Kotlin 断言 | 与 JUnit 配合，`assertEquals` 等 |
| **Truth** | 断言库 | 断言信息更友好：`assertThat(x).isEqualTo(y)` |
| **MockK** | Mock 框架（Kotlin 优先） | 语法简洁，支持协程、DSL、relaxed mock |
| **Mockito** | Mock 框架 | Java 生态成熟，Kotlin 使用需 `mockito-kotlin` |
| **Robolectric** | Android 框架模拟 | 在 JVM 上模拟 Android SDK（Resources、SharedPreferences、Shadow） |
| **Turbine** | Flow 测试 | `flow.test { assertEquals(x, awaitItem()) }` |
| **kotlinx-coroutines-test** | 协程测试 | `runTest`、`StandardTestDispatcher`、`advanceUntilIdle` |
| **MockWebServer** | HTTP 模拟 | OkHttp 官方，录制/回放 HTTP |
| **Room in-memory DB** | 数据库测试 | `Room.inMemoryDatabaseBuilder(context, Xxx::class.java).allowMainThreadQueries()` |

### 5. 协程测试：`runTest` 与调度器控制

```kotlin
class LoginViewModelTest {

    private val dispatcher = StandardTestDispatcher()

    @Before
    fun setUp() = Dispatchers.setMain(dispatcher)

    @After
    fun tearDown() = Dispatchers.resetMain()

    @Test
    fun `login success`() = runTest(dispatcher) {
        val vm = LoginViewModel(FakeUserRepo())

        vm.login("tom", "pwd")
        advanceUntilIdle()          // 推进所有挂起的协程

        assertTrue(vm.uiState.value.isLoggedIn)
    }
}
```

要点：

1. **`Dispatchers.setMain(dispatcher)`**：`viewModelScope` 用的是 `Dispatchers.Main`，JVM 上没有主线程 → 必须替换，否则协程根本不启动。
2. **`advanceUntilIdle()`**：推进到所有协程完成（`runTest` 结束时会自动调用，但断言前需要显式调用）。
3. **`advanceTimeBy()`**：只推进指定时间，用于测延时逻辑。
4. **`UnconfinedTestDispatcher`**：立即执行，便于断言顺序；`StandardTestDispatcher`（默认）需要显式推进。

### 6. Flow 测试：Turbine

```kotlin
@Test
fun `emits loading then success`() = runTest {
    val vm = UserListViewModel(FakeUserRepo())

    vm.uiState.test {
        assertEquals(true, awaitItem().loading)
        advanceUntilIdle()
        assertEquals(2, awaitItem().users.size)
        cancelAndIgnoreRemainingEvents()
    }
}
```

- `awaitItem()`：等待下一个发射值；`awaitComplete()`：等待流结束。
- **避免用 `first()` 断言**（只能拿到第一个值），`Turbine` 能断言**完整序列**。

### 7. MockK 常用写法

```kotlin
// 1. 创建 mock
val repo = mockk<UserRepository>()

// 2. 桩（stub）
every { repo.getUsers() } returns listOf(User("1", "Tom"))

// 3. 协程函数
coEvery { repo.login(any(), any()) } returns Result.success("token")

// 4. 验证
verify { repo.getUsers() }
verify(exactly = 1) { repo.getUsers() }
confirmVerified(repo)

// 5. relaxed mock：未显式桩的方法返回默认值，不抛异常
val relaxed = mockk<SomeService>(relaxed = true)

// 6. 捕获参数
val slot = slot<String>()
every { repo.login(capture(slot), any()) } returns Result.success("t")
repo.login("tom", "pwd")
assertEquals("tom", slot.captured)
```

> **Mock vs Fake 的选择**：
> - **Mock**：验证"交互"（是否调用、参数是什么）→ 适合 Repository 接口层。
> - **Fake**：提供**简化但真实**的实现 → 适合 ViewModel 测试，断言结果更可靠。
> - 建议：**优先写 Fake**（手写的内存实现），Mock 只在验证交互时使用。

## 代码示例

### 1. 业务逻辑类的纯单元测试

```kotlin
class PasswordValidator {

    sealed interface Result {
        object Valid : Result
        data class TooShort(val min: Int) : Result
        data class MissingNumber : Result
        data class MissingUpperCase : Result
    }

    fun validate(password: String): Result = when {
        password.length < 8 -> Result.TooShort(8)
        !password.any { it.isDigit() } -> Result.MissingNumber
        !password.any { it.isUpperCase() } -> Result.MissingUpperCase
        else -> Result.Valid
    }
}

// 测试
class PasswordValidatorTest {
    private val validator = PasswordValidator()

    @Test
    fun `short password is invalid`() {
        assertEquals(PasswordValidator.Result.TooShort(8), validator.validate("abc"))
    }

    @Test
    fun `valid password passes`() {
        assertEquals(PasswordValidator.Result.Valid, validator.validate("Abcdef12"))
    }
}
```

### 2. ViewModel 测试（Fake + 协程测试）

```kotlin
class FakeUserRepository(
    private val result: List<User> = listOf(User("1", "Tom"), User("2", "Jerry"))
) : UserRepository {
    var callCount = 0
    override suspend fun getUsers(): List<User> {
        callCount++
        return result
    }
}

class UserListViewModelTest {

    private val dispatcher = StandardTestDispatcher()
    private val repo = FakeUserRepository()

    @Before
    fun setUp() = Dispatchers.setMain(dispatcher)

    @After
    fun tearDown() = Dispatchers.resetMain()

    @Test
    fun `loading is false and users present after refresh`() = runTest(dispatcher) {
        val vm = UserListViewModel(repo)

        vm.refresh()
        advanceUntilIdle()

        val state = vm.uiState.value
        assertFalse(state.loading)
        assertEquals(2, state.users.size)
        assertNull(state.error)
        assertEquals(1, repo.callCount)
    }

    @Test
    fun `error state is set when repository throws`() = runTest(dispatcher) {
        val failing = object : UserRepository {
            override suspend fun getUsers(): List<User> = throw IOException("network down")
        }
        val vm = UserListViewModel(failing)

        vm.refresh()
        advanceUntilIdle()

        assertEquals("network down", vm.uiState.value.error)
        assertFalse(vm.uiState.value.loading)
    }
}
```

### 3. Repository 测试（MockWebServer）

```kotlin
class UserApiTest {

    private lateinit var server: MockWebServer
    private lateinit var api: UserApi

    @Before
    fun setup() {
        server = MockWebServer()
        server.start()
        val retrofit = Retrofit.Builder()
            .baseUrl(server.url("/"))
            .addConverterFactory(MoshiConverterFactory.create())
            .build()
        api = retrofit.create(UserApi::class.java)
    }

    @After
    fun teardown() = server.shutdown()

    @Test
    fun `returns users on success`() {
        server.enqueue(
            MockResponse().setBody("""{"items":[{"id":"1","name":"Tom"}]}""")
                .setResponseCode(200)
        )

        val result = runBlocking { api.getUsers() }

        assertEquals(1, result.items.size)
        assertEquals("Tom", result.items[0].name)
    }

    @Test
    fun `throws on 500`() {
        server.enqueue(MockResponse().setResponseCode(500))

        val result = runBlocking { runCatching { api.getUsers() } }

        assertTrue(result.isFailure)
    }
}
```

## 常见问题 / 面试要点

**读者问：Android 的单元测试和普通 JVM 单元测试有什么区别？为什么有些测试会报 "not mocked"？**

**AI答：**

1. **区别**：Android 项目里 `src/test/` 跑在 **JVM** 上，使用的是 `android.jar` 的**桩版本（stub）**——里面的方法要么**抛异常**（`RuntimeException("Stub!")`），要么**返回默认值**。
2. **"not mocked" 的原因**：单元测试默认**不运行 Android 框架**，你调用 `TextUtils.isEmpty()`、`Log.d()`、`Uri.parse()` 等方法就会炸。
3. **三种解决方案**：
   - **`isReturnDefaultValues = true`**（最快）：未 mock 的方法返回 `null`/`0`/`false` 而不是抛异常。适合只关心自己逻辑的场景。**但要注意返回值可能是"假"的**，断言时要小心。
   - **Robolectric**（推荐）：在 JVM 上提供**真实的 Android 框架实现**（通过下载对应 SDK 的 android-all jar），支持资源、SharedPreferences、Activity 生命周期（用 `ActivityScenario`）。
   - **把该逻辑移出 Android 依赖**：最佳解法——把工具类写成**纯 Kotlin**（接收 `String` 而不是 `Uri`），彻底不需要 Android 环境。
4. **面试加分**："Android 单测的核心限制是**不能访问真实 Android 框架**，解决办法有三档：返回默认值、Robolectric、以及**最好的一档——重构掉 Android 依赖**。"

---

**读者问：`Dispatchers.setMain()` 是什么？为什么不设置就会失败？**

**AI答：**

1. **原因**：`viewModelScope` 使用 `Dispatchers.Main.immediate`。在 JVM 单元测试中**没有 Android 主线程**，Android 的 `Dispatchers.Main` 会因为找不到 `Looper.getMainLooper()` 而抛异常：
   `IllegalStateException: Module with the Main dispatcher had failed to initialize`。
2. **`setMain` 的作用**：把 `Dispatchers.Main` 替换成测试用的调度器，让 `viewModelScope.launch` 能真正启动协程。

```kotlin
@Before
fun setUp() = Dispatchers.setMain(StandardTestDispatcher())

@After
fun tearDown() = Dispatchers.resetMain()
```

3. **必须 `resetMain()`**：否则测试之间的主线程调度器会互相污染，导致"单测单独跑通过、一起跑失败"这类**幽灵 bug**。
4. **`StandardTestDispatcher` vs `UnconfinedTestDispatcher`**：
   - `StandardTestDispatcher`（默认）：协程**不会自动执行**，需要 `advanceUntilIdle()` / `runCurrent()` 推进 → **可控**，适合断言中间状态。
   - `UnconfinedTestDispatcher`：`launch` 后立即执行到第一个挂起点 → 适合简单的顺序断言。
5. **注意**：`runTest(dispatcher)` 传入调度器后，`runTest` 内部会自动用虚拟时间推进（`advanceUntilIdle` 在 `runTest` 结束时自动调用），但**断言之前**仍建议显式 `advanceUntilIdle()`。

---

**读者问：Mock、Fake、Stub 有什么区别？什么时候用哪个？**

**AI答：**

1. **术语区分**（Martin Fowler 的定义）：
   - **Dummy**：只为了传参，**什么都不做**。
   - **Stub**：**返回预设结果**（"喂数据"）。
   - **Spy**：Stub + **记录调用**（事后验证交互）。
   - **Mock**：**预设期望**，不符合预期就**测试失败**（如"必须调用 `save()` 一次"）。
   - **Fake**：**简化但真实可用**的实现（内存版数据库、内存版文件系统）。
2. **Android 实践中的选择**：
   - **测试 ViewModel / 业务逻辑 → 优先 Fake**：手写 `FakeUserRepository`，断言**输出状态**，而不是验证交互。这样测试更稳定，重构时不易碎。
   - **测试 Repository / 网络层 → 用 MockWebServer**：它是一个"真实"的假服务器（Fake），能验证请求路径、Header、JSON 解析。
   - **测试"是否调用了埋点/保存" → 用 Mock**：验证交互。
   - **第三方 SDK（如支付 SDK）→ 用 Mock**：因为无法 Fake 整个 SDK。
3. **MockK vs Mockito**：
   - **MockK**：Kotlin 优先，语法简洁（`every {}`/`coEvery {}`），支持协程、密封类、扩展函数 DSL；
   - **Mockito**：Java 生态成熟，Android 官方文档示例多用它，但 Kotlin 用起来啰嗦（需 `mockito-kotlin` 扩展）。
4. **面试表达**："**Fake 验证结果，Mock 验证交互。业务测试优先 Fake，因为它对重构更宽容。**"

---

**读者问：怎么提高单元测试的实用价值？有什么实践准则？**

**AI答：**

给 6 条可落地的准则：

1. **测行为，不测实现**：
   - 断言"调用 `save()` 之后状态是已保存"，而不是断言"内部调用了某个私有方法" → 重构不会导致测试大面积变红。
2. **测试名即文档**：
   - 用"given-when-then"或"场景-预期"命名：`given logged out when submit empty then shows error`。
3. **每个测试只断言一件事**：
   - 一个测试多个断言，失败时定位困难。
4. **测试之间完全独立**：
   - 每个测试自己准备数据（`@Before` 里 new），不依赖执行顺序。
5. **边界值优先**：
   - 空字符串、0、负数、超长、null、并发冲突 —— 这些是 bug 高发区。
6. **覆盖率当参考，不当 KPI**：
   - 关注**核心业务逻辑的分支覆盖率**，而不是总行覆盖率。

再补一条**组织建议**：把测试放在**与被测类同包**的 `src/test/java/com/example/xxx/` 下，用 `XxxTest` 命名，与生产代码**一起 Review**（测试代码和实现同时改）。

---

**读者问：单测、UI 测试、Compose 测试怎么分工？覆盖率目标怎么定？**

**AI答：**

1. **分工**（金字塔）：
   - **单元测试（70%+）**：ViewModel、Reducer、UseCase、工具类、Repository 逻辑 → **JVM，毫秒级**。
   - **集成测试（20%）**：Room、Retrofit+MockWebServer、Hilt 依赖装配 → JVM + Robolectric。
   - **UI / E2E 测试（10%）**：关键业务链路（登录 → 下单 → 支付）→ 模拟器，**少而精**。
2. **Compose 测试的定位**：属于 UI 测试，但**运行在设备/模拟器上**（`androidTest`），或用 Robolectric 做 JVM 版（`robolectric` + `createComposeRule`，快但能力受限）。详见 [[Compose测试]]。
3. **覆盖率目标（务实版）**：
   - **domain / ViewModel 层**：行覆盖 ≥ 80%，**分支覆盖 ≥ 70%**；
   - **UI 层**：不追求行覆盖，用 **E2E 场景覆盖**代替；
   - **整体**：≥ 60%，且**不下降**（用 CI 门禁卡住）。
4. **CI 门禁**：测试失败必须阻断合并；覆盖率**下降超过阈值**（如 1%）也阻断。
5. **一句关键话**："**不要用覆盖率数字替代测试质量。** 100% 覆盖率的断言全为 `assertTrue(true)` 毫无价值；**核心业务路径有测试、边界有测试、回归有测试** 才是真的质量保障。"

# 逆向工具

## 一句话定义

逆向工程工具链是一套用于**分析 APK/DEX、查看字节码、动态 Hook 运行时、抓取与解密网络流量**的工具集合；掌握它既是安全研究的需要，也是理解"自己的 App 在别人眼里长什么样"的必要功课。

## 核心原理

### 1. Android 逆向的对象与流程

```text
APK (zip)
├── AndroidManifest.xml  (二进制 AXML) ──► apktool / aapt2 ──► 可读文本
├── classes.dex          (Dalvik 字节码) ─► jadx / dex2jar ──► Java 伪代码
│   └── (多 dex: classes2.dex ...)
├── resources.arsc        (二进制资源) ───► apktool / aapt2 ──► 可读资源
├── lib/armeabi-v8a/*.so  (native 代码) ──► Ghidra / IDA ─────► 汇编
└── assets/               (未压缩资源)
```

### 2. 静态分析工具

| 工具 | 类型 | 平台 | 用途 |
| --- | --- | --- | --- |
| **jadx** | DEX → Java 伪代码 | 跨平台（Java） | **首选**：开源、功能全、可直接搜字符串/GUID/URL |
| **apktool** | APK → smali + 资源 | 跨平台（Java/脚本） | 反编译资源、**反编译成 smali 再回编译**（改包、Hook 前提） |
| **aapt2 / aapt** | 资源与 Manifest 解析 | Android SDK | 查看包名、权限、版本、签名信息 |
| **dex2jar + JADX** | DEX → JAR | 跨平台 | 老方案，现在基本被 jadx 取代 |
| **enjarify** | DEX → 混淆 | | 谷歌出品，处理 ODEX/ART |
| **Ghidra** | native 逆向 | 跨平台（Java） | NSA 开源，反编译 .so、分析 Native 代码 |
| **IDA Pro** | native 逆向 | 商业 | 业界标准，配合 Hex-Rays 伪代码 |
| **JEB** | 全栈 | 商业 | 商业级 DEX + native 逆向 |
| **Frida** | 动态 Hook | 跨平台 | 运行时注入、Hook 方法、改参数 |
| **LSPosed / Xposed** | 框架级 Hook | Android | 系统级 Hook，持久化模块 |
| **mitmproxy / Charles / Burp** | 抓包 | 跨平台 | HTTP(S) 抓包与改包 |
| **Android Studio Build Analyzer / APK Analyzer** | 体积分析 | 官方 | 依赖与体积分析 |
| **Androguard** | Python 库 | 跨平台 | 脚本化分析 APK/DEX |
| **MobSF** | 自动化安全分析 | Web | 一键静态+动态扫描 |

### 3. jadx 的核心用法

```bash
# 打开 APK 或 DEX
jadx-gui app-release.apk

# 命令行反编译
jadx -d out/ app-release.apk

# 只导出某个类的源码
jadx --single-class com.example.pay.PayHelper app-release.apk

# 搜索特定字符串（Grep / --export-gradle）
jadx --export-gradle -d out/ app-release.apk
```

**实战技巧**：

1. **全局搜索关键字符串**：域名、API 路径、密钥名、"prod"、"secret"、"encrypt"。
2. **搜索 GUID / 资源 ID**：定位被混淆代码的原始含义。
3. **看 `R` 类**：资源 ID 与名字的对应关系。
4. **重点看 `Application` 类**：初始化逻辑、热修复入口、第三方 SDK 初始化。
5. **看签名校验、Root 检测、Hook 检测**：见下文。

### 4. apktool：反编译 smali 与回编译

```bash
# 反编译（资源 + smali）
apktool d app-release.apk -o out

# 改 smali 后回编译
apktool b out -o patched.apk

# 签名（先 zipalign 再 apksigner）
zipalign -p 4 patched.apk aligned.apk
apksigner sign --ks my.keystore --ks-pass pass:xxx aligned.apk
```

**典型用途**：
- 查看**混淆后**的真实控制流（jadx 的伪代码在复杂控制流下可能失真，smali 是真实字节码）；
- 修改 `AndroidManifest.xml`（加权限、改组件名）做**权限提升测试**；
- **绕过签名校验**（改 smali 中的 `verify` 逻辑）用于研究；
- 分析**加固/加壳** App（脱壳是另一套技术，见第 7 节）。

### 5. Frida：动态 Hook 的核心

Frida 让你能**在运行时**注入脚本，Hook Java/Kotlin 方法、native 函数，修改参数与返回值。

```bash
# 安装
pip install frida-tools
frida --version

# 附加到进程
frida -U -f com.example.app -l hook.js          # -f 启动并注入（spawn）
frida -U -p <pid> -l hook.js                     # 附加已运行进程
frida -U -n "App Name" -l hook.js

# 列出设备与应用
frida-ps -Uai
```

**Hook Java 方法示例**：

```javascript
// hook.js
Java.perform(function () {
    const LoginActivity = Java.use("com.example.login.LoginActivity");

    LoginActivity.checkPassword.implementation = function (pwd) {
        console.log("original pwd = " + pwd);
        return this.checkPassword("123456");   // 固定返回
    };

    // 打印所有调用
    const Log = Java.use("android.util.Log");
    Log.d.overload("java.lang.String", "java.lang.String").implementation =
        function (tag, msg) {
            console.log("[Log] " + tag + ": " + msg);
            return this.d(tag, msg);
        };
});
```

**Hook native 函数**：

```javascript
var addr = Module.findBaseAddress("libnative.so");
var func = Module.findExportByName("libnative.so", "nativeEncrypt");
Interceptor.attach(func, {
    onEnter: function (args) {
        console.log("nativeEncrypt called, arg0 = " + args[0]);
    },
    onLeave: function (retval) {
        console.log("nativeEncrypt returned " + retval);
    }
});
```

**常见用途**：
- 查看/修改运行时数据（密码、token、请求参数）；
- 绕过签名校验、Root/Hook 检测；
- 抓取加密前的明文（在 encrypt 之前 hook）；
- 定位崩溃（配合 `frida-trace`）。

### 6. 抓包与流量分析

| 工具 | 特点 |
| --- | --- |
| **Charles** | GUI 友好，支持 Map/Compose 限速、断点改包、SSL Proxying |
| **Burp Suite** | 功能最强（扫描、攻击），社区版有限制 |
| **mitmproxy** | **脚本化**（Python），可写规则自动改包/记录，CI 友好 |
| **HttpCanary / Packet Capture** | 手机端抓包（需 root 或 VPN 模式） |
| **PCAPdroid** | **无需 root**，用 VPN 抓包，App 不可绕过（除非 VPN 检测） |

**mitmproxy 脚本示例**：

```python
# modify.py —— 把 /v1/old 改成 /v2/new
def request(flow):
    if flow.request.path.startswith("/v1/old"):
        flow.request.path = flow.request.path.replace("/v1/old", "/v2/new")

def response(flow):
    if "api.example.com" in flow.request.pretty_host:
        print(flow.response.status_code, flow.request.path)
```

```bash
mitmproxy -s modify.py --listen-port 8080
```

**HTTPS 解密的前提**（详见 [[ADB]] 中的网络安全配置）：

- App 信任**用户 CA**（Android 7+ 需 debug 配置）；
- App **没有做 SSL Pinning**（有则需 Frida hook 或改代码绕过）；
- 未使用 **QUIC/HTTP3**（需禁用）。

### 7. 加固与脱壳

国内很多 App 会**加固**（加壳）：

| 加固方式 | 说明 | 脱壳思路 |
| --- | --- | --- |
| **DEX 加密** | 真实 dex 藏在 so/自定义格式里，启动时解密释放 | 内存 dump（Frida `frida-dexdump`）、在 `DexClassLoader` 处 hook |
| **VMP 虚拟化保护** | 关键方法字节码转为自定义虚拟机指令 | 极难，需要专用分析工具 |
| **函数抽取** | 只保护部分方法 | 定位壳的解密函数 |
| **代码混淆**（ProGuard/R8） | 改名、内联、控制流平坦化 | jadx + smali 分析 |

**脱壳通用手段**：

```javascript
// 内存中搜索 dex 头并 dump（思路示意）
Java.perform(function () {
    var DexFile = Java.use("dalvik.system.DexFile");
    DexFile.loadDex.overload("java.lang.String", "java.lang.String", "int", "java.lang.ClassLoader")
        .implementation = function (dexPath, optDir, flags, loader) {
            console.log("loadDex: " + dexPath);
            return this.loadDex(dexPath, optDir, flags, loader);
        };
});
```

> ⚠️ **合规提醒**：逆向与脱壳只应用于**自有应用的安全测试、授权的渗透测试或学术研究**。对他人商业 App 进行逆向、破解、绕过安全机制可能违反法律（著作权、反不正当竞争法、刑法）与 App 的用户协议。本笔记内容仅用于**理解自身产品的安全风险与防护**。

### 8. 从攻击者视角看防护（面试高频）

| 攻击手法 | 对应防护 |
| --- | --- |
| jadx 直接读逻辑 | **R8 混淆**（改类名/方法名/字符串加密） |
| smali 定位关键逻辑 | **控制流混淆**、字符串加密、指令重排 |
| 抓包看接口 | **HTTPS + 证书校验**、**SSL Pinning**、**Payload 加密** |
| Frida Hook 登录校验 | **运行时完整性校验**、**关键逻辑下沉到服务端** |
| 抓内存找密钥 | **密钥白盒化**、**服务端下发密钥**、不要硬编码 |
| 重打包分发 | **签名校验**、**包名/签名校验**、**渠道校验** |
| 模拟器/root 环境 | **设备环境检测**（但不能只依赖它） |
| 调试器附加 | **反调试**（`TracerPid` 检测、`ptrace` 自保护）、`Debug.isDebuggerConnected()` |

**关键的防守思想**（面试加分）：

1. **客户端的一切都可被篡改** → **核心业务校验必须在服务端**。
2. **混淆只是提高成本，不是万无一失**。
3. **检测与绕过永远在博弈** → 目标是提高攻击成本、缩短攻击窗口。
4. **多层次防护**：混淆（静态）+ 完整性校验（动态）+ 服务端校验（根本）。

### 9. 自查清单（保护自己的 App）

- [ ] release 构建**开启 R8 混淆 + 资源混淆 + 压缩**；
- [ ] **字符串加密**（API 地址、密钥名、关键常量不要明文）；
- [ ] **密钥不硬编码**（用 Android Keystore 或服务端下发）；
- [ ] **关键逻辑放服务端**（支付校验、额度计算、风控）；
- [ ] **证书校验**（可选 Pinning，注意可被绕过，只提高成本）；
- [ ] **防重打包**：运行时校验签名 + 包名（`PackageManager.getPackageInfo(GET_SIGNING_CERTIFICATES)`）；
- [ ] **Root / 模拟器 / Hook 检测**（作为风控信号，不作为唯一防线）；
- [ ] **日志脱敏**：不要在 release 里打印 token、密码、身份证；
- [ ] **代码完整性校验**：关键 dex / so 的 CRC 或签名校验；
- [ ] **定期用 jadx 检查自己的包**：看是否泄露敏感信息。

## 常见问题 / 面试要点

**读者问：Android 逆向的一般流程是什么？用哪些工具？**

**AI答：**

按**四阶段**答（这是标准流程，也是面试期望的结构）：

1. **静态分析（Static Analysis）**：
   - 用 **apktool** 解包 → 查看 `AndroidManifest.xml`（权限、四大组件、deeplink）、资源、smali；
   - 用 **jadx** 生成伪代码 → 搜字符串（域名、密钥、错误码）、看 `Application`、看混淆后的类结构；
   - 用 **aapt2** 查看包信息与签名；
   - 目标：搞清楚 App 的**功能结构、接口、关键逻辑位置**。
2. **动态分析（Dynamic Analysis）**：
   - 用 **Frida** 在运行时 Hook 关键方法、打印参数与返回值；
   - 用 **mitmproxy/Charles** 抓取并修改流量（注意 HTTPS 信任与 Pinning 问题）；
   - 用 **Xposed/LSPosed** 做持久化 Hook；
   - 目标：看**运行时真实行为**（比静态更准，因为能看到加密前的数据）。
3. **深度分析**：
   - **native 代码** → **Ghidra / IDA** 分析 .so；
   - **加固 App** → 脱壳（内存 dump）。
4. **漏洞挖掘与验证**：
   - 结合业务场景找风险（硬编码密钥、越权、支付校验在本地、组件导出未保护、deeplink 参数未校验）；
   - **动态验证**（PoC）。
5. **产出**：漏洞报告 + 修复建议 + **回归验证**。

---

**读者问：ProGuard/R8 混淆能防住逆向吗？防护的重点应该放在哪？**

**AI答：**

1. **混淆的作用**：把类名/方法名改成 `a`、`b`、`c`，去掉调试信息（行号、源文件名），**提高阅读成本**，但**不改变程序行为**。
2. **能防什么**：
   - **提高门槛**：逆向者要花时间理解 `a.java` 里到底做了什么；
   - **去掉线索**：无意义的 `SourceFile`/`LineNumberTable` 会让栈追踪变成 `Unknown Source`（**但这也会让你自己的线上崩溃堆栈失去可读性** → 需要单独处理）；
   - **移除未使用代码**（R8 tree-shaking）→ 减小体积，也顺带移除了一些不必要的攻击面。
3. **防不住什么**：
   - **字符串是明文**（除非额外做字符串加密）；
   - **控制流、算法逻辑、数据结构**依然可见；
   - 动态 Hook 可以**绕过混淆**（按签名 Hook，不关心类名）；
   - **服务端逻辑无法被混淆**。
4. **正确的防护重心（分四层）**：
   - **第 1 层：服务端**——**核心校验必须在服务端**（支付、额度、风控、密钥）。这是唯一根本性的防护。
   - **第 2 层：静态**——混淆 + 字符串加密 + 资源混淆 + 防重打包签名校验。
   - **第 3 层：动态**——Root/模拟器/Hook 检测、完整性校验、关键方法的服务端二次校验。
   - **第 4 层：运营**——风险监控、异常行为上报、灰度与快速回滚。
5. **面试金句**："**客户端是防线的一部分，不是防线本身。混淆能延缓攻击，但把校验放到服务端才能真正消除风险。**"

**读者问：Frida 的原理是什么？它怎么做到 Hook 的？**

**AI答：**

1. **注入方式**：
   - **`frida-server`**（或 `frida-gadget`）跑在设备上（需 root 或用 `frida-gadget` 集成进 APK）；
   - 通过 **USB/TCP 与 PC 上的 `frida` 客户端通信**；
   - 客户端把 JS 脚本发给设备，server 用 **V8/JavaScriptCore 引擎**（Frida 自带 QuickJS/V8）执行。
2. **Hook 的底层原理**：
   - **Java 层**：`Java.use()` 拿到类的包装，通过 `ART` 的**运行时 hook 机制**替换方法的入口（`art_method` 的 entry point），从而在调用原方法前后插入自己的逻辑 → 所以 Hook **不需要改 APK**。
   - **native 层**：`Interceptor.attach` 用 **inline hook**（覆盖函数开头的指令为跳转到 trampoline）实现，执行完再跳回原函数。
3. **能力**：
   - Hook 方法、修改参数与返回值、Hook 构造函数、替换整个方法实现；
   - 枚举类与对象、读取内存、dump 堆；
   - 拦截 `send`/`recv`、SSL 函数的明文。
4. **对抗与反制**（面试加分）：
   - **Frida 检测**：`/proc/self/maps` 里出现 `frida-agent`、`/proc/self/status` 的 `TracerPid`、端口 `27042` 监听、异常符号；
   - **反制手段**：检测后 `kill` 自身、修改内存权限、Hook Frida 自己的 API；
   - **攻防是持续的**：Frida 也有对抗手段（如 `frida-compile`、自定义 Gadget、名称混淆），**没有一劳永逸的检测**。
5. **合规提醒**：仅用于自有或授权目标。

**读者问：如果要给自己的 App 做安全测试，你会怎么做？**

**AI答：**

给一个**可执行的检查清单**（体现真实动手能力）：

1. **静态自查（不用任何第三方工具）**：
   - 用 **jadx 打开自己的 release 包**（**这一步就能暴露很多问题**）：
     - 搜 `http://`（明文 HTTP 域名）；
     - 搜 `key`、`secret`、`token`、`password`、`appkey`（硬编码密钥）；
     - 搜 `api.`、`base_url`（暴露服务端地址与内部环境）；
     - 看是否残留 `Log.d`（release 里打印敏感信息）。
   - 用 **apktool** 看 `AndroidManifest.xml`：多余权限、`exported=true` 的组件、`debuggable=true` 泄漏。
2. **动态自查**：
   - **Frida** Hook 关键校验（如支付金额校验、登录鉴权），验证"改成客户端可绕过"是否成立；
   - **抓包**（mitmproxy）确认接口是否有**服务端鉴权**（把 token 去掉看是否仍返回数据）；
   - **重打包**：改 apktool 解包 → 改 smali → 重签名 → 安装运行，验证是否有**防重打包**（很多 App 到这一步就"成功"了 → 说明需要加强）。
3. **权限与组件**：
   - 导出组件是否可被任意 App 调用（`am start` 直接拉起内部页面并传参）；
   - `ContentProvider` 是否越权可读（`content query`）。
4. **本地数据**：
   - `run-as`（debuggable 时）检查 SharedPreferences / 数据库里有没有存 token、密码明文；
   - 检查日志是否泄漏。
5. **产出**：按"**风险等级（高/中/低）× 修复成本**"排优先级，写成修复任务；修复后**回归验证**。
6. **加分表述**："**安全测试的最高性价比动作是：定期用 jadx 看自己的 release 包 + 用 mitmproxy 验证所有接口都有服务端鉴权。**这两件事能覆盖大部分真实风险。"

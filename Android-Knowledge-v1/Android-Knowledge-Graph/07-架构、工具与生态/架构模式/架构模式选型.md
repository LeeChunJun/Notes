# 架构模式选型

## 一句话定义

架构模式选型就是回答一个问题：**在当前项目的规模、团队能力、业务复杂度和技术栈下，用哪种模式能让代码改动成本最低、bug 最少、最好测**。

## 核心原理

### 1. 演进主线

```
MVC ──(给 View 加接口)──▶ MVP ──(Presenter 摘掉 View 依赖)──▶ MVVM ──(状态收敛+纯函数)──▶ MVI
 Android 上 Activity 即 Controller      Presenter 认识 View          ViewModel 不认识 View      唯一 reducer 入口
 逻辑与控件耦合                        逻辑可单测                   状态可保活、可复用           状态机可回放
```

它们是**同一条演进线上的四个刻度**，不是四种互斥的技术。演进的核心驱动力只有一个：**让"业务逻辑"摆脱对"界面对象"的依赖，从而可测试、可复用**。

### 2. 五个选型维度

| 维度                            | 说明                             | 影响                                                                   |
| ------------------------------- | -------------------------------- | ---------------------------------------------------------------------- |
| **业务复杂度**            | 页面是否有复杂状态迁移、多步流程 | 简单 → MVP/直接写；复杂 → MVVM/MVI                                   |
| **团队规模与水平**        | 团队是否理解单向数据流           | 混合团队 → 选团队最熟的；新人占比高 → 选 MVVM（Google 官方生态最好） |
| **技术栈**                | Compose or View                  | Compose → StateFlow + MVVM/MVI；View → LiveData + MVVM               |
| **生命周期/进程恢复需求** | 是否需要保活与恢复               | 需要 → 必须 ViewModel/SavedStateHandle                                |
| **多端/跨平台复用**       | 逻辑是否要复用到 iOS/Flutter     | 需要 → MVVM/MVI，逻辑放 KMP 模块                                      |

### 3. 决策表（实用版）

| 场景                          | 推荐                                                      | 理由                              |
| ----------------------------- | --------------------------------------------------------- | --------------------------------- |
| Demo / 一次性活动页           | 无架构 / MVC                                              | 过度设计成本高于收益              |
| 小型工具 App（1-3 人）        | MVP 或简单 MVVM                                           | 关键是不写"上帝 Activity"         |
| 中大型业务 App                | **MVVM + Hilt + StateFlow**                         | 官方生态齐、招人好找、AI 辅助友好 |
| 多步表单 / 支付 / IM / 播放器 | **MVVM + 局部 MVI**                                 | 状态机清晰，避免非法状态          |
| 多页面共享同一份复杂状态      | MVVM + 共享 Repository（内含 StateFlow）或 MVI + 单 Store | MVVM 本身不解决跨页共享           |
| 需要复用到 iOS/桌面           | MVVM/MVI + KMP 共享逻辑层                                 | 见 [[../09-跨平台与混合开发/README]]                               |
| 遗留 MVP + RxJava 项目        | 渐进迁移：新页面 MVVM，旧页面不动                         | 大爆炸重写风险极高                |

### 4. 混合策略（工业界真实做法）

**不要追求"全项目一个模式"**，而是按页面/按模块分层演进：

```text
App
├── core/            纯 Kotlin 模块：工具类、领域模型
├── domain/          纯 Kotlin + KMP：用例（UseCase）、Repository 接口
├── data/            Android 模块：Repository 实现、Retrofit、Room
└── feature/
    ├── login/       MVVM（ViewModel + StateFlow）
    └── checkout/    MVI（Reducer + Effect）  ← 状态复杂的页面
```

原则：**模式向下兼容**——下层不认识上层模式，上层可以用任意模式访问下层的 Repository 接口。

### 5. 评估架构质量的几个信号

出现以下情况，说明架构选型或落地出了问题：

| 信号                                          | 含义                            | 修复方向                         |
| --------------------------------------------- | ------------------------------- | -------------------------------- |
| ViewModel 超过 500 行                         | ViewModel 变成"第二个 Activity" | 抽 UseCase、拆 State、副作用外移 |
| 单元测试需要 Robolectric 才能跑               | 逻辑里混入了 Android 依赖       | 依赖倒置，抽取接口               |
| Activity 里还有 `if (isLoading)` 的业务判断 | 状态没有单一来源                | 收敛到 State                     |
| 旋转屏幕后界面回到初始态                      | 没用 ViewModel 或状态没进 VM    | 迁移到 ViewModel                 |
| 同一逻辑在两个页面各写一遍                    | 复用层缺失                      | 抽到 domain/use case             |

## 代码示例

### 1. 统一 Repository 接口，让上层模式自由切换

```kotlin
// domain 层：纯 Kotlin，不依赖 Android，可被 MVVM / MVI / Flutter 复用
interface UserRepository {
    fun observeUsers(): Flow<List<User>>
    suspend fun refresh(): Result<Unit>
}
```

### 2. 同一页面的两种实现对比

```kotlin
// —— MVVM 写法 ——
class LoginViewModel(private val repo: UserRepository) : ViewModel() {
    private val _state = MutableStateFlow(LoginState())
    val state: StateFlow<LoginState> = _state.asStateFlow()

    fun submit(user: String, pwd: String) {
        viewModelScope.launch {
            _state.update { it.copy(loading = true) }
            repo.login(user, pwd)
                .onSuccess { _state.update { s -> s.copy(loading = false, loggedIn = true) } }
                .onFailure { e -> _state.update { s -> s.copy(loading = false, error = e.message) } }
        }
    }
}

// —— MVI 写法 ——
sealed interface LoginIntent { data object Submit : LoginIntent; data class Result(val ok: Boolean, val msg: String?) : LoginIntent }
data class LoginState(val loading: Boolean = false, val loggedIn: Boolean = false, val error: String? = null)

fun reduce(s: LoginState, i: LoginIntent): LoginState = when (i) {
    LoginIntent.Submit -> s.copy(loading = true, error = null)
    is LoginIntent.Result -> s.copy(loading = false, loggedIn = i.ok, error = i.msg)
}
```

### 3. 用 ADR 记录架构决策（团队协作必备）

```markdown
# ADR-007：业务层统一采用 MVVM + StateFlow

## 状态
已接受（2026-11-04）

## 背景
新同事反馈 LiveData 与协程混用难以理解；RxJava 维护成本高。

## 决策
- UI 层统一使用 StateFlow + collectAsStateWithLifecycle
- 禁止在 ViewModel 中直接持有 Activity/View 引用
- 依赖注入统一使用 Hilt

## 后果
- 需要一次迁移（约 3 人日）
- 获得官方文档与 AI 辅助的一致性
```

## 常见问题 / 面试要点

**读者问：MVC、MVP、MVVM、MVI 到底该选哪个？给我一个不会错的选择策略。**

**AI答：**

按"**默认 + 例外**"两句话答，清晰且安全：

1. **默认选 MVVM**。理由：Google 官方推荐、Jetpack 官方库全是围绕 MVVM 设计的、Compose 官方模板就是 MVVM、招聘和团队协作成本最低、单元测试最方便。**在面试中说"我们项目用 MVVM + Hilt + StateFlow"，是完全安全且主流的回答**。
2. **例外只有两种情况用 MVI**：① 交互状态复杂且有明确迁移规则（多步表单、支付、播放器、IM）；② 需要操作回放/审计。这两种情况下说"我在该模块引入了 MVI 的 Reducer 思想来保证状态迁移可预测"，会显得有深度。
3. **MVP 只在两种情况下提及**：① 维护存量 MVP + RxJava 项目；② 团队 Java 为主、偏好显式接口契约。
4. **MVC 基本不作为"我的架构"回答**，但在面试被问"Activity 算 View 还是 Controller"时必须能讲（见 [[MVC与MVP]]）。

---

**读者问：面试官问我"你这个架构有什么缺点"，怎么答才不显得是外行？**

**AI答：**

主动给出**真实工程中的权衡**，这是资深候选人的标志。参考回答：

1. **MVVM 的常见缺陷**：ViewModel 容易膨胀成"第二个 Activity"，因为状态、副作用、业务编排都往里塞；跨页面共享状态 MVVM 没有标准解法，通常要靠单例 Repository 或引入额外 Store。
2. **我们怎么控制**：
   - **单文件行数约束**（ViewModel ≤ 300 行），超过就拆分；
   - **状态与副作用分离**：状态进 `State`，一次性事件走 `Channel`，不塞进 State；
   - **业务规则下沉到 domain 层 UseCase**，ViewModel 只做编排；
   - **State 用 sealed interface 建模互斥态**，避免 Boolean 组合爆炸。
3. **一致性成本**：引入 MVI 的地方和 MVVM 的地方并存，新人要理解两套写法；我们用 ADR + Code Review Checklist 约束。
4. **迁移成本**：老代码迁移是长期过程，我们采取"新代码用新规范，旧模块不主动重写"的策略，避免大爆炸重构。

> 关键：**每说一个缺点，紧跟一个"我们的应对"**，这才是工程能力的体现。

---

**读者问：有没有量化指标可以衡量一个项目的架构是否健康？**

**AI答：**

有，且都是可自动采集的：

| 指标                              | 采集方式                            | 健康参考值                                        |
| --------------------------------- | ----------------------------------- | ------------------------------------------------- |
| 单文件行数 / 圈复杂度             | Detekt / SonarQube                  | ViewModel ≤ 300 行；圈复杂度 ≤ 15               |
| 单测覆盖率                        | JaCoCo / Codecov                    | 核心 domain 层 ≥ 80%，整体 ≥ 60%                |
| 逻辑测试中需要 Robolectric 的比例 | 统计 `RobolectricTestRunner` 用量 | 越低越好，理想是 domain 层 0 使用                 |
| "上帝类"数量                      | 找出被引用次数 Top N 的类           | ViewModel 不应被 5 个以上页面直接依赖同一实例逻辑 |
| 跨层依赖违规数                    | ArchUnit 单元测试                   | 0（domain 不依赖 android、ui 不依赖 data 实现）   |
| 状态一致性缺陷数                  | 线上 Bug 分类                       | 归零                                              |

**ArchUnit 示例**（架构规则写进测试，防止架构腐化）：

```kotlin
@Test
fun `domain layer must not depend on android`() {
    ArchRuleDefinition.noClasses()
        .that().resideInAPackage("..domain..")
        .should().dependOnClassesThat().resideInAnyPackage("android..")
        .check(classes)
}
```

> 这点很加分：把架构约束变成**自动化测试**，而不是口头约定。

**读者问：如果让你给一个刚起步的团队定架构规范，你会写哪几条？**

**AI答：**

给 6 条"少而硬"的规范（每条都能落地、有明确判据）：

1. **依赖方向单向**：`ui → domain ← data`，domain 层不得出现任何 `android.*` import（用 ArchUnit 校验）。
2. **ViewModel 只做编排**：不写具体业务规则（业务规则进 domain UseCase），不直接持有 Activity 引用，不直接做耗时 IO（IO 进 Repository 内部 suspend 函数）。
3. **状态单一来源**：一个页面的可渲染状态只存在一个 `State` 数据类里，用 `sealed interface` 表达互斥态。
4. **一次性事件不落 State**：Toast/导航/权限请求走 `Channel` 事件流。
5. **依赖必须注入**：禁止在业务代码里 `new` 具体实现（如 `RetrofitUserRepository()`），一律走 Hilt。
6. **逻辑必须可测**：新增的 domain 层逻辑必须有对应单测；PR 模板里带上"如何验证"。

再补两条**软性**的：状态命名统一用 `xxxState` / `xxxUiState`；ViewModel 构造参数不超过 5 个（超过说明职责过多或该拆）。

---

**读者问：项目是 MVVM，但跨 3 个页面共享一份状态，怎么处理？需要改成 MVI 吗？**

**AI答：**

**不需要为了共享状态就全量改 MVI**，有更轻的方案，按推荐顺序：

1. **首选：把共享状态放在 Repository 层的 `StateFlow` 里**。
   - Repository 本身可以是单例（Hilt `@Singleton`），对外暴露 `val users: StateFlow<List<User>>`。
   - 多个页面的 ViewModel 各自订阅它，用 `stateIn(viewModelScope, SharingStarted.WhileSubscribed(5000), emptyList())` 共享上游，避免重复请求。
   - 优点：**零侵入**，不需要改架构模式，符合 MVVM 现有分层。
2. **其次：抽出一个"共享 ViewModel"**（Activity 作用域）`@HiltViewModel class ListSharedVM`，多个 Fragment 通过 `activityViewModels()` 共享。适用于同一 Activity 内多页面。
3. **再次：用 Navigation 传参/返回结果**（`savedStateHandle`）传递一次性数据，避免把"命令式传参"硬塞成状态。
4. **只有当这些都不够时**（状态迁移规则复杂、需要回放、多端共享），才在该模块引入 MVI Store 作为"单一真相源"。

补充一句面试加分：**共享状态的本质问题是"真相源唯一"**，MVI 之所以能解决，是因为它把状态收敛到了一个 Store；但只要真相源唯一，MVVM 一样能做。

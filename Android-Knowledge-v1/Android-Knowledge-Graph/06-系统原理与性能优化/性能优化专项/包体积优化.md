# 包体积优化

## 一句话定义

APK 体积优化的本质是**"只让用户下载他真正需要的东西"**。三条主线：**代码层（R8 混淆 + 压缩 + 依赖裁剪）**、**资源层（WebP 转换 + shrinkResources + 资源混淆）**、**native 层（abiFilters 只留 arm64 + 打包方式）**，再加上 **App Bundle 按需交付**这个"从分发机制上做减法"的终极手段。

## 核心原理

### 1. APK 的体积构成（**先知道钱花在哪**）

```text
【一个典型 APK 的构成（假设 50MB）】

  classes.dex            12 MB   (24%)   ← 应用代码
  lib/                    20 MB   (40%)   ← so 库（arm64 + armeabi + x86 + x86_64）
  res/                     8 MB   (16%)   ← 资源（图片为主）
  assets/                  3 MB    (6%)   ← assets（字体、离线数据、模型）
  resources.arsc          2 MB    (4%)   ← 资源索引表
  META-INF/               1 MB    (2%)   ← 签名、v1 签名块
  其他（kotlin、annotations、R.txt） 4 MB (8%)

  ⚠️ 关键认知：
  · so 库常常是最大头（尤其是"一个 SDK 带 4 个 ABI"的情况）
  · dex 的大小取决于"代码量 + 依赖数量"，R8 能砍掉 30%~60%
  · res 的大小取决于"图片数量 + 密度目录重复度"
```

```bash
# ✅ 快速看 APK 各部分占比
unzip -l app-release.apk | sort -k1 -n -r | head -30

# ✅ 看 dex 里的类分布
dexdump -f classes.dex | grep "Class descriptor" | head -50

# ✅ 看 apk 整体分析（Android Studio Build Analyzer 或 apkanalyzer）
apkanalyzer apk summary app-release.apk
apkanalyzer apk files list app-release.apk
apkanalyzer dex packages --defined-only app-release.apk
```

### 2. 代码优化：R8（**原理题必考**）

#### 2.1 R8 做了什么（**五件事**）

```text
【R8 = D8 的一部分 + ProGuard + 优化器】

  ① 混淆（Obfuscation）
     类名 → a/b/c，方法名 → a/b/c，字段名 → a/b/c
     目的：减小 dex 体积 + 增加逆向难度

  ② 压缩（Shrinking）
     删除"不可达"的类、方法、字段
     依据：静态可达性分析（entry point = manifest 声明的组件 + 反射规则）
     ⚠️ 危险：反射访问的类会被误删 → 必须写 -keep 规则

  ③ 优化（Optimization）
     · 方法内联（inlining）
     · 常量传播与折叠
     · 死代码消除
     · 类合并（ClassMerging）→ 类数量减少
     · 字符串合并（StringMerging）
     · 字段重排（FieldRepacking）

  ④ 资源压缩（shrinkResources）
     配合 isShrinkResources = true
     删除 res/ 中没有被引用的资源
     依据：aapt 生成的资源引用图 + 代码中的 R.xxx 引用 + manifest 引用
     ⚠️ 动态引用（getIdentifier）会导致误删 → 用 tools:keep 保留

  ⑤ dex 优化
     · 移除未使用的方法参数
     · 优化指令流
```

#### 2.2 R8 的配置（**Gradle**）

```kotlin
// app/build.gradle.kts
android {
    buildTypes {
        release {
            // ✅ 开启代码混淆 + 压缩
            isMinifyEnabled = true
            // ✅ 开启资源压缩（必须同时开 isMinifyEnabled）
            isShrinkResources = true

            proguardFiles(
                getDefaultProguardFile("proguard-android-optimize.txt"),  // ⚠️ 用 optimize 版本
                "proguard-rules.pro"
            )
        }
    }

    // ⚠️ R8 full mode（AGP 8.0+ 默认开启）
    //   优势：优化更激进，体积更小
    //   风险：更严格的可达性分析，可能影响反射/动态特性
}
```

```text
【getDefaultProguardFile 的三个版本】
  proguard-android.txt        基础
  proguard-android-optimize.txt  ✅ 推荐：开启优化（内联、合并、优化）
  proguard-android-annotations.txt  额外保留注解（影响体积）

  ⚠️ 不指定就等于没有优化（这是最常见的坑）
```

#### 2.3 keep 规则（**高频考点**）

```proguard
# proguard-rules.pro

# ① 保留注解与属性（很多框架依赖反射读取注解）
-keepattributes *Annotation*, Signature, InnerClasses, EnclosingMethod
-keepattributes SourceFile, LineNumberTable      # ⚠️ 去掉可进一步减小体积（但丢失堆栈行号）

# ② 保留崩溃堆栈的可读性（可选）
-keepattributes SourceFile,LineNumberTable
-renamesourcefileattribute SourceFile

# ③ 反射调用的类必须 keep
-keep class com.myapp.model.** { *; }
-keep class * implements java.io.Serializable { *; }

# ④ Parcelable / Serializable
-keepclassmembers class * implements android.os.Parcelable {
    public static final ** CREATOR;
}

# ⑤ 注解（ButterKnife / Dagger 生成的代码）
-keep class * implements javax.inject.Provider { <init>(); }
-keepclasseswithmembernames class * { @javax.inject.Inject <init>(...); }
-keepclasseswithmembernames class * { @dagger.Inject <init>(...); }

# ⑥ 枚举的 values()/valueOf()
-keepclassmembers enum * {
    public static **[] values();
    public static ** valueOf(java.lang.String);
}

# ⑦ Kotlin 协程
-keepclassmembers class kotlinx.coroutines.** { volatile <fields>; }

# ⑧ JNI 方法
-keepclasseswithmembernames,includedescriptorclasses class * {
    native <methods>;
}

# ⑨ 具体保留某个类的方法
-keep class com.myapp.CrashUtil {
    public static void ***(...);
}
```

| 规则 | 作用 |
| --- | --- |
| `-keep` | 保留类/成员，**且不混淆** |
| `-keepclassmembers` | 只保留成员（类可以被混淆或删除） |
| `-keepnames` | 保留类名（不混淆）但成员仍可被删 |
| `-dontwarn` | 抑制警告（第三方库缺引用时的报错） |
| `-allowaccessmodification` | 允许修改访问修饰符（优化必需） |
| `-optimizations` / `-optimizationpasses` | 控制优化强度（多轮优化） |

### 3. 依赖分析与无用库移除

```bash
# ✅ 列出所有依赖（包括传递依赖）
./gradlew :app:dependencies --configuration releaseRuntimeClasspath

# ✅ 找出"引入了但没用"的库（Android Studio → Analyze → Dependencies）
#   或使用 gradle-dependency-analyze 插件

# ✅ 排除某个传递依赖
```

```kotlin
// ✅ 排除传递依赖
implementation("com.squareup.okhttp3:okhttp:4.12.0") {
    exclude(group = "org.conscrypt", module = "conscrypt-android")  // 用系统版本
    exclude(group = "org.bouncycastle", module = "bcprov-jdk18on")
    exclude(group = "org.slf4j", module = "slf4j-api")             // Android 自带
}
```

```text
【常见的"隐形依赖臃肿"】
  ① 引入一个 SDK，结果拖进来 5 个库（okhttp + okio + kotlin-stdlib + conscrypt + slf4j）
  ② kotlin-stdlib 被重复打包（AGP 8.0+ 已默认打包到 APK，需要配置
     kotlin { coreLibraryDisabling? } 或 dependencyResolutionManagement）
  ③ 引入整个图片库但只用一个功能（Glide 全家桶 vs 只用 decoder）
  ④ 各 SDK 各自带一份 okio / gson
  ⑤ 同时引入了 gson 与 moshi / kotlinx-serialization

【解决】
  · 依赖可视化（./gradlew app:dependencies）
  · 用 dependencyAnalysis 插件找未使用的依赖
  · 优先选"轻量"实现（如用 org.json 代替 gson 处理简单 JSON）
  · 用 BOM 统一版本，避免重复
```

### 4. 资源优化

#### 4.1 图片格式与压缩

```text
【资源优化三板斧】
  ① 格式转换：PNG → WebP（aapt2 自动，或用 cwebp 手动）
     - aapt2 自动转换：AGP 3.0+，minSdk ≥ 18 时默认开启
     - 命令行批量转换：cwebp -q 80 -m 6 -metadata none in.png -o out.webp
  ② 密度目录去重：只保留必要的密度
     - 常见浪费：xxhdpi 放了图，hdpi/xhdpi 放了同一张图
     - 若设计只提供一套矢量图，删掉多余的 drawable-*dpi
  ③ 大图放 assets + 按需下载（见下）
```

```xml
<!-- Android Gradle Plugin 3.0+ 自动 WebP 转换（默认开启） -->
<gradle.properties>
android.enableResourceOptimizations=true
</gradle.properties>
```

```kotlin
// build.gradle.kts：显式配置 aapt2 的 WebP 行为
android {
    buildTypes {
        release {
            isMinifyEnabled = true
            isShrinkResources = true
        }
    }
    // ⚠️ 注意：PNG 的自动 WebP 转换只对 minSdk >= 18 生效
}
```

#### 4.2 `shrinkResources` 与动态资源引用

```proguard
# 动态获取资源 ID 时，必须保留这些资源
-keepclassmembers class * {
    @androidx.annotation.DrawableRes <fields>;
}
```

```xml
<!-- res/raw/keep.xml：显式保留不被引用的资源 -->
<resources xmlns:tools="http://schemas.android.com/tools"
    tools:keep="@drawable/splash_bg,@layout/activity_main" />
```

```kotlin
// ✅ 动态引用资源的正确方式（避免 getIdentifier，R8 友好）
@DrawableRes
val iconRes: Int = when (type) {
    "A" -> R.drawable.ic_a
    "B" -> R.drawable.ic_b
    else -> R.drawable.ic_default
}
```

#### 4.3 资源混淆（AndResGuard）

```text
【AndResGuard：资源名混淆】
  原理：重写 resources.arsc，把资源名从
        res/drawable/ic_home.png  →  res/a/b.png
        资源 ID 不变（0x7f0a0001），但名字变短
  收益：
    · APK 体积减少（资源路径字符串变短）
    · 逆向门槛提高（看不到有意义的名字）
  代价：
    · ⚠️ 运行时按名称找资源会失效
    · ⚠️ 某些三方 SDK 会按名字找资源（要配置 keep 规则）
    · ⚠️ 需要重新签名
  现状：AGP 自带的 `resource shrink` + `resource name obfuscation`（AGP 8.0+
        在 R8 full mode 下提供部分资源名混淆能力）已覆盖大部分需求
```

### 5. so 库优化（**最大的单块**）

#### 5.1 ABI 与 `abiFilters`

```kotlin
// app/build.gradle.kts
android {
    defaultConfig {
        // ✅ 只保留主流 ABI
        ndk {
            abiFilters += listOf("arm64-v8a")   // 只保留 64 位
            // 或：abiFilters += listOf("armeabi-v7a", "arm64-v8a")  // 需要兼容 32 位
        }
    }
}
```

```text
【为什么 so 这么大】
  ① 一个库要支持 4 个 ABI：armeabi-v7a / arm64-v8a / x86 / x86_64
     → 同一个库编译 4 遍，体积 ×4
  ② 每个 ABI 目录里可能有多个 so（libfoo.so + libbar.so）
  ③ 未 strip 的 so 带着符号表和调试信息（可增大 30%~50%）

【对策】
  ① abiFilters 只留 arm64-v8a（Google Play 现在要求提供 64 位版本）
     · 市场占比：arm64-v8a 覆盖 95%+ 活跃设备
     · ⚠️ 如果需要支持非常老的 32 位设备，再加 armeabi-v7a
  ② 用 NDK 的 strip（AGP 默认对 release 做 strip）
     · 手动验证：readelf -S libxxx.so | grep debug
  ③ 检查三方 AAR 里带的 so 是否重复（多个 AAR 带同名的 lib）
     → 遇到 "Duplicate native library" 错误就是这个
  ④ 升级到提供 arm64-only 版本的 SDK 版本
```

#### 5.2 `useLegacyPackaging` 与压缩

```kotlin
// app/build.gradle.kts
android {
    defaultConfig {
        // ✅ 压缩 native 库（so 以压缩形式存储，安装时解压）
        //    ⚠️ 需要配合 minSdk >= 23，且要求"安装时可直接从 APK 读取 so"
        useLegacyPackaging = true
    }
}
```

```text
【两种 native 库打包方式】
  ① 未压缩（useLegacyPackaging = false，默认）
     APK 里的 so 是压缩的 → 安装时需要解压到 nativeLibraryDir
     → 占用额外空间，安装慢

  ② 压缩（useLegacyPackaging = true）
     APK 里的 so 以 "stored" 方式原样存储
     → 安装时直接 mmap 映射（不需要解压）
     → 节省安装空间、加快安装
     → ⚠️ 要求 minSdk >= 23（否则无法从 APK 直接映射 so）
     → ⚠️ ⚠️ 注意：这个配置的命名容易误解：
        "legacy" 指的是"沿用 AGP 3.x 之前的行为"

  【重要】Google Play 要求所有 so 必须压缩存储（Play 会自动处理），
  所以在 Play 上分发时这个选项影响不大。
```

#### 5.3 检查 so 的构成

```bash
# ✅ 看 APK 里各 ABI 的 so 体积
unzip -l app-release.apk | grep "lib/" | awk '{print $1, $4}' | sort -rn

# ✅ 看单个 so 的 section（是否有未 strip 的符号表）
readelf -S lib/arm64-v8a/libfoo.so | grep -E "debug|symtab"

# ✅ 用 apkanalyzer 看
apkanalyzer files list app-release.apk | grep "\.so$"
```

### 6. AAB / App Bundle 与动态交付（**终极手段**）

```text
【为什么需要 App Bundle】
  APK 是"一刀切"的：所有设备下载包含全部 ABI 的同一个包。
  AAB 是"按需生成"的：Google Play 根据设备属性生成最优的 APK。

【Google Play 的动态交付机制】
  ① 基础模块（Base Module）
     · 包含所有设备都需要的代码和资源
     · 语言资源：按设备语言只下发对应的一份（省 20%~40%）
     · ABI：只下发设备对应的那个 ABI（省 ~40% of so）
     · 密度：只下发设备对应的密度目录（省 ~10%）

  ② 动态功能模块（Dynamic Feature Module）
     · 按需下载（用户用到才下载）或预下载
     · 典型场景：登录后才能用的模块、附加内容包

  ③ 分阶段交付（Staged Rollout）
     · 先给 1% 用户推送，观察崩溃率/ANR/启动指标
     · 指标正常再逐步放量

【实测收益】
  · 纯 AAB（未用动态功能）：用户下载体积通常比 APK 小 30%~50%
  · ⚠️ ⚠️ 关键：这是"用户下载体积"的减少，不是"APK 文件大小"的减少
     （Play 后台生成的 APK 依然包含全部内容，只是分发时按需组装）
```

```kotlin
// ✅ 动态功能模块的配置（:feature 模块）
plugins {
    id("com.android.dynamic-feature")
}

android {
    // ⚠️ 动态模块必须声明基础模块的 applicationId
    defaultConfig {
        applicationId = "com.demo"
    }
}

dependencies {
    implementation(project(":app"))   // 依赖基础模块
}
```

```kotlin
/**
 * ✅ 动态功能模块的加载
 */
class DynamicModuleManager {

    private val moduleManager = DynamicFeatureModuleManager.getInstance()

    /**
     * ✅ 用户触发时下载并安装模块
     */
    fun loadFeature(onComplete: (Boolean) -> Unit) {
        val moduleName = "feature_video"
        val splitRequest = SplitInstallRequest.newBuilder()
            .addModule(moduleName)
            .build()

        moduleManager.startInstall(splitRequest)
            .addOnSuccessListener { state ->
                if (state.isInstalled) {
                    onComplete(true)
                } else {
                    // 需要用户确认（Google Play 要求动态模块安装需用户交互）
                    onComplete(false)
                }
            }
            .addOnFailureListener { onComplete(false) }
    }

    /**
     * ✅ 检查模块是否已安装（已安装则直接进）
     */
    fun isInstalled(moduleName: String): Boolean =
        moduleManager.getInstalledModules().contains(moduleName)
}
```

```kotlin
// ✅ Gradle：基础模块的 bundle 配置
android {
    bundle {
        language { enableSplit = true }        // ✅ 按语言拆分
        density { enableSplit = true }         // ✅ 按密度拆分
        abi { enableSplit = true }             // ✅ 按 ABI 拆分
    }
}
```

### 7. 其它优化手段

```text
【① 移除不必要的依赖元数据】
  · 去除重复的 kotlin-stdlib（AGP 8.0+ 默认打进 APK）
  · 去掉 androidx 的重复版本（用 BOM）

【② 移除未使用的资源与依赖】
  · tools:keep / -keep 规则写好
  · 用 Lint 的 "UnusedResources" 检查

【③ 字体】
  · 不要把大字体文件放 res/font
  · 放 assets 并按需下载，或用系统字体 + downloadable fonts

【④ 大数据文件（模型、离线包）】
  · 放 assets 但运行时从 CDN 下载（首次启动后写入私有目录）
  · 或放 Play Asset Delivery

【⑤ 图片资源放 CDN】
  · 不进包，运行时用 Glide/Coil 从 CDN 加载
  · ⚠️ 代价：首次显示需要网络（或做本地缓存）

【⑥ vector drawable vs PNG】
  · 简单图标用 vector（几 KB vs 几十 KB）
  · 复杂插画不要转 vector（渲染开销大）

【⑦ 去除重复的 so】
  · 多个 AAR 携带同名 so 时用 packagingOptions 排除：
    packaging {
        resources {
            excludes += "/META-INF/{AL2.0,LGPL2.1}"
        }
    }
```

## 代码示例

### 1. 完整的包体积优化 Gradle 配置

```kotlin
// app/build.gradle.kts
plugins {
    id("com.android.application")
    id("com.android.dynamic-feature")   // 动态模块用
}

android {
    namespace = "com.demo"
    compileSdk = 34

    defaultConfig {
        applicationId = "com.demo"
        minSdk = 24
        targetSdk = 34
        versionCode = 1
        versionName = "1.0.0"

        // ✅ 只保留 arm64-v8a（覆盖 95%+ 设备）
        ndk {
            abiFilters += listOf("arm64-v8a")
        }

        // ✅ 压缩 native 库（安装时无需解压）
        //    ⚠️ 要求 minSdk >= 23
        useLegacyPackaging = true

        // ✅ 排除重复的 so / 签名
        packaging {
            resources {
                excludes += setOf(
                    "/META-INF/{AL2.0,LGPL2.1}",
                    "/META-INF/DEPENDENCIES",
                    "META-INF/*.kotlin_module"
                )
            }
            jniLibs {
                // ⚠️ 保留需要的 so，其余由 abiFilters 处理
                useLegacyPackaging = true
            }
        }
    }

    buildTypes {
        release {
            // ✅ 代码混淆 + 压缩 + 资源压缩
            isMinifyEnabled = true
            isShrinkResources = true

            proguardFiles(
                getDefaultProguardFile("proguard-android-optimize.txt"), // ⚠️ 必须用 optimize
                "proguard-rules.pro"
            )

            // ✅ 签名配置
            signingConfig = signingConfigs.getByName("release")
        }

        debug {
            applicationIdSuffix = ".debug"
            isMinifyEnabled = false
        }
    }

    // ✅ App Bundle 的动态拆分配置
    bundle {
        language { enableSplit = true }
        density { enableSplit = true }
        abi { enableSplit = true }
    }

    // ✅ 打包后自动统计体积
    applicationVariants.all {
        val outputDir = "${buildDir}/outputs/apk/${buildType.name}/"
        val reportFile = file("${buildDir}/outputs/apk/${buildType.name}/size-report.txt")
        afterEvaluate {
            packageApplication {
                val apkFiles = java.io.File(outputDir).listFiles { _, name ->
                    name.endsWith(".apk") || name.endsWith(".aab")
                } ?: emptyArray()
                doLast {
                    if (apkFiles.isNotEmpty()) {
                        val total = apkFiles.sumOf { it.length() }
                        reportFile.writeText(
                            buildString {
                                apkFiles.forEach {
                                    appendLine("${it.name}: ${it.length() / 1024 / 1024} MB")
                                }
                                appendLine("Total: ${total / 1024 / 1024} MB")
                            }
                        )
                    }
                }
            }
        }
    }
}
```

### 3. 构建期资源压缩与体积统计脚本

```kotlin
/**
 * ✅ 构建后自动分析 APK 各部分占比并输出报告
 */
object ApkSizeReporter {

    data class Part(val name: String, val bytes: Long)

    fun analyze(apkFile: File): List<Part> {
        val parts = mutableMapOf<String, Long>()

        java.util.zip.ZipFile(apkFile).use { zip ->
            zip.entries().asSequence().forEach { entry ->
                val category = when {
                    entry.name.startsWith("classes") && entry.name.endsWith(".dex") -> "dex"
                    entry.name.startsWith("lib/") -> {
                        // 再按 ABI 细分
                        val abi = entry.name.removePrefix("lib/").substringBefore("/")
                        "so/$abi"
                    }
                    entry.name.startsWith("res/") -> "res"
                    entry.name.startsWith("assets/") -> "assets"
                    entry.name == "resources.arsc" -> "resources.arsc"
                    entry.name.startsWith("META-INF/") -> "meta-inf"
                    else -> "other"
                }
                parts[category] = (parts[category] ?: 0L) + entry.size
            }
        }

        return parts.entries
            .sortedByDescending { it.value }
            .map { Part(it.key, it.value) }
    }

    fun printReport(apkFile: File) {
        val total = apkFile.length()
        println("APK: ${apkFile.name}  total=${total / 1024 / 1024}MB")
        analyze(apkFile).forEach { part ->
            val percent = part.bytes * 100.0 / total
            println("  ${part.name.padEnd(20)} ${part.bytes / 1024 / 1024}MB  ${"%.1f".format(percent)}%")
        }
    }
}
```

## 常见问题 / 面试要点

**读者问：怎么减小 APK 体积？请给出系统的方案。**

**AI答：**

1. **先测量**：`apkanalyzer apk summary` + Build Analyzer → 知道 dex / so / res 各占多少。
2. **代码层（收益最大）**：
   - **R8**：`isMinifyEnabled = true` + `isShrinkResources = true` + **必须用 `proguard-android-optimize.txt`**；
   - **依赖裁剪**：`./gradlew app:dependencies` 找出无用依赖，`exclude` 掉多余的传递依赖；
   - **避免重复打包**（kotlin-stdlib、gson、okio）；
   - **移除反射依赖的库**（反射代码多 → dex 大）。
3. **资源层**：
   - **PNG → WebP**（AGP 3.0+ 自动；或用 `cwebp` 手动批量转）；
   - **`shrinkResources`** 删掉未引用资源（配 `tools:keep` 与 `-keepclassmembers` 防误删）；
   - **精简密度目录**（只保留设计提供的密度）；
   - **矢量图标**用 VectorDrawable；
   - **大图/模型**移到 CDN 或 assets 按需下载。
4. **native 层**：
   - **`abiFilters` 只留 `arm64-v8a`**（省 40% 左右的 so）；
   - **strip** 符号表（AGP release 默认做）；
   - 排除重复 so（`packagingOptions`）。
5. **分发层（终极手段）**：
   - **AAB + Play 动态交付**：按语言/密度/ABI 拆分，**用户下载体积通常减少 30%~50%**；
   - **动态功能模块**：用到才下载；
   - **Play Asset Delivery**：大资源按需。
6. **流程保障**：**把体积指标写进 CI**（如"release APK 不得超过 20MB"），防止回退。
7. **面试话术**："**我的顺序是：先看构成，再对症下药。so 大就砍 ABI，dex 大就上 R8 + 依赖裁剪，res 大就 WebP + shrinkResources，最后用 AAB 的动态交付从分发机制上再省一次。**"

---

**读者问：R8 的原理是什么？它和 ProGuard 有什么区别？**

**AI答：**

1. **R8 做了什么**：
   - **混淆**：类/方法/字段重命名为 `a/a/a`；
   - **压缩（Shrinking）**：基于**静态可达性分析**删除不可达的类与成员；
   - **优化**：方法内联、常量折叠、死代码消除、**类合并**、字段重排；
   - **资源压缩**：删除未引用的 `res/` 资源；
   - **dex 优化**：移除无用参数、优化指令流。
2. **与 ProGuard 的区别**：
   | 维度 | ProGuard | R8 |
   | --- | --- | --- |
   | 归属 | 独立的第三方工具 | **Google 官方**，是 D8 的一部分 |
   | 优化能力 | 基础（主要是混淆 + 裁剪） | **强得多**（类合并、字段重排、dex 优化） |
   | 速度 | 慢 | **快**（增量处理） |
   | 与 D8 集成 | 需要额外跑 | **同一个 pipeline，产物更优** |
   | 兼容性 | 规则略有差异 | 兼容大部分 ProGuard 规则 |
   | Baseline Profile | 不支持 | **原生支持** |
3. **可达性分析的入口点（entry points）**：
   - Manifest 中声明的四大组件；
   - `keep` 规则声明的类；
   - 反射标注（`@Keep`）；
   - JNI 方法；
   - `resources.arsc` 中的资源引用。
4. **R8 full mode（AGP 8.0+ 默认）**：
   - 优化更激进（能改更多东西）→ 体积更小；
   - 风险：**可达性分析更严格**，某些依赖反射的库可能出问题 → 需要补 keep 规则。
5. **面试话术**："**R8 = ProGuard 的能力 + dex 优化器 + D8 集成。它比 ProGuard 强在两点：一是能优化 dex 指令本身，二是和 Baseline Profile 打通——R8 生成 dex，dex2oat 按 profile 编译。**"

---

**读者问：为什么 so 库这么大？怎么优化？**

**AI答：**

1. **三个原因**：
   - **① ABI 数量**：同一个库要为 `armeabi-v7a` / `arm64-v8a` / `x86` / `x86_64` 各编译一遍，**体积 ×4**。而**模拟器和少数旧设备**才需要 x86，**Play 已要求提供 64 位**；
   - **② 符号表与调试信息**：未 strip 的 so 带 `.symtab` / `.debug_*`，可增大 **30%~50%**；
   - **③ 第三方 SDK 携带大量不需要的能力**（如某个库带了完整图像编解码器）。
2. **优化手段**：
   - **`abiFilters += listOf("arm64-v8a")`** —— **收益最大**（so 直接少 3/4）；
   - **确认已 strip**：`readelf -S libxxx.so | grep debug`，release 构建 AGP 默认 strip；
   - **排除重复 so**：多个 AAR 带同名 so 时用 `packaging { jniLibs { pickFirsts += ... } }` 或 `excludes`；
   - **升级 SDK 到只提供 arm64 的版本**；
   - **用 `useLegacyPackaging = true`** 压缩 so（安装时无需解压，省安装空间）。
3. **排查命令**：
   ```bash
   unzip -l app.apk | grep "lib/" | awk '{split($4,a,"/"); s[a[2]]+=$1} END {for(k in s) print k, s[k]/1048576" MB"}'
   ```
4. **面试话术**："**so 大的头号原因是 ABI 冗余。Google Play 要求 64 位，arm64 覆盖 95% 以上设备，只留一个 ABI 是立竿见影的优化。**"

---

**读者问：资源混淆（AndResGuard）是什么？值得做吗？**

**AI答：**

1. **原理**：重写 APK 里的 `resources.arsc`，把资源路径从 `res/drawable-xxhdpi/ic_home.png` 改成 `res/a/b.png`。**资源 ID 不变**（`0x7f0a0001`），但路径字符串变短 → 体积减少 + 逆向门槛提高。
2. **收益**：
   - **体积**：路径字符串缩短，通常能省 1%~3%（图片多的应用更多）；
   - **安全**：逆向者看不到有意义的资源名。
3. **风险与代价**：
   - ⚠️ **运行时按名字找资源会失效**（`getIdentifier(name, "drawable", pkg)`）；
   - ⚠️ **三方 SDK 按名字找资源**（某些图片选择器、主题解析）会崩 → 需要配置保留规则；
   - ⚠️ **需要重新签名**（改了 APK 必须重签）；
   - ⚠️ 增加了构建复杂度与排障难度。
4. **现状与建议**：
   - **AGP 8.0+ 的 R8 full mode 已提供部分资源名混淆能力**；
   - 大多数团队的做法是：**先做 `shrinkResources`（安全、收益明确），再评估是否需要 AndResGuard**；
   - 收益有限时**不建议**引入额外风险。
5. **面试话术**："**资源混淆的收益是'锦上添花'，主要价值在安全而非体积。如果团队没有严格的资源白名单管理，我建议先做 shrinkResources，把复杂度留给真正有收益的地方。**"

---

**读者问：AAB 和 APK 有什么区别？为什么 AAB 能减小下载体积？**

**AI答：**

1. **本质区别**：
   - **APK**：一个包含全部内容的**完整包**，所有设备下载同一个文件；
   - **AAB**：一个**容器**（zip），上传到 Play 后，Google Play **根据每个设备的属性生成对应的 APK**。
2. **为什么能减小下载体积**：
   - **ABI 拆分**：只下发设备对应的那一个 ABI（armeabi-v7a / arm64-v8a / x86_64）——**so 部分直接减少约 75%**；
   - **语言拆分**：只下发设备语言对应的一份 `values-xx/`，而不是全部几十种语言；
   - **密度拆分**：只下发设备密度对应的 `drawable-xxhdpi/`，而不是全部密度。
3. **动态交付（PAD）**：
   - **动态功能模块**：用户用到才下载；
   - **分阶段发布**：先 1% 灰度，指标正常再放量。
4. **⚠️ 关键澄清**：
   - **AAB 减小的是"用户下载体积"，不是"APK 文件本身大小"**——Play 后台生成的 APK 依然包含该设备需要的全部内容；
   - **不用 Play 分发的应用**（国内应用市场、企业分发）**拿不到这些拆分收益**，仍需自己用 `bundletool` 生成多 ABI 的 APK。
5. **面试话术**："**AAB 的本质是'把分发的决定权从开发者手里交给分发平台'——平台最清楚每台设备需要什么。国内分发渠道不支持 AAB 的动态交付，所以 AAB 的收益在国内场景要打折。**"

---

**读者问：`shrinkResources` 是什么？开了为什么资源还会被误删？**

**AI答：**

1. **原理**：aapt2 在编译期生成**资源引用图**（哪个资源被哪个资源/代码引用），R8 结合这个图**删除未被引用的资源**。
2. **为什么必须配合 `isMinifyEnabled`**：
   - 资源引用主要体现在**代码里的 `R.xxx`**；
   - 只有开启了代码压缩，R8 才能分析出哪些 `R.xxx` 是不可达的 → 才知道哪些资源没被用；
   - **单独开 `isShrinkResources` 没有效果**。
3. **误删的三个典型场景**：
   - **① 动态资源引用**：`getIdentifier("icon_a", "drawable", pkg)` → 编译期看不到；
   - **② 反射设置的属性**：`android:background="@drawable/bg"` 在代码里是字符串；
   - **③ 三方 SDK 按名字找资源**。
4. **保留方式**：
   ```xml
   <!-- res/raw/keep.xml -->
   <resources tools:keep="@drawable/ic_dynamic,@layout/dyn_layout" />
   ```
   ```proguard
   -keepclassmembers class * {
       @androidx.annotation.DrawableRes <fields>;
   }
   ```
5. **验证方法**：
   - 跑一遍**全量回归测试**（特别是动态换肤/主题切换功能）；
   - 对比 `resources.arsc` 中资源条目的数量变化；
   - 用 `apkanalyzer resources value --config ...` 检查关键资源是否还在。
6. **面试话术**："**shrinkResources 的原理是'资源引用图 + 代码可达性分析'，所以必须和代码混淆一起开。它的风险全在'动态引用'上——凡是运行时拼字符串找资源的地方，都要显式 keep。**"

---

**读者问：怎么保证包体积优化不会"回退"？**

**AI答：**

1. **CI 体积门禁**：
   - 构建后自动统计各部分大小；
   - **超过阈值直接让 CI 失败**（如 "release APK > 25MB 则构建失败"）；
   - 与**上一次的构建产物对比**（`apkanalyzer apk compare`），把差异作为 PR 评论贴出来。
2. **依赖锁定**：
   - `dependencyLocking` / `gradle/verification-metadata.xml`（依赖校验）；
   - 禁止随意升级大依赖（升级要 review 体积变化）。
3. **资源使用规范**：
   - Lint 的 `UnusedResources` 作为 warning 提示；
   - Code Review 时检查新增的图片是否走了 WebP 流程；
   - **新增 native 库必须在 CI 检查 ABI 数量**。
4. **多渠道包监控**：
   - 不同渠道（应用市场 / Google Play / 企业）分别统计；
   - **AAB 的实际下载体积**用 `bundletool` 模拟目标设备验证。
5. **监控与告警**：
   - 灰度发布时监控**下载转化率**（体积增大 → 转化率下降）；
   - 用 Play Console 的"下载大小"报告。
6. **面试话术**："**体积优化最大的问题不是不会做，是改回去了。所以我会把体积门禁写进 CI，让'优化'变成一个不会退化的机制而不是一次性的活动。**"

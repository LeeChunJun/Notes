# 电量优化

## 一句话定义

电量优化的本质是**"把无条件的持续消耗，变成有条件的按需消耗"**。手机的电量被四大来源瓜分：**CPU、射频网络、显示/GPU、传感器**，每一条都有对应的治理手段。核心方法论是：**先用电量统计工具定位 Top 消耗项，再针对该项做工程治理**，而不是凭感觉优化。

## 核心原理

### 1. 电量的四大来源（**总纲，必背**）

```text
┌────────────────────────────────────────────────────────────────┐
│ ① CPU                                                        │
│    · 后台轮询（Handler 死循环、while(true){sleep}）              │
│    · 高频定时任务（Alarm 每分钟一次）                            │
│    · 大量计算 / 频繁 GC                                        │
│    · wakelock 未释放                                          │
│    💡 对策：改推送替代轮询；WorkManager 批量；降频；及时释放      │
├────────────────────────────────────────────────────────────────┤
│ ② 射频网络（Radio）                                             │
│    · 信号弱时反复重传（上行/下行都耗电）                         │
│    · 频繁建连（每次都要"唤醒基站"）                             │
│    · 心跳包（TCP keep-alive 太频繁）                            │
│    · 移动数据 vs Wi-Fi                                          │
│    💡 对策：请求合并；缓存；指数退避重连；批量上传；优先 Wi-Fi   │
├────────────────────────────────────────────────────────────────┤
│ ③ 显示 / GPU                                                   │
│    · 屏幕常亮（最大的单体消耗）                                  │
│    · 高刷新率                                                 │
│    · 过度绘制导致 GPU 满载                                     │
│    · 深色模式                                                 │
│    💡 对策：FLAG_KEEP_SCREEN_ON 用完即关；降刷新率；深色模式    │
├────────────────────────────────────────────────────────────────┤
│ ④ 传感器                                                       │
│    · GPS 高频定位（1s 一次能吃掉 10%+ 电量）                     │
│    · BLE 持续扫描                                             │
│    · 计步器 / 心率传感器常开                                    │
│    💡 对策：降频降精度；批量获取；用完即停                       │
└────────────────────────────────────────────────────────────────┘
```

> [!tip] **经验值**
> 一般应用的耗电构成大致是：**显示 40%~50%、网络 20%~30%、CPU 15%~25%、传感器 5%~10%**。但**"你的应用"不一样**——后台定位类应用可以到 70% 都是 GPS。所以**必须先测量**。

### 2. 定位高耗电：工具链（**必须先做这一步**）

#### 2.1 `dumpsys batterystats`

```bash
# ✅ 概览：按 UID 排名
adb shell dumpsys batterystats --charged

# ✅ 只看某个包
adb shell dumpsys batterystats --charged com.demo

# ✅ 更详细：包含 wakelock / 网络 / 唤醒来源的明细
adb shell dumpsys batterystats --charged --reset com.demo

# ⚠️ --reset 会清零计数，所以每次测量前先 reset
```

**输出里最关键的字段**：

```text
  Uid com.demo:
    ...
    Apk time:  0m 5s 123ms      ← 应用在前台的时间
    Uid timeout: 0m 0s 0ms      ← UID 超时被杀
    ...
    Wake lock com.demo:foo       ← wakelock 持有时长（★ 重点）
    ...

  Aggregated wakeup sources:
    com.demo: 123 wakeups        ← ★ 唤醒次数（重点！）
    ...

  Network: 
    com.demo: 45MB received, 12MB sent   ← 网络流量
```

| 指标 | 含义 | 优化指向 |
| --- | --- | --- |
| **Wakeup count** | 唤醒次数 | **后台轮询的核心证据**；理想值：每小时 < 10 次 |
| **Wake lock time** | wakelock 持有时长 | 忘记 release / 长期持有 |
| **Network traffic** | 流量 | 轮询下载、重复请求 |
| **Uid active time** | 活跃时长 | 长时间后台运行 |
| **Apk time** | 前台时长 | 前台自身消耗 |

```kotlin
/**
 * ✅ 应用内读取电量与充电状态
 */
object BatteryMonitor {

    /**
     * ✅ 获取当前电量百分比（注册广播比轮询省电）
     */
    fun getBatteryPercent(context: Context): Int {
        val intent = context.registerReceiver(null, IntentFilter(Intent.ACTION_BATTERY_CHANGED))
            ?: return -1
        val level = intent.getIntExtra(BatteryManager.EXTRA_LEVEL, -1)
        val scale = intent.getIntExtra(BatteryManager.EXTRA_SCALE, -1)
        return if (level >= 0 && scale > 0) level * 100 / scale else -1
    }

    /**
     * ✅ 注册电池状态广播（省电：只在变化时回调）
     */
    fun register(context: Context, onChanged: (Int, Boolean) -> Unit): BroadcastReceiver {
        val receiver = object : BroadcastReceiver() {
            override fun onReceive(ctx: Context, intent: Intent) {
                val level = intent.getIntExtra(BatteryManager.EXTRA_LEVEL, -1)
                val scale = intent.getIntExtra(BatteryManager.EXTRA_SCALE, -1)
                val plugged = intent.getIntExtra(BatteryManager.EXTRA_PLUGGED, 0) != 0
                if (level >= 0 && scale > 0) {
                    onChanged(level * 100 / scale, plugged)
                }
            }
        }
        context.registerReceiver(receiver, IntentFilter(Intent.ACTION_BATTERY_CHANGED))
        return receiver
    }

    /**
     * ✅ 判断是否处于省电模式（系统级省电开关）
     */
    fun isPowerSaveMode(context: Context): Boolean =
        (context.getSystemService(PowerManager::class.java)).isPowerSaveMode
}
```

### 3. 反模式清单（**面试要能列举**）

| # | 反模式 | 现象 | 修法 |
| --- | --- | --- | --- |
| 1 | **后台轮询**（`Handler.postDelayed` 死循环、`while(true){sleep}` 的 Service） | `batterystats` 里 wakeup 次数暴涨 | **改推送**（FCM / 长连接）；或 WorkManager 批量 |
| 2 | **高频 Alarm**（每分钟一次 `setExact`） | 频繁唤醒 CPU | 降到 15 分钟以上；用 WorkManager |
| 3 | ** wakelock 未释放** | wakelock 持有时间异常长 | try-finally + 超时 acquire |
| 4 | **高频定位**（1s 一次 `requestLocationUpdates`） | GPS 功耗飙升 | 降频到 30s+；降精度到 `PRIORITY_BALANCED_POWER_ACCURACY`；**用完即停** |
| 5 | **无节制的定位上传** | 网络 + GPS 双耗 | 批量攒够 N 个点再上传 |
| 6 | **固定间隔重连**（失败后每 1s 重试） | 弱网下疯狂耗电 | **指数退避**（1s→2s→4s→…→上限 5 分钟）+ 抖动 |
| 7 | **请求合并缺失**（首页 10 个接口各拉一次） | 网络流量与唤醒次数增加 | 合并接口；并发而非串行 |
| 8 | **屏幕常亮**（`FLAG_KEEP_SCREEN_ON` 未清除） | 显示功耗巨大 | 用完即 `clearFlags`；或用 `WindowInsetsController` |
| 9 | **过度绘制 / 高刷新率** | GPU 功耗高 | 深色模式；降低刷新率；减少 overdraw |
| 10 | **BLE 持续扫描** | 射频功耗高 | 扫描间隔放大；用 `setScanMode(SCAN_MODE_LOW_LATENCY)` → `SCAN_MODE_LOW_POWER`；**用完即停** |
| 11 | **频繁写数据库 / SharedPreferences** | 每次 commit 都 fsync，唤醒闪存 | 用 `apply()` 而非 `commit()`；批量写 |
| 12 | **大日志输出**（`Log.d` 每秒打印） | 写日志有 I/O 开销 | 生产环境关闭；用分级日志 |

### 4. CPU 与后台任务优化

```kotlin
/**
 * ✅ 正确的后台任务姿势：WorkManager + 约束 + 指数退避
 */
class SyncScheduler(private val context: Context) {

    private val workManager = WorkManager.getInstance(context)

    /**
     * ✅ 同步任务：只在有网络 + 电量不低时执行
     */
    fun scheduleSync() {
        val constraints = Constraints.Builder()
            .setRequiredNetworkType(NetworkType.CONNECTED)
            .setRequiresBatteryNotLow(true)       // ⚠️ 低电量不跑
            .build()

        val request = OneTimeWorkRequestBuilder<SyncWorker>()
            .setConstraints(constraints)
            .setBackoffCriteria(
                BackoffPolicy.EXPONENTIAL,          // ⚠️ 指数退避
                30, TimeUnit.SECONDS
            )
            .build()

        workManager.enqueueUniqueWork(
            "sync",
            ExistingWorkPolicy.KEEP,               // 不重复排队
            request
        )
    }

    /**
     * ✅ 批量上传：攒够 N 条再传，而不是每条一次请求
     */
    fun scheduleBatchUpload() {
        val request = OneTimeWorkRequestBuilder<BatchUploadWorker>()
            .setConstraints(
                Constraints.Builder()
                    .setRequiredNetworkType(NetworkType.UNMETERED)  // 只在 Wi-Fi
                    .setRequiresCharging(true)                      // 只在充电
                    .build()
            )
            .setBackoffCriteria(BackoffPolicy.EXPONENTIAL, 60, TimeUnit.SECONDS)
            .build()

        workManager.enqueue(request)
    }
}
```

```kotlin
/**
 * ✅ 指数退避 + 抖动的重连策略（网络层）
 */
class SmartRetry {

    private var retryCount = 0

    fun nextDelayMillis(base: Long = 1_000L, max: Long = 5 * 60 * 1000L): Long {
        // 指数退避：1s → 2s → 4s → 8s ...
        val exponential = base shl minOf(retryCount, 10)
        // 抖动（jitter）：避免大量客户端同时重连（惊群）
        val jitter = (Math.random() * 0.3 * exponential).toLong()
        retryCount++
        return minOf(exponential + jitter, max)
    }

    fun onSuccess() {
        retryCount = 0
    }
}
```

### 5. 网络优化

```text
【网络功耗的本质】
  ① 每次通信都要让基带从"睡眠"唤醒（"尾能耗" tail energy）
  ② 弱信号时手机的发射功率会大幅提升（功率与信号强度的指数关系）
  ③ 频繁建连（每次都要握手 + TLS 协商）比传输数据本身更耗电

【优化手段】
  ① 减少请求次数
     · 接口合并（首页 10 个接口 → 1 个聚合接口）
     · 增量同步（只传变更的部分，而不是全量）
     · 缓存 + 条件请求（ETag / If-Modified-Since → 304 也是一次网络交互）
  ② 减少连接成本
     · 连接复用（OkHttp 的 ConnectionPool）
     · HTTP/2 多路复用（一个 TCP 连接跑多个请求）
     · 预连接（Preconnect）：提前做 DNS + TCP + TLS
  ③ 数据压缩
     · gzip / br（Brotli）：流量减少 60%~80%，且减少射频工作时间
     · ⚠️ 代价：CPU 消耗增加（低电量模式可关闭）
  ④ 智能重连
     · 指数退避 + 抖动
     · 区分错误类型：4xx 不要重试，5xx/网络错误才重试
  ⑤ 网络类型选择
     · 大文件上传用 NetworkType.UNMETERED（只在 Wi-Fi）
     · 移动数据下降低图片质量
  ⑥ 推送替代轮询
     · FCM / 厂商推送：服务端主动推，客户端不需要唤醒
```

```kotlin
/**
 * ✅ OkHttp 的连接复用 + 缓存 + 压缩配置
 */
object HttpClientFactory {

    fun create(cacheDir: File): OkHttpClient {
        val cache = Cache(File(cacheDir, "http"), 10L * 1024 * 1024)   // 10MB 缓存

        return OkHttpClient.Builder()
            .cache(cache)                       // ✅ 磁盘缓存，减少请求
            .connectionPool(ConnectionPool(5, 5, TimeUnit.MINUTES))  // ✅ 连接复用
            .connectTimeout(10, TimeUnit.SECONDS)
            .readTimeout(15, TimeUnit.SECONDS)
            .retryOnConnectionFailure(true)
            // ✅ 失败重试交给上层做退避，OkHttp 内置重试不加延迟
            .addInterceptor { chain ->
                val request = chain.request()
                if (request.header("Accept-Encoding") == null) {
                    chain.proceed(
                        request.newBuilder()
                            .header("Accept-Encoding", "gzip, br")
                            .build()
                    )
                } else {
                    chain.proceed(request)
                }
            }
            .build()
    }
}
```

### 6. 定位优化（**耗电重灾区**）

```kotlin
/**
 * ✅ 定位优化的三个关键动作
 */
class LocationOptimizer(private val context: Context) {

    /**
     * ✅ ① 降频 + 降精度
     * @param intervalMs  最小时间间隔（毫秒）
     * @param fastestIntervalMs 最快间隔（移动过程中用）
     * @param priority    精度与功耗的权衡
     */
    fun startLocationUpdates(
        intervalMs: Long = 30_000L,
        fastestIntervalMs: Long = 10_000L,
        priority: Int = Priority.PRIORITY_BALANCED_POWER_ACCURACY
    ) {
        val request = LocationRequest.Builder(priority, intervalMs)
            .setMinUpdateIntervalMillis(fastestIntervalMs)
            .setMinUpdateDistanceMeters(50f)      // ⚠️ 移动超过 50m 才更新
            .setWaitForAccurateLocation(false)      // ⚠️ 不要为了精度一直等
            .build()

        val client = LocationServices.getFusedLocationProviderClient(context)
        client.removeLocationUpdates(locationCallback)   // ⚠️ 先移除旧的
        client.requestLocationUpdates(request, locationCallback, Looper.getMainLooper())
    }

    /**
     * ✅ ② 用完即停（最重要的一条）
     */
    fun stopLocationUpdates() {
        LocationServices.getFusedLocationProviderClient(context)
            .removeLocationUpdates(locationCallback)
    }

    /**
     * ✅ ③ 批量获取：一次拿多个位置（而不是一个一个要）
     */
    fun requestBatchLocations(count: Int = 10, callback: (List<Location>) -> Unit) {
        val request = LocationRequest.Builder(
            Priority.PRIORITY_HIGH_ACCURACY, 10_000L
        ).setMaxUpdateCountMillis(30_000L)   // 最多 30 秒
            .build()

        LocationServices.getFusedLocationProviderClient(context)
            .getCurrentLocation(Priority.PRIORITY_HIGH_ACCURACY, CancellationTokenSource().token)
            .addOnSuccessListener { /* 单次定位 */ }
    }

    private val locationCallback = object : LocationCallback() {
        override fun onLocationResult(result: LocationResult) {
            // ✅ 只取最后一个位置
            result.lastLocation?.let { onLocation(it) }
        }
    }

    private fun onLocation(location: Location) {}
}
```

```text
【定位功耗对比（经验值）】
  GPS 精度 + 1s 间隔 → 约 5%~10% 电量/小时
  GPS 精度 + 30s 间隔 → 约 1%/小时
  网络定位（粗略） → 约 0.1%/小时
  混合定位（先网络后 GPS） → 约 0.5%/小时

【关键策略】
  ① 前台粗定位（网络）→ 用户需要精度时再切 GPS
  ② 静止时降频、运动时提频
  ③ 用 setMinUpdateDistanceMeters 而不是纯时间间隔
  ④ 后台定位必须用前台服务（否则 Doze 会限制，且容易被杀）
```

### 8. 传感器优化

```kotlin
/**
 * ✅ 传感器：注册 → 使用 → 立刻注销
 */
class SensorOptimizer(private val context: Context) {

    private val sensorManager = context.getSystemService(SensorManager::class.java)
    private var stepCounter: Sensor? = null
    private var listener: SensorEventListener? = null

    /**
     * ✅ 开始计步：只在用户真正需要时开启
     */
    fun startStepCounting(onStep: (Int) -> Unit) {
        stepCounter = sensorManager.getDefaultSensor(Sensor.TYPE_STEP_COUNTER)
        listener = object : SensorEventListener {
            override fun onSensorChanged(event: SensorEvent?) {
                val steps = event?.values?.firstOrNull()?.toInt() ?: return
                onStep(steps)
            }
            override fun onAccuracyChanged(sensor: Sensor?, accuracy: Int) {}
        }
        // ✅ SENSOR_DELAY_UI（~60ms）而不是 FASTEST（每条数据都报）
        sensorManager.registerListener(listener, stepCounter, SensorManager.SENSOR_DELAY_UI)
    }

    /**
     * ✅ 停止计步（必须调用！）
     */
    fun stopStepCounting() {
        listener?.let { sensorManager.unregisterListener(it) }
        listener = null
    }

    /**
     * ✅ BLE 扫描：低功耗模式 + 间隔放大
     */
    fun startBleScan(callback: (String) -> Unit) {
        val scanner = context.getSystemService(BluetoothManager::class.java)
            ?.adapter?.bluetoothLeScanner ?: return

        val settings = ScanSettings.Builder()
            .setScanMode(BluetoothAdapter.SCAN_MODE_LOW_POWER)  // ⚠️ 不是 LOW_LATENCY
            .build()

        val filters = listOf(ScanFilter.Builder().setDeviceAddress(DEVICE_ADDR).build())

        scanner.startScan(filters, settings, object : ScanCallback() {
            override fun onScanResult(callbackType: Int, result: ScanResult) {
                callback(result.device.address)
                // ⚠️ 找到目标后立刻停止扫描
                scanner.stopScan(this)
            }
            override fun onScanFailed(errorCode: Int) {}
        })
    }
}
```

### 9. 完整的省电治理框架

```text
【分层治理】
  ① 架构层（最有效）
     · 推送替代轮询
     · WorkManager 统一调度所有后台任务

     · 缓存减少网络请求
     · 指数退避重连
     · 数据压缩
     · 关闭生产环境日志
  ③ 资源层
     · 深色模式
```

```kotlin
/**
 * ✅ 省电网络请求：缓存 + 合并 + 退避 + 批量
 */
class PowerEfficientNetwork(private val context: Context) {

    private val client = HttpClientFactory.create(context.cacheDir)
    private val cache = JsonCache(context)

    /**
     * ✅ 带缓存的请求：命中缓存则完全不发网络请求（省电效果最大）
     */
    suspend fun <T> fetchWithCache(
        url: String,
        ttlMillis: Long = 5 * 60_000L,
        parser: (String) -> T
    ): Result<T> = withContext(Dispatchers.IO) {
        // ① 缓存命中且未过期
        cache.get(url, ttlMillis)?.let { return@withContext Result.success(parser(it)) }

        // ② 走网络
        val result = runCatching {
            client.newCall(Request.Builder().url(url).build()).execute().use { response ->
                response.body?.string() ?: error("empty body")
            }
        }

        // ③ 成功后写缓存
        result.onSuccess { cache.put(url, it) }
        result.map(parser)
    }

    /**
     * ✅ 批量上传：攒够 N 条或超过 T 秒才发一次
     */
    suspend fun batchUpload(items: List<UploadItem>, batchSize: Int = 50) {
        items.chunked(batchSize).forEach { batch ->
            withContext(Dispatchers.IO) {
                val body = Json.encodeToString(batch)
                val request = Request.Builder()
                    .url(UPLOAD_URL)
                    .post(body.toRequestBody("application/json".toMediaType()))
                    .build()
                client.newCall(request).execute().use { }
            }
        }
    }
}
```

## 常见问题 / 面试要点

**读者问：怎么优化应用的电量消耗？**

**AI答：**

1. **第一步：测量，不要凭感觉**。
   - `adb shell dumpsys batterystats --charged <pkg>` → 看 **wakeup 次数**（**最关键的指标**）、wakelock 持有时长、网络流量；
   - **Battery Historian** → 可视化看唤醒来源与时间轴；
   - 理想值：**后台唤醒 < 10 次/小时**。
2. **第二步：按四大来源治理**：
   - **CPU**：改推送替代轮询；WorkManager 批量 + 约束 + 指数退避；及时释放 wakelock；关闭生产日志；
   - **网络**：接口合并；缓存 + 条件请求；连接复用（HTTP/2）；数据压缩；指数退避 + 抖动重连；大文件只在 Wi-Fi 传；
   - **显示/GPU**：深色模式；降低刷新率；减少过度绘制；`FLAG_KEEP_SCREEN_ON` 用完即清；
   - **传感器**：降频 + 降精度 + `setMinUpdateDistanceMeters`；**用完即注销**；BLE 用 `SCAN_MODE_LOW_POWER`。
3. **第三步：低电量降级**：监听电量与 `PowerManager.isPowerSaveMode`，低电量时停定位、降频率、关动画。
4. **第四步：防回退**：把"唤醒次数/小时"等指标上报到监控平台并设阈值告警。
5. **面试话术**："**我的省电优化第一句话一定是'batterystats 看 wakeup 次数'——因为唤醒次数直接反映了后台任务的健康度。轮询型 App 的唤醒次数是正常 App 的几十倍。**"

---

**读者问：Android 的电量都消耗在哪？有哪些优化手段？**

**AI答：**

1. **四大来源（按占比排序）**：
   | 来源 | 典型占比 | 关键指标 |
   | --- | --- | --- |
   | **显示 / GPU** | 40%~50% | 屏幕常亮、高刷新率、过度绘制 |
   | **射频网络** | 20%~30% | 弱信号重传、频繁建连、心跳 |
   | **CPU** | 15%~25% | 轮询、GC、wakelock |
   | **传感器** | 5%~10% | 高频定位、BLE 扫描 |
2. **每一类的治理**：
   - **显示**：深色模式（OLED）、降刷新率、`Surface.setFrameRate`、减少 overdraw、`FLAG_KEEP_SCREEN_ON` 用完即清；
   - **网络**：接口合并、缓存、条件请求（ETag）、连接复用、gzip/br 压缩、指数退避 + 抖动、Wi-Fi 优先；
   - **CPU**：推送替代轮询、WorkManager 批量、降频、及时释放 wakelock、关日志；
   - **传感器**：降频降精度、距离触发、批量获取、用完即停。
3. **两个容易被忽略的"隐形耗电"**：
   - **SharedPreferences 的 `commit()`**（每次都 fsync，唤醒闪存）→ 用 `apply()`；
   - **频繁写数据库 / 大量小文件 IO** → 批量写。
4. **重要认知**：**"App 在后台时仍耗电"** 大多是这三类：wakelock 未释放、定时唤醒（Alarm/Job/Service）、网络重连。
5. **面试话术**："**显示是最大的头，但也是最容易优化的（深色模式）。真正难的是后台耗电，因为那说明你的 App 在'用户看不见的时候还在做事'——要么是设计问题，要么是实现问题。**"

---

**读者问：怎么定位一个高耗电的问题？完整流程是什么？**

**AI答：**

1. **第 1 步：确认范围**。
   - 是**整个 App** 高耗电，还是**某个场景**（定位、上传、直播）？
   - 是**所有用户**还是**特定机型/系统版本**？
2. **第 2 步：`dumpsys batterystats`**：
   ```bash
   adb shell dumpsys batterystats --charged --reset com.demo
   # 让应用在后台运行 30~60 分钟
   adb shell dumpsys batterystats --charged com.demo
   ```
   - 看 **Wakeup count**（唤醒次数，**轮询的直接证据**）；
   - 看 **Wake lock** 段落（wakelock 持有时长）；
   - 看 **Network** 段落（流量）；
   - 看 **Proc** 段落（进程被启动的次数）。
3. **第 3 步：Battery Historian**：
   - `adb shell dumpsys batterystats --history > history.txt` → 上传到 Battery Historian；
   - 看 **Wakeup** 面板：**具体是哪个组件唤醒了 CPU**；
   - 看 **Proc** 面板：进程被系统杀又重启的"锯齿"（说明在挣扎保活）。
4. **第 4 步：代码层定位**：
   - 搜代码里的 `postDelayed` 循环、`AlarmManager.setRepeating`、`while(true)`、`requestLocationUpdates`；
   - 检查 wakelock 的 acquire/release 是否配对；
   - 检查重连逻辑是不是固定间隔。
5. **第 5 步：验证**：
   - 改造后重新测量，**对比 wakeup 次数**（这是最客观的指标）；
   - 做 A/B（线上灰度对比耗电投诉率）。
6. **面试话术**："**我的定位链路是'batterystats 看指标 → Historian 看唤醒来源 → 代码搜索对应模式 → 改完对比唤醒次数'。唤醒次数是硬指标，因为它是可量化的、且直接对应用户投诉。**"

**读者问：Battery Historian 怎么看？它能看出什么？**

**AI答：**

1. **是什么**：Google 官方的电池耗电可视化工具（`developer.android.com/tools/battery-historian`）。
2. **数据来源**：`dumpsys batterystats --history` 导出的文本，或 `adb bugreport` 中包含的 battery historian 数据。
3. **能看出的关键信息**：
   - **各应用的耗电排名**（Uid 级别）；
   - **唤醒来源（Wakeup）**：**哪个组件在什么时刻唤醒了 CPU**——这是定位轮询的黄金线索；
   - **wakelock 持有时间轴**；
   - **进程生命周期（Proc）**：进程启动/被杀/重启的"锯齿"；
   - **网络流量与时长**；
   - **电量变化曲线**与唤醒事件的时间关联。
4. **典型分析路径**：
   ```text
   ① 看 "App Standby / Uid" 排名 → 找到你的应用
   ② 看 "Wakeup" 面板 → 哪个时间点、哪个组件唤醒的
   ③ 交叉看 "Proc" 面板 → 那个时间点进程是不是被杀又重启了
   ④ 得出结论：如果是自己的定时任务 → 改 WorkManager；
      如果是三方 SDK → 换 SDK 或加约束
   ```
5. **局限**：
   - 需要**长时间采样**（至少几小时，最好一整天）才能反映真实使用；
   - 只能看**统计**，不能定位到具体代码行；
   - 实验室环境（一直插着 USB 供电）结果会失真。
6. **面试话术**："**Battery Historian 的价值在于'时间关联'——它能告诉你'下午 3 点到 5 点之间，你的 App 唤醒了 CPU 200 次'，这个时间段的信息往往直接指向某个定时任务或某个 SDK。**"

---

**读者问：后台任务应该怎么写才不费电？`WorkManager` 和 `JobScheduler` 怎么选？**

**AI答：**

1. **根本原则**：**后台任务必须由系统调度，而不是应用自己计时**。
   - 自己计时 = 强制唤醒设备 = 全用户买单；
   - 系统调度 = 系统可以批量、合并、择机执行。
2. **`WorkManager` vs `JobScheduler`**：
   | 维度 | WorkManager | JobScheduler |
   | --- | --- | --- |
   | 抽象 | 面向业务的抽象 | 系统调度 API |
   | 持久化 | ✅ 进程死/重启后继续 | ❌ 进程死即丢 |
   | 链式依赖 | ✅ | ❌ |
   | 唯一工作 | ✅ `ExistingWorkPolicy` | ❌ |
   | 重试退避 | ✅ 内置 | 需自行配置 |
   | 选型 | **默认选它** | 需要精确控制时 |
3. **省电的正确姿势（WorkManager 配置）**：
   ```kotlin
   Constraints.Builder()
       .setRequiredNetworkType(NetworkType.UNMETERED)  // 只在 Wi-Fi
       .setRequiresBatteryNotLow(true)                 // 电量不低
       .setRequiresCharging(true)                      // 在充电
       .setRequiresStorageNotLow(true)                 // 空间充足
       .build()
   // + 指数退避
   .setBackoffCriteria(BackoffPolicy.EXPONENTIAL, 30, TimeUnit.SECONDS)
   ```
4. **额外省电技巧**：
   - **`ExistingWorkPolicy.KEEP`**：避免重复排队（否则会堆积多个任务）；
   - **合并任务**：不要为每个事件都 enqueue 一次，而是用一个周期性任务批量处理；
   - **周期任务 ≥ 15 分钟**（系统硬性限制）；
   - **`Result.retry()`** 而不是自己 `delay` 重试。
5. **面试话术**："**省电的后台任务只有一条原则：让系统决定什么时候跑，应用只声明条件。我见过最糟的写法是 `while(true) { Thread.sleep(5000); upload(); }`，这是 Doze 和 Standby 存在的根本原因。**"

---

**读者问：定位怎么优化才不费电？**

**AI答：**

1. **三个核心手段**：
   - **① 降频 + 降精度**：
     - `Priority.PRIORITY_BALANCED_POWER_ACCURACY`（粗略）vs `PRIORITY_HIGH_ACCURACY`（精确，功耗差数倍）；
     - 导航才用高精度；列表定位用粗略；
     - 间隔从 1s 放大到 15s~60s。
   - **② 距离触发**：`setMinUpdateDistanceMeters(30f)` —— **比时间间隔更省电**（静止时完全不触发）。
   - **③ 用完即停**：`removeLocationUpdates()`，这是**最容易被忽略也最重要的一条**。
2. **批量获取**：一次要多个位置而不是一个一个要（`getCurrentLocation` 配合 `MaxUpdateCountMillis`）。
3. **混合定位**：先用网络定位拿粗略位置，用户需要精度时再切 GPS。
4. **数据上传也要省**：**攒够 N 个点再批量上传**（避免每 10 秒一次网络请求 → 固定间隔重连）。
5. **后台定位的限制**：
   - 必须用**前台服务 + 通知**（否则 Doze 限制、且容易被杀）；
   - Android 14+ 需声明 `foregroundServiceType="location"` 与对应权限。
6. **功耗量级（经验值）**：GPS 精度 + 1s 间隔 ≈ **5%~10% 电量/小时**；30s 间隔 ≈ 1%/小时；网络定位 ≈ 0.1%/小时。
7. **面试话术**："**定位省电的三个字：降频、降精、停掉。第三条最关键——我见过太多 App 注册了定位却从来不注销，OnDestroy 里少一行 removeLocationUpdates 就多耗几个百分点。**"

---

**读者问：网络请求怎么优化才省电？**

**AI答：**

1. **理解功耗来源**：**射频每次通信都要唤醒基带（tail energy）**，而且**弱信号时发射功率指数级上升**。所以"少通信"比"传得小"更重要。
2. **减少请求次数**：
   - **接口合并**（首页 10 个接口 → 1 个聚合接口）；
   - **增量同步**（只传变更）；
   - **缓存 + 条件请求**（ETag / Last-Modified → 304 也是网络交互，但流量极小）；
   - **本地缓存优先**：命中缓存就不发请求（省电效果最大）。
3. **减少单次成本**：
   - **连接复用**（OkHttp `ConnectionPool`；HTTP/2 多路复用）；
   - **预连接**（提前完成 DNS + TCP + TLS 握手，TLS 握手是最贵的部分之一）；
   - **数据压缩**（gzip / br，流量减少 60%~80%，射频工作时间同步减少）。
4. **重连策略**：
   - **指数退避**（1s→2s→4s→…→上限）+ **随机抖动**（避免惊群）；
   - **区分错误类型**：4xx 不重试，5xx / 网络异常才重试。
5. **网络类型感知**：
   - 大文件上传用 `NetworkType.UNMETERED`（只在 Wi-Fi）；
   - 移动数据下降低图片质量、减少请求体。
6. **推送替代轮询**：**这是最彻底的方案**——服务端推，客户端不唤醒。
7. **面试话术**："**网络省电的第一原则是'少通信'，第二是'别在弱信号下通信'（强信号下同样的数据射频功耗低得多），第三是'用推送替代轮询'。**"

---

**读者问：屏幕相关怎么省电？深色模式真的有用吗？**

**AI答：**

1. **深色模式**：
   - **在 OLED 屏幕上确实有效**——黑色像素不发光，理论上能省 10%~30%（取决于内容）；
   - **在 LCD 背光屏幕上基本无效**（背光一直亮着）；
   - 实践上要配合 `AppCompatDelegate.MODE_NIGHT_FOLLOW_SYSTEM` 跟随系统。
2. **屏幕常亮**：
   - `FLAG_KEEP_SCREEN_ON` **必须用完即清**（`clearFlags`）——这是最常见的"用户投诉屏幕一直亮"的原因；
   - 更好的做法：用 `WindowInsetsController` 配合可见性判断。
3. **刷新率**：
   - Android 11+ `Surface.setFrameRate()`：静态内容降到 60，滚动时升到 120；
   - Android 12+ **LTPO 自适应刷新率**：静止时降到 1Hz；
   - `window.attributes.preferredRefreshRate = 60f` 强制低刷。
4. **GPU / 过度绘制**：
   - 过度绘制让 GPU 满载 → 功耗上升（**CPU 不高但 GPU 很忙**）；
   - 减少阴影（用 elevation）、减少半透明叠加、减少背景层。
5. **其它**：
   - **动画**：掉帧时多耗电；关闭不必要的动画；
   - **深色模式 + 降低刷新率 + 用完即关常亮**是屏幕侧的三板斧。
6. **面试话术**："**屏幕侧我会说三条：深色模式（OLED 才有效）、用完即关常亮、静态内容降刷新率。第三条在 LTPO 机型上效果最明显，静止时可以降到 1Hz。**"

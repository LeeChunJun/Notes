# 内存优化

## 一句话定义

内存优化的本质是**在"减少占用、复用对象、及时释放"三件事上做工程化取舍**。Android 应用最常见的三个内存问题分别是：**Bitmap 撑爆 native heap、静态引用导致泄漏、缓存无上限导致抖动**。定位手段是标准的三件套：**Memory Profiler 看趋势 → Heap Dump 看对象 → LeakCanary / MAT 看引用链**；治理手段是：**采样解码 + LruCache + 对象池 + onTrimMemory 分级释放**。

## 核心原理

### 1. 内存优化的三个抓手（**总纲**）

```text
┌──────────────────────────────────────────────────────────────┐
│ ① 减少占用（Don't allocate）                                   │
│    · Bitmap 采样解码（inSampleSize）+ 颜色格式降级             │
│    · 大数组分片 / mmap / 流式处理                              │
│    · 避免装箱、避免不必要的大对象                              │
│    · 布局层级扁平化（减少 View 对象数量）                        │
├──────────────────────────────────────────────────────────────┤
│ ② 复用对象（Reuse）                                            │
│    · Bitmap 对象池（避免反复创建 native 内存）                  │
│    · StringBuilder 复用、View 复用（RecyclerView）            │
│    · 线程池复用、协程作用域复用                                │
│    · 图片缓存 LruCache（避免重复解码）                          │
├──────────────────────────────────────────────────────────────┤
│ ③ 及时释放（Release in time）                                  │
│    · 消除泄漏（静态引用 / 内部类 / Handler / ThreadLocal）      │
│    · 缓存设上限（LruCache）                                    │
│    · onTrimMemory 分级降级                                     │
│    · onDestroy 清理资源（WebView / Cursor / 注册）              │
└──────────────────────────────────────────────────────────────┘
```

### 2. Bitmap 内存是怎么算的（**高频计算题**）

```text
【Bitmap 内存公式】
  内存 = 宽度 × 高度 × 每像素字节数

  每像素字节数由 inPreferredConfig 决定：
    ARGB_8888 → 4 字节（默认）
    RGB_565   → 2 字节（省一半，无透明通道）
    ARGB_4444 → 2 字节（已废弃）
    ALPHA_8   → 1 字节（只有 alpha 通道）
    HARDWARE  → 0 字节（GPU 纹理，但不可读像素、不能复用/变换）

  举例：一张 1080×1920 的全屏图
    ARGB_8888 → 1080 × 1920 × 4 = 8,294,400 字节 ≈ 7.9 MB
    RGB_565   → 1080 × 1920 × 2 = 4,147,200 字节 ≈ 3.95 MB

  ⚠️ 注意：getByteCount() 只算"像素数据"，
     getAllocationByteCount() 还要加上 Bitmap 对象本身的开销（通常几十字节）
```

```text
【Bitmap 内存放在哪里】
  Android 7.1 及以前：像素数据在 Dalvik/ART Java 堆 → 占用 memoryClass 配额
  Android 8.0 起    ：像素数据在 Native Heap → 不占 Java 堆配额
                      → 但 GC 不再自动回收，必须显式 recycle() 或依赖内存压力回收
                      → Java 堆里只剩一个很小的 Bitmap 壳对象（约几十字节）

  面试话术："**8.0 之后 Bitmap 不再是'Java 堆里的东西'了，所以'看到 Java 堆不高就以为没内存问题'是个常见误判——真正吃掉内存的是 native heap 和 graphics。**"
```

### 3. Bitmap 采样解码：`inSampleSize` 与 `inPreferredConfig`

#### 3.1 `BitmapFactory.Options` 关键字段

| 字段 | 作用 | 面试要点 |
| --- | --- | --- |
| `inJustDecodeBounds` | **只解析尺寸，不解码像素** | 第一次解码必设，用于算 `inSampleSize` |
| `inSampleSize` | **采样率**，必须是 2 的幂（1,2,4,8...） | 值为 2 表示宽高各减半 → **内存变成 1/4** |
| `inPreferredConfig` | 目标颜色格式 | `RGB_565` 省一半内存；`ARGB_8888` 保透明 |
| `inScaled` | 是否按 `inDensity/inTargetDensity` 缩放 | `inDensity = 160` 可避免大图被放大 |
| `inMutable` | 是否可修改像素 | 需修改像素时必须为 true（会多占内存） |
| `inPremultiplied` | 预乘 alpha | 默认 true |
| `inPurgeable`（旧） | 已废弃 | — |

#### 3.2 标准的两段式采样流程

```text
【为什么必须两次解码】
  第一次：inJustDecodeBounds = true
          → BitmapFactory 只读图片头，解析出 outWidth/outHeight
          → ❗不会分配像素内存
  第二次：设置 inSampleSize = 2 的幂，使得
          outWidth / inSampleSize ≈ 目标宽度
          → 正式解码，内存只有原图的 1/4（采样率 2）

  ⚠️ 关键：如果第一次就把 inSampleSize 设成 1 再解码，
     那么 8MB 的图就已经进内存了，再怎么"缩"也来不及。
```

#### 3.3 采样率计算

```text
  要求：解码后的尺寸 >= 目标尺寸（宁可略大也不要糊）
  公式：inSampleSize = 2^k，使得
        outWidth / 2^k >= reqWidth  且  outHeight / 2^k >= reqHeight

  例：原图 4000×3000，目标 1080×1080
     k=0: 4000×3000  → 4000 >= 1080 ✓ 但 3000 >= 1080 ✓  → 但 k=0 太大
     实际取 2 的幂中满足条件的最小值：
     k=1: 2000×1500  ✓
     k=2: 1000×750   → 1000 < 1080 ✗
     → inSampleSize = 2
     内存 = 2000 × 1500 × 4 = 12MB（原图 48MB）

  ⚠️ 采样率是 2 的幂，所以尺寸会有"跳变"（可能偏小）。
     对清晰度要求高的场景（如图片详情页），
     应使用 Android 官方库 Coil / Glide 的精确缩放（它们内部用 BitmapShader + Canvas 做精确变换）。
```

### 5. LruCache：缓存的上限与淘汰

```text
【LruCache 的工作原理】
  LinkedHashMap（accessOrder = true）维护访问顺序
  每次 get() / put() → 把该 Entry 移到链表尾部（最近使用）
  超出 maxSize → 淘汰链表头部（最久未使用）
  sizeOf() 是抽象方法 → 由调用方定义"大小"的含义（字节数、条目数）
```

```kotlin
/**
 * ✅ 标准 LruCache：以 KB 为单位
 */
class ImageCache(maxKb: Int = 20 * 1024) : LruCache<String, Bitmap>(maxKb) {

    override fun sizeOf(key: String, value: Bitmap): Int {
        // ⚠️ 用 allocationByteCount（包含 Bitmap 对象开销）更准确
        return value.allocationByteCount / 1024
    }

    override fun entryRemoved(evicted: Boolean, key: String, oldValue: Bitmap, newValue: Bitmap?) {
        if (evicted && oldValue.isRecycled.not()) {
            // ⚠️ 淘汰的 Bitmap 不需要 recycle()！
            // 因为它可能还被某个正在绘制的 Canvas 引用，recycle 会导致
            // "Canvas: trying to use a recycled bitmap" 崩溃。
            // ✅ 正确做法：什么都不做，让 GC 回收。
        }
    }

    fun get(key: String): Bitmap? = get(key)
}
```

**关键决策：LruCache 的 size 应该是进程可用内存的多少？**

```text
  参考公式（业界常用）：
    maxSize = (Runtime.getRuntime().maxMemory() / 1024) * 1/8

  理由：
    · Java 堆上限通常 192MB ~ 512MB
    · 1/8 = 24MB ~ 64MB 作为图片缓存
    · 留出 7/8 给业务对象，避免缓存把堆吃满触发 LMK

  注意事项：
    ① 图片缓存只是缓存的一部分，还要给列表数据、页面对象留空间
    ② 低端机（2GB RAM）上 1/8 可能过大，建议 1/16
    ③ 用 onTrimMemory 动态缩小缓存（见下）
```

### 6. 内存分析工具链（**必须掌握的四个**）

| 工具 | 用途 | 关键操作 |
| --- | --- | --- |
| **Android Studio Memory Profiler** | 实时看堆/native/graphics 占用、分配记录、GC 事件 | `Dump the heap` 抓 hprof；`Record allocations` 看对象分配 |
| **Heap Dump（hprof）** | 某一时刻的堆快照 | `adb shell am dumpheap <pkg> /sdcard/heap.hprof` → `adb pull` |
| **MAT（Memory Analyzer Tool）** | Eclipse 的 hprof 分析器，**Leak Suspects 报告**最强 | "Path to GC Roots → exclude weak/soft references" 找持有链 |
| **LeakCanary** | **自动**检测泄漏并给出可读的引用链 | 集成到 debug 包，泄漏时自动抓 dump 并弹窗 |

#### 6.1 Memory Profiler 的四个视图（**面试要能说**）

```text
1. Overview（总览）
   ├─ Heap：Java 堆（已分配 / 剩余 / 增长上限）
   ├─ Native Heap：so 的 malloc（Bitmap 像素在这里）
   ├─ Graphics：GPU 纹理
   ├─ Code：代码段
   └─ Stack：线程栈
   → 关键结论：Bitmap 问题的"Total PSS"高但"Heap"不高 → 看 Native Heap

2. Memory PSS（按进程分列）
   → 比 Total PSS 更准确（含共享内存分摊）

3. Heap Dump
   → 点"Dump the heap"，等待几秒

4. Allocation Tracking（分配记录）
   → 只在 debug 包可用
   → 记录每次 new 的调用栈 → 定位"是谁在疯狂创建对象"
   → 开启后显著变慢，不要在 release 用
```

#### 6.2 LeakCanary 的工作原理（**高频原理题**）

```text
【LeakCanary 四阶段流水线】
  ① Watcher（监听）
     └─ ApplicationWatcher / ActivityLifecycleCallbacks
     └─ 在 Activity onDestroy 后延迟 5 秒（KEY_WATCHER_DURATION）
        检查该 Activity 是否仍可达
        → 可达 = 可能泄漏
        ↓
  ② Heap Dump（抓快照）
     └─ Debug.dumpHprofData(file) → 写 hprof 文件
     └─ 整个进程会短暂 Stop-The-World（约几百 ms）
     ↓
  ③ 分析（Shark）
     └─ Shark：Square 开发的 Kotlin hprof 解析库
     └─ 用 HprofParser 解析堆快照 → 建立对象图
     └─ 计算每个对象的 retained size（保留大小）
        （retained size = 该对象独占的内存，剔除它独占可达的子树）
     ↓
  ④ 引用链分析（找 GC Root）
     └─ 从泄漏对象出发做 BFS/DFS，找到最短的到 GC Root 的引用路径
     └─ 关键：排除 WeakReference / SoftReference / PhantomReference 的引用
        （弱引用被清空是正常的，不算泄漏）
     └─ 输出 LeakTrace：
        ┌────────────────────────────────────┐
        │ Leak: 0a1b2c3d MyActivity          │
        │ GC Root: Local variable in main    │
        │ ├─ MyActivity.mContext (Context)   │
        │ │   ← 静态字段/内部类持有          │
        └────────────────────────────────────┘
```

### 7. 对象池与复用（**减少分配 = 减少 GC**）

```text
【为什么复用能优化内存】
  GC 的成本 ∝ 存活对象扫描量 + 分配量
  · 高频创建短命对象 → 分配速率高 → GC 频繁 → STW 变多 → 掉帧
  · 复用对象 → 分配速率下降 → GC 频率下降 → 帧率提升

【典型可池化的对象】
  · Bitmap（最典型，native 内存，创建成本最高）
  · StringBuilder / StringBuffer
  · 线程池（ThreadPoolExecutor）
  · 协程调度器 / Dispatcher
  · View（RecyclerView）
  · Matrix / Rect / Path（绘制频繁时）
  · 序列化 buffer（ByteArray）
```

#### 7.1 Bitmap 池（**重点**）

```kotlin
/**
 * ✅ 简单的 Bitmap 内存池（基于内存位图）
 * 适用场景：频繁加载大小相近的缩略图（如列表快速滑动）
 */
object BitmapPool {

    private val pool = mutableListOf<Bitmap>()
    private const val MAX_POOL_SIZE = 8
    private const val MAX_BITMAP_SIZE = 512 * 512 * 4   // 1MB 以内才入池

    /** 获取一个可复用且足够大的 Bitmap */
    fun obtain(width: Int, height: Int, config: Bitmap.Config = Bitmap.Config.ARGB_8888): Bitmap {
        synchronized(pool) {
            val index = pool.indexOfFirst { it.width >= width && it.height >= height }
            if (index >= 0) {
                val bitmap = pool.removeAt(index)
                // ⚠️ 复用前必须清空，否则会有残影
                bitmap.eraseColor(0)
                return bitmap
            }
        }
        return Bitmap.createBitmap(width, height, config)
    }

    /** 归还到池中 */
    fun recycle(bitmap: Bitmap) {
        if (bitmap.isRecycled) return
        if (bitmap.byteCount > MAX_BITMAP_SIZE) {
            bitmap.recycle()
            return
        }
        synchronized(pool) {
            if (pool.size < MAX_POOL_SIZE) {
                pool.add(bitmap)
            } else {
                bitmap.recycle()
            }
        }
    }
}
```

> [!warning] **Bitmap 池的三大坑**
> 1. **复用后必须 `eraseColor(0)`**，否则会看到上一个 bitmap 的残影。
> 2. **尺寸不匹配**：池里的 bitmap 可能比需要的大，绘制时要按目标尺寸 `drawBitmap(src, srcRect, dstRect, paint)`，否则会变形。
> 3. **`recycle()` 的时机**：**只有在确定没有任何 Canvas / Drawable 还引用它时才能 recycle**。现代 Android（8.0+）推荐**不手动 recycle**，交给 GC + `NativeAllocationRegistry` 处理。

> [!tip] **生产环境建议：直接用 Coil / Glide**
> 它们已经实现了**内存缓存 + 磁盘缓存 + Bitmap 池 + 生命周期感知 + 自动降采样**，并处理好了所有上述坑。手写池容易引入更难查的 bug。

### 8. `onTrimMemory` 与内存监控

#### 8.1 分级与响应

| 常量 | 值 | 触发场景 | 响应策略 |
| --- | --- | --- | --- |
| `TRIM_MEMORY_RUNNING_MODERATE` | 5 | 系统开始回收**后台**进程，本进程在前台 | 清理二级缓存 |
| `TRIM_MEMORY_RUNNING_LOW` | 10 | 回收更激进 | 清理大部分缓存 |
| `TRIM_MEMORY_RUNNING_CRITICAL` | 15 | 本进程即将被杀 | 清理一切可清理的 |
| `TRIM_MEMORY_UI_HIDDEN` | 20 | **UI 不可见**（`onStop` 之后） | 清理 UI 相关资源（图片缓存） |
| `TRIM_MEMORY_BACKGROUND` | 40 | 进程在后台且已被缓存 | 清空所有缓存 |
| `TRIM_MEMORY_MODERATE` | 60 | 后台，内存紧张 | 清空缓存 |
| `TRIM_MEMORY_COMPLETE` | 80 | 进程即将被杀 | 清空一切，持久化必要状态 |

```kotlin
/**
 * ✅ onTrimMemory 的正确使用
 */
class MyApplication : Application(), ComponentCallbacks2 {

    override fun onTrimMemory(level: Int) {
        super.onTrimMemory(level)
        when (level) {
            ComponentCallbacks2.TRIM_MEMORY_UI_HIDDEN -> {
                // 页面不可见：清图片缓存（用户回来看时重新加载即可）
                ImageCache.get().evictAll()
            }
            ComponentCallbacks2.TRIM_MEMORY_RUNNING_LOW -> {
                // 前台但内存紧张：清掉一半缓存
                ImageCache.get().trimToSize(ImageCache.get().maxSize() / 2)
            }
            ComponentCallbacks2.TRIM_MEMORY_COMPLETE -> {
                // 准备被杀：清空所有缓存，持久化关键状态
                ImageCache.get().evictAll()
                // ⚠️ 不要在这里做耗时 IO！
            }
        }
    }
}
```

> [!warning] **`onTrimMemory` 在主线程回调**
> 清理大对象（解码、序列化）应放到后台线程，否则会造成卡顿。

#### 8.2 内存监控与 LMK

```text
【内存监控的三层】
  ① 应用自身感知
     · onTrimMemory / onLowMemory（系统通知）
     · Debug.getRuntimeStats()["gc.count"] / ["gc.time"]（GC 次数与总耗时）
     · Runtime.getRuntime()（maxMemory / totalMemory / freeMemory）
  ② 系统侧统计
     · ActivityManager.getProcessMemoryInfo() → Debug.MemoryInfo（PSS）
     · dumpsys meminfo <pkg>
  ③ 内核侧
     · lmkd 守护进程：读 MemAvailable / SwapFree / Zram
     · 按 oom_score_adj 从高到低杀进程
     · 阈值可通过 /sys/module/lowmemorykiller/parameters 调整
```

### 9. 常见 OOM 场景与对策

| 场景 | 根因 | 对策 |
| --- | --- | --- |
| **大图解码 OOM** | 一张 4000×3000 的图 = 48MB | `inSampleSize` 采样；`RGB_565`；用 `ImageDecoder`（API 28+）的 `setTargetSampleSize` |
| **列表快速滑动 OOM** | 一次性加载几十张大图 | 列表项用**缩略图尺寸**解码；LruCache；`RecyclerView` 复用 |
| **批量加载 OOM** | 循环里 decode 累积 | 用 `LruCache` + 及时释放；分批加载 |
| **内存泄漏 OOM** | 泄漏对象持续累积 | LeakCanary 定位并修复 |
| **缓存无上限 OOM** | `HashMap` 当缓存 | 改 `LruCache` + 上限 |
| **大数组 OOM** | `byte[10_000_000]` | 分片处理 / mmap / 流式 |
| **多进程 OOM** | 多个进程各占一份内存 | 主进程只留 UI，独立进程放重任务 |
| **Fragment 泄漏 OOM** | Fragment 持有 Activity | 用 `viewLifecycleOwner` / `Fragment.viewLifecycleOwner.lifecycleScope` |
| **Compose 误用 OOM** | `remember` 住大对象 | 大对象用 `remember` + `DisposableEffect` 释放；避免在 `remember` 里缓存 Bitmap |

**预防性兜底**：

```kotlin
    // ⚠️ largeHeap 只是提高上限，不是解决方案
```

### 1. 完整的 Bitmap 采样解码工具

```kotlin
object BitmapDecoder {

    /**
     * ✅ 从 Uri 安全地解码一张缩略图
     * @param reqWidth  目标最大宽度（px）
     * @param reqHeight 目标最大高度（px）
     * @param config    颜色格式，RGB_565 可省一半内存
     */
    fun decodeSampled(
        context: Context,
        uri: Uri,
        reqWidth: Int,
        reqHeight: Int,
        config: Bitmap.Config = Bitmap.Config.RGB_565
    ): Bitmap? {
        val resolver = context.contentResolver

        // ① 第一遍：只读尺寸，不分配像素内存
        val boundsOptions = BitmapFactory.Options().apply {
            inJustDecodeBounds = true
        }
        resolver.openInputStream(uri)?.use {
            BitmapFactory.decodeStream(it, null, boundsOptions)
        }
        val (outWidth, outHeight) = boundsOptions.outWidth to boundsOptions.outHeight
        if (outWidth <= 0 || outHeight <= 0) return null

        // ② 计算采样率（2 的幂）
        val sampleSize = calculateInSampleSize(outWidth, outHeight, reqWidth, reqHeight)

        // ③ 第二遍：正式解码
        val decodeOptions = BitmapFactory.Options().apply {
            inSampleSize = sampleSize
            inPreferredConfig = config
            inScaled = true
            inDensity = 160          // 避免按密度二次放大
            inTargetDensity = 160
        }
        return resolver.openInputStream(uri)?.use {
            BitmapFactory.decodeStream(it, null, decodeOptions)
        }
    }

    /**
     * ✅ 计算 inSampleSize：必须满足 解码后尺寸 >= 目标尺寸
     */
    private fun calculateInSampleSize(
        width: Int, height: Int,
        reqWidth: Int, reqHeight: Int
    ): Int {
        var sampleSize = 1
        if (height > reqHeight || width > reqWidth) {
            val halfHeight = height / 2
            val halfWidth = width / 2
            while (halfHeight / sampleSize >= reqHeight && halfWidth / sampleSize >= reqWidth) {
                sampleSize *= 2
            }
        }
        return sampleSize
    }

    /**
     * ✅ Android 9+ 官方推荐 API：ImageDecoder
     *    支持 setTargetSampleSize（可为任意值，不限于 2 的幂），比 BitmapFactory 更灵活
     */
    fun decodeWithImageDecoder(context: Context, uri: Uri, reqWidth: Int): Bitmap? {
        val source = ImageDecoder.createSource(context.contentResolver, uri)
        return ImageDecoder.decodeBitmap(source) { decoder, info, _ ->
            decoder.setTargetSampleSize(
                (info.size.width / reqWidth).coerceAtLeast(1)
            )
            decoder.allocator = ImageDecoder.ALLOCATOR_SOFTWARE   // 允许读像素
            decoder.memorySizePolicy = ImageDecoder.MEMORY_POLICY_LOW_RAM
        }
    }
}
```

### 2. LruCache + 磁盘缓存的完整图片加载器

```kotlin
/**
 * ✅ 内存缓存 + 磁盘缓存的最小实现
 * 演示 LruCache 的正确用法：sizeOf / entryRemoved 不 recycle
 */
class ImageLoader(private val context: Context) {

    private val memoryCache: LruCache<String, Bitmap> = run {
        val maxKb = (Runtime.getRuntime().maxMemory() / 1024).toInt() / 8
        object : LruCache<String, Bitmap>(maxKb) {
            override fun sizeOf(key: String, value: Bitmap) = value.allocationByteCount / 1024
            override fun entryRemoved(evicted: Boolean, key: String, old: Bitmap, new: Bitmap?) {
                // ⚠️ 绝不 recycle()：可能仍被正在绘制的 Canvas 引用
            }
        }
    }

    private val diskCacheDir = File(context.cacheDir, "img").apply { mkdirs() }

    suspend fun load(url: String, reqWidth: Int): Bitmap? = withContext(Dispatchers.IO) {
        val key = "${url}_$reqWidth"

        // ① 内存缓存命中
        memoryCache.get(key)?.let { return@withContext it }

        // ② 磁盘缓存命中
        val file = File(diskCacheDir, key.hashCode().toString())
        if (file.exists()) {
            val bmp = BitmapFactory.decodeFile(file.absolutePath, bitmapOptions(reqWidth))
            if (bmp != null) {
                memoryCache.put(key, bmp)
                return@withContext bmp
            }
        }

        // ③ 网络加载（这里用简化的示意）
        val bytes = download(url) ?: return@withContext null
        file.writeBytes(bytes)                 // 写磁盘
        val bmp = BitmapFactory.decodeByteArray(bytes, 0, bytes.size, bitmapOptions(reqWidth))
        if (bmp != null) memoryCache.put(key, bmp)
        bmp
    }

    private fun bitmapOptions(reqWidth: Int) = BitmapFactory.Options().apply {
        inSampleSize = 2
        inPreferredConfig = Bitmap.Config.RGB_565
    }

    private fun download(url: String): ByteArray? = null   // 实际项目用 OkHttp

    /** 内存压力时按比例缩小缓存 */
    fun onTrimMemory(level: Int) {
        when (level) {
            ComponentCallbacks2.TRIM_MEMORY_UI_HIDDEN -> memoryCache.evictAll()
            ComponentCallbacks2.TRIM_MEMORY_RUNNING_LOW -> {
                memoryCache.trimToSize(memoryCache.maxSize() / 2)
            }
            ComponentCallbacks2.TRIM_MEMORY_COMPLETE -> memoryCache.evictAll()
        }
    }
}
```

### 4. 内存抖动的检测与治理

```kotlin
/**
 * ✅ 内存抖动（Thrashing）检测：
 *    特征 = GC 频繁，但每次回收量很小，堆使用率长期贴近上限
 */
object ThrashingDetector {

    private var lastGcCount = 0
    private var sampleCount = 0

    /**
     * 每秒采样一次，连续 3 次"GC 频繁但回收量小"则判定为抖动
     */
    fun sample(): Boolean {
        val stats = Debug.getRuntimeStats()
        val gcCount = stats["gc.count"]?.toLongOrNull() ?: 0L
        val rt = Runtime.getRuntime()
        val used = rt.totalMemory() - rt.freeMemory()

        val gcDelta = gcCount - lastGcCount
        lastGcCount = gcCount
        sampleCount++

        // 堆使用率 > 85%
        val usage = used.toDouble() / rt.maxMemory()
        // 一秒内 GC 超过 5 次
        val gcFrequent = gcDelta > 5

        if (usage > 0.85 && gcFrequent) {
            APM.report("memory_thrashing", "usage=$usage", "gcDelta=$gcDelta")
            return true
        }
        return false
    }
}
```

```kotlin
/**
 * ✅ 把缓存治理集中到一个地方

class CacheGovernor(private val app: Application) {

    private val imageCache = ImageCache(maxKb = 24 * 1024)
    private val dataCache = LruCache<String, Any>(8 * 1024)   // 条目数

    fun init() {
        app.registerComponentCallbacks(object : ComponentCallbacks2 {
            override fun onTrimMemory(level: Int) {
                when (level) {
                    ComponentCallbacks2.TRIM_MEMORY_UI_HIDDEN -> {
                        imageCache.evictAll()

                    ComponentCallbacks2.TRIM_MEMORY_RUNNING_LOW -> {
                        imageCache.trimToSize(imageCache.maxSize() / 2)
                        dataCache.evictAll()
                    }
                    ComponentCallbacks2.TRIM_MEMORY_RUNNING_CRITICAL,
                    ComponentCallbacks2.TRIM_MEMORY_BACKGROUND,
                    ComponentCallbacks2.TRIM_MEMORY_MODERATE -> {
                        imageCache.evictAll()
                        dataCache.evictAll()
                    }
                    ComponentCallbacks2.TRIM_MEMORY_COMPLETE -> {
                        imageCache.evictAll()
                        dataCache.evictAll()
                        // 持久化关键状态（放后台线程）
                    }
                }
            }
            override fun onLowMemory() {
                imageCache.evictAll()
            }
            override fun onConfigurationChanged(newConfig: Configuration) {}
        })
    }
}
```

## 常见问题 / 面试要点

**读者问：怎么定位一个内存泄漏？完整流程是什么？**

**AI答：**

1. **第一步：确认是"泄漏"还是"正常高水位"**。
   - 重复进入/退出页面 20~50 次，看 **PSS 是否单调递增**；
   - 正常会稳定在某个平台（缓存填满后不再涨），泄漏会持续上涨；
   - 这是 LeakCanary 的核心判定逻辑（对象在 GC 后仍可达即判定泄漏）。
2. **第二步：抓 Heap Dump**。
   - Android Studio → Memory Profiler → `Dump the heap`；
   - 命令行：`adb shell am dumpheap <pkg> /sdcard/heap.hprof` → `adb pull`；
   - LeakCanary 会**自动**抓取并在检测到泄漏时弹出可视化页面。
3. **第三步：分析引用链，找 GC Root（关键）**。
   | GC Root | 典型含义 | 修法 |
   | --- | --- | --- |
   | `static field` | 静态变量持有 | 改用 Application / WeakReference |
   | `inner class` | 非静态内部类 | 抽成 static + 弱引用 |
   | `MessageQueue` | Handler 延迟消息 | `removeCallbacksAndMessages(null)` |
   | `ThreadLocal` | 线程池的 ThreadLocal 未清 | `finally { remove() }` |
   | `Local Broadcast Receiver` | 广播未反注册 | `unregisterReceiver` |
   | `View` | View 的监听器 / 动画 | 移除监听 / `cancel()` 动画 |
   - MAT：`Leak Suspects` → `Path to GC Roots` → **exclude weak/soft references**；
   - LeakCanary：用 **Shark** 解析 hprof，输出 `LeakTrace`（对象 → 引用链 → GC Root）。
4. **第四步：修复并验证**：重复触发 GC 确认能被回收；再跑一轮 LeakCanary 确认无新泄漏；回归测试 PSS 曲线平稳。
5. **面试话术**："**我的定位路径是：先用 PSS 曲线判断'是不是泄漏'，再用 LeakCanary 直接看引用链（它已经自动做了'找最短 GC Root 路径'这件事），最后按 GC Root 分类修。MAT 是补充手段，一般用于分析复杂的 native 泄漏。**"

---

**读者问：Bitmap 的内存怎么算？为什么 decode 出来的图比文件大那么多？**

**AI答：**

1. **公式**：`内存 = 宽 × 高 × 每像素字节数`。
   - ARGB_8888 = 4 字节/像素 → 1080×1920 = **7.9 MB**；
   - RGB_565 = 2 字节/像素 → 1080×1920 = **3.95 MB**；
   - ARGB_4444 = 2 字节（已废弃）；ALPHA_8 = 1 字节；HARDWARE = 0（GPU 纹理）。
2. **为什么比文件大**：**PNG/JPEG 是压缩格式，解码后变成未压缩的原始像素**。一张 2MB 的 JPEG，解码成 ARGB_8888 可能是 8MB —— **放大了 4 倍**。
3. **精确值用 `getAllocationByteCount()`**（含 Bitmap 对象开销），`getByteCount()` 只算像素。
4. **Android 8.0 的变化**：像素数据从 **Java 堆搬到 native heap** → 不占 `memoryClass` 配额，但**GC 不再自动回收**，需要显式处理或依赖 `NativeAllocationRegistry`。
5. **因此的排查技巧**：如果 **Java 堆不高但 Total PSS 很高**，一定要去看 **Native Heap**（Bitmap 在那里）。
6. **面试话术**："**Bitmap 内存 = 解码后的像素量，不是文件大小。JPG 是压缩的，decode 完就是原始像素。8.0 之后这块内存还在 native heap，所以看 Java 堆看不出问题，得看 Native Heap 和 Graphics。**"

---

**读者问：OOM 怎么防？有哪些常见的 OOM 场景？**

**AI答：**

1. **防御策略（分层）**：
   - **① 源头减少**：采样解码、`RGB_565`、大数组分片/mmap、避免不必要的大对象；
   - **② 复用**：Bitmap 池、`LruCache`、View 复用、线程池复用；
   - **③ 及时释放**：消除泄漏、缓存上限、`onTrimMemory` 分级清理；
   - **④ 兜底**：`OutOfMemoryError` 处理里清缓存并提示；**`largeHeap` 只是提高上限，不是解决方案**。
2. **典型场景与对策**：
   - **大图解码** → `inSampleSize` + `ImageDecoder.setTargetSampleSize`；
   - **列表滑动** → 缩略图尺寸解码 + `LruCache` + `RecyclerView` 复用；
   - **批量加载** → 分批 + 分页 + 及时释放；
   - **泄漏累积** → LeakCanary；
   - **缓存无上限** → `LruCache`；
   - **超大数组** → 分片 / `MappedByteBuffer` / 流式；
   - **多进程放大** → 重任务放独立进程。
3. **`largeHeap` 的真相**：
   - 提升的是 **Java 堆上限**（`getLargeMemoryClass()`），**对 native 内存无效**；
   - 堆越大 → GC 停顿越长；
   - RSS 更大 → **oom_score_adj 更容易被 LMK 盯上**；
   - 正确顺序：**先优化，实在不够再考虑**。
4. **面试话术**："**防 OOM 是一个体系：源头少分配、过程中复用、结束时释放、兜底做降级。`largeHeap` 是把问题推后，不是解决。**"

---

**读者问：LeakCanary 的原理是什么？它是怎么判断"泄漏"的？**

**AI答：**

1. **四阶段流水线**：
   - **Watcher**：监听 Activity/Fragment/View 的销毁（`ActivityLifecycleCallbacks`），销毁后延迟约 5 秒（给 GC 留时间）再检查对象**是否仍可达**；
   - **Heap Dump**：`Debug.dumpHprofData()` 写 hprof（整个进程短暂 STW）；
   - **分析（Shark）**：Shark 是 Square 写的 Kotlin hprof 解析库，构建对象图，计算 **retained size**（保留大小 = 该对象独占的内存）；
   - **引用链分析**：从泄漏对象反向 BFS/DFS，找到**最短的到 GC Root 的路径**，并**排除 Weak/Soft/Phantom 引用**（弱引用被清空是正常行为，不算泄漏）。
2. **判定"泄漏"的核心**：**对象在一次强制 GC 之后仍然可达**。如果可达，说明有人（GC Root）还强引用着它。
3. **输出的 LeakTrace 结构**：`泄漏对象 → 中间持有者（如 MyActivity.mContext）→ GC Root（如 static field）`。
4. **版本演进**：1.x 的 `RefWatcher` → 2.x 的 `AppWatcher`（自动安装）→ 2.12+ 移除 `RefWatcher` 概念、引入 Kotlin API。
5. **注意**：LeakCanary **只能发现 Java 层的泄漏**，native 层的泄漏（malloc 未释放）它无能为力。
6. **面试话术**："**LeakCanary 的本质是'GC Root 可达性分析'。它不发明新的检测方法，它把 MAT 的核心能力（找最短 GC Root 路径）用 Kotlin 实现并自动化了，再加上 Android 特有的'强制 GC 后仍可达'判定。**"

---

**读者问：`inSampleSize` 怎么用？为什么不能只解码一次？**

**AI答：**

1. **`inSampleSize` 是采样率**，取值必须是 **2 的幂**（1、2、4、8…）。值为 2 表示**宽高各减半**，像素量变成 **1/4**（内存也变 1/4）。
2. **必须两段式**：
   - 第一次 `inJustDecodeBounds = true` → **只解析图片头拿到 outWidth/outHeight，不分配任何像素内存**；
   - 根据目标尺寸算出 `inSampleSize`；
   - 第二次正式解码。
3. **为什么不能一次**：如果在第一次就把 `inSampleSize` 设成 1（或没设），**大图的像素已经进内存了**，之后再缩也来不及——这正是 OOM 的典型原因。
4. **计算公式**：`inSampleSize = 2^k`，使 `outWidth/2^k >= reqWidth && outHeight/2^k >= reqHeight`。宁可略大于目标，也不要小于。
5. **缺点**：采样率是 2 的幂，尺寸会"跳变"（从 2 到 4 直接减半），可能出现偏糊。
   - 需要精确缩放时用 **Coil / Glide**（内部用 `BitmapShader` + `Canvas` 做精确变换）；
   - 或用 **Android 9+ 的 `ImageDecoder.setTargetSampleSize()`**（支持任意采样率）。
6. **面试话术**："**`inJustDecodeBounds` 那一遍是免费的，因为它只读文件头。这就是'先量后裁'的思路。**"

---

**读者问：`onTrimMemory` 有哪些级别？分别在什么场景触发？**

**AI答：**

1. | 级别 | 场景 | 建议动作 |
   | --- | --- | --- |
   | `TRIM_MEMORY_UI_HIDDEN` (20) | **UI 不可见**（onStop 后） | 清图片/渲染缓存（最常用） |
   | `TRIM_MEMORY_RUNNING_MODERATE` (5) | 前台，系统开始回收后台进程 | 适度清二级缓存 |
   | `TRIM_MEMORY_RUNNING_LOW` (10) | 前台，回收更激进 | 清大部分缓存 |
   | `TRIM_MEMORY_RUNNING_CRITICAL` (15) | 前台，本进程快被杀 | 清一切可清的 |
   | `TRIM_MEMORY_BACKGROUND` (40) | 后台且已缓存 | 清空全部缓存 |
   | `TRIM_MEMORY_MODERATE` (60) | 后台，内存紧张 | 清空缓存 |
   | `TRIM_MEMORY_COMPLETE` (80) | 即将被杀 | 清空一切 + 持久化状态 |
2. **要点**：
   - **`onTrimMemory` 在主线程回调** → 清理大对象要放后台线程；
   - `onLowMemory()` 是老 API，已基本被 `TRIM_MEMORY_COMPLETE` 取代；
   - 它**是通知，不是强制**：应用不响应，系统也会在必要时直接杀进程。
3. **面试话术**："**`onTrimMemory` 是系统给的水位通知，做分级降级用。但它是**最后一层保险**，不能替代真正的内存优化。**"

---

**读者问：什么是内存抖动（Memory Thrashing）？怎么发现和治理？**

**AI答：**

1. **定义**：**物理内存充足，但进程频繁 GC、每次回收量却很少**，GC 线程长期占满 CPU，表现为卡顿、耗电、ANR 风险上升。
2. **机理链条**：
   ```text
   堆使用率接近上限
     → 每次分配都触发 GC
     → GC 扫描后发现大部分对象仍存活（说明是"缓存堆积"不是"垃圾过多"）
     → 回收量极小 → 堆使用率几乎不降
     → 很快又触发下一次 GC → 恶性循环
   ```
3. **常见根因**：缓存无上限；内存泄漏；大对象频繁分配；无界集合。
4. **识别方法**：
   - Memory Profiler 里 **GC 事件几乎连续**，每次 freed 的 KB 很小；
   - ART GC 日志：`freed 12KB ... footprint 45MB/56MB` 且事件密集；
   - `Debug.getRuntimeStats()["gc.count"]` 增速异常；
   - **PSS 平稳但 GC 频繁**。
5. **治理**：
   - 缓存设上限（`LruCache`）；
   - 消除泄漏；
   - 对象复用（Bitmap 池、`StringBuilder` 复用）；
   - 大数据分片/流式；
   - `onTrimMemory` 动态缩容；
   - 极端场景：把大列表页放独立进程。
6. **面试话术**："**抖动的判据是'GC 频繁但回收量小'——这说明问题不是垃圾多，而是活对象多，属于'缓存失控'或'泄漏'，单纯调大堆只会更糟。**"

**读者问：LruCache 的大小怎么定？淘汰时需要 recycle Bitmap 吗？**

**AI答：**

1. **大小经验公式**：`maxSize = Runtime.getRuntime().maxMemory() / 1024 / 8`（**字节为单位的缓存则用 /8**）。理由：Java 堆通常 192~512MB，1/8 留给图片缓存，其余留给业务对象。低端机建议 1/16。
2. **`sizeOf()` 要与 `maxSize` 单位一致**：用字节就返回字节，用条目数就返回条目数。**混用是最常见的错误**。
3. **淘汰时不要 `recycle()`**：
   - 淘汰的 Bitmap **可能仍被正在绘制的 Canvas / Drawable 引用**；
   - `recycle()` 后再绘制会抛 **"Canvas: trying to use a recycled bitmap"**；
   - **Android 8.0+ 推荐不手动 recycle**，交给 GC + `NativeAllocationRegistry`；
   - 正确做法：`entryRemoved` 里**什么都不做**。
4. **另外**：如果确实要提前释放 native 内存，可以调 `bitmap.setPremultiplied` 之类的无用操作——**更实际的是用 `BitmapFactory.Options.inMutable` 控制**，或**在确定无引用时（比如页面销毁后）**再 recycle。
5. **面试话术**："**LruCache 的淘汰是'逻辑释放'不是'物理释放'。8.0 之后 Bitmap 在 native heap，GC 不会立刻回收，但只要没有强引用，最终一定会被 `NativeAllocationRegistry` 回收。手动 recycle 反而容易引入崩溃。**"

**读者问：WebP、AVIF、PNG、JPEG 怎么选？转换应该在什么时候做？**

**AI答：**

1. | 格式 | 选型场景 |
   | --- | --- |
   | **PNG** | 需要**无损**、需要**透明**、纯色/文字/截图/渐变 |
   | **JPEG** | 照片、不需要透明（兼容性最好） |
   | **WebP** | **Android 首选**：有损照片 + 透明图标都能用，体积约为 JPEG 的 25%~35%；**API 18+ 全支持** |
   | **AVIF** | 追求极限体积，**Android 12+（API 31）系统解码器直接支持**；编码慢，适合构建期离线转换 |
   | **HEIC** | iOS 生态优先；Android 需 `androidx.heif` 库 |
2. **转换时机**：**构建期（离线）**，不要在运行时转换（耗 CPU、耗电、占内存）。
   - AGP 3.0+ 默认对 **PNG 资源自动转 WebP**（minSdk ≥ 18 时）；
   - 也可以用 `cwebp` / `avifenc` 在 CI 里批量转换；
   - 转换脚本示例：`cwebp -q 80 -m 6 input.png -o output.webp`。
3. **注意**：
   - **有损 WebP 会引入 JPEG 类似的伪影**，纯色渐变图建议用 lossless；
   - **透明图必须用 lossless WebP 或保留 PNG**（有损 WebP 的 alpha 也会被有损压缩）；
   - **WebP 解码比 JPEG 慢**（但 GPU 上传更快，整体持平或更优）。
4. **面试话术**："**格式选型的三条线：要不要透明、要不要无损、目标 API 等级。WebP 是 Android 的默认答案；AVIF 是 Android 12+ 的答案；PNG 留给需要无损透明的场景。转换一定放构建期。**"

# 内存管理

## 一句话定义

Android 的内存管理是**多进程 + 多堆 + 内核 LMK** 共同作用的体系：每个进程有 **Java 堆（dalvik/ART heap）、native heap、graphics、mmap** 等多个内存分区，系统用 `ActivityManagerService` 计算每个进程的内存配额（`memoryClass`），用 **LMK（Low Memory Killer Daemon）** 在压力下杀进程。**ART 用 Concurrent Copying GC** 取代了 Dalvik 的 mark-sweep，目标是把 GC 停顿从"不可控的长停顿"降到"亚毫秒级的并发收集"。

## 核心原理

### 1. Android 的内存分区（**必须分清**）

```text
进程内存（PSS 视角）
┌────────────────────────────────────────────────────────────┐
│ Java Heap (dalvik heap / ART managed heap)                  │
│   ├─ Java 对象、数组                                      │
│   ├─ Bitmap 像素数据  ← Android 8.0 之前在这里！            │
│   └─ 配额：memoryClass / largeMemoryClass                 │
├────────────────────────────────────────────────────────────┤
│ Native Heap                                               │
│   ├─ Bitmap 像素数据  ← Android 8.0 之后在这里              │
│   ├─ Skia/OpenGL 缓冲、so 库的 malloc                       │
│   ├─ ART 自身（Runtime、CompiledCode、GC 辅助结构）          │
│   └─ 无独立配额，但计入进程总 RSS                         │
├────────────────────────────────────────────────────────────┤
│ Graphics                                                 │
│   ├─ GPU 纹理、SurfaceFlinger 缓冲                          │
│   └─ 与设备 GPU 内存规格相关                               │
├────────────────────────────────────────────────────────────┤
│ mmap (Mapped)                                            │
│   ├─ 映射的 .so 文件、.jar/.apk（dexopt 产物）               │
│   ├─ 共享内存（Binder、Ashmem/Memfd）                       │
│   └─ 文件映射页：文件在内存中的缓存（可被回收）              │
├────────────────────────────────────────────────────────────┤
│ Other / Stack / Code                                     │
└────────────────────────────────────────────────────────────┘
```

| 分区 | 内容 | 配额 | 回收方式 |
| --- | --- | --- | --- |
| **Dalvik/ART Heap** | Java 对象、数组、（8.0 前）Bitmap 像素 | `memoryClass`（默认 192MB/256MB/512MB 视设备） | **GC**（CC GC） |
| **Native Heap** | Bitmap 像素（8.0+）、so 的 malloc、Skia | 无独立配额，计入进程总内存 | **`malloc` 的 free + native GC 触发**（`Bitmap.recycle()` 或内存压力下由 `NativeAllocationRegistry` 跟踪回收） |
| **Graphics** | GPU 纹理 | 与 GPU 规格相关 | 由系统与 GPU 驱动管理 |
| **mmap** | so、dex、共享内存、文件缓存 | 计入 RSS 但可回收 | 页面回收（文件映射） |

> [!warning] **Android 8.0 的 Bitmap 内存迁移（高频考点）**
> - **7.1 及之前**：Bitmap 像素数据在 **Dalvik heap**，占用 dalvik 配额，且 GC 需要额外做 native 引用管理 → 容易 OOM，GC 也慢。
> - **8.0 起**：像素数据移到 **native heap**，用 `Bitmap.getByteCount()` 仍然返回同样的值，但：
>   - **不再占用 dalvik 配额**（`heapAllocatedSize` 变小）；
>   - **GC 不再自动回收 native 内存**，需要显式 `recycle()` 或依赖 `NativeAllocationRegistry` 的阈值触发；
>   - 因此 **`Bitmap.recycle()` 的必要性上升了**，但**在绘制后 recycle 仍会 crash**（"Canvas: trying to use a recycled bitmap"），所以正确做法是**池化复用**。

### 2. ART vs Dalvik（**核心对比题**）

| 维度 | **Dalvik（Android 4.4 前）** | **ART（Android 5.0+）** |
| --- | --- | --- |
| **字节码格式** | DEX（Dalvik EXecutable） | DEX（V5.0 引入 ODEX，V7.0 后基本统一 DEX） |
| **编译方式** | **JIT（Just-In-Time）**：解释执行 + 热点 JIT | **AOT（Ahead-Of-Time）** + **JIT** + **解释器** 三级 |
| **编译时机** | 运行时热点方法 | 安装时 `dex2oat` 全量预编译（AOT）→ 运行时 JIT 补充 → 解释器兜底 |
| **产物** | `odex`（可选） | `oat`/`vdex`（含 DEX + 机器码） |
| **GC 算法** | **Mark-Sweep**（非分代，全堆扫描，停顿长） | **Concurrent Copying GC（CC GC）**，**分代 + 并发复制 + 大对象空间** |
| **GC 停顿** | **数百 ms ~ 秒级** | **亚毫秒级**（并发 + 增量），且**几乎没有 stop-the-world** |
| **方法内联** | 有限 | 运行时内联 + **编译期内联（AOT）** |
| **堆大小** | 固定 `-Xms`/`-Xmx`，增长困难 | **可增长**（`dalvik.vm.heapgrowthlimit`），large heap 可申请更多 |
| **JIT 编译器** | **Dalvik JIT（快，代码质量一般）** | **ART JIT（慢但代码质量高，类似 C2）** + **dex2oat 编译器**（AOT） |
| **启动速度** | 快（无需安装期编译） | **首次安装后首次启动慢**（需要 dex2oat），之后快 |
| **多核支持** | 基本单核 | **完全多线程**，JIT 可以多线程编译 |

#### 2.1 ART 的三级执行模型（**必背**）

```text
┌─────────────────────────────────────────────────────────┐
│  1. 解释执行 (Interpreter)                                │
│     - 所有方法先以解释方式执行，保证正确性                 │
│     - 冷启动时大量方法处于此状态                            │
│     ↓ 热点检测（解释执行计数达到阈值）                      │
│  2. JIT 编译 (Just-In-Time)                              │
│     - 运行时编译热点方法为机器码                            │
│     - ART 的 JIT 编译质量高（接近 C2），但编译本身耗时      │
│     ↓ 设备闲置 / 后台 / 充电时                             │
│  3. AOT 编译 (Ahead-Of-Time) — dex2oat                  │
│     - 安装时（PackageManagerService）执行 dex2oat          │
│     - 输出 .oat 文件，包含 DEX + 机器码 + 校验信息          │
│     - 这是"安装慢、运行快"的根源                           │
└─────────────────────────────────────────────────────────┘
```

**`dex2oat` 的关键参数**：

| 参数 | 含义 | 影响的场景 |
| --- | --- | --- |
| `--compiler-filter=everything` | 全量编译所有方法 | 默认（`speed` profile） |
| `--profile=xxx.prof` | **按 profile 编译**（只编译热点方法） | **Baseline Profile** 的核心机制 |
| `--quick-compile` | 快速编译（较少优化） | **启动关键路径专用**，加快安装 |
| `--dexopt=none` | 不编译，只保留 DEX | `adb shell cmd package compile --reset` 后 |
| `--inline-threads` / `--compiler-jobs` | 并行编译 | 加快安装速度 |

**Baseline Profile 的原理**（面试高频）：

```text
Baseline Profile 文件（baseline-prof.txt）
  ↓ 安装时
dex2oat --profile=baseline-prof.txt --quick-compile
  ↓ 产物
oat 文件包含：
  ① 启动路径上方法的机器码（跳过 JIT 等待）
  ② 这些方法的校验信息（运行时 dex 校验更快）
  ③ class 初始化信息预计算
```

**收益来源**：
- **跳过解释执行 + 跳过 JIT 编译等待**（方法第一次调用就是本地代码）；
- **预计算 class 初始化状态**（`Class` 静态字段的默认值与 `<clinit>` 顺序提前算好）；
- **减少 dex 校验时间**（oat 里已包含校验信息）。

详见 [[../性能优化专项/启动优化]]。

### 3. ART 的 GC：Concurrent Copying GC（**核心原理**）

#### 3.1 三种 GC 算法对比

| 算法 | 原理 | 优点 | 缺点 |
| --- | --- | --- | --- |
| **标记-清除（Mark-Sweep）** | 标记可达对象 → 清除不可达 | 实现简单，**无需移动对象** | **产生内存碎片**；**需要扫描整个堆**；**STW 时间长**（Dalvik 用的就是这个） |
| **复制（Copying / Semispace）** | 把存活对象复制到另一块空间，原区整体回收 | **无碎片**；分配极快（**bump pointer**）；只需扫描存活对象 | **需要双倍空间**；**存活率高时复制成本大** |
| **分代（Generational）** | 按年龄分代，新生代频繁回收、老生代很少 | **大部分对象朝生夕死**，新生代回收极快 | 需要处理跨代引用（写屏障 / remembered set） |

#### 3.2 CC GC 的设计（**面试加分项**）

ART 的 CC GC 是 **"并发复制 + 分代 + 大对象空间"** 的组合：

```text
ART 堆空间布局
┌──────────────────────────────────────────────────────────┐
│  Space A (from-space)   ┌──────────────────────────────┐ │
│  ┌────────────────────┐ │  Space B (to-space)           │ │
│  │  Young Generation  │ │  ┌────────────────────────┐  │ │
│  │  (新生代)           │ │  │  Young Generation      │  │ │
│  │  - 复制代价低        │ │  │  (存活对象复制到这里)    │  │ │
│  │  - Eden/Survivor    │ │  └────────────────────────┘  │ │
│  └────────────────────┘ │                              │ │
│  ┌────────────────────┐ │  ┌────────────────────────┐  │ │
│  │  Large Object Space │ │  │  Large Object Space    │  │ │
│  │  (LOS, 大对象)      │ │  │  (> 12KB 的数组)       │  │ │
│  └────────────────────┘ │  └────────────────────────┘  │ │
│                         └──────────────────────────────┘ │
│  ┌──────────────────────────────────────────────────────┐ │
│  │  Non-moving space (CardTable, 线程本地分配区等)         │ │
│  └──────────────────────────────────────────────────────┘ │
└──────────────────────────────────────────────────────────┘
```

**关键机制**：

1. **并发复制（Concurrent Copying）**：
   - GC 的**标记与复制阶段与业务线程并发执行**（业务线程被挂起的时间极短）；
   - 业务线程在 GC 期间继续分配内存（分配到 **from-space**）；
   - GC 线程扫描 **from-space**，把存活对象**复制到 to-space**；
   - 复制完成后**交换两个 space 的角色**（`Flip`），from-space 被整体回收。

2. **CardTable（写屏障）**：
   - 从老生代指向新生代的引用（跨代引用）会**增加复制复杂度**（新生代复制后，老生代的引用指向会失效）；
   - ART 用 **CardTable + 写屏障（Write Barrier）** 记录"哪些老生代对象引用了新生代对象"，GC 时只扫描这些"脏卡片"区域；
   - 写屏障**有性能成本**（每次引用赋值都要检查），这是 ART GC 的主要 overhead 之一。

3. **线程本地分配区（Thread Local Allocation - TLAB）**：
   - 每个线程有自己的分配缓冲，避免分配时的锁竞争；
   - 这是 ART 分配速度快的原因。

4. **Large Object Space（LOS）**：
   - **大于 12KB（`kLargeObjectSize`）的数组**单独放在 LOS；
   - LOS 使用**非移动（non-moving）**策略——因为移动大数组的复制成本太高；
   - **面试点**：**大数组（如 `byte[100_000]`、`String` 背后的 char 数组）不会导致"复制风暴"**，因为它们在 LOS 里原地回收；
   - 但 LOS 的分配容易**导致空间浪费**（大数组申请时会做对齐，可能产生碎片）。

5. **Rosalloc（Region-based Allocator）**：
   - ART 从 Android 8.0（Oreo）开始引入 **Rosalloc** 替换 `dlmalloc`；
   - 按 **region（1MB 粒度）** 管理内存，每个 region 属于一个 size class；
   - **小对象分配极快**（region 内 bump pointer），**大对象用 mmap**；
   - 好处：内存使用率更高（减少碎片）、分配/释放更快。

#### 3.3 ART 的 GC 触发与日志

```text
GC 日志格式（Android 11+）
Explicit concurrent copying GC freed 1234KB AllocSpace bytes, 45% growth, footprint 45MB/56MB, 12MB/16MB, trim 5MB, los 10MB
```

| 字段 | 含义 |
| --- | --- |
| `Explicit` | 显式 GC（`System.gc()` 或 VMDebug） |
| `concurrent copying GC` | 使用的 GC 算法 |
| `freed XXXKB` | 本次回收释放的内存 |
| `XX% growth` | 相比上次 GC 的堆增长百分比 |
| `footprint A/B` | 堆占用 / 堆上限 |
| `trim` | trim 掉的内存 |
| `los` | 大对象空间占用 |

**关键指标**："**GC 频率与 `footprint` 接近上限的次数是内存问题的先行指标。**"

### 4. 内存限制与内存等级（**`memoryClass` / `onTrimMemory`**）

#### 4.1 内存配额

```java
// ActivityManager
int memoryClass = ActivityManager.getMemoryClass();          // 普通应用，如 192/256/512
int largeMemoryClass = ActivityManager.getLargeMemoryClass();  // 申请了 largeHeap 后的值

// manifest 中申请 large heap
<application android:largeHeap="true" />
```

| 设备档位 | 典型 `memoryClass` |
| --- | --- |
| 低端（< 2GB RAM） | 96MB ~ 192MB |
| 中端（2~4GB） | 192MB ~ 256MB |
| 高端（> 4GB） | 256MB ~ 512MB |

**`largeHeap` 的真相**：
- 申请后 `memoryClass` 会变成 `largeMemoryClass`（通常更大，如 512MB → 768MB）；
- **但它不是"无限制"**——只是**提高了 Java 堆的上限**，native 内存仍然受限；
- **副作用**：
  - **GC 更慢**（堆越大，扫描/复制越多）；
  - **系统杀进程的优先级降低**（因为进程"占用"更多，系统更不愿意回收它）——但当系统整体内存紧张时，**大堆进程反而更容易成为 OOM killer 的目标**；
  - **设备整体的内存压力会更大**（更多进程存活 → 更容易触发全局 LMK）。
- **面试话术**："**`largeHeap` 是把双刃剑：它解决单进程 OOM，但会加剧系统级内存压力，让 GC 停顿变长。正确的做法永远是先优化内存占用，而不是靠 `largeHeap` 兜底。**"

#### 4.2 `onTrimMemory` 与 `onLowMemory`

```java
public class MyApplication : Application() {
    @Override
    public void onTrimMemory(int level) {
        super.onTrimMemory(level);
        switch (level) {
            case TRIM_MEMORY_RUNNING_LOW:          // 5: 系统开始杀后台进程
                // 释放缓存，保留核心数据
                break
            case TRIM_MEMORY_RUNNING_CRITICAL:     // 15: 系统即将杀本进程
                // 释放一切可释放的
                break
            case TRIM_MEMORY_UI_HIDDEN:            // 20: UI 不可见了（onTrimMemory 的通用入口）
                // 释放 UI 相关资源
                break
            case TRIM_MEMORY_BACKGROUND:           // 40: 进程被放到后台，且已被缓存
                // 释放所有缓存
                break
            case TRIM_MEMORY_MODERATE:             // 60: 内存紧张
                break
            case TRIM_MEMORY_COMPLETE:             // 80: 进程即将被杀死
                break
            case TRIM_MEMORY_RUNNING_LOW:          // 同上
                break
        }
    }

    @Override
    public void onLowMemory() {
        super.onLowMemory()
        // 旧 API，等价于 TRIM_MEMORY_COMPLETE
    }
}
```

**`onTrimMemory` 级别表（Android 14 后的 API）**：

| 常量 | 值 | 触发条件 | 应对策略 |
| --- | --- | --- | --- |
| `TRIM_MEMORY_UI_HIDDEN` | 20 | UI 不可见 | 释放 UI 资源（图片缓存、临时数据） |
| `TRIM_MEMORY_RUNNING_MODERATE` | 5 | 系统开始回收后台进程 | 适度释放缓存 |
| `TRIM_MEMORY_RUNNING_LOW` | 10 | 系统回收更激进 | 释放大部分缓存 |
| `TRIM_MEMORY_RUNNING_CRITICAL` | 15 | 即将杀本进程 | 释放全部可释放资源 |
| `TRIM_MEMORY_BACKGROUND` | 40 | 后台且已被缓存 | 清空所有缓存 |
| `TRIM_MEMORY_MODERATE` | 60 | 后台，内存紧张 | 清空缓存 |
| `TRIM_MEMORY_COMPLETE` | 80 | 进程即将被杀 | 清空一切 |

> **注意 API 34 的变化**：Android 14 引入 `TRIM_MEMORY_UI_HIDDEN` 的新语义，并新增了 `onTrimMemory` 的 `TRIM_MEMORY_BACKGROUND` 等级别的区分调整。实际项目按"UI_HIDDEN / RUNNING_LOW / COMPLETE"三档处理即可。

### 5. LMK（Low Memory Killer Daemon）

```text
┌───────────────────────────────────────────────────────────┐
│                     system_server                          │
│  ActivityManagerService → ProcessList                     │
│    ├─ 维护所有进程的 LRU 顺序（oom_score_adj / adj）        │
│    └─ 内存压力时调用 killBackgroundProcesses()             │
└───────────────────────────────────────────────────────────┘
              │  lmkd (独立进程 /init 启动)
              ▼
┌───────────────────────────────────────────────────────────┐
│  lmkd (/dev/kmem)                                          │
│   1. 周期性读取内核的内存信息                              │
│      (MemAvailable, SwapFree, Zram)                       │
│   2. 计算 minfree / 压力等级                               │
│   3. 达到阈值 → 按 oom_score 排序杀进程                    │
│      （kill 的顺序由 oom_score_adj 决定）                    │
│   4. 回收 ZRAM 中的压缩页面                                │
└───────────────────────────────────────────────────────────┘
```

**`oom_score_adj`（进程的"被杀优先级"）**：

| adj 值 | 进程类型 | 含义 |
| --- | --- | --- |
| `-1000` | 系统前台进程 | **永不杀** |
| `0` | 前台应用 | 最后才被杀 |
| `100~200` | 可见应用（`VISIBLE`） | 较晚被杀 |
| `200~500` | 服务进程（`SERVICE`） | 较早被杀 |
| `900` | 缓存/后台（`CACHED`） | **最先被杀** |
| `1000+` | 空进程 | 立即被杀 |

**关键点**：
- **应用无法直接控制 `oom_score_adj`**（`android:process` + `android:persistent` 只能有限影响）；
- **保留后台进程的正确方式**：
  - **前台服务（`FOREGROUND_SERVICE`）**：系统会尽量保留，但需要常驻通知（Android 14 起还有类型限制与 `FOREGROUND_SERVICE_TYPE` 声明）；
  - **`WorkManager` / `JobScheduler`**：系统按 Doze/配额调度，反而**更不容易被杀**；
  - **不要依赖常驻 Service 保活**（见 [[电源管理]]）。
- **`lmkd` 的调整**（系统侧）：`/sys/module/lmkd/parameters/minfree`。

### 6. 内存抖动（Memory Thrashing）（**高频概念题**）

**定义**：系统物理内存充足，但**某个进程频繁 GC 且每次回收很少**，导致 CPU 被 GC 占满、界面卡顿、耗电增加。

```text
内存抖动的形成机制：

  堆空间接近上限（比如 memoryClass = 192MB，已用 180MB）
        │
        ▼
  分配新对象 → 触发 GC
        │
        ▼
  GC 扫描整个堆 → 发现大部分对象仍存活（缓存占了大头）
        │
        ▼
  只回收了 1MB（回收量 / 堆大小 = 很低）
        │
        ▼
  几毫秒后又分配 → 再次触发 GC
        │
        ▼
  ┌──────────────────────────────┐
  │  GC 频率极高 + 每次回收量极小  │
  │  = 内存抖动（Thrashing）       │
  └──────────────────────────────────┘
        │
        ▼
  主线程/GC 线程抢占 CPU → 掉帧、卡顿、耗电
```

**成因**：

1. **缓存类对象堆积**：Bitmap 缓存、List 缓存、JSON 缓存无上限地增长；
2. **对象生命周期过长**：本该释放的对象被长生命周期引用持有（内存泄漏）；
3. **大对象频繁创建**：每次都分配大数组 → 快速逼近上限；
4. **错误的缓存策略**：用 `HashMap` 当无限缓存，**没有 LRU 与容量上限**；
5. **Fragment/Context 泄漏**（经典场景）：泄漏的 Activity 使整个 View 树常驻。

**识别方法**：
- Memory Profiler 看 **GC 频率**（每次分配都触发 GC）；
- 看 **`AllocSpace` 与 `FreeSpace` 的差值很小**（每次回收很少）；
- 看 `footprint` 是否长期贴近上限；
- ART 的 GC 日志中 `freed` 的 KB 数很小而 `GC` 频繁出现。

**解决**：
1. **给所有缓存加上限**（`LruCache`）；
2. **在 `onTrimMemory` 中分级清理**；
3. **消除泄漏**（见 [[../性能优化专项/内存优化]]）；
4. **减少大对象分配**（复用对象、流式处理而不是一次性加载全部）；
5. **降低 `memoryClass` 压力**：拆进程（大列表页放独立进程）。

### 7. 内存泄漏的分类（**必背，高频**）

**内存泄漏的定义**：**不再被使用的对象仍然被引用，无法被 GC 回收**。

| # | 类型 | 典型写法 | 成因 | 排查特征 |
| --- | --- | --- | --- | --- |
| **1** | **静态引用** | `static Activity mActivity;` | 静态字段持有 Activity，生命周期长于 Activity | LeakCanary 显示 `GC Root: static field` |
| **2** | **单例持有 Context** | `object Single { var ctx: Context }` | 单例持有 Activity Context（应持 Application） | `GC Root: static field` |
| **3** | **非静态内部类 / 匿名内部类** | `btn.setOnClickListener(object : View.OnClickListener { ... })` | 内部类隐含持有外部类（Activity）引用，生命周期与回调绑定 | `GC Root: inner class` |
| **4** | **Handler 延迟消息** | `handler.postDelayed(runnable, 60_000)` | 消息在队列里被 Delay 持有 60 秒 → 持有 Activity | `GC Root: MessageQueue` |
| **5** | **ThreadLocal 未 remove** | `threadLocal.set(activity)` | 线程池的线程长期存活，`ThreadLocalMap` 持有 Entry → Value → Activity | `GC Root: ThreadLocal` |
| **6** | **注册未反注册** | `registerReceiver` / `registerListener` / `addOnGlobalLayoutListener` / `ContentObserver` 未注销 | 系统/长生命周期对象持有回调 → 持有 Activity | `GC Root: xxx` |
| **7** | **无限增长的集合** | `list.add(...)` 永不清除 | 集合持有大量对象 | `GC Root: static field`（集合本身静态） |
| **8** | **协程作用域未取消** | `GlobalScope.launch { activity.xxx }` | 协程持有 Activity 直到结束 | `GC Root: coroutine` |
| **9** | **Lambda 捕获** | Kotlin 中 lambda 捕获外部变量时生成 `Function1` 对象持有引用 | 长期存活的回调持有 Activity | `GC Root: lambda` |
| **10** | **WebView 未销毁** | `webView.destroy()` 未调用 | WebView 内部持有 Activity | `GC Root: WebView` |
| **11** | **InputMethodManager 的 `Cursor`** | 未 `close()` | native 侧持有 | `GC Root: Cursor` |
| **12** | **动画未取消** | `ValueAnimator` 未 `cancel()`；`ObjectAnimator` 持有目标对象 | 动画运行在 Choreographer 回调链上 | `GC Root: Animator` |

**排查时的"GC Root"对照表（LeakCanary 关键）**：

| LeakCanary 显示的 GC Root | 典型泄漏源 |
| --- | --- |
| `static field` | 静态变量、单例持有的 Context |
| `inner class` | 非静态内部类、匿名内部类 |
| `MessageQueue` | Handler 延迟消息、Handler 持有 Activity |
| `ThreadLocal` | 线程池 + ThreadLocal |
| `Local Broadcast Receiver` | 未注销的 `LocalBroadcastManager` 回调 |
| `View` | 未移除的 OnGlobalLayoutListener、Animator |
| `InputManager` / `Insets` | 未取消的键盘监听 |

### 8. OOM 的分类与处理

```text
OOM 的三种形态：
1. java.lang.OutOfMemoryError: Failed to allocate a 12582948 byte allocation
   → Java 堆不够（dalvik/ART heap 超限）
2. java.lang.OutOfMemoryError: Failed to allocate a 12582948 byte allocation
   with 4194304 free bytes and 200MB until OOM, target footprint 250MB,
   growth limit 268MB
   → Java 堆不够（ART 的详细日志，含 growth limit）
3. Out of memory (native) / signal 11 (SIGSEGV) / SIGABRT
   → native 内存不足（Bitmap、so、Skia），进程被 native 层 kill
```

**处理策略（分层）**：

```text
第 1 层：预防（最重要）
  ├─ 采样加载 Bitmap（inSampleSize）
  ├─ LruCache 限制缓存大小
  ├─ 消除所有泄漏
  └─ 大列表分页/分片加载

第 2 层：降级（onTrimMemory）
  ├─ UI_HIDDEN：清图片缓存
  ├─ RUNNING_LOW：清二级缓存
  └─ COMPLETE：清全部缓存 + 停止非关键任务

第 3 层：兜底（真的 OOM 了）
  ├─ try-catch OOM → 释放缓存 → 重试一次
  ├─ 崩溃上报（区分 Java OOM 与 native OOM）
  └─ 提示用户"内存不足，请关闭其他应用"

第 4 层：架构级
  ├─ 大列表页放独立进程（内存隔离，进程被杀不影响主进程）
  └─ 用 native 大内存（mmap 文件映射）绕过 Java 堆限制
```

### 1. 内存分级监控与降级（`onTrimMemory`）

```kotlin
class MemoryGovernor(private val app: Application) {

    /** 三级缓存：内存越小，保留的越少 */
    private val imageCache = LruCache<String, Bitmap>(maxSize = 20 * 1024 * 1024)
    private val dataCache = LruCache<String, Any>(maxSize = 10 * 1024 * 1024)

    fun install() {
        app.registerActivityLifecycleCallbacks(object : Application.ActivityLifecycleCallbacks {
            override fun onActivityCreated(a: Activity, b: Bundle?) {}
            override fun onActivityStarted(a: Activity) {}
            override fun onActivityResumed(a: Activity) {}
            override fun onActivityPaused(a: Activity) {}
            override fun onActivityStopped(a: Activity) {}
            override fun onActivitySaveInstanceState(a: Activity, b: Bundle) {}
            override fun onActivityDestroyed(a: Activity) {}
        })
    }

    /** 在 Application.onTrimMemory 中调用 */
    fun onTrim(level: Int) {
        when {
            level >= TRIM_MEMORY_COMPLETE -> {
                // 即将被杀：清空一切
                imageCache.evictAll()
                dataCache.evictAll()
            }
            level >= TRIM_MEMORY_MODERATE || level >= TRIM_MEMORY_RUNNING_LOW -> {
                // 内存紧张：清掉一半
                imageCache.trimToSize(imageCache.size() / 2)
            }
            level >= TRIM_MEMORY_UI_HIDDEN -> {
                // UI 不可见：清图片缓存
                imageCache.evictAll()
            }
            level >= TRIM_MEMORY_BACKGROUND -> {
                dataCache.evictAll()
            }
        }
    }

    /** 主动回收缓存（配合 LeakCanary 的 AppWatcher） */
    fun clearForLeakDetection() {
        imageCache.evictAll()
        dataCache.evictAll()
    }
}
```

### 3. `ThreadLocal` 泄漏的正确处理

```kotlin
/**
 * ✅ ThreadLocal 泄漏的根因：线程池的线程长期存活，
 * ThreadLocalMap 的 Entry 强引用 Value。
 * 必须在 finally 中 remove()。

class RequestContext {
    companion object {
        private val current = ThreadLocal<RequestContext?>()

        fun begin(): RequestContext {
            val ctx = RequestContext()
            current.set(ctx)
            return ctx
        }

        fun current(): RequestContext? = current.get()

        fun end() {
            // ✅ 关键：必须清理，否则线程复用时会串数据 + 泄漏
            current.remove()
        }
    }

    var userId: String? = null
    var traceId: String? = null
}

    try {
        doWork()
    } finally {
        RequestContext.end()   // ✅
    }
```

### 4. 内存抖动的检测（**线上自监控**）

```kotlin
class MemoryThrashingDetector(private val context: Context) {

    private var lastGcCount = 0
    private var lastTime = 0L
    private val freeBytes = AtomicLong(0)

    /** Android 8.0+ 可以用 Debug.getMemoryInfo */
    fun sample() {
        val info = Debug.MemoryInfo()
        Debug.getMemoryInfo(info)
        val total = info.totalPss * 1024L
        val dalvik = info.dalvikPss * 1024L
        val native = info.nativePss * 1024L
        val heap = Runtime.getRuntime()
        val used = heap.totalMemory() - heap.freeMemory()

        // 判定：堆使用率 > 85% 且持续
        val usage = used.toDouble() / heap.maxMemory()
        if (usage > 0.85) {
            // 连续采样，检测是否抖动
            if (lastTime > 0 && SystemClock.uptimeMillis() - lastTime < 1000) {
                freeBytes.addAndGet(used)
            }
            lastTime = SystemClock.uptimeMillis()
        }
    }

    /** 更准的方案：接入 Debug.getRuntimeStats() 统计 GC 次数 */
    fun gcCount(): Long {
        val stats = Debug.getRuntimeStats()
        return stats["gc.count"].toLongOrNull() ?: 0
    }
}
```

### 5. 大对象与大数组的处理（**LOS 意识**）

```kotlin
object BigDataLoader {

    /**
     * ✅ 避免一次性加载大数组到内存。
     * 大于 12KB 的数组会进入 ART 的 Large Object Space（非移动策略），
     * 频繁分配/回收会加剧空间浪费与 GC 压力。
     */
    fun loadInChunks(file: File, chunkSize: Int = 64 * 1024): Sequence<ByteArray> = sequence {
        file.inputStream().buffered().use { input ->
            val buffer = ByteArray(chunkSize)
            while (true) {
                val read = input.read(buffer)
                if (read <= 0) break
                // 注意：每次 yield 出去的 buffer 会被复用，调用方需复制
                yield(buffer.copyOf(read))
            }
        }
    }

    /** ✅ 用 mmap 把大文件映射到内存，不占用 Java 堆 */
    fun mapFile(file: File): MappedByteBuffer? = try {
        FileChannel.open(file.toPath(), StandardOpenOption.READ).use { channel ->
            channel.map(READ_ONLY, 0, channel.size())
        }
    } catch (e: IOException) {
        null
    }
}
```

## 常见问题 / 面试要点

**读者问：Android 的内存分哪几块？各自的配额和回收方式是什么？**

**AI答：**

1. **Java Heap（dalvik / ART managed heap）**：Java 对象、数组。配额是 `ActivityManager.getMemoryClass()`（典型 192MB / 256MB / 512MB）。回收靠 **GC**。
2. **Native Heap**：**Android 8.0 起 Bitmap 像素数据在这里**（之前在 Java 堆）、so 库的 `malloc`、Skia 缓冲、ART Runtime 自身。没有独立配额，但计入进程 RSS。
3. **Graphics**：GPU 纹理与 SurfaceFlinger 缓冲，由 GPU 驱动与系统管理。
4. **mmap**：映射的 `.so`、`.oat`/`.dex`、Binder 共享内存、文件页缓存。可被系统回收。
5. **关键变化**：**Android 8.0 把 Bitmap 像素从 Java 堆搬到 native 堆**，好处是不占 dalvik 配额、GC 更快；代价是**GC 不再自动回收 native 内存**，需要 `recycle()` 或依赖内存压力回收。
6. **面试话术**："**记忆口诀：Java 堆有配额、GC 管；native 堆没配额、malloc 管；graphics 是 GPU 的；mmap 是文件的。**"

---

**读者问：ART 的 GC 和 Dalvik 有什么区别？为什么 ART 的 GC 停顿更短？**

**AI答：**

| 维度 | Dalvik | ART |
| --- | --- | --- |
| 算法 | **Mark-Sweep**（全堆扫描，STW 长，数百 ms~秒级） | **Concurrent Copying GC**（并发 + 复制 + 分代 + LOS） |
| 停顿 | 长（停止业务线程） | **亚毫秒级**，业务线程基本不感知 |
| 堆 | 固定大小，不易增长 | **可增长**，`largeHeap` 可进一步提升 |
| 分代 | 无 | **有**（新生代用复制，老生代用标记-整理） |
| 大对象 | 与普通对象混在一起 | **Large Object Space（LOS）**，> 12KB 单独管理，非移动策略 |
| 分配器 | `dlmalloc` | **Rosalloc**（region + size class，Android 8.0+） |

**ART 停顿更短的四个原因**：
1. **并发标记与复制**：GC 与业务线程并行，只在极短的关键点（root 扫描、space 交换）暂停；
2. **分代**：新生代对象大多朝生夕死，复制时只需复制**少量存活对象**，成本远低于全堆扫描；
3. **CardTable + 写屏障**：只扫描"可能持有新生代引用"的老生代卡片，而不是全堆；
4. **Rosalloc + TLAB**：分配快（bump pointer，无锁），减少因分配触发的 STW。

**加分**："**ART 的 `explicit` GC（比如 `System.gc()`）会触发一次并发 GC 并等待完成，比 Dalvik 的完全 STW 好，但仍应避免在主线程频繁调用。**"

---

**读者问：什么是内存抖动（Memory Thrashing）？怎么发现和解决？**

**AI答：**

1. **定义**：**物理内存充足，但进程频繁 GC 且每次回收量很少**，GC 线程占满 CPU，表现为卡顿、耗电、ANR 风险增加。
2. **成因机制**：堆使用率接近上限 → 分配即触发 GC → GC 扫描后发现**大部分对象仍存活**（说明是"缓存堆积"而不是"垃圾过多"）→ 回收量极小 → 很快又触发下一次 GC → **恶性循环**。
3. **常见根因**：
   - **缓存无上限**（`HashMap` 当缓存、`List` 无限 add）；
   - **内存泄漏**（本该释放的对象被持有 → 堆逼近上限 → GC 回收不了 → 抖动）；
   - **大对象频繁分配**（每次请求都 new 一个大数组）；
   - **Context/Activity 泄漏**（经典场景：Fragment 引用 Activity）。
4. **识别方法**：
   - Memory Profiler 观察 **GC 事件频率**（几乎每次分配都 GC）；
   - ART GC 日志里 `freed` 的 KB 数**很小**，但 GC 事件密集；
   - `footprint` 长期贴近上限；
   - **LeakCanary** 报警。
5. **解决**：
   - **给缓存设上限**（`LruCache`）；
   - **消除泄漏**；
   - **对象复用**（`StringBuilder` 复用、Bitmap 池）；
   - **`onTrimMemory` 分级清理**；
   - **大数据分片/流式处理**；
   - **极端场景：把大列表页放到独立进程**（进程被 OOM 杀死也不影响主进程）。

---

**读者问：内存泄漏有哪几种情况？分别怎么产生的？**

**AI答：**

按"持有链"的来源分类（面试要能列 6 种以上并说明**为什么**会持有）：

1. **静态字段持有**：`static Activity`、单例持有 Activity Context。静态字段生命周期 = 进程，Activity 销毁后仍被引用。**修法**：单例只持 `Application`；确需 Activity 时用 `WeakReference`。
2. **非静态内部类 / 匿名内部类**：`object : OnClickListener {}` 隐含持有外部 Activity 的 `this$0`。回调若被长生命周期对象持有（View 树、`Handler`），Activity 就泄漏了。**修法**：抽成静态类 + `WeakReference`，或在 `onDestroy` 里解绑。
3. **Handler 延迟消息**：`postDelayed` 的 Runnable 在 `MessageQueue` 里被持有 N 秒 → 持有 Activity。**修法**：`onDestroy` 里 `removeCallbacksAndMessages(null)`，或用 `Handler(Looper.getMainLooper())` + 弱引用。
4. **ThreadLocal 未清理**：线程池的线程长期存活 → `ThreadLocalMap` 的 Entry 强引用 Value。**修法**：`finally { threadLocal.remove() }`。
5. **注册未反注册**：`registerReceiver`、`registerListener`、`ContentObserver`、`OnGlobalLayoutListener`、`ViewTreeObserver` 未注销。**修法**：`onDestroy` 反注册；能用生命周期感知就用 `Lifecycle` 自动解绑。
6. **协程作用域未取消**：把 Activity 的作用域用成 `GlobalScope`，协程持有 Activity 直到完成。**修法**：用 `lifecycleScope` / `viewModelScope`（自动随生命周期取消）。
7. **无限增长的集合**：静态 `List` / `Map` 持续 add。**修法**：`LruCache` + 上限。
8. **WebView 未 `destroy()`**、**Cursor 未 `close()`**、**Animator 未 `cancel()`**。

**排查抓手**：**LeakCanary 的 "GC Root" 字段**——它直接告诉你"是谁在持有"，是最高效的定位手段。

---

**读者问：怎么排查一个内存泄漏？完整流程是什么？**

**AI答：**

1. **确认是泄漏还是正常高水位**：
   - 重复进入/退出页面 20 次，看 PSS 是否**单调递增**（正常会稳定在某个平台，泄漏会持续上涨）；
   - 这是 LeakCanary 的核心判定逻辑（它通过 `AnalysisResult` 判断"对象在 GC 后仍存活"）。
2. **抓 Heap Dump**：
   - Android Studio → Memory Profiler → `Dump the heap`；
   - 或命令行：`adb shell am dumpheap <pkg> /sdcard/heap.hprof`，然后 `adb pull`；
   - 生产环境：**LeakCanary 自动抓取**（默认 debug 包；release 包需 `LeakCanary` 的 `AppWatcher`）。
3. **分析引用链**：
   - Android Studio 的 Memory Profiler 会自动给出 **"Retained Objects"** 与引用路径；
   - MAT（Memory Analyzer Tool）：`Leak Suspects` 报告 → 逐个看 **Path to GC Roots → exclude weak/soft references**；
   - LeakCanary 用 **Shark** 库（Kotlin 实现的 hprof 解析器）做同样的事，输出更直观的引用链。
4. **定位 GC Root**（**这是关键**）：
   | GC Root | 含义 | 典型修法 |
   | --- | --- | --- |
   | `static field` | 静态变量持有 | 改用 Application / WeakReference |
   | `inner class` | 非静态内部类 | 抽成 static + 弱引用 |
   | `MessageQueue` | Handler 消息 | `removeCallbacksAndMessages` |
   | `ThreadLocal` | 线程本地变量 | `remove()` |
   | `Local Broadcast Receiver` | 未注销的广播回调 | `unregisterReceiver` |
   | `View` | View 监听器/动画 | 移除监听 / `cancel()` 动画 |
5. **修复并验证**：
   - 修复后**重复触发 GC**，确认对象能被回收；
   - **再跑一轮 LeakCanary**，确认无新泄漏；
   - 回归：反复进出页面 50 次，PSS 曲线应保持平稳。

---

**读者问：`onTrimMemory` 有哪些级别？分别怎么响应？**

**AI答：**

| 常量 | 值 | 触发场景 | 响应策略 |
| --- | --- | --- | --- |
| `TRIM_MEMORY_UI_HIDDEN` | 20 | **UI 不可见**（`onStop` 之后） | 释放 UI 相关资源（图片缓存、渲染缓存） |
| `TRIM_MEMORY_RUNNING_MODERATE` | 5 | 系统开始回收**后台**进程，本进程仍在前台 | 适度释放二级缓存 |
| `TRIM_MEMORY_RUNNING_LOW` | 10 | 回收更激进 | 释放大部分缓存 |
| `TRIM_MEMORY_RUNNING_CRITICAL` | 15 | 本进程即将被杀 | 释放一切可释放资源 |
| `TRIM_MEMORY_BACKGROUND` | 40 | 进程在后台且已被缓存 | **清空所有缓存** |
| `TRIM_MEMORY_MODERATE` | 60 | 后台，内存紧张 | 清空缓存 |
| `TRIM_MEMORY_COMPLETE` | 80 | 进程即将被杀 | 清空一切，保存必要状态 |

**要点**：
1. **`onTrimMemory` 不在主线程吗？** —— **在主线程**。所以里面的清理要轻量，大对象的释放应放在后台线程。
2. **`onLowMemory()`** 是老 API，现在基本由 `TRIM_MEMORY_COMPLETE` 取代。
3. **实践建议**：**`UI_HIDDEN` 是最常用的钩子**（页面不可见时清图片缓存）；`RUNNING_LOW` 是紧急信号；`COMPLETE` 是"准备被杀"，此时应把必要状态持久化。
4. **面试话术**："**`onTrimMemory` 是系统给应用的'内存水位通知'。合理的分级响应能显著降低 OOM 概率，但**不能替代**真正的内存优化——它只是'优雅降级'的最后一层保险。**"

---

**读者问：`largeHeap` 有什么作用？有什么风险？**

**AI答：**

1. **作用**：manifest 声明 `android:largeHeap="true"` 后，`ActivityManager.getMemoryClass()` 返回更大的值（对应 `getLargeMemoryClass()`），**Java 堆上限提高**（典型从 192MB → 512MB/768MB）。
2. **不作用的方面**：
   - **native 内存不受此配额直接限制**（Bitmap 8.0 后在 native heap，本来就不受这个限制）；
   - **不会让系统更"手下留情"**，反而**更容易被 LMK 盯上**（进程 RSS 更大 → oom_score 更高）。
3. **风险**：
   - **GC 停顿变长**（堆越大，CC GC 扫描/复制越多）；
   - **系统整体内存压力上升**（更多进程能存活 → 全局更容易触发 LMK，**杀别的进程**）；
   - **低端机上更严重**（物理内存本来就少）。
4. **面试话术**："**`largeHeap` 是'把问题往后推'，不是'解决问题'。正确的顺序是：先优化内存占用（采样、池化、消除泄漏、缓存上限），只有在明确知道自己的峰值需求（比如要处理大图/大列表）且验证过低端机表现后，才考虑 `largeHeap`。**"

---

**读者问：LMK 是怎么决定杀哪个进程的？应用能做什么？**

**AI答：**

1. **LMK（lmkd）的工作**：
   - 独立于 system_server 的守护进程，周期性读取内核内存信息（`MemAvailable`、`SwapFree`、`Zram`）；
   - 内存低于阈值时，按进程的 **`oom_score_adj`**（也叫 `adj`）从高到低排序杀；
   - 同时回收 ZRAM 里的压缩页面来腾空间；
   - 早期版本（`< 4.3`）是 `LowMemoryKiller` 内核模块；`4.3` 后改为用户空间的 `lmkd`。
2. **`oom_score_adj` 分级**（`ProcessList` 维护）：
   - `-1000`：系统前台进程（永不被杀）；
   - `0`：前台应用；
   - `100~200`：可见应用；
   - `200~500`：服务进程；
   - `900`：缓存进程（**最先被杀**）；
   - `1000+`：空进程。
3. **应用能做的**：
   - **前台服务**（带常驻通知）：系统会尽量保住，但 Android 8+ 后后台启动前台服务受限，Android 14 起还需要声明 `foregroundServiceType`；
   - **WorkManager / JobScheduler**：系统调度，反而不会被随意杀；
   - **独立进程承载重任务**：被杀不影响主进程；
   - **不能做的**：试图通过常驻 Service / `AlarmManager` 高频唤醒来"保活"（既不可靠又违规，见 [[电源管理]]）。
4. **加分**："**系统判断杀谁，本质上是判断'这个进程最近有没有给用户带来价值'——前台 > 与用户有交互 > 有服务 > 纯后台。所以产品设计上的'保活'最终都应该落在'给用户价值'上。**"

---

**读者问：ART 为什么要用 Concurrent Copying GC？它是怎么做到"并发"的？**

**AI答：**

1. **要解决的问题**：Dalvik 的 mark-sweep 需要**全堆扫描 + stop-the-world**，GC 停顿可达数百毫秒到秒级，直接导致掉帧和 ANR。
2. **CC GC 的核心思想**：**把"标记"和"复制"都与业务线程并发执行**。
3. **具体机制**：
   - 堆分为 **from-space** 与 **to-space** 两个等大的区域（Rosalloc 时代按 region 管理）；
   - GC 线程扫描 **from-space**，把**存活对象复制到 to-space**；
   - 业务线程在 GC 期间**继续在 from-space 分配新对象**；
   - GC 完成后**交换两个 space**（flip），旧的 from-space 整体回收。
4. **跨代引用怎么处理**：
   - 用 **CardTable + 写屏障**：每次修改老生代对象的引用时，写屏障检查目标是否在新生代，若是则把该老生代对象的 card 标脏；
   - GC 时只需扫描"脏 card"覆盖的区域，而不是整个老生代。
5. **仍需暂停的极短时刻**：
   - **Root 扫描**（栈上、静态变量、JNI 全局引用）；
   - **Space 交换**；
   - 这两个点总共通常在**亚毫秒级**。
6. **大对象（LOS）**：**> 12KB 的数组单独放在 Large Object Space，采用非移动策略**——移动大数组的复制成本太高，所以原地回收。副作用是 LOS 容易产生空间碎片（分配时按页对齐）。
7. **加分**："**CC GC 的精髓是'用空间换时间'——复制比标记-清除贵，但换来的是极短的 STW 和无碎片。移动端内存紧张，所以用 '双 space 轮换' 而不是 '碎片整理' 是更划算的取舍。**"

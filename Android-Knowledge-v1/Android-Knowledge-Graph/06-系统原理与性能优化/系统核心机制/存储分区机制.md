# 存储分区机制

## 一句话定义

Android 的存储机制经历了三个阶段：**"全设备文件系统"（≤ Android 9）→ "分区存储 / Scoped Storage"（Android 10+）→ "细分媒体权限"（Android 13+）**。它的本质是**从"应用拥有文件系统访问权"改成"应用只能访问自己创建的文件 + 通过 MediaStore 访问媒体库"**。理解这一机制的关键不是记 API，而是明白**文件访问的"钥匙"从 `READ_EXTERNAL_STORAGE` 换成了 `MediaStore` + `MediaStore.VOLUME_EXTERNAL_*` URI**。

## 核心原理

### 1. 内部存储 vs 外部存储（**底层差异是根本**）

```text
【内部存储 Internal Storage】
  /data/data/<pkg>/            ← 应用私有目录（App-private）
      ├── files/               ← Context.getFilesDir()
      ├── cache/               ← Context.getCacheDir()
      ├── databases/           ← Context.getDatabasePath()
      ├── shared_prefs/        ← Context.getSharedPreferences()
      ├── no_backup/           ← 备份时排除
      └── lib/                 ← so 库
  物理位置：/data 分区（加密，userdata）
  文件系统：ext4 / f2fs
  访问权限：仅本应用 UID（Linux 文件权限 0700）
  卸载时：随应用一起删除

【外部存储 External Storage】
  /storage/emulated/0/         ← 共享存储（Primary / emulated volume）
      ├── Android/data/<pkg>/  ← 应用在外部的私有目录
      ├── Android/media/<pkg>/
      ├── DCIM/                ← 相机照片
      ├── Pictures/ Movies/ Music/
      └── Download/ Documents/
  物理位置：/storage/emulated 是 "FUSE" 挂载点
            真实数据在 /data/media/<userId> 或 独立的 userdata 分区
  文件系统：FUSE（sdcardfs 的替代）→ 内核 FUSE + sdcard daemon
  访问权限：受 Scoped Storage 严格限制
  卸载时：Android/data/<pkg> 会被删除，其余保留
```

#### 1.1 FUSE 文件系统（**加分项，理解底层**）

```text
【为什么 /sdcard 不是真实分区】
  App 进程
    │  read("/storage/emulated/0/DCIM/a.jpg")
    ▼
  内核 VFS → FUSE mount point（/storage/emulated/0）
    │  把 FUSE 请求转发给 userspace 守护进程
    ▼
  /system/bin/sdcard（或 sdcardfuse / fuse passthrough）
    │  在这里做：
    │    - Scoped Storage 权限检查（这是"分区存储"真正生效的地方！）
    │    - FUSE / sdcardfs 的 inode 映射
    │    - 路径 → MediaStore / FUSE daemon 的转换
    ▼
  /data/media/0/...  （真正的数据）
```

**关键结论**：**分区存储的权限检查并不是在内核 VFS 里做的，而是在 userspace 的 FUSE daemon 里做的**。这就是为什么：
- 用 root 或某些 native 手段仍可能绕过；
- **`ContentResolver` 通过 MediaStore 走的是 Binder 通道**（绕过 FUSE 的路径检查，但受 MediaStore 层的权限控制）；
- 文件路径 API（`File`）与 `ContentResolver`（`Uri`）在权限行为上**不完全一致**。

| 维度 | **内部存储** | **外部存储（共享）** |
| --- | --- | --- |
| 路径 | `/data/data/<pkg>/` | `/storage/emulated/0/`（或 `/sdcard/`） |
| 挂载 | ext4/f2fs（真实分区） | **FUSE**（userspace 守护进程） |
| 权限粒度 | **仅本应用 UID** | **按 Scoped Storage 规则**（应用 + 媒体类型） |
| 备份 | `no_backup` 目录默认排除 | 参与备份（`backup_rules` 控制） |
| 卸载清理 | 全部删除 | 仅 `Android/data/<pkg>` 删除 |
| 直接 `File` 读写 | ✅ 永远允许 | ⚠️ 受限（Scoped Storage 后） |
| `MediaStore` 读写 | ❌ 不适用 | ✅ 推荐路径 |
| 敏感数据 | ✅ 适合（内部） | ❌ 不适合（外部可被其他应用读，Android 10 前） |

### 2. Scoped Storage（分区存储）的引入

#### 2.1 Android 10（API 29）的变化

```text
【Android 10 之前：传统模型（Legacy）】
  App 申请 READ_EXTERNAL_STORAGE / WRITE_EXTERNAL_STORAGE
    → 授予后，可以：
        · 读写整个共享存储（/sdcard 下任意路径）
        · 用 File API 直接操作任意文件
        · 用 ContentResolver 查询 MediaStore（拿到 file:// Uri）
  问题：
    ❌ 一个相册权限就能读全盘文件
    ❌ 卸载后文件残留（Android 9 及以前）
    ❌ 无法追踪文件归属
    ❌ 应用卸载后遗留垃圾文件

【Android 10：Scoped Storage（分区存储）】
  引入 3 个概念：
    ① 应用私有目录（App-specific directory）
       /storage/emulated/0/Android/{data,media,obb}/<pkg>/
       → 无需任何权限即可读写
       → 卸载时自动删除
       → 不进入媒体库，不被其他应用索引

    ② MediaStore 分区
       → 通过 ContentResolver + MediaStore.* URI 访问媒体
       → 写入自己创建的媒体 → 无需权限
       → 读取他人创建的媒体 → 需要 READ_EXTERNAL_STORAGE

    ③ 直接文件路径（raw path）
       → Android 10 仍可写（但 Android 11 收紧）
       → Android 11+ 需要 MANAGE_EXTERNAL_STORAGE 或用 MediaStore
```

#### 2.2 targetSdk 30 前后的差别对比表（**必背**）

| 行为 | **targetSdk ≤ 29** | **targetSdk ≥ 30** |
| --- | --- | --- |
| 读取**自己创建**的媒体 | ✅ 无权限 | ✅ 无权限（通过 MediaStore 或自己的文件） |
| 读取**其他应用创建**的媒体 | 需 `READ_EXTERNAL_STORAGE` | 需 `READ_EXTERNAL_STORAGE` |
| 写入**任意位置**的文件 | 需 `WRITE_EXTERNAL_STORAGE` | **❌ 禁止**（只能写自己的目录或通过 MediaStore 插入） |
| 用 `File` 直接写 `/sdcard/Pictures/x.jpg` | ✅ | ❌（`FileNotFoundException` / `EACCES`） |
| `MediaStore` 插入图片得到 `Uri` | `content://media/...` 或 `file://` | **必须**是 `content://media/...`（不可暴露真实路径） |
| 请求 `MediaStore.getMediaFileId()` 拿 file path | ✅ 可用 | **❌ 不可用**（返回 null / 抛异常） |
| `ContentResolver.takePersistableUriPermission` | 可用 | 可用（**这是访问他人文件的正确方式**） |
| 删除自己创建的媒体 | ✅ | ✅（无需权限） |
| 删除他人创建的媒体 | 需 `WRITE_EXTERNAL_STORAGE` | **❌ 不可**（只能删自己创建的） |
| 访问 `Android/data/<other>/` | 需权限 | **❌ 不可**（Android 11+） |
| 挂载外部存储 | 自动挂载 | **❌ 不可**（`MANAGE_EXTERNAL_STORAGE`） |
| `requestLegacyExternalStorage` | 无意义 | 可在 `targetSdk=29` 时声明 `true` **临时豁免**（Android 10 有效，Android 11 忽略） |

> [!warning] **requestLegacyExternalStorage 的正确用法**
> ```xml
> <!-- 仅在 targetSdk = 29 时生效；Android 11+ 直接忽略 -->
> <application
>     android:requestLegacyExternalStorage="true"
>     android:targetSdkVersion="29">
> ```
> 这是给"从旧版本升级、还没适配分区存储"的应用的**过渡开关**，Android 11 起完全失效。

### 3. 分区存储下的读写方式

#### 3.1 写图片 / 视频：MediaStore 插入（**推荐路径**）

```kotlin
/**
 * ✅ 分区存储下写媒体的正确方式：MediaStore.insert + ContentResolver.openOutputStream
 * 关键点：
 *  1. 用 IS_PENDING 先占位，写完再置 0（避免扫描到半成品文件）
 *  2. RELATIVE_PATH 决定落到哪个目录（Android 10+）
 *  3. DISPLAY_NAME 是文件名（不需要完整路径）
 */
fun saveImageToGallery(context: Context, bitmap: Bitmap): Uri? {
    val resolver = context.contentResolver
    val values = ContentValues().apply {
        put(MediaStore.Images.Media.DISPLAY_NAME, "photo_${System.currentTimeMillis()}.jpg")
        put(MediaStore.Images.Media.MIME_TYPE, "image/jpeg")
        // Android 10+：用 RELATIVE_PATH 指定目录，不要写绝对路径
        put(MediaStore.Images.Media.RELATIVE_PATH, Environment.DIRECTORY_PICTURES + "/MyApp")
        // Android 10+：标记为 pending，写完再清除
        put(MediaStore.Images.Media.IS_PENDING, 1)
    }

    // insert 到外部存储卷（Android 10+ 用 EXTERNAL_CONTENT_URI）
    val uri = resolver.insert(MediaStore.Images.Media.EXTERNAL_CONTENT_URI, values) ?: return null

    resolver.openOutputStream(uri)?.use { out ->
        bitmap.compress(Bitmap.CompressFormat.JPEG, 90, out)
    }
    // 清除 pending，文件正式对媒体库可见
    resolver.update(uri, ContentValues().apply {
        put(MediaStore.Images.Media.IS_PENDING, 0)
    }, null, null)
    return uri
}
```

#### 3.2 读媒体：三种方式

```kotlin
/**
 * ✅ 方式一：查询 MediaStore（拿 content:// Uri）
 *    - 只能拿到 Uri，不能拿到真实路径（Android 10+）
 *    - 需要 READ_EXTERNAL_STORAGE（读他人文件）
 */
fun queryImages(context: Context): List<Uri> {
    val projection = arrayOf(
        MediaStore.Images.Media._ID,
        MediaStore.Images.Media.DISPLAY_NAME,
        MediaStore.Images.Media.DATE_ADDED
    )
    val selection = "${MediaStore.Images.Media.SIZE} > 0"
    val uris = mutableListOf<Uri>()
    context.contentResolver.query(
        MediaStore.Images.Media.EXTERNAL_CONTENT_URI,
        projection, selection, null,
        "${MediaStore.Images.Media.DATE_ADDED} DESC"
    )?.use { cursor ->
        val idCol = cursor.getColumnIndexOrThrow(MediaStore.Images.Media._ID)
        while (cursor.moveToNext()) {
            val id = cursor.getLong(idCol)
            uris.add(ContentUris.withAppendedId(MediaStore.Images.Media.EXTERNAL_CONTENT_URI, id))
        }
    }
    return uris
}

/**
 * ✅ 方式二：SAF（Storage Access Framework）用户授权
 *    - 用户通过系统文件选择器主动选择文件 → 获得临时读权限
 *    - 用 takePersistableUriPermission 持久化
 *    - 无需任何存储权限，是"访问用户指定文件"的正解
 */
fun persistPermission(context: Context, uri: Uri) {
    val flags = uri.flags and
        (Intent.FLAG_GRANT_READ_URI_PERMISSION or Intent.FLAG_GRANT_WRITE_URI_PERMISSION)
    context.contentResolver.takePersistableUriPermission(uri, flags)
}

/**
 * ✅ 方式三：应用私有目录（无需任何权限）
 */
fun appPrivateDir(context: Context): File {
    // getExternalFilesDir(null) → /storage/emulated/0/Android/data/<pkg>/files
    return context.getExternalFilesDir(null) ?: context.filesDir
}
```

#### 3.3 访问"用户选中的文件"（SAF）——**最被低估的正确姿势**

```kotlin
/**
 * ✅ 通过 ACTION_OPEN_DOCUMENT 让用户选文件。
 * 优势：
 *  - 不需要任何存储权限
 *  - 支持长期授权（takePersistableUriPermission）
 *  - 在 Android 11+ 的 "Restricted storage"（受限存储）下也能工作
 */
fun pickFile(activity: Activity) {
    val intent = Intent(Intent.ACTION_OPEN_DOCUMENT).apply {
        addCategory(Intent.CATEGORY_OPENABLE)
        type = "*/*"
        // 可限制到图片
        // putExtra(Intent.EXTRA_MIME_TYPES, arrayOf("image/*"))
    }
    activity.startActivityForResult(intent, REQUEST_PICK)
}
```

### 4. MANAGE_EXTERNAL_STORAGE（所有文件访问）

```text
【MANAGE_EXTERNAL_STORAGE（所有文件访问权限）】
  引入：Android 11（API 30）
  类型：特殊权限（special / appop）
  权限名：android.permission.MANAGE_EXTERNAL_STORAGE
  授予方式：❌ 不弹窗，必须跳转到系统设置页由用户手动开启
  检查方式：Environment.isExternalStorageManager()

  能力：
    ✓ 读写共享存储中的任意文件（含 Android/data、其他应用目录）
    ✓ 用 File API 直接操作任意路径
    ✓ 不需要 READ/WRITE_EXTERNAL_STORAGE
    ✓ 仍然不能访问 /data/data/<other pkg>（应用私有目录永远隔离）

  ⚠️ 重大限制：
    ① Google Play 政策：只有"核心功能"（文件管理器、备份恢复、杀毒、
       文档编辑、加密/解密工具、磁盘分析、备份）才允许申请；
       绝大多数应用（相机、壁纸、社交、地图）❌ 不允许
    ② 国内应用市场（华为、小米、OPPO、vivo 等）也普遍限制
    ③ 即使拿到权限，用户也可随时在设置里关闭
    ④ targetSdk 30+ 的应用若声明了 MANAGE_EXTERNAL_STORAGE，
       即使用了该权限，在 Google Play 上架审核会被重点关注
```

```kotlin
/**
 * ✅ 正确的申请流程：先检查 → 未授权则引导到系统设置页
 */
fun ensureAllFilesAccess(context: Context): Boolean {
    if (Environment.isExternalStorageManager()) return true

    val intent = Intent(Settings.ACTION_MANAGE_APP_ALL_FILES_ACCESS_PERMISSION).apply {
        data = Uri.fromParts("package", context.packageName, null)
    }
    try {
        context.startActivity(intent)
    } catch (e: ActivityNotFoundException) {
        // 兜底：跳到所有应用的管理页
        context.startActivity(Intent(Settings.ACTION_MANAGE_ALL_FILES_ACCESS_PERMISSION))
    }
    return false
}
```

### 5. Android 13+ 的细分媒体权限（**高频考点**）

Android 13（API 33）把笼统的 `READ_EXTERNAL_STORAGE` 拆成了**按媒体类型**的权限：

| 权限 | 保护的媒体 | 备注 |
| --- | --- | --- |
| `READ_MEDIA_IMAGES` | 图片 | 替代 `READ_EXTERNAL_STORAGE` 的图片部分 |
| `READ_MEDIA_VIDEO` | 视频 | 同上 |
| `READ_MEDIA_AUDIO` | 音频 | 同上 |
| `READ_MEDIA_VISUAL_USER_SELECTED` | **用户选中的**部分照片/视频 | **API 34 新增**（"部分照片访问"） |
| `READ_EXTERNAL_STORAGE` | —— | **仍保留但权限上限降为 19**（低于 33）→ **不再授予任何媒体读取能力** |

#### 5.1 "部分照片访问"的选择性授权（**Android 14+ 的重点**）

```text
【Android 14（API 34）新增 READ_MEDIA_VISUAL_USER_SELECTED】
  当用户拒绝"完整照片访问"时，系统会提供"选择部分照片"选项。
  授予后，应用只能访问用户选中的那些照片。

  申请流程：
    requestPermissions([READ_MEDIA_IMAGES, READ_MEDIA_VIDEO])
      │
      ├─ 用户选"允许所有照片/视频" → 完整权限
      └─ 用户选"仅选择的照片" → 只获得 READ_MEDIA_VISUAL_USER_SELECTED
                                → 应用必须处理"只能看到部分内容"的逻辑
                                → 需要引导用户去系统设置里补选
```

```kotlin
/**
 * ✅ Android 13/14 的媒体权限申请（含部分访问处理）
 */
fun requestMediaPermission(activity: ComponentActivity, launcher: ActivityResultLauncher<Array<String>>) {
    val permissions = mutableListOf(
        Manifest.permission.READ_MEDIA_IMAGES,
        Manifest.permission.READ_MEDIA_VIDEO
    )
    // Android 14+：如果用户选择了"部分访问"，需要引导去设置页补全
    if (Build.VERSION.SDK_INT >= Build.VERSION_CODES.UPSIDE_DOWN_CAKE) {
        permissions.add(Manifest.permission.READ_MEDIA_VISUAL_USER_SELECTED)
    }
    launcher.launch(permissions.toTypedArray())
}

/**
 * ✅ 判断当前是"完整访问"还是"部分访问"
 */
fun hasFullMediaAccess(context: Context): Boolean {
    return if (Build.VERSION.SDK_INT >= Build.VERSION_CODES.TIRAMISU) {
        ContextCompat.checkSelfPermission(context, Manifest.permission.READ_MEDIA_IMAGES)
                == PackageManager.PERMISSION_GRANTED &&
        ContextCompat.checkSelfPermission(context, Manifest.permission.READ_MEDIA_VIDEO)
                == PackageManager.PERMISSION_GRANTED
    } else {
        ContextCompat.checkSelfPermission(context, Manifest.permission.READ_EXTERNAL_STORAGE)
                == PackageManager.PERMISSION_GRANTED
    }
}
```

### 6. StorageVolume（存储卷）与多用户

```text
【StorageVolume 概念】
  一个设备可以挂载多个"存储卷"（volume）：
    · primary   → /storage/emulated/0  （emulated，内部共享存储的主卷）
    · SD 卡     → /storage/XXXX-XXXX
    · USB OTG   → /storage/XXXX-XXXX

  API：
    StorageManager.getStorageVolumes()          → 枚举所有卷
    StorageVolume.getDirectory(Environment.DIRECTORY_PICTURES)  → 该卷下的 Pictures 目录
    StorageVolume.getUuid()                     → 卷标识（持久化时要记录）
    StorageVolume.getDescription()              → 面向用户的名称

  ⚠️ 关键：外部存储 URI 是"按卷"区分的！
     MediaStore.setIncludeVolume() / MediaStore.getContentUri(VOLUME_EXTERNAL_PRIMARY)
     MediaStore.getContentUri(MediaStore.VOLUME_EXTERNAL_PRIMARY)
     MediaStore.setRequireOriginal()            → 拿原图而非缩略图（API 29+）
```

```kotlin
/**
 * ✅ 多卷存储下正确地查询媒体（不能硬编码 EXTERNAL_CONTENT_URI）
 */
fun queryImagesAllVolumes(context: Context): List<Uri> {
    val result = mutableListOf<Uri>()
    val volumes = context.getSystemService(StorageManager::class.java).storageVolumes
    for (volume in volumes) {
        val collection = MediaStore.Images.Media.getContentUri(volume)
        context.contentResolver.query(
            collection,
            arrayOf(MediaStore.Images.Media._ID),
            null, null,
            "${MediaStore.Images.Media.DATE_ADDED} DESC"
        )?.use { cursor ->
            val idCol = cursor.getColumnIndexOrThrow(MediaStore.Images.Media._ID)
            while (cursor.moveToNext()) {
                result.add(ContentUris.withAppendedId(collection, cursor.getLong(idCol)))
            }
        }
    }
    return result
}
```

```text
【多用户与存储】
  · 用户 0（主用户）：/data/media/0、/storage/emulated/0
  · 用户 10：/data/media/10、/storage/emulated/10
  · 每个用户有独立的媒体库与外部存储视图
  · MediaStore 的查询天然按当前用户过滤
  · WorkManager / JobScheduler 的任务按 UID 隔离
  · ⚠️ 跨用户访问需要 MANAGE_EXTERNAL_STORAGE 或系统权限
```

### 7. 分区存储对第三方 SDK 的影响（**工程重点**）

```text
【典型兼容性问题】
  ① 旧版图片选择器（三方 SDK）
     直接用 File("/storage/emulated/0/DCIM/xxx.jpg")
     → targetSdk 30+ 时：文件不存在 / EACCES / "无法解码"
     → 修法：改用 MediaStore 查询，或用 SDK 新版本，或引导用户用系统 Photo Picker

  ② 微信/QQ 分享、裁剪、压缩 SDK
     很多老 SDK 依赖 WRITE_EXTERNAL_STORAGE 与真实路径
     → targetSdk 30+ 直接失败
     → 修法：升级 SDK；或把文件写到应用私有目录 → 用 FileProvider 共享

  ③ 上传/下载 SDK 写 /sdcard/xxx
     → 失败；改写 getExternalFilesDir()

  ④ 数据库/Realm 直接在 /sdcard 建库
     → Android 11+ 不允许；改到 Context.getDatabasePath()

  ⑤ 相册扫描类 SDK（读取全部媒体）
     → 需要细分媒体权限；Android 14 可能是"部分访问"

【通用修法优先级】
  1. 升级 SDK 到支持分区存储的版本（首选）
  2. 改用 SAF / MediaStore / Photo Picker
  3. 改用应用私有目录 + FileProvider 共享
  4. 目标定位为文件管理器/备份类 → 申请 MANAGE_EXTERNAL_STORAGE
```

#### 7.1 Photo Picker（**Android 13+ 推荐**）

```text
【Photo Picker（系统照片选择器）】
  API：MediaStore.ACTION_PICK_IMAGES（API 33+）
  优势：
    ✅ 用户只授权"选中的几张"，不暴露整个媒体库
    ✅ 不需要任何存储权限
    ✅ 未来 Android 版本会保持可用（Google 承诺）
    ✅ 配合 ACTION_PICK_IMAGES 的 "photo picker backport" 可下推到 Android 11/12
  降级方案：
    if (SDK_INT >= 33) startActivityForResult(Intent(MediaStore.ACTION_PICK_IMAGES), req)
    else → Intent(Intent.ACTION_OPEN_DOCUMENT) 或 ACTION_GET_CONTENT
```

```kotlin
/**
 * ✅ Photo Picker：不需要任何存储权限
 */
```

### 8. 存储相关的性能与内存提示

```text
【存储与内存/性能的联动】
  ① 大文件不要读进内存
     → 流式读写（InputStream/OutputStream），或 mmap
     → 避免 byte[] 大数组（> 12KB 进入 ART 的 Large Object Space）

  ② 图片放外部存储的私有目录，避免占内存
     → Context.getExternalFilesDir(null) 与内存是两套配额体系

  ③ 数据库与 SharedPreferences 放内部存储
     → 内部存储是加密的 ext4/f2fs，事务与 mmap 性能更好

  ④ 外部存储的读写经过 FUSE daemon，比内部存储慢
     → 高频小文件读写要评估 FUSE 开销

  ⑤ 缓存目录可被系统随时清理
     → 缓存不能放 getCacheDir()，重要数据放 getFilesDir() 或数据库
```

```kotlin
object MediaStoreHelper {

    /**
     * ✅ 写入图片到公共图库（分区存储标准做法）
     * 返回 content:// Uri（不是 file:// 路径）
     */
    fun saveBitmap(context: Context, bitmap: Bitmap, relativePath: String = "Pictures/MyApp"): Uri? {
        val resolver = context.contentResolver
        val name = "IMG_${System.currentTimeMillis()}.jpg"
        val values = ContentValues().apply {
            put(MediaStore.Images.Media.DISPLAY_NAME, name)
            put(MediaStore.Images.Media.MIME_TYPE, "image/jpeg")
            put(MediaStore.Images.Media.RELATIVE_PATH, relativePath)
            put(MediaStore.Images.Media.IS_PENDING, 1)   // 写完再置 0
        }
        val uri = resolver.insert(MediaStore.Images.Media.EXTERNAL_CONTENT_URI, values)
            ?: return null
        resolver.openOutputStream(uri)?.use { out ->
            bitmap.compress(Bitmap.CompressFormat.JPEG, 90, out)
        } ?: return null
        resolver.update(uri, ContentValues().apply {
            put(MediaStore.Images.Media.IS_PENDING, 0)
        }, null, null)
        return uri
    }

    /**
     * ✅ 删除媒体：只有"自己创建的"才能删，无需任何权限
     */
    fun delete(context: Context, uri: Uri): Boolean = try {
        context.contentResolver.delete(uri, null, null) > 0
    } catch (e: SecurityException) {
        false   // 删别人的文件会抛 SecurityException
    }

    /**
     * ✅ 读取图片内容（不把整图读进内存，用流式 + inSampleSize 采样）
     */
    fun loadSampledBitmap(context: Context, uri: Uri, reqWidth: Int, reqHeight: Int): Bitmap? {
        val resolver = context.contentResolver

        // 第一次：只读尺寸
        val bounds = BitmapFactory.Options().apply { inJustDecodeBounds = true }
        resolver.openInputStream(uri)?.use {
            BitmapFactory.decodeStream(it, null, bounds)
        }
        if (bounds.outWidth <= 0 || bounds.outHeight <= 0) return null

        // 第二次：按采样率解码
        val options = BitmapFactory.Options().apply {
            inSampleSize = calculateInSampleSize(bounds, reqWidth, reqHeight)
            inPreferredConfig = Bitmap.Config.RGB_565   // 省一半内存
        }
        return resolver.openInputStream(uri)?.use {
            BitmapFactory.decodeStream(it, null, options)
        }
    }

    private fun calculateInSampleSize(
        options: BitmapFactory.Options,
        reqWidth: Int,
        reqHeight: Int
    ): Int {
        val (height, width) = options.outHeight to options.outWidth
        var inSampleSize = 1
        if (height > reqHeight || width > reqWidth) {
            val halfHeight = height / 2
            val halfWidth = width / 2
            while (halfHeight / inSampleSize >= reqHeight && halfWidth / inSampleSize >= reqWidth) {
                inSampleSize *= 2
            }
        }
        return inSampleSize
    }
}
```

```kotlin
/**
 * ✅ 完整的媒体查询：处理多卷、原始文件、权限分支

class MediaRepository(private val context: Context) {

    /**
     * @param imageOnly true 只查图片，false 查视频
     */
    fun queryMedia(imageOnly: Boolean = true): List<MediaItem> {
        val items = mutableListOf<MediaItem>()
        val storageManager = context.getSystemService(StorageManager::class.java)

        for (volume in storageManager.storageVolumes) {
            // ✅ 用卷的 content uri，而不是硬编码 EXTERNAL_CONTENT_URI
            val collection = if (imageOnly) {
                MediaStore.Images.Media.getContentUri(volume)
            } else {
                MediaStore.Video.Media.getContentUri(volume)
            }

            val projection = arrayOf(
                MediaStore.MediaColumns._ID,
                MediaStore.MediaColumns.DISPLAY_NAME,
                MediaStore.MediaColumns.SIZE,
                MediaStore.MediaColumns.DATE_MODIFIED
            )

            context.contentResolver.query(
                collection,
                projection,
                null, null,
                "${MediaStore.MediaColumns.DATE_MODIFIED} DESC"
            )?.use { cursor ->
                val idCol = cursor.getColumnIndexOrThrow(MediaStore.MediaColumns._ID)
                val nameCol = cursor.getColumnIndexOrThrow(MediaStore.MediaColumns.DISPLAY_NAME)
                val sizeCol = cursor.getColumnIndexOrThrow(MediaStore.MediaColumns.SIZE)

                while (cursor.moveToNext()) {
                    val id = cursor.getLong(idCol)
                    items += MediaItem(
                        uri = ContentUris.withAppendedId(collection, id),
                        name = cursor.getString(nameCol) ?: "",
                        size = cursor.getLong(sizeCol),
                        // ✅ 记录卷 UUID，用于后续精确访问
                        volumeUuid = volume.uuid
                    )
                }
            }
        }
        return items
    }

    data class MediaItem(
        val uri: Uri,
        val name: String,
        val size: Long,
        val volumeUuid: String
    )
}
```

## 常见问题 / 面试要点

**读者问：什么是分区存储（Scoped Storage）？它解决什么问题？**

**AI答：**

1. **定义**：Android 10（API 29）引入的存储访问模型。核心变更是**"应用不再拥有整个外部文件系统的访问权"**，只能访问：
   - **自己创建的文件**（应用私有目录 + 自己写入 MediaStore 的媒体）；
   - **用户明确授权的文件**（SAF / `takePersistableUriPermission`）；
   - **通过 `MANAGE_EXTERNAL_STORAGE` 获得的"所有文件"访问权**（受限）。
2. **解决的老问题**：
   - 一个 `READ_EXTERNAL_STORAGE` 就能读全盘 → **最小权限原则**被打破；
   - 应用卸载后文件残留 → 应用私有目录**卸载即删**；
   - 无法追踪文件归属 → **MediaStore 成为统一的媒体元数据库**；
   - `/sdcard` 是 FUSE，路径不可靠 → **以 Uri 为一等公民**。
3. **实现层面**：分区存储的检查**发生在 userspace 的 FUSE daemon（sdcard）中**，而 `MediaStore` 走的是 Binder 通道，两者权限行为略有差异。
4. **注意**：**分区存储是"按 targetSdk 生效"的**。`targetSdk ≤ 29` 的应用在 Android 10 上仍走 legacy 模型（除非声明 `requestLegacyExternalStorage`）。
5. **面试话术**："**分区存储的本质是把'文件系统路径'降级为'内容 Uri'。路径只对应用自己的目录有效，跨应用访问一律走 `ContentResolver` + Uri。**"

---

**读者问：targetSdk 30 前后，读图库的行为有什么区别？**

**AI答：**

| 场景 | targetSdk ≤ 29 | targetSdk ≥ 30 |
| --- | --- | --- |
| 读自己创建的图片 | ✅ 直接用 `File` 路径 | ✅ 用 `content://` Uri（`File` 路径可能已不适用） |
| 读别人创建的图片 | 需 `READ_EXTERNAL_STORAGE`，可拿 file 路径 | 需 `READ_EXTERNAL_STORAGE`，**只能拿 Uri**，`getMediaFileId` 失效 |
| 写公共目录 | 需 `WRITE_EXTERNAL_STORAGE` | **❌ 禁止直写**，只能 `MediaStore.insert` 或写自己的目录 |
| 删别人创建的图片 | 需 `WRITE_EXTERNAL_STORAGE` | **❌ 禁止**（只能删自己创建的） |
| 访问 `Android/data/<other>/` | 需权限 | **❌ 禁止**（Android 11+） |

1. **最关键的三点**：
   - **路径失效**：`MediaStore.getMediaFileId()` 在 targetSdk 30+ 返回 null，**拿不到真实路径**，必须全程用 Uri；
   - **写权限消失**：`WRITE_EXTERNAL_STORAGE` 在 targetSdk 30+ **完全无效**（系统不再授予）；
   - **删除受限**：只能删自己创建的。
2. **迁移期方案**：targetSdk = 29 时可声明 `android:requestLegacyExternalStorage="true"` 临时豁免（**仅 Android 10 有效，Android 11+ 忽略**）。
3. **面试话术**："**targetSdk 30 的分水岭是'路径'和'Uri'的地位反转：30 之前路径是一等公民，30 之后 Uri 才是。**"

---

**读者问：Android 13 的细分媒体权限和 Android 14 的"部分照片访问"是什么？**

**AI答：**

1. **Android 13（API 33）的拆分**：`READ_EXTERNAL_STORAGE` 被拆成 `READ_MEDIA_IMAGES` / `READ_MEDIA_VIDEO` / `READ_MEDIA_AUDIO`，**按需申请**。旧的 `READ_EXTERNAL_STORAGE` 保留但权限上限被降到 19（低于 33），**申请它不再能读到任何媒体**。
2. **Android 14（API 34）的"部分照片访问"**：新增 `READ_MEDIA_VISUAL_USER_SELECTED`。用户拒绝"全部允许"时可以选择"仅允许选中的照片"，此时应用只能访问用户勾选的部分。
3. **应用的适配要求**：
   - 申请时要**同时带上** `READ_MEDIA_IMAGES`、`READ_MEDIA_VIDEO` 和 `READ_MEDIA_VISUAL_USER_SELECTED`（API 34+）；
   - 拿到权限后要**判断是完整访问还是部分访问**（部分访问时列表会缺数据，需要引导用户去设置页补选）；
   - 部分访问场景下**扫描媒体库得到的条目会不完整**，不能用"数量少"判断为 bug。
4. **最佳实践**：优先用 **Photo Picker**（`MediaStore.ACTION_PICK_IMAGES`）——**完全不需要存储权限**，用户只授权选中的那几张，且 Google 承诺保持可用；Android 11/12 可通过 backport 库使用。
5. **面试话术**："**Android 13/14 的方向是'权限颗粒度越来越细'。系统不想让任何应用拿到'整个媒体库'，所以推出了细分权限 + 部分授权 + Photo Picker 三件套。**"

---

**读者问：`MANAGE_EXTERNAL_STORAGE` 是什么？什么应用才能申请？**

**AI答：**

1. **定义**：Android 11（API 30）引入的**特殊权限**（special / appop），允许应用读写**共享存储中的任意文件**（包括 `Android/data/`、其它应用的目录）。
2. **授予方式**：**没有运行时弹窗**。必须通过 `ACTION_MANAGE_APP_ALL_FILES_ACCESS_PERMISSION` **跳转到系统设置页**，由用户手动开启。用 `Environment.isExternalStorageManager()` 检查状态。
3. **政策限制（关键）**：
   - **Google Play**：仅限"核心功能"类应用——文件管理器、备份恢复、杀毒、文档编辑、磁盘分析、加密工具、**虚拟机/沙盒**。相机、壁纸、社交、地图等**❌ 不允许**；
   - 国内应用市场同样普遍限制；
   - 声明了该权限的 targetSdk 30+ 应用在上架时会**被重点审核**。
4. **即使拿到也有边界**：
   - 用户可随时在设置里关闭；
   - **永远无法访问其它应用的内部私有目录** `/data/data/<other>/`（那是 Linux 权限 + SELinux 管的，与本权限无关）；
   - **不能绕过** Android 11+ 对 `Android/data` 与 `Android/obb` 的限制（这两个目录即使有该权限也**不能直接访问**，需通过 SAF 或 MediaStore 下载接口）。
5. **面试话术**："**`MANAGE_EXTERNAL_STORAGE` 是给'文件管理器'这类应用留的口子，不是万能钥匙。面试时如果我说'我的应用需要它来读图片'，那基本就被判定为不合规了。**"

---

**读者问：内部存储和外部存储的底层差异是什么？为什么说外部存储是 FUSE？**

**AI答：**

1. **内部存储**：`/data/data/<pkg>/`，物理上是 **ext4 / f2fs** 真实分区（userdata），**加密**（FBE 文件级加密，锁屏后密钥在内存，`Direct Boot` 未解锁时不可用）。访问靠 **Linux 文件权限（0700）**，只有本应用 UID 能访问。
2. **外部存储**：`/storage/emulated/0/` **不是真实分区**，而是一个 **FUSE 挂载点**。真实数据在 `/data/media/<userId>`，由 userspace 守护进程（`/system/bin/sdcard`）暴露。
3. **FUSE 的三个后果**：
   - **权限检查发生在 userspace**（FUSE daemon）→ 分区存储的规则由它执行；
   - **路径不保证真实** → 不能拿 `file://` Uri 长期持有；
   - **性能低于本地文件系统**（多一层用户态来回）→ 高频小文件 IO 要评估开销。
4. **SD 卡 / USB**：这些是**真实的块设备分区**，用 `vfat`/`exfat` 挂载，**不经过 FUSE**，但 Android 11+ 需要 `MANAGE_EXTERNAL_STORAGE` 或 SAF 才能直接访问。
5. **多用户**：每个用户有独立的 `/data/media/<userId>` 与 `/storage/emulated/<userId>`。
6. **面试话术**："**内部存储是'真文件系统 + 权限隔离 + 加密'；外部存储是'FUSE 虚拟层 + MediaStore 元数据层'。搞懂这个区别，就理解了为什么分区存储要靠 MediaStore 而不是靠路径。**"

---

**读者问：分区存储对第三方 SDK 有什么影响？遇到老 SDK 崩溃怎么排查？**

**AI答：**

1. **典型症状**：
   - `FileNotFoundException` / `EACCES` 访问 `/sdcard/xxx`；
   - `MediaStore.getMediaFileId()` 返回 null 或抛异常；
   - 选图后拿到 **空 Uri** 或 **打不开**；
   - 裁剪/压缩后输出文件为 0 字节；
   - 上传 SDK 报"存储空间不足"（其实是没权限写）。
2. **排查步骤**：
   - **确认 targetSdk**：`targetSdk >= 30` 且未适配 → 100% 是分区存储问题；
   - **看是否有 `requestLegacyExternalStorage`**（targetSdk 29 时有效）；
   - **看日志里的 `Permission denied` / `EACCES` 路径**：是 `/sdcard/xxx`（路径访问）还是 `content://`（Uri 访问）；
   - **用 `adb shell ls -l /sdcard/Android/data/`** 确认目录归属。
3. **修法优先级**：
   1. **升级 SDK** 到支持分区存储的版本（首选）；
   2. **改用 MediaStore 查询 + `ContentResolver.openInputStream`**；
   3. **改用 SAF（`ACTION_OPEN_DOCUMENT`）**，尤其是用户主动选文件的场景；
   4. **改用 Photo Picker**（API 33+，可下推）；
   5. **把中间文件写到 `getExternalFilesDir()`**，用 **FileProvider** 分享给三方 SDK；
   6. 确实是文件管理类应用 → 申请 `MANAGE_EXTERNAL_STORAGE`。
4. **面试话术**："**分区存储导致的线上问题，根因几乎都是'第三方 SDK 还在用绝对路径访问共享存储'。排查时先看 targetSdk，再看崩溃路径是不是 `/sdcard/` 开头。**"

---

**读者问：`StorageVolume` 是什么？多卷和 SD 卡怎么处理？**

**AI答：**

1. **定义**：`StorageVolume`（API 24+）表示一个**存储卷**：主卷（`/storage/emulated/0`，emulated）、SD 卡、USB OTG、外部 SD 等。
2. **核心 API**：
   - `StorageManager.getStorageVolumes()` → 枚举所有卷；
   - `StorageVolume.getDirectory(type)` → 该卷下的标准目录（如 `DIRECTORY_PICTURES`）；
   - `StorageVolume.getUuid()` → 持久化标识；
   - `StorageVolume.getDescription()` → 面向用户的名称（"内部存储"/"SD 卡"）。
3. **MediaStore 是按卷分区的**：
   - `MediaStore.Images.Media.getContentUri(volume)` → 该卷的集合 Uri；
   - `MediaStore.setIncludeVolume()` → 设置"写入目标卷"；
   - `MediaStore.setRequireOriginal()`（API 29+）→ 拿原图而非缩略图。
   - **硬编码 `MediaStore.Images.Media.EXTERNAL_CONTENT_URI` 会漏掉 SD 卡上的照片**——这是常见 bug。
4. **SD 卡的特殊限制**（Android 11+）：
   - 直接 `File` 访问 SD 卡路径被**禁止**；
   - 需要 `MANAGE_EXTERNAL_STORAGE` **或**通过 SAF / `MediaStore` 的 `MediaStore.Downloads` 接口；
   - **USB OTG 移除后卷失效**，Uri 需要重新解析。
5. **多用户**：每个用户有独立的媒体库与存储视图，MediaStore 查询天然按当前用户过滤。
6. **面试话术**："**`StorageVolume` 提醒我们一件事：'外部存储'不是一个，而是'一组卷'。写代码时凡是硬编码 `EXTERNAL_CONTENT_URI` 的地方，都要检查是不是漏了 SD 卡。**"

---

**读者问：应用想给别的应用分享一个文件，怎么做才安全？**

**AI答：**

1. **绝对不要**直接把 `/sdcard/xxx` 的路径或 `file://` Uri 给别人——**`FileUriExposedException`**（targetSdk 24+ 会直接崩），且泄露了路径等于泄露了文件。
2. **正确做法：`FileProvider`**：
   - 在 `AndroidManifest.xml` 声明 `provider`，`android:author authorities="${applicationId}.fileprovider"`、`exported="false"`、`grantUriPermissions="true"`；
   - 用 `res/xml/file_paths.xml` 声明可分享的目录（`files-path` / `cache-path` / `external-files-path` / `external-cache-path` / `external-path`）；
   - 用 `FileProvider.getUriForFile(context, "${packageName}.fileprovider", file)` 生成 `content://` Uri。
3. **授权方式**：
   - `Intent.setData(uri)` + `addFlags(Intent.FLAG_GRANT_READ_URI_PERMISSION)`；
   - 或 `ClipData.newRawUri("", uri)` + `setClipData`（**多个 Uri 时必须用 ClipData，否则只授权第一个**）；
   - `PendingIntent` 场景要显式传 `FLAG_GRANT_READ_URI_PERMISSION`。
4. **接收方**：`context.contentResolver.openInputStream(uri)` 即可（授权是临时的，随 Intent 生命周期）。
5. **接收别人的文件**：用 SAF（`ACTION_OPEN_DOCUMENT`）+ `takePersistableUriPermission` 持久化授权。
6. **面试话术**："**分享文件的标准链路是：`FileProvider` 生成 `content://` Uri → Intent 携带 `FLAG_GRANT_*` 权限 → 接收方通过 `ContentResolver` 读。路径永远不跨进程传递。**"

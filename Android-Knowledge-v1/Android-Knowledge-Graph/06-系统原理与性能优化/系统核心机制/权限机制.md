# 权限机制

## 一句话定义

Android 权限是**沙箱模型下的能力授予机制**：系统按 **dangerous（运行时授权）/ normal（安装时自动授予）/ special（特殊管理类）** 三档管理权限，危险的必须在**运行时由用户确认**。理解权限机制的三个关键点：**权限组（permission group）决定申请弹窗的聚合**、**权限可以随时被撤销**、**分区存储与 Android 13 的媒体权限让"权限申请"从"一个"变成了"一组"。

## 核心原理

### 1. 权限的分类（**必背**）

| 类别 | 保护级别 | 安装时 | 运行时 | 举例 |
| --- | --- | --- | --- | --- |
| **normal** | `normal` | **自动授予** | ❌ 不需要 | `INTERNET`、`ACCESS_NETWORK_STATE`、`VIBRATE`、`RECEIVE_BOOT_COMPLETED` |
| **dangerous** | `dangerous` | ❌ 不授予 | ✅ **必须运行时申请** | `CAMERA`、`RECORD_AUDIO`、`READ_CONTACTS`、`ACCESS_FINE_LOCATION`、`READ_EXTERNAL_STORAGE` |
| **special / 特殊管理** | `signature` / `signature\|privileged` / `appop` / `development` | 取决于保护级别 | 通过**系统设置页**引导用户开启 | `SYSTEM_ALERT_WINDOW`、`REQUEST_INSTALL_PACKAGES`、`MANAGE_EXTERNAL_STORAGE`、`WRITE_SETTINGS`、`QUERY_ALL_PACKAGES` |

**保护级别（protectionLevel）的完整列表**：

| 保护级别 | 含义 |
| --- | --- |
| `normal` | 任何应用都可申请，安装即授予 |
| `dangerous` | 需要用户运行时确认 |
| `signature` | **只有用相同证书签名**的应用才能获得（系统应用级） |
| `signatureOrSystem` / `signature\|privileged` | 相同签名 **或** 预装为系统应用 |
| `appop` | **AppOps** 机制：可被用户在设置里单独开关（如"允许后台访问位置"） |
| `development` | 开发阶段使用 |
| `installer` | 只有安装了该权限的"安装器"应用才能获得 |
| `verified` | 需要设备"verified boot"状态 |

> **面试高频**：**`SYSTEM_ALERT_WINDOW` 与 `REQUEST_INSTALL_PACKAGES` 是 `signature|appop|special` 级别**，声明了不代表能直接用——必须**跳转到系统设置页让用户手动开启**，且 `shouldShowRequestPermissionRationale` 对它们**永远返回 false**。

### 2. 危险权限的完整清单（**高频背诵题**）

Android 的危险权限按 **权限组（permission group）** 划分。申请时**同组一起弹窗**。

| 权限组 | 权限 | 保护级别 |
| --- | --- | --- |
| **CALENDAR** | `READ_CALENDAR`、`WRITE_CALENDAR` | dangerous |
| **CAMERA** | `CAMERA` | dangerous |
| **CONTACTS** | `READ_CONTACTS`、`WRITE_CONTACTS`、`GET_ACCOUNTS` | dangerous |
| **LOCATION** | `ACCESS_FINE_LOCATION`、`ACCESS_COARSE_LOCATION`、`ACCESS_BACKGROUND_LOCATION` | dangerous（background 单独申请） |
| **MICROPHONE** | `RECORD_AUDIO` | dangerous |
| **PHONE** | `READ_PHONE_STATE`、`READ_PHONE_NUMBERS`、`CALL_PHONE`、`ANSWER_PHONE_CALLS`、`READ_CALL_LOG`、`WRITE_CALL_LOG`、`ADD_VOICEMAIL`、`USE_SIP`、`PROCESS_OUTGOING_CALLS` | dangerous |
| **SENSORS** | `BODY_SENSORS` | dangerous |
| **SMS** | `SEND_SMS`、`RECEIVE_SMS`、`READ_SMS`、`RECEIVE_WAP_PUSH`、`RECEIVE_MMS` | dangerous |
| **STORAGE** | `READ_EXTERNAL_STORAGE`、`WRITE_EXTERNAL_STORAGE`、`ACCESS_MEDIA_LOCATION` | dangerous（**Android 13+ 已被细分媒体权限替代**） |
| **NEARBY_DEVICES**（Android 12+） | `BLUETOOTH_SCAN`、`BLUETOOTH_CONNECT`、`BLUETOOTH_ADVERTISE`、`UWB_RANGING`、`NFC` | dangerous |
| **NOTIFICATIONS**（Android 13+） | `POST_NOTIFICATIONS` | dangerous（**运行时新增强制权限**） |
| **ACTIVITY_RECOGNITION**（Android 10+） | `ACTIVITY_RECOGNITION` | dangerous |
| **READ_MEDIA_*`**（Android 13+） | `READ_MEDIA_IMAGES`、`READ_MEDIA_VIDEO`、`READ_MEDIA_AUDIO`、`READ_MEDIA_VISUAL_USER_SELECTED` | dangerous（**取代 STORAGE 组**） |

### 3. 安装时授权 vs 运行时授权

```text
【normal 权限】
  安装 APK
    → PackageManagerService 解析 Manifest
    → 检查保护级别是 normal
    → 自动写入该应用的权限授予表（/data/system/packages.xml）
    → 安装完成，用户无感知
  ⚠️ Android 6.0 之前，所有权限都是这样一次性授予的（安装即授权）

【dangerous 权限（Android 6.0+）】
  安装 APK
    → Manifest 中声明 dangerous 权限
    → **不会自动授予**，在 /data/system/packages.xml 中标记为 "requested"
    → 用户首次触发相关功能时，应用调用 requestPermissions()
    → 系统弹出权限对话框
    → 用户选择 → PMS 记录 granted / denied
```

**运行时授权的核心流程**：

```mermaid
sequenceDiagram
    participant App as 应用
    participant P as PackageManagerService
    participant UI as 系统权限弹窗

    App->>P: checkSelfPermission(perm)  (Context.checkSelfPermission)
    P-->>App: PERMISSION_GRANTED / DENIED
    alt DENIED
        App->>App: shouldShowRequestPermissionRationale(perm)
        Note over App: true=永久拒绝需去设置; false=首次申请或已拒绝
        App->>UI: requestPermissions(perms, requestCode)
        UI-->>App: onRequestPermissionsResult(requestCode, perms, grantResults)
    end
```

**系统内部的关键方法**：

| 方法 | 所属 | 说明 |
| --- | --- | --- |
| `Context.checkSelfPermission(perm)` | 应用 | 查询**自己**是否被授予 |
| `PackageManager.checkPermission(perm, pkgName)` | 应用 | 查询**其他包**的权限（需知道包名） |
| `Activity.shouldShowRequestPermissionRationale(perm)` | 应用 | **是否需要解释**：true 表示曾被拒绝（且不是"不再询问"）；false 表示首次申请或已被永久拒绝 |
| `ActivityCompat.requestPermissions(activity, perms, code)` | 应用 | 发起申请 |
| `Activity.onRequestPermissionsResult(code, perms, results)` | 应用 | 回调（已废弃，推荐用 ActivityResult API） |
| `PackageManager.setPermissionFlags()` | 系统 | 设置 `FLAG_USER_FIXED` / `FLAG_USER_SENSITIVE_WHEN_GRANTED` 等 |
| `PackageManagerService.revokeRuntimePermission()` | 系统 | 撤销权限（自动权限会撤销，权限撤销通知） |

### 4. 权限的存储位置（**加分点**）

```text
权限授予状态存储在：
  /data/system/packages.xml      ← 主存储（PackageManagerService 管理）
  /data/system/users/<userId>/package-restrictions.xml  ← 用户限制
  /data/system/users/<userId>/grants.xml（部分设备）

每条记录形如：
  <package name="com.example" ...>
      <granted-permission name="android.permission.CAMERA" granted="true" flags="USER_SET" />
      <requested-permission name="android.permission.RECORD_AUDIO" granted="false" />
  </package>

重要 flags：
  USER_SET          用户明确同意
  USER_FIXED        用户勾选了"不再询问"（应用无法再弹窗，只能引导去设置）
  ONE_TIME          一次性权限（Android 6.0 特有，应用重启后失效）
  RESTRICTION_INSTALL / RESTRICTION_USER ← 与"应用受限访问"相关
```

**AppOps 机制（Android 10+ 重要变化）**：

```text
AppOpsService 位于 system_server
  ├─ 管理"权限的细粒度开关"，例如：
  │    CAMERA → op_camera
  │    ACCESS_FINE_LOCATION → op_stress_location / op_location
  │    READ_CONTACTS → op_read_contacts
  └─ 与权限系统并行：即使权限是 granted，
       用户仍可在设置里单独关闭某个 AppOp
       （例如"允许后台访问位置"开关）

命令：adb shell cmd appops set com.example CAMERA deny
```

### 5. 权限撤销与监听（**面试加分**）

**权限可能被撤销的几种情况**：
1. **用户手动去设置里撤销**；
2. **权限自动过期**（Android 11+ 的"自动撤销权限"功能，未使用的权限 3 个月后自动撤销，可通过 `android:maxSdkVersion` + `autoRevokeWhitelist` 调整）；
3. **权限被"降级"**（用户选择了"仅允许在使用时允许"，系统从 `ACCESS_FINE_LOCATION` 降级到 `ACCESS_COARSE_LOCATION`）；
4. **用户撤销了某个权限组的一个权限**，同组的其他权限也可能被连带处理；
5. **系统"应用受限访问"（Android 14）**：用户可以把应用设为"受限访问"，此时**所有权限都被视为未授予**（除了少数）。

**监听权限被撤销**：

```kotlin
class PermissionWatcher(private val context: Context) {

    private val listener = OnPermissionsChangeListener { /* API 31+ */ }

    fun start() {
        // Android 11+：PackageManager 有权限变更回调
        if (Build.VERSION.SDK_INT >= Build.VERSION_CODES.S) {
            // 通过 ContentObserver 监听 packages.xml 变化更通用
        }
        // 通用方案：ContentObserver 监听权限授予表
        val observer = object : ContentObserver(Handler(Looper.getMainLooper())) {
            override fun onChange(selfChange: Boolean) {
                // 重新检查关键权限状态
                recheckPermissions()
            }
        }
        context.contentResolver.registerContentObserver(
            Uri.parse("content://com.android.settings"),  // 部分 ROM 有效
            true, observer
        )
    }

    private fun recheckPermissions() {
        val camera = ContextCompat.checkSelfPermission(context, Manifest.permission.CAMERA)
        if (camera != PackageManager.PERMISSION_GRANTED) {
            // 权限被撤销，切换到降级 UI
            onPermissionRevoked()
        }
    }
}
```

**更可靠的官方做法**：在每次进入关键功能时**重新 `checkSelfPermission`**，而不是依赖监听（因为监听不可靠且不保证及时）。

### 6. 权限组（permission group）的机制（**核心概念**）

```xml
<!-- AndroidManifest.xml 中声明 -->
<uses-permission android:name="android.permission.CAMERA" />
<uses-permission android:name="android.permission.RECORD_AUDIO" />

<!-- 声明权限组（可选，用于说明应用的核心功能） -->
<uses-permission-group android:name="android.permission-group.CAMERA" />
```

**规则**：
- **同一权限组内的权限，系统只弹一个对话框**，用户一次决定整组；
- **`requestPermissions` 传入多个权限时，若属于同组，只弹一个**；
- **`onRequestPermissionsResult` 会返回所有请求的权限**，但**同组内的权限结果是"绑定"的**——用户同意一组里的一个，整组都会授予；
- **应用可以自定义权限组**（`<permission-group>`），但**不能改变系统权限组的划分**。

**权限组的一个实际影响**：`CAMERA` 组只有 `CAMERA` 一个权限；`LOCATION` 组有 3 个（fine/coarse/background）；`STORAGE` 组在 Android 13+ 已被 `READ_MEDIA_*` 组逐步替代。

### 7. 自定义权限（**面试高频**）

```xml
<!-- 定义权限 -->
<permission
    android:name="com.example.permission.READ_USER_DATA"
    android:description="@string/permission_desc"
    android:label="@string/permission_label"
    android:protectionLevel="signature" />

<!-- 使用权限（自己的应用用） -->
<uses-permission android:name="com.example.permission.READ_USER_DATA" />

<!-- 其他应用想用，需要先在他们的 manifest 声明 uses-permission -->
```

| protectionLevel | 谁能获得 |
| --- | --- |
| `normal` | 任何应用申请即授予（不推荐用于敏感数据） |
| `dangerous` | 运行时申请，用户确认 |
| `signature` | **只有与定义方使用相同签名证书的应用**才能获得（最安全） |
| `signature\|privileged` | 相同签名 **或** 预装为系统应用 |

**保护级别可以组合**：`dangerous|signature` 表示"需要运行时申请 **且** 签名相同"。

**自定义权限的两个经典用途**：
1. **保护自己的组件**（Service / Provider / Receiver）：
   ```xml
   <service
       android:name=".UserService"
       android:exported="true"
       android:permission="com.example.permission.READ_USER_DATA" />
   ```
2. **SDK 的能力授权**（第三方 SDK 给宿主应用"授权"）：SDK 定义一个 `signature` 级权限，只有用 SDK 提供方证书签名的应用才能获得——这样可以防止第三方应用盗用 SDK。

### 8. `ActivityResult` API 的权限申请（**现代写法**）

```kotlin
class PermissionActivity : AppCompatActivity() {

    // ✅ 推荐：ActivityResultContracts.RequestMultiplePermissions
    private val requestPermission = registerForActivityResult(
        ActivityResultContracts.RequestMultiplePermissions()
    ) { result ->
        // result 是 Map<权限, 是否授予>
        val cameraGranted = result[Manifest.permission.CAMERA] ?: false
        val audioGranted = result[Manifest.permission.RECORD_AUDIO] ?: false
        when {
            cameraGranted && audioGranted -> startRecording()
            // shouldShowRequestPermissionRationale 为 true 表示"曾拒绝过"
            shouldShowRationale(Manifest.permission.CAMERA) -> showRationaleDialog {
                requestPermission.launch(arrayOf(Manifest.permission.CAMERA))
            }
            else -> {
                // 首次申请 或 已"不再询问"
                if (hasRequestedBefore) {
                    // 已"不再询问"，只能引导去设置
                    showSettingsDialog()
                } else {
                    requestPermission.launch(arrayOf(Manifest.permission.CAMERA, Manifest.permission.RECORD_AUDIO))
                }
            }
        }
    }
}
```

**各种 `ActivityResultContracts`**：

| Contract | 用途 |
| --- | --- |
| `RequestPermission()` | 请求单个危险权限 |
| `RequestMultiplePermissions()` | 请求多个危险权限 |
| `TakePicture()` / `TakeVideo()` | 相机（**自动申请 CAMERA 权限**） |
| `PickVisualMedia()` | 选图/选视频（**Android 13+ 的 Photo Picker，不需要任何存储权限**） |
| `OpenDocument()` | 打开文档（**SAF，不需要存储权限**） |
| `CreateDocument()` | 创建文档 |
| `StartActivityForResult()` | 通用启动 |

> **加分点**：`ActivityResultContracts.TakePicture()` 等内置契约**会自动处理对应的权限申请**（内部用 `RequestMultiplePermissions` 组合而成），是"零权限感知"的最佳实践。

### 9. Android 11+ / 13+ 的权限变化（**高频新特性**）

| 版本 | 变化 | 影响 |
| --- | --- | --- |
| **Android 10** | **分区存储**（Scoped Storage）默认开启（targetSdk 29+） | 读写外部存储不再需要权限；见 [[存储分区机制]] |
| **Android 10** | `ACCESS_BACKGROUND_LOCATION` **必须单独申请** | 不能与前台定位一起申请；且申请时系统会先拒绝并提示"始终允许"选项 |
| **Android 11** | **一次性权限（One-time permission）** | 用户选择"仅此一次"，**应用重启后权限失效** |
| **Android 11** | **自动撤销权限** | 未使用的权限 3 个月后自动撤销（可通过 `autoRevokeWhitelist` 豁免） |
| **Android 11** | `MANAGE_EXTERNAL_STORAGE` | 访问所有文件需要特殊权限（见 [[存储分区机制]]） |
| **Android 12** | `BLUETOOTH_SCAN` / `BLUETOOTH_CONNECT` | 拆分了旧 `BLUETOOTH` / `BLUETOOTH_ADMIN` |
| **Android 12** | **启动时精确闹钟（`SCHEDULE_EXACT_ALARM`）** | 从 Android 13 起默认不授予 |
| **Android 13** | **`POST_NOTIFICATIONS`** | **运行时权限**，不发通知就不弹窗 |
| **Android 13** | **细分媒体权限** | `READ_EXTERNAL_STORAGE` 被 `READ_MEDIA_IMAGES/VIDEO/AUDIO` 替代；**不申请也能通过 Photo Picker 选图** |
| **Android 13** | 相册选择的"部分选择" | `READ_MEDIA_VISUAL_USER_SELECTED` |
| **Android 14** | **前台服务类型（`foregroundServiceType`）** | 必须声明具体类型，且各类型有启动限制 |
| **Android 14** | **"受限访问"（Restricted Access）** | 用户可把应用设为受限，**所有权限视为未授予** |
| **Android 15** | **强制边到边（Edge-to-edge）** | 与权限无关但影响布局 |

**Android 13+ 通知权限的最佳实践**：

```kotlin
// Android 13+：必须显式申请 POST_NOTIFICATIONS
if (Build.VERSION.SDK_INT >= Build.VERSION_CODES.TIRAMISU) {
    val granted = ContextCompat.checkSelfPermission(
        this, Manifest.permission.POST_NOTIFICATIONS
    ) == PackageManager.PERMISSION_GRANTED

    if (!granted) {
        // 在用户真正需要通知的场景（如开启消息提醒）时申请，而不是启动就申请
        notificationPermissionLauncher.launch(Manifest.permission.POST_NOTIFICATIONS)
    }
}
```

### 10. 权限申请的最佳实践（**面试话术 + 工程规范**）

```text
【黄金流程】

  1. 检查权限
     checkSelfPermission(perm) == GRANTED ?
        ├─ 是 → 继续业务流程
        └─ 否 ↓

  2. 判断是否需要解释
     shouldShowRequestPermissionRationale(perm)
        ├─ true  → 曾拒绝过 → 弹自定义解释 Dialog → 用户同意后 requestPermissions
        ├─ false + 从未申请过 → 直接 requestPermissions
        └─ false + 已经申请过 → 用户勾了"不再询问" → 只能引导去设置页
                                        （Intent(Settings.ACTION_APPLICATION_DETAILS_SETTINGS)）

  3. 处理回调
     onRequestPermissionsResult / ActivityResult 回调
        ├─ 授予 → 继续
        ├─ 拒绝但业务可降级 → 降级功能 + 解释
        └─ 拒绝且业务不可用 → 引导去设置 + 说明后果
```

**六条工程原则**：

1. **在需要时申请，不在启动时申请**：启动就弹权限框是差评的来源，也是审核不通过的原因。
2. **先解释后申请**：先告诉用户"为什么需要"，再弹系统框。用户拒绝后再次申请前，仍要解释。
3. **权限最小化**：只申请当前功能真正需要的权限。**能用 Photo Picker / SAF 就不要申请存储权限**。
4. **权限组整体处理**：知道同组权限会一起弹窗、一起授予。
5. **处理"不再询问"**：`shouldShowRequestPermissionRationale == false` 且已申请过 → **必须引导去设置**。
6. **处理权限被撤销**：每次进入关键功能时重新 `checkSelfPermission`，不要假设权限一直在。

**权限被永久拒绝的判断**（实用技巧）：

```kotlin
/**
 * ✅ 判断用户是否勾选了"不再询问"。
 * 原理：
 *   - 首次申请：requested=false, granted=false → 不需要解释（还没问过）
 *   - 拒绝一次：requested=true, granted=false, userFixed=false → 需要解释
 *   - 永久拒绝：userFixed=true → 不需要解释（不能再弹了）
 */
fun Activity.isPermanentlyDenied(permission: String): Boolean {
    val flags = packageManager.getPermissionFlags(permission, packageName)
    val requested = flags and PackageManager.FLAG_REQUESTED != 0
    val userFixed = flags and PackageManager.FLAG_USER_FIXED != 0
    val granted = ContextCompat.checkSelfPermission(this, permission) == PackageManager.PERMISSION_GRANTED
    return requested && !granted && userFixed
}
```

## 代码示例

### 1. 完整的权限管理封装（**生产级写法**）

```kotlin
/**
 * 权限请求封装：
 * - 统一的申请入口
 * - 自动处理"解释"与"不再询问"
 * - 支持多个权限的批量申请
 */
class PermissionManager(private val activity: ComponentActivity) {

    /** 待申请权限的回调 */
    private var pendingAction: ((Map<String, Boolean>) -> Unit)? = null

    private val launcher = activity.registerForActivityResult(
        ActivityResultContracts.RequestMultiplePermissions()
    ) { result ->
        val action = pendingAction
        pendingAction = null
        action?.invoke(result)
    }

    /**
     * 申请权限。
     * @param permissions 需要申请的权限
     * @param onResult   回调：Map<权限, 是否授予>
     */
    fun request(permissions: Array<String>, onResult: (Map<String, Boolean>) -> Unit) {
        val notGranted = permissions.filter {
            ContextCompat.checkSelfPermission(activity, it) != PackageManager.PERMISSION_GRANTED
        }

        if (notGranted.isEmpty()) {
            // 全部已授予
            onResult(permissions.associateWith { true })
            return
        }

        // 判断是否有需要解释的权限
        val needRationale = notGranted.any { activity.shouldShowRequestPermissionRationale(it) }

        if (needRationale) {
            // 曾经拒绝过：先解释
            showRationaleDialog(notGranted) {
                launch(notGranted, onResult)
            }
        } else {
            launch(notGranted, onResult)
        }
    }

    private fun launch(permissions: List<String>, onResult: (Map<String, Boolean>) -> Unit) {
        pendingAction = onResult
        launcher.launch(permissions.toTypedArray())
    }

    private fun showRationaleDialog(permissions: List<String>, onConfirm: () -> Unit) {
        MaterialAlertDialogBuilder(activity)
            .setTitle("需要相机权限")
            .setMessage("拍照需要访问相机权限，我们不会收集您的照片。")
            .setPositiveButton("继续") { _, _ -> onConfirm() }
            .setNegativeButton("取消", null)
            .show()
    }

    /** 引导用户去系统设置页（用于"不再询问"的情况） */
    fun openAppSettings() {
        val intent = Intent(Settings.ACTION_APPLICATION_DETAILS_SETTINGS).apply {
            data = Uri.fromParts("package", activity.packageName, null)
        }
        activity.startActivity(intent)
    }

    /** 判断是否已被永久拒绝（不能再弹系统框） */
    fun isPermanentlyDenied(permission: String): Boolean {
        val flags = activity.packageManager.getPermissionFlags(permission, activity.packageName)
        val requested = flags and PackageManager.FLAG_REQUESTED != 0
        val userFixed = flags and PackageManager.FLAG_USER_FIXED != 0
        val granted = ContextCompat.checkSelfPermission(activity, permission) == PackageManager.PERMISSION_GRANTED
        return requested && !granted && userFixed
    }
}
```

        }
    }

## 常见问题 / 面试要点

**读者问：Android 的权限有哪几类？危险权限有哪些？**

**AI答：**

1. **三类**：
   - **normal**：安装即自动授予，用户无感知（`INTERNET`、`ACCESS_NETWORK_STATE`、`VIBRATE`）；
   - **dangerous**：运行时授权，需要用户确认（相机、定位、麦克风、通讯录、电话、短信、日历、传感器等）；
   - **special/特殊管理**：通过**系统设置页**由用户手动开启（`SYSTEM_ALERT_WINDOW` 悬浮窗、`REQUEST_INSTALL_PACKAGES` 安装包、`MANAGE_EXTERNAL_STORAGE` 所有文件访问、`WRITE_SETTINGS` 修改系统设置）。
2. **危险权限（按权限组）**：
   - `CALENDAR`：`READ_CALENDAR`、`WRITE_CALENDAR`
   - `CAMERA`：`CAMERA`
   - `CONTACTS`：`READ_CONTACTS`、`WRITE_CONTACTS`、`GET_ACCOUNTS`
   - `LOCATION`：`ACCESS_FINE_LOCATION`、`ACCESS_COARSE_LOCATION`、`ACCESS_BACKGROUND_LOCATION`
   - `MICROPHONE`：`RECORD_AUDIO`
   - `PHONE`：`READ_PHONE_STATE`、`READ_PHONE_NUMBERS`、`CALL_PHONE`、`ANSWER_PHONE_CALLS`、`READ_CALL_LOG`、`WRITE_CALL_LOG`、`ADD_VOICEMAIL`、`USE_SIP`、`PROCESS_OUTGOING_CALLS`
   - `SENSORS`：`BODY_SENSORS`
   - `SMS`：`SEND_SMS`、`RECEIVE_SMS`、`READ_SMS`、`RECEIVE_WAP_PUSH`、`RECEIVE_MMS`
   - `STORAGE`（Android 13+ 已被 `READ_MEDIA_*` 替代）
   - `ACTIVITY_RECOGNITION`（Android 10+）
   - `NEARBY_DEVICES`：蓝牙相关（Android 12+）
   - `POST_NOTIFICATIONS`（Android 13+）
3. **必须强调**："**危险权限是按'权限组'管理的——同组权限一起弹窗、一起授权。比如申请了 `ACCESS_FINE_LOCATION`，用户同意后 `ACCESS_COARSE_LOCATION` 也会一起被授予。**"

---

**读者问：运行时权限的申请流程是什么？`shouldShowRequestPermissionRationale` 有什么用？**

**AI答：**

1. **流程**：
   ```
   checkSelfPermission(perm)
     ├─ GRANTED → 直接用
     └─ DENIED
          ├─ shouldShowRequestPermissionRationale(perm)
          │    ├─ true  → 用户拒绝过（但没勾"不再询问"）→ 先弹自定义解释 Dialog → 同意后 requestPermissions
          │    ├─ false + 从未申请 → 直接 requestPermissions（系统会弹框）
          │    └─ false + 已申请过 → 用户勾了"不再询问" → **系统不再弹框**，只能引导去设置页
          └─ requestPermissions(perms, requestCode)
               └─ onRequestPermissionsResult / ActivityResult 回调
   ```
2. **`shouldShowRequestPermissionRationale` 的语义**（这是最容易答错的地方）：
   - **`true`**：**用户曾经拒绝过这个权限**，且**没有**勾选"不再询问"。此时再次调用 `requestPermissions` **仍会弹系统框**（但先解释一下体验更好）。
   - **`false`**：两种情况——**从未申请过**（第一次，直接申请即可）；**用户勾了"不再询问"**（**再申请也不会弹框**，只能去设置页）。
   - **区分这两种 `false`**：用 `PackageManager.getPermissionFlags()` 看 `FLAG_REQUESTED` 和 `FLAG_USER_FIXED`。
3. **`special` 权限（如 `SYSTEM_ALERT_WINDOW`）**：`shouldShowRequestPermissionRationale` **永远返回 false**，因为它们不是运行时权限，**必须跳 `Settings.ACTION_MANAGE_OVERLAY_PERMISSION` 让用户手动开**。
4. **面试话术**："**`shouldShowRequestPermissionRationale` 的返回值不是简单的'要不要解释'，它是'用户是不是拒绝过但还愿意再给机会'。正确的产品逻辑是：true → 解释后再申请；false 且已申请过 → 引导去设置；false 且首次 → 直接申请。**"

---

**读者问：权限被撤销了怎么知道？有哪些情况会导致权限被撤销？**

**AI答：**

1. **撤销的情况**：
   - **用户手动在设置里撤销**；
   - **Android 11+ 的自动撤销**：权限授予 3 个月未被使用 → 系统自动撤销（可用 `android:autoRevokeWhitelist` 豁免）；
   - **权限降级**：用户把精确位置改成"大致位置" → `ACCESS_FINE_LOCATION` 被撤销，只保留 `ACCESS_COARSE_LOCATION`；
   - **Android 14 的"受限访问"**：用户把应用设为受限 → 所有权限视为未授予；
   - **卸载重装**：权限全部重置。
2. **检测方式（推荐顺序）**：
   - **首选：每次进入关键功能时重新 `checkSelfPermission`**——最简单、最可靠、零成本；
   - **辅助：`ContentObserver` 监听权限授予表变化**（`/data/system/packages.xml`）——实现复杂、ROM 差异大，不可靠；
   - **Android 11+ 的 `PackageManager.addOnPermissionsChangeListener`**——但它是 **`@SystemApi`/隐藏 API**，普通应用不可用。
3. **处理方式**：
   - **降级而不是崩溃**：切换到"无权限状态"的 UI（占位图 + 提示）；
   - **引导用户去设置**：`Settings.ACTION_APPLICATION_DETAILS_SETTINGS`；
   - **不要静默失败**：用户会遇到"功能莫名其妙不能用"，体验极差。
4. **面试加分**："**权限是'动态状态'不是'一次性授予'。工程上正确的姿势是：把权限检查做成一个统一的入口函数，每次调用敏感功能前都过一遍这个函数，而不是在启动时检查一次然后假设权限一直在。**"

---

**读者问：权限组（permission group）是什么？为什么申请一个权限会连带授予其他权限？**

**AI答：**

1. **定义**：系统把语义相关的权限归为一组（如 `CAMERA`、`LOCATION`、`CONTACTS`、`PHONE`、`SMS`、`STORAGE`、`NOTIFICATIONS`）。每个权限在 Manifest 中都通过 `android:permissionGroup` 关联到某个组。
2. **行为**：
   - **同组权限在一次弹窗中一起呈现**，用户一次决定；
   - **`requestPermissions` 传入同组的多个权限，只弹一个框**；
   - **用户同意后，同组的权限全部被授予**（即使你只申请了其中一个）；
   - **系统框的文案也是按组生成的**（"允许 XX 访问相机和麦克风？"）。
3. **实际影响**：
   - 如果你申请 `ACCESS_FINE_LOCATION`，用户同意后 `ACCESS_COARSE_LOCATION` 也被授予；
   - 如果你同时申请 `CAMERA` 和 `RECORD_AUDIO`（不同组），会弹**两个**框；
   - 应用可以通过 `<uses-permission-group>` 声明"本应用的核心功能依赖哪个权限组"，系统会据此调整弹窗展示。
4. **自定义权限组**：应用可以通过 `<permission-group android:name="...">` 定义自己的组，**但不能改变系统权限的分组**。
5. **面试话术**："**权限组是系统为了让弹窗'一次决策'而做的语义聚合。知道这一点很重要——如果你在一次请求里混了三个组，用户会连续看到三个弹窗，转化率会下降。更好的做法是按组分批请求，或者用 `ActivityResultContracts` 的组合契约（如 `TakePicture`）让系统帮你合并。**"

---

**读者问：自定义权限怎么定义？`signature` 级别是什么意思？**

**AI答：**

1. **定义**（在 `<manifest>` 中）：
   ```xml
   <permission
       android:name="com.example.permission.READ_USER_DATA"
       android:description="@string/desc"
       android:label="@string/label"
       android:protectionLevel="signature" />
   ```
2. **保护级别**：
   - **`normal`**：安装即授予，不安全；
   - **`dangerous`**：运行时申请；
   - **`signature`**：**只有使用与权限定义者相同签名证书的应用**才能获得（系统会自动校验签名）。**最安全的自定义权限级别**；
   - **`signature|privileged`**：相同签名 **或** 预装为系统应用；
   - 可组合：`dangerous|signature`。
3. **典型用途**：
   - **保护自己的组件**（Service/Provider/Receiver）：`<service android:permission="com.example.permission.X" android:exported="true" />`；
   - **SDK 的授权机制**：第三方 SDK 定义 `signature` 权限，只有用 SDK 方证书签名的应用才能获得——防止 SDK 被盗用。
4. **注意事项**：
   - 权限**一旦发布就很难改**（改保护级别需要用户重新安装）；
   - `signature` 权限**同签名即可自动授予**，**不需要运行时申请**（因为系统按签名判定）；
   - 使用自定义权限的组件，**调用方必须显式声明 `uses-permission`**，否则会被拒绝（`SecurityException`）。
5. **加分**："**第三方 SDK 保护自己的能力不被盗用的标准做法，就是用 `signature` 级自定义权限——这样即使别人反编译了你的 APK，也无法直接调用你的 SDK 能力，因为签名对不上。**"

---

**读者问：Android 13+ 的通知权限有什么变化？该怎么处理？**

**AI答：**

1. **变化**：Android 13（API 33）引入 **`POST_NOTIFICATIONS`** 作为**运行时权限**。未授予时，**所有通知都不会展示**（不是延迟展示，是完全不展示）。
2. **关键细节**：
   - **系统会自动弹一次**：升级到 Android 13 后首次启动，系统会**自动弹一次通知权限框**（由系统控制，App 无法控制时机）；
   - **App 主动申请**：升级后用户如果拒绝过，App 仍可在合适时机用 `requestPermissions` 再次申请（系统会再弹一次）；
   - **通知渠道（Notification Channel）**：Android 8.0 引入，**权限在渠道级别上也可能被用户单独关闭**（用户在系统设置的"通知"里可以逐渠道关）。
3. **最佳实践**：
   - **不要在启动时申请**——等用户真正开启某类提醒时再申请；
   - **提供降级**：没通知权限也要能用（用应用内消息中心）；
   - **渠道细分**：把"营销推送"和"订单通知"分成不同渠道，让用户能精细控制。
4. **代码**：
   ```kotlin
   if (Build.VERSION.SDK_INT >= Build.VERSION_CODES.TIRAMISU) {
       requestPermissionLauncher.launch(Manifest.permission.POST_NOTIFICATIONS)
   }
   ```
5. **面试话术**："**通知权限是 Android 13 之后所有 App 都必须面对的'合规门槛'。它和相机定位不同——它不影响核心功能，只影响触达能力。所以正确的策略是'不申请也不崩、降级可用、在用户主动订阅时申请'。**"

---

**读者问：Android 11+ 的分区存储对权限有什么影响？**

**AI答：**

1. **Android 10（targetSdk 29+）引入 Scoped Storage（分区存储）**：
   - **不再需要 `READ_EXTERNAL_STORAGE` / `WRITE_EXTERNAL_STORAGE`** 就能读写自己创建的文件和通过 `MediaStore` 添加的媒体；
   - 应用**只能看到自己的目录 + 共享集合（图片/视频/音频/下载）**；
   - 直接用 `File` API 访问其他应用的文件会失败。
2. **Android 11（targetSdk 30+）**：
   - **强制执行分区存储**（targetSdk 29 及以下还能通过 `requestLegacyExternalStorage` 临时豁免，**Android 11 起该属性被忽略**）；
   - 引入 **`MANAGE_EXTERNAL_STORAGE`**（"所有文件访问权限"），需要用户手动在设置里开启；
   - 文件访问方式进一步收紧（`MediaStore` 的 `IS_PENDING`、不能直接改 `ContentResolver` 的 `DATE_MODIFIED` 等）。
3. **Android 13（targetSdk 33+）**：
   - **细分媒体权限**：`READ_MEDIA_IMAGES`、`READ_MEDIA_VIDEO`、`READ_MEDIA_AUDIO` 替代 `READ_EXTERNAL_STORAGE`；
   - **Photo Picker**：用户通过系统照片选择器选图时，**App 不需要任何媒体权限**。
4. **最佳实践**：
   - **优先用 SAF（`ACTION_OPEN_DOCUMENT`）和 Photo Picker**——**零权限**；
   - 必须长期访问整个图库时才申请 `READ_MEDIA_*`；
   - 确实需要全文件访问（如文件管理器、备份工具）才申请 `MANAGE_EXTERNAL_STORAGE`（**Google Play 有额外的审核要求**）。
5. **详见** [[存储分区机制]]。

**读者问：怎么判断用户是"拒绝了一次"还是"勾选了不再询问"？**

**AI答：**

1. **两个信号组合判断**：
   ```kotlin
   val flags = packageManager.getPermissionFlags(permission, packageName)
   val requested = flags and PackageManager.FLAG_REQUESTED != 0
   val userFixed = flags and PackageManager.FLAG_USER_FIXED != 0
   val granted = ContextCompat.checkSelfPermission(this, permission) == PackageManager.PERMISSION_GRANTED

   when {
       granted -> "已授权"
       !requested -> "从未申请"           // 系统会弹框
       userFixed -> "永久拒绝（不再询问）"  // 只能去设置
       else -> "拒绝过一次"               // 还能再弹框
   }
   ```
2. **标志位说明**：
   - **`FLAG_REQUESTED`**：用户是否已经对该权限做过选择（无论同意还是拒绝）；
   - **`FLAG_USER_FIXED`**：用户是否勾选了"不再询问"（此时 `shouldShowRequestPermissionRationale` 返回 false）；
   - **`FLAG_USER_SET`**：用户明确同意；
   - **`FLAG_ONE_TIME`**：一次性权限（Android 6.0），App 重启后失效。
3. **与 `shouldShowRequestPermissionRationale` 的关系**：
   - `shouldShowRequestPermissionRationale == true` ⟺ "拒绝过一次但没勾不再询问"；
   - `shouldShowRequestPermissionRationale == false` 且 `requested == true` ⟺ **永久拒绝**；
   - `shouldShowRequestPermissionRationale == false` 且 `requested == false` ⟺ **从未申请**。
4. **产品动作**：
   - "拒绝过一次" → **再次申请前先解释**（转化率更高）；
   - "永久拒绝" → **只能引导去设置页**，要明确告诉用户"去设置里开启 XX 权限"。
5. **面试加分**："**这是一个很多 App 做错的地方——把 `shouldShowRequestPermissionRationale == false` 一律当成'首次申请'，结果用户勾了'不再询问'之后 App 还在反复调 `requestPermissions`，系统再也不弹框，用户就永远用不了功能。**"

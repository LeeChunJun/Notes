# 安全基础

## 一句话定义

Android 安全的四条防线是：**组件导出边界（谁可以调我）→ 代码与资源的混淆加固（不让看懂）→ 运行时环境检测（不让 hooking）→ 数据与通信的加密保护（不让拿到）**。技术手段只能**提高攻击成本**而不能绝对防御，因此现代 Android 安全的思路是"**纵深防御 + 合规优先**"，而不是"某个加密算法够强"。

## 核心原理

### 1. 四大组件的导出安全（**最基础也最常被忽略**）

```text
【Android 组件的默认导出规则】
  · 声明了 <intent-filter> → 默认 exported = true
  · 未声明 <intent-filter>   → 默认 exported = false

  ⚠️ Android 12（API 31）起：只要声明了 <intent-filter>，
     就必须显式写 android:exported="true"/"false"，
     否则安装时直接报错（Manifest merger failed）
```

#### 1.1 四组件的风险矩阵

| 组件 | 导出后的风险 | 防护手段 |
| --- | --- | --- |
| **Activity** | 未授权页面被直接拉起（**绕过登录/权限校验**）；`intent` 中的参数被伪造 | `exported="false"` + 自定义 `permission`；**在 `onCreate` 里校验来源** |
| **Service** | 未授权调用后台服务（触发数据上传、执行命令） | `exported="false"`；`android:permission` |
| **BroadcastReceiver** | 接收伪造广播触发逻辑（如"修改设置"、"发通知"） | `exported="false"`；**动态注册的 receiver 必须用 `RECEIVER_NOT_EXPORTED`（API 33+）** |
| **ContentProvider** | 读写私有数据（数据库、文件）；**`provider` 的 `exported` 默认值取决于 `targetSdk`** | `exported="false"`；`android:readPermission` / `writePermission` |

```xml
<!-- ✅ 安全的组件声明 -->
<activity
    android:name=".ui.MainActivity"
    android:exported="true">                     <!-- 需要被 Launcher 启动 -->
    <intent-filter>
        <action android:name="android.intent.action.MAIN" />
        <category android:name="android.intent.category.LAUNCHER" />
    </intent-filter>
</activity>

<activity
    android:name=".ui.PayActivity"
    android:exported="false" />                  <!-- ❌ 绝不能导出 -->

<service
    android:name=".service.SyncService"
    android:exported="false"
    android:permission="com.myapp.permission.SYNC" />

<receiver
    android:name=".receiver.BootReceiver"
    android:exported="true"
    android:permission="android.permission.RECEIVE_BOOT_COMPLETED">
    <intent-filter>
        <action android:name="android.intent.action.BOOT_COMPLETED" />
    </intent-filter>
</receiver>

<!-- ✅ 自定义 signature 级别权限：只有同签名的应用能访问 -->
<permission
    android:name="com.myapp.permission.SYNC"
    android:protectionLevel="signature" />
```

#### 1.2 `PendingIntent` 的三个坑（**高频考点**）

```kotlin
/**
 * ✅ PendingIntent 安全写法
 */
object PendingIntentFactory {

    /**
     * ⚠️ 坑一：必须显式指定 FLAG_IMMUTABLE（Android 12+ 强制）
     *    FLAG_MUTABLE 会让接收方可以修改原始 Intent 的内容 → 提权漏洞
     */
    fun immutableBroadcast(context: Context, requestCode: Int): PendingIntent {
        val intent = Intent(context, MyReceiver::class.java).apply {
            action = "com.myapp.ACTION_SYNC"
        }
        return PendingIntent.getBroadcast(
            context,
            requestCode,
            intent,
            PendingIntent.FLAG_UPDATE_CURRENT or PendingIntent.FLAG_IMMUTABLE
        )
    }

    /**
     * ⚠️ 坑二：requestCode 必须唯一
     *    相同 requestCode 会覆盖之前的 PendingIntent → 触发错乱的逻辑
     *    做法：用 intent 的 action 或 data 的 hashCode 作为 requestCode
     */
    fun uniqueRequestCode(intent: Intent): Int =
        (intent.action.hashCode() xor intent.data?.hashCode() ?: 0) and 0x7FFFFFFF

    /**
     * ⚠️ 坑三：exported 的 PendingIntent 相当于"把你的权限借出去"
     *    任何应用都能通过它启动你未导出的组件（隐式提权）
     *    → 需要暴露时用显式 Intent + 最小权限
     */
    fun explicitPendingIntent(context: Context, cls: Class<*>): PendingIntent {
        val intent = Intent(context, cls)
        return PendingIntent.getActivity(
            context, 0, intent,
            PendingIntent.FLAG_UPDATE_CURRENT or PendingIntent.FLAG_IMMUTABLE
        )
    }
}
```

#### 1.3 隐式 Intent 的注入风险

```kotlin
/**
 * ✅ 导出 Activity 必须校验 intent 来源

class DeepLinkActivity : Activity() {

    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)

        // ⚠️ 绝不能信任 intent 的 extras —— 外部应用可以伪造
        val rawUrl = intent.getStringExtra("url")

        url != null && TRUSTED_HOSTS.any { url.startsWith("https://$it/") }

        private val TRUSTED_HOSTS = setOf("myapp.com", "api.myapp.com")
        private val ALLOWED_COMPONENTS = mapOf(
            "profile" to ProfileActivity::class.java,
            "settings" to SettingsActivity::class.java
        )
    }
}
```

### 2. 代码混淆：ProGuard / R8

#### 2.1 混淆能防什么、不能防什么

```text
【混淆的能力边界】
  ✅ 能提高逆向门槛：
     · 类名/方法名/字段名不可读
     · 字符串常量可加密
     · 控制流可混淆
     · 资源名可混淆（AndResGuard）

  ❌ 不能防御：
     · 运行时动态行为（Frida hook 一切）
     · 网络抓包（除非用了 SSL Pinning）
     · 本地数据被读（除非用了 Keystore + 加密）
     · 逻辑被绕过（除非服务端做校验）
     · Root 设备上的内存读取

  ⚠️ 核心认知：**混淆是"增加成本"，不是"建立边界"。真正的边界必须在服务端。**
```

#### 2.2 字符串加密

```kotlin
/**
 * ✅ 字符串加密：编译期把明文替换成密文 + 运行时解密
 * 原理：
 *   · 编译期（Gradle Transform/字节码处理）把所有 String 常量替换为
 *     XorDecrypt("明文", key).toString()
 *   · 运行时调用解密方法还原
 * 收益：静态分析（jadx）看不到明文
 */
object StringEncrypt {

    /**
     * ✅ XOR 解密（实现可自行加固：加壳、字节码变换、多层）
     */
    fun decrypt(encrypted: ByteArray, key: ByteArray): String {
        val result = ByteArray(encrypted.size)
        for (i in encrypted.indices) {
            result[i] = (encrypted[i].toInt() xor key[i % key.size].toInt()).toByte()
        }
        return String(result, Charsets.UTF_8)
    }

    /**
     * ✅ 编译期生成的调用形式（由 Gradle 插件自动替换字符串常量）
     *    StringEncrypt.decrypt(byteArrayOf(0x1A, 0x2B), byteArrayOf(0x5F))
     */
    fun decrypt(encrypted: ByteArray, key: ByteArray): ByteArray {
        val result = ByteArray(encrypted.size)
        for (i in encrypted.indices) {
            result[i] = (encrypted[i].toInt() xor key[i % key.size].toInt()).toByte()
        }
        return result
    }
}
```

```text
【进阶加固手段】
  ① 控制流混淆（Ollvm / OLLVM-like）：把 if/else 改成不透明谓词
  ② 代码块分割（插入垃圾指令打断反编译器的控制流分析）
  ③ 函数隐藏（把方法体抽到 native）
  ④ VMP 虚拟化（把字节码解释到自定义虚拟机里）—— 强度最高、成本也最高
```

### 3. 应用加固

#### 3.1 APK 签名（**必考，四代签名**）

| 版本 | 引入 | 机制 | 解决的问题 |
| --- | --- | --- | --- |
| **v1（JAR Signing）** | Android 1.0 | 对每个文件单独计算 SHA-1 摘要，写入 `META-INF/*.SF` 和 `*.RSA` | 校验完整性；**不能防止整体替换**（可删旧签名加新签名） |
| **v2（APK Signature Scheme v2）** | Android 7.0（API 24） | 在 ZIP 中央目录前插入 **APK Signing Block**，签名覆盖整个 ZIP 内容 | **防整体替换**（改任何一个字节签名都失效）；**安装速度更快**（v1 要逐文件校验） |
| **v3（APK Signature Scheme v3）** | Android 9（API 28） | 引入 **key rotation**（密钥轮换）：新旧签名共存，用户可从旧版升级 | 支持密钥轮换（APK 签名密钥泄露后可换新）；支持 **APK Signature Scheme v3.1**（API 33+，限定 targetSdk） |
| **v4（APK Signature Scheme v4）** | Android 11（API 30） | **独立的签名文件**（`*.idsig`），签名 **APK 的分块哈希** | 支持 **adb incremental install**（增量安装，几秒完成） |

```text
【签名算法】
  v1/v2/v3：SHA-256（或 SHA-1）+ RSA / ECDSA / DSA
  签名内容：证书 + 公钥 + 摘要
  校验者：PackageManagerService（安装时）与 PackageManager（运行时）

【多签名（multi-signature）】
  · v3 引入：APK 可以同时有多个签名者
  · 用途：应用由多个开发者/组织共同签名
  · 校验规则：只要所有签名者都有效即通过
```

```bash
# ✅ 查看 APK 的签名信息
apksigner verify --verbose --print-certs app-release.apk

# ✅ 分别看 v2/v3 是否启用
apksigner verify --verbose app-release.apk | grep -E "v1|v2|v3"

# ✅ 用 keytool 看证书
keytool -printcert -jarfile app-release.apk

# ✅ 用 jarsigner 签名（v1）
jarsigner -verbose -sigalg SHA256withRSA -digestalg SHA-256 \
  -keystore my.jks -storepass xxx app.apk alias
```

#### 3.2 防二次打包

```kotlin
/**
 * ✅ 防二次打包：运行时校验签名
 */
object SignatureVerifier {

    /**
     * ✅ 校验当前 APK 的签名是否与预期一致
     */
    fun verify(context: Context): Boolean {
        val packageManager = context.packageManager
        val packageName = context.packageName

        // ✅ 获取当前签名
        val signatures = if (Build.VERSION.SDK_INT >= Build.VERSION_CODES.P) {
            val info = packageManager.getPackageInfo(
                packageName, PackageManager.GET_SIGNING_CERTIFICATES
            )
            info.signingInfo?.apkContentsSigners
        } else {
            @Suppress("DEPRECATION")
            packageManager.getPackageInfo(packageName, PackageManager.GET_SIGNATURES).signatures
        } ?: return false

        // ✅ 与内置的期望值比对（期望值本身要加密存储）
        val expected = EXPECTED_SIGNATURES
        return signatures.any { sig ->
            expected.any { expectedSig ->
                MessageDigest.getInstance("SHA-256")
                    .digest(sig.toByteArray())
                    .contentEquals(expectedSig)
            }
        }
    }

    /**
     * ✅ 校验 APK 文件本身的完整性（防止二次打包后重签名）
     */
    fun verifyApkIntegrity(context: Context): Boolean {
        val apkPath = context.applicationInfo.sourceDir
        val digest = MessageDigest.getInstance("SHA-256")
        FileInputStream(apkPath).use { input ->
            val buffer = ByteArray(8192)
            while (true) {
                val read = input.read(buffer)
                if (read <= 0) break
                digest.update(buffer, 0, read)
            }
        }
        // 与服务端下发的期望值比对
        return digest.digest().contentEquals(EXPECTED_APK_HASH)
    }
}
```

> [!warning] **防御的局限**
> 签名校验防不住**Root 设备 + Frida 改返回值**。真正的防线是**服务端校验关键操作**（如支付、会员状态的二次校验）。

#### 3.3 防调试（**原理题**）

```text
【三种防调试手段】
  ① ptrace 自查（TracerPid）
     · 原理：一个进程只能被一个 tracer 附加
     · 自查方式：以子进程调用 ptrace(PTRACE_TRACEME)，
       如果返回 -1 说明已有 debugger 附加（父进程已被 trace）
     · 简单实现：检查 /proc/self/status 的 TracerPid 字段
       TracerPid != 0 → 有人附加了 debugger

  ② /proc/self/status 的 TracerPid
     · 正常：TracerPid: 0
     · 被调试：TracerPid: <pid>
     · ⚠️ 简单可绕过（改字段 / 直接改内存）

  ③ Debug.isDebuggerConnected() / Debug.waitingForDebugger()
     · Android 提供的官方 API
     · ⚠️ 同样可被 hook 绕过
```

```kotlin
/**
 * ✅ 防调试检测（多层次）
 */
object AntiDebug {

    /**
     * ① 检查 TracerPid
     */
    fun isBeingTraced(): Boolean {
        return try {
            File("/proc/self/status").useLines { lines ->
                lines.firstOrNull { it.startsWith("TracerPid:") }
                    ?.substringAfter(":")
                    ?.trim()
                    ?.toIntOrNull()?.let { it != 0 } ?: false
            }
        } catch (e: Exception) {
            false
        }
    }

    /**
     * ② ptrace 自查（经典的"双保险"）
     */
    fun ptraceSelf(): Boolean {
        return try {
            // ⚠️ 这个 ptrace 必须由子进程调用
            val pid = android.os.Process.myPid()
            val status = Runtime.getRuntime().exec(
                "su -c 'cat /proc/$pid/status'"
            ).inputStream.bufferedReader().readText()
            status.contains("TracerPid:\t0").not()
        } catch (e: Exception) {
            false
        }
    }

    /**
     * ③ 检查调试器相关属性
     */
    fun hasDebugProperties(): Boolean {
        return android.os.Debug.isDebuggerConnected() ||
                android.os.Debug.waitingForDebugger()
    }

    /**
     * ④ 检测 Frida / Xposed 的痕迹（更实用）
     */
    fun hasHookFramework(): Boolean {
        // 检查运行时的 classloader
        val classLoader = AntiDebug::class.java.classLoader
        val classNames = mutableListOf<String>()
        var loader: ClassLoader? = classLoader
        while (loader != null) {
            classNames.add(loader.toString())
            loader = loader.parent
        }
        // 检查 /proc/self/maps 里的可疑 so
        val maps = try {
            File("/proc/self/maps").readText()
        } catch (e: Exception) {
            ""
        }
        val suspicious = listOf(
            "frida", "xposed", "substrate", "libhoudini",
            "r2", "armadillo", "libvirbox"
        )
        return suspicious.any { maps.contains(it, ignoreCase = true) }
    }
}
```

#### 3.4 防 Frida / Xposed（**原理题必考**）

```text
【Frida 的工作原理】
  ① Frida Server（或 Gadget）以 root 身份运行在设备上
  ② 通过 adb 转发（forward）建立与目标进程的通信
  ③ 注入 frida-agent 到目标进程
  ④ Agent 加载后，使用 Dobby / AndroDefence 等做 Inline Hook：
     直接修改目标函数在内存中的机器码开头（mov rax, addr; jmp rax）
  ⑤ Java 层通过 JVMTI（Java Virtual Machine Tool Interface）
     替换 ArtMethod 的入口点（把 native_entry_point 换成自己的），
     实现 Java 方法的 Hook
  ⑥ JS 脚本通过 RPC 与 Agent 通信，动态 Hook 任意函数

  【关键结论】
  · Frida 依赖代码在内存中被修改 → 一切"内存完整性校验"都能检测
  · 但只要检测逻辑本身在进程内，Frida 也能 Hook 掉检测逻辑
  · → 真正的对抗是"检测代码不在目标进程里"（服务端 / native 层对抗）

【常见检测手段】
  ① 扫描 /proc/self/maps 是否有 frida-agent.so / libfrida.so
  ② 扫描 /proc/self/task/*/status 的 TracerPid
  ③ 检查 TCP 端口（27042 是 Frida 默认端口）
  ④ 枚举已加载模块（ElfReader / dl_iterate_phdr）
  ⑤ 检查 native 函数的 prologue 是否被改写（对比磁盘中的原始字节）
  ⑥ 检查 ART 内部结构是否被篡改（ArtMethod 的入口点是否在 .so 的合法范围内）
  ⑦ inline hook 检测：读取函数前 4 字节，判断是否是跳转指令

【Xposed / LSPosed 的工作原理】
  ① 修改 Zygote 的启动流程（ZygoteInit / app_process）
  ② 在类加载时劫持 ClassLoader，改写 findClass / loadClass
  ③ 在方法入口注入 trampoline，替换 ArtMethod
  ④ 全局 Hook 框架（XposedBridge.hookMethod）

  【检测手段】
  ① 检查 XposedBridge / XposedHelpers 类是否存在（用 Class.forName 试探）
  ② 检查 /system/framework/XposedBridge.jar、/system/app/Superuser.apk
  ③ 检查 de.robv.android.xposed.* 包
  ④ 检查 LSPosed 的 magisk 模块目录
  ⑤ 检查 Zygote 的父进程 / cmdline 是否被修改
```

```kotlin
/**
 * ✅ Frida 检测的实用实现
 */
class FridaDetector(private val context: Context) {

    private val suspiciousFiles = listOf(
        "/data/local/tmp/frida-server",
        "/data/local/tmp/re.frida.server",
        "/data/local/tmp/frida",
        "/usr/local/lib/frida",
        "/system/app/Superuser.apk",
        "/system/framework/XposedBridge.jar",
        "/system/lib/libXposedBridge.so",
        "/system_ext/framework/XposedBridge.jar"
    )

    /**
     * ① 文件路径检测
     */
    fun checkFiles(): Boolean = suspiciousFiles.any { File(it).exists() }

    /**
     * ② /proc/self/maps 检测
     */
    fun checkMaps(): Boolean {
        val maps = try {
            File("/proc/self/maps").readText()
        } catch (e: Exception) {
            return false
        }
        val keywords = listOf("frida", "gadget", "xposed", "riru", "zygisk")
        return keywords.any { maps.contains(it, ignoreCase = true) }
    }

    /**
     * ③ 端口检测（Frida 默认 27042）
     */
    fun checkPorts(): Boolean {
        return try {
            // 尝试连接 Frida 默认端口
            java.net.Socket().use { socket ->
                socket.connect(java.net.InetSocketAddress("127.0.0.1", 27042), 200)
                true
            }
        } catch (e: Exception) {
            false
        }
    }

    /**
     * ④ 运行时 Hook 框架检测
     */
    fun checkHookFrameworks(): Boolean {
        val classes = listOf(
            "de.robv.android.xposed.XposedBridge",
            "org.lsposed.lspd.core.Main",
            "com.saurik.substrate.MSUBSTITUTE"
        )
        return classes.any { className ->
            try {
                Class.forName(className, false, context.classLoader)
                true
            } catch (e: ClassNotFoundException) {
                false
            }
        }
    }

    /**
     * ✅ 综合检测：任一命中即判定为风险环境
     */
    fun isCompromised(): Boolean =
        checkFiles() || checkMaps() || checkPorts() || checkHookFrameworks()
}
```

### 4. Root / 模拟器检测

```kotlin
/**
 * ✅ Root 与模拟器检测
 */
class EnvironmentDetector(private val context: Context) {

    /**
     * ① Root 检测：多条线索综合判断（单条都容易被绕过）
     */
    fun isRooted(): Boolean {
        return hasRootBinaries() || hasRootApps() || hasSuProperty() || isRWSystem()
    }

    private fun hasRootBinaries(): Boolean {
        val paths = arrayOf(
            "/system/bin/su", "/system/xbin/su", "/sbin/su",
            "/system/sd/xbin/su", "/data/local/xbin/su", "/data/local/bin/su",
            "/system/bin/daemonsu", "/su/bin/su"
        )
        return paths.any { File(it).exists() }
    }

    private fun hasRootApps(): Boolean {
        val packages = arrayOf(
            "com.noshufou.android.su",
            "com.thirdparty.superuser",
            "eu.chainfire.supersu",
            "com.koushikdutta.superuser",
            "com.topjohnwu.magisk",
            "com.kingroot.kingroot",
            "com.zhiqupk.root.global"
        )
        return packages.any {
            try {
                context.packageManager.getPackageInfo(it, 0)
                true
            } catch (e: PackageManager.NameNotFoundException) {
                false
            }
        }
    }

    private fun hasSuProperty(): Boolean {
        val props = arrayOf("ro.build.tags", "ro.debuggable", "ro.secure")
        return props.any {
            try {
                val value = SystemProperties.get(it)
                value == "test-keys" || (it == "ro.debuggable" && value == "1")
            } catch (e: Exception) {
                false
            }
        }
    }

    private fun isRWSystem(): Boolean {
        val path = "/system"
        val runtime = Runtime.getRuntime()
        val process = runtime.exec("ls -ld $path")
        process.waitFor()
        // 尝试挂载为读写
        return try {
            runtime.exec("mount -o remount,rw $path").waitFor() == 0
        } catch (e: Exception) {
            false
        }
    }

    /**
     * ② 模拟器检测
     */
    fun isEmulator(): Boolean {
        return checkBuildProperties() || checkFiles() || checkSensor() || checkQemu()
    }

    private fun checkBuildProperties(): Boolean {
        val fields = mapOf(
            "ro.hardware" to listOf("goldfish", "ranchu", "vbox86p", "nox", "ttVM_x86"),
            "ro.product.model" to listOf("sdk", "Android SDK built for x86", "Emulator", "google_sdk"),
            "ro.kernel.qemu" to listOf("1"),
            "ro.product.device" to listOf("generic", "vbox86p", "nox", "emulator")
        )
        return fields.any { (key, values) ->
            val prop = SystemProperties.get(key)
            values.any { prop.contains(it, ignoreCase = true) }
        }
    }

    private fun checkFiles(): Boolean {
        val paths = arrayOf(
            "/dev/socket/qemud", "/dev/qemu_pipe", "/system/lib/libc_malloc_debug_qemu.so",
            "/sys/qemu_trace", "/system/bin/qemu-props"
        )
        return paths.any { File(it).exists() }
    }

    private fun checkSensor(): Boolean {
        // 模拟器的传感器读数全是 0
        val sm = context.getSystemService(SensorManager::class.java)
        val sensor = sm.getDefaultSensor(Sensor.TYPE_ACCELEROMETER) ?: return false
        val values = FloatArray(3)
        sensor.getFloatValues(values)
        return values[0] == 0f && values[1] == 0f && values[2] == 0f
    }

    private fun checkQemu(): Boolean {
        return try {
            Runtime.getRuntime().exec("su -c 'ls /dev/qemu_pipe'")
                .inputStream.bufferedReader().readText().contains("qemu_pipe")
        } catch (e: Exception) {
            false
        }
    }
}
```

### 5. 网络安全

#### 5.1 证书校验与 SSL Pinning

```text
【默认的 TLS 校验做了什么】
  系统 TrustManager 校验：
  ① 证书链是否有效（由 CA 签发、未过期）
  ② 域名（CN / SAN）是否匹配
  ③ 是否在系统信任的 CA 列表里
  ❌ 漏洞：用户安装了自定义 CA（抓包代理）→ 校验通过 → 可被中间人
  ⚠️ Android 7+ 默认不再信任用户安装的 CA（除非 debug 包配置了 network_security_config）

【SSL Pinning 的三种实现】
  ① Certificate Pinning（证书固定）
     · 固定服务器的证书（或公钥）
     · ⚠️ 证书续期（Let's Encrypt 90 天）会导致失效 → 必须支持备用 pin
  ② Public Key Pinning（公钥固定）★ 推荐
     · 固定 SPKI（SubjectPublicKeyInfo）的 hash
     · 证书换了但公钥没换 → 不受影响
  ③ HPKP（已废弃）—— 不要用
```

```kotlin
/**
 * ✅ SSL Pinning：OkHttp + 自定义 TrustManager
 */
object CertificatePinner {

    /**
     * ✅ 备用 pin：主 pin 失效时用备用 pin（应对证书续期）
     */
    private val PINNED_CERTS = listOf(
        "sha256/AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA=",   // 主
        "sha256/BBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBB="   // 备用
    )

    fun createTrustManager(): X509TrustManager {
        val trustManager = Platform.get().trustManager
        return object : X509TrustManager {
            override fun checkClientTrusted(chain: Array<X509Certificate>, authType: String) = Unit
            override fun checkServerTrusted(chain: Array<X509Certificate>, authType: String) {
                // ✅ 先走系统默认校验（证书链 + 域名）
                trustManager.checkServerTrusted(chain, authType)

                // ✅ 再校验 pin
                val isPinned = chain.any { cert ->
                    val publicKey = cert.publicKey.encoded
                    val pin = "sha256/" + Base64.encodeToString(
                        MessageDigest.getInstance("SHA-256").digest(publicKey),
                        Base64.NO_WRAP
                    )
                    PINNED_CERTS.contains(pin)
                }
                if (!isPinned) {
                    throw SSLPeerUnverifiedException("证书未通过 Pin 校验")
                }
            }
            override fun getAcceptedIssuers(): Array<X509Certificate> =
                trustManager.acceptedIssuers
        }
    }

    /**
     * ✅ OkHttp 官方推荐：CertificatePinner
     */
    fun buildClient(): OkHttpClient {
        return OkHttpClient.Builder()
            .certificatePinner(
                CertificatePinner.Builder()
                    .add("api.myapp.com", "sha256/AAAA...")
                    .add("api.myapp.com", "sha256/BBBB...")
                    .build()
            )
            .build()
    }
}
```

### 6. 本地数据安全

#### 6.1 AES + Android Keystore

```text
【Android Keystore 的关键特性】
  · 密钥存放在系统级的安全硬件（TEE / StrongBox）里
  · 应用进程拿不到密钥的明文（只能请求系统用密钥做加解密）
  · 密钥与应用 UID 绑定 → 换应用（不同签名）用不了
  · 部分设备支持"用户认证后才可用"（setUserAuthenticationRequired）

【关键 API】
  KeyGenParameterSpec.Builder(alias, PURPOSE_ENCRYPT | PURPOSE_DECRYPT)
    .setBlockModes(BLOCK_MODE_GCM)      // ✅ GCM 同时提供加密与完整性校验
    .setEncryptionPaddings(ENCRYPTION_PADDING_NONE)
    .setKeySize(256)
    .setUserAuthenticationRequired(false)
    .setUnlockedDeviceRequired(true)    // API 28+：设备解锁后才可用
```

```kotlin
/**
 * ✅ 用 Android Keystore 保护本地数据
 */
class SecureStorage(private val context: Context) {

    private val keyAlias = "myapp_data_key"

    /**
     * ✅ 获取（或创建）保存在 Keystore 中的 AES 密钥
     * ⚠️ 密钥本身永远不出安全硬件
     */
    private fun getOrCreateKey(): SecretKey {
        val keyStore = KeyStore.getInstance("AndroidKeyStore").apply { load(null) }
        (keyStore.getKey(keyAlias, null) as? SecretKey)?.let { return it }

        val generator = KeyGenerator.getInstance(KeyProperties.KEY_ALGORITHM_AES, "AndroidKeyStore")
        generator.init(
            KeyGenParameterSpec.Builder(
                keyAlias,
                KeyProperties.PURPOSE_ENCRYPT or KeyProperties.PURPOSE_DECRYPT
            )
                .setBlockModes(KeyProperties.BLOCK_MODE_GCM)
                .setEncryptionPaddings(KeyProperties.ENCRYPTION_PADDING_NONE)
                .setKeySize(256)
                // ⚠️ Android 12+ 强烈建议：只在设备解锁后可用
                .setUnlockedDeviceRequired(true)
                .build()
        )
        return generator.generateKey()
    }

    /**
     * ✅ 加密并保存（IV 由 cipher 生成，必须一起存储）
     */
    fun encryptAndSave(key: String, plaintext: String) {
        val cipher = Cipher.getInstance("AES/GCM/NoPadding")
        cipher.init(Cipher.ENCRYPT_MODE, getOrCreateKey())
        val iv = cipher.iv
        val ciphertext = cipher.doFinal(plaintext.toByteArray(Charsets.UTF_8))

        // ⚠️ 每次加密的 IV 都不同，必须和密文一起存
        prefs().edit()
            .putString("$key.iv", Base64.encodeToString(iv, Base64.NO_WRAP))
            .putString("$key.data", Base64.encodeToString(ciphertext, Base64.NO_WRAP))
            .apply()
    }

    /**
     * ✅ 解密读取
     */
    fun decrypt(key: String): String? {
        val ivBase64 = prefs().getString("$key.iv", null) ?: return null
        val dataBase64 = prefs().getString("$key.data", null) ?: return null

        val cipher = Cipher.getInstance("AES/GCM/NoPadding")
        cipher.init(
            Cipher.DECRYPT_MODE,
            getOrCreateKey(),
            GCMParameterSpec(128, Base64.decode(ivBase64, Base64.NO_WRAP))
        )
        val plaintext = cipher.doFinal(Base64.decode(dataBase64, Base64.NO_WRAP))
        return String(plaintext, Charsets.UTF_8)
    }

    private fun prefs() =
        context.getSharedPreferences("secure_data", Context.MODE_PRIVATE)
}
```

### 7. 密钥管理（**红线**）

```text
【绝对不能做的事】
  ❌ 硬编码密钥在代码里
     private static final String API_KEY = "sk-xxxxx";
     → 反编译即得（R8 只是改名，字符串常量还在）

  ❌ 硬编码密钥在资源文件里
     strings.xml: <string name="api_key">sk-xxxxx</string>
     → 一样能解出来

  ❌ 硬编码密钥在 so 里（只是更难，不是不能）

  ❌ 用固定 IV 的 AES-CBC
     → 相同明文产生相同密文，可被字典攻击
     → 必须每次随机 IV

  ❌ 自己实现加密算法

【正确的做法】
  ① 服务端下发短期 token（配合设备指纹 + 时间戳 + 签名）
  ② 长期密钥用 Android Keystore 生成（不出安全硬件）
  ③ 密钥派生用 PBKDF2 / Argon2（存的是盐 + 派生结果，不是原密码）
  ④ 敏感数据"存半"：服务端存一部分，本地存另一半
  ⑤ 密钥分片：多个地方各存一部分，运行时拼接（增加静态分析成本）
  ⑥ 网络传输用 TLS 1.2/1.3 + (可选) Pinning
```

```kotlin
/**
 * ✅ 正确的密钥管理：服务端下发短期令牌 + Keystore 保护
 */
class TokenManager(private val context: Context) {

    private val secureStorage = SecureStorage(context)

    /**
     * ✅ 服务端下发短时效 token（带过期时间与设备绑定）
     */
    suspend fun refreshToken(): Boolean {
        val deviceId = DeviceIdUtil.get(context)
        val response = api.login(deviceId = deviceId)

        // ✅ 用 Keystore 保护 token 的存储
        secureStorage.encryptAndSave("auth_token", response.token)
        return true
    }

    /**
     * ✅ 从 Keystore 读取
     */
    fun getToken(): String? = secureStorage.decrypt("auth_token")
}
```

### 2. 反调试与 Frida 检测的完整实现

```kotlin
/**
 * ✅ 安全环境检测器：综合多维度信号
 */
class SecurityEnvironmentChecker(private val context: Context) {

    data class Report(
        val isRooted: Boolean,
        val isEmulator: Boolean,
        val isDebugged: Boolean,
        val hasHookFramework: Boolean,
        val isFridaPresent: Boolean
    ) {
        val riskLevel: String
            get() = when {
                isFridaPresent || hasHookFramework -> "HIGH"
                isDebugged -> "MEDIUM"
                isRooted || isEmulator -> "LOW"
                else -> "NONE"
            }
    }

    fun check(): Report = Report(
        isRooted = checkRoot(),
        isEmulator = checkEmulator(),
        isDebugged = checkDebugger(),
        hasHookFramework = checkHookFramework(),
        isFridaPresent = checkFrida()
    )

    /**
     * ✅ ① 防调试：TracerPid + ptrace 自查 + Debug API
     */
    private fun checkDebugger(): Boolean {
        // TracerPid
        val tracerPid = try {
            File("/proc/self/status").useLines { lines ->
                lines.first { it.startsWith("TracerPid:") }
                    .substringAfter(":").trim().toInt()
            }
        } catch (e: Exception) {
            0
        }
        if (tracerPid != 0) return true

        // 官方 API
        if (android.os.Debug.isDebuggerConnected()) return true
        if (android.os.Debug.waitingForDebugger()) return true

        // 检查调试器常见痕迹
        val debugProps = listOf("ro.debuggable", "ro.secure")
        val hasDebugProp = debugProps.any { prop ->
            try {
                SystemProperties.get(prop) == "1"
            } catch (e: Exception) {
                false
            }
        }
        return hasDebugProp
    }

    /**
     * ✅ ② Frida 检测：文件 + maps + 端口 + 线程名
     */
    private fun checkFrida(): Boolean {
        // 文件
        val fridaFiles = listOf(
            "/data/local/tmp/frida-server",
            "/data/local/tmp/re.frida.server",
            "/data/local/tmp/frida-agent-.so",
            "/data/local/tmp/.frida"
        )
        if (fridaFiles.any { File(it).exists() }) return true

        // /proc/self/maps
        val maps = try { File("/proc/self/maps").readText() } catch (e: Exception) { "" }
        if (maps.contains("frida", ignoreCase = true) ||
            maps.contains("gadget", ignoreCase = true)
        ) return true

        // 端口
        if (isPortOpen("127.0.0.1", 27042)) return true

        // 线程名（Frida 的 agent 线程）
        val threads = try {
            File("/proc/self/task").listFiles()?.mapNotNull { task ->
                try {
                    File(task, "comm").readText().trim()
                } catch (e: Exception) {
                    null
                }
            } ?: emptyList()
        } catch (e: Exception) {
            emptyList()
        }
        return threads.any { it.contains("gadget", ignoreCase = true) }
    }

    private fun isPortOpen(host: String, port: Int): Boolean = try {
        java.net.Socket().use { it.connect(java.net.InetSocketAddress(host, port), 300) }
        true
    } catch (e: Exception) {
        false
    }

    /**
     * ✅ ③ Hook 框架检测
     */
    private fun checkHookFramework(): Boolean {
        val xposedClasses = listOf(
            "de.robv.android.xposed.XposedBridge",
            "de.robv.android.xposed.XposedHelpers",
            "org.lsposed.lspd.core.Main"
        )
        if (xposedClasses.any {
                try {
                    Class.forName(it, false, context.classLoader); true
                } catch (e: Exception) { false }
            }
        ) return true

        val xposedFiles = listOf(
            "/system/framework/XposedBridge.jar",
            "/system/app/Superuser.apk",
            "/system_ext/framework/XposedBridge.jar",
            "/data/adb/modules/zygisk_lsposed"
        )
        return xposedFiles.any { File(it).exists() }
    }

    private fun checkRoot(): Boolean {
        val suPaths = listOf(
            "/system/bin/su", "/system/xbin/su", "/sbin/su",
            "/system/sd/xbin/su", "/data/local/xbin/su", "/data/local/bin/su"
        )
        if (suPaths.any { File(it).exists() }) return true
```

## 常见问题 / 面试要点

**读者问：应用被逆向怎么防？有哪些手段？**

**AI答：**

1. **先讲清楚能力边界**（这决定了回答的专业度）：
   - **能提高攻击成本**：混淆、字符串加密、完整性校验、运行时检测；
   - **不能绝对防御**：Root 设备 + Frida 可以 Hook 掉进程内的任何检测逻辑；
   - **真正的边界必须在服务端**：关键判断（会员、支付、积分）服务端做二次校验。
2. **分层手段**：
   - **代码层**：R8 混淆（类名/方法名不可读）+ `shrinkResources`；字符串加密（编译期替换 + 运行时解密）；控制流混淆；资源名混淆。
   - **完整性层**：运行时校验 APK 签名（防二次打包）；校验 so/dex 的完整性；校验关键方法的字节码是否被改写（inline hook 检测）。
   - **运行时层**：防调试（TracerPid / ptrace 自查 / `Debug.isDebuggerConnected`）；防 Frida（扫 `/proc/self/maps`、文件、端口 27042、线程名）；防 Xposed（类探测 + 文件探测）；Root / 模拟器检测。
   - **网络层**：TLS + SSL Pinning（阻断抓包与代理）；关键操作服务端校验。
3. **高级对抗（加分）**：
   - **VMP 虚拟化**（把关键逻辑跑在自实现的解释器里，Hook 的是虚拟机而不是原始函数）；
   - **代码存放在服务端**（最彻底的方案）；
   - **关键逻辑拆成多段 + 运行时拼接**（增加静态分析成本）；
   - **native 层做检测**（比 Java 层更难 Hook）。
4. **面试话术**："**我的观点是：客户端加固的目标不是'不可破解'，而是把攻击成本从'几小时'提高到'几周'，并配合服务端校验形成真正的闭环。纯客户端方案在有 Root 的设备上一定是可以绕过的。**"

---

**读者问：Frida 的原理是什么？怎么检测它？**

**AI答：**

1. **工作原理（五步）**：
   - ① Frida Server（root 运行）或 Frida Gadget（嵌入 APK）启动；
   - ② 通过 adb 端口转发（`adb forward tcp:27042 tcp:27042`）与目标进程通信；
   - ③ **注入 agent** 到目标进程；
   - ④ agent 用 **Inline Hook**（修改函数入口的机器码为跳转指令）Hook native 函数；用 **JVTI（JVMTI）** 替换 `ArtMethod` 的入口点 Hook Java 方法；
   - ⑤ JS 脚本通过 RPC 与 agent 通信，**动态 Hook 任意函数、读写任意内存**。
2. **检测手段（四类信号）**：
   - **文件**：`/data/local/tmp/frida-server`、`re.frida.server`、`frida-agent.so`；
   - **内存映射**：`/proc/self/maps` 中出现 `frida`、`gadget`；
   - **端口**：27042（Frida 默认）可连接；
   - **线程**：`/proc/self/task/*/comm` 中有 `gadget` 相关线程名；
   - **函数入口检查**：读取函数前几个字节，判断是否为跳转指令（inline hook 特征）。
3. **检测的局限（必须说）**：
   - Frida 可以 **Hook 掉你的检测函数**，让它返回"安全"；
   - 可以 **重命名 /proc 下的文件**（需要 root + 挂钩 libc）；
   - 新型的 Frida 版本会修改自身名字；
   - **所以纯客户端检测永远不是终点**。
4. **更强的对抗**：
   - **把检测放在 native 层 + 自己做 hook 检测**（inline hook 检测相对难绕过）；
   - **关键逻辑服务端化**（最彻底）；
   - **VMP 虚拟化**（Hook 的是解释器，攻击者需要理解并修改整个 VM，成本极高）；
   - **检测代码与被检测代码分离**（检测在独立进程或服务端）。
5. **面试话术**："**Frida 的核心是'在运行时改写代码'。所以检测的思路就是'检查我的代码有没有被改'——检查 maps、检查函数入口的字节码。绕过它也很容易，所以最终要靠服务端校验。**"

**读者问：怎样保护本地的密钥和数据？**

**AI答：**

1. **红线（先说不能做什么）**：
   - ❌ 密钥硬编码在代码或资源里（R8 只是改名，字符串常量还在）；
   - ❌ 固定的 IV（AES-CBC 固定 IV 会让相同明文产生相同密文）；
   - ❌ 自己实现加密算法；
   - ❌ 把 token 长期硬编码。
2. **正确做法**：
   - **① Android Keystore**：AES-GCM 密钥存在 TEE/StrongBox 里，**应用进程拿不到密钥明文**，只能请求系统加解密；密钥与 UID 绑定。
   - **② 每次加密用随机 IV**（GCM 的 `cipher.iv` 自动生成），**IV 必须和密文一起存**。
   - **③ 密钥轮换与版本管理**：换密钥时用 `keyAlias` 带版本号（`key_v1` → `key_v2`），解密时按版本尝试。
   - **④ 服务端下发短期凭证**（access token），配合设备指纹 + 时间戳 + 签名。
   - **⑤ 签名优先于加密**：需要证明"是我发的"时用 Keystore 里的 **ECDSA 私钥签名**（私钥同样不出安全硬件）。
   - **⑥ 网络传输**：TLS 1.2/1.3 + Pinning；敏感字段额外应用层加密。
3. **补充措施**：
   - **`FLAG_SECURE`** 防截屏录屏（也会让最近任务缩略图变空白）；
   - **`android:allowBackup="false"`** 禁止 `adb backup` 导出数据；
   - **`android:usesCleartextTraffic="false"`** + `network_security_config` 禁明文；
   - **不写日志**（尤其不要打印完整请求体、token、身份证）。
4. **面试话术**："**密钥保护的原则是'让密钥永远不需要出现在应用进程里'——Keystore 做到了这一点。对称加密用 AES-GCM，身份认证用 ECDSA 签名，长效凭证一律走服务端。**"

**读者问：四大组件的导出安全应该怎么做？有哪些坑？**

**AI答：**

1. **默认规则**：有 `<intent-filter>` → 默认 exported=true；没有 → false。**Android 12+ 必须显式声明**。
2. **四大组件各自的处置**：
   - **Activity**：只有 Launcher 和深链入口导出；**导出后必须校验 intent 参数**（防止参数注入、越权跳转）。
   - **Service**：**一律不导出**；需要跨应用调用时用 `signature` 级自定义权限。
   - **BroadcastReceiver**：静态注册的按需导出（BOOT_COMPLETED 需要系统权限）；**动态注册的必须用 `ContextCompat.RECEIVER_NOT_EXPORTED`（API 33+ 强制）**。
   - **ContentProvider**：默认 `exported` 与 `targetSdk` 相关（**targetSdk 17 及以下默认 true，18+ 默认 false**）；不导出 + 读写权限分离。
3. **三大坑**：
   - **① `PendingIntent`**：必须 `FLAG_IMMUTABLE`；requestCode 必须唯一；**导出的 PendingIntent 等于把权限借给外部**。
   - **② 隐式 Intent 注入**：外部可以伪造 `extras` 里的类名/URL → 必须做白名单校验。
   - **③ `android:grantUriPermissions`**：给了 `true` 又导出 provider，就等于开放了 URI 授权。
4. **自检手段**：
   - `aapt dump xmltree app.apk AndroidManifest.xml` 看导出属性；
   - **Android Lint** 的 `ExportedReceiver` / `IntentFilterExportedReceiver` 警告；
   - 第三方扫描工具（`androguard`、`apktool`）。
5. **面试话术**："**导出安全我会从'最小暴露面'讲：只导出必须的入口，其余全关；导出的一定加权限 + 参数白名单；PendingIntent 必须 IMMUTABLE。这三条能挡掉大部分组件暴露漏洞。**"

**读者问：APK 签名有哪几种版本？有什么区别？**

**AI答：**

1. | 版本 | 引入版本 | 核心机制 | 解决了什么 |
   | --- | --- | --- | --- |
   | **v1** | Android 1.0 | 对每个文件算 SHA-1，写入 `META-INF/*.SF` + `*.RSA` | 完整性校验；但**不能防止整体替换** |
   | **v2** | Android 7.0 | 在 ZIP 中央目录前插入 **APK Signing Block**，签名覆盖整个 ZIP | **防整体替换**；安装更快（不用逐文件校验） |
   | **v3** | Android 9 | 引入 **key rotation**（新旧签名共存）+ 多签名 | 支持密钥轮换；支持多组织共同签名 |
   | **v4** | Android 11 | **独立签名文件** `*.idsig`，签名分块哈希 | 支持 **adb 增量安装**（几秒完成） |
2. **v1 的缺陷（面试要能说清）**：
   - v1 只签名"文件内容摘要列表"，**没有覆盖 ZIP 的结构**；
   - 攻击者可以**删除旧的 META-INF 签名、添加新的签名**，APK 内容不变但签名变了 → **v1 挡不住二次打包**；
   - v2/v3 签名覆盖整个 APK（包括 ZIP 结构），改任何一个字节签名就失效。
3. **v3 的 key rotation**：
   - 新版本的签名可以声明"**由旧版本的签名密钥签发**"；
   - 设备上安装了旧版（用旧密钥签名）→ 可以直接升级到新版（用新密钥签名）；
   - 目的是**密钥泄露后可以换密钥而不强制用户重装**。
4. **校验时机**：
   - **安装时**：`PackageManagerService` 校验，不通过则拒绝安装；
   - **运行时**：`PackageManager.getPackageInfo(GET_SIGNING_CERTIFICATES)` 取当前签名，与期望值比对（防二次打包）。
5. **命令**：
   ```bash
   apksigner verify --verbose --print-certs app.apk
   apksigner sign --v1-signing-enabled true --v2-signing-enabled true --v3-signing-enabled true app.apk
   ```
6. **面试话术**："**v1 是逐文件签名，挡不住整体替换；v2 签名覆盖整个 APK，v3 在此基础上加了密钥轮换，v4 是为了增量安装单独出的签名文件。**"

**读者问：SSL Pinning 是什么？有什么风险？**

**AI答：**

1. **是什么**：在 TLS 握手时，除了系统的证书链校验，还额外校验服务器的**证书公钥指纹（SPKI hash）**是否在预置的 pin 列表里。**不匹配就断开连接。**
2. **两种 pin**：
   - **Certificate Pinning**：固定整个证书 → **证书续期会导致失效**（Let's Encrypt 只有 90 天）；
   - **Public Key Pinning**：固定公钥（SPKI）→ **推荐**，证书换新但公钥不变时不受影响。
3. **为什么要备用 pin**：
   - 必须同时配置 **主 pin + 备用 pin**；
   - 切换时先发布"同时包含新旧 pin"的版本，等客户端更新完再移除旧 pin；
   - 否则 pin 一旦失效，**所有客户端直接断网**（这是事故级别的风险）。
4. **风险**：
   - **pin 配置错误 → 全量断网**；
   - **证书轮换未协调 → 断网**；
   - **调试不便**：需要在 debug 包里关闭或配置信任用户 CA。
5. **实现**：
   - OkHttp 的 `CertificatePinner`（推荐）；
   - 自定义 `X509TrustManager`（可以做更细的逻辑）。
6. **合规性提醒**：**Google Play 要求 pin 的备份 pin 至少有效 1 年**。
7. **面试话术**："**Pinning 是拿'可用性风险'换'安全性'。所以必须配备用 pin、有轮换预案、debug 包单独放行——这是最容易出事故的地方。**"

**读者问：Root 检测、模拟器检测可靠吗？**

**AI答：**

1. **结论**：**都不可靠，只能提高门槛**。
2. **Root 检测的常见线索**：
   - `su` 二进制文件路径（`/system/bin/su`、`/sbin/su` 等）；
   - Root 管理器 App 包名（Magisk、SuperSU、KingRoot）；
   - `ro.build.tags == "test-keys"`、`ro.debuggable == 1`；
   - `/system` 可被挂载为读写；
   - `which su` / `Runtime.exec("su")` 是否成功。
3. **模拟器检测的常见线索**：
   - Build 属性（`ro.hardware == "goldfish"`、`ro.kernel.qemu == 1`、`ro.product.model` 含 "sdk"）；
   - 设备文件（`/dev/qemu_pipe`、`/dev/socket/qemud`、`/sys/qemu_trace`）；
   - **加速度传感器读数全为 0**（真机不会）；
   - IMEI 为 000000000000000（不推荐，Google Play 政策敏感）。
4. **为什么容易绕过**：
   - 隐藏 su（Magisk 的 DenyList）、改 `ro.build.tags`；
   - Hook 掉检测方法（Xposed / Frida）；
   - 检测代码本身在进程内 → **可以被 Hook**。
5. **正确的策略**：
   - **检测只是"信号"，不是"结论"**；
   - **把信号上报服务端，由服务端决策**（是否禁止支付、是否限制功能）；
   - **不要把 root 设备直接拒绝服务**（会误伤开发者和测试机）；
   - **多信号交叉**：root + 调试 + hook 同时出现 → 高风险。
6. **面试话术**："**Root/模拟器检测我的定位是'采集风险信号上报'，不是'本地判决'。因为客户端的一切判断都可以被绕过，最终策略应该在服务端。**"

**读者问：隐私合规在开发上要注意什么？**

**AI答：**

1. **权限最小化**：
   - 只申请真正用到的权限，**能不用就不申请**；
   - Android 13+ 用 `READ_MEDIA_IMAGES` 等细分权限代替 `READ_EXTERNAL_STORAGE`；
   - **拒绝后不重复弹窗**（用 `shouldShowRequestPermissionRationale` 判断）；
   - **用 Photo Picker / SAF 代替存储权限**（完全不需要权限）。
2. **SDK 清单（Privacy Manifest）**：
   - Google Play 要求应用与**每个第三方 SDK** 都声明收集了哪些数据；
   - 2024 年起第三方 SDK 未声明会导致**安装被阻止**；
   - 检查方式：Play Console 的 Data Safety 表 + 应用内的 `PrivacyPolicy` 类。
3. **App 隐私标签**：
   - 必须与实际行为一致；**误导性声明会导致下架甚至封号**。
4. **采集时机**：
   - **隐私政策同意之前不能采集任何设备信息**（包括广告 SDK 的初始化）；
   - 提供"撤回同意"的入口。
5. **数据删除**：
   - **账号注销必须真的删除数据**（这是国内合规的硬性要求）；
   - 备份规则里也要排除敏感数据（`data_extraction_rules.xml`）。
6. **本地存储**：
   - 敏感数据加密（Keystore + AES）；
   - `allowBackup="false"` 或精细配置备份规则。
7. **面试话术**："**合规在开发上的落点主要是三处：权限申请要少而准、SDK 要盘清楚并声明、用户同意之前不要初始化任何采集型 SDK。**"

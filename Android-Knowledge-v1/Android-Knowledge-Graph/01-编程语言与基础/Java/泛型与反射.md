# 泛型与反射

## 一句话定义

**泛型**是 Java 5 引入的**编译期类型安全**机制：它让类/方法能操作"类型参数"而不是具体类型，从而写出 `List<String>` 而不是 `List` + 强制转换；但由于 JVM 字节码层面**没有泛型**（类型擦除），泛型信息只存在于编译器的 `Signature` 属性中，运行时完全不可见。**反射**则是 Java 在运行时**内省**类型的能力——读取类的结构（字段、方法、注解）并动态操作对象。两者在 Android 里的典型交汇点是：**APT（注解处理器）用"编译期反射"生成代码以绕过运行时反射的性能代价**。

## 核心原理

### 1. 类型擦除（Type Erasure）

**Java 编译泛型的三步走**：

```text
编译器处理：
  List<String> list = new ArrayList<>();
  list.add("hello");
  String s = list.get(0);        // 需要插入 checkcast String

  ↓ 编译

字节码（javap -c）：
  list.add("hello");             // 方法签名变成 add(Ljava/lang/Object;)V
  checkcast java/lang/String     // 编译器插入的向下转型
  astore_2
```

**擦除规则表**：

| 泛型声明 | 擦除后 | 说明 |
| --- | --- | --- |
| `List<T>` | `List` | 无界类型参数 → 擦除为 `Object` |
| `List<T extends Number>` | `List` | 有界 → 擦除为**上界** `Number` |
| `List<T extends Number & Comparable>` | `List` | 多重上界 → 擦除为**第一个**上界 |
| `List<?>` | `List` | 无界通配符 → `Object` |
| `List<? extends Number>` | `List` | 协变通配符 → `Number` |
| `List<? super Number>` | `List` | 逆变通配符 → `Object` |
| `Map<K, V>` | `Map` | 多个参数 → 全部擦除 |
| `T[] array` | `Object[]` | **数组也不能具体化** |
| `static <T> void foo(T t)` | `static void foo(Object t)` | 方法参数也一样 |
| `T method()` | `Object method()` | 返回值也一样 |

**类型擦除带来的四个直接后果**：

```java
// ① 不能 new T[]
List<String>[] arr = new List<String>[10];      // ❌ 编译错误：generic array creation

// ② 不能 instanceof T
Object o = "str";
if (o instanceof List<String>) { }              // ❌ 编译错误：incompatible types
// ✅ 只能检查到原始类型
if (o instanceof List<?>) { }

// ③ 不能基本类型做类型参数
List<int> list;                                  // ❌ 编译错误
List<Integer> list2;                             // ✅ 只能装箱

// ④ 静态字段不能使用类的类型参数
class Box<T> {
    static T value;                              // ❌ 编译错误：non-static type variable T
    // ✅ 必须用具体类型
    static Object staticValue;
}
```

### 2. 桥接方法（Bridge Method）与类型检查

**类型擦除导致的"方法覆盖"问题**：

```java
class Node<T> {
    public void set(T value) { }      // 擦除后：set(Object)
}

class StringNode extends Node<String> {
    @Override
    public void set(String value) { } // 擦除后：set(String)
}
```

**问题**：`Node<String>.set(String)` 并没有真正覆盖 `Node.set(Object)`（方法签名不同）。

**javac 的解决方案——桥接方法**：

```text
javac 编译 StringNode 时，额外生成：
  public void set(Object value) {
      this.set((String) value);      // 桥接方法（synthetic + bridge）
  }

运行时多态：
  Node<String> n = new StringNode();
  n.set("hello");
    ↓ 编译后实际调用
  n.set(Object)                     // 因为静态类型是 Node，编译器调 set(Object)
    ↓ 虚派发到实际类型
  StringNode.set(Object)            // 桥接方法
    ↓ 桥接方法内部强转并转发
  StringNode.set(String)            // 真正的方法
```

```text
javap -p StringNode.class 输出：
  public void set(java.lang.String);          ← 真正的方法
  public void set(java.lang.Object);          ← 桥接方法（synthetic bridge）
```

**运行时类型检查（Runtime Type Check）**：

```java
// 编译器插入的 checkcast
Object result = node.get(0);
String s = (String) result;    // 编译为：checkcast java/lang/String
```

- 如果实际对象是 `Integer`，会在**运行时**抛 `ClassCastException`（不是编译期）。
- 这就是"泛型只在编译期生效"的直接体现。

### 3. 通配符与 PECS 原则

**三种通配符**：

| 写法 | 名称 | 含义 | 读取 | 写入 |
| --- | --- | --- | --- | --- |
| `List<?>` | 无界通配符 | 任意类型的 List | ✅ 只能读为 `Object` | ❌ 不能添加（除 null） |
| `List<? extends Number>` | 上界/协变 | `List<Number>` 或 `List<Integer>` | ✅ 读为 `Number` | ❌ 不能添加具体类型 |
| `List<? super Number>` | 下界/逆变 | `List<Object>` 或 `List<Number>` | ✅ 读为 `Object` | ✅ 可添加 `Number` 及其子类 |

**为什么 `? extends` 不能写入**：

```java
List<? extends Number> list = new ArrayList<Integer>();
list.add(1);      // ❌ 编译错误
```

**编译器的推理**：`list` 的静态类型是"某个未知的 `List<? extends Number>`"。如果允许 `list.add(1)`，那么当这个未知类型实际是 `List<Double>` 时，就会往里面塞进一个 `Integer` —— **破坏类型安全**。所以编译器直接拒绝。

**为什么 `? super` 不能读取为具体类型**：

```java
List<? super Integer> list = new ArrayList<Number>();
Integer i = list.get(0);   // ❌ 编译错误
```

**推理**：`list` 实际可能是 `List<Object>`，里面装的是 `String`，取出时按 `Integer` 强转会 `ClassCastException`。所以只能读为 `Object`。

**PECS 原则（Producer EXTends, Consumer SUPERS）**：

> **Producer（产出 T 的地方）用 `? extends T`；Consumer（消费 T 的地方）用 `? super T`。**

```java
// ✅ Producer：只读取
void printAll(List<? extends Number> list) {
    for (Number n : list) { System.out.println(n); }   // 读作 Number
}

// ✅ Consumer：只写入
void addNumbers(List<? super Integer> list) {
    list.add(1);
    list.add(2);
}

// ❌ 两个都要：只能退化到 List<Number>
void both(List<Number> list) {
    list.add(1);              // 写
    Number n = list.get(0);   // 读
}
```

**PECS 的实战应用——`Collections.copy`**：

```java
public static <T> void copy(List<? super T> dest, List<? extends T> src)
```

- `dest` 是 **Consumer**（接收 T）→ `? super T`。
- `src` 是 **Producer**（产出 T）→ `? extends T`。
- 结果：`copy(ArrayList<Number>, ArrayList<Integer>)` **可以编译通过**，而且 `copy(ArrayList<Object>, ArrayList<String>)` 也可以。

### 4. 泛型类、泛型方法与类型参数约束

```java
// 泛型类
public class Result<T> {
    private final T value;
    private final Throwable error;
    private Result(T value, Throwable error) { this.value = value; this.error = error; }
    public static <T> Result<T> success(T value) { return new Result<>(value, null); }
    public static <T> Result<T> failure(Throwable e) { return new Result<>(null, e); }
    public T get() { if (error != null) throw new RuntimeException(error); return value; }
}

// 泛型方法（类型参数在方法上）：调用时由编译器推断
public static <T> List<T> listOf(T... items) {
    return Arrays.asList(items);
}
List<String> a = listOf("a", "b");   // ✅ 推断 T = String
List<Integer> b = listOf(1, 2);      // ✅ 推断 T = Integer

// 泛型方法 vs 泛型类的类型参数作用域
// 泛型类的 T 在整个类可见；泛型方法的 <T> 只在方法内可见，且可以遮蔽类的 T
public class Cache<K, V> {
    public <T> T get(K key, Class<T> type) { return null; }   // 方法级 T
}
```

**类型参数约束**：

```java
// ① 上界（extends）
public class NumberBox<T extends Number> {
    private T value;
    public double doubleValue() { return value.doubleValue(); }   // ✅ 能调用 Number 的方法
}

// ② 多重上界：第一个必须是类，其余必须是接口
public class SerializableBox<T extends Number & Comparable<T> & Serializable> { }
// 多个上界时不能再用 extends，只能用 &

// ③ 下界通配符（super）：只能用在参数位置
public static void process(List<? super Integer> list) { }
public static ? super Integer wrong() { }    // ❌ 返回位置不能用下界通配符

// ④ 递归类型参数
public class Node<T extends Node<T>> {
    private T parent;
    private List<T> children = new ArrayList<>();
}
// 用法：class MyNode extends Node<MyNode> {}
```

**通用的泛型工具方法**：

```java
// 从 Map 中安全取值，避免 ClassCastException
public static <K, V> V getOrDefault(Map<K, V> map, K key, V defaultValue) {
    V v = map.get(key);
    return v != null ? v : defaultValue;
}
```

### 5. 反射 API 详解

**反射的四大入口**：

```java
// ① Class 对象（每个类都有对应的 Class 实例）
Class<?> clazz = String.class;
Class<?> clazz2 = "hello".getClass();
Class<?> clazz3 = Class.forName("java.lang.String");

// ② Constructor（构造器）
Constructor<?> ctor = clazz.getDeclaredConstructor();
Object obj = ctor.newInstance();
Constructor<?>[] ctors = clazz.getDeclaredConstructors();

// ③ Method（方法）
Method m = clazz.getMethod("length");          // 只找 public
Method m2 = clazz.getDeclaredMethod("value");  // 找所有（含 private）
Object result = m.invoke("hello");

// ④ Field（字段）
Field f = clazz.getDeclaredField("value");
f.setAccessible(true);                          // 突破访问检查
Object v = f.get(obj);
f.set(obj, newValue);
```

**核心 API 分类表**：

| API | 语义 |
| --- | --- |
| `getMethod` / `getField` | 只返回 **public** 成员（含继承的） |
| `getDeclaredMethod` / `getDeclaredField` | 返回本类**声明**的所有成员（public/protected/private/package），**不含继承的** |
| `setAccessible(true)` | 关闭访问检查（Java 9+ 对模块系统有额外限制） |
| `getMethods()` vs `getDeclaredMethods()` | 前者含继承的 public 方法 |
| `isInstance(obj)` | 判断对象是否属于某类型（**类型擦除下唯一可靠的运行时类型检查**） |
| `getGenericSuperclass()` / `getGenericType()` | 获取**泛型信息**（ParameterizedType） |
| `getAnnotations()` / `getAnnotation(Class)` | 读取运行时保留的注解 |

**泛型信息的运行时读取**：

```java
// 读取父类的泛型参数
class UserService extends BaseService<User, Long> { }

Type superclass = UserService.class.getGenericSuperclass();
if (superclass instanceof ParameterizedType) {
    ParameterizedType pt = (ParameterizedType) superclass;
    Type[] args = pt.getActualTypeArguments();
    Class<?> entityType = (Class<?>) args[0];      // User
    Class<?> idType = (Class<?>) args[1];          // Long
}

// 读取方法参数的泛型
Method m = Dao.class.getDeclaredMethod("query", Wrapper.class);
ParameterizedType pt = (ParameterizedType) m.getGenericParameterTypes()[0];
Type actual = pt.getActualTypeArguments()[0];      // 可能是 WildcardType
```

**Java 8+ 的类型判断工具**：

```java
Type type = field.getGenericType();
if (type instanceof ParameterizedType) {
    ParameterizedType pt = (ParameterizedType) type;
    Class<?> raw = (Class<?>) pt.getRawType();
    Type arg = pt.getActualTypeArguments()[0];
    if (arg instanceof Class) {
        Class<?> c = (Class<?>) arg;
    } else if (arg instanceof ParameterizedType) {
        ParameterizedType nested = (ParameterizedType) arg;
    } else if (arg instanceof WildcardType) {
        WildcardType wt = (WildcardType) arg;
        Type[] upper = wt.getUpperBounds();   // ? extends X 的 X
        Type[] lower = wt.getLowerBounds();   // ? super X 的 X
    } else if (arg instanceof GenericArrayType) {
        GenericArrayType gat = (GenericArrayType) arg;
    } else if (arg instanceof TypeVariable) {
        TypeVariable<?> tv = (TypeVariable<?>) arg;
    }
}
```

### 6. 反射的性能开销

**开销来源**：

```text
调用一次反射方法：
  ① Method.invoke 本身
  ② 参数装箱（int → Integer）
  ③ 数组创建（Object[] 承载参数）
  ④ 访问检查（除非 setAccessible）
  ⑤ 方法内可能的反射调用自身
```

**基准参考（相对耗时）**：

| 操作 | 相对耗时（普通调用 = 1） |
| --- | --- |
| 直接方法调用 | 1× |
| `Method.invoke`（已 `setAccessible`） | ~10× |
| `Method.invoke`（未 `setAccessible`） | ~30×+ |
| `Field.get/set` | ~10× |
| `Class.forName`（首次） | 很高（类加载） |
| `newInstance`（已缓存 Constructor） | ~10× |
| Gson 反射解析一个对象 | 高（数百倍） |

**Android 上的特殊情况**：

- **ART 上没有 JIT 的第一次执行**（解释执行），反射的开销在冷启动时更明显。
- **R8/ProGuard 混淆会破坏反射**：
  - 类名/方法名被混淆 → `Class.forName("com.example.Foo")` 找不到。
  - **解法**：给需要反射的类加 `@Keep`（`androidx.annotation.Keep`）或混淆规则 `-keep class com.example.model.** { *; }`。
  - **更好的解法**：改用 **APT / KSP 编译期生成代码**，完全避免运行时反射（见下节）。

### 7. 注解（Annotation）：定义、Retention、Target

**自定义注解**：

```java
@Retention(RetentionPolicy.RUNTIME)                       // 生命周期
@Target({ElementType.TYPE, ElementType.METHOD})          // 可标注位置
@Inherited                                                // 是否被子类继承
@Documented                                              // 是否进 javadoc
public @interface CustomAnnotation {
    String value() default "";                            // 必须有默认值（无则必须传）
    int count() default 0;
    Class<?>[] types() default {};
}
```

**RetentionPolicy 四种**：

| 策略 | 保留到 | 运行时可见 | 典型用途 |
| --- | --- | --- | --- |
| `SOURCE` | **仅源码**，编译后丢弃 | ❌ | 编译期标记（`@SuppressWarnings`、Lombok 注解） |
| `CLASS` | 编译到 **class 文件**，运行时不可见 | ❌ | 字节码增强（如 `@NotNull` 注解处理器） |
| `RUNTIME` | 保留到运行时 | ✅ | 运行时反射读取（`@Inject`、`@Serializable`） |
| 缺失（默认） | 等同 `CLASS` | ❌ | — |

**Target 的取值**：

```text
TYPE, FIELD, METHOD, PARAMETER, CONSTRUCTOR, LOCAL_VARIABLE,
ANNOTATION_TYPE, PACKAGE, TYPE_PARAMETER, TYPE_USE, MODULE, RECORD_COMPONENT
```

**Android 内置注解**：

```java
@Nullable / @NonNull      // androidx.annotation —— 静态分析
@Keep                    // 防止混淆
@IntDef / @StringDef     // 限定"整型常量集合"
@RequiresApi              // 标注 API 级别要求
@CallSuper                // 强制调用父类方法
@MainThread               // 线程约束（Lint 检查）
@WorkerThread
@VisibleForTesting
```

**`@IntDef` 举例**：

```java
@IntDef({View.VISIBLE, View.INVISIBLE, View.GONE})
@Retention(RetentionPolicy.SOURCE)
public @interface Visibility {}

public void setVisibility(@Visibility int visibility) { ... }
// 调用 setVisibility(3) → 编译错误（3 不在 IntDef 列表里）
```

### 8. 注解处理的两条路线：APT / KSP vs 运行时反射

```text
                    注解 @Foo
                         │
        ┌────────────────┴────────────────┐
        ▼                                 ▼
  【编译期处理】                       【运行时处理】
  APT / KSP / Lombok                 反射 (RUNTIME retention)
        │                                 │
        ├─ 生成代码或修改字节码             ├─ Class.getAnnotation()
        ├─ 零运行时开销                    ├─ 有运行时开销
        ├─ 编译期报错                      ├─ 运行时才可能发现错误
        └─ 需要重新编译                    └─ 改注解立即生效
```

**对比表**：

| 维度 | APT / KSP（编译期） | 运行时反射 |
| --- | --- | --- |
| **处理时机** | 编译期 | 运行时 |
| **性能** | ✅ 零运行时开销（生成普通 Java 代码） | ❌ 显著开销 |
| **错误发现** | ✅ 编译期 | ❌ 运行时 |
| **增量构建** | ⚠️ KSP 优于 APT（APT 有增量编译问题） | ✅ 不影响编译 |
| **实现复杂度** | ❌ 需写处理器/写 KSP 插件 | ✅ 简单 |
| **工具链** | APT（javac）/ KSP（Kotlin） | 标准反射 API |
| **代表** | Dagger、Room、Glide、Butterknife、Hilt | Gson、Jackson、传统序列化 |

**Android 上的注解处理器演进**：

| 方案 | 说明 | 现状 |
| --- | --- | --- |
| **APT**（Annotation Processing Tool） | `javax.annotation.processing` 规范，javac 内置 | Java 处理器仍需用；Kotlin 源码需 `kapt`（性能差，已弃用） |
| **kapt** | Kotlin 的 APT 桥接 | ⚠️ **已弃用**（Kotlin 1.9+ 警告，2.0 仍可用但不再推荐） |
| **KSP**（Kotlin Symbol Processing） | Kotlin 编译器原生 API，**不生成字节码** | ✅ **当前推荐** |

**KSP 的优势**：

```text
APT：  Kotlin 源码 → kapt（生成 stub）→ javac 处理 stub → 生成代码 → 编译
      ↑ 慢：多一轮 stub 生成与编译

KSP： Kotlin 源码 → KSP 插件（直接读 Kotlin 符号）→ 生成 Kotlin 源码 → 编译
      ↑ 快：跳过 stub 与 javac，且是增量的
```

**实战：为 Retrofit / Room / Hilt 使用 KSP**：

```kotlin
// app/build.gradle.kts
plugins {
    id("com.google.devtools.ksp") version "2.0.20-1.0.25"
}

dependencies {
    implementation("com.squareup.retrofit2:retrofit:2.11.0")
    ksp("com.squareup.retrofit2:converter-moshi:2.11.0")     // ✅ KSP
    // kapt("com.squareup.retrofit2:converter-moshi:2.11.0")  // ❌ 旧写法

    implementation("androidx.room:room-runtime:2.6.1")
    ksp("androidx.room:room-compiler:2.6.1")                   // ✅ KSP

    implementation("com.google.dagger:hilt-android:2.51.1")
    ksp("com.google.dagger:hilt-compiler:2.51.1")              // ✅ KSP
}
```

**注解处理器的标准结构（APT）**：

```java
@SupportedAnnotationTypes("com.example.MyAnnotation")
@SupportedSourceVersion(SourceVersion.RELEASE_17)
public class MyProcessor extends AbstractProcessor {

    @Override
    public boolean process(Set<? extends TypeElement> annotations, RoundEnvironment roundEnv) {
        for (Element element : roundEnv.getElementsAnnotatedWith(MyAnnotation.class)) {
            if (element.getKind() != ElementKind.CLASS) continue;
            TypeElement classElement = (TypeElement) element;
            String className = classElement.getQualifiedName().toString();
            // 生成代码
            String generated = "package com.example.generated;\n"
                    + "public class " + className + "Factory {\n"
                    + "  public static Object create() { return new " + className + "(); }\n"
                    + "}\n";
            try {
                JavaFile file = SourceVersion.latestSupported(processingEnv.getSourceVersion())
                        .createSourceFile("com.example.generated." + className + "Factory");
                file.addImport("com.example." + className);
                file.addStatement("public static Object create() { return new " + className + "(); }");
                file.close();
            } catch (IOException e) {
                processingEnv.getMessager().printMessage(Diagnostic.Kind.ERROR, e.getMessage());
            }
        }
        return true;   // 返回 true 表示"已消费"这些注解
    }
}
```

### 9. Android 中的实际用途

| 场景 | 技术 | 机制 |
| --- | --- | --- |
| **依赖注入** | Dagger / Hilt | APT/KSP **编译期**生成组件代码，零反射 |
| **数据库** | Room | APT/KSP 生成 `UserDao_Impl`，运行期调用 |
| **网络** | Retrofit | APT/KSP 生成 `UserService_Impl`（动态代理 + 反射调用方法） |
| **图片加载** | Glide / Coil | APT 生成 API + 运行时反射访问资源 |
| **序列化** | Gson / Moshi / kotlinx.serialization | Gson/Moshi 用**运行时反射**；kotlinx.serialization 用**编译期插件生成 serializer**（无反射） |
| **依赖注入（轻量）** | Koin / dagger-android（手动） | **运行时反射 + DSL** |
| **路由** | ARouter | APT 生成路由表 |
| **View 绑定** | Butterknife / ViewBinding | APT 生成绑定类 |

**为什么 Dagger 选择编译期而不是反射**：

```text
运行时反射方案（Dagger 早期 / Koin）：
  App 启动 → 扫描注解 → 反射创建对象图 → 首次使用有延迟
  ❌ 启动慢、无法静态检查依赖是否齐全、混淆易失效

编译期方案（Dagger / Hilt）：
  编译 → APT 生成 UserComponentImpl.java（普通 Java 代码）
  运行 → 直接 new，无反射
  ✅ 启动零延迟、缺依赖编译期报错、混淆安全（用 @Inject 绑定而非类名）
```

**Kotlin 为什么不需要担心类型擦除**（面试高频）：

```text
Java：  List<String> 运行时是 List   → 需要反射才能知道 T
Kotlin：List<String> 运行时仍是 List<String>（Kotlin 的泛型保留在元数据里）
        → 可以通过 reified + T::class.java 拿到类型
```

**但 Kotlin 仍需要 `reified`**：因为 `reified` 不是"Kotlin 独有"，而是"JVM 层面有独立实现"。Kotlin 编译器会把 `List<String>` 记录到 `@Metadata` 注解里，运行时可通过 `kotlin.reflect` 读回，但**这只在 Kotlin 反射库（kotlin-reflect）可用时生效**，且比 Java 反射更慢。`reified` 是**编译期特化**，比运行时反射快得多。

### 10. 反射 vs 泛型 vs 注解：三者关系总结

```text
泛型：    编译期的类型约束 → 提升编译期安全，运行时被擦除
注解：    元数据 → 编译期（APT/KSP）或运行时（反射）消费
反射：    运行时的类型内省 → 突破编译期约束，但有性能与安全代价

三者组合的典型模式：
  ① @Inject（注解，RUNTIME）+ APT（编译期消费）→ 零反射的依赖注入
  ② <T>（泛型，编译期）+ Class<T>（显式传递）→ 绕过擦除的泛型解析
  ③ reified（Kotlin，编译期特化）→ 零反射的泛型实例化
```

### 1. 泛型工具类：Result 与类型安全的 Map 操作

```java
/**
 * 类型安全的 Result 封装。
 * 关键点：
 * 1. 静态工厂方法上的 <T> 是方法级类型参数，由调用点推断
 * 2. 返回泛型类型的 Class<T>，绕过类型擦除
 */
public final class Result<T> {

    private final T value;
    private final Throwable error;
    private final boolean success;

    private Result(T value, Throwable error, boolean success) {
        this.value = value;
        this.error = error;
        this.success = success;
    }

    public static <T> Result<T> success(T value) {
        return new Result<>(value, null, true);
    }

    public static <T> Result<T> failure(Throwable error) {
        return new Result<>(null, error, false);
    }

    /** 泛型方法 + 函数式接口：链式转换，类型自动推导 */
    public <R> Result<R> map(Function<T, R> mapper) {
        if (!success) {
            @SuppressWarnings("unchecked")
            Result<R> r = (Result<R>) this;   // 失败时保持类型（编译器无法推断 R）
            return r;
        }
        try {
            return Result.success(mapper.apply(value));
        } catch (Exception e) {
            return Result.failure(e);
        }
    }

    public T get() {
        if (!success) throw new IllegalStateException("Result is failure", error);
        return value;
    }

    public T getOrDefault(T fallback) {
        return success ? value : fallback;
    }

    public boolean isSuccess() { return success; }
    public Throwable getError() { return error; }
}
```

**使用**：

```java
Result<User> r = Result.success(new User("Alice", 30));
Result<String> name = r.map(User::getName);         // 类型自动推断 R = String
Result<Integer> len = r.map(u -> u.getName().length());
```

### 2. PECS 原则的实战：通用工具方法

```java
/**
 * PECS：
 * - Producer（只读）用 ? extends
 * - Consumer（只写）用 ? super
 */
public final class CollectionUtils {

    /** Consumer：把 Integer 列表的所有元素复制到目标列表（目标能装 Integer 或其父类） */
    public static void addAllIntegers(List<? super Integer> dest, List<? extends Integer> src) {
        for (Integer i : src) {
            dest.add(i);
        }
    }

    /** Producer：读取任意 Number 子类的列表，统一当作 Number 处理 */
    public static double sum(List<? extends Number> numbers) {
        double total = 0;
        for (Number n : numbers) {   // 读作 Number —— 安全
            total += n.doubleValue();
        }
        return total;
    }

    /** 演示 PECS 让调用变得更灵活 */
    public static void demo() {

        List<Number> numbers = new ArrayList<>();
        List<Object> objects = new ArrayList<>();

        addAllIntegers(numbers, ints);   // ✅ src 是 ? extends Integer（Producer）
        addAllIntegers(objects, ints);   // ✅ dest 是 ? super Integer（Consumer）
        // addAllIntegers(ints, numbers);  // ❌ 编译错误：numbers 不是 ? extends Integer

        System.out.println(sum(ints));     // ✅
        System.out.println(sum(Arrays.asList(1.5, 2.5)));  // ✅ Double 列表
    }
```

### 3. 反射：运行时动态调用与字段访问

```java
/**
 * 反射工具类：演示 Class / Constructor / Method / Field 的完整 API。
 * ⚠️ 生产环境请优先考虑 KSP/APT 生成的代码替代反射。
 */
public final class Reflect {

    private Reflect() {}

    /** 通过类全名创建实例（支持无参构造） */
    public static <T> T newInstance(String className) throws Exception {
        Class<?> clazz = Class.forName(className);
        Constructor<?> ctor = clazz.getDeclaredConstructor();
        ctor.setAccessible(true);
        @SuppressWarnings("unchecked")
        T instance = (T) ctor.newInstance();
        return instance;
    }

    /** 反射调用方法：兼容 private */
    public static Object invoke(Object target, String methodName, Object... args) throws Exception {
        Class<?> clazz = target.getClass();
        // 从类及其父类中查找方法
        Method method = findMethod(clazz, methodName, args.length);
        method.setAccessible(true);
        return method.invoke(target, args);
    }

    private static Method findMethod(Class<?> clazz, String name, int paramCount) {
        for (Class<?> c = clazz; c != null; c = c.getSuperclass()) {
            for (Method m : c.getDeclaredMethods()) {
                if (m.getName().equals(name) && m.getParameterCount() == paramCount) {
                    return m;
                }
            }
        }
        throw new NoSuchMethodException(name);
    }

    /** 反射读写字段（含 private，需 setAccessible） */
    public static Object getField(Object target, String fieldName) throws Exception {
        Field field = findField(target.getClass(), fieldName);
        field.setAccessible(true);
        return field.get(target);
    }

    public static void setField(Object target, String fieldName, Object value) throws Exception {
        Field field = findField(target.getClass(), fieldName);
        field.setAccessible(true);
        field.set(target, value);
    }

    private static Field findField(Class<?> clazz, String name) {
        for (Class<?> c = clazz; c != null; c = c.getSuperclass()) {
            try {
                return c.getDeclaredField(name);
            } catch (NoSuchFieldException ignored) {
                // 继续向父类查找
            }
        }
        throw new NoSuchFieldException(name);
    }

    /** 读取泛型父类参数：拿到运行时的真实类型 */
    public static Class<?>[] resolveTypeArguments(Class<?> subclass) {
        Type superclass = subclass.getGenericSuperclass();
        if (superclass instanceof ParameterizedType) {
            Type[] args = ((ParameterizedType) superclass).getActualTypeArguments();
            Class<?>[] result = new Class<?>[args.length];
            for (int i = 0; i < args.length; i++) {
                result[i] = args[i] instanceof Class ? (Class<?>) args[i] : Object.class;
            }
            return result;
        }
        return new Class<?>[0];
    }

    /** 读取方法上的运行时注解 */
    public static <A extends Annotation> A findMethodAnnotation(
            Class<?> clazz, String methodName, Class<A> annotationType) {
        for (Method m : clazz.getDeclaredMethods()) {
            if (m.getName().equals(methodName)) {
                A ann = m.getAnnotation(annotationType);
                if (ann != null) return ann;
            }
        }
        return null;
    }
}
```

### 4. 运行时反射读取泛型类型：实现通用 DAO

```java
/**
 * 演示如何通过反射获取泛型类型，实现"通用"的 BaseDao。
 * ⚠️ 这是理解 Room / MyBatis 原理的基础。
 */
public abstract class BaseDao<T, ID> {

    private final Class<T> entityClass;

    @SuppressWarnings("unchecked")
    public BaseDao() {
        // 关键：通过 getGenericSuperclass 拿到父类的泛型实参
        Type superclass = getClass().getGenericSuperclass();
        if (!(superclass instanceof ParameterizedType)) {
            throw new IllegalArgumentException("BaseDao 必须被具体泛型子类继承");
        }
        ParameterizedType parameterized = (ParameterizedType) superclass;
        Type entityType = parameterized.getActualTypeArguments()[0];
        if (entityType instanceof Class) {
            this.entityClass = (Class<T>) entityType;
        } else if (entityType instanceof ParameterizedType) {
            // 处理 BaseDao<User, List<Long>> 这种嵌套泛型
            this.entityClass = (Class<T>) ((ParameterizedType) entityType).getRawType();
        } else {
            throw new IllegalArgumentException("无法解析实体类型: " + entityType);
        }
    }

    public Class<T> getEntityClass() {
        return entityClass;
    }

    /** 用反射创建一个实例 */
    public T createInstance() throws Exception {
        Constructor<T> ctor = entityClass.getDeclaredConstructor();
        ctor.setAccessible(true);
        return ctor.newInstance();
    }
}

// 使用
public class UserDao extends BaseDao<User, Long> {
    public void log() {
        System.out.println("实体类型 = " + getEntityClass().getName());   // User
    }
}
```

### 5. 自定义注解 + 运行时处理

```java
/**
 * ① 自定义注解
 */
@Retention(RetentionPolicy.RUNTIME)                       // 运行时可见 → 可被反射读取
@Target(ElementType.METHOD)
public @interface Debounce {
    long millis() default 300;
    boolean onMainThread() default true;
}

/**
 * ② 运行时处理：通过反射扫描并执行
 */
public final class AnnotationScanner {

    /** 扫描类中所有带 @Debounce 的方法 */
    public static List<Method> findDebounced(Class<?> clazz) {
        List<Method> result = new ArrayList<>();
        for (Method m : clazz.getDeclaredMethods()) {
            if (m.isAnnotationPresent(Debounce.class)) {
                result.add(m);
            }
        }
        return result;
    }

    /** 根据注解配置动态执行 */
    public static Object invokeWithConfig(Object target, Method method, Object... args)
            throws Exception {
        Debounce d = method.getAnnotation(Debounce.class);
        if (d == null) return method.invoke(target, args);

        if (d.onMainThread()) {
            new Handler(Looper.getMainLooper()).post(() -> {
                try { method.invoke(target, args); }
                catch (Exception e) { e.printStackTrace(); }
            });
            return null;
        }
        return method.invoke(target, args);
    }
}
```

### 6. APT 注解处理器：编译期生成工厂代码

```java
/**
 * ① 被处理的注解
 */
@Retention(RetentionPolicy.SOURCE)     // SOURCE 即可 —— 编译后丢弃
@Target(ElementType.TYPE)
public @interface AutoFactory {}

/**
 * ② 注解处理器
 */
@SupportedAnnotationTypes("com.example.AutoFactory")
@SupportedSourceVersion(SourceVersion.RELEASE_17)
public class AutoFactoryProcessor extends AbstractProcessor {

    @Override
    public boolean process(Set<? extends TypeElement> annotations, RoundEnvironment roundEnv) {
        for (Element element : roundEnv.getElementsAnnotatedWith(AutoFactory.class)) {
            if (element.getKind() != ElementKind.CLASS) continue;

            TypeElement typeElement = (TypeElement) element;
            String qualifiedName = typeElement.getQualifiedName().toString();
            String simpleName = typeElement.getSimpleName().toString();
            String packageName = typeElement.getQualifiedName()
                    .getEnclosingElement() != null
                    ? elements().getPackageOf(typeElement).getQualifiedName().toString()
                    : "";

            try {
                JavaFile factory = SourceVersion.latestSupported(
                        processingEnv.getSourceVersion())
                        .createSourceFile(packageName + "." + simpleName + "Factory");

                factory.addJavadoc("自动生成的工厂类\n");
                factory.addStatement("public final class " + simpleName + "Factory {");
                factory.addStatement("  private " + simpleName + "Factory() {}");
                factory.addStatement("  public static " + simpleName + " create() {");
                factory.addStatement("    return new " + simpleName + "();");
                factory.addStatement("  }");
                factory.addStatement("}");
                factory.close();

                processingEnv.getMessager().printMessage(
                        Diagnostic.Kind.NOTE, "Generated " + simpleName + "Factory");
            } catch (IOException e) {
                processingEnv.getMessager().printMessage(
                        Diagnostic.Kind.ERROR, "生成失败: " + e.getMessage());
            }
        }
        return true;
    }

    private Elements elements() {
        return processingEnv.getElementUtils();
    }
}
```

## 常见问题 / 面试要点

**读者问：什么是类型擦除？它带来了哪些问题和后果？**

**AI答：**

1. **定义**：JVM 字节码层面**没有泛型**（为了兼容 Java 5 之前的字节码），编译器把泛型信息擦除，只在 class 文件的 `Signature` 属性里保留**声明级**的类型信息（用于编译器检查），**运行时完全不可见**。

2. **擦除规则**：
   - 无界 `T` → `Object`。
   - 有界 `T extends Number` → `Number`（第一个上界）。
   - 通配符 → `Object`（`? extends Number` → `Number`，`? super Number` → `Object`）。
   - **方法参数/返回值**上的类型参数同样被擦除。
   - **静态字段**不能引用类的类型参数。

3. **四个直接后果**：

```java
List<String>[] arr = new List<String>[10];   // ❌ 不能创建泛型数组
if (o instanceof List<String>) { }            // ❌ 不能对参数化类型做 instanceof
List<int> list;                               // ❌ 不能用基本类型
class Box<T> { static T v; }                  // ❌ 静态成员不能用类级 T
```

4. **更隐蔽的后果——桥接方法**：

```text
class Node<T> { void set(T v) {} }        // 擦除成 set(Object)
class StringNode extends Node<String> { void set(String v) {} }
                                       // ↑ 并没有真的覆盖 set(Object)
编译器生成桥接方法：
  void set(Object v) { set((String) v); }   // synthetic + bridge
```

   → 运行时通过 vtable 查 `set(Object)`，命中桥接方法，再转发到 `set(String)`。**泛型协变/逆变在继承体系中靠桥接方法维持多态**。

5. **运行时类型检查**：

```java
Object o = list.get(0);
String s = (String) o;    // 编译成 checkcast，运行时可能抛 ClassCastException
```

   → 泛型安全是**编译期**的，跨方法边界的类型安全要靠 `checkcast` 保证。

6. **如何绕过擦除**：
   - **显式传 `Class<T>`**（Java 唯一标准做法）。
   - **Kotlin 的 `reified`**（编译期特化，零反射）。
   - **反射读取 `Signature` / `getGenericSuperclass()`**（有运行时开销，Android 上还要防混淆）。

7. **面试话术**："类型擦除是 JVM 规范决定的（兼容性），代价是运行时拿不到 `T`，所以 Java 不能 `new T[]`、不能 `instanceof T`、不能 `T.class`。绕过的办法是显式传 `Class<T>`，Kotlin 则用 `reified` 在编译期特化。"

---

**读者问：什么是 PECS 原则？为什么 `? extends` 不能写入、`? super` 不能读取？**

**AI答：**

1. **PECS = Producer EXTends, Consumer SUPERS**：
   - **Producer**（产出 `T` 的容器，只读）→ `? extends T`。
   - **Consumer**（消费 `T` 的容器，只写）→ `? super T`。

2. **为什么 `? extends T` 不能写入**：

```java
List<? extends Number> list = new ArrayList<Integer>();
list.add(1);   // ❌ 编译错误
```

   **推理**：编译器的视角是"这是一个**类型未知**的 `List`，它的元素类型是某个 `Number` 的子类型"。如果允许 `add(1)`，那么当这个未知类型实际是 `List<Double>` 时，就会往里塞进 `Integer` —— **破坏泛型不变性（invariance）**，堆里就会出现 `List<Double>` 里装着 `Integer` 的脏数据。

   → **`? extends` = "只读视图"（readonly view）**。

3. **为什么 `? super T` 不能读取为 `T`**：

```java
List<? super Integer> list = new ArrayList<Number>();
Integer i = list.get(0);   // ❌ 编译错误
```

   **推理**：`list` 实际可能是 `List<Object>`，里面装的是 `String`。按 `Integer` 取出会在运行时 `ClassCastException`。所以只能读成 `Object`。

   → **`? super` = "只写视图"（consumer view）**，也常称 **contravariant**。

4. **实战案例**：

```java
// Collections.copy 的 PECS 设计
public static <T> void copy(List<? super T> dest, List<? extends T> src)
```

   - `dest` 消费 `T` → `? super T`。
   - `src` 产出 `T` → `? extends T`。
   - 结果：`copy(List<Object>, List<String>)` **可以编译**（Java 库如果写成 `copy(List<T>, List<T>)` 就完全没法这样用）。

5. **实际项目中的 PECS 例子**：

```java
// ✅ 消费者：往 List<Object> 里塞 Integer
public static void addTo(List<? super Integer> list) {
    list.add(1);
}
List<Object> objs = new ArrayList<>();
addTo(objs);          // ✅ 编译通过

// ✅ 生产者：读取 List<Double> 当作 List<? extends Number>
public static double sum(List<? extends Number> list) { ... }
sum(Arrays.asList(1.0, 2.0));   // ✅
```

6. **常见错误**：

```java
// ❌ 错误：想要"既能读又能写"就用 List<?>
List<?> list = new ArrayList<String>();
list.add("x");   // ❌ 编译错误 —— ? 就是 ? extends Object，只能读
```

7. **面试话术**："PECS 是 Java 泛型**不变性**下的安全折中。`? extends` 表达'我只读，元素至少是 T'；`? super` 表达'我只写，T 能装进去'。标准库的 `Collections.copy` 就是教科书示范：目标参数用 `? super T`，源参数用 `? extends T`。"

---

**读者问：桥接方法（Bridge Method）是什么？为什么需要它？**

**AI答：**

1. **问题根源**：泛型子类擦除后无法真正覆盖父类的泛型方法。

```java
class Node<T> {
    public void set(T value) { }        // 擦除后签名：set(Object)
}
class StringNode extends Node<String> {
    @Override
    public void set(String value) { }   // 擦除后签名：set(String)
}
```

   `StringNode.set(String)` 与 `Node.set(Object)` **签名不同**，JVM 认为它们是**两个无关的方法**（Java 语言的"重写"发生在编译期，字节码层面靠桥接方法维持）。

2. **javac 的解决方案**：编译 `StringNode` 时自动生成一个**桥接方法**：

```java
// javac 自动生成（标记为 synthetic + bridge）
public void set(Object value) {
    this.set((String) value);
}
```

3. **运行时多态链路**：

```text
Node<String> node = new StringNode();
node.set("hello");
   ↓ 编译后：静态类型是 Node，编译器生成 invokevirtual Node.set(Object)
   ↓ 虚派发：在 StringNode 的 vtable 中查找 set(Object)
   → 命中桥接方法 set(Object)
   → 桥接方法强转 (String) 并调用 set(String)
```

4. **查看桥接方法**：

```bash
javap -p -c StringNode.class
# 输出中带 "bridge" 标记的方法
```

5. **另一个作用——协变返回类型的桥接**：

```java
class Parent { Object get() { return null; } }
class Child extends Parent { @Override String get() { return ""; } }
// javac 生成：public Object get() { return get(); }   ← 桥接
```

6. **实践影响**：
   - **反射扫描方法时会看到重复的方法**（真实方法 + 桥接方法）。用 `method.isBridge()` / `isSynthetic()` 过滤。
   - **方法句柄（MethodHandle）查找要小心**：桥接方法的参数类型是擦除后的类型。
   - **JSON 序列化框架**：Gson 等遍历字段时一般用 `getDeclaredFields()`（字段没有桥接问题），但用 `getMethods()` 时会看到桥接方法导致**重复解析**。
   - **Android 的 `@JsonClass`** 之类框架需要过滤 bridge。

7. **面试话术**："桥接方法是 javac 为泛型子类自动生成的 `synthetic` 方法。父类的 `set(T)` 擦除成 `set(Object)`，子类的 `set(String)` 没法在字节码层面覆盖它，javac 就生成一个 `set(Object)` 桥接方法转发过去，保证运行时多态正确。反射扫描时要用 `isBridge()` 过滤掉。"

**读者问：反射的性能开销有多大？Android 上有什么替代方案？**

**AI答：**

1. **开销来源**：

```text
Method.invoke(obj, args)
  ① 参数装箱（int → Integer）
  ② 创建 Object[] 参数数组
  ③ 访问检查（未 setAccessible 时更贵）
  ④ 实际方法调用（无法被 JIT 深度内联）
  ⑤ 可能触发类的初始化
```

2. **量级（相对直接调用）**：

| 操作 | 相对耗时 |
| --- | --- |
| 直接调用 | 1× |
| `Method.invoke`（`setAccessible(true)`） | ~10× |
| `Method.invoke`（未 `setAccessible`） | ~30×+ |
| `Field.get/set` | ~10× |
| Gson 解析一个对象（反射） | 数百倍 |
| `Class.forName`（首次，含类加载） | 极高 |

3. **Android 上的额外问题**：
   - **ART 冷启动无 JIT**：首次执行是解释执行，反射的动态调用点更难被优化。
   - **混淆**：R8 会重命名类/方法/字段，`Class.forName("com.example.User")` 直接失效。
   - **多 dex 懒加载**：反射触发类加载会引入额外的加载延迟。

4. **替代方案（按推荐度排序）**：

| 方案 | 机制 | 例子 |
| --- | --- | --- |
| **① 编译期生成代码（KSP/APT）** | 生成普通 Java/Kotlin 代码，零反射 | Dagger/Hilt、Room、Glide、ARouter |
| **② 编译期插件** | 编译器插件生成 serializer | kotlinx.serialization、Parcelize |
| **③ 显式传 `Class<T>`** | 手动携带类型信息 | `gson.fromJson(json, User.class)` |
| **④ Kotlin `reified`** | 编译期特化 | `inline fun <reified T> parse()` |
| **⑤ 运行时反射** | 标准反射 API | Gson（默认）、Jackson |

5. **Android 的具体实践**：

```kotlin
// ❌ 反射解析 JSON：慢 + 混淆风险
val type = Class.forName("com.example.model.User")
val user = gson.fromJson(json, type)

// ✅ kotlinx.serialization：编译期生成，零反射，混淆安全
@Serializable
data class User(val name: String)
val user = Json.decodeFromString<User>(json)
```

6. **必须用反射时的加固措施**：

```kotlin
// ① 保留混淆
@Keep
class User { ... }

// 或在 proguard-rules.pro：
// -keep class com.example.model.** { *; }

// ② 缓存反射结果（不要每次调用都 getDeclaredMethod）
private val methodsCache = ConcurrentHashMap<String, Method>()

// ③ 用 setAccessible(true) 减少访问检查开销
// ④ Android 9+ 隐藏 API 限制：不要反射 JDK 内部类
```

7. **面试话术**："反射的开销主要在装箱、参数数组、访问检查和无法内联上，大约慢一个数量级。Android 上的替代方案优先级是：**KSP/APT 生成代码 > 编译期插件（kotlinx.serialization）> 显式 Class<T> > reified > 运行时反射**。Gson 默认走反射，所以大列表解析时我会换成 kotlinx.serialization 或手动映射。"

**读者问：注解的 `Retention` 有哪几种？分别用在什么场景？**

**AI答：**

1. **四种 `RetentionPolicy`**：

| 策略 | 生命周期 | 运行时反射可见 | 典型用途 |
| --- | --- | --- | --- |
| `SOURCE` | **仅源码**，编译时丢弃 | ❌ | 编译期标记：Lombok（`@Data`）、`@SuppressWarnings`、`@IntDef`（Lint 用） |
| `CLASS` | 写入 class 文件（**默认**） | ❌ | 字节码增强工具：AndroidX 的 `@RestrictTo`、Error Prone |
| `RUNTIME` | 保留到运行时 | ✅ | 运行时反射消费：`@Inject`（配合 APT）、`@Serializable`、`@IntDef`（部分） |
| 未指定 | 等同 `CLASS` | ❌ | — |

2. **判断依据——谁消费这个注解**：

```text
注解被谁消费？
  ├─ 编译器（Lombok / APT）→ SOURCE 足够（甚至更好，零运行时负担）
  ├─ 字节码增强工具        → CLASS
  ├─ 运行时反射框架        → RUNTIME（必须）
  └─ Lint 静态检查        → CLASS 或 RUNTIME（看实现）
```

3. **`@Target` 控制可标注位置**：

```java
@Target({ElementType.TYPE, ElementType.METHOD, ElementType.FIELD})
@Retention(RetentionPolicy.RUNTIME)
public @interface Inject {}

// ❌ 用在构造参数上会编译报错
```

   常用取值：`TYPE`、`METHOD`、`FIELD`、`PARAMETER`、`CONSTRUCTOR`、`LOCAL_VARIABLE`、`TYPE_USE`、`TYPE_PARAMETER`、`ANNOTATION_TYPE`。

4. **`@Inherited` 的语义**：只有 `ElementType.TYPE` 注解才可能继承；且**只对 `Class.getAnnotation()` 有效**，对 `getDeclaredAnnotation()` 无效。

5. **Android 实战**：

```kotlin
// ① @Keep（androidx.annotation）—— RUNTIME
@Keep
class UserEntity { @Keep var name: String = "" }

// ② @IntDef（androidx.annotation）—— SOURCE
@IntDef(SIZE_SMALL, SIZE_LARGE)
@Retention(RetentionPolicy.SOURCE)
annotation class Size

// ③ @Inject（javax.inject）—— RUNTIME（但由 APT 消费）
@Inject constructor(private val repo: UserRepository)

// ④ @Parcelize —— CLASS
@Parcelize
data class User(val id: Long, val name: String) : Parcelable
```

6. **常见坑**：

```kotlin
// ❌ 坑 1：给注解加上了 @Target(FIELD)，但你想标注在类上 → 编译报错
// ❌ 坑 2：Retention 写成 SOURCE，但运行时框架要读 → 反射拿不到（getAnnotation 返回 null）
// ❌ 坑 3：@Inherited 只对类有效，接口上的注解不会被实现类继承
```

7. **面试话术**："Retention 取决于**谁消费这个注解**：编译期工具用 `SOURCE`（Lombok），字节码工具用 `CLASS`，运行时反射才需要 `RUNTIME`。Android 里 `@Keep`、`@Inject` 是 RUNTIME，`@IntDef` 是 SOURCE，`@Parcelize` 是 CLASS。选错会直接导致'反射读不到注解'。"

**读者问：APT、kapt、KSP 有什么区别？Android 现在该用哪个？**

**AI答：**

1. **三者的关系**：

```text
APT (Annotation Processing Tool)
  ├─ 规范：javax.annotation.processing（javac 内置）
  ├─ 处理 .java 源文件
  └─ 工作流程：javac 解析 → 生成 stub → 处理器处理 stub → 生成代码 → javac 编译生成代码

kapt (Kotlin Annotation Processing Tool)
  ├─ Kotlin 的 APT 桥接
  ├─ 流程：Kotlin 编译 → 生成 Java stub（.java）→ javac + APT 处理 stub → 生成代码 → Kotlin 编译生成的代码
  └─ ⚠️ 已弃用（Kotlin 1.9+ 警告，2.x 不再推荐新项目使用）

KSP (Kotlin Symbol Processing)
  ├─ Kotlin 编译器原生 API（1.8.0 稳定，2.0+ 主流）
  ├─ 直接读取 Kotlin 符号（PSI），不生成 stub
  └─ 流程：Kotlin 编译 → KSP 插件处理符号 → 生成 Kotlin 源码 → Kotlin 编译生成代码
```

2. **性能对比**：

| 维度 | APT | kapt | KSP |
| --- | --- | --- | --- |
| **处理 Kotlin 源码** | ❌ 需要 stub | ✅（但慢） | ✅ **原生** |
| **增量编译** | ⚠️ 常需全量重编 | ❌ 增量支持差 | ✅ **原生增量** |
| **额外编译轮次** | 是 | 是（stub + javac + kotlinc） | 否 |
| **速度** | 中 | **最慢** | **最快** |
| **生态成熟度** | ✅ 成熟 | ✅ 成熟（但弃用中） | ✅ 主流库已支持 |
| **官方状态** | 仍在维护（Java 处理器） | **弃用** | **推荐** |

3. **Android 现在的选择**：

```kotlin
plugins {
    id("com.google.devtools.ksp") version "2.0.20-1.0.25"
}

dependencies {
    implementation("androidx.room:room-runtime:2.6.1")
    ksp("androidx.room:room-compiler:2.6.1")            // ✅ KSP

    implementation("com.google.dagger:hilt-android:2.51.1")
    ksp("com.google.dagger:hilt-compiler:2.51.1")       // ✅ KSP

    implementation("com.squareup.retrofit2:retrofit:2.11.0")
    ksp("com.squareup.retrofit2:converter-moshi:2.11.0") // ✅ KSP
}
```

4. **什么时候还需要 APT/kapt**：
   - 处理器**只支持 Java**（还没实现 KSP 版本）——某些老库。
   - 需要处理 **Java 源码**里的注解（KSP 主要面向 Kotlin 符号，对 Java 支持有限）。
   - **纯 Java 项目**（无 Kotlin）→ 用 APT 即可。

5. **KSP 的原理**：

```text
Kotlin 编译器
   ↓ 解析源码，生成 PSI（Program Structure Interface）符号树
KSP 插件（实现在 Kotlin 编译器插件 API 里）
   ↓ 读取/修改符号树，生成新的 Kotlin 文件
编译器继续编译（生成的文件 + 原文件）
```

   - KSP 插件用 **Kotlin 编写**（而不是 Java），有类型安全。
   - KSP API 提供 `Resolver`（查询类、函数、属性）、`CodeGenerator`（生成文件）。

6. **面试话术**："APT 是 javac 的规范，只处理 Java；kapt 是 Kotlin 的桥接方案，要生成 stub，很慢且已弃用；**KSP 是 Kotlin 编译器原生的符号处理 API，不生成 stub、支持增量，是现在的推荐**。Android 项目里 Room/Hilt/Retrofit 都应该用 `ksp(...)` 而不是 `kapt(...)`。"

**读者问：Kotlin 为什么没有类型擦除的问题？`reified` 是怎么解决的？**

**AI答：**

1. **Kotlin 的泛型保留在元数据里**：

```text
Java：  List<String> → 运行时是 List（完全擦除）
Kotlin： List<String> → 运行时仍是 List<String>（类型信息存在 @Metadata 注解里）
```

   - Kotlin 编译器把泛型签名写进 class 文件的 **`@kotlin.Metadata` 注解**（`kotlin.Metadata`）。
   - 通过 `kotlin.reflect`（kotlin-reflect 库）可以在运行时读回。

2. **但这不等于"运行时能用"**：

```kotlin
// ❌ 即使在 Kotlin 里，泛型参数在运行时也不能直接用（除非 reified）
fun <T> foo(x: Any) {
    if (x is T) { }          // ❌ 编译错误：cannot check for instance of erased type
}
```

   原因：Kotlin 的编译器在生成代码时**同样要把 `T` 替换成一个具体类型**（Kotlin 也编译成 JVM 字节码），替换的目标是 `Any`（即 Java 的 `Object`）。泛型信息虽然保留在元数据里，但**编译器不会为它生成运行时检查**。

3. **`reified` 的解法——编译期特化**：

```kotlin
inline fun <reified T> parse(json: String): T =
    gson.fromJson(json, T::class.java)
```

   **编译过程**：

```text
源码：inline fun <reified T> parse(json: String): T = gson.fromJson(json, T::class.java)

编译器处理 inline 函数：
  ① 检查 T 是否被 reified
  ② 为每个调用点生成一份特化代码，把 T 替换为实际类型
  ③ 把特化后的函数体内联到调用点

调用处：parse<User>(json)
  ↓ 特化后
  gson.fromJson(json, User.class.java)     ← T 被替换成具体类型 ✅
```

4. **与 Java 的对应关系**：

```text
Java 的做法：  gson.fromJson(json, User.class)            ← 手动传 Class
Kotlin reified：gson.fromJson(json, T::class.java)        ← 编译期自动填
本质相同，都是"让类型信息在运行时可见"，只是 Kotlin 用编译期替换自动化了它。
```

5. **`reified` 的限制**：

| 限制 | 原因 |
| --- | --- |
| 必须 `inline` | 编译器需要在编译期生成特化版本 |
| 只能用于**顶层函数/扩展函数** | 成员函数不能 inline（多态性） |
| 不能与 `vararg` 同用 | 编译器限制 |
| 不能是 `open`/`abstract`/`override` | 编译期无法确定实现 |

6. **为什么 Kotlin 仍推荐 `reified` 而不是 `kotlin.reflect`**：

```text
kotlin.reflect 读 @Metadata：
  ✅ 能拿到所有泛型信息（不需要调用点已知）
  ❌ 需要 kotlin-reflect 依赖（~3MB）
  ❌ 运行时解析开销大
  ❌ Android 上 R8 需要额外 keep 规则

reified：
  ✅ 零运行时开销（编译期就定死了）
  ✅ 无额外依赖
  ❌ 需要调用点已知具体类型
```

7. **面试话术**："Kotlin 的泛型信息保留在 `@Metadata` 里，比 Java 多留了一点，但编译器生成代码时同样把 `T` 替换成 `Any`，所以 `x is T` 依然不行。`reified` 的本质是**编译期在每个调用点特化一份代码**，把 `T` 换成实际类型，等价于 Java 里手动传 `Class<T>`，但自动化了。"

**读者问：反射在 Android 上有什么安全风险？**

**AI答：**

1. **主要风险点**：

| 风险 | 说明 |
| --- | --- |
| **访问隐藏 API** | Android 9（API 28）起限制对 `java.*` / `android.*` 内部 API 的反射访问，会打印警告并最终抛 `NoSuchMethodException` |
| **混淆失效** | R8 改名后，`Class.forName` / `getMethod` 找不到目标 |
| **安全绕过** | 反射可绕过 `private` 访问控制，被用于 Hook、篡改校验逻辑 |

2. **隐藏 API 限制（灰名单 → 黑名单）**：

```text
Android 9 (P)：灰名单 —— 访问时打印 "Accessing hidden method" 警告，仍可访问

非 SDK 接口（vendor 私有 API）始终受限
```

**规避方式**（非官方，不建议生产使用）：

```kotlin
// 绕过隐藏 API 限制的常见手法（Root/特定环境）
val method = Class.forName("android.app.ActivityThread")
    .getDeclaredMethod("currentActivityThread")
    .apply { isAccessible = true }
```

3. **合规风险**：

   - 金融、电商类 App 过安全检测时，反射调用敏感 API 容易被标记。

```kotlin
// ① 混淆安全的反射：使用字符串常量 + @Keep

    @Keep
    fun createStore(): Any? = try {
        val clazz = Class.forName(CLASS_NAME)
        clazz.getDeclaredConstructor().apply { isAccessible = true }.newInstance()
    } catch (e: Exception) {
        null
    }
}

// ② 优先用 KSP 生成代码，完全避免反射
// ③ 缓存反射结果
// ④ 不要反射操作 ActivityThread / ServiceManager 等系统内部类
```

5. **面试话术**："反射在 Android 上的三个风险是**隐藏 API 限制**（API 28 起的灰/黑名单）、**混淆失效**、以及**性能**。工程上的做法是：优先用 KSP/APT 生成代码替代反射；必须反射时用 `@Keep` + 混淆规则保护，并缓存反射结果。"

**读者问：什么是泛型协变和逆变？Java 的 `Producer EXTends, Consumer SUPERS` 在实际开发中怎么用？**

**AI答：**

1. **不变性（Invariance）是 Java 泛型的默认行为**：

```java
List<String> list = new ArrayList<>();
List<Object> objects = list;   // ❌ 编译错误
```

   → `List<String>` **不是** `List<Object>` 的子类型。这叫**不变性**。

2. **协变（Covariance）**——只读视角：

```java
List<? extends Number> numbers = new ArrayList<Integer>();   // ✅
Number n = numbers.get(0);      // ✅ 读作 Number
numbers.add(1);                 // ❌ 不能写
```

3. **逆变（Contravariance）**——只写视角：

```java
List<? super Integer> objects = new ArrayList<Number>();   // ✅
objects.add(1);                 // ✅ 能写 Integer
Integer i = objects.get(0);      // ❌ 不能读成 Integer（实际可能是 String）
```

4. **PECS 在真实 API 中的体现**：

```java
// ✅ 生产者：把一堆 Integer 复制到一个"能装 Integer"的目标
public static <T> void copy(List<? super T> dest, List<? extends T> src)

// ✅ 消费者：读取一批 Number，不关心具体子类
public static double sum(List<? extends Number> list)

// ✅ 既读又写：只能用 List<T>（或具体类型）
public static void both(List<Number> list)
```

5. **一个真实场景**——通用缓存：

```java
public class Cache<K, V> {
    private final Map<K, V> map = new ConcurrentHashMap<>();

    // ✅ V 只能被读取 → ? extends V
    public V getIfPresent(K key) { return map.get(key); }

    // ✅ V 只能被写入 → ? super V
    public void put(K key, V value) { map.put(key, value); }

    // ✅ 通用工厂：接受任意 V 的生产者
    public <T extends V> void putAll(K key, List<? extends T> values) {
        values.forEach(v -> map.put(key, v));
    }
}
```

6. **常见误用与纠正**：

```java
// ❌ 错误：为了"通用"而用 List<?>
void process(List<?> list) {
    Object o = list.get(0);      // 只能读成 Object
    list.add("x");               // ❌ 编译错误
}

// ✅ 正确：按角色选择通配符
void consume(List<? super Integer> list) { list.add(1); }        // 写入
void produce(List<? extends Number> list) { Number n = list.get(0); }  // 读取
```

7. **Kotlin 的对应物**：

```kotlin
// Kotlin 用【声明处变型】而不是【使用处变型】
// out = 协变（Producer），in = 逆变（Consumer）
class Producer<out T> { fun produce(): T = TODO() }        // 只能产出 T
class Consumer<in T> { fun consume(item: T) = Unit }        // 只能消费 T

// 使用处投影：out T / in T
fun <T> produceAll(list: List<out T>): List<T> = list       // 等价于 Java 的 List<? extends T>
fun <T> consumeAll(list: List<in T>, item: T) = Unit        // 等价于 Java 的 List<? super T>

// ⚠️ Kotlin 的 List<T> 默认是【协变的】（out T）——与 Java 的 List<T>（不变）不同！
val ints: List<Int> = listOf(1, 2, 3)
val anys: List<Any> = ints          // ✅ Kotlin 允许！Java 不允许
```

   → **这是 Kotlin 与 Java 互操作时的一个经典坑**：Kotlin 的 `List<T>` 传到 Java 时是 `List<? extends T>`（因为 Kotlin 的 `List` 声明为 `out T`）。

8. **面试话术**："Java 泛型默认**不变**，用 `? extends`（协变，只读）和 `? super`（逆变，只写）来放宽。PECS 原则：**Producer 用 extends，Consumer 用 super**。最经典的应用是 `Collections.copy(dest: List<? super T>, src: List<? extends T>)`——正因为用了 PECS，`copy(List<Object>, List<String>)` 才能编译通过。Kotlin 用的是**声明处变型**（`out`/`in`），而且 `List<T>` 本身是协变的——这点和 Java 不同，跨语言调用时要注意。"

---

**读者问：注解处理器（APT）是怎么工作的？它和 `kapt`、`ksp` 的编译流程有什么不同？**

**AI答：**

1. **APT 的完整编译流程**：

```text
javac 编译开始
   ↓
① javac 解析源码，生成【抽象语法树（AST）】
   ↓
② javac 扫描源码中的注解，发现有处理器声明处理该注解
   ↓
③ 调用处理器的 process() 方法
      · 处理器通过 RoundEnvironment 拿到【被标注的元素】
      · 通过 processingEnv 拿到 TypeElement / Elements / Filer
      · 用 Filer 生成【新的 .java 源文件】
   ↓
④ javac 把生成的源文件加入编译
   ↓
⑤ 重复 ③~④（多轮处理，直到没有新文件生成）
   ↓
⑥ 编译完成，生成 .class
```

2. **关键 API**：

```java
public interface ProcessingEnvironment {
    TypeElement getTypeElement(CharSequence name);       // 按全限定名获取类型元素
    Elements getElementUtils();                          // 工具类
    Filer getFiler();                                    // ✅ 生成文件
    Messager getMessager();                              // ✅ 打印诊断信息（警告/错误）
    Map<String, String> getOptions();                    // ✅ 读取注解处理器选项
    SourceVersion getSourceVersion();
}
```

3. **`Filer` 生成文件的四种方式**：

```java
// ① 生成 Java 源文件（最常用）
JavaFile file = filer.createSourceFile("com.example.GeneratedFactory");
file.addStatement("public class GeneratedFactory { ... }");
file.close();

// ② 生成【资源文件】（如 Dagger 的元数据、Room 的 json）
FileObject resource = filer.createResource(
        StandardLocation.CLASS_OUTPUT, "", "META-INF/my-metadata.json");

// ③ 生成【类文件】（字节码注入，如 Lombok 的部分能力）
FileObject classFile = filer.createClassFile("com.example.Generated");

// ④ 读取已有资源
FileObject existing = filer.getResource(StandardLocation.CLASS_OUTPUT, "", "data.json");
```

4. **处理器的生命周期与多轮（Round）**：

```text
第 1 轮：处理【原始源码】中的注解
第 2 轮：处理第 1 轮【生成的源码】中的注解（如果有）
第 3 轮：...直到没有新文件生成
最后一轮：processingOver() == true，此时不应再生成文件
```

5. **三种工具的流程对比**：

```text
APT（javac 原生）：
  javac → AST → 处理 stub？→ 生成 .java → javac 继续编译

kapt（Kotlin 的桥接）：
  Kotlin 编译器 → 解析 Kotlin 源码 → 生成【Java stub】（.java 文件）
                → 用 stub 跑 APT → 生成 .java
                → javac 编译 stub + 生成代码
                → Kotlin 编译器编译生成的代码
  ⚠️ 多轮编译，慢；增量编译支持差

KSP（Kotlin 原生符号处理）：
  Kotlin 编译器 → 解析源码 → 生成【PSI 符号树】（不是 stub）
                → KSP 插件直接读符号树 → 生成【Kotlin 源文件】
                → Kotlin 编译器继续编译
  ✅ 快、增量友好、无 stub
```

6. **KSP 的 API 概览**：

```kotlin
// 处理器的入口
class MyProcessorProvider : SymbolProcessorProvider {
    override fun create(environment: SymbolProcessorEnvironment): SymbolProcessor {
        return MyProcessor(environment.codeGenerator, environment.logger)
    }
}

// 处理器的实现
class MyProcessor(
    private val codeGenerator: CodeGenerator,
    private val logger: KSPLogger
) : SymbolProcessor {
    override fun process(resolver: Resolver): List<KSAnnotated> {
        val symbols = resolver.getSymbolsWithAnnotation(MyAnnotation::class.qualifiedName!!)
        symbols.forEach { symbol ->
            val file = codeGenerator.createNewFile(
                Dependencies(false),
                packageName = "com.example.generated",
                fileName = "Generated"
            )
            file.buffer.write("public class Generated { ... }")
        }
        return emptyList()   // 返回空表示不延迟处理
    }
}
```

7. **选型结论**：

| 场景 | 选择 |
| --- | --- |
| **纯 Kotlin 项目** | ✅ **KSP** |
| **纯 Java 项目** | APT（不需要 KSP） |
| **Kotlin + Java 混合，且处理器只支持 Java** | kapt（唯一选择，但慢） |
| **Dagger / Hilt / Room / Glide** | ✅ 都有 KSP 版本，优先用 KSP |
| **需要处理 Java 源码里的注解** | APT（KSP 对 Java 源码支持有限） |

8. **面试话术**："APT 是 javac 的标准注解处理机制——javac 解析源码生成 AST 后调用处理器的 `process()`，处理器通过 `Filer` 生成新的 `.java` 源文件，javac 再把它编入。整个过程是**多轮**的（生成的代码里的注解会再触发处理）。**kapt** 是 Kotlin 的桥接，要先生成 Java stub 再跑 APT，所以慢且增量支持差，**已弃用**；**KSP** 是 Kotlin 编译器原生的符号处理 API，直接读 PSI 符号树不生成 stub，**快且增量友好**，是现在的推荐。Android 项目里的 Dagger/Hilt/Room 都应该用 `ksp(...)`。"

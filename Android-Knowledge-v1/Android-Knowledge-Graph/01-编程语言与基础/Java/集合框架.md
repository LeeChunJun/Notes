# 集合框架

## 一句话定义

Java 集合框架（Collections Framework）是一套为**存储与操作一组对象**设计的统一 API 体系，核心是 `Collection`（List / Set / Queue）与 `Map` 两大分支。面试中最常被追问的是三件事：**`HashMap` 的底层结构与扩容**（数组 + 链表 + 红黑树）、**`ArrayList` 与 `LinkedList` 的取舍**、**`ConcurrentHashMap` 如何在并发下保证安全**（CAS + `synchronized` 桶锁）。Android 里的 `SparseArray`、`ArrayMap`、`CopyOnWriteArrayList` 是平台对通用集合的针对性优化。

## 核心原理

### 1. 集合框架的接口体系

```text
                    java.util
                       │
        ┌──────────────┴──────────────┐
        ▼                             ▼
   Collection                     Map
   （单列）                       （双列）
        │                             │
   ┌────┼────┐              ┌────────┼────────┐
   ▼    ▼    ▼              ▼        ▼        ▼
 List  Set  Queue         HashMap  TreeMap  Hashtable
   │    │    │              │        │        │
   │    │    ├── Deque ←────┘        │        └── Properties
   │    │    └── BlockingQueue        │
   │    │                            │
   │    ├── SortedSet ←─── TreeSet   │
   │    └── NavigableSet             │
   │                                 │
   └── AbstractCollection             └── SortedMap / NavigableMap
       ├── AbstractList                   (TreeMap)
       ├── AbstractSet
       └── AbstractQueue
```

**三大核心接口的语义**：

| 接口 | 语义 | 关键约束 | 典型实现 |
| --- | --- | --- | --- |
| `List` | **有序、可重复** | 按索引访问（`get(i)` O(1)） | `ArrayList`、`LinkedList`、`CopyOnWriteArrayList` |
| `Set` | **无重复** | `equals`/`hashCode` 判重 | `HashSet`、`LinkedHashSet`、`TreeSet` |
| `Queue` / `Deque` | **FIFO / 双端** | 队头出队 | `PriorityQueue`、`ArrayDeque`、`LinkedList` |
| `Map` | **键值对** | 键唯一、按 key 查找 | `HashMap`、`LinkedHashMap`、`TreeMap`、`ConcurrentHashMap` |

**`Collection` 的默认方法（Java 8+）**：

```java
// Collection 接口上的 Stream 与集合视图
default Stream<E> stream()
default Stream<E> parallelStream()
default Spliterator<E> spliterator()
default List<E> toList()                          // Java 16+
default boolean removeIf(Predicate<? super E> filter)
default boolean containsAll(Collection<?> c)
default boolean addAll(Collection<? extends E> c)
```

**Android 特有集合（`android.util`）**：

| 集合 | 底层 | 适用场景 |
| --- | --- | --- |
| `SparseArray<T>` | 稀疏数组（int key → value，**无装箱**） | key 是稀疏 int（id、hashCode） |
| `SparseArrayCompat<T>` | 同上（AndroidX 版本，兼容旧 API） | 同上 |
| `SparseBooleanArray` / `SparseIntArray` / `SparseLongArray` | 原始类型专用 | 免装箱 |
| `ArrayMap<K,V>` | **两个并行数组**（比 HashMap 省内存，查询慢） | key/value 都是小对象、数量少（<几十） |
| `HashMap`（Android 版） | Android 对 HashMap 做了优化 | 常规选择 |

> **面试点**：`ArrayMap` 的内存优势来自"没有 `Node` 对象"（每个 entry 只是两个数组里的两个槽位），代价是二分查找 O(log n) 且 key 必须是可排序的。

### 2. `ArrayList` vs `LinkedList`

| 维度 | `ArrayList` | `LinkedList` |
| --- | --- | --- |
| **底层** | **动态数组**（`Object[] elementData`） | **双向链表**（`Node<E> first/last`） |
| **随机访问 `get(i)`** | ✅ **O(1)**（数组下标） | ❌ **O(n)**（要遍历链表） |
| **尾部添加 `add(e)`** | ✅ **O(1)**（amortized） | ✅ O(1) |
| **头部插入 `add(0, e)`** | ❌ **O(n)**（要移动数组元素） | ✅ O(1) |
| **任意位置插入/删除** | O(n)（移动元素） | O(1)（找到节点后） |
| **查找 `contains/indexOf`** | O(n) | O(n) |
| **内存占用** | **低**（一个数组引用） | **高**（每个元素一个 `Node` 对象：prev/next/item 三个引用） |
| **缓存友好性** | ✅ 好（连续内存） | ❌ 差（节点分散在堆上） |
| **实现接口** | `List` | `List` + `Deque` + `Queue` |
| **GC 压力** | 低 | 高（大量小对象） |

**`ArrayList` 的扩容机制（面试高频）**：

```java
// JDK 8+ 源码简化
private static final int DEFAULT_CAPACITY = 10;
private static final int MAX_ARRAY_SIZE = Integer.MAX_VALUE - 8;

private Object[] elementData;
private int size;

public boolean add(E e) {
    ensureCapacityInternal(size + 1);   // ① 确保容量
    elementData[size++] = e;           // ② 赋值
    return true;
}

private void ensureCapacityInternal(int minCapacity) {
    if (minCapacity - elementData.length > 0) {
        grow(minCapacity);
    }
}

private void grow(int minCapacity) {
    int oldCapacity = elementData.length;
    int newCapacity = oldCapacity + (oldCapacity >> 1);   // ① 1.5 倍增长
    if (newCapacity - minCapacity < 0) newCapacity = minCapacity;
    if (newCapacity - MAX_ARRAY_SIZE > 0) newCapacity = hugeCapacity(minCapacity);
    elementData = Arrays.copyOf(elementData, newCapacity);  // ② 复制数组
}
```

**关键点**：

1. **默认容量 10**，`new ArrayList<>()` 是**延迟分配**的（JDK 8+ 初始为**空数组**，第一次 add 才分配 10）。
2. **扩容为 1.5 倍**（`oldCapacity + (oldCapacity >> 1)`），不是 2 倍。
3. **`Arrays.copyOf` 是 O(n) 复制** → 所以"扩容是 O(n)"，但**摊还（amortized）O(1)**（因为扩容频率是指数级递减的）。
4. **`remove` 不会缩容**（`size` 减小但 `elementData` 不变）→ 内存不会还给 GC，除非 `trimToSize()`。

> **Android 特有**：`ArrayList` 在 Android 上同样是动态数组；`android.util.SparseArray` 是"int key 免装箱"的替代。

### 3. `ArrayDeque` 与 `PriorityQueue`

**`ArrayDeque`**：基于**环形数组**实现的双端队列。

| 特性 | 说明 |
| --- | --- |
| **底层** | `Object[] elements`（环形） |
| **不允许 null** | ❌ 插入 null 抛 `NullPointerException`（用于区分"空队列"和"null 元素"） |
| **头部/尾部增删** | ✅ **O(1)**（均摊） |
| **栈用途** | `push/pop/peek` = `addFirst/removeFirst/peekFirst` |
| **队列用途** | `offer/poll/peek` |
| **替代 LinkedList** | ✅ **推荐**：更好的缓存局部性、更少的内存开销、无 null 限制问题 |

```java
// 用 ArrayDeque 实现栈（比 LinkedList 快）
Deque<Integer> stack = new ArrayDeque<>();
stack.push(1); stack.push(2);
int top = stack.pop();

// 用 ArrayDeque 实现 BFS 队列
Deque<Node> queue = new ArrayDeque<>();
queue.offer(root);
while (!queue.isEmpty()) {
    Node n = queue.poll();
    queue.offer(n.left);
    queue.offer(n.right);
}
```

**`PriorityQueue`**：二叉堆实现的**优先队列**。

- 底层：`Object[] queue` + **二叉堆**。
- **不是有序的**——`iterator()` 遍历出的顺序**不保证排序**！要排序需 `new PriorityQueue<>(c).poll()` 逐个取出，或先放入 `List` 再排序。
- 时间复杂度：`offer`/`poll` **O(log n)**；`peek` O(1)。
- **不允许 null**。

### 4. `CopyOnWriteArrayList`

**写时复制（Copy-On-Write）**：写操作时**复制整个底层数组**，然后替换引用。

```java
public class CopyOnWriteArrayList<E> implements List<E>, RandomAccess {
    private volatile Object[] array;   // volatile 保证可见性

    public boolean add(E e) {
        synchronized (lock) {
            Object[] newArray = Arrays.copyOf(array, array.length + 1);
            newArray[array.length] = e;
            array = newArray;          // 原子替换引用
            return true;
        }
    }

    public E get(int index) {
        return (E) array[index];       // 读不加锁 ✅
    }

    public Iterator<E> iterator() {
        return new COWIterator<>(array);   // 迭代器持有快照
    }
}
```

| 特性 | 说明 |
| --- | --- |
| **读性能** | ✅ **无锁**，极高（直接读 volatile 数组） |
| **写性能** | ❌ 极低（每次写都 **O(n) 复制**整个数组） |
| **迭代器** | ✅ **不会抛 `ConcurrentModificationException`**（基于快照） |
| **迭代器弱一致性** | 迭代过程中看到的可能是**旧数据**，不保证最新 |
| **内存** | 写操作产生大量临时数组 → GC 压力大 |
| **线程安全** | ✅ 单个方法原子；多个方法的**组合不是原子的** |

**适用场景（面试标准答案）**：

1. ✅ **读多写少**（如配置列表、黑名单、路由表、监听器列表）。
2. ✅ **需要遍历时不能抛 `ConcurrentModificationException`**。
3. ✅ **迭代器需要快照语义**。
4. ❌ **写频繁**（写放大严重）。
5. ❌ **需要强一致的多方法组合**（如 `if (!list.isEmpty()) list.get(0)` 不是原子的）。

**典型用途**：

```java
// ① 事件监听器列表（注册少、触发频繁）
private final CopyOnWriteArrayList<Listener> listeners = new CopyOnWriteArrayList<>();
void notifyAll() {
    for (Listener l : listeners) {      // 迭代器是快照，安全
        l.onEvent();
    }
}

// ② Android 中的典型：观察者列表
```

### 5. `HashMap` 底层结构：数组 + 链表 + 红黑树

#### 5.1 数据结构

```text
HashMap (table: Node[])
   │
   ├─ bucket[0] → null
   ├─ bucket[1] → null
   ├─ bucket[2] → Node(key=1,val=A) → Node(key=3,val=C) → Node(key=9,val=I)   ← 链表
   ├─ bucket[3] → null
   └─ bucket[4] → TreeNode(key=5) → TreeNode(key=7) → ...                          ← 红黑树
```

**`Node` 结构**（JDK 8+）：

```java
static class Node<K, V> implements Map.Entry<K, V> {
    final int hash;          // 缓存的 hashCode（扰动后的）
    final K key;
    V value;
    Node<K, V> next;         // 链表指针（红黑树时指向树节点）
    Node(int hash, K key, V value, Node<K,V> next) { ... }
}
```

#### 5.2 `put` 的完整流程

```java
public V put(K key, V value) {
    int hash = hash(key);                      // ① 计算 hash（扰动）
    if ((tab = table) == null || (n = tab.length) == 0)
        n = (tab = resize()).length;           // ② 首次 → 初始化并扩容
    if ((p = tab[i = (n - 1) & hash]) == null)  // ③ 定位桶（取模用位运算）
        tab[i] = newNode(hash, key, value, null);
    else {
        // ④ 桶不为空
        if (p.hash == hash && ((k = p.key) == key || (key != null && key.equals(k))))
            p.value = value;                   // ⑤ 已存在 → 覆盖 value
        else if (p instanceof TreeNode)
            ((TreeNode<K,V>)p).putTreeVal(this, tab, hash, key, value);   // ⑥ 红黑树插入
        else {
            Node<K,V> e; int b, binCount = 0;
            for (; (e = p.next) != null; p = e.next, ++binCount) {
                if (e.hash == hash && ((k = e.key) == key || (key != null && key.equals(k))))
                    break;                      // ⑦ 遍历链表找相同 key
            }
            if (e == null) {
                p.next = newNode(hash, key, value, null);   // ⑧ 追加到链表尾部
                if (binCount >= TREEIFY_THRESHOLD - 1)      // ⑨ 链表长度 ≥ 8 → 树化
                    treeifyBin(tab, hash);
            } else if (oldValue != null)
                e.value = value;
        }
    }
    ++size;
    afterInsertion(true);
    return oldValue;
}
```

#### 5.3 hash 扰动函数

```java
static final int hash(Object key) {
    int h;
    return (key == null) ? 0 : (h = key.hashCode()) ^ (h >>> 16);
    //                        ↑ 高位异或到低位：把高位信息混入低位
}
```

**为什么要 `h ^ (h >>> 16)`**：

```text
HashMap 定位桶：(n - 1) & hash
  ↑ n 是 2 的幂，(n-1) 是低位全 1 的掩码
  ↑ 所以只有 hash 的【低位】参与定位！

问题：hashCode() 的高位信息会被完全丢弃
  例：hashCode = 0xABCD0000 和 0xABCD0001
       低 16 位都是 0 → 定位到同一个桶 → 冲突加剧

解决：h ^ (h >>> 16) 把高 16 位异或到低 16 位
       → 0xABCD0000 → 0xABCD0000
       → 0xABCD0001 → 0xABCD0000 ^ 0x0001 = 0xABCD0001
       → 低位差异被保留 ✅
```

#### 5.4 为什么容量必须是 2 的幂

```text
取模：(n - 1) & hash
  n = 16 (2^4) → n-1 = 0b1111
  hash & 0b1111 = hash 的低 4 位  ← 等价于 hash % 16 ✅（只对 2 的幂成立）

为什么不用 % ？
  % 是除法指令（较慢），& 是位运算（极快）⚡
  而且 % 对负数处理不同，& 不会有负数问题

扩容时：
  容量翻倍 → n-1 的掩码多一位 → 原来的 hash 依然适用
  扩容后元素要么留在原位，要么移动到「原位 + oldCap」
  → 迁移成本可控（见 5.6）
```

**代价**：初始容量不是 2 的幂时，`HashMap` 会**向上取整到最近的 2 的幂**。

```java
// ✅ 最佳实践：预估容量，避免多次扩容
// 期望存入 12 个元素 → 初始容量设为 16（12/0.75 = 16）
HashMap<String, String> map = new HashMap<>(16);
```

#### 5.5 扩容过程（resize）

```java
final Node<K,V>[] resize() {
    Node<K,V>[] oldTab = table;
    int oldCap = (oldTab == null) ? 0 : oldTab.length;
    int oldThr = threshold;
    int newCap, newThr = 0;
    if (oldCap > 0) {
        if (oldCap >= MAXIMUM_CAPACITY) {
            threshold = Integer.MAX_VALUE;
            return oldTab;
        }
        else if ((newCap = oldCap << 1) < MAXIMUM_CAPACITY && oldCap >= DEFAULT_INITIAL_CAPACITY)
            newThr = newCap * (int) loadFactor;      // 阈值翻倍
    }
    else if (oldThr > 0) newCap = oldThr;
    else { newCap = DEFAULT_INITIAL_CAPACITY; newThr = (int)(DEFAULT_LOAD_FACTOR * DEFAULT_INITIAL_CAPACITY); }

    Node<K,V>[] newTab = new Node[newCap];           // 分配新数组
    if (oldTab != null) {
        for (int j = 0; j < oldCap; ++j) {
            Node<K,V> e;
            if ((e = oldTab[j]) != null) {
                oldTab[j] = null;
                if (e.next == null)                    // 只有一个元素
                    newTab[e.hash & (newCap - 1)] = e;
                else if (e instanceof TreeNode)
                    ((TreeNode<K,V>)e).split(this, newTab, j, oldCap);
                else {                                // 链表拆分
                    Node<K,V> loHead = null, loTail = null;
                    Node<K,V> hiHead = null, hiTail = null;
                    do {
                        Node<K,V> next = e.next;
                        if ((e.hash & oldCap) == 0) {  // ① hash & oldCap == 0 → 留在原位
                            if (loTail == null) loHead = e;
                            else loTail.next = e;
                            loTail = e;
                        } else {                       // ② 否则移动到 原位 + oldCap
                            if (hiTail == null) hiHead = e;
                            else hiTail.next = e;
                            hiTail = e;
                        }
                    } while ((e = next) != null);
                    if (loTail != null) { loTail.next = null; newTab[j] = loHead; }
                    if (hiTail != null) { hiTail.next = null; newTab[j + oldCap] = hiHead; }
                }
            }
        }
    }
    table = newTab;
    threshold = newThr;
    return newTab;
}
```

**扩容的巧妙之处**：因为容量是 2 的幂，扩容后元素的新位置只有**两个可能**：

```text
原来的桶下标：hash & (oldCap - 1)
扩容后下标：    hash & (newCap - 1) = hash & (2*oldCap - 1)

结论：新下标要么等于【原下标】，要么等于【原下标 + oldCap】

判断方法：if ((hash & oldCap) == 0) → 留在原位
          else                    → 移到 原位 + oldCap

→ 不需要重新计算 hash，也不需要重新分配每个元素的桶 ✅
→ 但仍需要遍历旧数组重建链表
```

**注意**：链表**拆分**成两条（`loHead/hiHead`），JDK 8 用了 `do-while` 循环来避免额外的 `e.next == null` 检查。

#### 5.6 树化（Treeify）机制

| 常量 | 值 | 含义 |
| --- | --- | --- |
| `TREEIFY_THRESHOLD` | 8 | 链表长度 ≥ 8 → 树化 |
| `UNTREEIFY_THRESHOLD` | 6 | 红黑树节点数 ≤ 6 → 退化为链表 |
| `MIN_TREEIFY_CAPACITY` | 64 | 数组容量 < 64 时**不树化**（直接扩容） |

**树化的双重条件**（`treeifyBin`）：

```java
final void treeifyBin(Map.Entry<K,V>[] tab, int hash) {
    int n = tab.length;
    if (n < MIN_TREEIFY_CAPACITY)             // ① 容量不足 → resize 而不是树化
        resize();
    else {
        Node<K,V> e = tab[(n - 1) & hash];
        if (e != null && (e instanceof TreeNode || ((e = e.next) != null))) {
            tab[(n - 1) & hash] = new TreeNode<>(tab, e);   // ② 真正的树化
            ((TreeNode<K,V>)tab[(n - 1) & hash]).split(this, tab, hash);
        }
    }
}
```

> **为什么容量 < 64 不树化？**
> 树节点（`TreeNode`）的内存开销约是普通 `Node` 的 **2 倍**（多了 parent/left/right/prev 四个引用）。链表长度到 8 说明冲突比较严重，但此时扩容到 64 通常更划算——既能分散冲突，又避免了大量树节点的内存开销。**经验值：桶少时优先扩容，桶多时优先树化。**

**树化的收益**：链表查找 O(n) → 红黑树 O(log n)。在恶意构造大量相同 hash 的场景下（如攻击者故意制造 hash 碰撞），能把 O(n) 的 DoS 攻击降到 O(log n)。

### 6. `LinkedHashMap` 与 `TreeMap`

**`LinkedHashMap`**：在 `HashMap` 的 `Node` 基础上**多一个 `before/after` 双向链表指针**，维护**插入顺序**（或访问顺序，可开启 LRU）。

```java
// LRU Cache 的标准实现
public class LruCache<K, V> extends LinkedHashMap<K, V> {
    private final int maxSize;

    public LruCache(int maxSize) {
        super(16, 0.75f, true);        // 第三个参数 accessOrder = true
        this.maxSize = maxSize;
    }

    @Override
    protected boolean removeEldestEntry(Map.Entry<K, V> eldest) {
        return size() > maxSize;
    }
}
```

**`TreeMap`**：基于**红黑树**实现，key 有序（自然序或自定义 `Comparator`）。

| 操作 | `HashMap` | `TreeMap` |
| --- | --- | --- |
| `get/put` | O(1) | **O(log n)** |
| `firstKey/lastKey` | O(n) | **O(log n)** |
| `floorKey/ceilingKey` | ❌ | ✅ |
| `subMap/headMap/tailMap` | ❌ | ✅ |
| 遍历顺序 | 无序 | **有序** |

**Android 中的替代**：`TreeMap` 在 Android 上比 `HashMap` 慢很多，Google 官方文档明确建议**避免在 Android 上使用 `TreeMap` 和 `LinkedHashMap`**，优先用 `HashMap`。

### 7. `HashSet` 的实现

```java
public class HashSet<E> extends AbstractSet<E> implements Set<E> {
    private static final Object PRESENT = new Object();
    private final Map<E, Object> map;      // ✅ 用 HashMap 承载

    public HashSet() {
        map = new HashMap<>();
    }
    public boolean add(E e)      { return map.put(e, PRESENT) == null; }
    public boolean remove(Object o) { return map.remove(o) == PRESENT; }
    public boolean contains(Object o) { return map.containsKey(o); }
    public int size() { return map.size(); }
}
```

> **面试点**：`HashSet` **没有额外的内存开销**，它就是**用 `HashMap` 的 key 集合**实现的（value 统一是一个 `PRESENT` 哨兵对象）。`LinkedHashSet` 同理基于 `LinkedHashMap`。

### 8. `ConcurrentHashMap`：并发容器

#### 8.1 JDK 7 vs JDK 8 的演进

| | JDK 7 | JDK 8+ |
| --- | --- | --- |
| **结构** | `Segment` 数组 + `HashEntry` 链表 | `Node` 数组 + 链表 + 红黑树（**与 HashMap 一样**） |
| **并发控制** | **分段锁（Segment Lock）**：默认 16 个 Segment，每段一把锁 | **桶锁（Bucket Lock）+ CAS + synchronized** |
| **并发度** | 固定为 Segment 数量（默认 16） | **= 桶数**（可动态扩展） |
| **扩容** | 需要**多个 Segment 同时扩容**，可能死锁 | 单个桶逐个迁移，**无死锁** |
| **size()** | 需要统计所有 Segment | 用 `baseCount` + `CounterCell` 分散计数 |

#### 8.2 JDK 8+ 的核心机制

```java
public class ConcurrentHashMap<K, V> extends AbstractMap<K, V> implements ConcurrentMap<K, V> {
    private static final int DEFAULT_CAPACITY = 16;
    private static final int MAXIMUM_CAPACITY = 1 << 30;
    private static final int DEFAULT_CONCURRENCY_LEVEL = 16;

        final K key;

        Node(int hash, K key, V value, Node<K,V> next) { ... }
    }

    transient volatile Node<K,V>[] table;      // ✅ volatile
    private volatile long baseCount;
    private transient volatile CounterCell[] counterCells;
    private volatile int sizeCtl;              // 扩容阈值 / 状态标记
```

**`putVal` 的核心流程**：

```java
final V putVal(K key, V value, boolean onlyIfAbsent) {
    if (key == null || value == null) throw new NullPointerException();
    int hash = spread(key.hashCode());      // ① 扰动 hash
    int binCount = 0;
    for (Node<K,V>[] tab = table;;) {
        Node<K,V> f; int n, i, fh;
        if (tab == null || (n = tab.length) == 0)
            tab = initTable();               // ② 初始化表
        else if ((f = tabAt(tab, i = (n - 1) & hash)) == null) {
            if (casTabAt(tab, i, null, new Node<K,V>(hash, key, value, null)))   // ③ CAS 放入空桶
                break;
        }
        else if ((fh = f.hash) == MOVED)      // ④ 该桶正在扩容 → helpJoin
            helpTransfer(tab, fh);
        else {
            boolean added = false;
            synchronized (f) {               // ⑤ 锁住桶头节点
                if (tabAt(tab, i) == f) {
                    if (fh >= 0) {           // ⑥ 链表
                        for (Node<K,V> e = f;; ++binCount) {
                            if (e.hash == hash && ((ek = e.key) == key || (ek != null && key.equals(ek)))) {
                                oldVal = e.value;
                                if (!onlyIfAbsent && oldVal != null)
                                    e.value = value;     // ⑦ 覆盖 value（volatile 写）
                                break;
                            }
                            if ((e = e.next) == null) {
                                if (casNext(f, e, new Node<K,V>(hash, key, value, null)))  // ⑧ CAS 追加
                                    break;
                            }
                        }
                    }
                    else if (f instanceof TreeNode)   // ⑨ 红黑树
                        added = ((TreeNode<K,V>)f).putTreeVal(this, tab, hash, key, value);
                }
            }
            if (added) break;
        }
    }
    addCount(1L, binCount);
    return oldVal;
}
```

**三个关键点**：

1. **`tabAt` 用 `getObjectVolatile` 读取**（`Unsafe.getObjectVolatile`），保证读到的是**最新**的桶头节点。
2. **空桶插入用 CAS**：不需要加锁。
3. **非空桶加 `synchronized` 锁桶头节点**：**锁的粒度是"桶"而不是"整个 Map"**——这正是 JDK 8 去掉 `Segment` 的原因（`Segment` 本质上就是一个"大粒度的桶锁"包装，JDK 8 把它下推到了桶级别）。

#### 8.3 `size()` 为什么昂贵

```java
public int size() {
    long sum = 0;
    CounterCell[] cs = counterCells;
    if (cs != null) {
        for (CounterCell c : cs)
            if (c != null) sum += c.value;
    }
    return sum + baseCount;
}
```

- `baseCount` 是一个 `long`，`addCount` 用 **CAS** 更新。
- **CAS 失败**时，创建一个 `CounterCell` 把计数分散到数组里（**分散计数**，`LongAdder` 的思想）。
- 原因：如果所有线程都 CAS 同一个 `baseCount`，高并发下 CAS 失败率高，性能反而差。

#### 8.4 与其他并发方案对比

| 方案 | 锁粒度 | 读性能 | 写性能 | 迭代器 | 适用 |
| --- | --- | --- | --- | --- | --- |
| `Hashtable` | **整表** `synchronized` | ❌ 慢 | ❌ 慢 | 抛 CME | 基本不用 |
| `Collections.synchronizedMap` | **整表** 外部锁 | ❌ 慢 | ❌ 慢 | 需手动 `sync` | 简单包装 |
| **`ConcurrentHashMap`** | **桶级** | ✅ 无锁读 | ✅ CAS + 桶锁 | ✅ 弱一致 | ✅ **首选** |
| `CopyOnWriteArrayList` | 写时复制 | ✅ 无锁读 | ❌ 极慢 | ✅ 快照 | 读多写少 |

### 1. `HashMap` 的手写实现（理解底层）

```java
/**
 * 手写简化版 HashMap，展示：
 * 1. 数组 + 链表
 * 2. hash 扰动
 * 3. 扩容（1.5 倍）与元素迁移
 * 4. 为什么容量是 2 的幂
 */
public class SimpleHashMap<K, V> {

    /** 链表节点 */
    static class Node<K, V> {
        final int hash;
        final K key;
        V value;
        Node<K, V> next;

        Node(int hash, K key, V value, Node<K, V> next) {
            this.hash = hash;
            this.key = key;
            this.value = value;
            this.next = next;
        }
    }

    private static final int DEFAULT_CAPACITY = 16;
    private static final float LOAD_FACTOR = 0.75f;

    private Node<K, V>[] table;
    private int size;
    private int threshold;

    @SuppressWarnings("unchecked")
    public SimpleHashMap() {
        table = new Node[DEFAULT_CAPACITY];
        threshold = (int) (DEFAULT_CAPACITY * LOAD_FACTOR);
    }

    /** hash 扰动：把高 16 位混入低 16 位，避免高位信息被丢弃 */
    private static int hash(Object key) {
        if (key == null) return 0;
        int h = key.hashCode();
        return h ^ (h >>> 16);
    }

    public V put(K key, V value) {
        int h = hash(key);
        int index = (table.length - 1) & h;      // 位运算取模（容量是 2 的幂）
        Node<K, V> node = table[index];

        // 桶为空
        if (node == null) {
            table[index] = new Node<>(h, key, value, null);
            size++;
            if (size > threshold) resize();
            return null;
        }

        // 遍历链表
        Node<K, V> prev = null;
        while (node != null) {
            if (node.hash == h && (node.key == key || (key != null && key.equals(node.key)))) {
                V old = node.value;
                node.value = value;
                return old;
            }
            prev = node;
            node = node.next;
        }
        // 未找到，追加到链表尾部
        prev.next = new Node<>(h, key, value, null);
        size++;
        if (size > threshold) resize();
        return null;
    }

    public V get(Object key) {
        int h = hash(key);
        int index = (table.length - 1) & h;
        for (Node<K, V> node = table[index]; node != null; node = node.next) {
            if (node.hash == h && (node.key == key || (key != null && key.equals(node.key)))) {
                return node.value;
            }
        }
        return null;
    }

    /** 扩容：容量 × 2，并把元素从原桶拆分到「原位」和「原位 + oldCap」 */
    @SuppressWarnings("unchecked")
    private void resize() {
        Node<K, V>[] oldTable = table;
        int oldCap = oldTable.length;
        Node<K, V>[] newTable = new Node[oldCap << 1];
        threshold = (int) (newTable.length * LOAD_FACTOR);

        for (int j = 0; j < oldCap; j++) {
            Node<K, V> e = oldTable[j];
            if (e == null) continue;

            Node<K, V> loHead = null, loTail = null;   // 留在原位
            Node<K, V> hiHead = null, hiTail = null;   // 移动到 j + oldCap

            while (e != null) {
                Node<K, V> next = e.next;
                if ((e.hash & oldCap) == 0) {
                    if (loTail == null) loHead = e; else loTail.next = e;
                    loTail = e;
                } else {
                    if (hiTail == null) hiHead = e; else hiTail.next = e;
                    hiTail = e;
                }
                e = next;
            }
            if (loTail != null) { loTail.next = null; newTable[j] = loHead; }
            if (hiTail != null) { hiTail.next = null; newTable[j + oldCap] = hiHead; }
        }
        table = newTable;
    }

    public int size() { return size; }
}
```

```java
    private final ConcurrentHashMap<String, List<String>> grouped = new ConcurrentHashMap<>();

    /**
     * ✅ 原子读改写：computeIfAbsent 保证同一 key 只初始化一次

        counters.computeIfAbsent(key, k -> new AtomicInteger(0))
                .incrementAndGet();

     * ✅ 原子分组：避免 "containsKey + put" 的竞态

    public void addToGroup(String group, String item) {

                .add(item);
    }

    /**
     * ✅ 原子 merge：多个线程累加同一个计数
     */
    private final ConcurrentHashMap<String, Long> sums = new ConcurrentHashMap<>();

    public void addSum(String key, long delta) {
        sums.merge(key, delta, Long::sum);
    }

    /**
     * ❌ 错误写法：containsKey + put 不是原子的

    public void addWrong(String key, String value) {
        if (!grouped.containsKey(key)) {
            grouped.put(key, new ArrayList<>());     // ❌ 竞态
        }
        grouped.get(key).add(value);
    }

    /**
     * ✅ 正确写法
     */
    public void addCorrect(String key, String value) {
        grouped.computeIfAbsent(key, k -> new ArrayList<>()).add(value);
    }

    /**
     * ✅ 遍历：ConcurrentHashMap 的迭代器是弱一致的，不会抛 CME
     */
    public Map<String, Integer> snapshot() {
        Map<String, Integer> result = new HashMap<>();
        for (Map.Entry<String, AtomicInteger> e : counters.entrySet()) {
            result.put(e.getKey(), e.getValue().get());
        }
        return result;
    }
```

### 4. `ArrayDeque` vs `LinkedList` vs `PriorityQueue`

```java
/**
 * 队列与栈的正确选型。
 */
public class QueueDemo {

    /**
     * ✅ BFS 队列：用 ArrayDeque（比 LinkedList 更快更省内存）
     */
    public List<Integer> bfs(int[][] graph, int start) {
        List<Integer> result = new ArrayList<>();
        boolean[] visited = new boolean[graph.length];
        Deque<Integer> queue = new ArrayDeque<>();     // ✅ 环形数组实现
        queue.offer(start);
        visited[start] = true;

        while (!queue.isEmpty()) {
            int cur = queue.poll();
            result.add(cur);
            for (int next : graph[cur]) {
                if (!visited[next]) {
                    visited[next] = true;
                    queue.offer(next);
                }
            }
        }
        return result;
    }

    /**
     * ✅ 栈：用 ArrayDeque（不要用 LinkedList）
     */
    public int[] reverse(int[] input) {
        Deque<Integer> stack = new ArrayDeque<>();
        for (int i : input) stack.push(i);
        int[] out = new int[input.length];
        for (int i = 0; i < out.length; i++) out[i] = stack.pop();
        return out;
    }

    /**
     * ✅ 优先队列：Top-K 问题
     * 注意：PriorityQueue【本身不是有序的】，需要逐个 poll 才是有序的
     */
    public int[] topK(int[] nums, int k) {
        PriorityQueue<Integer> pq = new PriorityQueue<>(k);   // 小顶堆
        for (int n : nums) {
            pq.offer(n);
            if (pq.size() > k) pq.poll();       // 移除最小
        }
        int[] result = new int[pq.size()];
        // 从大到小取出：先 poll 到底，再反转
        for (int i = result.length - 1; i >= 0; i--) result[i] = pq.poll();
        return result;
    }
}
```

## 常见问题 / 面试要点

**读者问：`HashMap` 的底层数据结构是什么？为什么数组长度必须是 2 的幂？**

**AI答：**

1. **数据结构（JDK 8+）**：**数组 + 链表 + 红黑树**。
   - 主结构是 `Node[] table`（数组）。
   - 冲突时先用**链表**追加（`Node.next`）。
   - 单个桶的链表长度 **≥ 8**（`TREEIFY_THRESHOLD`）且**数组容量 ≥ 64**（`MIN_TREEIFY_CAPACITY`）时，**树化**为红黑树。
   - 红黑树节点数 **≤ 6**（`UNTREEIFY_THRESHOLD`）时**退化**回链表。

2. **为什么容量是 2 的幂**：

```java
// 定位桶
int index = (n - 1) & hash;      // n = table.length
```

   - `n` 是 2 的幂时，`n-1` 是**二进制全 1**（如 `16-1 = 0b1111`），所以 `(n-1) & hash` **等价于 `hash % n`**，但用的是**位运算**（比除法快得多，且没有负数问题）。
   - 扩容时（容量翻倍），掩码多一位，元素的新位置只有**两种可能**：`原位` 或 `原位 + oldCap`，可以用 `(hash & oldCap) == 0` 判断，**无需重新计算 hash**。
   - 代价：传入非 2 的幂初始容量时会被**向上取整**。

3. **负载因子**：`0.75`（默认）。`threshold = capacity * 0.75`。超过就扩容 → **空间与时间的折中**：平均负载越低冲突越少，但内存浪费越多。

4. **树化阈值为什么是 8**：链表查找 O(n)，8 次比较已经不划算；红黑树 O(log n)。同时 `MIN_TREEIFY_CAPACITY = 64` 保证"桶少时优先扩容"（红黑树节点内存是普通节点的 2 倍）。

5. **面试话术**："JDK 8 的 `HashMap` 是**数组 + 链表 + 红黑树**。容量取 2 的幂是为了用 `(n-1) & hash` 替代取模，并且让扩容时的元素迁移只需要判断 `hash & oldCap` 就能确定新位置。链表长度到 8 且数组容量到 64 才树化，是为了在'冲突严重'和'内存开销'之间取平衡。"

**读者问：`HashMap` 的扩容过程是怎样的？为什么扩容是 O(1) 的？**

**AI答：**

1. **触发条件**：`size > threshold`（`threshold = capacity * 0.75`），在 `put` 之后检查。

2. **扩容倍数**：**2 倍**（`newCap = oldCap << 1`），同时 `threshold` 也翻倍。

3. **迁移算法**（`resize()`）：

```text
旧数组：oldTab[0..oldCap-1]
新数组：newTab[0..2*oldCap-1]

对每个旧桶 j 的链表：
  遍历节点 e：
    if ((e.hash & oldCap) == 0)
        → 放入 newTab[j]            （留在原位）
    else
        → 放入 newTab[j + oldCap]    （移动到 原位 + oldCap）
```

4. **为什么这样是对的**：

```text
旧下标 = hash & (oldCap - 1)     （取低 log2(oldCap) 位）
新下标 = hash & (2*oldCap - 1)    （取低 log2(oldCap)+1 位）

新下标比旧下标只多了一个"最高位"的判断：
  新增的那一位 = hash & oldCap
  → 为 0 → 新下标 = 旧下标
  → 为 1 → 新下标 = 旧下标 + oldCap
```

   → **扩容时不需要重新计算 hash，也不需要重新分配桶**，只需要把一条链表拆成两条。

5. **"O(1) 的扩容"是误解——正确说法是"均摊 O(1)"**：
   - **单次扩容**是 O(n)（要遍历所有桶迁移元素）。
   - 但扩容次数是 **O(log n)**，每次翻倍，所以**摊还到每次 `put` 是 O(1)**（类似动态数组的摊还分析）。
   - 严格地说：n 次插入的总成本是 O(n)，所以均摊 O(1)。

6. **JDK 7 vs JDK 8 的迁移差异**：
   - **JDK 7**：头插法迁移（`e.next = newTab[i]; newTab[i] = e;`）→ **会颠倒链表顺序**（并发下可能形成环）。
   - **JDK 8**：**尾插法**（拆成 `loHead/loHead` 两条链）→ 保持顺序，无环。

7. **面试话术**："扩容是 2 倍，迁移时元素的新位置只有'原位'和'原位 + oldCap'两种，靠 `hash & oldCap` 一位判断就能确定，所以不需要重新算 hash。单次扩容是 O(n)，但扩容次数是 log 级，摊还到每次插入是 O(1)。JDK 8 用尾插法迁移，还修掉了 JDK 7 头插法可能形成环形链的 bug。"

**读者问：`ConcurrentHashMap` 是怎么保证线程安全的？和 `Hashtable` 有什么区别？**

**AI答：**

1. **JDK 8+ 的三大机制**：

| 机制 | 说明 |
| --- | --- |
| **① CAS** | **桶为空**时插入：用 `casTabAt` 无锁插入；`tabAt` 用 `getObjectVolatile` 读，保证看到最新桶头 |
| **② 桶级 `synchronized`** | **桶不为空**时：锁住**桶头节点**（`synchronized (f)`），只影响同一个桶的并发 |
| **③ volatile** | `Node.value`、`Node.next`、`table` 都是 `volatile`，保证可见性与有序性 |

2. **与 `Hashtable` / `synchronizedMap` 的核心区别——锁粒度**：

```text
Hashtable / synchronizedMap：整表一把锁
  线程 A 写 bucket[1]  ─┐
  线程 B 读 bucket[2]  ─┴─→ 互相阻塞 ❌

ConcurrentHashMap：桶级锁
  线程 A 写 bucket[1]  ──► 锁 bucket[1]
  线程 B 读 bucket[2]  ──► 不受影响 ✅ 并发度 = 桶数
```

3. **JDK 7 vs JDK 8 的演进**：

| | JDK 7 | JDK 8+ |
| --- | --- | --- |
| 结构 | `Segment[]` + `HashEntry` 链表 | `Node[]` + 链表 + 红黑树 |
| 锁 | **分段锁**：16 个 Segment，每段一把 `ReentrantLock` | **桶锁 + CAS + synchronized** |
| 并发度上限 | 16（固定） | = 桶数（可扩展到数千） |
| 扩容 | 多 Segment 同时扩容，**可能死锁** | 单桶逐个迁移，**无死锁** |
| `size()` | 遍历所有 Segment | `baseCount` + `CounterCell` 分散计数 |

4. **`size()` 为什么昂贵**：

```java
private void addCount(long x, int binCount) {
    Cell[] cs; long b, v; int m; Cell c;
    if ((cs = counterCells) != null || casBaseCount(b = baseCount, b + x)) return;
    // CAS 成功 → 直接更新 baseCount
    // CAS 失败 → 创建 CounterCell 分散计数（LongAdder 思想）
}
```

   → 高并发下所有线程 CAS 同一个变量会大量失败，**分散到数组**可以显著提升成功率。

5. **读操作完全无锁**：`get()` 只是 `tabAt`（volatile 读）+ 遍历链表/树，无任何同步。

6. **迭代器是弱一致的**：不会抛 `ConcurrentModificationException`，也不保证看到最新数据。

7. **面试话术**："JDK 8 的 `ConcurrentHashMap` 用 **CAS + 桶级 `synchronized`**：空桶插入走 CAS 完全无锁，非空桶只锁桶头节点，锁粒度比整表锁细得多，**并发度等于桶数**。JDK 7 的 `Segment` 分段锁本质上是'大粒度桶锁'，JDK 8 把它下推到桶级别，顺带解决了扩容死锁问题。"

**读者问：`ArrayList` 和 `LinkedList` 怎么选？为什么几乎所有人都用 `ArrayList`？**

**AI答：**

1. **核心对比**：

| 维度 | `ArrayList` | `LinkedList` |
| --- | --- | --- |
| 底层 | **动态数组** | **双向链表** |
| `get(i)` | **O(1)** | **O(n)** |
| 尾部添加 | O(1) | O(1) |
| 头部插入 | O(n) | O(1) |
| 内存 | **低**（1 个数组） | **高**（每元素 1 个 `Node`，3 个引用） |
| 缓存友好 | **✅ 连续内存** | ❌ 节点分散 |
| GC 压力 | **低** | 高（大量小对象） |

2. **`LinkedList` 唯一的理论优势是"头部插入 O(1)"，但实际几乎不成立**：
   - 现实场景中头部插入很少，尾部添加才是主流（两者都是 O(1)）。
   - `LinkedList` 的 `get(i)` 是 O(n)——而**按下标访问**恰恰是 `List` 最常用的操作。
   - `LinkedList` 每个元素多一个 `Node` 对象（24-32 字节），**GC 压力大**，Android 上尤其明显。
   - `LinkedList` 的节点在堆上**不连续**，CPU 缓存命中率差，实测吞吐往往低于 `ArrayList`。

3. **`LinkedList` 实际能用的场景**：
   - 需要**频繁在中间插入/删除**且**已知节点位置**（持有迭代器或节点引用）。
   - 需要**双端队列**语义 → 但应该用 **`ArrayDeque`**（环形数组，更快更省）。
   - 需要实现**链表结构的数据结构**（如 LRU 的双向链表节点）。

4. **Android 上的建议**：
   - Google 官方文档明确：**避免使用 `LinkedList` 和 `TreeMap`**（性能在移动端更差）。
   - 用 `ArrayList` 或 `ArrayDeque` 替代。

5. **`ArrayList` 的扩容**：
   - 初始容量 10（**JDK 8+ 首次 add 才真正分配**）。
   - 扩容 **1.5 倍**：`oldCapacity + (oldCapacity >> 1)`。
   - `Arrays.copyOf` → 单次扩容 O(n)，**摊还 O(1)**。
   - `remove` **不缩容** → 需要 `trimToSize()` 手动回收。

6. **面试话术**："几乎总是 `ArrayList`：随机访问 O(1)、内存连续、缓存友好、GC 压力小。`LinkedList` 唯一的优势是头部插入 O(1)，但这个场景应该用 `ArrayDeque`；而且 `LinkedList` 每个元素多一个 `Node` 对象，在 Android 上 GC 压力明显，Google 官方也明确不建议使用。"

**读者问：`CopyOnWriteArrayList` 适用于什么场景？为什么写性能这么差还要用它？**

**AI答：**

1. **原理**：写操作时**复制整个底层数组**，然后用 `volatile` 引用**原子替换**。

```java
public boolean add(E e) {
    synchronized (lock) {
        Object[] newArray = Arrays.copyOf(array, array.length + 1);
        newArray[array.length] = e;
        array = newArray;         // ✅ volatile 写，读方立刻看到新数组
        return true;
    }
}
```

2. **三个关键性质**：

| 性质 | 说明 |
| --- | --- |
| **读完全无锁** | `get(i)` 直接读 volatile 数组 → 极快 |
| **写极慢** | 每次写 **O(n) 复制**整个数组 → 内存分配 + GC 压力巨大 |
| **迭代器是快照** | 迭代器持有创建时的数组引用 → **不会抛 `ConcurrentModificationException`**，但可能读到**旧数据**（弱一致） |

3. **适用场景（四个条件同时满足才考虑）**：

   1. ✅ **读远多于写**（写 : 读 < 1 : 100）。
   2. ✅ **集合不大**（几十到几百个元素），否则复制成本不可接受。
   3. ✅ **需要遍历时容忍弱一致性**（不要求看到最新数据）。
   4. ✅ **需要"读不加锁"**（高并发读场景下避免锁竞争）。

4. **经典应用**：
   - **监听器 / 观察者列表**（注册少、回调多）：`CopyOnWriteArrayList<Listener>`。
   - **配置快照**、**路由表**、**黑名单**。
   - **Android 的很多框架**用 `CopyOnWriteArraySet` 管理监听器。

5. **不适用**：

   - ❌ **写频繁**（如日志队列、消息缓冲）→ 写放大严重。
   - ❌ **需要强一致的多方法组合**：

```java
// ❌ 不是原子的！两个线程可能同时进入 if
if (!list.isEmpty()) {
    Object first = list.get(0);
}
```

   - ❌ 需要**实时更新**（读到的可能是旧快照）。

6. **替代方案**：

| 需求 | 更好的选择 |
| --- | --- |
| 高并发读 + 偶尔写 | `ConcurrentHashMap` / `CopyOnWriteArrayList` |
| 高并发写 | `ConcurrentLinkedQueue`（无锁 CAS 队列） |
| 生产者-消费者 | `ArrayBlockingQueue` / `LinkedBlockingQueue` |
| 阻塞队列 | `LinkedBlockingQueue` |

7. **面试话术**："`CopyOnWriteArrayList` 用**写时复制**换来了无锁读和不会抛 CME 的快照迭代器。代价是每次写都 O(n) 复制数组，GC 压力大。它只在'读极多写极少 + 集合不大 + 需要遍历快照'的场景才合适，最典型的就是监听器列表。写频繁的场景应该用 `ConcurrentLinkedQueue` 或 `ConcurrentHashMap`。"

**读者问：`Collections.synchronizedMap` 和 `ConcurrentHashMap` 有什么区别？为什么推荐后者？**

**AI答：**

1. **`Collections.synchronizedMap` 的本质**：返回一个**包装类**（`SynchronizedMap`），它的每个方法都 `synchronized (mutex)`。

```java
static class SynchronizedMap<K,V> implements Map<K,V>, Serializable {
    final Map<K,V> m;         // 包装的原始 Map
    final Object mutex;       // 锁对象

    public V get(Object key) { synchronized (mutex) { return m.get(key); } }
    public V put(K key, V value) { synchronized (mutex) { return m.put(key, value); } }
    // ... 每个方法都加锁
}
```

2. **三个本质区别**：

| 维度 | `synchronizedMap` | `ConcurrentHashMap` |
| --- | --- | --- |
| **锁粒度** | **整表**（一把锁） | **桶级**（`synchronized` 锁桶头节点） |
| **读操作** | ❌ 也要加锁 | ✅ **完全无锁**（volatile 读） |
| **并发度** | **1**（所有操作互斥） | **= 桶数** |
| **复合操作原子 API** | ❌ 没有 | ✅ `putIfAbsent` / `computeIfAbsent` / `merge` |
| **迭代器** | ❌ 会抛 CME（需手动 `sync`） | ✅ 弱一致，不抛 CME |
| **`size()`** | 需加锁 | ✅ 分散计数，近似无锁 |

3. **性能差距**：

```text
synchronizedMap：读-写并发度 = 1（完全串行）
ConcurrentHashMap：读-写并发度 ≈ 桶数（数千）
```

   高并发场景下差距可能是**数量级**的。

4. **`synchronizedMap` 的正确用法（复合操作必须手动加锁）**：

```java
Map<String, String> map = Collections.synchronizedMap(new HashMap<>());

// ⚠️ 复合操作不会自动加锁！必须手动同步
synchronized (map) {
    if (!map.containsKey(key)) {
        map.put(key, value);
    }
}
```

5. **`ConcurrentHashMap` 的原子复合操作**：

```java
map.putIfAbsent(key, value);                        // 原子
map.computeIfAbsent(key, k -> new ArrayList<>());   // 原子
map.compute(key, (k, v) -> v == null ? 1 : v + 1);  // 原子
map.merge(key, 1, Integer::sum);                    // 原子
```

6. **Android 上的注意**：
   - `ConcurrentHashMap` 在 Android 上是**完全支持的**（从 API 1 就有）。
   - Android 的 `SparseArray` 等**不是线程安全的**，多线程下仍需外部同步或换用 `ConcurrentHashMap`。

7. **面试话术**："`synchronizedMap` 只是给 `HashMap` 包了一层**整表锁**，读也要加锁，并发度是 1，而且复合操作还得手动 `synchronized(map)`。`ConcurrentHashMap` 用 **CAS + 桶级锁**把并发度提升到桶数，读完全无锁，还提供 `computeIfAbsent`/`merge` 这些原子复合 API。所以除非有特殊理由，一律用 `ConcurrentHashMap`。"

**读者问：为什么 `HashMap` 不是线程安全的？多线程下会出什么问题？**

**AI答：**

1. **根本原因**：
   - `HashMap` 的 `put` 是**读-改-写**复合操作（找到桶 → 遍历链表 → 挂上新节点 → `size++`），**没有同步**。
   - `size`、`modCount` 等字段**不是 volatile**，也没有 `synchronized` 保护。
   - `Node.next` 的写入也是普通写，**没有内存屏障**。

2. **三类典型问题**：

```text
① 丢失更新（Lost Update）
   线程 A: 读 size = 5
   线程 B: 读 size = 5
   线程 A: 写 size = 6
   线程 B: 写 size = 6        → 实际存了 2 个，size 却是 6 ❌

② 链表成环（Infinite Loop）—— JDK 7 的头插法扩容导致
   线程 A 扩容时把 node1 → node2
   线程 B 同时扩容时把 node2 → node1
   → 形成环，遍历时死循环 💀（JDK 8 尾插法已修复）

③ 数据不可见 / 结构损坏
   线程 A 构建了新的桶链表，但没有及时对线程 B 可见
   → B 读到半成品状态，size 与实际内容不一致
```

3. **解决方案**：

| 场景 | 方案 |
| --- | --- |
| 单线程 / 线程封闭 | 直接用 `HashMap` |
| 读多写少 | `Collections.synchronizedMap` 或 `ConcurrentHashMap` |
| 高并发 | **`ConcurrentHashMap`**（首选） |
| 不可变共享数据 | `Collections.unmodifiableMap(map)`（**必须在初始化完成后**再包装） |
| Android 键为 int | `SparseArray` + 外部同步，或用 `ConcurrentHashMap<Integer, T>` |

4. **`Hashtable` 为什么线程安全但不用**：
   - 每个方法都 `synchronized`（整表锁）→ 性能差。
   - 不允许 `null` 键值。
   - 遗留类，**JDK 8+ 建议用 `ConcurrentHashMap` 替代**。

5. **面试话术**："`HashMap` 的 `put` 是无保护的读-改-写，`size` 不是 volatile，`Node.next` 写入也没有内存屏障，所以并发下会丢失更新，JDK 7 还会因为头插法扩容形成环形链表。要并发安全就用 `ConcurrentHashMap`（CAS + 桶锁），或者在确知不会被并发修改时用 `Collections.unmodifiableMap` 做不可变共享。"

**读者问：`HashSet` 是怎么实现的？它和 `HashMap` 有什么区别？为什么说它没有额外开销？**

**AI答：**

1. **实现方式**：`HashSet` **内部持有一个 `HashMap`**，把元素当作 **key**，value 统一用一个**哨兵对象** `PRESENT`。

```java
public class HashSet<E> extends AbstractSet<E> implements Set<E> {
    // 所有元素共享同一个哨兵对象
    private static final Object PRESENT = new Object();
    private final Map<E, Object> map;

    public HashSet() { map = new HashMap<>(); }

    public boolean add(E e)       { return map.put(e, PRESENT) == null; }
    public boolean remove(Object o) { return map.remove(o) == PRESENT; }
    public boolean contains(Object o) { return map.containsKey(o); }
    public int size()              { return map.size(); }
    public Iterator<E> iterator()  { return map.keySet().iterator(); }
}
```

2. **为什么说"没有额外开销"**：
   - `HashSet` **没有自己的存储结构**，全部委托给内部的 `HashMap`。
   - `PRESENT` 是**静态单例**，1000 个元素也只占**一份** `Object`（16 字节）。
   - 唯一的额外成本是**多一个 `HashMap` 对象本身**（约 48 字节的头部）。
   - → **`HashSet` ≈ `HashMap` 的内存占用**，而不是"HashMap + 一份元素拷贝"。

3. **`LinkedHashSet` 同理**：内部是 `LinkedHashMap`，多维护一条双向链表以保持插入顺序。

4. **判重逻辑**：`HashSet` 的"重复"判定 = **`HashMap` 的 key 相等判定** = `hashCode()` 相等 **且** `equals()` 相等。

```java
// ⚠️ 关键：如果重写 equals 必须同时重写 hashCode，否则违反 hashCode 契约
@Override
public boolean equals(Object o) { ... }     // 必须同时
@Override
public int hashCode() { ... }               // 必须同时
```

   → 否则：`HashSet` 会把"逻辑相等但 hashCode 不同"的对象当作两个不同元素存进去。

5. **`TreeSet` 完全不同**：基于 `TreeMap`（红黑树），value 是哨兵，**key 必须实现 `Comparable`**（或提供 `Comparator`），插入是 **O(log n)**，遍历是**有序**的。

6. **面试话术**："`HashSet` 内部就是一个 `HashMap`，元素当 key，value 全部指向同一个 `PRESENT` 哨兵对象，所以内存占用和 `HashMap` 基本一样。它和 `HashMap` 的区别是只暴露 key 相关的 API。`TreeSet` 则是基于 `TreeMap` 的有序集合，插入 O(log n) 且 key 必须可比较。"

**读者问：`HashMap` 的 `hashCode()` 和 `equals()` 应该怎么重写？不重写会怎样？**

**AI答：**

1. **契约（`Object.hashCode` 的规范）**：
   - 若两个对象 `equals()` 为 **true**，则它们的 `hashCode()` **必须相等**。
   - 若两个对象的 `hashCode()` 相等，**不要求** `equals()` 也相等（**哈希碰撞**是允许的）。
   - 同一个对象在**未被修改**的情况下，多次调用 `hashCode()` 必须返回**相同的值**（所以 `hashCode` 里不能有可变状态，也不能用 `System.identityHashCode` 之外的不稳定源）。

2. **正确重写方式**：

```java
public class User {
    private final int id;
    private final String name;

    @Override
    public boolean equals(Object o) {
        if (this == o) return true;              // ① 引用相等快路径
        if (o == null || getClass() != o.getClass()) return false;   // ② 类型检查
        User user = (User) o;
        return id == user.id;                   // ③ 用【参与业务相等判定】的字段
    }

    @Override
    public int hashCode() {
        return Objects.hash(id);                // ④ 必须用【与 equals 一致】的字段
        // ✅ Objects.hash 会用 Arrays.hashCode 组合，避免多个字段哈希相乘溢出
    }
}
```

3. **不重写的后果**：

```text
场景：重写了 equals 但没重写 hashCode
  new User(1, "A").equals(new User(1, "B"))  → true（业务上相等）
  但两者的 hashCode 不同（Object.hashCode 是【内存地址】）
  → 放进 HashMap 会被分到【不同的桶】
  → HashMap.get() 找不到！💥

场景：反过来（重写 hashCode 但没重写 equals）
  → 两个"业务相等"的对象 hashCode 相同但 equals 返回 false
  → HashSet 会把它们当两个元素存进去（去重失效）
```

4. **字段选择的建议**：
   - **只把参与 `equals` 的字段**放进 `hashCode`（否则违反契约）。
   - 优先用**不可变的、唯一的**字段（如 id、code）。
   - 避免用 `hashCode` 里依赖**可变字段**（改了之后在 `HashMap` 里就找不到了 → 这叫"**破坏了 Map 的 key 不变性假设**"）。
   - `Objects.hash(a, b)` 的实现是 `Arrays.hashCode`，会用 `31` 进制组合，比手写 `a * 31 + b` 更不容易碰撞。

5. **Android 中的实战坑**：

```kotlin
// ❌ 危险：data class 的 equals/hashCode 基于【全部构造字段】
data class User(val id: Long, var name: String)
// 如果 name 可变，放进 HashMap 后修改 name → 找不到了

// ✅ 若字段可变，用自定义 equals/hashCode 只基于不可变字段
```

6. **面试话术**："重写 `equals` **必须**同时重写 `hashCode`，且两者用的字段要一致——因为 `HashMap` 先比 hash 再比 equals，hash 不一致就根本不会走 `equals`。常见坑是 `data class` 的字段可变，放进 Map 后修改字段导致 '元素丢了'；或者只重写 `equals` 导致业务相等的对象落进不同的桶，get 不到。"

**读者问：`Iterator` 的 `remove()` 为什么叫 `ConcurrentModificationException`？快速失败（fail-fast）是什么？**

**AI答：**

1. **异常的产生**：

```java
List<String> list = new ArrayList<>(List.of("a", "b", "c"));
Iterator<String> it = list.iterator();
it.next();              // 读取 "a"
list.remove("b");       // ❌ 修改了集合的结构
it.next();              // 💥 ConcurrentModificationException
```

2. **fail-fast 的实现原理**：

```java
// ArrayList 内部
private transient int modCount;   // 每次【结构性修改】都 ++

public Iterator<E> iterator() {
    return new Itr();   // 把当前的 modCount 快照记下来
}

private class Itr implements Iterator<E> {
    int expectedModCount = modCount;   // ① 创建迭代器时记录快照

    public E next() {
        checkForComodification();      // ② 每次取值前检查
        ...
    }
    final void checkForComodification() {
        if (modCount != expectedModCount)
            throw new ConcurrentModificationException();
    }
}
```

   → **结构性修改（structural modification）**：改变元素**个数**或**顺序**的操作（`add` / `remove` / `clear` / `addAll` / `sort` / `removeIf`）。
   → **非结构性修改**：`set(index, element)`（只换值，不改结构）——**不会**触发异常。

3. **为什么要有 fail-fast**：**尽早暴露 bug**。在迭代中修改集合，通常是逻辑错误，会导致"读到一半的元素不见了"或"跳过元素"。fail-fast 把这类隐蔽 bug 变成**明确的异常**。

4. **fail-fast 的局限**：
   - **只是尽力而为的检测，不是线程安全保证**。
   - **不保证一定抛异常**：并发修改时可能因为时序问题没检测到就"静默"通过。
   - **可能误报**：某些实现（如 `ArrayList.remove(Object)` 删除了一个**不存在**的元素）也会 `modCount++`，导致迭代器抛出异常——虽然集合实际没变。

5. **`ConcurrentHashMap` 的迭代器不同**：

```java
// ConcurrentHashMap 的迭代器：弱一致（weakly consistent）
// - 不会抛 ConcurrentModificationException
// - 反映【迭代器创建时或之后】的状态
// - 可能看到也可能看不到并发修改的部分
```

   → 这是**故意设计**的：`ConcurrentHashMap` 面向高并发，如果迭代器抛 CME，反而不可用。

6. **正确的并发遍历方式**：

```java
// ✅ 方案 1：CHM 自己的迭代器（弱一致，无 CME）
for (Map.Entry<String, Integer> e : concurrentMap.entrySet()) { ... }

// ✅ 方案 2：CopyOnWriteArrayList 的迭代器（快照）
for (String s : copyOnWriteList) { ... }

// ✅ 方案 3：加锁遍历（强一致）
synchronized (list) {
    for (String s : list) { ... }
}
```

7. **面试话术**："`ConcurrentModificationException` 来自 **fail-fast** 机制：集合内部维护一个 `modCount`（结构性修改计数器），迭代器创建时记下快照，每次 `next()` 前比对，不一致就抛异常。目的是**尽早暴露**'迭代中修改集合'这个逻辑 bug。但它**不是线程安全保证**——只是尽力检测。`ConcurrentHashMap` 的迭代器则是**弱一致**的，故意不抛 CME。"

# 跨语言互调

## 一句话定义

**跨语言互调（Interoperability）** 指 Kotlin 与 Java 之间的双向调用，以及 Kotlin/Java 与 **C/C++（NDK/JNI）** 的互调。Kotlin 之所以能与 Java 无缝互调，是因为它**编译到同一套 JVM 字节码**；难点不在"能不能调"，而在于**Kotlin 的语言特性（默认参数、空安全、扩展函数、密封类、挂起函数）无法 1:1 映射到 Java**，需要靠 `@JvmStatic`、`@JvmField`、`@JvmOverloads`、`@JvmName`、`@Throws`、`@JvmInline` 等注解在**编译期生成桥接代码**来解决。

## 核心原理

### 1. Kotlin 与 Java 的互调基础

```text
Kotlin 源码 ──┐
              ├──→ Kotlin 编译器 ──→ JVM 字节码 (.class) ──→ JVM / ART
Java 源码  ──┘
```

- 两者编译到**同一个 classpath**，遵循同一套 JVM 规范。
- Kotlin 额外写入 **`@kotlin.Metadata`** 注解，记录 Kotlin 特有的类型信息（可空性、扩展接收者、协变/逆变声明等）。
- **关键结论**：互调的**兼容性由字节码决定**，而不是由源语言决定。

### 2. Kotlin 调用 Java vs Java 调用 Kotlin 的根本差异

| 维度 | Kotlin → Java | Java → Kotlin |
| --- | --- | --- |
| **空安全** | Java 平台类型（platform type）→ **Kotlin 侧要判空** | Kotlin 的 `null` 检查在 Java 侧**被绕过**（Java 看不到） |
| **默认参数** | Java 调用方**必须传全部参数**（除非生成重载） | Kotlin 侧可省略（有默认值） |
| **命名参数** | ❌ Java 不支持 | ❌ Java 不支持 |
| **扩展函数** | Java **无法调用**（是静态方法，名字不直观） | Java **无法调用** |
| **密封类** | Java 可以访问 `sealed` 子类，但**不能穷举**（没有 `when` 完备性检查） | — |
| **数据类** | Java 需要调用 `component1()`、`copy()`（可用但笨拙） | — |
| **`object` 单例** | Java 调用 `INSTANCE`（或 `@JvmStatic` 后直接调用） | — |
| **顶层函数/属性** | Java 需 `FileNameKt.func()` | Java 无法访问（除非 `@file:JvmName`） |
| **挂起函数** | Java 需用 `Continuation` 手写或用 `kotlinx-coroutines-jdk8` 的 `future` 扩展 | — |
| **可变参数** | Kotlin `vararg` → Java 数组参数 ✅ | — |
| **泛型** | Java 的 `List<String>` → Kotlin 的 `(Mutable)List<String!>` | Kotlin 的 `List<String>` → Java 的 `List<? extends String>` |

**平台类型（Platform Type）**——Kotlin 调用 Java 的核心概念：

```kotlin
// Java
public String getName() { return null; }

// Kotlin 侧
val name: String = javaObj.name    // ✅ 编译通过！
                            // 但 name 的类型是 String!（平台类型）
name.length                        // ✅ 编译通过，但运行时可能 NPE 💥
```

- 平台类型 `String!` = `String` 或 `null`，编译器**不强制检查**。
- 解决方法：显式声明可空 `val name: String? = javaObj.name`。
- **实践建议**：**把 Java 边界包一层 Kotlin 扩展/适配器**，统一处理 null。

### 3. `@JvmStatic` 与 `@JvmField`

**问题**：`object` 单例里的方法在 Java 中怎么调用？

```kotlin
// Kotlin
object UserManager {
    fun create(name: String): User = User(name)
    val DEFAULT_NAME = "default"
}
```

```java
// Java 调用（默认情况）
UserManager.INSTANCE.create("Alice");    // ⚠️ 要写 INSTANCE
String s = UserManager.INSTANCE.getDEFAULT_NAME();
```

**`@JvmStatic`**：

```kotlin
object UserManager {
    @JvmStatic
    fun create(name: String): User = User(name)

    @JvmStatic
    val DEFAULT_NAME = "default"
}
```

```java
// Java 调用（加了 @JvmStatic）
UserManager.create("Alice");     // ✅ 直接调用
String s = UserManager.DEFAULT_NAME;
```

**底层原理**：

```text
@JvmStatic 的伴生对象（companion object）成员：
  原本只在伴生对象里，Java 需要 UserManager.Companion.create()

  加上 @JvmStatic 后：
  ① 伴生对象里保留原方法（供 Kotlin 用）
  ② 【额外】在宿主类上生成一个 static 方法，委派给伴生对象

  public final class UserManager {
      public static final UserManager INSTANCE = new UserManager();
      private static final Companion Companion = new Companion();

      // @JvmStatic 生成的静态方法
      public static User create(String name) {
          return Companion.create(name);
      }
  }
```

| 注解 | 作用 | Java 侧效果 |
| --- | --- | --- |
| `@JvmStatic` | 成员函数/属性 → 静态 | `UserManager.create(...)` |
| `@JvmField` | 属性 → **public 静态字段**（去掉 getter/setter） | `UserManager.DEFAULT_NAME`（直接字段访问） |

**`@JvmField` 的限制**：

```kotlin
@JvmField
val x = 1                 // ✅ 可以
@JvmField
var y = 1                 // ❌ 编译错误：@JvmField 不能用于可变属性
@JvmField
private val z = 1         // ❌ 编译错误：@JvmField 不能用于 private
@JvmField
val w: Int by lazy { 1 }  // ❌ 编译错误：@JvmField 不能用于委托属性
@JvmField
val v get() = 1           // ❌ 编译错误：@JvmField 不能用于自定义 getter（无 backing field）
```

**为什么需要 `@JvmField`**：Android 的 Java 代码（大量遗留代码）习惯直接访问 `public static final` 常量，用 `@JvmField` 可以避免 `getXxx()` 的调用开销与啰嗦。

### 4. `@JvmOverloads`：默认参数与 Java 重载

**问题**：Kotlin 的默认参数在 Java 中不可用。

```kotlin
// Kotlin
fun show(title: String, subtitle: String = "副标题", duration: Int = 3000) { }
```

```java
// Java 调用（默认情况）—— 必须传所有参数
show("标题", "副标题", 3000);
```

**`@JvmOverloads`**：

```kotlin
@JvmOverloads
fun show(title: String, subtitle: String = "副标题", duration: Int = 3000) { }
```

```java
// Java 调用（加了 @JvmOverloads）
show("标题");                       // ✅ 生成的重载
show("标题", "副标题");              // ✅
show("标题", "副标题", 3000);        // ✅ 原本的方法
```

**生成规则**：为参数列表的**每个尾部默认值组合**生成一个重载。

```text
fun show(a: String, b: String = "x", c: String = "y")
  ↓ @JvmOverloads 生成
show(String, String, String)    // 完整版
show(String, String)            // 省略 c
show(String)                    // 省略 b、c
```

**注意**：
- `@JvmOverloads` 只能用于**有默认参数**的函数。
- 每个重载都会**增加方法数量** → 增加 DEX 体积。Kotlin 官方库里的 `@JvmOverloads` 用得比较克制。
- **只在需要给 Java 调用时加**。

### 5. `@JvmName`：重命名与文件级门面

**用途一：修改生成的方法名（解决平台声明冲突）**：

```kotlin
// 两个不同的 Kotlin 文件可以有同名顶层函数，但 JVM 类名会冲突
// FileA.kt: fun process() → AClassKt.process()
// FileB.kt: fun process() → BClassKt.process()   ✅ 实际不冲突

// 但如果是同一个文件里的两个同名扩展函数：
// Util.kt
fun String.process() { }        // → UtilKt.process(String)
fun Int.process() { }           // → UtilKt.process(Int)  ✅ 不冲突（参数不同）

// 真正的冲突：同一文件内的同名【顶层函数】（参数也相同）
```

```kotlin
@file:JvmName("StringUtils")
package com.example.util

fun String.isValid(): Boolean = isNotEmpty()
fun String.trimOrDefault(default: String): String = ifBlank { default }
```

```java
// Java 调用
StringUtils.isValid("abc");
StringUtils.trimOrDefault("  ", "x");
```

**用途二：解决"平台声明冲突（platform declaration clash）"**：

```kotlin
// 冲突场景：Kotlin 扩展函数名与某个 Java 类的方法名冲突
// 报错：Platform declaration clash: The following declarations have the same JVM signature (isEmpty()Ljava/lang/String;)
@JvmName("isNotBlankOrNull")
fun String.isEmpty(): Boolean = ...
```

**用途三：为顶层成员创建一个 Java 友好的"门面类"**：

```kotlin
@file:JvmName("MyExtensions")
package com.example.ext

// Java 调用：MyExtensions.doSomething()
fun doSomething() { }
```

> **面试高频**：Kotlin 的顶层函数编译成**文件名的静态方法**（`Utils.kt` → `UtilsKt`），文件名带 `Kt` 后缀是为了**避免与类名冲突**。

### 6. `@Throws`：受检异常的桥接

**问题**：Java 有**受检异常（checked exception）**，Kotlin **没有受检异常**的概念。

```kotlin
// Kotlin
fun readFile(path: String): String {
    return File(path).readText()      // 可能抛 IOException，但 Kotlin 不要求声明
}
```

```java
// Java 调用
try {
    readFile("/sdcard/a.txt");
} catch (IOException e) {      // ❌ 编译错误：unreachable catch block
    // 因为 Kotlin 没声明 throws，Java 不知道它会抛 IOException
}
```

**`@Throws`**：

```kotlin
@Throws(IOException::class)
fun readFile(path: String): String {
    return File(path).readText()
}
```

```java
// Java 调用
try {
    readFile("/sdcard/a.txt");
} catch (IOException e) {      // ✅ 编译通过
}
```

**底层**：Kotlin 编译器在方法上生成 `Exceptions` 属性：

```text
public static void readFile(String path) throws java.io.IOException;
```

**双向关系**：
- **Kotlin → Java**：Kotlin **可以**调用会抛受检异常的 Java 方法，**不需要** try-catch（但仍要处理 `Exception` 类型的抛出）。
- **Java → Kotlin**：Java **看不到** Kotlin 的受检异常声明 → 需要 `@Throws` 才能 catch。
- **实践建议**：在**库的公共 API** 上加 `@Throws`，这样 Java 调用方能正确处理。

### 7. `object` 单例、`companion object` 与 Java 的对应

| Kotlin | Java 侧默认访问方式 | 加注解后 |
| --- | --- | --- |
| `object Foo { fun bar() {} }` | `Foo.INSTANCE.bar()` | `@JvmStatic` → `Foo.bar()` |
| `class Foo { companion object { fun bar() {} } }` | `Foo.Companion.bar()` | `@JvmStatic` → `Foo.bar()` |
| `class Foo { companion object { val X = 1 } }` | `Foo.Companion.getX()` | `@JvmField` → `Foo.X`（静态字段） |

```kotlin
// 最佳实践：companion object + @JvmStatic + @JvmField
class Config {
    companion object {
        @JvmField
        val DEFAULT_TIMEOUT_MS: Long = 10_000L

        @JvmStatic
        fun create(): Config = Config()
    }
}
```

```java
// Java 侧
long t = Config.DEFAULT_TIMEOUT_MS;   // ✅ 静态字段
Config c = Config.create();            // ✅ 静态方法
```

### 8. 扩展函数与 Java SAM 互转

**Java 调用 Kotlin 扩展函数**：

```kotlin
// StringExtensions.kt
fun String.isValidEmail(): Boolean = contains("@") && contains(".")
```

```java
// Java 侧：扩展函数是【静态方法】，但名字带 "Kt" 后缀
StringExtensions.isValidEmail("a@b.com");   // ⚠️ 能用但不优雅
```

**解决方案**：用 `@file:JvmName` + 顶层函数：

```kotlin
@file:JvmName("TextUtils")
package com.example.ext

fun isValidEmail(text: String): Boolean = text.contains("@") && text.contains(".")
```

```java
TextUtils.isValidEmail("a@b.com");   // ✅
```

**Kotlin 调用 Java 的 SAM 接口**：

```java
// Java
public interface Callback {
    void onResult(String data);
}
```

```kotlin
// Kotlin —— ✅ SAM 转换
callback(object : Callback {
    override fun onResult(data: String) { }
})
callback { data -> }                          // ✅ 简写（SAM 转换）
callback(Callback { data -> })                // ✅ 显式

// Kotlin 的 fun interface 也支持 SAM 转换（Kotlin 1.4+）
fun interface OnClick {
    fun onClick(v: View)
}
val listener = OnClick { v -> v.visibility = View.GONE }   // ✅
```

**Kotlin 的函数类型 ↔ Java 函数式接口**：

```kotlin
// Kotlin 函数类型在 JVM 上是 Function1<T, R> 接口
val f: (Int) -> Int = { it * 2 }

// Java 侧
Function1<Integer, Integer> f = x -> x * 2;   // ✅ Java 可以用（但要处理装箱）
```

**`Function1` 与 Java 函数式接口的互转工具**（kotlin-stdlib 提供）：

```kotlin
// Kotlin 函数类型 → Java 的 Function
val javaFn: java.util.function.Function<Int, Int> = { it * 2 }

// Java 函数式接口 → Kotlin 函数类型
val ktFn: (Int) -> Int = javaFn::apply
```

> **注意**：Java 的 `Function<Integer, Integer>` 和 Kotlin 的 `(Int) -> Int` 在类型系统上是**不同的**（装箱 vs 泛型），转换时会有装箱开销。

### 9. Kotlin 的 `value class`（`@JvmInline`）

**问题**：Kotlin 的"值类（value class）"在编译后会**装箱**成一个对象，丢失了"零开销"的特性。

```kotlin
// Kotlin 1.5 之前的 value class
@JvmInline
value class Password(val s: String)
```

- **原理**：编译器会为值类生成**实例化（box）**和**拆箱（unbox）**的方法：`box-impl`、`unbox-impl`。
- 如果值类作为**泛型类型参数**、存入 `List<Password>`、或作为可空类型 → 会被**装箱**成真正的对象 → 有额外内存与性能开销。

**`@JvmInline` 注解（Kotlin 1.5+）**：

```kotlin
@JvmInline
value class Password(val s: String)
```

- **本质**：把值类**内联展开**到使用它的位置（类似 C++ 的 `struct` 传值语义）。
- **在 JVM 上**：编译成一个**私有字段 + 静态的 `box-impl`/`unbox-impl` 方法**，没有真正的类实例。
- **Java 侧**：Java **看不到** `Password` 类，只能看到它的**底层表示**（`String`）。
  - `Password("123")` 在 Java 侧就是 `"123"`。
  - Java 方法签名会变成 `void login(String password)`。

```kotlin
@JvmInline
value class UserId(val value: Long)

// Kotlin 侧
@JvmInline
value class Meters(val value: Double) {
    fun toFeet(): Double = value * 3.28084
}

fun distance(a: Meters, b: Meters): Double = (b.value - a.value).absoluteValue
```

**内存对比**：

```text
普通 class（装箱）：
  UserId 对象：对象头 16 字节 + Long 8 字节 = 24 字节
  List<UserId> 中还要额外存引用 8 字节

@JvmInline value class（内联）：
  UserId(id) 直接是 long，List<Long> 里存 8 字节
  → 零额外开销 ✅
```

**限制**：

| 限制 | 说明 |
| --- | --- |
| 必须是**单个 val 属性** | 不能有多个属性 |
| 属性必须是 `val` | 不能是可变 |
| 不能是 `open`/`abstract`/`sealed` | 必须是 `final` |
| **不能继承** | 不能有父类 |
| 可空时**会装箱** | `Password?` → 真正的对象 |
| 作为**泛型类型参数**时**会装箱** | `List<Password>` → 装箱 ⚠️ |
| Java 侧**看不到这个类型** | 只看到底层类型 |

**Android 中的典型用途**：避免为 ID、金额、距离等"包装语义"分配对象。

```kotlin
// ✅ 好的用法
@JvmInline value class UserId(val value: Long)
@JvmInline value class Millis(val value: Long)

// ❌ 会装箱，失去意义
val ids: List<UserId> = listOf(UserId(1), UserId(2))
```

### 10. NDK 与 JNI 原理

```text
┌────────────────────────────────────────────────────────────┐
│  Java / Kotlin 层                                            │
│    native fun compressBitmap(bitmap: Bitmap): ByteArray      │
│                          ↓                                  │
│  ┌──────────────────────────────────────────────────────┐   │
│  │  JNI 桥接层（JNI Functions）                          │   │
│  │   JavaVM* / JNIEnv* / 方法注册表                       │   │
│  └──────────────────────────────────────────────────────┘   │
│                          ↓                                  │
│  ┌──────────────────────────────────────────────────────┐   │
│  │  C/C++ 层（.so 共享库）                               │   │
│  │   extern "C" JNIEXPORT ... JNICALL Java_xxx_xxx(...)  │   │
│  └──────────────────────────────────────────────────────┘   │
└────────────────────────────────────────────────────────────┘
```

**核心概念**：

| 概念 | 说明 |
| --- | --- |
| **`JavaVM*`** | **进程级**的 VM 指针，**一个进程只有一个**。任何 native 线程都要 `AttachCurrentThread` 才能用 JNI |
| **`JNIEnv*`** | **线程级**的 JNI 接口指针，每个线程一个。**不能在 native 线程间传递** |
| **方法注册** | Java 方法名 → native 函数指针的映射表 |
| **`System.loadLibrary("name")`** | 加载 `libname.so` |
| **`JNI_OnLoad`** | 库加载时回调，可在这里动态注册方法 |
| **`JNI_OnUnload`** | 库卸载时回调 |

**两种方法注册方式**：

```text
① 静态注册（按命名约定）
   Java:  native int add(int a, int b);
   C++:   JNIEXPORT jint JNICALL Java_com_example_MathUtils_add
                (JNIEnv* env, jobject thiz, jint a, jint b) { return a + b; }

   缺点：类名/方法名必须与 C++ 函数名完全一致 → 混淆后失效（需要 keep 规则）

② 动态注册（在 JNI_OnLoad 中）
   C++:
   static JNINativeMethod methods[] = {
       {"add", "(II)I", (void*)Java_com_example_MathUtils_add}
   };
   JNIEXPORT jint JNICALL JNI_OnLoad(JavaVM* vm, void* reserved) {
       JNIEnv* env = nullptr;
       vm->GetEnv((void**)&env, JNI_VERSION_1_6);
       jclass clazz = env->FindClass("com/example/MathUtils");
       env->RegisterNatives(clazz, methods, sizeof(methods)/sizeof(methods[0]));
       return JNI_VERSION_1_6;
   }

   优点：函数名可以任意（可用宏生成）→ 混淆安全 ✅
```

**`System.loadLibrary` 与 `System.load`**：

```kotlin
// ✅ 标准做法：加载 "libnative-lib.so"
System.loadLibrary("native-lib")

// ⚠️ 路径必须是绝对路径，且要处理权限
System.load("/data/app/xxx/lib/arm64/libnative.so")
```

**JNI 的调用开销**：

```text
Java → native 调用涉及：
  ① 线程状态切换（Java 线程 → native）
  ② 参数的 JNI 转换（jstring → jchar* 需要内存分配 + UTF-8 转换）
  ③ 返回值的 JNI 转换
  ④ 异常检查

单次调用开销：约 10~100ns（不含实际计算）
→ 大量细粒度调用（如在循环里逐像素操作）会非常慢
```

**常用 JNI API**：

```c
// 获取类/方法/字段
jclass cls = env->FindClass("com/example/Foo");
jmethodID mid = env->GetMethodID(cls, "getName", "()Ljava/lang/String;");
jfieldID fid = env->GetFieldID(cls, "count", "I");

// 调用 Java 方法
jstring result = (jstring)env->CallObjectMethod(obj, mid);

// 创建对象
jobject newObj = env->NewObject(cls, ctor, args);

// 字符串转换（需要释放！）
const char* utfChars = env->GetStringUTFChars(str, nullptr);
env->ReleaseStringUTFChars(str, utfChars);

// 抛异常
env->ThrowNew(env->FindClass("java/lang/IllegalStateException"), "message");

// 局部引用表管理（关键！）
env->PushLocalFrame(64);
... // 创建大量局部引用
env->PopLocalFrame(nullptr);   // 一次性释放 ✅
```

**局部引用表（Local Reference Table）**——JNI 最大的坑：

```text
每个 native 线程有 16 个 JNI 局部引用槽位（JNI spec 规定至少 16）
超出 → 抛出 "local reference table overflow" 错误

规则：
  ① Java 对象传给 native 时，会创建【局部引用】阻止 GC 回收
  ② 局部引用在 native 方法返回时【自动释放】
  ③ 在一个 native 方法里创建 1000 个局部引用 → 溢出 💥

解法：
  PushLocalFrame(64) / PopLocalFrame()      // 分段处理
  DeleteLocalRef(ref)                       // 手动释放单个
  NewGlobalRef / DeleteGlobalRef            // 全局引用（不会自动释放，必须手动 delete）
```

**`NewGlobalRef` 的内存泄漏**：

```c
// ❌ 泄漏：每次都创建全局引用，从不释放
jobject global = env->NewGlobalRef(localObj);

// ✅ 正确
jobject global = env->NewGlobalRef(localObj);
if (global != NULL) {
    env->DeleteGlobalRef(global);      // ✅ 必须释放
}
```

### 11. JNI 的性能问题与替代方案

**JNI 的主要性能问题**：

| 问题 | 说明 |
| --- | --- |
| **调用开销** | 每次调用有状态切换 + 参数转换（约 10-100ns） |
| **字符串转换** | `GetStringUTFChars` 需要**分配内存 + UTF-16 → UTF-8 转换**（中文字符串尤其贵） |
| **数组拷贝** | 传递大数组要 `GetByteArrayElements` → **全量拷贝**到 native 堆 |
| **对象字段访问** | 每次访问 `obj.field` 都要 `GetFieldID` + `GetObjectField` |
| **异常开销** | native 调用返回后 JVM 要检查是否有待处理异常 |

**优化手段**：

```kotlin
// ✅ 1. 减少调用次数：把多次 JNI 调用合并成一次
// ❌ 逐像素调用 native：1M 次 JNI 调用
// ✅ 一次传入整个 Bitmap，由 native 内部批量处理

// ✅ 2. 避免重复 GetFieldID：缓存 jfieldID / jmethodID
```

```c
// ✅ 缓存字段/方法 ID（初始化时取一次）
static jfieldID g_countField = nullptr;
if (g_countField == nullptr) {
    g_countField = env->GetFieldID(cls, "count", "I");
}
```

```kotlin
// ✅ 3. 减少字符串转换：传递 byte[] 而不是 String
native fun decode(bytes: ByteArray): ByteArray

// ✅ 4. 使用 DirectByteBuffer / 内存映射文件：零拷贝
val buffer = ByteBuffer.allocateDirect(size)
buffer.put(data)
native fun process(buffer: ByteBuffer)

// ✅ 5. 用 critical array（禁止 GC）
```

**替代方案**：

| 方案 | 说明 | 适用 |
| --- | --- | --- |
| **Rust / C++ 库 + JNI** | 主流做法（Flutter、TensorFlow Lite、ffmpeg） | 性能关键算法 |
| **RenderScript**（已废弃） | Google 的 GPU 计算框架 | 已淘汰 |
| **OpenGL ES / Vulkan** | GPU 计算 | 图像、图形 |
| **Metal Performance Shaders** | Apple 生态 | iOS |
| **纯 Kotlin/Java** | 不涉及 native | 绝大多数业务逻辑 |
| **Kotlin Multiplatform** | 共享逻辑到 C interop | 跨平台 |
| **WebAssembly** | 浏览器外的沙箱执行 | 特定场景 |
| **SQLite 扩展** | 数据库层用 C 加速 | 查询性能 |

**判断是否需要 JNI**：

```text
✅ 值得用 JNI：
  - 已有成熟的 C/C++ 库（图像编解码、加密、机器学习模型）
  - 计算密集且 Kotlin/Java 优化不了（编解码、音视频处理）
  - 需要复用现有 native 代码库

❌ 不值得：
  - 简单的数值计算 → Kotlin 完全够用（JIT/AOT 会优化）
  - 频繁的小粒度跨语言调用 → JNI 开销占大头
  - 团队没有 C/C++ 能力 → 维护成本高
```

### 12. Kotlin 互调的常见坑

| 坑 | 现象 | 解法 |
| --- | --- | --- |
| **平台类型 NPE** | Kotlin 调 Java，编译通过但运行时 NPE | 显式声明可空类型 + 判空；或写 Kotlin 扩展包装 |
| **默认参数不可用** | Java 调用 Kotlin 必须传全参 | `@JvmOverloads` |
| **`object` 要写 INSTANCE** | Java 调用 Kotlin 单例啰嗦 | `@JvmStatic` |
| **顶层函数名带 Kt** | `UtilsKt.doSomething()` | `@file:JvmName("Utils")` |
| **扩展函数 Java 调不了** | Java 侧找不到 | 写顶层函数 + `@file:JvmName` |
| **受检异常 catch 不到** | Java catch 编译报错 | `@Throws(IOException::class)` |
| **命名冲突** | "Platform declaration clash" | `@JvmName` |
| **伴生对象常量要 getter** | `Config.Companion.getX()` | `@JvmField` |
| **`@JvmField` 用在 var** | 编译错误 | 改成 `val` |
| **协程调 Java 的 suspend 函数** | 需要手动构造 Continuation | 用 `kotlinx-coroutines-jdk8` 的 `future` / `asDeferred` |
| **JNI 局部引用溢出** | "local reference table overflow" | `PushLocalFrame` / `DeleteLocalRef` |
| **JNI 全局引用泄漏** | 内存持续增长 | `DeleteGlobalRef` |
| **JNI 字符串未释放** | native 内存泄漏 | `ReleaseStringUTFChars` |
| **混淆后 native 方法找不到** | `UnsatisfiedLinkError` | 动态注册 或 proguard keep 规则 |

**proguard 规则（JNI + 混淆）**：

```proguard
# 静态注册的 native 方法：必须 keep 类名和方法名
-keepclasseswithmembernames class * {
    native <methods>;
}

# 动态注册：只需 keep 类名（因为 JNI_OnLoad 里用 FindClass 查找）
-keep class com.example.nativebridge.** { *; }
```

```kotlin
    external fun toGrayscale(pixels: ByteArray, width: Int, height: Int): ByteArray
```

**C++ 侧**：

```cpp
#include <jni.h>
#include <android/log.h>
#include <vector>
#include <mutex>

#define LOG_TAG "ImageProcessor"
#define LOGE(...) __android_log_print(ANDROID_LOG_ERROR, LOG_TAG, __VA_ARGS__)

namespace {

// 缓存的方法 ID（避免每次调用都 GetMethodID）
jfieldID g_widthField = nullptr;
std::mutex g_cacheMutex;

/**
 * 动态注册表：函数名可以是任意 C++ 名字（混淆安全）
 */
JNINativeMethod g_methods[] = {
    {"toGrayscale", "([BII)[B", reinterpret_cast<void *>(toGrayscale)},
    {"processBatch", "([BI)I",   reinterpret_cast<void *>(processBatch)},
};

}  // namespace

extern "C" {

/**
 * 灰度处理：使用 PushLocalFrame 管理局部引用，避免溢出
 */
JNIEXPORT jbyteArray JNICALL toGrayscale(
        JNIEnv* env, jobject /*thiz*/, jbyteArray pixels, jint width, jint height) {

    // ① 声明局部引用帧：最多 64 个局部引用，超出自动回收
    if (env->PushLocalFrame(64) != 0) {
        return nullptr;
    }

    jsize length = env->GetArrayLength(pixels);
    jbyte* src = env->GetByteArrayElements(pixels, nullptr);

    if (src == nullptr) {
        env->PopLocalFrame(nullptr);
        return nullptr;
    }

    // ② 分配结果数组
    jbyteArray result = env->NewByteArray(length);
    if (result == nullptr) {
        env->ReleaseByteArrayElements(pixels, src, JNI_ABORT);
        env->PopLocalFrame(nullptr);
        return nullptr;
    }
    jbyte* dst = env->GetByteArrayElements(result, nullptr);

    // ③ 实际计算：灰度 = 0.299R + 0.587G + 0.114B
    for (jsize i = 0; i + 2 < length; i += 4) {
        int a = src[i + 3];
        int gray = static_cast<int>(0.299 * src[i] + 0.587 * src[i + 1] + 0.114 * src[i + 2]);
        dst[i] = static_cast<jbyte>(gray);
        dst[i + 1] = static_cast<jbyte>(gray);
        dst[i + 2] = static_cast<jbyte>(gray);
        dst[i + 3] = static_cast<jbyte>(a);
    }

    // ④ ✅ 必须释放（否则 native 内存泄漏）
    env->ReleaseByteArrayElements(result, dst, 0);
    env->ReleaseByteArrayElements(pixels, src, JNI_ABORT);

    // ⑤ 释放局部引用帧
    env->PopLocalFrame(result);   // 把 result 弹出帧（同时释放帧内其他局部引用）
    return result;
}

/**
 * 批量处理：演示全局引用的正确使用
 */
JNIEXPORT jint JNICALL processBatch(
        JNIEnv* env, jobject thiz, jbyteArray pixels, jint count) {

    jsize length = env->GetArrayLength(pixels);
    jbyte* src = env->GetByteArrayElements(pixels, nullptr);
    if (src == nullptr) return -1;

    int processed = 0;
    for (jsize i = 0; i < length && processed < count; ++i) {
        src[i] = static_cast<jbyte>(255 - src[i]);   // 反色
        ++processed;
    }
    env->ReleaseByteArrayElements(pixels, src, 0);
    return processed;
}

/**
 * JNI_OnLoad：动态注册方法（在库加载时执行一次）
 */
JNIEXPORT jint JNICALL JNI_OnLoad(JavaVM* vm, void* /*reserved*/) {
    JNIEnv* env = nullptr;
    if (vm->GetEnv(reinterpret_cast<void**>(&env), JNI_VERSION_1_6) != JNI_OK) {
        return JNI_ERR;
    }

    jclass clazz = env->FindClass("com/example/nativebridge/ImageProcessor");
    if (clazz == nullptr) {
        LOGE("找不到 ImageProcessor 类");
        return JNI_ERR;
    }

    // ✅ 动态注册：函数名可以任意 → ProGuard 混淆不影响
    if (env->RegisterNatives(clazz, g_methods,
                             sizeof(g_methods) / sizeof(g_methods[0])) != JNI_OK) {
        LOGE("JNI 方法注册失败");
        return JNI_ERR;
    }
    return JNI_VERSION_1_6;
}

/**
 * JNI_OnUnload：释放全局资源
 */
JNIEXPORT void JNICALL JNI_OnUnload(JavaVM* /*vm*/, void* /*reserved*/) {
    std::lock_guard<std::mutex> lock(g_cacheMutex);
    g_widthField = nullptr;
}

}  // extern "C"
```

### 4. JNI 中安全地调用 Kotlin/Java 方法

```cpp
/**
 * 演示在 native 层回调 Kotlin 方法时的安全实践。
 */
extern "C" JNIEXPORT void JNICALL callKotlinCallback(
        JNIEnv* env, jobject thiz, jobject callback) {

    // ① 局部引用帧：保护调用期间创建的所有局部引用
    if (env->PushLocalFrame(16) != 0) return;

    jclass callbackClass = env->GetObjectClass(callback);
    jmethodID onResult = env->GetMethodID(callbackClass, "onResult", "(Ljava/lang/String;)V");

    if (onResult == nullptr) {
        // 找不到方法 → 抛出 Java 异常（正确做法，不要返回 NULL 了事）
        jclass excClass = env->FindClass("java/lang/NoSuchMethodError");
        if (excClass != nullptr) {
            env->ThrowNew(excClass, "onResult method not found");
        }
        env->PopLocalFrame(nullptr);
        return;
    }

    // ② 创建 Java String：必须用 NewString（不能直接传 C 字符串）
    jstring result = env->NewStringUTF("处理完成");

    // ③ 调用 Java 方法；调用前要清除待处理的异常
    if (env->ExceptionCheck()) {
        env->ExceptionDescribe();
        env->ExceptionClear();
    }
    env->CallVoidMethod(callback, onResult, result);

    // ④ 检查调用是否抛出异常
    if (env->ExceptionCheck()) {
        env->ExceptionDescribe();
        env->ExceptionClear();
    }

    // ⑤ 释放局部引用帧
    env->PopLocalFrame(nullptr);
}
```

### 6. 用 Kotlin 扩展函数包装 Java API（消除平台类型风险）

```kotlin
/**
 * ✅ 最佳实践：把 Java 边界包一层 Kotlin 扩展，统一处理 null 与平台类型。
 */
object JavaInterop {

    /**
     * Java 的 Cursor 包装成安全的 Kotlin 扩展
     */
    fun Cursor.stringForColumn(name: String): String? {
        val index = getColumnIndex(name)
        // getColumnIndex 返回 -1 表示列不存在
        return if (index < 0 || isNull(index)) null else getString(index)
    }

    /**
     * Java 的 Bundle 包装（Android 13+ 有类型安全的重载）
     */
    fun Bundle.getStringOrDefault(key: String, default: String = ""): String =
        if (Build.VERSION.SDK_INT >= 33) {
            getString(key, default)
        } else {
            @Suppress("DEPRECATION")
            getString(key) ?: default
        }

    /**
     * Java 的 SharedPreferences 包装成委托
     */
    fun SharedPreferences.stringDelegate(key: String, default: String = ""): ReadWriteProperty<Any?, String> =
        object : ReadWriteProperty<Any?, String> {
            override fun getValue(thisRef: Any?, property: KProperty<*>): String =
                thisRef?.let { getString(key, default) } ?: default

            override fun setValue(thisRef: Any?, property: KProperty<*>, value: String) {
                edit().putString(key, value).apply()
            }
        }
}
```

## 常见问题 / 面试要点

**读者问：Kotlin 调用 Java 和 Java 调用 Kotlin，有什么本质区别？**

**AI答：**

1. **根本原因**：Kotlin 编译到**同一套 JVM 字节码**，互调在字节码层面完全对称；差别全部来自**语言特性无法 1:1 映射**。

2. **Kotlin → Java 的三个核心差异**：

| 差异 | 说明 |
| --- | --- |
| **平台类型（Platform Type）** | Java 的方法返回类型在 Kotlin 里变成 `String!`（可空可不空），**编译器不强制判空** → 最常见的 NPE 来源 |
| **默认参数** | Kotlin 有，Java 没有 → Java 必须传全部参数（除非 `@JvmOverloads`） |
| **扩展函数/顶层函数** | 是**静态方法**，Java 侧要用 `FileNameKt.func()` 或 `@file:JvmName` |

3. **Java → Kotlin 的三个核心差异**：

| 差异 | 说明 |
| --- | --- |
| **受检异常** | Kotlin 没有受检异常 → Java 看不到 `throws` 声明 → `catch` 编译报错（需 `@Throws`） |
| **`object` 单例** | Java 要写 `INSTANCE`（或 `@JvmStatic`） |
| **协变/逆变** | Kotlin 的 `List<out T>` → Java 看到 `List<? extends T>`；Java 的 `List<? extends T>` → Kotlin 看到 `List<T>`（投影被"接受"） |

4. **平台类型的危险示例**：

```kotlin
// Java: public String getName() { return null; }
// Kotlin
val name = javaObj.name        // 类型是 String!，编译器放行
name.length                    // ✅ 编译通过，💥 运行时 NPE
```

   **解决**：显式 `val name: String? = javaObj.name` 强制判空。

5. **工程实践建议**：
   - **在 Kotlin 侧包一层扩展/适配器**，把 Java API 的平台类型收敛成安全的 Kotlin 类型。
   - 库的公共 API 上加 `@JvmStatic` / `@JvmOverloads` / `@Throws`，让 Java 调用方体验良好。

6. **面试话术**："互调在字节码层是完全对称的，差异全来自语言特性不匹配。**Kotlin 调 Java 最大坑是平台类型**——Java 的方法返回 `String` 在 Kotlin 里是 `String!`，编译器不检查 null，运行时炸。**Java 调 Kotlin 最大坑是受检异常**——Kotlin 没有 `throws` 声明，Java catch 不到，得用 `@Throws`。另外默认参数、object 单例、顶层函数都需要 `@JvmOverloads`/`@JvmStatic`/`@file:JvmName` 来桥接。"

---

**读者问：`@JvmStatic`、`@JvmField`、`@JvmOverloads` 分别解决什么问题？**

**AI答：**

1. **`@JvmStatic`** —— 让 `object` 或 `companion object` 的成员在 Java 中成为**静态成员**。

```kotlin
object Config {
    @JvmStatic fun create() = Config()
}
// Java: Config.create()     （不加注解要写 Config.INSTANCE.create()）
```

   **底层**：伴生对象里保留原方法，**额外**在宿主类生成一个 `static` 方法委派过去。

2. **`@JvmField`** —— 让属性成为 **public 静态字段**（去掉 getter/setter）。

```kotlin
object Config {
    @JvmField val TIMEOUT = 10_000L
}
// Java: Config.TIMEOUT      （不加注解要写 Config.INSTANCE.getTIMEOUT()）
```

   **限制**（都会编译报错）：
   - 只能用于 **`val`**（不能 `var`）。
   - 不能是 **`private`**。
   - 不能是**委托属性**（`by lazy`）。
   - 不能有**自定义 getter**（没有 backing field）。

3. **`@JvmOverloads`** —— 为**有默认参数**的函数生成重载，让 Java 能省略参数。

```kotlin
@JvmOverloads
fun show(title: String, subtitle: String = "副标题", duration: Int = 3000) { }
// Java 可调用：show("t") / show("t", "s") / show("t", "s", 3000)
```

   **代价**：每个重载都占 DEX 体积 → 只在确实要给 Java 调用的 API 上加。

4. **四者对比速查**：

| 注解 | 作用对象 | Java 侧效果 |
| --- | --- | --- |
| `@JvmStatic` | `object`/`companion` 的**函数** | 静态方法 |
| `@JvmField` | `object`/`companion` 的 **`val` 属性** | 静态字段（无 getter） |
| `@JvmOverloads` | **有默认参数的函数** | 生成多个重载 |
| `@JvmName` | **文件/函数** | 修改生成的 JVM 名字 |
| `@Throws` | **函数** | 声明受检异常 |

5. **面试话术**："这四个注解都是**编译期**给 Java 补齐 Kotlin 缺失的能力：`@JvmStatic` 补静态方法、`@JvmField` 补静态字段、`@JvmOverloads` 补重载、`@Throws` 补受检异常。它们都是在 Kotlin 源码上加的，**不改变 Kotlin 侧的行为**。`@JvmField` 有严格限制：只能 `val`、不能 `private`、不能委托属性、不能自定义 getter。"

**读者问：JNI 的原理是什么？`JavaVM` 和 `JNIEnv` 有什么区别？**

**AI答：**

1. **调用链路**：

```text
Kotlin/Java: native fun foo(): Int
   ↓
JNI 桥接层：Java_包名_类名_方法名（C 函数）
   ↓
C/C++ 实现
```

2. **`JavaVM*` vs `JNIEnv*`（核心区别）**：

| | `JavaVM*` | `JNIEnv*` |
| --- | --- | --- |
| **作用域** | **进程级**（一个进程只有一个） | **线程级**（每线程一个） |
| **主要能力** | 获取/创建 `JNIEnv*`、附加线程 | 所有 JNI 函数（`FindClass`、`GetMethodID`、`NewStringUTF`…） |
| **能否跨线程传** | ✅ 可以（是进程级单例） | ❌ **绝对不能**（不同线程的 `JNIEnv` 不同） |

3. **native 线程的正确姿势**：

```cpp
// native 线程必须先 Attach
JavaVM* g_vm = nullptr;
JNIEnv* env = nullptr;
g_vm->AttachCurrentThread(&env, nullptr);
// ... 使用 env ...
g_vm->DetachCurrentThread();   // 线程结束时
```

   → **忘记 `AttachCurrentThread` 是 JNI 崩溃的头号原因**（所有 `env->xxx` 调用都是野指针）。

4. **方法注册的两种方式**：

| 方式 | 原理 | 优缺点 |
| --- | --- | --- |
| **静态注册** | 函数名必须严格为 `Java_全限定类名_方法名` | 简单；**混淆后失效**（需 `-keepclasseswithmembernames` 规则） |
| **动态注册** | 在 `JNI_OnLoad` 里用 `RegisterNatives` 建立映射 | 函数名可任意（宏生成）→ **混淆安全 ✅**；推荐 |

5. **核心 JNI API 分类**：

```text
类/对象：  FindClass, GetObjectClass, NewObject, NewGlobalRef, DeleteGlobalRef
方法：     GetMethodID, CallObjectMethod, CallVoidMethod, CallIntMethod
字段：     GetFieldID, GetObjectField, SetObjectField
字符串：   NewStringUTF, GetStringUTFChars, ReleaseStringUTFChars
数组：     GetByteArrayElements, ReleaseByteArrayElements
异常：     ThrowNew, ExceptionCheck, ExceptionClear, ExceptionDescribe
引用管理： PushLocalFrame, PopLocalFrame, DeleteLocalRef
```

6. **面试话术**："JNI 是 Java 与 native 之间的桥。`JavaVM*` 是**进程级**的（一个进程一个），`JNIEnv*` 是**线程级**的（每线程一个，**绝对不能跨线程传**）。native 线程必须先 `AttachCurrentThread` 才能用 JNI。方法注册推荐**动态注册**（`JNI_OnLoad` + `RegisterNatives`），因为函数名可以用宏生成，不受混淆影响。"

**读者问：JNI 有什么性能问题？什么时候该用 JNI？**

**AI答：**

1. **五个主要性能问题**：

| 问题 | 成本 | 优化 |
| --- | --- | --- |
| **调用开销** | 每次约 10~100ns（线程状态切换 + 参数转换） | **减少调用次数**，批量处理 |
| **字符串转换** | `GetStringUTFChars` 需要**分配 native 内存 + UTF-16→UTF-8 转换**（中文更贵） | 传 `byte[]` / `ByteBuffer` |
| **数组拷贝** | `GetXxxArrayElements` **全量拷贝**到 native 堆 | 用 `DirectByteBuffer` / 内存映射 |
| **重复 ID 查找** | 每次 `GetFieldID` 都要字符串查找 | **缓存 `jfieldID`/`jmethodID`** |
| **异常检查** | 每次调用返回后都要检查 | 批量调用，一次检查 |

2. **优化的核心原则**：

```text
❌ 逐像素 / 逐元素跨语言调用   → JNI 开销远大于计算本身
✅ 一次传入整个数组，在 native 内部循环处理

❌ 每次访问都 GetFieldID
✅ 初始化时缓存静态 jfieldID

❌ 传 String 让 native 解析
✅ 传 byte[] 让 native 处理字节
```

3. **什么时候值得用 JNI**：

```text
✅ 值得：
  - 已有成熟的 C/C++ 库（图像编解码、加密、机器学习、音视频）
  - 计算密集且 JVM 优化不了（但要先 profile 确认）
  - 需要复用现有 native 代码

❌ 不值得：
  - 简单数值计算 → Kotlin 足够（JIT/AOT 会优化）
  - 细粒度频繁的跨语言调用 → 开销占大头
  - 团队没有 C/C++ 能力 → 维护成本高、崩溃排查难
```

4. **现代替代方案**：

| 方案 | 说明 |
| --- | --- |
| **Rust + NDK** | 内存安全，性能接近 C++；被 Android 官方推荐 |
| **OpenGL ES / Vulkan Compute** | GPU 计算，适合图像与并行计算 |
| **Kotlin Multiplatform + C interop** | 跨平台共享逻辑 |
| **数据库层优化** | 用 SQLite 扩展而非 JNI |
| **纯 Kotlin** | 绝大多数业务逻辑 |

5. **JNI 的稳定性风险**：
   - **native 崩溃 = 整个进程崩溃**（没有 Java 异常能救）。
   - **内存泄漏**（native 侧）无法被 Java GC 回收 → 表现为"用了几天就 OOM"。
   - **ABI 兼容**：不同 Android 版本的 NDK ABI（armeabi-v7a / arm64-v8a / x86_64）都要编译。

6. **面试话术**："JNI 的开销主要在**调用频率、字符串转换和数组拷贝**上。优化原则是'**减少调用次数、传原始数据、缓存 ID**'。要不要用 JNI 要看场景：复用已有 native 库或计算密集才值得；简单计算用 Kotlin 就够。而且 JNI 的代价是**native 崩溃 = 进程崩溃**、**native 内存泄漏 GC 管不了**，所以能用纯 Kotlin 就不碰 JNI。"

**读者问：`@JvmInline value class` 是什么？它解决了什么问题？**

**AI答：**

1. **要解决的问题**：Kotlin 的 `value class`（值类）本意是"**零运行时开销的类型安全包装**"，但早期版本有致命缺陷——**一旦被装箱**（作为泛型参数、存进集合、变成可空类型），就会生成真正的对象，**完全失去优势**。

2. **`@JvmInline`（Kotlin 1.5+）的解法**：**取消装箱，改为内联展开**。

```kotlin
@JvmInline
value class UserId(val value: Long)

// 编译后：没有 UserId 类实例，只有一个 private final long value 字段
// 使用处直接内联成 long
```

3. **内存对比**：

```text
普通 class：
  UserId 对象 = 对象头 16 字节 + Long 8 字节 = 24 字节
  List<UserId> 里还要存引用 8 字节

@JvmInline value class：
  UserId(1L) 直接是 long
  → 零额外开销 ✅
```

4. **限制（面试重点）**：

| 限制 | 原因 |
| --- | --- |
| 必须**单个 val 属性** | value class 只能包装一个值 |
| 属性必须是 **`val`** | 可变会破坏"值语义" |
| **不能被继承**、不能 `open`/`sealed` | — |
| **可空时装箱** | `UserId?` → 真正的对象 |
| **作为泛型参数时装箱** | `List<UserId>` → 装箱 ⚠️ **最容易踩的坑** |
| **Java 侧看不到这个类型** | 只暴露底层类型（`long`） |

5. **Java 侧的互操作**：

```kotlin
@JvmInline value class UserId(val value: Long)
fun findUser(id: UserId): User? = null
```

```java
// Java 侧：看到的是 long，不是 UserId
User findUser(long id);
```

6. **Android 中的典型用途**：为 ID、金额、时间戳、坐标等加类型安全，同时不付内存代价。

```kotlin
@JvmInline value class UserId(val value: Long)
@JvmInline value class SessionToken(val value: String)

// ✅ 正确用法：避免不同 ID 类型混用
fun follow(target: UserId) { ... }
fun follow(target: SessionToken) { }   // ✅ 类型不同，编译期就能发现

// ❌ 无意义：包装成对象反而更费内存
val ids = listOf(UserId(1))     // 装箱了
```

7. **面试话术**："`@JvmInline value class` 是 Kotlin 1.5 引入的**零成本类型安全包装**。它取消装箱，编译器在调用点把类型**内联展开**成底层类型（`long`/`String`），所以既拿到了类型安全，又没有内存开销。代价是：**可空或作为泛型参数时会重新装箱**，而且 **Java 侧看不到这个类型**，只看到底层类型。"

**读者问：为什么 Kotlin 里 Java 方法的返回值可以不加 `?`？平台类型到底是什么？**

**AI答：**

1. **平台类型（Platform Type）的定义**：Java 的类型**本身没有 nullability 信息**（Java 8 之前；Java 8+ 有 JSR 308 的注解但不是强制的）。Kotlin 编译器在读取 Java 声明时，会把 Java 的引用类型标记为**平台类型 `T!`**，意思是"**可能是 T，也可能是 null，但 Kotlin 编译器不做检查**"。

```java
public class User {
    public String getName() { return null; }     // 可能返回 null
    public void setName(String name) { }
}
```

```kotlin
val user: User = User()
val name = user.name        // name 的类型是 String!（平台类型）
name.length                // ✅ 编译通过，运行时 NPE 💥
```

2. **平台类型的三种表现**：

| 位置 | Kotlin 侧表现 |
| --- | --- |
| **返回值** | `String!` —— 可赋给 `String` 或 `String?` |
| **参数** | `String!` —— 可以传 `String` 或 `null` |
| **属性（getter）** | 同返回值 |

3. **怎么消除平台类型**：

```kotlin
// ① 显式声明可空类型（编译器会插入 null 检查）
val name: String? = user.name
println(name?.length)

// ② 用 Kotlin 扩展包装
fun User.nameOrNull(): String? = this.name
```

4. **平台类型是 Kotlin 的"安全网"设计**：
   - 如果强制所有 Java 返回值都当可空处理 → 到处都是 `!!` 或 `?.`，代码噪音大。
   - 如果都当非空 → 大量潜在 NPE。
   - **平台类型是折中**：默认信任 Java 的"契约"（一般不会返回 null），但允许你主动声明可空来获得检查。

5. **Android 实战中的常见 NPE 来源**：

```kotlin
// ① Bundle.getString 可能返回 null（平台类型）
val name = bundle.getString("name")        // String!
val len = name.length                       // 💥 如果 bundle 里没有 "name"

// ② Cursor.getString 在列不存在时可能异常
// ③ TextView.text 可空

// ✅ 建议：在数据边界显式处理
val name: String? = bundle.getString("name")
```

6. **面试话术**："平台类型是 Kotlin 对'Java 没有 nullability 信息'的折中：`String!` 表示**编译器不强制判空**，但你可以主动声明成 `String?` 来获得检查。Java 返回值直接赋给非空变量是安全的（信任契约），但如果 Java 实现可能返回 null，就会变成运行时空指针。**最佳实践是：把 Java API 边界包一层 Kotlin 扩展，显式收敛成可空或非空类型**。"

**读者问：Kotlin 的协程（suspend 函数）怎么从 Java 调用？`

**AI答：**

1. **根本困难**：Kotlin 的 `suspend` 函数在 JVM 上被编译成**接收一个 `Continuation` 参数**的方法：

```kotlin
suspend fun fetchUser(id: Long): User
// 编译成：
Object fetchUser(long id, Continuation<? super User> continuation)
```

   → Java 调用方必须**手动构造 `Continuation`**，极其繁琐。

2. **三种解决方案**：

**① `kotlinx-coroutines-jdk8` 的 `future` 扩展（最常用）**：

```kotlin
// Kotlin 侧：提供 Java 友好的 Future 接口
fun fetchUserAsync(id: Long): CompletableFuture<User> = future {
    fetchUser(id)      // ✅ 在协程里调用 suspend 函数
}
```

```java
// Java 侧
CompletableFuture<User> future = UserApi.fetchUserAsync(1L);
future.thenAccept(user -> System.out.println(user.getName()));
```

**② `suspendCoroutine` 手写桥接（理解原理用）**：

```kotlin
fun fetchUserBlocking(id: Long): User {
    var result: User? = null
    var error: Throwable? = null
    val latch = CountDownLatch(1)

    scope.launch {
        try {
            result = fetchUser(id)      // 在协程里调用 suspend 函数
        } catch (e: Throwable) {
            error = e
        } finally {
            latch.countDown()
        }
    }

    latch.await()                       // ⚠️ 阻塞当前线程（不推荐）
    error?.let { throw it }
    return result!!
}
```

   → 这个版本会**阻塞线程**，不推荐在 Android 主线程用。

**③ Kotlin `CoroutineScope` + Java 的回调接口**：

```kotlin
// 对 Java 最友好的形式：暴露一个普通的方法 + 回调
fun fetchUser(id: Long, onSuccess: (User) -> Unit, onError: (Throwable) -> Unit) {
    scope.launch {
        try {
            onSuccess(fetchUser(id))
        } catch (e: Throwable) {
            onError(e)
        }
    }
}
```

```java
// Java 侧：完全不需要理解协程
api.fetchUser(1L, user -> render(user), error -> showError(error));
```

3. **最佳实践**：**不要让 Java 调用方直接接触 `Continuation`**。正确做法是：
   - 在 Kotlin 侧提供一个**Java 友好的门面**（回调 / `CompletableFuture`）。
   - 协程的实现细节完全封装在 Kotlin 层。

4. **常见坑**：

```kotlin
// ❌ 坑 1：Java 调用 suspend 函数时忘了传 Continuation → 编译错误
// fetchUser(1L)   // Java: 需要 fetchUser(1L, continuation)

// ❌ 坑 2：在 Java 里误以为可以像普通方法一样调用 → NoSuchMethodError

// ❌ 坑 3：把 suspend 函数当作"自动在后台执行" —— 它不会！
// suspend 函数的执行取决于调用它的协程上下文
```

5. **面试话术**："Kotlin 的 `suspend` 函数编译成**带 `Continuation` 参数**的方法，Java 直接调用很痛苦。正确做法是**在 Kotlin 侧提供 Java 友好的门面**——要么用 `kotlinx-coroutines-jdk8` 的 `future {}` 返回 `CompletableFuture`，要么直接暴露**回调接口**。核心原则是：**协程的实现细节不外泄给 Java**。另外要记住 `suspend` 不等于'后台执行'——它只在被调用的协程上下文里运行。"

**读者问：Kotlin 的 `object`、顶层函数、`companion object` 在 Java 里分别怎么调用？为什么这么别扭？**

**AI答：**

1. **三种形态的 Java 访问方式**：

```kotlin
// ① 顶层函数（Top-level function）
// 文件：StringValidators.kt
fun isValidEmail(s: String): Boolean = ...
```
```java
// Java：文件类名 + "Kt" 后缀（因为 JVM 的类名不能与包名冲突，也不能重名）
StringValidatorsKt.isValidEmail("a@b.com");
```
   → **Kotlin 加 `Kt` 后缀是为了避免与同包下的类重名**（文件 `Foo.kt` → 类 `FooKt`，这样同包可以同时有 `class Foo` 和 `Foo.kt`）。

```kotlin
// ② object 单例
object AppConfig {
    fun create() = AppConfig()
    val TIMEOUT = 1000L
}
```
```java
// Java 默认：
AppConfig.INSTANCE.create();
long t = AppConfig.INSTANCE.getTIMEOUT();
```

```kotlin
// ③ companion object
class UserRepo {
    companion object {
        fun create() = UserRepo()
        val DEFAULT = "x"
    }
}
```
```java
// Java 默认：
UserRepo.Companion.create();
String s = UserRepo.Companion.getDEFAULT();
```

2. **用注解优化**：

```kotlin
object AppConfig {
    @JvmStatic fun create() = AppConfig()       // → AppConfig.create()
    @JvmField val TIMEOUT = 1000L                // → AppConfig.TIMEOUT
}

class UserRepo {
    companion object {
        @JvmStatic fun create() = UserRepo()     // → UserRepo.create()
        @JvmField val DEFAULT = "x"              // → UserRepo.DEFAULT
    }
}
```

```kotlin
@file:JvmName("StringValidators")               // → StringValidators.isValidEmail()
fun isValidEmail(s: String): Boolean = ...
```

3. **为什么设计成这样（Kotlin 团队的取舍）**：

| Kotlin 的优势 | Java 侧的不便 |
| --- | --- |
| `object` 支持**继承**（Java 单例不能被继承） | 需要 `INSTANCE` |
| `companion object` 支持**接口实现**、多实例伴随 | 需要 `Companion` |
| 顶层函数**没有类包装**，写工具函数更简洁 | 需要 `FileNameKt` + `Kt` 后缀 |
| **属性 + 自定义 getter** 表达力强 | Java 需要 `getXxx()` |
| 默认参数、命名参数 | Java 需 `@JvmOverloads` |

   → **本质上是 Kotlin 表达能力更强带来的"代价"**，用注解可以把这个代价降到最低。

4. **最佳实践——为 Java 调用方设计 API**：

```kotlin
// ✅ 组合使用注解，给 Java 一个"正常"的 API
object Network {
    @JvmField val BASE_URL = "https://api.example.com"
    @JvmStatic fun client(): OkHttpClient = ...
}

@JvmOverloads
fun request(path: String, timeoutMs: Long = 10_000, retries: Int = 3) { }
```

5. **面试话术**："Kotlin 的 `object` 在 Java 里是 `Xxx.INSTANCE`，`companion object` 是 `Xxx.Companion`，顶层函数是 `FileNameKt.func()`——因为 JVM 的类名不能重名，Kotlin 给文件类加了 `Kt` 后缀。`Kt` 后缀正是为了让 `Foo.kt` 和 `class Foo` 能共存。解决办法是 `@JvmStatic`（静态方法）、`@JvmField`（静态字段）、`@file:JvmName`（改文件名）。本质上这是 Kotlin 更强的表达能力带来的代价，用注解能把它降到最低。"

**读者问：JNI 调用时为什么会崩溃？本地方法引用（native reference）泄漏是怎么排查的？**

**AI答：**

1. **崩溃的四大根因**：

```text
① 忘记 AttachCurrentThread
   native 线程里直接用 JNIEnv* → 野指针 → SIGSEGV 💥
   现象：随机崩溃，多线程下高发

② 局部引用表溢出（Local Reference Table Overflow）
   一个 native 方法里创建 > 16 个局部引用 → 抛异常或崩溃
   现象：处理大量数据时崩溃（如遍历一个 1000 条的查询结果）

③ 忘记 ReleaseStringUTFChars / ReleaseXxxArrayElements
   native 内存泄漏 → 逐渐 OOM（Java 的 GC 管不了 native 内存）

④ 忘记 DeleteGlobalRef
   全局引用泄漏 → 对象永远无法被 GC 回收
```

2. **JNI 引用表的规则**：

```text
局部引用（Local Reference）：
  · 线程私有
  · 数量上限：JNI 规范要求至少 16 个槽位（实际各平台不同）
  · 生命周期：native 方法【返回时自动释放】
  · 手动释放：DeleteLocalRef(ref)

全局引用（Global Reference）：
  · 跨线程有效
  · 生命周期：【不会自动释放】，必须手动 DeleteGlobalRef
  · 弱全局引用（Weak Global Reference）：不阻止 GC 回收

弱引用（Weak Reference）：
  · 不阻止 GC 回收对象
  · 使用前必须 NewLocalRef 转成局部引用
```

3. **局部引用溢出的正确解法**：

```cpp
// ❌ 错误：循环里创建局部引用，累积到 1000 个
for (int i = 0; i < 1000; i++) {
    jstring s = env->NewStringUTF("item");
    env->CallVoidMethod(obj, mid, s);
    // 局部引用一直累积 → 溢出
}

// ✅ 方案 1：手动释放
for (int i = 0; i < 1000; i++) {
    jstring s = env->NewStringUTF("item");
    env->CallVoidMethod(obj, mid, s);
    env->DeleteLocalRef(s);          // ✅ 及时释放
}

// ✅ 方案 2：使用局部引用帧（推荐）
if (env->PushLocalFrame(64) != 0) return;   // 开启帧，最多 64 个
for (int i = 0; i < 1000; i++) {
    jstring s = env->NewStringUTF("item");    // 超出 64 个会自动释放旧的
    env->CallVoidMethod(obj, mid, s);
}
env->PopLocalFrame(nullptr);                  // 一次性释放整帧
```

4. **全局引用泄漏的排查**：

```text
排查手段：
① Android Studio Memory Profiler → 打开 .hprof → 看 "Native Memory" / "JNI Global References"
② LeakCanary（native leak 部分）→ 显示 native 分配栈
③ dumpsys meminfo <package> → 看 "Native Heap" 是否持续增长
④ 在 native 侧埋点：统计 NewGlobalRef / DeleteGlobalRef 的次数，两边应该配平

常见泄漏点：
  · 全局变量持有 jobject
  · 单例缓存了 Activity 的引用
  · 回调注册后没有反注册（native 侧的全局引用）
  · 异常路径上提前 return，漏掉了 DeleteGlobalRef
```

5. **异常处理的正确姿势**：

```cpp
// ❌ 错误：Java 方法调用后不检查异常
env->CallVoidMethod(obj, mid);
jstring result = (jstring)env->GetObjectField(obj, fid);  // 💥 携带未处理异常继续执行 → 崩溃

// ✅ 正确：每次调用后检查
env->CallVoidMethod(obj, mid);
if (env->ExceptionCheck()) {
    env->ExceptionDescribe();     // 打印到 logcat
    env->ExceptionClear();        // 清除异常，继续执行
    return;
}
```

   → **JNI 规则**：一旦有异常挂起，**只能调用少数几个特定函数**（`ExceptionCheck` / `ExceptionClear` / `ExceptionDescribe` / `DeleteLocalRef` / `DeleteGlobalRef` / `Release*`），其他调用都是**未定义行为**。

6. **native 线程的正确模板**：

```cpp
// ✅ 线程启动时 Attach，结束时 Detach
void* thread_func(void* arg) {
    JNIEnv* env = nullptr;
    if (g_vm->AttachCurrentThread(&env, nullptr) != JNI_OK) {
        LOGE("AttachCurrentThread 失败");
        return nullptr;
    }
    // ... 使用 env ...

    g_vm->DetachCurrentThread();
    return nullptr;
}
```

7. **面试话术**："JNI 崩溃主要四个原因：**忘记 `AttachCurrentThread`**（native 线程野指针）、**局部引用表溢出**（一个方法里创建超过 16 个局部引用）、**忘记 `Release*` 系列**（native 内存泄漏）、**忘记 `DeleteGlobalRef`**（全局引用泄漏，GC 管不了）。解法是用 `PushLocalFrame`/`PopLocalFrame` 管理局部引用、用 `try-finally` 语义保证 `DeleteGlobalRef`。另外 JNI 规定：**有异常挂起时只能调 `ExceptionCheck`/`ExceptionClear` 等少数函数**，其他调用是未定义行为。"

---

**读者问：Kotlin 的 `object` 和 Java 的单例有什么区别？Kotlin 的 `data class` 在 Java 里怎么用？**

**AI答：**

1. **`object` vs Java 单例的四个区别**：

| 维度 | Kotlin `object` | Java 静态单例 |
| --- | --- | --- |
| **继承** | ✅ **可以被继承**（`object` 是普通的类） | ❌ 静态方法不能被继承 |
| **实现接口** | ✅ `object : Listener { }` | ❌ 需要额外写静态内部类 |
| **初始化时机** | 类首次被访问时（懒加载，由 JVM 保证线程安全） | 取决于实现（`static final` 字段初始化时机） |
| **Java 侧访问** | `Xxx.INSTANCE`（或 `@JvmStatic`） | `Xxx.getInstance()` |

2. **`object` 可以被继承**（这是 Kotlin 相比 Java 的独特之处）：

```kotlin
open class Base {
    open fun greet() = "Base"
}

object MyImpl : Base() {
    override fun greet() = "MyImpl"
}

val b: Base = MyImpl
b.greet()      // "MyImpl" —— ✅ object 参与正常的虚派发
```

   → Java 的静态单例**做不到**（静态方法没有多态）。

3. **`object` 的线程安全初始化**：

```text
Kotlin 的 object 初始化由 JVM 保证【类初始化锁】保证线程安全
→ 多个线程同时首次访问 MyImpl.xxx() 时，JVM 保证只初始化一次
→ 这是 JVM 规范保证的，不需要额外同步
```

4. **`data class` 在 Java 侧的使用**：

```kotlin
data class User(val id: Long, val name: String, val age: Int)
```

```java
// Java 侧生成的 API：
User u = new User(1L, "Alice", 30);   // ✅ 构造函数
long id = u.getId();                    // ✅ getter（不是 public final 字段！）
String name = u.getName();
User copy = u.copy(2L, "Bob", 31);      // ✅ copy（但需要传全部参数）
User copy2 = u.component1();            // ⚠️ component1 返回 id（Long），不是 User
```

   **Java 侧的三个坑**：
   - **属性是 `getXxx()` 不是字段**（Kotlin 的 `val` 编译成 private final 字段 + public getter）。
   - **`copy()` 必须传全部参数**（Kotlin 有默认参数，Java 没有 → 需 `@JvmOverloads` 但 `copy` 是编译器生成的，加不了）。
   - **没有 `equals` 的对称性保证**？—— 实际上 `data class` 会生成 `equals`/`hashCode`/`toString`/`copy`/`componentN`，Java 侧都能用，只是形式不同。

5. **`data class` 的限制**：

```kotlin
// ❌ 编译错误：data class 必须至少有一个参数
data class Empty()

// ❌ 编译错误：所有参数必须是 val 或 var
data class Bad(val a: Int, b: Int)

// ❌ 编译错误：不能是 abstract/open/sealed
open data class Bad2(val a: Int)

// ❌ 编译错误：不能继承其他类（只能实现接口）
data class Bad3(val a: Int) : SomeBaseClass()

// ✅ 可以实现接口
data class Good(val a: Int) : Comparable<Good> { ... }
```

6. **`data class` 的 `equals`/`hashCode` 语义**：

```kotlin
data class User(val id: Long, val name: String)
// equals 比较【所有构造参数】
// hashCode 基于【所有构造参数】
```

   → 与 Java 里手写 `equals`/`hashCode` 一样，**可变字段会破坏 hashCode 契约**（放进 `HashMap` 后改字段就找不到了）。

7. **面试话术**："Kotlin 的 `object` 和 Java 的静态单例最大的不同是**它可以被继承、可以实现接口、参与正常的虚派发**——Java 的静态单例做不到。`object` 的初始化由 JVM 的类初始化锁保证线程安全。`data class` 在 Java 侧能用，但属性是 `getXxx()` 而不是字段，`copy()` 必须传全参数（因为默认参数加不了 `@JvmOverloads`），而且 `equals`/`hashCode` 基于全部构造参数——所以可变字段放进 `HashMap` 会出问题。"

# 高阶函数与扩展

## 一句话定义

**高阶函数**是"接收函数作为参数或返回函数"的函数，它是 Kotlin 一切声明式 API（`map` / `filter` / `let` / Flow 操作符）的语法基础；**扩展函数**则是"给已有类凭空加方法"的语法糖，编译后变成静态方法（`static` 方法 + 第一个参数是接收者），因此不需要修改原类、不需要继承、也不需要动态派发。两者合起来构成了 Kotlin **"不修改原类也能扩展行为"** 的核心表达力。

## 核心原理

### 1. 高阶函数与函数类型

Kotlin 中"函数是一等公民"的具体体现是 **函数类型（Function Type）**：

```kotlin
// 函数类型：参数类型 -> 返回类型
val sum: (Int, Int) -> Int = { a, b -> a + b }

// 带接收者的函数类型（Extension Function Type）
val String.shout: () -> String get() = this.uppercase() + "!"

// 返回函数的函数（高阶函数的典型形态）
fun makeAdder(n: Int): (Int) -> Int = { it + n }

// 把函数作为参数传递
fun operate(a: Int, b: Int, op: (Int, Int) -> Int): Int = op(a, b)
```

**底层表示**：`(Int, Int) -> Int` 在 JVM 上编译为 **`kotlin.jvm.functions.Function2<Integer, Integer, Integer>`** 的实例（`Function0` ~ `Function22`）。

```text
Kotlin 函数类型            JVM 实际类型
──────────────────────    ────────────────────────────────────
() -> Unit              →  Function0<Unit>
(Int) -> String         →  Function1<? super Integer, ? extends String>
(Int, Int) -> Int       →  Function2<? super Integer, ? super Integer, ? extends Integer>
(String) -> Unit        →  Function1<? super String, Unit>
```

> **面试冷知识**：因为函数类型在 JVM 上是接口（不是 `invokedynamic` + LambdaMetafactory，虽然 Kotlin 1.5+ 编译 lambda 字面量时会用 `invokedynamic`），所以：
> - Kotlin **可以**用 `Function1` 类型对 Java 的函数式接口做 SAM 转换。
> - Java **不能**直接使用 Kotlin 的 `Function1` 作为 SAM 目标（但 Kotlin 提供了 `kotlin.jvm.Function` 到 Java 函数式接口的转换器）。

### 2. inline 函数：消除函数对象与 Lambda 对象

#### 2.1 为什么需要 inline

普通函数传入 lambda 时会产生**两个额外的对象**：

```text
每次调用
  ├─ ① 函数对象：Function1 实例（captures 外部变量）
  └─ ② Lambda 对象：真正的实现体被编译成匿名内部类
```

`inline` 把函数体**直接展开（文本替换）到调用点**，从而不需要创建函数对象和 Lambda 对象。

```kotlin
// 编译器自动 inline（不需要写 inline 关键字）
public inline fun <T> Iterable<T>.forEach(action: (T) -> Unit) {
    for (element in this) action(element)
}

// 需要手写 inline 的场景：接受 lambda 参数的高阶函数
inline fun <T> measureTime(block: () -> T): T {
    val start = System.nanoTime()
    val result = block()
    println("耗时 ${(System.nanoTime() - start) / 1_000_000} ms")
    return result
}
```

#### 2.2 inline 的三大能力

`inline` 函数体内可以访问 `public` / `internal` 的非局部返回、`vararg`、`reified` 类型参数。

| 能力 | 语法 | 用途 |
| --- | --- | --- |
| **非局部返回（Non-local return）** | `return` 直接返回外层函数 | 早退（early return） |
| **变参（vararg）** | `vararg T` | 包装可变参数 |
| **具体化类型（reified）** | `inline fun <reified T> ...` | 运行时读取类型信息 |

```kotlin
// ① 非局部返回
inline fun process(list: List<String>) {
    list.forEach {
        if (it.isEmpty()) return      // ✅ 直接返回 process()，不是只退出 forEach
        println(it)
    }
    println("永远不会被打印")
}

// ② vararg
inline fun logAll(vararg tags: String, message: String) {
    tags.forEach { println("[$it] $message") }
}
logAll("A", "B", message = "hello")

// ③ reified
inline fun <reified T> parse(json: String): T =
    gson.fromJson(json, T::class.java)     // ✅ T::class.java 需要 reified
```

#### 2.3 inline 的代价与规则

- **代价**：代码体积膨胀（每个调用点都展开一份）。所以**只对"高频 + 小体积"的函数用 inline**，如 `also` / `let` / `apply` / `run` / `with` / `takeIf` / `repeat` / `forEach` / `let`。
- **规则**：
  - `inline` 函数**只能是 public 或 internal**（private inline 会有 "public-API inline function cannot access non-public-API" 错误）。
  - `inline` 函数引用的属性/方法必须也是 public 或 internal。
  - `inline` 函数**不能**是 `abstract` / `open`（非 final 的成员函数不能 inline，因为无法在编译期确定实现）。

### 3. noinline 与 crossinline

这两个修饰符是 `inline` 的"补丁"，用来**关掉某些 inline 带来的能力**。

| 修饰符 | 作用 | 为什么需要 |
| --- | --- | --- |
| `noinline` | 参数**不内联**，仍然编译成函数对象 | 需要把函数**作为值传递**给别的函数；或者需要**非局部返回被禁止**（返回外层） |
| `crossinline` | 参数可以内联，但**禁止非局部返回** | 允许内联（省对象），但不允许 `return` 跳出外层函数 |

#### 3.1 noinline 的典型场景

```kotlin
// 场景 A：把函数对象存起来 / 传给另一个函数
inline fun save(block: () -> Unit) {
    val task = Runnable { block() }    // ❌ 若 block 内联，这里可以写，但下面就传不出去了
    executor.submit(task)
}

// 正确写法：noinline
inline fun schedule(block: () -> Unit) {
    val task = Runnable { block() }    // ✅ block 编译成 Function0 对象
    executor.submit(task)
}

// 场景 B：禁止非局部返回
inline fun runIf(condition: Boolean, block: () -> Unit) {
    if (condition) block()
}
fun test() {
    runIf(false) { return }   // 若无 noinline，这里 return 会返回 test()（非局部返回）
}
```

**更重要的原因**：Kotlin 编译器对 inline 函数体做**控制流分析**。如果参数被内联，编译器需要追踪"这个 lambda 里的 `return`/`break`/`continue` 跳到哪里"，当 lambda 被传给**多个**调用点或**非内联**的上下文时，会报 "Inline function ... cannot be used as a crossinline/noinline parameter" 错误。

#### 3.2 crossinline 的典型场景

```kotlin
// 需要内联优化，但 lambda 里不能 return 外层
inline fun repeat(times: Int, action: (Int) -> Unit) {
    for (i in 0 until times) action(i)
}

// 场景：把 action 同时用于两个地方（比如先执行再重试），此时 lambda 可能被"多次调用"
inline fun <T> retry(times: Int, action: () -> T): T {
    repeat(times) {          // action 内联进来；action 里的 return 会跳出 retry —— 语义混乱
        try { return action() } catch (e: Exception) { /* retry */ }
    }
    error("unreachable")
}
```

**`crossinline` 的典型场景是 `forEach` 的 `crossinline` 参数**：

```kotlin
public inline fun <T> Iterable<T>.forEach(crossinline action: (T) -> Unit) {
    for (element in this) action(element)
}
```

`crossinline` 保证"这个 lambda 会被内联进一个循环体，且 `return` 只能返回 `forEach` 本身，不能返回更外层"——这正是 `forEach` 需要的语义（`forEach` 是内联函数，`return` 只能从 `forEach` 返回）。

> **面试话术**："`inline` 把函数体展开到调用点，代价是失去两个能力：参数可以被当**值**传递（非内联），以及 lambda 里可以**非局部返回**。`noinline` 关掉前者（参数变回一个函数对象），`crossinline` 关掉后者（仍然内联优化，但 `return` 只能返回当前内联函数）。"

### 4. reified：为什么需要它

`reified`（具体化）让编译器把类型参数 `T` 在**编译期**替换成实际类型，从而允许 `is`、`as`、`T::class.java` 这类**运行时需要类型信息**的操作。

```kotlin
// ❌ 普通泛型：编译后 T 被擦除为 Object，拿不到具体类型
fun <T> jsonParser(): JsonParser<T> = GsonJsonParser()   // 擦除后是 JsonParser<Object>

// ✅ reified：编译器在每个调用点把 T 替换为实际类型
inline fun <reified T> Gson.fromJson(json: String): T = fromJson(json, T::class.java)
```

**原理对比**：

```text
普通泛型（擦除）                    reified
──────────────────────          ──────────────────────
fun <T> foo(x: T)                inline fun <reified T> foo(x: T)
   ↓ 编译                          ↓ 编译
void foo(Object x)               void foo(String x)     ← 在调用点特化
   ↓                              ↓
T::class → 报错                  T::class.java → String.class ✅
x is T    → 报错                  x is String → 正常 ✅
```

**关键限制**：

1. `reified` **必须**配合 `inline`（编译器需要把类型信息写进字节码）。
2. `reified` 类型参数**可以是可空类型**（`T::class` 对可空类型返回的是"装箱后的类型"，`T::class` 在 `T` 可空时得到的是 `Foo::class`，但 `null` 判断要另处理）。
3. **不能**用于**成员函数**（扩展函数可以，因为扩展函数本身就是静态方法）——非扩展的成员函数不能 inline。
4. **不能**与 `vararg` 一起用（Kotlin 限制）。

```kotlin
// ✅ 扩展函数 + reified
inline fun <reified T> Intent.getParcelableExtraCompat(name: String): T? =
    if (Build.VERSION.SDK_INT >= 33) getParcelableExtra(name, T::class.java)
    else @Suppress("DEPRECATION") getParcelableExtra(name) as? T

// ❌ 成员函数不能 reified
class Holder {
    inline fun <reified T> get(): T = null as T   // 编译错误：'reified' type parameter is not allowed in a member function
}
```

### 5. 扩展函数原理：编译成静态方法

**这是面试官必问的第一层。**

```kotlin
fun String.isBlankOrNull(): Boolean = this.isBlank() || this == null
```

编译后（`javap` 结果）：

```text
public final class FooKt {                        // 文件名 FooKt = 文件名 + "Kt"
    public static boolean isBlankOrNull(String $this) {   // 接收者变成第一个参数
        return StringsKt.isBlank($this) || $this == null;
    }
}
```

**结论**：

| 特性 | 说明 |
| --- | --- |
| **静态派发（Static Dispatch）** | 编译成 `static` 方法，**不是**虚方法 → **不能被子类重写** |
| **接收者是第一个参数** | `a.foo(b)` → `FooKt.foo(a, b)` |
| **文件即类名** | `Extensions.kt` → `ExtensionsKt`；多个文件同名会冲突（用 `@file:JvmName`） |
| **导入方式** | `import a.b.isBlankOrNull`（导入的是**顶层函数**，不是成员） |

```kotlin
// 调用形式
"hello".isBlankOrNull()
        ↓ 编译为
ExtensionsKt.isBlankOrNull("hello")
```

**扩展属性**同理，编译成静态的 `getXxx()` / `setXxx()`：

```kotlin
val String.initial: Char get() = first()
    ↓
public static final char getInitial(String $this) { return $this.charAt(0); }
```

> **注意**：扩展属性**没有 backing field**（不能有 `var` 的真实存储），`var` 扩展属性必须有自定义的 getter/setter，setter 默认用 `$this` 无法赋值（因为接收者是 `val`）。

### 6. 扩展函数 vs 成员函数：优先级规则

**这是面试官必问的第二层。**

```kotlin
class Animal {
    fun speak() = "Animal speaks"
}
class Dog : Animal() {
    fun speak() = "Dog barks"          // 成员函数重写
}

// 扩展函数
fun Animal.speak() = "Extension speaks"
fun Dog.speak() = "Dog extension"      // ⚠️ 编译错误！成员函数优先，同名扩展被"遮蔽"（shadowed）
```

**优先级规则（从高到低）**：

```text
1. 成员函数（member）              ← 永远最高优先
2. 扩展函数（extension）           ← 按"最具体的接收者静态类型"匹配
3. 泛型扩展（generic extension）    ← 例如 fun <T> T.foo()
4. 扩展属性（extension property）   ← 无成员属性可匹配时
5. 成员属性
```

**关键推论**：

```kotlin
fun Any?.toStringOrEmpty(): String = this?.toString() ?: ""

// Dog 有成员 toString()
val d: Dog = Dog()
d.toStringOrEmpty()   // ✅ 调用扩展（toStringOrEmpty 成员不存在）
d.toString()          // ✅ 调用成员的 toString()
```

**成员扩展函数（Member Extension Functions）**——面试第三层：

```kotlin
class Html {
    fun render(block: StringBuilder.() -> Unit): String {
        val sb = StringBuilder()
        sb.block()          // 在 StringBuilder 的作用域里执行 block
        return sb.toString()
    }
}

fun StringBuilder.buildHtml(): String {
    append("<h1>")
    append(this)          // this 是 StringBuilder
    append("</h1>")
    return toString()
}
```

```kotlin
// 使用
val html = Html().render {
    buildHtml()           // ✅ 隐式接收者 this = StringBuilder
}
```

**成员扩展的关键特性**：

| 特性 | 说明 |
| --- | --- |
| **静态派发** | 编译成类的成员方法，接收者是**第一个参数** |
| **有 `this`（外部类实例）** | 在成员扩展内部，`this` 指外部类，`this@Outer` 可访问 |
| **不能被继承/重写** | 静态方法，子类无法 override |
| **派发基于静态类型** | `val a: Animal = Dog(); a.memberExt()` 调用的是 `Animal` 版本的扩展 |
| **必须显式导入** | 成员扩展**不在作用域内自动可见**，需要 `import pkg.Outer.memberExt` |
| **不能有 `override`** | 扩展不能重写成员 |

```kotlin
// 派发是静态的
class Base { fun ext() = "Base.ext" }
class Derived : Base() { fun ext() = "Derived.ext" }   // 这是"遮蔽"，不是重写

fun Base.ext() = "Base extension"
fun Derived.ext() = "Derived extension"

val b: Base = Derived()
b.ext()    // 调用成员 → "Derived.ext"（成员永远优先，且成员是虚派发）
```

### 7. 作用域函数完全对比表

Kotlin 提供 5 个核心作用域函数 + 2 个判定函数。**选错的代价是"接收者丢失"和"返回值错误"。**

| 函数 | 接收者 | 返回值 | 作用 | 典型场景 |
| --- | --- | --- | --- | --- |
| `let` | `it` | **lambda 的结果** | 安全调用 + 空检查 | `nullable?.let { ... }` |
| `run` | `it` | **lambda 的结果** | 计算值 + 空检查 | `val r = repo.run { query() }` |
| `with` | `this` | **lambda 的结果** | 多次访问同一对象 | `with(textView) { text = ...; setText(...) }` |
| `apply` | `this` | **接收者本身** | 配置对象 | `TextView().apply { text = "hi" }` |
| `also` | `it` | **接收者本身** | 附加副作用 | `builder.apply {}.also { log(it) }` |
| `takeIf` | `it` | 接收者或 null | 条件满足则保留 | `takeIf { it > 0 }` |
| `takeUnless` | `it` | 接收者或 null | 条件**不**满足则保留 | `takeUnless { it.isEmpty() }` |

**决策树**：

```text
需要把对象当作参数传进去？ → let / also（用 it）
需要把对象当作"上下文"来配置？ → apply / with（用 this）
需要用对象计算出一个新值？ → let / run
需要配置完再拿回对象？ → apply
需要副作用（打日志/校验）但保持链式？ → also
takeIf vs takeUnless：条件是"要保留"用 takeIf，是"要排除"用 takeUnless
```

**经典组合拳**：

```kotlin
// apply + also：先配置，再打日志
val tv = TextView(context).apply {
    text = "Hello"
    setTextColor(Color.RED)
}.also {
    Log.d(TAG, "创建了 TextView: $it")
}

// let + also：安全取值 + 副作用
val len = user?.name?.let { it.length }.also { Log.d(TAG, "长度 $it") }

// with：连续操作同一对象
with(binding) {
    title.text = "标题"
    submit.isEnabled = true
}
```

**`run` vs `with` 的区别**（常被问）：

| | `run` | `with` |
| --- | --- | --- |
| 接收者 | `it` | `this` |
| 空安全 | ✅ `nullable?.run {}` | ❌ `with` 不接受可空 |
| 返回 | lambda 结果 | lambda 结果 |

### 8. Lambda 与 SAM 转换、函数引用

#### 8.1 Lambda 语法

```kotlin
// 单参数：it（隐式）
list.forEach { println(it) }

// 多参数：显式命名
list.forEach { item, index -> println("$index: $item") }

// 空参数 it：写 _
list.forEach { _ -> doSomething() }

// 多行 lambda：最后一个表达式是返回值
val result = run {
    val a = 1
    val b = 2
    a + b        // ← 返回值
}
```

#### 8.2 SAM 转换（Single Abstract Method）

Kotlin 调用 Java 的函数式接口时**自动转换**：

```kotlin
// Java
public interface Runnable { void run(); }
public interface Comparator<T> { int compare(T a, T b); }

// Kotlin 中直接传 lambda
thread(start = true) { println("hello") }              // SAM 转换
listOf(3, 1, 2).sortedWith { a, b -> b - a }          // SAM 转换

// 显式构造 SAM 实例（需要保留类型信息时）
val r: Runnable = Runnable { println("hi") }
```

**SAM 转换的限制**：

| 限制 | 说明 |
| --- | --- |
| **只对 Java 接口生效** | Kotlin 函数式接口**不能**用 lambda 隐式转换（Kotlin 1.4+ 需要 `fun interface` + 显式转换） |
| **构造函数引用** | Java 接口的构造函数引用要写成 `Runnable { }`（不能 `::Runnable`） |
| **Kotlin `fun interface`** | Kotlin 1.4+ 定义的 `fun interface` 支持 SAM 转换，但需要显式写 `SamInterface { ... }` |

```kotlin
// Kotlin fun interface
fun interface OnClickListener {
    fun onClick(view: View)
}
val listener = OnClickListener { v -> v.visibility = View.GONE }  // ✅ 显式 SAM 转换
```

#### 8.3 函数引用

| 写法 | 含义 | 类型 |
| --- | --- | --- |
| `::foo` | 顶层函数引用 | `KFunction1<...>` |
| `String::length` | **绑定**成员引用（已确定接收者） | `() -> Int` |
| `String::isEmpty` | 未绑定（接收者是参数） | `(String) -> Boolean` |
| `::Foo` | 构造器引用 | `() -> Foo` |
| `Foo::new` | 构造器引用（带参数） | `(Int) -> Foo` |
| `obj::method` | 绑定实例方法 | `(...) -> R` |
| `Foo::class` | **类字面量**（Kotlin 1.1+） | `KClass<Foo>` |

```kotlin
val lengthRef: (String) -> Int = String::length       // 未绑定
val len2: (String) -> Int = { it.length }
val len3 = "abc"::length                             // 绑定，返回 () -> Int

fun create(): Thread = Thread(::runTask)
val factory: (Int) -> Foo = Foo::new

// 类字面量 vs Java 的 Foo.class
val kClass: KClass<Foo> = Foo::class
val javaClass: Class<Foo> = Foo::class.java
```

**Kotlin 1.1+ 的 `::class` 是 Kotlin 特有的**（Java 需要 `Foo.class`）。但 `::class.java` 可以拿到 Java 的 `Class` 对象——这是 Kotlin 与 Java 互操作的关键桥梁（见 [[../跨语言互调]]）。

### 9. 操作符重载（Operator Overloading）

Kotlin 允许重载一批固定名字的运算符，**通过 `operator` 修饰符声明**。

```kotlin
data class Vec2(val x: Double, val y: Double) {
    // 单目运算：unaryPlus / unaryMinus / not / inc / dec
    operator fun unaryMinus(): Vec2 = Vec2(-x, -y)
    operator fun inc(): Vec2 = Vec2(x + 1, y + 1)

    // 二元运算：plus / minus / times / div / rem
    operator fun plus(other: Vec2): Vec2 = Vec2(x + other.x, y + other.y)
    operator fun times(scalar: Double): Vec2 = Vec2(x * scalar, y * scalar)

    // 比较：compareTo（重写后可用 < > <= >=）
    override fun compareTo(other: Vec2): Int =
        compareValuesBy(this, other, { it.x }, { it.y })

    // 范围：rangeTo
    operator fun rangeTo(other: Vec2): ClosedFloatingPointRange<Vec2> = ...
}

// 包含：contains
operator fun ClosedRange<Int>.contains(v: Vec2) = ...
```

**可重载的运算符清单**：

| 类别 | 运算符 | 方法名 |

### 10. 委托（Delegation）：Kotlin 的"组合替代继承"

#### 10.1 委托的三种形态

```kotlin
// ① 接口委托：把接口实现委托给另一个对象（"by" 关键字）
class AppListAdapter : RecyclerView.Adapter<VH>() by BaseAdapter()

// ② 类委托：Kotlin 没有 Java 的"类委托"语法，但可以用接口委托实现
class FancyListAdapter(private val base: BaseAdapter) : Adapter by base

// ③ 属性委托：把属性的读写委托给一个对象
class LazyDelegate<T>(private val initializer: () -> T) {
    private var value: T? = null
    operator fun getValue(thisRef: Any?, property: KProperty<*>): T {
        if (value == null) value = initializer()
        return value as T
    }
}
```

#### 10.2 标准库委托

| 委托 | 作用 | 原理 |
| --- | --- | --- |
| `by lazy { }` | **延迟初始化**（线程安全，默认 `SYNCHRONIZED`） | 双重检查 + `synchronized` |
| `by Delegates.observable(...)` | 属性变化回调 | setter 前后触发 |
| `by Delegates.vetoable(...)` | 属性变化可拒绝 | 返回 false 则拒绝赋值 |
| `by lateinit var` | 延迟初始化（非空类型） | 运行时检查 `== null` 抛 `UninitializedPropertyAccessException` |
| `by viewBinding()` | ViewBinding 委托 | 反射 + 缓存 |
| `by activityViewModels()` | ViewModel 委托 | `ViewModelStore` |

```kotlin
// lazy 三种模式
private val a by lazy { expensive() }                              // 默认 SYNCHRONIZED（线程安全）
private val b by lazy(LazyThreadSafetyMode.NONE) { expensive() }    // 无锁（单线程用，最快）
private val c by lazy(LazyThreadSafetyMode.PUBLICATION) { e() }     // 可能多次初始化
```

**`lazy` 的源码要点**：

```kotlin
public actual fun <T> lazy(initializer: () -> T): Lazy<T> = SynchronizedLazyImpl(initializer)

private class SynchronizedLazyImpl<out T>(initializer: () -> T) : Lazy<T> {
    private var initializer: (() -> T)? = initializer
    @Volatile private var _value: Any? = UNINITIALIZED_VALUE
    override val value: T
        get() {
            val v = _value
            if (v !== UNINITIALIZED_VALUE) {
                @Suppress("UNCHECKED_CAST") return v as T     // ✅ 已初始化，直接返回
            }
            return synchronized(this) {                    // ✅ 双重检查 + 锁
                val v = _value
                if (v === UNINITIALIZED_VALUE) {
                    _value = initializer!!.invoke()
                }
                v as T
            }
        }
}
```

**`lateinit` vs `lazy`**：

| | `lateinit var` | `by lazy` |
| --- | --- | --- |
| 类型 | **只能非空**（`lateinit var name: String`） | 任意类型（含可空） |
| 是否可用 `?` | ❌ | ✅ |
| 检查时机 | 访问时抛 `UninitializedPropertyAccessException` | 访问时初始化 |
| `isInitialized` | ✅ 有这个属性 | ❌ |
| 初始化位置 | 任意（通常 `onCreate`） | 声明处 |

### 11. Sequence vs List：惰性求值

```kotlin
// List（Eager）：立即执行，全部结果装进内存
val list = listOf(1, 2, 3, 4, 5)
    .map { it * 2 }
    .filter { it > 4 }
    .toList()      // ← 到这里才真正计算，但前面的 map/filter 早已全跑完

// Sequence（Lazy）：按需计算，边算边给
val seq = sequenceOf(1, 2, 3, 4, 5)
    .map { it * 2 }
    .filter { it > 4 }
    .toList()      // ← 惰性：map 只对通过 filter 的元素执行
```

| 维度 | List | Sequence |
| --- | --- | --- |
| 求值策略 | **立即求值（Eager）** | **惰性求值（Lazy）** |
| 内存 | 中间集合全部驻留 | 只保留当前元素 |
| 多次遍历 | 每次遍历重新计算（除非 `.toList()`） | **同一个 Sequence 只能消费一次**（`iterator()` 是受限的） |
| 短路操作 | `first`/`take` 会遍历但前面的已算完 | `first`/`take` **提前终止**，后面的不计算 |
| 链式操作 | 返回新 List（每个操作一个对象） | 返回同一个 Sequence 包装器（几乎零分配） |
| 典型用途 | 数据量小、需要多次索引/遍历 | 数据量大、只需前 N 个、链式操作多 |

**关键性能对比**：

```kotlin
// 假设 list 有 1,000,000 条
val eager = list.map { expensive(it) }.filter { it > 0 }.first()
//   → map 对 100 万条全部执行，filter 也执行 100 万次

val lazy = list.asSequence().map { expensive(it) }.filter { it > 0 }.first()
//   → 遇到第一个满足条件的就停止，可能只执行了几次
```

**Sequence 的两个常见坑**：

1. **同一个 Sequence 不能重复消费**：`sequence.constrainOnce()` 可以限制只消费一次（Android 的 `LiveData` 转换就用了这个）。
2. **`Sequence` 不是 `Collection`**，没有 `size`/`get()`；需要时调 `.toList()` 转换。

```kotlin
// 在 Android 里把 List 转成 Sequence 做查询
val users: List<User> = loadUsers()
val seniors = users.asSequence()
    .filter { it.age >= 60 }
    .sortedBy { it.name }
    .take(10)
    .toList()
```

### 3. noinline + crossinline 的实际应用

```kotlin
/**
 * noinline：把 lambda 当作"值"传递给其他函数（需要对象身份）。
 * crossinline：允许内联优化，但禁止非局部返回。
 */
inline fun <T> runTwice(
    initial: T,
    noinline block: (T) -> Unit      // 需要把 block 作为对象传出去 → noinline
) {
    val wrapped = { v: T -> block(v) }   // 必须能引用 block 作为值
    wrapped(initial)
    wrapped(initial)
}

/**
 * crossinline：lambda 会被内联进循环，但不允许 return 外层函数。
 * forEach 就是这样声明的。
 */
inline fun <T> Iterable<T>.forEachSafe(crossinline action: (T) -> Unit) {
    for (e in this) action(e)
}

fun useCrossinline() {
    listOf(1, 2, 3).forEachSafe {
        if (it == 2) return      // ✅ 只能从 forEachSafe 返回，不是从 useCrossinline 返回
        println(it)
    }
}
```

### 8. Sequence：惰性求值的实际收益

```kotlin
/**
 * Sequence 在大数据量上的优势：
 * 1. 不创建中间集合 → 减少 GC 压力
 * 2. 短路操作提前终止 → 避免无用计算

data class Sensor(val id: Int, val value: Double, val timestamp: Long)

fun analyze(sensors: List<Sensor>): List<Sensor> {

    val eager = sensors

        .filter { it.value > 100.0 }
        .take(10)

    val lazy = sensors.asSequence()

        .filter { it.value > 100.0 }
        .take(10)
        .toList()

}
```

## 常见问题 / 面试要点

**读者问：`inline` 函数的原理是什么？它到底优化了什么？**

**AI答：**

1. **原理**：编译器在编译期把 `inline` 函数体**文本替换**到每个调用点（字节码层面的展开），而不是生成一个方法再调用。
2. **优化了什么**：
   - **消除函数对象**：不再创建 `Function1` 实例（省一次堆分配）。
   - **消除 Lambda 对象**：lambda 字面量不再编译成匿名内部类（省一次对象 + 一次虚调用）。
   - **允许非局部返回**：`return` 可以直接返回外层函数，不需要 `Label` 或 `Result` 包装。
   - **允许 `reified`**：把类型参数在编译期特化。
   - **允许访问 private 成员**：内联后能访问外部类的私有成员（这是 Kotlin 集合库大量使用 inline 的原因）。
3. **代价**：
   - **代码体积膨胀**（每个调用点一份拷贝）→ 增加 DEX 体积和指令缓存压力。
   - **不能有 open/abstract/override 修饰**（编译期无法确定实现）。
   - **只能是 public 或 internal**（内联代码会进入调用方模块）。
4. **什么时候用**：
   - lambda 参数**只调用一次**。
   - 函数体**很小**（几行）。
   - 需要**非局部返回**或 **`reified`**。
   - 标准库里的 `let` / `apply` / `also` / `run` / `with` / `takeIf` 都是这个模式。
5. **面试话术**："`inline` 是**零成本抽象**的手段——用编译期代码膨胀换取运行时零分配。代价是包体积增大，所以我只对'小函数 + 单次调用 + 需要非局部返回'的场景使用。"

---

**读者问：既然有 `inline` 了，为什么还需要 `noinline` 和 `crossinline`？**

**AI答：**

1. **`inline` 附带了三个"特权"**：
   - 参数被内联（不再作为函数对象存在）。
   - lambda 里的 `return` 是**非局部返回**（直接返回外层函数）。
   - lambda 里的 `break` / `continue` 会跳转出内联函数。
2. **`noinline` 的作用**：**关掉第 1 条**——参数不再内联，编译成真正的函数对象。
   - **什么时候需要**：
     - 需要把函数对象**作为值传递**给另一个函数（`executor.submit { block() }`）。
     - 需要在**多个地方引用同一个 lambda 对象**（要求对象身份，如 `===` 比较）。
     - 需要**禁止非局部返回**（把 `return` 限制在当前函数内）。
3. **`crossinline` 的作用**：**关掉第 2 条**——lambda 仍然被内联（省对象），但**禁止非局部返回**。
   - **什么时候需要**：lambda 会被放在**循环或多个调用点**里，此时非局部返回的语义变得歧义（返回到哪个外层？），必须禁止。
   - 标准库例子：`Iterable.forEach(crossinline action: (T) -> Unit)`、`Iterable.any(crossinline predicate)`。
4. **对比记忆**：

| 修饰符 | 是否内联 | 允许非局部 return | 适用 |
| --- | --- | --- | --- |
| 无 | ✅ | ✅ | 简单、调用一次的 lambda |
| `noinline` | ❌ | ❌ | 需要当值传递 |
| `crossinline` | ✅ | ❌ | 循环/多调用点 |

5. **面试话术**："`inline` 的三个特权是打包给的，`noinline` 收回第一个（当值传递），`crossinline` 收回第二个（禁止非局部返回）。本质上，`noinline` 是'我需要这个函数对象'，`crossinline` 是'我要优化但不想让 return 乱跳'。"

---

**读者问：为什么 Kotlin 需要 `reified`？Java 有类似的东西吗？**

**AI答：**

1. **根因：类型擦除（Type Erasasure）**。JVM 的泛型是**编译期特性**（为了向后兼容 Java 5 之前的字节码），编译器把 `List<String>` 编译成 `List`，`String` 只存在于 `Signature` 属性中，运行时完全看不到。
2. **后果**：运行时需要类型信息的操作全部不可用：

```java
// Java 中都编译不过
if (x instanceof T) { }        // 编译错误
T[] arr = new T[10];           // 编译错误
T.class                        // 编译错误
```

3. **Kotlin 的解法：`reified`**：
   - `inline fun <reified T> foo()`：编译器在**每个调用点**生成一份特化代码，把 `T` 替换成实际类型。
   - `T::class.java` → 调用点变成 `String.class.java`。
   - `x is T` → 调用点变成 `x is String`。
4. **Java 的对应物**：
   - **没有** `reified`。Java 的替代方案是**显式传入 `Class` 对象**：

```java
// Java 的做法：手动传 Class
public static <T> T fromJson(String json, Class<T> type) {
    return gson.fromJson(json, type);
}
```

   - Java 16+ 的 **Pattern Matching for instanceof** 解决了 `instanceof` 问题，但仍未解决 `new T[]` 和 `T.class`。
5. **Kotlin 的对应物**：

```kotlin
// Kotlin 的做法：reified
inline fun <reified T> fromJson(json: String): T = gson.fromJson(json, T::class.java)
// 调用：fromJson<User>(json)
```

6. **限制**：
   - 必须 `inline`。
   - 不能是**成员函数**（只允许顶层函数和扩展函数，因为它们编译为静态方法）。
   - 不能和 `vararg` 同时使用。
7. **Android 中的实战**：
   - `Bundle.getParcelableExtra(name, T::class.java)`（API 33+）。
   - `Intent.getSerializableExtra(name, T::class.java)`。
   - Gson / Moshi 的泛型解析封装。
   - Room 的 `@TypeConverter` 泛型辅助。
8. **面试话术**："`reified` 是 Kotlin 对 JVM 类型擦除的补丁。它要求 `inline`，因为编译器必须在调用点特化出具体类型；Java 只能让你显式传 `Class<T>`，本质上是一回事。"

**读者问：扩展函数的原理是什么？为什么它不能重写成员函数？**

**AI答：**

1. **编译产物**：扩展函数编译成**顶层静态方法**，接收者变成第一个参数，文件被编译成 `文件名Kt` 类。

```kotlin
fun String.isEmptyOrNull() = isEmpty() || this == null
// 编译后：
public static boolean isEmptyOrNull(String $this) { ... }
```

2. **为什么不能重写成员函数**：
   - 扩展是**静态派发**（编译期根据静态类型确定调用目标），成员函数是**动态派发**（运行时根据实际类型 vtable 查找）。
   - 如果允许扩展重写成员，静态派发就无法在编译期确定该调谁，语义会混乱。
   - 所以 Kotlin 的规则是：**成员永远优先**。写了一个与成员同名的扩展，编译器会报 **"Extension is shadowed by a member"**（警告或错误，取决于 Kotlin 版本）。
3. **派发是静态的**——重要推论：

```kotlin
open class Base { open fun f() = "Base.f" }
class Derived : Base() { override fun f() = "Derived.f" }

fun Base.ext() = "Base.ext"
fun Derived.ext() = "Derived.ext"

val b: Base = Derived()
b.ext()    // ✅ 调 Base.ext（静态类型决定），不是 Derived.ext
```

   → 扩展函数**不能实现多态**。要多态请用成员函数或接口。

4. **扩展 vs 成员的优先级**：

```text
成员函数  >  扩展函数（按最具体静态类型匹配）  >  泛型扩展  >  扩展属性  >  成员属性
```

5. **扩展函数的限制**：
   - 不能有 `override`。
   - 不能是 `open`（也没有多态）。
   - 扩展属性**没有 backing field**。
   - 成员扩展函数**不会自动导入**，需要显式 `import`。
6. **面试话术**："扩展函数就是**语法糖版的静态方法**。它的好处是能在不修改原类、不用继承的前提下给第三方类加方法；代价是**静态派发**，没有多态能力，且**永远让位于成员函数**。"

**读者问：成员扩展函数是什么？为什么它需要显式 import？**

**AI答：**

1. **定义**：定义在**类内部**、但接收者是**另一个类型**的函数。

```kotlin
class Html {
    fun render(block: StringBuilder.() -> Unit): String {
        val sb = StringBuilder()
        sb.block()
        return sb.toString()
    }
}

// StringBuilder 的成员扩展
fun StringBuilder.buildHtml(): String {
    append("<h1>"); append(this); append("</h1>")
    return toString()
}
```

2. **本质**：它编译成 `Html` 类的**成员静态方法**（接收者仍是第一个参数），但因为定义在类里，可以访问该类的 `private` 成员和 `this`（外部类实例）。

3. **为什么需要显式 import**：
   - 成员扩展**不在文件/包的作用域内自动可见**，必须 `import 包名.外部类.成员扩展名`。
   - 原因：它会**污染外部类的命名空间**——如果自动可见，任何 `StringBuilder` 变量都会突然多出一堆方法，造成歧义和阅读干扰。
4. **关键特性**：

| 特性 | 说明 |
| --- | --- |
| **有 `this`** | 内部 `this` = 外部类实例；`this@Html` 可显式访问 |
| **静态派发** | 编译为成员静态方法，**不能被继承/重写** |
| **派发基于静态类型** | `val b: Base = Derived(); b.memberExt()` 调的是 `Base` 的实现 |
| **可访问 private** | 因为本质在类内部 |

5. **典型用途**：
   - **Builder 模式**：`fun Builder.withXxx()` 链式配置。
   - **Compose 的 `ColumnScope` / `RowScope`**：这就是**成员扩展**的经典应用——`Column { Text(...) }` 里的 `Text` 之所以能拿到 `ColumnScope` 的权重，是因为 `ColumnScope` 的成员扩展被隐式导入了。
   - **DSL 的作用域**：`StringBuilder.() -> Unit` 形式的带接收者 lambda。

6. **面试话术**："成员扩展是**定义在类里、作用于外部类型**的函数，它编译成类的成员静态方法，能访问外部类的 `this` 和 private 成员。Compose 的 `ColumnScope` 就是典型例子。它必须显式 import，是为了避免给外部类型'无端增加'一堆可能造成歧义的方法。"

**读者问：`let`、`apply`、`run`、`with`、`also` 有什么区别？怎么选？**

**AI答：**

1. **三个维度决定行为**：

| 函数 | 接收者引用 | 返回值 |
| --- | --- | --- |
| `let` | `it` | lambda 结果 |
| `run` | `it` | lambda 结果 |
| `apply` | `this` | 接收者本身 |
| `with` | `this` | lambda 结果 |
| `also` | `it` | 接收者本身 |

2. **记忆口诀**：
   - **"返回值看谁"**：`let` / `run` / `with` 返回 **lambda 结果**；`apply` / `also` 返回 **接收者本身**。
   - **"this 还是 it"**：`apply` / `with` 用 `this`（把对象当上下文）；`let` / `run` / `also` 用 `it`（把对象当参数）。
3. **选型决策树**：

```text
要判空后使用？        → let 或 run（this?.let{} / this?.run{}）
要配置对象并返回对象？  → apply
要计算出一个新值？     → run（用 this 访问多个成员）或 let（只需一个值）
要连续操作同一对象？   → with
要在链中插入副作用？    → also
```

4. **代码示例对比**：

```kotlin
val name: String? = "Kotlin"

// let：安全取值 + 计算结果
val length = name?.let { it.length }                       // 6

// run：安全取值 + 多个成员访问
val upper = name?.run { uppercase() }                       // "KOTLIN"

// apply：配置对象
val view = TextView(ctx).apply {
    text = "hi"
    setTextColor(Color.RED)
}                                                          // 返回 TextView

// with：连续操作
with(view) {
    text = "hi"
    visibility = View.VISIBLE
}                                                          // 返回 Unit（最后一个表达式）

// also：链式副作用
val result = compute()
    .also { Log.d(TAG, "结果 $it") }
    .map { it * 2 }
```

5. **`with` 的一个坑**：它**不能用于可空对象**（`with(nullable) {}` 编译不过），需要 `with(nullable!!)` 或 `with(nullable ?: return)`。
6. **性能差异**：全部是 `inline` 函数，**零额外对象分配**，性能一致，可以放心使用。
7. **面试话术**："我按两个维度选：**返回值**和**接收者的引用方式**。要新值用 `let`/`run`；要对象本身用 `apply`/`also`；要 `this` 上下文用 `apply`/`with`；要 `it` 参数用 `let`/`run`/`also`。链式配置我几乎总是 `apply`，链式打日志用 `also`。"

**读者问：`Flow` 的操作符为什么用 `inline`？操作符链会不会有性能问题？**

**AI答：**

1. **为什么用 inline**：
   - Flow 的操作符**几乎全部是 inline**（`map`、`filter`、`flowOn`、`catch` 等）。
   - 原因一：**消除函数对象**。`flow.map { ... }` 如果不 inline，每次调用都会创建 `Function1` 对象，在链式操作中会累积。
   - 原因二：**需要非局部返回**（`return@map` 或直接 `return`）以及访问 `internal` 成员（`SafeCollector`、`FlowCollector`）。
   - 原因三：**Flow 的编译器插件（`inline` + `crossinline` 组合）**能对 Flow 链做优化。
2. **性能结论**：
   - **inline 本身不是运行时优化**（运行时两者几乎一样），真正的收益是**少分配对象**。
   - Flow 链的**主要开销**在两处：
     1. **上下文切换**（`flowOn` 用 Channel 切换线程，有一次线程切换成本）。
     2. **装箱**（泛型 `T` 在 JVM 上是 `Object`，`Int` 会装箱成 `Integer`）。
3. **Flow 特有的优化点**：

```kotlin
// ❌ 装箱：Flow<Int> 在 JVM 上是 Flow<Integer>
val flow: Flow<Int> = flowOf(1, 2, 3)

// ✅ 避免装箱：使用 @JvmInline value class 或专门的特化类型
// kotlinx.coroutines 提供了 Flow 的特化：Flow<Int> 内部使用 int 槽位优化
```

4. **`flowOn` 的成本**：每次 `flowOn` 都会创建一个 `Channel` 和一次调度。**链上多个 `flowOn` 会被合并**（只有最靠近源的那个生效），所以不必担心。
5. **面试话术**："Flow 操作符用 inline 主要是为了**零分配**和**允许非局部返回**。Flow 链真正的性能成本不在 inline，而在**上下文切换**和**装箱**，所以我在链上尽量少用 `flowOn`，并且用 `asSequence()` 处理纯 CPU 的集合转换。"

**读者问：Kotlin 的委托（Delegation）和 Java 的继承有什么区别？**

**AI答：**

1. **范式差异**：
   - Java：**继承**（is-a），子类依赖父类的实现与状态。
   - Kotlin：**委托**（has-a），把接口的实现转交给另一个对象。
2. **Kotlin 的三种委托**：

```kotlin
// ① 接口委托（class delegation）
interface Base { fun f() }
class Impl : Base { override fun f() = "impl" }
class Wrapper(b: Base) : Base by b      // ✅ 全部方法自动转发

// ② 属性委托（property delegation）
class User {
    var name: String by Delegates.observable("") { _, _, new -> println(new) }
    val config: Config by lazy { loadConfig() }
}

// ③ 局部委托
var counter = 0
val counterDelegate = object : IntProperty { ... }
```

3. **相对继承的优势**：
   - **运行时组合优于编译期继承**：可以在运行时决定委托对象。
   - **避免继承耦合**：委托对象的实现变化不影响委托方。
   - **接口委托支持"混入多个实现"**：一个类可以 `by` 多个不同接口的实例，组合出多重继承的效果。
4. **Kotlin 没有"类委托"语法**（Java 有 `class A extends B` 的类委托形态），Kotlin 的 `by` **只能委托接口**——这是刻意的设计：限制继承深度。
5. **Android 中的应用**：
   - `RecyclerView.Adapter` 的基类委托。
   - `by viewModels()` / `by activityViewModels()`：ViewModel 的属性委托。
   - `by lazy { }`：延迟初始化。
   - `by viewBinding()`：ViewBinding 委托（内部用反射 + 缓存 + 生命周期清理）。
6. **面试话术**："Kotlin 更推荐**组合优于继承**。接口委托让我不用写一堆'纯转发'的样板方法，属性委托把'延迟初始化''观察变化''作用域共享'这些横切逻辑从业务代码里抽出来。Android 里 `by viewModels()` 就是典型——一行代码拿到正确作用域的 ViewModel。"

**读者问：Sequence 和 List 有什么区别？什么时候用 Sequence？**

**AI答：**

1. **核心区别：求值策略**。

| | List | Sequence |
| --- | --- | --- |
| 求值 | **立即（Eager）** | **惰性（Lazy）** |
| 中间集合 | 每个操作产生一个新 List | 不产生中间集合 |
| 短路 | `first`/`take` 仍会算完前面的 | **提前终止**，后面的不执行 |
| 遍历次数 | 可反复遍历 | **只能消费一次**（`iterator()` 受限） |
| 操作符 | `Iterable` 扩展 | `Sequence` 扩展（名字大多相同） |

2. **性能对比**：

```kotlin
val list = (1..1_000_000).toList()

// Eager：map 和 filter 都要跑 100 万次
val a = list.map { it * 2 }.filter { it > 100 }.first()

// Lazy：遇到第一个满足条件的就停，可能只算几十次
val b = list.asSequence().map { it * 2 }.filter { it > 100 }.first()
```

3. **什么时候用 Sequence**：
   - 数据量大（几千到几十万）。
   - 链式操作多（每个操作省一次集合分配 → 减少 GC 压力）。
   - 有**短路**需求（`first`、`take`、`any`）。
   - **纯内存数据**，不需要 `List` 的随机访问能力。
4. **什么时候用 List**：
   - 数据量小（几百条以内）。
   - 需要**多次遍历**或**随机访问**。
   - 需要传给只接受 `List` 的 API。
5. **注意**：Android 的 `LiveData` / `Flow` 转换里常用 `asSequence()` 做多步转换；Room 的 `Flow<List<T>>` 也常用 `asSequence().map{}.toList()` 减少中间分配。
6. **面试话术**："`Sequence` 是**惰性求值**的管道：每个元素'流过'整条链时才计算，中间不落集合。数据量大 + 链式操作 + 有短路时用 `Sequence`；需要多次遍历或随机访问时用 `List`。"

**读者问：Kotlin 的操作符重载有限制吗？为什么 `+=` 有两种写法？**

**AI答：**

1. **可重载的运算符是封闭列表**，只有约 30 个，且大部分需要 `operator` 修饰符。
2. **核心限制**：

| 限制 | 说明 |
| --- | --- |
| **不能重载 `+` 为 `+=`** | `plus` 和 `plusAssign` **必须同时存在**才能用 `+=`；如果两者都定义了，`a += b` 会**优先调用 `plusAssign`**（原地修改），而不是 `plus` + 赋值 |
| **不能定义 `equals` 为扩展** | `==` 只能通过重写 `equals` 实现 |
| **`compareTo` 决定 `>` `<`** | 重写后 `<` `>` `<=` `>=` 都可用 |
| **不能重载 `new`** | 用 `invoke` 操作符代替 |
| **`in` 需要 `contains`** | `!in` 自动取反 |
| **重载不能改变优先级** | Kotlin 明确规定了操作符优先级，**不能像 C++ 那样自定义** |

3. **`plus` vs `plusAssign` 的选择**：

```kotlin
data class MutableList(val items: MutableList<Int> = mutableListOf()) {
    operator fun plus(other: MutableList): MutableList = MutableList(items + other.items)  // 返回新对象
    operator fun plusAssign(other: MutableList) { items.addAll(other.items) }                // 原地修改
}
```

   - **规则**：如果 `plusAssign` **存在**，`a += b` 用 `plusAssign`；否则用 `a = a.plus(b)`。
   - **陷阱**：两者都定义时行为会变化，且 `plusAssign` 可能**修改了原对象**（导致 `val` 的"不可变性"错觉）。**Kotlin 官方建议：优先只定义 `plus`，不要同时定义 `plusAssign`**（除非确实需要原地修改的性能收益）。
4. **`getValue` / `setValue` 操作符**是委托的基础：

```kotlin
operator fun <T> Preference.getValue(thisRef: Any?, property: KProperty<*>): T
operator fun <T> Preference.setValue(thisRef: Any?, property: KProperty<*>, value: T)
```

5. **面试话术**："Kotlin 的操作符重载是**受限但类型安全**的：只有固定的一批名字，且必须显式 `operator`。一个常见坑是同时定义 `plus` 和 `plusAssign`——`+=` 会优先走 `plusAssign`，可能意外地原地修改了对象。"

**读者问：Kotlin 的函数类型（`(Int) -> String`）在 JVM 上是什么？为什么能这样？**

**AI答：**

1. **JVM 映射**：

```text
Kotlin 函数类型                JVM 实际类型
──────────────────────       ──────────────────────────────────────
() -> Unit                  →  Function0<Unit>
(Int) -> String             →  Function1<? super Integer, ? extends String>
(Int, Int) -> Int           →  Function2<...>
(String) -> Unit            →  Function1<? super String, Unit>
```

   → 函数类型在 JVM 上是 **`kotlin.jvm.functions.FunctionN`** 的**接口实例**，不是 `invokedynamic`（`invokedynamic` 只用于**编译 lambda 字面量**时的实现细节）。

2. **为什么 Java 能把 Kotlin 函数类型当 SAM 用**：

```kotlin
val f: (Int) -> Int = { it * 2 }
```

```java
// Java 侧：Function1 本身是 Java 的函数式接口（只有一个抽象方法 invoke）
Function1<Integer, Integer> f = x -> x * 2;   // ✅ Java 可以用 lambda
```

   → 因为 `Function1` 定义在 Kotlin 里但编译成 **Java 可见的接口**，Java 编译器把它当成普通函数式接口处理。

3. **装箱问题**：

```text
(Int) -> Int  →  Function1<Integer, Integer>   ← 泛型只能是引用类型
                →  调用时 int 会被【装箱】成 Integer
```

   → Kotlin 对**函数类型的参数和返回值**不做基本类型特化。涉及大量基本类型的场景要留意装箱开销。
   → （对比：Kotlin 的 `Flow<Int>` 有专门的特化优化 `FlowCollector` 内部使用 int 槽位。）

4. **FunctionN 的变型（variance）**：

```kotlin
public interface Function1<in P1, out R> {
    public fun invoke(p1: P1): R
}
```

   - **`P1` 是 `in`（逆变）**：函数**接收** P1 → 允许 `Function1<Any, R>` 用在需要 `Function1<String, R>` 的地方。
   - **`R` 是 `out`（协变）**：函数**返回** R → 允许 `Function1<P, String>` 用在需要 `Function1<P, Any>` 的地方。
   - **这个设计是安全的**：接收更宽的类型 + 返回更窄的类型，永远是安全的。

5. **变型的实际应用**：

```kotlin
// ✅ 一个"接收任意 Number 的函数"可以赋给"接收 Int 的函数"
val anyNumber: (Number) -> String = { it.toString() }
val intOnly: (Int) -> String = anyNumber      // ✅ 合法（逆变）

// ❌ 反过来不合法
val intOnly: (Int) -> String = { it.toString() }
val anyNumber: (Number) -> String = intOnly   // ❌ 编译错误
```

6. **函数引用 vs lambda**：

```kotlin
val f1: (Int) -> Int = { it * 2 }        // lambda 字面量
val f2: (Int) -> Int = ::doubleIt         // 函数引用（可调用对象的引用）
val f3: (Int) -> Int = Integer::toDouble  // 绑定的可调用引用
```

   - **函数引用**是**对象的引用**，可以传递、比较（`===`）、存起来。
   - **lambda 字面量**每次求值可能创建新对象（除非被 inline 优化掉）。
   - **重要区别**：函数引用**不会**被 inline 优化掉（它是一个已存在的对象）；lambda 字面量作为 inline 参数时会被内联。

7. **面试话术**："Kotlin 的函数类型在 JVM 上是 `kotlin.jvm.functions.FunctionN` 接口实例，`Function1<in P1, out R>` —— 参数逆变、返回值协变。Java 把它当普通函数式接口用。需要注意**基本类型会装箱**（`(Int) -> Int` 底层是 `Function1<Integer, Integer>`）。另外**函数引用是对象**（可传递、可比较、不会被 inline 掉），而 lambda 字面量在被 inline 时会被展开。"

**读者问：Kotlin 的 `let`、`apply` 这些作用域函数有性能问题吗？为什么标准库全都用 `inline`？**

**AI答：**

1. **结论：没有性能问题，可以放心使用**。原因是它们**全部是 `inline` 函数**。

```kotlin
public inline fun <T> T.apply(block: T.() -> Unit): T {
    contract { callsInPlace(block, InvocationKind.EXACTLY_ONCE) }
    block(this)
    return this
}
```

   → `inline` 让编译器把函数体**展开到调用点**，**不创建 lambda 对象、不创建函数对象** → **零额外分配**。

2. **如果不 inline 会怎样**：

```text
非 inline 的 apply：
  每次调用 → 创建 1 个 Function1 对象（捕获 receiver）
  → 100 万次调用 = 100 万次堆分配 → GC 压力显著

inline 的 apply：
  每次调用 → 0 次分配（代码直接展开）
  → 编译器甚至能做【逃逸分析】和【常量折叠】
```

3. **`contract { callsInPlace(...) }` 的作用**（Kotlin 1.3+ 的编译期契约）：

```kotlin
contract { callsInPlace(block, InvocationKind.EXACTLY_ONCE) }
```

   - 告诉编译器"这个 lambda 会被【恰好一次】地调用" → 编译器可以做**智能转换（smart cast）**：

```kotlin
val x: String? = getString()
x?.let {
    // ✅ 在这里 x 被智能转换成非空 String
    println(x.length)      // 编译通过
}
```

   - 没有 contract 时编译器不知道 lambda 何时执行，无法做智能转换。

4. **`inline` 带来的三个额外能力**（这些是它们被 inline 的真正原因）：
   - **非局部返回**：`let { if (it == null) return }` 能直接返回外层函数。
   - **访问 internal 成员**：inline 函数体被展开到调用方模块，可以访问 `internal` 声明。
   - **避免函数对象分配**：性能。

5. **什么时候**不该**用 `inline`**：

```text
❌ 函数体很大 → 每个调用点都展开一份 → 代码膨胀（DEX 变大）
❌ lambda 参数被多次调用 → 内联后代码重复
❌ 需要把 lambda 当对象传出去 → 必须 noinline
❌ 需要在 lambda 里做非局部返回但不希望如此 → crossinline
```

   → 标准库的策略是：**只对"极小 + 只调用一次"的函数 inline**（`let`/`apply`/`also`/`run`/`with`/`takeIf` 都是 1-3 行）。

6. **一个常被误解的点**：

```kotlin
// ❌ 很多人以为这里有性能问题
list.map { it * 2 }.filter { it > 4 }

// ✅ map/filter 也是 inline 的（kotlin.collections 里的）→ 零分配
//    真正开销在【遍历本身】和【集合的分配】，不在 lambda
```

7. **面试话术**："作用域函数**没有性能问题**，因为标准库把它们全部定义成了 `inline`——函数体展开到调用点，lambda 和函数对象都不分配。加上 `contract { callsInPlace }` 还能让编译器做智能转换。反过来说，`inline` 有代价：代码膨胀、只能用于 public/internal、不能有非局部返回，所以标准库只对极小的函数用。"

**读者问：`lateinit var` 和 `by lazy {}` 有什么区别？什么时候用哪个？**

**AI答：**

1. **核心区别**：

| 维度 | `lateinit var` | `by lazy { }` |
| --- | --- | --- |
| **类型要求** | ❌ **只能是非空类型**（`lateinit var name: String`） | ✅ 任意类型（含可空） |
| **能否用 `?`** | ❌ 不能（`lateinit var name: String?` 编译错误） | ✅ 可以 |
| **初始化位置** | **任意**（通常在 `onCreate` / `init` 块） | **声明处**（`lazy` 块） |
| **检查时机** | **访问时**抛 `UninitializedPropertyAccessException` | 访问时**初始化**（若无参则永不初始化） |
| **`isInitialized`** | ✅ **有这个属性** | ❌ 没有 |
| **线程安全** | ❌ 不保证（赋值与读取可能竞态） | ✅ **默认 `SYNCHRONIZED`**（线程安全） |
| **能否重新赋值** | ✅ 可以（多次赋值） | ❌ **只初始化一次**（`lazy` 缓存结果） |

2. **`lateinit` 的底层原理**：

```kotlin
// 编译后：lateinit 属性 + 一个 isInitialized 标记
private lateinit var name: String
// 访问时：
if (!name$delegate.isInitialized()) throw UninitializedPropertyAccessException(...)
```

   - Kotlin 用一个 **`$delegate` 对象**记录初始化状态。
   - **`lateinit` 只对非空类型有效**，因为编译器需要在字段里放 `null` 作为"未初始化"标记 → 非空类型的字段默认不能为 `null`，Kotlin 用 `$delegate` 绕过。

3. **`by lazy` 的三种模式**：

```kotlin
private val a by lazy { expensive() }                              // 默认 SYNCHRONIZED（线程安全）
private val b by lazy(LazyThreadSafetyMode.NONE) { expensive() }    // 无锁（单线程，最快）
private val c by lazy(LazyThreadSafetyMode.PUBLICATION) { e() }     // 可能多次初始化
```

4. **`lazy` 的性能细节**（**面试加分点**）：

```kotlin
private class SynchronizedLazyImpl<out T>(initializer: () -> T) : Lazy<T> {
    private var initializer: (() -> T)? = initializer
    @Volatile private var _value: Any? = UNINITIALIZED_VALUE

    override val value: T
        get() {
            val v = _value
            if (v !== UNINITIALIZED_VALUE) {
                @Suppress("UNCHECKED_CAST") return v as T     // ① 已初始化 → 直接返回（无锁！）
            }
            return synchronized(this) {                       // ② 双重检查 + 锁
                val v = _value
                if (v === UNINITIALIZED_VALUE) {
                    _value = initializer!!.invoke()
                }
                v as T
            }
        }
}
```

   - **关键**：`_value` 是 **`@Volatile`**，第一次初始化后**读路径完全无锁**（只有 volatile 读的开销）。
   - **双重检查锁定（Double-Checked Locking）**的标准实现。

5. **选型决策**：

```text
需要非空类型 + 必须在某处（onCreate）赋值 + 可能重新赋值
  → lateinit var

需要非空类型 + 声明处就能确定初始化逻辑 + 只初始化一次 + 多线程可能访问
  → by lazy { }

需要可空类型
  → by lazy { }（lateinit 做不到）

需要线程安全
  → by lazy { }（默认模式）

Android 里的典型：
  → lateinit var binding: ActivityMainBinding      // 在 onCreate 里 inflate
  → private val repo by lazy { UserRepository() }    // 首次使用时创建
```

6. **`lateinit` 的常见坑**：

```kotlin
// ❌ 坑 1：忘记赋值就访问 → 运行时崩溃（UninitializedPropertyAccessException）
lateinit var name: String
fun get() = name.length        // 💥

// ❌ 坑 2： lateinit 不能用于基本类型
lateinit var count: Int          // ❌ 编译错误：基本类型不需要初始化检查

// ❌ 坑 3： 不能用于 nullable 类型
lateinit var name: String?       // ❌ 编译错误

// ❌ 坑 4： 不能用于局部变量（只支持成员属性和顶层属性）
// ❌ 坑 5： 不能有自定义 getter
```

7. **面试话术**："两者都是延迟初始化，但 `lateinit` **只能用于非空成员属性**，用 `$delegate` 记录初始化状态，有 `isInitialized` 可以检查，**允许重新赋值**；`by lazy` **支持任意类型**，声明处初始化，**只初始化一次**，默认是**线程安全**的（`SYNCHRONIZED` 模式，底层是 `@Volatile` + 双重检查锁，初始化后读路径完全无锁）。Android 里典型用法是 `lateinit var binding`（onCreate 里赋值）和 `private val repo by lazy { }`（首次使用创建）。"

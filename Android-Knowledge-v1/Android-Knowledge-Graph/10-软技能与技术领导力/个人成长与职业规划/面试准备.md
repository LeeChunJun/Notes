# 面试准备

## 一句话定义

面试准备不是"把八股背完"，而是**把散落在项目里的经验，翻译成面试官能听懂、能验证、且能证明你判断力的语言**——知识储备决定你的下限，**表达的清晰度与真实感决定你的上限**。

## 核心原理

### 1. 面试官到底在考什么

面试官在 30-60 分钟里要判断的是**四件事**，而不是你记住了多少 API：

```text
┌──────────────────────────────────────────────────────┐
│  1. 深度   —— 这个知识点你懂不懂原理，还是只会用        │
│     问："Handler 消息机制底层是怎么调度消息的？"        │
├──────────────────────────────────────────────────────┤
│  2. 广度   —— 你的知识面能不能覆盖岗位要求              │
│     问："Compose 和传统 View 体系你都能讲讲吗？"        │
├──────────────────────────────────────────────────────┤
│  3. Ownership —— 你对自己写的东西负责到什么程度          │
│     问："这个方案你为什么这么选？当时考虑过什么？"      │
├──────────────────────────────────────────────────────┤
│  4. 成长性 —— 你的能力上限在哪，学习能力如何            │
│     问："你没做过的部分，你打算怎么上手？"             │
└──────────────────────────────────────────────────────┘
```

**关键推论**：

- **能背出来 ≠ 能答好**。背出来的答案听感像"背书"，能讲原理的答案听感像"做过"。
- **深度比广度重要**。广度是筛简历的门槛，深度是拿 offer 的关键。
- **Ownership 是分水岭**。"我们团队做了 X"（无主体）与"我负责 X，做了 Y，遇到 Z，最终 W"（有主体）的差别，面试官一听就知道。

### 2. 面试的四类问题与应对

| 类型 | 典型问题 | 考察 | 应对策略 |
| --- | --- | --- | --- |
| **知识原理题** | "讲讲 Activity 启动流程" | 深度 | **分层回答**：先给主干流程，再主动展开细节 |
| **场景设计题** | "设计一个图片加载库" | 综合 | **先澄清需求**，再给分层方案，最后给取舍 |
| **项目深挖题** | "你简历上这个启动优化具体怎么做的？" | Ownership / 真实性 | **讲透一个真实的、有数据、有代价的项目** |
| **行为面试题** | "讲一次你处理技术分歧的经历" | 软技能 / 团队 | **STAR 法则**，讲具体事件和你的判断 |

**通用原则**：**先给结论，再给论据，最后给细节**。面试官需要 30 秒就知道你懂不懂，才愿意继续听细节。

### 3. 简历项目描述：STAR + 量化

**弱描述 vs 强描述**：

```text
❌ 弱
"负责公司核心 App 的开发工作，使用 MVVM 架构，使用 Retrofit + OkHttp
 进行网络请求，使用 Room 做本地存储。"

问题：
- 没有"我"，看不出你的边界
- 没有问题背景
- 没有结果
- 技术栈罗列（谁都能写）
```

```text
✅ 强
"【背景】App 冷启动 P90 2.1s，低于行业 1.5s 的预期，直接影响新用户次日留存。
 【方案】我对比了全异步化、惰性加载、按优先级调度三种方案，
        评估维度是首屏可用时间、SDK 兼容性和改造成本，
        最终选择按优先级调度的启动任务框架（任务依赖用 DAG 描述，构建期校验无环）。
 【实现】我设计并实现了任务调度器 + 构建期依赖校验，
        把三方 SDK 初始化改成可延迟，并接入 App Startup。
 【结果】冷启动 P90 降到 1.05s，启动期崩溃率从 0.8% 降到 0.15%，
        新用户次日留存提升 2.3%。
 【代价】构建期多了 8s（我们用 CI 分级缓存缓解），
        并且因为初始化时序调整，下线了一个依赖早期初始化的实验功能。"
```

**量化维度清单**（找到适合你项目的）：

| 类别 | 指标 |
| --- | --- |
| **性能** | 启动耗时（P50/P90）、包体积（MB / 占比）、内存峰值、帧率、掉帧率、首屏时间 |
| **稳定性** | 崩溃率（分版本/机型）、ANR 率、线上事故数 |
| **效率** | 需求交付周期、构建时长、CI 通过率、代码重复率、测试覆盖率 |
| **规模** | DAU、模块数、接入方数、代码行数、协作者人数 |
| **业务** | 转化率、留存、GMV、客单价（间接） |
| **质量** | Review 一次通过率、返工率、线上缺陷数 |

**注意**：**"负责"不如"主导"**，但**不要夸大**。面试官会追问细节，虚夸一次就全盘崩塌。**只写你真的做过、且能扛住 3 层追问的事。**

### 5. 手写题清单

**面试官要求手写时，考的不是"能不能编译"，而是"**你是否理解这个 API 的行为边界**"。**

| 题目 | 考察点 | 关键点 |
| --- | --- | --- |
| **单例（线程安全）** | 静态分析、双检锁 | 为什么要 `volatile`（禁止指令重排） |
| **线程池** | 7 参数、拒绝策略 | 为什么不推荐 `Executors`（无界队列 OOM） |
| **LruCache** | LinkedHashMap + 内存计算 | 为什么用 `LinkedHashMap` 的 accessOrder |
| **Handler 消息机制** | Looper/MessageQueue | 同步屏障、Message.target 的作用 |
| **Binder 代理** | Proxy/Stub | `transact` → `onTransact` → `Stub.Proxy` |
| **Compose 状态容器** | `remember`/`mutableStateOf` | 重组范围、`derivedStateOf` |
| **协程调度** | `CoroutineScope` + `Dispatcher` | 结构化并发、取消 |
| **生产者消费者** | `BlockingQueue`/`Channel` | 有界 vs 无界、`Channel` 的关闭语义 |
| **单例持有 Context 的泄漏** | 场景分析 | 生命周期不匹配 |
| **String 转数字** | 边界处理 | 溢出、空串、非法字符 |
| **LRU + 手写链表** | 数据结构 | 常考 |
| **防抖节流** | 时间窗口 | 面试官爱问实际场景 |

**手写题的答题模板**：

```text
① 先说思路（30 秒）
② 写核心代码
③ 说边界情况（空、并发、越界、异常）
④ 说真实项目里我会怎么用
```

**第 ③ 步是最加分的地方**——它证明你知道这个 API 在什么情况下会出问题。

### 6. 系统设计题（Android 方向）

**准备 4 个能讲透的设计题**，每个按"**需求澄清 → 分层方案 → 关键实现 → 取舍 → 优化方向**"讲：

| 题目 | 核心考察点 |
| --- | --- |
| **设计一个图片加载库** | 缓存分层（内存/磁盘）、内存计算、生命周期绑定、并发去重、LRU 淘汰 |
| **设计一个埋点 SDK** | 事件采集、批量上报、失败重试、离线存储、隐私合规、无侵入接入 |
| **设计一个 IM 框架** | 长连接、心跳、消息可靠性（ACK/重传）、离线推送、多端同步 |
| **设计一个组件化路由** | 路由表生成（APT）、参数传递、拦截（登录/维护）、降级 |
| **设计一个启动优化框架** | 任务 DAG、依赖校验、并发控制、失败降级、耗时监控 |

**通用答题框架**：

```text
① 需求澄清（2 分钟）
   "这个库的使用者是谁？规模多大？有没有性能/体积约束？"
   —— 澄清本身就是加分项

② 分层方案（3 分钟）
   画出模块划分与数据流

③ 关键实现（5 分钟）
   只讲 1-2 个最核心的点，讲透，其余一句带过
   —— 不要面面俱到，面试官会打断

④ 取舍与边界（3 分钟）
   "这个方案在什么情况下不适用？"

⑤ 优化方向（1 分钟）
   "如果规模再涨 10 倍，我会先优化 XXX"
```

**关键**：**不要试图讲完所有细节。** 讲完一个"核心实现"后主动停下来问"这块要不要展开？"，能控制节奏。

### 7. 行为面试题（STAR 法则）

**STAR**：

```text
S Situation  背景——当时的处境、约束
T Task        任务——你要解决什么，你的责任边界
A Action      行动——你具体做了什么（重点，占 60%）
R Result      结果——量化结果 + 后续影响 + 学到什么
```

**准备 5-6 个能反复复用的"故事"**，覆盖不同场景：

| 故事类型 | 覆盖的问题 |
| --- | --- |
| **技术攻坚** | 讲一次你解决了什么棘手问题 |
| **技术决策** | 讲一次你做了有争议的技术选型 |
| **失败复盘** | 讲一次你没做好并改进的经历 |
| **冲突处理** | 讲一次你和同事/上级有分歧并解决 |
| **带人/影响他人** | 讲一次你让别人的能力提升 |
| **主动担当** | 讲一次没人要求你做的事 |

**行为题答错的典型模式**：

```text
❌ "我们团队做了一次技术改造，效果很好。"
   —— 没有"我"，没有过程，没有数据

❌ "遇到冲突我会先沟通，理解对方的需求，然后找到共同点。"
   —— 空洞，没有具体事件，没有证明你能处理冲突

❌ "我失败了会总结经验教训，下次改进。"
   —— 没有真实失败经历，或者没有具体改进
```

**STAR 的例子（技术攻坚）**：

```text
S："我们的 App 在 Android 8 机型上启动崩溃率有 3%，但其他机型正常，
    总崩溃率只有 0.3%，所以在总看板里完全看不到。"

T："我负责定位这个问题并给出修复方案。"

A："我先按维度拆监控，发现问题只在 8.0-8.1。
    拉堆栈看到是 RuntimeException: Method not found，
    反射调用了 API 29 才有的方法。
    我加了 API level 判断，同时把这个改动同步到了另外两个类似反射调用的地方，
    并在 CI 加了 lint 规则检测反射调用新 API。"

R："8 机型崩溃率降到 0.05%，整体崩溃率从 0.3% 降到 0.12%。
    更重要的是那条 lint 规则后来又拦下了 3 个同类问题。"
```

**这个例子的力量在于**：有具体现象、有排查路径、有**举一反三**（同步改了另外两处）、有**机制化改进**（加 lint 规则）、有量化结果。**这就是资深工程师和"修完这个 bug"的区别。**

### 8. 面试当天的准备

```text
【设备与素材】
☐ 模拟器或真机（能跑 Demo 项目），电充满
☐ 投屏 / 录屏工具（分享代码时投屏效果最好）
☐ IDE 预热：常用工程打开、字体调大、主题调浅色
☐ 显示器缩放 100%，不要在缩放的屏幕上投屏

【网络】
☐ 热点备胎（面试间 WiFi 不稳是常见意外）
☐ 手机热点 + 电脑连，测试一次
☐ 关掉 VPN/代理（防止面试官看不到投屏）

【内容】
☐ 项目 Demo 能跑起来（系统设计题可能要现场演示）
☐ 简历打印一份（纸质，面试时对照）
☐ 简历上的每个数字都能说清楚来源

【形象与表达】
☐ 提前 10 分钟到场，测试摄像头/麦克风
☐ 语速放慢，紧张时容易抢话
☐ 想不清楚就说"我想一下"，然后组织语言
     （沉默比乱说更差，但比胡说要好）
```

**关键细节**：

- **允许说"我不知道"**：但要**给出你会怎么查**。
  - ❌ "这个我不太清楚。"
  - ✅ "这个我不确定。我的理解是……但我记得官方文档里有个相关的说明，我没记准。如果现在要解决，我会先去看 X 文档/用 Y 工具验证。"
- **主动澄清问题**：面试官问了个含糊的问题，先确认："您是想问 A 还是 B？"
- **管理时间**：如果面试官在你讲到一半时打断并转向，别硬拉回来。

## 常见问题 / 面试要点

**读者问：Android 面试应该重点准备哪些内容？时间有限怎么取舍？**

**AI答：**

1. **优先级排序**（基于大厂面试的实际考察频率）：
   - **第一梯队（必须透）**：第 6 部分（系统原理 + 性能优化）、第 2 部分（核心组件）、第 5 部分（Handler 机制）。
     - 这几块是"**不问会怀疑你写过程序员**"的内容。
   - **第二梯队（必须熟）**：第 3 部分（UI 绘制 + Compose）、第 7 部分（MVVM + Hilt）、第 1 部分（协程）。
   - **第三梯队（要有印象）**：第 4 部分（Room/DataStore）、第 8 部分（模块化/CI）。
   - **第四梯队（看岗位）**：第 9 部分（跨平台）、第 10 部分（软技能，Leader 岗必需）。
2. **时间有限时的"保底策略"**：
   - **先保证第一梯队能脱稿讲 3 分钟**，再补充第二梯队。
   - **每个知识点用"一句话 + 三个要点"的形式记**，比完整背书更抗遗忘。
   - **优先准备"能被追问"的**：能讲清原理的知识点，即使忘掉细节也能靠原理推出来；只能背结论的，忘了就完全没了。
3. **最高性价比的投入**：**把你项目里的 3 件事讲透**。
   - 理由：项目经历是面试官唯一能验证你真实性的部分，且几乎每轮都会被追问到细节。
   - **一个讲透的项目 > 十个背熟的知识点**。
4. **不要平均用力**：把 60% 时间花在第一梯队 + 项目打磨上。
5. **面试话术**："如果时间紧我会这么排：先花一周把启动流程、Binder、Handler、渲染机制这四个'原理硬骨头'啃透，因为这几块不问会怀疑你只是 API 调用者；然后花一周把项目里三件事讲到能扛住三层追问；第三周补 MVVM/Hilt/协程这些'高频常规题'；最后一周做模拟面试查漏。"

---

**读者问：简历上的项目怎么写才能加分？**

**AI答：**

1. **三个硬要求**：
   - **有"我"**：写清楚你的责任边界。面试官要判断的是你，不是团队。
   - **有量化**：性能、稳定性、效率、业务，任选其一，但要具体。
   - **有代价**：只讲收益的像宣传稿。**能讲出"这个方案让我们放弃了什么"才可信。**
2. **结构模板（每个项目 4-6 行）**：
   ```text
   【背景 + 问题（含数据）】
   【方案 + 你的决策（为什么选它）】
   【你做的关键实现（2-3 个技术点）】
   【结果（量化前后对比）】
   【代价与缓解】
   ```
3. **技术栈罗列没用**："使用 Retrofit + OkHttp + Room"这类描述谁都能写，且会被追问到细节。**把技术栈写进"实现"里**："用 Retrofit + OkHttp 统一封装了网络层，拦截器里做统一鉴权与日志，通过 Converter 统一错误映射"。
4. **慎用"负责"**：如果确实是主导，用"主导"；如果只是参与，写"参与 <具体模块> 的 <具体工作>"。**用词模糊会被追问，露馅后所有其他内容也会被怀疑。**
5. **只写你扛得住三层追问的事**：
   - 面试官通常会问："为什么这么做？""有没有别的方案？""结果怎么验证的？""有什么坑？"
   - **写进去的每一项都要能答出这四问**，答不出的就从简历上删掉。
6. **排版**：一段一项目，用短句，不要长段落。**面试官平均在简历上花 30-60 秒。**
7. **面试话术**："我改简历时用的标准是——每一条都能被追问三层。写之前我会自己先回答这三个问题：为什么这么做、有没有别的方案、结果怎么测的。答不上来的就不写。另外我刻意写了代价，因为面试官看到只有收益的项目，反而会怀疑是不是真的。"

---

**读者问：面试时遇到不会的题怎么办？硬编还是承认？**

**AI答：**

1. **绝对不要硬编**。追问三层必露馅，而且**一旦被识破，前面所有内容的可信度都会被打折**。
2. **但也不要只说"我不会"**——要给**你的思路**：
   ```text
   ✅ "这块我没有实际处理过。但我的排查思路会是：
       先确认 X，然后看 Y，如果 Y 不成立就往 Z 方向查。
       我记得这块和 A 有关，具体我要去查一下 A 的文档确认。"
   ```
   这展示的是**方法论**——面试官通常更看重"遇到未知怎么办"。
3. **把"不会"转化为"学习能力"**：
   - "我没做过这个，但我做过类似的 B，我是这么做的……如果换成这个场景，我会先……"
4. **面试官追问"那你说说 A 的原理"时**：如果确实知道，就正常讲——**这往往是转折点**（面试官在测试你的诚实度）。
5. **实在不会时，可以反问**：面试官提问本身也是他的信息。"您问这个是因为我们这个岗位会用到这块吗？"——这能帮你调整后续回答的深度。
6. **面试话术**："我的原则是不编。没做过的事我直接说没做过，但我会说清楚我会怎么查、怎么定位——毕竟工作中大部分问题我都没在面试前见过，处理方式是一样的。硬编的风险太大，因为面试官追问三层一定会露，而且露馅之后我前面讲的所有东西他都会重新怀疑。"

---

**读者问：面试中怎么讲项目才能让面试官信服？**

**AI答：**

1. **用"背景 → 问题 → 决策 → 实现 → 结果 → 代价"六段式**，先给结论再展开。
2. **强调"决策"而不是"执行"**：
   - ❌ "我实现了启动优化框架"（这是任务描述，任何人都能说）
   - ✅ "我们有三个方案，我评估的维度是 X/Y/Z，选了 B，因为……"
   - **面试官想听的是"你怎么决定的"**，这才是他判断你是否够 senior 的地方。
3. **一定要讲代价**：
   - "代价是构建期多了 8s，我们用 CI 分级缓存缓解；而且因为初始化时序调整，下线了一个依赖早期初始化的实验功能。"
   - **这句话会显著提升可信度**——因为只有真正做过的人才会想到要说明代价。
4. **准备好被追问三层**：
   - "为什么不用 A？" → "A 的问题是……"
   - "这个数据怎么测的？" → "用 XX 工具，按维度切分……"
   - "有没有出过什么问题？" → "有，一次灰度时……，我们加了……"
   - **能扛住三层追问的项目，才是真项目。**
5. **讲你**做了什么，而不是**我们团队**做了什么（除非明确说明"我负责其中 X"）。
6. **避免的表述**：
   - ❌ "我们团队做了 X，效果很好"（无主体、无过程、无数据）
   - ❌ 大量技术名词堆砌（"用了 A、B、C、D"）
   - ❌ "这个很简单"（贬低问题）

---

**读者问：面试官问"你觉得自己最大的短板是什么"或者"你最近一次被否掉是什么体验"这类问题，怎么答才不翻车？**

**AI答：**

1. **这类问题是"压力测试"，不是"真心提问"。** 面试官在测三件事：**你是不是真的反思过、你是不是一个安全的人（会不会甩锅）、你的自我认知和实际能力是否匹配。**
2. **选一个"真但可控"的短板**——标准是：
   - **是真的**（不是"我太追求完美了"这种假短板）。
   - **不致命**（不能是"我不擅长写代码"这种岗位核心能力）。
   - **有改进动作**（证明你能自我修正）。
   - **不能牵涉到品质问题**（不能说"我不太守时"）。
3. **推荐的回答结构**：
   ```text
   ① 短板（具体、可验证）
      "我的短板是：过早动手写实现，方案阶段花的时间不够。
       上个项目里我提前进入了开发，结果接口改了三次，
       多花了大���一周。"

   ② 影响与代价（承认后果，不辩解）
      "这导致我一开始低估了方案评审的价值。"

   ③ 我做了什么改进（有机制，不是"我以后注意"）
      "后来我改成了先写方案文档再动手，
       并且把这个步骤写进了团队的 PR 模板里——
       现在我发起的 PR 都会先附一页方案摘要。"

   ④ 结果（最好有）
      "上一个迭代我的方案返工次数从 3 次降到 0。"
   ```
4. **"被否掉的体验"类问题的答法**：
   - **讲一个真实的、有具体过程的否定**（方案被评审打回、代码被 reviewer 打回、设计被推翻）。
   - **重点讲你的反应**：先确认是否对方对 → 找数据/做实验 → 必要时推翻自己。
   - **如果最终对方对了、你错了**：**大方承认**。"最终证明他是对的，因为我们在真实数据上验证时发现了……这让我把评估维度里补了'运维复杂度'这一项。"
   - **最忌讳**："我没被否过"（不可信）或"都是别人不懂"（红旗）。
5. **绝对不要说的**：
   - ❌ "我最大的缺点是太努力了"（假，且显得油腻）
   - ❌ "我没什么缺点"（不诚实）
   - ❌ 拿一个岗位核心能力当短板（"我代码写得不够优雅"在技术岗上是危险信号）
   - ❌ 说前同事/前公司的坏话来当短板（"我们之前团队管理很乱"——会被读成你会甩锅）
6. **最好的准备方式**：**面试前先写好 2 个"我真实犯过的错 + 改进了什么机制"的故事**。这两个故事在行为面试、技术深挖、Leader 岗的"自省能力"环节都能复用。
7. **面试话术**："我准备过这类问题。我会讲一个真实的、有具体后果的错误，然后讲我做了什么机制上的改进——因为只有机制上的改进才能防止复发。我不会说'我以后注意'这种话，因为那等于没改。"

# 新人指导与知识传递

## 一句话定义

带新人不是"分配任务"和"回答问题"，而是一套**有路径、有节奏、有反馈的工程能力培养机制**——目标是让新人从"能提交代码"变成"**能独立负责一个模块并做出技术判断**"。

## 核心原理

### 1. 为什么"带新人"是技术领导力的核心指标

**一个团队的技术水平，本质上是这个团队"平均水平 + 最差水平"决定的**，而不是由最厉害的那个人决定。

```text
团队产出 ≈ f(团队最低水平, 团队平均水平, 团队最高水平)

如果新人 3 个月还是"要人盯着写"：
  → 团队在持续消耗 senior 的时间
  → senior 没有时间做更重要的架构设计
  → 团队永远缺 senior
  → 恶性循环

如果新人 6 个月能独立负责模块：
  → senior 的时间释放到架构与攻坚
  → 团队有冗余，能承接更多业务
  → 正向循环
```

**面试信号**：面试官问"你带过新人吗"，真正想听的是：

1. 你有没有**体系化**的培养方法（而不是"我让他跟着我做"）。
2. 你**有没有衡量过效果**（而不是"他后来转正了"）。
3. 你能不能讲出**具体的成长轨迹**（而不是泛泛而谈）。

### 2. 90 天成长路径

```text
第 1-2 周    融入期（Explore）
├── 目标：能跑起来、能提 PR、能看懂代码结构
├── 动作：
│   ├── 环境搭建（当天就要能跑通构建 + 装到真机）
│   ├── 读 README + 架构文档 + 最近的 10 个 PR
│   ├── 修复 3 个小 bug（"最好的学习是改真实的代码"）
│   └── 配一个 buddy（不是 mentor）
└── 验收：能独立提 PR 并通过 review

第 3-6 周    熟悉期（Understand）
├── 目标：理解核心业务链路，能改需求
├── 动作：
│   ├── 负责一个小需求（完整走一遍：设计→开发→测试→发布→监控）
│   ├── 读这个模块的历史 commit（代码考古，理解"为什么"）
│   ├── 学习技术栈：架构模式、网络层、数据层、CI 流程
│   └── 参加 Code Review（先只看不评论，之后学着提）
└── 验收：能独立完成一个中等需求

第 7-12 周   独立期（Contribute）
├── 目标：能独立负责一个模块，能做技术判断
├── 动作：
│   ├── 独立负责一个 feature 模块
│   ├── 参与技术方案讨论（有话语权，能质疑）
│   ├── 写一份该模块的技术文档（最好的学习产出）
│   └── 修复线上问题（值班跟一轮）
└── 验收：能独立设计方案、评估技术方案、评估技术方案
```

**关键原则**：

- **第 1 周必须能跑起来**。环境跑不通的团队，新人第一周会浪费在装环境上，信心受挫。
- **每个阶段有明确的"验收"**。没有验收的成长路径 = 没有路径。
- **第 7-12 周必须让他做技术判断**（参与方案讨论、评估别人的方案）。**只写代码的新人成长极慢**——因为技术判断力只能通过做判断长出来。

### 3. 学习路径：从"看"到"做"

```text
① 读书/看文档      →  建立概念地图
      ↓
② 读真实代码       →  理解"文档里的东西在这怎么落地"
      ↓
③ 改真实代码      →  在反馈中学会边界与规范
      ↓
④ 独立负责       →  形成 ownership
      ↓
⑤ 教别人         →  真正掌握（费曼学习法）
```

**每一步都有"陷阱"，需要刻意设计**：

| 陷阱 | 表现 | 对策 |
| --- | --- | --- |
| **只读书不做** | 读了 10 本书，写不了代码 | 每本书必须配一个动手 demo |
| **只写代码不读** | 会用但不知道为什么，出错不会排查 | 每次 debug 完写"根因笔记" |
| **只做不教** | 会用但讲不清，换个场景就不会 | 安排他做一次分享 |
| **过早独立** | 一个人闷头写两周，方向错了没人知道 | 设 checkpoint 频率 |

### 4. Pair Programming：怎么用才有效

**Pair 的两种模式**：

| 模式 | 做法 | 适合 |
| --- | --- | --- |
| **Driver-Navigator**（传统） | 一人敲键盘（Driver），一人导航（Navigator） | 复杂逻辑、调试 |
| **Ping-Pong**（现代推荐） | 每人 20-30 分钟交换角色 | 学习新技术、结对解决难题 |

**关键点**：

- **Ping-Pong 优于传统模式**：传统模式下 Navigator 容易变成"看着不说话的人"，而 Ping-Pong 强制双方都动手。
- **限时**：一次 pair **不超过 2 小时**。超过人会疲劳，效率断崖。
- **有明确目标**：不是"我们一起看看这个代码"，而是"我们一起搞明白这个模块的数据流"。
- **轮换搭档**：新人应该和不同的人 pair，学到不同的风格。

**但要清楚 Pair 的局限**：

```text
Pair Programming 适合：
  ✓ 传授团队约定和代码风格
  ✓ 复杂问题的联合排查
  ✓ 新人第一个需求的"贴身指导"

Pair Programming 不适合：
  ✗ 日常需求开发（成本太高，2 人 1 倍产出）
  ✗ 机械性工作（写 CRUD、抄页面）
  ✗ 长期绑定（会造成路径依赖）
```

### 5. 内部培训与分享

**选题的三个来源**：

```text
① 反复被问的问题         → 说明文档缺失，是最高价值选题
② 踩过的坑               → 别人会踩同样的坑
③ 团队正在做的事的原理   → 帮大家理解"为什么要这么做"
```

**不要讲的选题**：

- ❌ 官方文档的搬运（大家会自己看）
- ❌ "我最近学了个新框架"（除非团队要用）
- ❌ 纯技术栈科普（除非团队里有大量新人）

**分享技巧**：

| 技巧 | 说明 |
| --- | --- |
| **分层听众** | 同一主题讲两版：15 分钟的"是什么"和 45 分钟的"怎么用 / 坑在哪" |
| **用真实案例** | 用团队自己的代码、自己的 bug 讲，不要用网上下载的例子 |
| **留 10 分钟问答** | 问答环节能暴露你讲得不清楚的地方 |
| **录屏存档** | 缺席的人能补看，也避免重复讲 |
| **讲完留文档** | 分享的 PPT + 文字说明进 Wiki，**一次投入长期收益** |
| **控制时长** | 45 分钟是上限，注意力会掉 |

**分享的价值不在"讲"，在"准备"**。为了讲清楚一个主题，你要重新梳理一遍自己的理解——**这个过程本身就是最大的收获**。

### 6. 知识传递的机制化

**依赖"人"的知识传递是不可靠的**（人一走知识就没了）。要**机制化**：

| 机制 | 作用 | 实现 |
| --- | --- | --- |
| **README + 架构文档** | 让任何人能快速理解模块 | 每个模块必须有 README（怎么用、怎么跑、怎么 debug） |
| **ADR** | 保留决策上下文 | 见 [[../技术文档与知识沉淀/ADR架构决策记录]] |
| **代码注释** | 解释"为什么" | 重点解释反直觉的实现（**不要解释"是什么"**） |
| **Wiki / 文档站** | 沉淀非代码知识 | 踩坑记录、排障手册、术语表 |
| **值班轮转** | 强制接触真实问题 | 每个新人跟一轮值班 |
| **录制** | 降低重复讲解成本 | 关键流程录屏 |
| **Onboarding 清单** | 避免遗漏关键步骤 | 见下方模板 |

**注释的写法（Android 场景）**：

```kotlin
// ❌ 解释"是什么"——代码本身已经说了
// 计算总价格
val total = price * count

// ✅ 解释"为什么"——这是新人最需要的信息
// 这里不用 BigDecimal 的 divide 是因为订单金额必须向下取整到分，
// 财务规定多出的部分计入"抹零"科目，由对账任务在次日处理。
// 详见 JIRA FIN-2231（2026-01 财务审计后确定）
val total = BigDecimal(price).multiply(BigDecimal(count))
    .setScale(2, RoundingMode.DOWN)
```

### 7. 常见失败模式

| 失败模式 | 表现 | 后果 | 对策 |
| --- | --- | --- | --- |
| **答疑机器** | senior 每天被各种问题打断 | senior 被拖垮 | **规定答疑时段 + 引导到文档 + buddy 优先** |
| **只给任务不讲背景** | "你把这个 bug 修了" | 新人不知道为什么，修完也不知道学到了什么 | 讲清楚**背景和上下文** |
| **任务太碎** | 分配一堆改文案、改布局的活 | 成长极慢，且形成"低价值工作"的印象 | 保证有**至少一个完整需求** |
| **任务太重** | 直接扔一个复杂模块 | 挫败、卡住、失去信心 | 拆成有阶段性验收的任务 |
| **不放手** | 每一步都要 review 到极致 | 新人永远学不会独立 | **逐步放手**：先看方案 → 再看代码 → 最后只看结果 |
| **没有反馈** | 半年后才发现新人成长不够 | 错过干预窗口 | 每周 15 分钟 1:1 |
| **把新人当廉价劳动力** | 只用不培养 | 团队成长停滞 | 每个新人都要产出文档/分享 |
| **负面反馈方式不当** | 当众批评 | 心理安全崩塌 | **表扬公开、批评私下** |
| **老人被绑在新人上** | senior 长期带新人不产出 | 团队产出下降 | **限时**，老人要"放手" |

### 8. 逐步放手的三阶段模型

```text
阶段 1：结对（Pair）
  我主导，新人跟随
  关注点：我做决策，新人观察我的思路
  典型时长：1-2 周

阶段 2：复核（Review）
  新人主导，我 review
  关注点：新人做决策，我提问
  典型时长：3-6 周
  关键：不要每行都改，只对"方向性"的问题干预

阶段 3：放手（Delegate）
  新人独立，我只看结果和监控
  关注点：结果达成 + 复盘
  典型时长：6 周之后
```

**关键**：**阶段 2 是最容易做错的**。很多 senior 在阶段 2 忍不住每行都改，结果新人永远学不会。**正确做法是：新人写的代码，允许有"不完美"，只要不影响正确性就让他提交。** 让他自己发现 reviewer 的意见并修正，比你直接改更有学习价值。

### 9. 1:1 沟通：低成本高回报

**每周 15 分钟**，固定时间，固定人，**不汇报进度**（进度看任务系统）。

**建议的四个问题**：

```text
1. "这周有没有什么事让你卡住了？"        → 找阻塞
2. "最近写的代码里，哪段你自己最不满意？" → 自我评估能力
3. "有没有什么是你看到但不知道该管的事？" → 培养主动性
4. "你希望 3 个月后能独立做什么？"       → 对齐期待
```

**反面做法**：

- ❌ 变成进度汇报会（→ 去看任务系统）。
- ❌ 只问"进度怎么样了"（→ 对方只会说"还行"）。
- ❌ 攒到有问题才谈（→ 变成秋后算账）。
- ❌ 只在出问题时谈（→ 新人会有防御心理）。

### 10. 衡量效果：不能只靠"他转正了"

**可以量化的指标**：

| 维度 | 指标 | 说明 |
| --- | --- | --- |
| **产出** | 独立负责的模块数、完成的完整需求数 | 转正前能独立负责几个模块 |
| **质量** | 其 PR 的 review 一次通过率、返工率 | 反映"是否真的理解" |
| **速度** | 从需求到上线的平均耗时（对比同阶段老人） | 反映熟练度 |
| **协作** | 是否能主动发现并提出问题 | 反映主动性 |
| **沉淀** | 产出的文档数、分享次数、Wiki 贡献 | **反映"不只是自己会用"** |
| **保留** | 团队内非该新人的成员对代码的抱怨是否减少 | 反映融入质量 |

**最有效的检验方法**：**看他写的代码，需不需要别人来"翻译"**。

- 需要别人解释才能改 → 还在依赖期。
- 别人能直接改 → 已建立 ownership。

### 3. 分享 PPT 的结构模板（45 分钟）

```markdown
# 分享主题：[主题名]

**分享人**：{} | **时长**：45 分钟 | **日期**：2026-XX-XX

---

## 0. 讲之前先确认（3 min）
- [ ] 听众画像（谁会来、他们的已知水平）
- [ ] 目标：听完他们能做什么 / 避免什么坑
- [ ] 有没有已有文档可以替代？（有就直接发文档，不讲）

## 1. 引入：为什么这个主题值得花 45 分钟（3 min）
- 我们团队踩的真实坑（不是抽象概念）
- 一个具体的问题场景

## 2. 是什么（5 min）
- 最小可用概念（不超过 3 个）
- 一张图讲清整体

## 3. 怎么用（15 min）
- 我们的真实代码示例
- 关键 API / 配置
- 演示（可选，现场跑更有说服力）

## 4. 坑在哪（15 min）★ 最值钱的部分
- 3-5 个我们真实踩过的坑
- 每个坑：现象 → 原因 → 怎么解
- 常见错误用法 vs 正确用法对比

## 5. Q&A（7 min）

## 6. 延伸
- 文档链接、源码链接、ADR 链接
- 录屏存档链接

```

```markdown
> 用法：新人第一天读一遍；遇到问题先搜这里。
> 维护：每个踩坑的人负责补充自己那一条。

## 编译与构建

### ❌ kapt 在新项目里
**现象**：编译慢 30s+，KSP 明显更快
**原因**：kapt 用 Stub 文件 + 动态代理
**解法**：新项目统一用 KSP
**参考**：ADR-0009

---

### ❌ 依赖版本冲突
**现象**：`Duplicate class xxx found in modules`
**原因**：传递依赖引入了不同版本
**解法**：用 Version Catalog 统一版本，`./gradlew :app:dependencies` 定位
**参考**：docs/adr/0008-version-catalog.md

---

## 运行时

### ❌ 在 Application 里初始化耗时 SDK
**现象**：冷启动 P90 2.3s
**原因**：第三方 SDK 同步初始化 + 类加载
**解法**：延迟到 idle / 用 App Startup 调度
**参考**：ADR-0015 启动优化

---

### ❌ 主线程读写 SharedPreferences
**现象**：偶发 ANR
**原因**：首次 getXxx 会阻塞等待 SP 加载
**解法**：用 DataStore，或在 Application.onCreate 提前预热
```

## 常见问题 / 面试要点

**读者问：怎么带新人才能让他成长快？**

**AI答：**

1. **要有路径，不能只给任务**：
   - 我用 **90 天三阶段**：融入期（第 1-2 周，能跑起来、能提 PR）→ 熟悉期（第 3-6 周，理解核心链路、独立完成中等需求）→ 独立期（第 7-12 周，独立负责模块、参与技术决策）。
   - **每个阶段有明确验收**。没有验收的成长计划等于没有计划。
2. **第 1 周最关键**：
   - **当天就要能跑通构建**。环境跑不通会严重打击信心，而且浪费掉最宝贵的第一周。
   - **给"第一周该看什么"的清单**，不要甩一整个 Wiki。
   - **修 3 个小 bug** 是最好的入门练习——真实的代码、真实的 review、真实的反馈。
3. **任务难度要匹配当前阶段**：
   - 太碎（只改文案）→ 成长慢，且形成"我是打杂的"的印象。
   - 太重（直接扔核心模块）→ 挫败、卡住。
   - **原则：至少保证有一个"完整的端到端需求"**，让他体验设计→开发→测试→发布→监控的全流程。
4. **要"讲背景"，不只"给任务"**：
   - "修一下这个 bug" → 新人不知道为什么，改完也不知道学到了什么。
   - "订单模块的库存扣减有并发问题，线上已经出过一次事故（附复盘链接），你看下" → 他会自己去研究。
5. **逐步放手**：
   - 结对（我主导）→ 复核（他主导，我提问）→ 放手（他独立，我看结果）。
   - **最容易做错的是阶段 2**：忍不住每行都改，结果新人永远学不会。**允许不完美，让他自己从 review 意见里学。**
6. **固定 1:1（每周 15 分钟）**：
   - **不汇报进度**（进度看任务系统），而是问四个问题：卡住的事？最不满意的代码？看到但不知道该管的事？3 个月后想独立做什么？
   - 这四个问题能暴露真实状态，比"这周还行吗"有效十倍。
7. **避免变成"答疑机器"**：
   - 设固定答疑时段、引导先查 Wiki、设 buddy 做第一道答疑。
   - **不背着新人干活** —— 长期绑定 senior 会拖垮团队。
8. **面试话术**："我用 90 天三阶段来带人，每阶段有验收：第 2 周能独立提 PR，第 6 周独立完成一个中等需求并画出模块架构，第 12 周独立负责模块且能在方案评审里提出有效意见。放手是分阶段的——结对、复核、放逐步渐。我特别强调'允许不完美'，因为在复核阶段我如果每行都改，新人永远学不会独立判断。每周还有一次 15 分钟的 1:1，不谈进度只谈四个开放问题，效果比进度汇报好很多。"

**读者问：怎么判断新人培养得怎么样？有什么衡量指标？**

**AI答：**

1. **不要只看"转正了"**。转正只说明"能干活"，不代表"能独立负责"。
2. **可量化的指标**：
   - **产出**：转正前独立负责的模块数、完成的完整需求数。
   - **质量**：PR 的一次通过率、返工率、其代码的线上缺陷数。
   - **速度**：从需求到上线的耗时（与同期老人对比）。
   - **协作**：能否主动发现并提出问题、能否参与技术决策。
   - **沉淀**：产出的文档数、分享次数、Wiki 贡献 —— **这条最能区分"会用"和"理解"**。
   - **保留**：其他成员对他代码的抱怨是否减少（反映融入质量）。
3. **最有效的单一检验**：**他的代码需不需要别人"翻译"**。
   - 需要别人解释才能改 → 还在依赖期。
   - 别人能直接接手改 → 已建立 ownership。
4. **反例信号（要警惕）**：
   - 只会写代码，不参与任何技术讨论 → 成长停滞。
   - 每次都"都行，你决定" → 缺乏判断力，不是尊重。
   - 从不主动问问题，也不看别人的代码 → 可能只是被动执行。
5. **有意识地制造"成长时刻"**：
   - 让他在方案评审中先发言（哪怕没人听）。
   - 让他给同事做一次技术分享（暴露理解深度的最好方式）。
   - 让他独立处理一次线上问题。
6. **面试话术**："我用四类指标衡量：产出（独立负责的模块数）、质量（PR 一次通过率和其代码的线上缺陷）、协作（能不能在方案评审里提出有效意见）、沉淀（有没有产出文档和分享）。最后一条我认为最能区分'会用'和'真正理解'。如果一个新人能给别人讲清楚他负责的模块，说明他不是靠人扶着走的。"

---

**读者问：知识传递怎么做得系统？人走了知识就丢了怎么办？**

**AI答：**

1. **区分"知识"的两类**：
   - **显性知识**（能写下来的）：代码、文档、ADR、Wiki → **靠机制沉淀**。
   - **隐性知识**（写不下来的）：手感、经验、踩坑的直觉 → **靠人传人 + 转化为显性知识**。
   - **目标是把隐性知识持续转化为显性知识**。
2. **机制化手段（按可靠性排序）**：
   - **代码 + 测试**：最可靠的（不会被遗忘，会被 CI 验证）。
   - **ADR**：保留决策上下文（半年后有人问"为什么"时救命）。
   - **README / 架构文档**：每个模块必须有。
   - **踩坑 Wiki**：把"隐性知识"显性化。
   - **录屏**：关键流程（成本低、效果好）。
   - **值班轮转**：强制接触真实问题。
3. **让"写文档"成为交付的一部分**：
   - 新人转正的硬性条件之一是"产出模块技术文档"。
   - 每个大需求归档时，同时更新对应模块的 README。
   - **文档不更新 = 需求没完成**（写进 Definition of Done）。
4. **知识流失的真正解药是"降低对个人的依赖"**：
   - **Bus factor**：每个关键模块至少有 2 个人能改。
   - **轮转**：值班、分享、模块 owner 备份。
   - **检查点**：模块必须有至少 2 个 git 熟悉者（通过 review 参与度衡量）。
5. **面试话术**："我把知识传递分两类：能写下来的靠机制沉淀——代码、ADR、README、踩坑清单；写不下来的经验要主动转成显性的，比如我要求新人转正前必须写一份模块文档并做一次分享，这个过程本身就是把隐性知识显性化。对抗人员流失，我更关注 bus factor：每个关键模块至少两个人能改，我们通过 review 参与度和值班轮转来保证。"

---

**读者问：面试怎么讲"带人"的经验？**

**AI答：**

1. **要讲方法，不能只讲结果**：
   - ❌ "我带过两个新人，都转正了。"
   - ✅ "我用 90 天三阶段带人：融入期让新人第 1 周就能提 PR，熟悉期独立完成中等需求，独立期负责模块并参与方案评审。放手是分阶段的——结对、复核、放逐步渐。复核阶段我允许代码不完美，因为他需要自己从 review 意见里学。衡量用四类指标：产出、质量、协作、沉淀。"
2. **要讲一个具体的"教会了什么"的例子**：
   - "有个新人一开始 review 时只会说'这里写得不好'，我教他用三段式——事实、影响、建议，后来他能在 PR 里提出让作者直接采纳的评论。"
   - "我带他做了一次线上问题处理，从拉日志、看堆栈到判断影响面，全程让他主导，我在旁边。他后来说这是他成长最快的一次。"
3. **要讲"我自己的调整"**（体现反思）：
   - "我一开始会每行都改他的代码，后来发现他改第二版时同样的问题还在犯。改成只在方向性问题上干预后，他明显进步快了。"
   - "我曾把答疑搞成随时响应，结果自己被拖垮，也让他形成依赖。改成固定答疑时段 + buddy 优先之后，双方都轻松了。"
4. **讲"沉淀"的产出**：
   - "我建了团队的踩坑 Wiki 和 ADR 目录。现在新人入职第一周要读一遍，比我一对一讲效率高。"
5. **Leader 岗的加分点**：
   - 讲你**如何让团队整体变强**，而不只是带一两个人。
   - "我做了一次 Code Review 评论分级规范，把机械检查全交给 CI，人只看判断力部分——review 质量从'挑格式'变成了'提设计问题'。"

---

**读者问：新人很内向、不敢提问、怕犯错，怎么带这种新人？**

**AI答：**

1. **先区分三种情况**，处理方式完全不同：

| 情况 | 表现 | 可能原因 | 怎么办 |
| --- | --- | --- | --- |
| **性格内向但能力够** | 不主动问，但问的问题很准 | 性格 + 不确定"该不该问" | 给足安全感，降低提问成本 |
| **能力不够不敢问** | 问的问题很浅，容易卡住 | 知识缺口 + 怕被否定 | 补前置知识 + 拆小任务 |
| **怕犯错型** | 反复确认、不敢动手 | 过去的负面经历 | **公开犯错是安全的**，让他看到别人也犯错 |

2. **对内向但能力够的新人（最常见也最被误解）**：
   - **误解**：以为他"不积极"，实际上他只是**在脑子里先想清楚才开口**——这类人一旦开口，质量往往很高。
   - **对策：把"当众提问"改成"书面提问"**。
     - 让他把问题写在文档评论、Issue、或者你的聊天窗口里，而不是在会上举手。
     - **书面 = 思考时间 = 更高质量的提问**。
   - **给他"独处准备期"**：技术方案评审前给他 30 分钟独处时间准备意见，会上不用第一个发言。
   - **一对一渠道**：明确告诉他"有想法随时找我，不用等开会"。很多内向的人只在私聊里敢说真话。

3. **对能力不够的新人**：
   - **他卡住的地方通常有共性**——把它变成一篇文档 / 一份 checklist，比一对一讲 10 次更有效。
   - **主动降低任务难度**：给"能在 2 小时内完成并验证"的小任务，**先建立"我能做成"的信心**，再逐步加码。
   - **给"可模仿的样本"**：指一个他可以照着改的现有模块，比抽象讲解有效。

4. **对怕犯错的新人（最需要关注）**：
   - **关键动作：让"犯错是安全的"变得可见**。
     - 你自己在 review 里公开承认自己的失误（"这个我当初也搞错过，原因是……"）。
     - 团队里正常的氛围是"**问题被暴露出来是好事**"，而不是"谁错了"。
   - **明确"不追责"的边界**：代码写错 → 正常，帮你改；绕过流程/隐瞒 → 要谈。
   - **不要在 review 里用"你又犯了"这种表达**——用"这里我们换个写法更安全，因为……"。
   - **给"安全的错误环境"**：分支保护、Code Review 先不合并、自动化测试兜底——**让试错成本真的低**，而不只是嘴上说"没关系"。

5. **一个通用的高杠杆做法：结对（Pair）**。
   - 内向新人跟着一位耐心的同事 pair，比自己摸索更快——**因为提问的压力被消除了**（两个人不是在"被考核"）。
   - **但要注意配对的姿势**：不要让 senior 一个人讲、另一个人打字。要 **Ping-Pong**（轮流敲键盘），否则内向的那个会退化成"观察者"。

6. **什么时候该警惕不是"性格问题"**：
   - 如果 3 个月后他仍然从不主动沟通、从不主动暴露问题（哪怕是小事）、从不参与讨论——**要正视沟通能力这个短板**，而不是继续当成"内向"。
   - 处理方式：**明确、具体、私下地给出期望**："我需要你在遇到阻塞 30 分钟内告诉我，而不是自己卡两天。这不是能力问题，是协作方式。"
   - **不要说"你要更主动"**——太抽象，无法行动。要说"**阻塞超过 30 分钟就找我**"。

7. **面试话术**："我会先区分是性格、还是能力、还是安全感问题。内向但能力够的新人，我会把提问从'会上举手'改成'书面/私聊'——他不是不思考，是需要思考时间；能力不够的，我会把卡点沉淀成文档并拆小任务；怕犯错的，我会让'犯错是安全的'变成可见的事实，比如在 review 里公开承认自己的失误。我特别在意一点：不要把'不主动沟通'长期当成'内向'来容忍。如果三个月还是这样，我会明确说'遇到阻塞 30 分钟内告诉我'，把期望具体化。因为长期的沟通问题会变成团队协作的隐性成本。"

# 技术选型与决策

## 一句话定义

技术选型是"**在多个可行方案中，依据明确的约束和评估维度做出一个有依据、可追溯、可复盘的判断**"；它的核心能力不是"知道哪个框架好"，而是"**能把模糊的偏好转化为可比较的证据**"。

## 核心原理

### 1. 选型的五步框架

```text
① 明确约束        →  什么是不管用什么方案都不能突破的？
        ↓
② 列出候选        →  包括"什么都不做"和"自己造"
        ↓
③ 定义评估维度    →  维度必须在打分之前定好
        ↓
④ 收集证据        →  数据 > 基准测试 > 文档 > 经验 > 直觉
        ↓
⑤ 决策并记录      →  ADR + 验证计划 + 重新评估的触发条件
```

**关键纪律**：**第 ③ 步的维度必须在打分之前定好。** 否则你会不自觉地调整权重，让自己的方案胜出——这是技术选型中最常见的自欺。

### 2. 第 ① 步：约束比方案更重要

**约束分四类**：

| 类别 | 说明 | 例子 |
| --- | --- | --- |
| **硬约束** | 不满足就直接出局，不参与打分 | 团队只有 Kotlin、没有 iOS 需求、必须支持 Android 5.0 |
| **软约束** | 影响打分权重 | 团队规模、学习成本、现有技术栈 |
| **组织约束** | 来自公司/上级 | 必须是集团技术栈、必须通过安全合规评审 |
| **时间约束** | 交付窗口 | 2 周内必须上线 |

**最容易被忽略的是"什么都不做"和"自己造"这两个候选**：

```text
候选清单必须包含：
☐ 什么都不做（用现有方案继续，代价是什么？）
☐ 造轮子（自己实现，成本多少？）
☐ 换一个成熟库
☐ 引入一个重量级框架
```

**"什么都不做"经常是正确答案**。很多技术选型失败的根源是：**把"引入新技术"当成了默认选项，而没有认真评估"维持现状"的代价**。

### 3. 第 ③ 步：评估维度怎么定

**维度来源**：**这个团队、这个项目当前的真实痛点**。不要抄别人的评估表。

| 维度类型 | 例子 | 适用场景 |
| --- | --- | --- |
| **工程质量** | 稳定性、维护活跃度、文档质量、Issue 响应速度 | 长期维护的核心模块 |
| **性能** | 启动耗时、内存占用、包体积、渲染帧率 | 性能敏感场景 |
| **开发效率** | API 易用性、IDE 支持、调试体验 | 日常业务开发 |
| **团队成本** | 学习曲线、招聘难度、现有代码可复用度 | 团队扩张期 |
| **风险** | 供应商依赖、许可证、维护者数量、breaking change 频率 | 关键路径依赖 |
| **合规** | 开源协议（GPL/AGPL 传染性）、隐私合规、审计要求 | 企业项目 |

**给 Android 团队的具体维度示例**：

```text
选型：图片加载库（Glide / Coil / Picasso / Fresco）

| 维度           | 权重 | 说明                                    |
|----------------|------|-----------------------------------------|
| Kotlin 支持    | 15%  | 我们是纯 Kotlin 项目                     |
| Compose 适配   | 20%  | 新页面用 Compose，需要 seamless 集成     |
| 内存占用       | 15%  | 低端机占比 30%                          |
| 包体积         | 10%  | 每 MB 都影响下载转化                     |
| 维护活跃度     | 20%  | 最近 3 个月有提交、有响应 Issue          |
| 学习成本       | 10%  | 团队没人用过                            |
| 许可证         | 10%  | 必须是 Apache 2.0                       |
```

### 4. 第 ④ 步：证据的优先级

```text
证据强度（从强到弱）：

★★★★★  自己项目的真实数据（基准测试、灰度数据）
★★★★☆  官方文档 / 源码 / 官方性能报告
★★★☆☆  独立第三方基准测试（如 tvOS/Benchmarks）
★★☆☆☆  社区实测文章、知名团队的技术分享
★☆☆☆☆  个人经验、直觉、"听说"
```

**最有力的证据是自己项目的 PoC**。在真实代码里写一个最小验证：

```kotlin
// PoC：对比两个方案在真实场景下的表现
// 1. 列表首屏渲染 1000 项图片的耗时与内存
// 2. 内存峰值
// 3. 包体积增量
// 4. 是否有 GC 抖动

@Run
fun benchmarkImageLoaders() {
    val items = (1..1000).map { ImageItem(it) }

    // Glide
    measure("glide") { runGlideScenario(items) }

    // Coil
    measure("coil") { runCoilScenario(items) }
}

private fun measure(name: String, block: () -> Unit) {
    val before = Debug.getNativeHeapAllocatedSize()
    val start = System.nanoTime()
    block()
    val durationMs = (System.nanoTime() - start) / 1_000_000
    val after = Debug.getNativeHeapAllocatedSize()
    println("$name: ${durationMs}ms, native heap +${(after - before) / 1024}KB")
}
```

**关键**：**PoC 要在真实项目的真实数据上跑**，用真实数据量、真实机型。玩具项目的结论没有参考价值。

### 5. 加权决策矩阵（Weighted Decision Matrix）

```text
方案打分（1-5 分，5 最好）：

| 维度         | 权重 | Glide | Coil | Picasso | 自研 |
|--------------|------|-------|------|---------|------|
| Kotlin 支持  | 15%  |   3   |   5  |    2    |   4  |
| Compose 适配 | 20%  |   3   |   5  |    1    |   5  |
| 内存占用     | 15%  |   3   |   5  |    3    |   2  |
| 包体积       | 10%  |   3   |   4  |    4    |   5  |
| 维护活跃度   | 20%  |   4   |   5  |    1    |   1  |
| 学习成本     | 10%  |   4   |   3  |    4    |   2  |
| 许可证       | 10%  |   5   |   5  |    5    |   5  |
|--------------|------|-------|------|---------|------|
| 加权总分     | 100% | 3.40  | 4.60 | 2.40  | 3.40 |
```

**注意"自研"和"Glide"同分**——这恰恰说明**自研不是免费的**，它的"维护活跃度"和"学习成本"劣势抵消了它的其他优势。很多团队在"用现成 vs 自研"上纠结时，忘了把**长期维护成本**算进去。

**加权总分只是参考，不是结论**。还要看：

1. **是否存在"一票否决项"**（如许可证不允许、必须支持某平台）。
2. **差距是否显著**：4.6 vs 3.4 差距大，值得换；4.1 vs 3.9 差距小，**换的迁移成本可能超过收益**——**"最好的方案"和"值得换的方案"是两回事**。
3. **锁定成本**：换掉现有方案的成本（迁移工作量、历史数据兼容、老代码维护）。

### 6. 短期与长期的权衡

这是技术选型最核心的张力。

```text
短期收益（快）                        长期成本（慢）
──────────────────────────────    ────────────────────────────
✅ 快速交付功能                    ❌ 维护成本随时间增长
✅ 少写样板代码                    ❌ 学习新技术的团队成员成本
✅ 短期效果明显                    ❌ 技术债利息持续累积
✅ 满足当前需求                    ❌ 需求演进后可能不再适用
```

**一个判断框架**：

```text
              这个决策的"影响半径"有多大？
                    │
        ┌───────────┼───────────┐
        │           │           │
     局部          模块          架构
   (一个函数)    (一个 feature)  (跨模块/依赖方向)
        │           │           │
   随时可改      需要排期      难以逆转
   直接改        写 ADR        写 ADR + 迁移计划
```

**"影响半径"越大的决策，越应该慢、应该留证据、应该做 PoC。**

**另一个关键判断：这个技术会消失吗？**

```text
会消失的技术（谨慎）：
  - 依赖单一维护者个人仓库的库
  - 商业模式不稳定（可能随时停止维护或商业化改变条款）
  - 依赖私有 API、非公开渠道更新的工具

不太会消失的技术（可以更激进）：
  - Kotlin 官方库（Jetpack）
  - 遵循稳定 API 承诺的成熟库
  - 有多个独立维护者的标准（SQL、HTTP）
```

### 7. 认知偏误：选型时最容易犯的错

| 偏误 | 表现 | 后果 |
| --- | --- | --- |
| **锚定效应** | 第一个想到的方案成为基准，其他方案都与它比 | 错过了明显更好的方案 |
| **现状偏误**（惯性思维） | "我们一直这么做" | 继承了历史包袱 |
| **沉没成本** | "我们已经投入 3 个月了，不能放弃" | 在错的路上继续投入 |
| **从众** | "大厂都在用" | 忽略自己的具体约束 |
| **确认偏误** | 只收集支持自己方案的证据 | 决策变成自我论证 |
| **可得性启发** | "我上次用 X 就出了问题" | 用单个样本否定整个方案 |
| **方案依附** | 喜欢某个技术，为它找理由 | 技术成了目的而非手段 |

**对抗偏误的方法**：

1. **强制写下"至少 3 个候选"**，包括"什么都不做"和"自研"。
2. **让不同角色独立打分**再汇总——**先各自判断再讨论**，避免第一个发言的人锚定所有人（这正是"静默瀑布"效应）。
3. **要求写出"选这个方案的代价"**——**写不出代价，说明还没想清楚**。
4. **明确"什么会让我们改变主意"**——预先写下证伪条件。
5. **让最可能反对的人先发言**。

### 8. 可逆决策 vs 不可逆决策

```text
┌──────────────────────────────────────────────────────────┐
│                    可逆决策                               │
│  成本低、影响小、可以回滚                                   │
│  → 快速决定，用最小成本做实验                              │
│  → 例：换个日志库、试试新的 Gradle 插件、加个测试框架      │
│  → 原则：Don't overthink it，Ship it and learn           │
├──────────────────────────────────────────────────────────┤
│                   不可逆决策                               │
│  成本高、影响大、难以回滚                                   │
│  → 慢决策，充分收集证据，做 PoC，写 ADR                    │
│  → 例：架构分层、跨端方案、数据库选型、DI 框架             │
│  → 原则：慎重，用证据而非直觉                              │
└──────────────────────────────────────────────────────────┘
```

**关键**：**不要用不可逆决策的严谨程度去对待可逆决策**（分析到瘫痪），**也不要用可逆决策的随意程度对待不可逆决策**（一锤子买卖）。

### 9. 决策之后：验证与重新评估

**选型不是终点**。一个完整的选型决策包含：

1. **决策记录**（ADR，见 [[../技术文档与知识沉淀/ADR架构决策记录]]）。
2. **验证方式**：怎么知道这个决策是对的？
   - **技术指标**：编译时长、崩溃率、内存占用。
   - **业务指标**：需求交付周期、缺陷率、新人上手时间。
3. **重新评估的触发条件**（**写在 ADR 里**）：

```markdown
## Validation
- 迁移完成后 4 周复盘一次
- 触发重新评估的条件：
  1. 库的维护活跃度下降（6 个月无提交或有未修复的高危 CVE）
  2. 团队规模从 5 人增长到 15 人以上（维护成本模型变化）
  3. 出现新的官方方案且现有方案有明确迁移路径
  4. 关键指标未达标（编译时长未下降 30%）
```

**"触发重新评估的条件"是 ADR 里最有价值但最少被写的部分**——它让决策变成**可证伪的假设**，而不是一次性拍板。

### 10. 选型的常见错误

| 错误 | 表现 | 纠正 |
| --- | --- | --- |
| **技术驱动的选型** | "这个技术很火/很先进" | 从约束和痛点出发 |
| **忽略退出成本** | 只看引入成本 | 评估数据迁移、团队学习、供应商锁定 |
| **不做 PoC** | 直接全量引入 | 先在真实场景验证关键假设 |
| **一次选太多** | 同时引入 5 个新库 | 一次一个，有收益再下一个 |
| **只看技术不看团队** | 选了团队没人会的东西 | 评估团队技能现状 |
| **选了没有维护者的库** | 个人仓库项目 | 检查维护者数量与商业背景 |
| **忽略合规** | 引入 GPL 库 | 许可证必须先过 |
| **决策无记录** | 半年后没人知道为什么 | 写 ADR |

## 代码示例

### 1. 技术选型评估表模板

```markdown
# 技术选型评估：[决策名称]

**日期**：2026-XX-XX
**决策人**：{}
**参与评估**：{}
**关联 ADR**：ADR-XXXX

## 1. 背景与约束

### 要解决的问题
[具体的问题，带数据]

### 硬约束（不满足直接出局）
- [ ] 必须支持 minSdk 24+
- [ ] 许可证必须是 Apache 2.0 / MIT
- [ ] 必须支持 Kotlin 2.0 + Compose
- [ ] 团队无额外招人计划

### 软约束
- 团队 6 人，Android 经验平均 3 年
- 现有工程 8 个模块，日均构建 12 分钟
- 低端机（<2G RAM）占线上 25%

### 时间约束
- 需在 2026-04-15 前上线

## 2. 候选方案

| 方案 | 简介 | 状态 |
| --- | --- | --- |
| A: Glide | 成熟的图片加载库 | 候选 |
| B: Coil | Kotlin 原生图片库 | 候选 |
| C: Picasso | 老牌图片库，维护停滞 | 候选 |
| D: 不引入 | 沿用现有方案 | 候选 |
| E: 自研 | 基于 ImageDecoder 实现 | 候选 |

## 3. 评估维度（打分前确定）

| 维度 | 权重 | 依据 |
| --- | --- | --- |
| Kotlin/Compose 支持 | 20% | 新页面全用 Compose |
| 内存占用 | 15% | 低端机占 25% |
| 包体积 | 10% | 转化率敏感 |
| 维护活跃度 | 20% | 长期维护依赖 |
| 团队学习成本 | 10% | 团队无人用过 Coil |
| 迁移成本 | 15% | 现有 12 处 Glide 用法 |
| 许可证 | 10% | 合规要求 |

## 4. 打分

| 维度 | 权重 | A Glide | B Coil | C Picasso | D 不引入 | E 自研 |
| --- | --- | --- | --- | --- | --- | --- |
| Kotlin/Compose 支持 | 20% | 3 | 5 | 2 | 2 | 5 |
| 内存占用 | 15% | 3 | 5 | 3 | 2 | 2 |
| 包体积 | 10% | 3 | 4 | 4 | 5 | 5 |
| 维护活跃度 | 20% | 4 | 5 | 1 | 5 | 1 |
| 团队学习成本 | 10% | 4 | 3 | 4 | 5 | 2 |
| 迁移成本 | 15% | 5 | 2 | 4 | 5 | 1 |
| 许可证 | 10% | 5 | 5 | 5 | 5 | 5 |
| **加权总分** | 100% | **3.55** | **4.10** | **2.90** | **3.85** | **3.00** |

> 注：D「不引入」得分不低——这提醒我们**现状也有成本**，不能默认它是 0 分。

## 5. PoC 验证

在真实模块 `feature/product` 上实现两种方案，对比：

| 指标 | Glide | Coil | 说明 |
| --- | --- | --- | --- |
| 列表首屏（1000 项）耗时 | 480ms | 420ms | 低端机 Pixel 3a |
| 内存峰值 | +38MB | +29MB | |
| 包体积增量 | +1.2MB | +0.9MB | |
| 60fps 掉帧率 | 4.2% | 1.8% | |

## 6. 结论

**选择 B: Coil**

理由：
1. 总分最高（4.10 vs 3.55），且在团队最关心的 Compose 支持与内存上优势明确
2. PoC 在真实场景验证了性能优势，不是纸上谈兵
3. 迁移成本虽高（12 处用法），但这部分是确定的工作量（预估 3 人日）

**自研方案被否决的原因**：
虽然性能可控、许可证无忧，但需要长期维护解码、缓存、内存管理、
图片格式支持等完整能力，预估年维护成本 20 人日，超出团队承载。

**不引入方案被否决的原因**：
现有方案在 Compose 下体验差（需额外写 AndroidView 桥接），
且内存占用高，正是本次要解决的问题。

## 7. 代价与风险（必填）

- 迁移需要 3 人日，期间新旧并存可能引入不一致
- Coil 团队规模小于 Glide，供应商风险略高
- 团队 2 人需要学习 Kotlin DSL 风格的 API

## 8. 验证与重新评估

- 迁移完成后对比内存指标与崩溃率
- 6 个月后复盘：若 Coil 停止维护超过 6 个月，重新评估
- 若低端机占比下降到 10% 以下，重新评估内存权重
```

### 2. 选型决策的 ADR（精简版）

```markdown
# ADR-0021: 图片加载库选用 Coil

- **Status**: Accepted
- **Date**: 2026-03-20
- **Deciders**: @张三 @李四
- **Related**: ADR-0005, ADR-0018

## Context
- 现有 Glide 在 Compose 下需 AndroidView 桥接，代码冗余
- 低端机（<2G RAM）占线上 25%，图片加载导致的 OOM 占崩溃 Top3
- 低端机列表滑动掉帧率 4.2%，超过 3% 的告警阈值
- 硬约束：Apache 2.0 许可证、minSdk 24、Compose 全面迁移中

## Decision
采用 Coil 2.x 替换 Glide，作为图片加载的统一方案。

## Consequences
### 正面
- 低端机列表掉帧率预期从 4.2% 降至 2% 以下
- 内存峰值预期降低约 25%（PoC 实测 -9MB）
- Kotlin 原生 API，与 Compose 天然集成

### 负面
- 迁移 12 处调用点，预估 3 人日
- Coil 维护团队规模小于 Glide，长期供应商风险略高
- 团队需学习其 DSL 风格 API

### 后续约束
- 禁止在 feature 模块直接使用 Glide（通过 ArchUnit 规则校验）
- 迁移完成前，新代码一律使用 Coil

## Alternatives Considered
- **Glide**：成熟稳定，但 Compose 集成成本高，内存表现不佳。不满足核心痛点。
- **Picasso**：维护停滞（最后提交 2021 年）。否决。
- **不引入**：现有方案在 Compose 下体验差，正是待解决问题。否决。
- **自研**：年维护成本约 20 人日，超出团队承载能力。否决。

## Validation
- 4 周后对比迁移模块的内存与掉帧指标
- 触发重新评估：Coil 停止维护超 6 个月，或出现高危 CVE 未修复
```

### 3. 选型的 PoC 代码骨架

```kotlin
// 选型 PoC：在真实模块上对比两个候选方案
// 只验证关键假设，不追求完整实现

@Run
@Config(sdk = [29], qualifiers = "w411dp-h891dp-xhdpi")
fun benchmarkCandidate() {
    val items = (1..500).map { i -> ProductItem(id = i, imageUrl = url(i)) }

    // 场景 1：首次加载（冷缓存）
    measure("candidateA-cold") { loadAll(items) { render(it) } }
    measure("candidateB-cold") { loadAll(items) { render(it) } }

    // 场景 2：滚动（复用）
    measure("candidateA-scroll") { scrollList(items) }
    measure("candidateB-scroll") { scrollList(items) }

    // 关键指标：内存峰值、GC 次数、耗时
}

private fun measure(name: String, block: () -> Unit) {
    Runtime.getRuntime().gc()
    val memBefore = Debug.getMemoryInfo(Runtime.getRuntime().let { arrayOf(it) })
    val start = System.nanoTime()
    block()
    val ms = (System.nanoTime() - start) / 1_000_000
    val memAfter = Debug.getMemoryInfo(Runtime.getRuntime().let { arrayOf(it) })
    println(
        "$name: ${ms}ms, " +
        "java=${(memAfter.totalPss - memBefore.totalPss)}KB, " +
        "native=${(memAfter.nativePss - memBefore.nativePss)}KB"
    )
}
```

## 常见问题 / 面试要点

**读者问：技术选型怎么做才科学？有什么标准流程吗？**

**AI答：**

1. **五步框架**：
   - **① 明确约束**（硬约束 / 软约束 / 组织约束 / 时间约束）——**硬约束不满足直接出局**。
   - **② 列候选**，**必须包含"什么都不做"和"自己造"**。
   - **③ 定义评估维度**（**必须在打分前定好**，否则会不自觉调权重）。
   - **④ 收集证据**（自己项目数据 > 官方文档 > 第三方基准 > 社区文章 > 直觉）。
   - **⑤ 决策并记录**（ADR + 验证方式 + 重新评估触发条件）。
2. **最容易被跳过的是第 ① 步和第 ⑤ 步**：
   - 跳过约束 → 选了一个很棒但不适合自己的方案。
   - 跳过记录 → 半年后没人知道为什么，重复讨论。
3. **打分工具是辅助，不是决策**：
   - 加权矩阵让讨论显性化、可比较，但**差距小的时候不构成换的理由**——**迁移成本常常超过收益**。
   - **"最好的方案"和"值得换的方案"是两回事。**
4. **别忘了"什么都不做"**：很多选型的正确答案是不换。**现状也有成本**（要算出来），但换的成本也要算。
5. **面试话术**："我做选型的顺序是：先列硬约束把方案筛一遍，再定评估维度（这一步一定在打分之前），然后用 PoC 在真实项目里跑数据，最后写 ADR 记录决策、代价和重新评估的条件。加权矩阵我会用，但它只是让讨论显性化的工具——如果两个方案分差不到 0.5 分，我会选迁移成本低的那个，因为换的代价通常比分的差距更值钱。"

---

**读者问：怎么在短期交付和长期技术债之间做权衡？**

**AI答：**

1. **先算"影响半径"**：
   - **局部决策**（一个函数、一个工具类）→ 快速决定，改错成本低。
   - **架构决策**（分层、跨端方案、数据库选型、依赖方向）→ 慢决策，要证据。
   - **不要用不可逆决策的严谨度对待可逆决策**（会分析到瘫痪），**也不要用可逆决策的随意程度对待不可逆决策**。
2. **技术债是有价的，不是纯成本**：
   - 主动借入的技术债**可以是好决策**——前提是：**明确知道代价 + 有明确的还款计划 + 真的还了**。
   - 危险的是**利息持续累积且没人承认**。
3. **短期 vs 长期的判断标准**：**这个技术/架构还能撑多久？**
   - 如果业务预期还有 6 个月就下线了 → 现在做完美架构是浪费。
   - 如果预期至少 2 年 → 短期方案要算上利息。
4. **给"技术债预算"而不是"技术债零容忍"**：
   - 每个迭代固定留 15-20% 容量还债。
   - **把技术债偿还记入排期预算**，和其他需求竞争——想加功能？可以，但要说明它会推迟多少偿还。
5. **怎么跟老板谈**：
   - 不要说"这段代码很烂"，要说"**这个模块每次需求改动要多花 2 天，一年 20 次需求 = 40 人日**"。
   - 用**事故关联**加强论证："过去 6 个月 12 个 P1，8 个根因指向同一模块。"
6. **面试话术**："我的判断标准是影响半径加债务利息。短期交付我一定优先，但有两个前提：一是我会明确写下这笔债的代价和还款计划，二是利息累积到超过重构成本时必须还。我们团队的做法是每个迭代留 20% 容量还债，而不是等'有空'——空闲时间永远不存在。"

---

**读者问：选型时总是有人反对怎么办？**

**AI答：**

1. **先分清是"有信息的反对"还是"无信息的反对"**：
   - **有信息的反对**（提出具体的风险、场景、失败案例）→ **必须认真对待**，往往是对的。
   - **无信息的反对**（"我觉得不行"、"我们一直用 X"、"太新了"）→ 需要引导他给出具体场景。
2. **用提问把反对具体化**：
   - "你担心的是什么？能举个具体场景吗？"
   - "如果……会发生什么？"
   - **反对一旦被具体化，就可以被评估**（可以查证、可以做 PoC）。
3. **让最可能反对的人先发言**（在正式讨论前私下问）：
   - 公开场合第一个反对的人会定调；私下先收集能让讨论更充分。
   - 也避免"为了反对而反对"。
4. **不要用投票决**：
   - 投票会掩盖真正的技术理由。
   - 正确做法：**把分歧转化为一个可验证的问题**（"我们各写个 PoC，周三看数据"）。
5. **共识 vs 决策权**：
   - 技术分歧 → 由决策人拍板，**记录在 ADR 里**（包括被否决的方案和理由）。
   - **有条件共识**是健康的状态："我同意这个方向，但要求先验证 X"。
6. **如果反对是对的**：感谢并采纳，这是决策流程在起作用。
   - **如果是无信息的反对且被驳回**：在 ADR 里记录"曾提出 X 意见，理由 Y"，避免下次重复争论。
7. **面试话术**："遇到反对我第一件事是把反对具体化——'你担心什么'、'什么场景会出问题'。因为只有具体的反对才能被评估。如果还是无法验证，我就建议各写个最小 PoC 用数据说话。如果纯粹是偏好之争，我按决策权拍板，但会把反对意见和我的理由一起写进 ADR，这样下次不会重复讨论。"

---

**读者问：面试怎么讲技术选型经历？**

**AI答：**

1. **必须讲"取舍"，只讲结论没有说服力**：
   ```text
   ❌ "我们用了 Coil，因为它是 Kotlin 原生的。"
   ✅ "我们要解决的是低端机图片加载导致的 OOM 和滚动掉帧。
        候选有 Glide、Coil、不引入、自研四个。
        评估维度是 Compose 集成、内存、包体积、维护活跃度、迁移成本、许可证。
        PoC 在真实列表上跑下来，Coil 内存峰值低 9MB，掉帧从 4.2% 降到 1.8%。
        最后选 Coil。代价是迁移 12 处调用点要 3 人日，而且 Coil 的维护团队比 Glide 小，
        所以我们在 ADR 里写了重新评估条件：Coil 停更超 6 个月就重新审视。"
   ```
2. **必须讲"代价"**：
   - 只讲收益 → 听起来像宣传。
   - 讲出代价 → 显得真实可信，也证明你是做了完整决策。
3. **必须讲"否决了什么以及为什么"**：
   - "自研被否决，因为年维护成本 20 人日超出团队承载。"
   - "不引入被否决，因为现有方案在 Compose 下体验差，正是待解决的问题。"
4. **加分项：讲你怎么避免"选错"**：
   - "我们在 ADR 里写了重新评估的触发条件，这是把决策变成可证伪的假设。"
   - "我们用技术雷达管理选型，避免团队各处引入不同方案。"
5. **避免的表述**：
   - ❌ 讲成"我选了 X"（显得只是执行）
   - ❌ 讲成"我们团队一致决定"（听起来像没参与讨论）
   - ❌ 只讲技术不讲决策过程

---

**读者问：引入一个新技术的成本到底有多大？能不能"先用起来再说"？**

**AI答：**

1. **能，但要先知道"先起来"的代价是什么。**引入一项新技术的**完整成本**包含 6 块，**大部分不在"接入"这一步**：

| 成本块 | 内容 | 容易被低估吗 |
| --- | --- | --- |
| **接入成本** | 依赖引入、API 学习、改造现有代码 | 最容易看到，也**最容易被高估** |
| **迁移成本** | 存量代码改造、老数据兼容、老接口适配 | **常被低估** |
| **学习成本** | 团队 N 人 × 学习曲线 × 期间效率损失 | **最常被低估** |
| **维护成本** | 版本升级、API 变更适配、社区答疑 | **几乎总是被低估** |
| **依赖风险** | 维护者数量、许可证、商业模式变更、供应链攻击 | **几乎总是被忽略** |
| **机会成本** | 引入新技术占用的注意力 vs 本可以做别的 | **从不被计算** |

2. **一个经验公式**（用于快速估算）：

```text
总成本 ≈ 接入成本(1~2 人日)
       + 迁移成本(存量调用点 × 0.5 人日)
       + 学习成本(团队人数 × 1 人日)     ← 只算"能上手"的最低成本
       + 维护成本(年化：每半年 0.5~1 人日应对升级与问题)
       + 风险成本(不可量化，但必须问"维护者只有一个人吗？")
```

   **示例**：一个 6 人团队，引入一个替代现有方案的库，有 12 处调用点：
   ```text
   接入 1.5 + 迁移 6 + 学习 6 + 年维护 2 ≈ 15.5 人日 ≈ 3 人周
   ```
   如果收益只是"代码写起来顺手一点"，**这个投入通常不划算**。如果收益是"消除了每月 4 小时的线上问题排查"，那就划算。

3. **"先用起来再说"的风险**：
   - **一旦进入主干，撤出成本会指数上升**——依赖越深、数据格式越绑定，越难拔。
   - **最容易的失败形态**：试用了 2 周觉得不错 → 铺开用了 6 个月 → 社区停止维护 → **比原来的方案更糟**（因为还要维护自己的 fork）。
   - **对策**：**用明确的退出条件来约束试用**。
     - "先用 3 个月" → 但要有"什么情况下停掉"的判据。
     - **先在边缘场景用**（新模块、实验功能），不要一上来替换核心链路。
     - **保留旧方案**直到新方案被验证（灰度 + 双轨）。

4. **依赖风险的具体评估清单**（面试常被追问）：
   - **维护者数量**：只有 1 个人 → 高风险（他离职/生病，项目就死）。
   - **仓库活跃度**：最近 3 个月有提交吗？Issue 有响应吗？
   - **商业背景**：个人爱好项目 vs 有商业支撑的公司项目。
   - **许可证**：Apache 2.0 / MIT 安全；**GPL / AGPL 有传染性**，闭源 App 要格外小心。
   - **依赖深度**：它自己又依赖多少东西？（一个"轻量"库依赖 50 个传递依赖就一点也不轻）
   - **供应链**：是否在有已知漏洞的包列表里。

5. **什么时候"先用起来再说"是对的**：
   - **可逆决策**（成本低、影响小、能轻松撤出）→ 直接试，比如加个测试框架、换个日志库。
   - **团队已经有人熟悉** → 学习成本接近 0。
   - **有明确的验证指标和期限** → "3 个月内启动耗时降不到 15% 就撤"。
   - **社区维护活跃且许可证清晰** → 风险可控。

6. **面试话术**："我评估新技术时会把成本拆成六块：接入、迁移、学习、维护、依赖风险、机会成本。真正容易被低估的是学习和维护——很多团队只算了接入，发现三个月后一半人在补文档、一半人在处理版本升级问题。我的判断是：可逆的技术可以先用起来再说，但必须写明退出条件和验证期限；不可逆的技术（数据格式、依赖方向、跨端方案）必须先做 PoC 和 ADR。另外我会评估维护者数量和许可证——只有一个人维护的个人项目，我会慎用。"

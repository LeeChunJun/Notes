# 代码审查最佳实践

## 一句话定义

Code Review 是在代码合入前，用**其他人的视角**发现"**作者看不见的问题**"的机制——它同时是**质量手段**、**知识传播手段**和**设计一致性手段**，但**它绝不能变成找茬或表演技巧的场合**。

## 核心原理

### 1. Code Review 的三个真实目标

```text
目标 1：发现缺陷          ── 但只是副产品，不是主要目标
目标 2：传播知识          ── 新人通过看 PR 学到团队约定与领域知识
目标 3：统一设计与规范    ── 保证同一类问题在项目里只有一种解法
```

**Google 的研究数据（值得记住，面试常引）**：

| 指标 | 数据 |
| --- | --- |
| 代码审查能发现的问题中，**能导致生产事故的只占 5%~10%** | 所以 Review 的主要价值不是抓 bug |
| **代码审查的主要收益是"知识共享"和"设计一致性"** | |
| 审查者的价值在于"**了解变更的上下文与影响**"，而非单纯找 bug | |
| **变更超过 400 行后，审查发现缺陷的效率显著下降** | 所以要拆分 PR |

**面试话术**："很多人以为 Code Review 是为了抓 bug，其实数据上只有 5% 到 10% 的 review 发现的问题会导致生产事故。真正的价值是知识共享和设计一致性——让团队里对同一类问题只有一种解法，避免每写一个模块就发明一套新架构。这也是为什么 review 应该由不同的人来做，而不是找最严格的那个当门神。"

### 2. 建设性反馈的三段式

**核心公式**：

```
        ┌──────────────────────────────────────────┐
        │  ① 事实  →  ② 影响  →  ③ 建议/提问       │
        └──────────────────────────────────────────┘
         客观描述   为什么这重要   给出方向
```

**对照表**：

| ❌ 无效评论 | ✅ 有效评论 |
| --- | --- |
| "这里写错了" | "`loadUser()` 在主线程调用，第 3 次 IO 会在低端机上造成 200ms+ 阻塞，建议放到 `viewModelScope` 的 IO 调度器上" |
| "这段代码很烂" | "这个 `if-else` 有 6 个分支，建议用 sealed class 建模，这样编译器能提醒你处理新分支" |
| "为什么这么写？"（质问语气） | "这里的轮询间隔是硬编码的 5s，是有特定原因吗？如果是想降低服务端压力，也许 `WorkManager` 的最小周期是 15min 更合适" |
| "感觉不太对" | "我担心这里的重试没有退避，如果服务端持续 5xx 会形成请求风暴。参考 `ApiClient` 里的 `ExponentialBackoff`？" |
| "+1" / "已修复"（无信息量） | "✅ 同意，走 `RemoteConfig` 下发开关更好" |
| "这写法不优雅" | "（无信息量，无法行动）" |

**关键差别**：

- **有效评论让作者知道"下一步做什么"**，或者让作者思考一个之前没想到的问题。
- **无效评论只是传递情绪**。

**一个反直觉但重要的点**：**"提问"往往比"建议"更好**。

> "这里为什么用 `GlobalScope` 而不是 `viewModelScope`？" —— 作者可能自己就会意识到问题。
> "这里应该用 `viewModelScope`。" —— 作者可能只是照改，下次还会犯。

**建议用问句 + 表达不确定性**，把判断权留给作者：

```text
✅ "我理解这里用 `Lazy` 是为了延迟初始化？不过 `Lazy` 本身是线程安全的，
    但如果在 `get()` 之后又用 `!!` 强转，可能拿到 null——这块我可能理解错了，
    能讲一下初始化顺序吗？"

❌ "这里必然 NPE，必须改掉。"
```

### 3. 审查清单（Review Checklist）

**按维度组织，避免遗漏**：

| 维度 | 检查项 |
| --- | --- |
| **正确性** | 边界条件（空、0、最大值、负数）是否处理？并发安全？错误路径是否完整？ |
| **资源管理** | Context/View 是否被长生命周期持有？协程/线程是否取消？监听是否反注册？ |
| **性能** | 主线程 IO？循环里 new 对象？布局层级是否过深？列表是否用 RecyclerView？ |
| **安全** | 是否明文传输？敏感信息是否打日志？Intent 是否导出？权限是否最小化？ |
| **线程** | 是否在主线程做 IO？LiveData/StateFlow 是否在正确线程更新？ |
| **架构一致性** | 依赖方向是否正确？有没有绕过 Repository 直接调网络？状态管理方式是否统一？ |
| **可维护性** | 命名是否表意？函数是否过长？是否有重复代码？魔法值？ |
| **测试** | 是否有对应单测？关键分支覆盖了吗？ |
| **兼容性** | 是否影响老版本用户？与 API 契约是否一致？ |
| **体验** | 是否有加载/空态/错误态？深色模式？无障碍（contentDescription）？ |

**关键**：**清单是"提醒自己别漏"，不是"逐条打分"**。逐条打分会让 review 变成表格填写，失去价值。

### 4. 评论分级：不同严重度用不同标记

| 级别 | 含义 | 是否阻塞合并 | 示例 |
| --- | --- | --- | --- |
| 🔴 **blocking** | 必须改，否则不能合入 | ✅ 阻塞 | 安全漏洞、资源泄漏、主线程 IO、架构方向错误 |
| 🟡 **suggestion** | 建议改，作者可以拒绝并说明理由 | ❌ 不阻塞 | 命名可以更清晰、可以抽成方法 |
| 🔵 **question** | 我没看懂，请解释 | ❌ 不阻塞（但作者必须回应） | "这里的并发假设是什么？" |
| ⚪ **nit** | 吹毛求疵，可选 | ❌ 不阻塞 | "这里可以加个空格" |
| 💚 **praise** | 值得表扬的做法 | ❌ | "这里用 sealed interface 建模很棒，避免了非法状态" |

**规则**：

- **只有 blocking 才阻塞合并**，其余一律不阻塞。
- **nit 不要用 emoji 或"nit:"以外的标记**，避免淹没重要评论。
- **一条 PR 里的 blocking 评论不应该超过 3-5 条**。超过说明这个 PR 太大，应该拆。
- **表扬要具体**："✅ 这段用 `sealed interface` 建模避免了 `loading && error != null` 的非法状态" 比 "👍" 有用一百倍。

### 5. 大 PR 的处理

**问题**：超过 400 行的变更，审查效率断崖式下降，审查者会开始"扫一眼过"。

**处理策略**：

1. **拆分 PR**：
   - **纯机械改动单独提**（格式化、自动重命名、依赖升级、代码生成产物）——**这些应该由工具审查，人不看**。
   - **功能改动单独提**。
   - **顺序很重要**：先提机械改动（reviewer 可以快速 approve），再提依赖它的功能改动。
2. **自审先做**：
   - 提 PR 前自己看一遍 diff，确认没有调试代码（`println`、TODO 注释掉的代码、`.git` 里的密钥）。
   - **写好 PR 描述**：改了什么、为什么、怎么测、有什么风险。**描述清楚的 PR，review 时间能减半。**
3. **指定 reviewer 的方向**：
   - 找**这个模块的 owner**（最懂业务正确性的人）。
   - 找**架构层的人**（如果是跨模块的架构性改动）。
   - **不要每次都找同一个最严格的人**——他不是质量保障，他是团队的瓶颈。
4. **紧急情况**：
   - 明确标记 `[紧急]`（线上故障），允许先合后审，但**必须 24 小时内补审**。

### 6. 响应时效与异步化

**期望**：

| 场景 | 期望响应时间 |
| --- | --- |
| 日常 PR | 24 小时内 |
| 阻塞别人的 PR | 尽快，且**明确告知预计时间** |
| 紧急修复 | 立即 |
| 复杂 PR | 先给一个初步反馈（哪怕是"我需要时间细看"） |

**关键**：**"我今天来不及看，明天给你"也是有效响应**。最糟糕的是**沉默**——提交者不知道你会不会看，只能干等。

**异步优先**：

- **书面评论优于口头**（可追溯、可异步、可搜索）。
- **避免在别人的 PR 上直接改代码**（剥夺了作者的学习机会，也让 diff 混乱）。**要改就在评论里给出具体建议，让作者自己改。**
- 紧急的线上问题除外。

### 7. 处理分歧

```text
分歧出现
   │
   ├─ 作者解释后双方理解一致 ──────→ 结束
   │
   ├─ 技术分歧：谁的方案更好？
   │     ├─ 有数据/实验 → 用数据裁决
   │     ├─ 无数据但可验证 → 约定一个小 PoC，限时给结论
   │     └─ 纯偏好 → 作者决策（作者对自己的代码负责），reviewer 记录异议
   │
   └─ 原则分歧：是否违反团队规范？
         ├─ 规范明确 → 按规范来，或先改规范（走 ADR）
         └─ 规范不明确 → 讨论并补充规范
```

**黄金规则**：

> **技术分歧用数据裁决，偏好之争用实验裁决，无解之争用"谁先做"裁决。**
> 永远不要让 review 变成一场辩论赛——要么当场收敛，要么转化为一个 owner + deadline 的验证任务。

**"作者决策"原则**：对于**纯技术偏好**的分歧，**由作者做最终决定**。理由：

- 作者对自己的实现有完整上下文，reviewer 只有片段。
- 让作者拥有决定权，能培养 ownership。
- 但如果是**blocking 级别**的问题（安全、泄漏、架构方向），reviewer 有权坚持。

### 8. Reviewer 的心态

```text
❌ Reviewer 心态：我是守门人，我要证明这段代码不够好
✅ Reviewer 心态：我要确认这段代码能被合入，同时帮作者变得更好
```

**具体行为差异**：

| ❌ | ✅ |
| --- | --- |
| 逐行挑刺，纠结命名 | 只在真正影响理解时提命名 |
| 用"我觉得"否定别人的设计 | 先理解设计意图，再判断 |
| 只提问题，不给方向 | 提出问题 + 给出方向或参考 |
| 纠结格式（交给 lint） | 关注正确性、架构、安全 |
| 让作者猜我想要什么 | 直接说清"必须改成什么样" |
| 提 20 条评论 | 提 3 条真正重要的 |

**克制很重要**：**一个充满 30 条 nit 的 review，会让作者对 review 产生免疫**。下一次他就不会认真看了。**少量高质量的评论 > 大量低质量的评论。**

### 9. 对新人的 Review 要更友善

- **多给上下文**：不要只说"改成这样"，要说"为什么这样更好，以及在什么场景下会出问题"。
- **先私下聊，再公开评论**：如果是明显的问题，新人第一次遇到时，**私下说比在 PR 上说更有效**（保护心理安全）。
- **区分"必须改"和"建议"**：新人容易把所有评论都当成批评，**明确标记等级能帮他区分**。
- **表扬要具体**：新人需要知道哪里做得好，才能复制。

### 10. 用工具把人力用在刀刃上

**应该由工具做（人不看）**：

- 代码格式（ktlint / Spotless）
- 静态检查（Lint / detekt / SonarQube）
- 依赖漏洞扫描（Dependabot / Snyk）
- 提交信息校验（commitlint）
- 冲突标记检测（.orig/.rej 文件、调试代码检测）
- 密钥泄露检测（gitleaks / GitHub Secret Scanning）

**应该由人做**：

- 业务逻辑正确性
- 架构方向与一致性
- 边界条件与异常路径
- 可读性与可维护性
- **"这个改动是否解决了真正的问题"**

**核心思想**：**把机械性的检查自动化，人力专注于需要上下文和判断力的部分**——这是 review 质量的根本提升方式。

- [ ] 依赖方向正确（feature 不依赖 app，core 不依赖 feature）

### 4. 用 GitHub/GitLab 自动化机械检查

```yaml
# .github/workflows/pr-check.yml —— 把机械检查交给 CI，人只看需要判断的部分
name: PR Check
on: pull_request

jobs:
  mechanical:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-java@v4
        with: { distribution: temurin, java-version: 17 }

      - name: 格式检查 (ktlint)
        run: ./gradlew ktlintCheck

      - name: 静态检查 (lint + detekt)
        run: ./gradlew lintDebug detekt

      - name: 单元测试
        run: ./gradlew testDebugUnitTest

      - name: 依赖漏洞扫描
        uses: dependency-review-action@v4

      - name: 密钥泄露检测
        uses: gitleaks/gitleaks-action@v2

      - name: 调试代码检测
        run: |
          if git diff origin/${{ github.base_ref }}...HEAD | grep -nE '^\+.*(println\(|Log\.d\(|System\.out\.print|TODO: remove)'; then
            echo "❌ 检测到调试代码或待办标记"
            exit 1
          fi

  size-check:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: PR 变更行数检查
        run: |
          LINES=$(git diff origin/${{ github.base_ref }}...HEAD --numstat | awk '{s+=$1+$2} END {print s}')
          echo "变更行数: $LINES"
          if [ "$LINES" -gt 400 ]; then
            echo "⚠️ PR 超过 400 行，审查效率会显著下降，建议拆分"
          fi
```

### 5. 一份高质量 Review 评论的完整示例

```markdown
🔴 blocking
`OrderDetailActivity` 在 `onCreate` 里直接调用了 `Api.getOrder()`。

这条路径会在主线程发起网络请求，在低端机上会造成启动期 300ms+ 的主线程阻塞，
直接劣化启动指标（我们监控 P90 启动耗时，阻塞超过 100ms 就会计入）。

建议改为：
```kotlin
private val viewModel: OrderDetailViewModel by viewModels()

override fun onCreate(savedInstanceState: Bundle?) {
    super.onCreate(savedInstanceState)
    lifecycleScope.launch {
        repeatOnLifecycle(Lifecycle.State.STARTED) {
            viewModel.uiState.collect { render(it) }
        }
    }
}
```
仓库里 `UserListActivity` 已经是这个模式，可以直接参考（见 `UserListViewModel`）。

### 6. Review 时长与质量的度量

#!/usr/bin/env bash
# scripts/review-metrics.sh —— 度量 review 响应速度与 PR 规模分布
set -euo pipefail

REPO="${1:-.}"

echo "===== 最近 30 天 PR review 响应时长 ====="
git log --since="30 days" --merges --pretty=format:'%H %ct' \
  | while read -r sha ts; do
      first_comment=$(
        git log "$sha" --pretty=format:'%ct' --skip=0 -1 2>/dev/null || echo ""
      )
      echo "$sha merged_at=$ts"
  done | head -20

echo
echo "===== PR 规模分布 ====="
git log --since="90 days" --pretty=format:'%H' \
  | while read -r sha; do
      git show --numstat --pretty=format:'' "$sha" 2>/dev/null \
        | awk 'NF==3 {s+=$1+$2} END {if (s>0) print s}'
    done \
  | awk '{ if ($1<=100) a++; else if ($1<=400) b++; else c++ }
         END { printf "≤100 行: %d\n100-400 行: %d\n>400 行: %d\n", a, b, c }'

## 常见问题 / 面试要点

**读者问：Code Review 的价值到底在哪？它能发现多少问题？**

**AI答：**

1. **数据要记准**（Google 的公开研究）：
   - Review 发现的缺陷中，**只有约 5%~10% 会导致生产事故**。
   - 所以"Review 是为了抓 bug"是**对价值的一次严重低估**。
2. **真实的三个目标**：
   - **知识传播**：新人通过 review 学到团队约定、领域知识、常见坑。**这是最大收益。**
   - **设计一致性**：保证同一类问题在项目里只有一种解法（不会出现 A 模块用 Hilt、B 模块手写 Dagger）。
   - **知识共享的副产品**：多一个人理解这段代码，Bus factor 提高，人员流动风险降低。
3. **不擅长发现的**：需要运行时才能暴露的问题（并发竞态、性能退化）、需求理解偏差（**代码写得对但做的是错的事**）。
4. **补充手段**：自动化测试抓功能缺陷，监控抓线上问题，**review 抓"设计问题"**。三者互补，**不能用 review 代替测试，也不能用测试代替 review**。
5. **面试话术**："我统计过我们团队的 review 结论，能直接导致线上事故的缺陷只占大概 5% 到 10%。所以我把 review 的定位放在'知识传播和设计一致性'上——确保团队里同类问题只有一种解法。对能自动检出的机械问题（格式、潜在泄漏、依赖漏洞），我们全部交给 CI，人只看需要判断力的部分。"

---

**读者问：怎么写出让作者能接受的 Review 评论？**

**AI答：**

1. **三段式：事实 → 影响 → 建议/提问**。缺任何一段都无效：
   - 只说事实（"这里在主线程做 IO"）——作者不知道有多严重。
   - 只说影响（"这会导致卡顿"）——作者不知道改哪。
   - 只说建议（"用协程"）——作者不知道为什么，会抵触。
2. **用"问句 + 表达不确定"代替"断言"**：
   - ✅ "我理解这里用 `GlobalScope` 是为了不受 `viewModel` 生命周期约束？但这会导致协程泄漏，我可能没理解到设计意图，能讲讲吗？"
   - ❌ "这里必须改，GlobalScope 是错的。"
   - **原理**：把判断权交还作者，作者会自己说服自己；这比被要求修改有效得多。
3. **区分严重度**，用标记明确：
   - 🔴 blocking（必须改）/ 🟡 suggestion（建议）/ 🔵 question（求解释）/ ⚪ nit（吹毛求疵）/ 💚 praise（表扬）
   - **规则：只有 blocking 阻塞合入**。如果一条 PR 里 blocking 超过 5 条，说明 PR 太大，该拆。
4. **给方向而不是只给答案**：
   - ❌ "改成 `viewModelScope`"
   - ✅ "建议放到 `viewModelScope` + IO 调度器，仓库里 `UserListViewModel` 是这个模式，可以直接参考"——**给出参考对象比给答案更容易被接受**。
5. **表扬要具体**：
   - ❌ "👍"
   - ✅ "这里用 sealed interface 建模，避免了 `loading && error != null` 的非法状态"——**具体的表扬会被复制，泛泛的不会**。
6. **克制**：**nit 不要超过 3 条**。满屏 nit 会让作者对 review 免疫，这是长期损害。
7. **面试话术**："我写 review 评论守三条：讲清事实、说清影响、给方向或者提问。最重要的是用问句——把判断权留给作者。因为 review 的目的是让作者理解，不是让作者服从。分级也很关键，只有 blocking 才阻塞合入，否则大家会学会忽略你的评论。"

---

**读者问：PR 太大怎么办？Reviewer 应该全部看完吗？**

**AI答：**

1. **数据**：变更超过 **400 行**，审查发现缺陷的效率**显著下降**——不是线性下降，是断崖。
2. **Reviewer 的正确做法**：
   - **不硬啃**。花 20 分钟扫一遍结构和 diff 概览，判断这个 PR 是否该拆。
   - **如果该拆，直接说"这个 PR 建议拆成 3 个：机械改动、依赖层、UI 层，先合机械改动"**——这是**最有价值的 review 结论**。
   - 拆完之后再认真 review 拆分后的部分。
3. **作者的拆分策略**：
   - **机械改动单独提**（格式化、自动重命名、依赖升级、代码生成）——**这些应该由 CI 检查，人不看**。
   - **功能改动单独提**。
   - **顺序**：先机械（易 approve），再功能（依赖前面的）。
4. **紧急情况**：线上事故的紧急修复可以先合后审，但**必须 24 小时内补审**。
5. **面试话术**："我的判断是：PR 超过 400 行，我不会硬看，因为那是在假装 review。我会先花 15 分钟看结构，如果发现能拆，会直接建议作者拆——这比我在一个 2000 行的 diff 里挑出三个 typo 有价值得多。"

---

**读者问：作者不接受 Review 意见，双方僵持了怎么办？**

**AI答：**

1. **先区分意见的类型**，很多僵持其实源于没分清：
   - **blocking（正确性/安全/架构方向）** —— 有客观依据，**坚持**。可以升级到技术负责人裁决。
   - **suggestion（风格/写法偏好）** —— **作者有权拒绝**。Reviewer 说"我觉得这样更好"，作者说"我这样是有原因的，因为 X"，那就够了。
   - **question（没看懂）** —— 作者必须回应。
2. **分歧处理三条路**：
   - **有数据** → 用数据裁决（压测、火焰图、基准测试）。
   - **可验证** → 约定一个**限时的小 PoC**（比如"我们各写 30 行跑个 benchmark，周三给结论"），避免变成口头辩论。
   - **纯偏好** → **作者决策**。作者对自己的实现有完整上下文，reviewer 只有片段。
3. **升级机制**：技术分歧超过 1 轮无法收敛 → 引入第三方（架构师/技术负责人）**当场裁决**，不在群里拉扯。
4. **根本原因往往不是技术**：僵持常来自"这件事的重要性认知不同"——reviewer 以为是 P0 问题，作者以为是 P2。**把评论的严重度标清楚**（blocking vs suggestion）能大幅减少这种僵持。
5. **不要在 PR 上硬扛**：把讨论移到线下或单独会议，PR 上只留结论。**PR 评论区不是辩论场。**
6. **面试话术**："我遇到过分歧，我的处理方式是先问自己：这是 correctness 问题还是风格问题？correctness 我一定坚持，风格问题作者说了算。如果是技术优劣之争且没有数据，我会建议各写个 30 行的 PoC 跑一下，用结果决定——这比谁说服谁有效。如果作者明确解释了设计意图且确实合理，我接受。review 的目的是让代码变好，不是让作者听我的。"

---

**读者问：面试怎么体现你的 Code Review 能力？**

**AI答：**

1. **讲机制而不只是讲"我会 review"**：
   - "我们把机械检查全部交给 CI——格式、静态检查、依赖漏洞、密钥检测、调试代码检测；人只看需要判断力的部分。"
   - "我们用评论分级，只有 blocking 阻塞合入，suggestion/question/nit 不阻塞。"
   - "PR 超过 400 行我们要求拆分，机械改动单独提。"
2. **讲你怎么帮人成长**：
   - "对新人我第一次会私下说，第二次才在 PR 上说——保护心理安全，也避免把人逼到不敢提交。"
   - "我给的具体建议都会带上仓库里的参考实现，比如'参考 UserListViewModel 的写法'，比直接给答案更容易被接受。"
3. **讲你推动的改进**（这是最好用的素材）：
   - "我们曾经 review 全是格式和命名讨论，我统计了一下，能导致生产事故的缺陷只占 5% 到 10%。所以我推动了把格式检查交给 ktlint，人只看正确性和架构。review 质量明显提升，新人也不再觉得 review 是在挑刺。"
   - "我引入了一个机制：review 超过 24 小时没响应，提交者可以直接 @ 到我。这解决了 PR 挂着没人看的问题。"
4. **讲一次你给出高质量评论的例子**：
   - 用三段式描述一个具体评论：事实（主线程 IO）→ 影响（劣化启动 P90）→ 建议（参考某处实现）。**这个结构本身就很能体现专业性。**
5. **避免的表述**：
   - ❌ "我 review 很仔细"（无信息量）。
   - ❌ "我会帮新人 review"（像在说自己很忙，不是能力）。
   - ❌ 只讲自己怎么挑刺，不讲怎么帮人。

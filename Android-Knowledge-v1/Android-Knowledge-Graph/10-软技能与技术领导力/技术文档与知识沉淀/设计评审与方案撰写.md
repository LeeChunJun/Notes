# 设计评审与方案撰写

## 一句话定义

技术方案文档是"**把一个技术决策变成可执行、可评审、可验收的说明书**"；设计评审是"**在投入开发之前，用集体的经验把方案的漏洞暴露出来**"的机制——两者合起来，是工程师从"写代码"走向"负责一个模块"的第一个台阶。

## 核心原理

### 1. 为什么需要方案评审

一句话：**代码写出来要几天，改架构要几个月。错误的架构决策的修复成本，会随实现程度指数级上升。**

```text
方案阶段          实现早期          实现中期          上线后
  │                  │                 │                │
  ▼                  ▼                 ▼                ▼
改方案: 1天        改方案: 3天      改方案: 2周       改方案: 2月+
重构成本 ────────────────────────────────────────────────►
```

**评审的真实价值**不是"让大家同意我的方案"，而是：

1. **让盲区暴露**：写方案的人一定看不到自己的盲区（"知识的诅咒"——你知道的东西已经看不出来了）。
2. **让方案可执行**：评审会强迫你把"我觉得这样行"变成"每一步怎么做、谁做、多久、怎么验收"。
3. **让决策可追溯**：评审纪要 + ADR 一起，构成完整的决策链路。
4. **让上下文共享**：评审是最有效的知识扩散方式，参与者会记住讨论过的东西。

### 2. 技术方案文档的标准结构

```markdown
# [模块/功能] 技术方案

- 作者：{姓名}
- 状态：草稿 | 评审中 | 已通过 | 已归档
- 评审人：{姓名}
- 日期：{YYYY-MM-DD}
- 关联需求：{JIRA/需求文档链接}

## 1. 背景与问题
（为什么现在要做这件事？现状有什么痛点？用数据说话）

## 2. 目标与非目标
（本次要达成什么？明确"不做什么"，防止范围蔓延）

## 3. 方案对比
（至少两个候选方案，按统一维度对比，附推荐结论与理由）

## 4. 推荐方案详细设计
（架构图、关键接口、时序、数据流、状态机、异常处理）

## 5. 影响面评估
（对现有模块、接口、数据库、线上兼容性的影响；改动清单）

## 6. 风险与兜底
（可能出什么问题？监控指标？降级/回滚方案？）

## 7. 排期与里程碑
（拆成可交付的阶段，每阶段有明确的验收标准）

## 8. 监控与验收
（上线后看哪些指标？灰度策略？什么条件算成功？）
```

**每一节的作用**：

| 章节 | 回答的问题 | 最常见的错误 |
| --- | --- | --- |
| 背景与问题 | 为什么要做？不做会怎样？ | 只写"优化一下架构"，没有数据和痛点 |
| 目标与非目标 | 做到什么程度就停？ | 不写非目标，评审时范围无限扩大 |
| 方案对比 | 为什么选这个不选那个？ | 只写一个方案，假装没有选择 |
| 详细设计 | 具体怎么实现？ | 只有架构图，没有接口和边界定义 |
| 影响面评估 | 会波及到谁？ | 漏掉老版本兼容，导致线上事故 |
| 风险与兜底 | 出问题怎么办？ | 完全不写，等出事才想 |
| 排期与里程碑 | 分几步交付？ | 一个大版本全做完，无法灰度 |
| 监控与验收 | 怎么算做成了？ | 没有量化成功标准，上线后无法判断 |

### 3. "目标与非目标"为什么最重要

这一节经常被省略，但它是**防止范围蔓延最有效的手段**。

```markdown
## 目标
1. 冷启动耗时从 2.1s 降到 1s 以内（P90）
2. 启动期崩溃率从 0.8% 降到 0.2% 以下
3. 新增的初始化框架不要求业务方改动现有代码

## 非目标
1. 不解决包体积问题（另立项目）
2. 不重构业务层架构（与本次无关）
3. 不支持 iOS（本次只针对 Android）
4. 不引入跨端方案（KMP 调研另开 ADR）
```

**为什么有效**：评审时一定会有人说"顺便把 X 也做了吧"，有了"非目标"这一节，你就有了一个**不带情绪的拒绝依据**——不是"我不想做"，而是"这明确不在本次范围内"。

### 4. 方案对比的正确姿势

**必须用同一套维度打分**，且**维度在对比之前就定好**（避免事后为了衬托自己的方案而改维度）。

```markdown
| 维度 | 权重 | 方案A: 引入 Hilt | 方案B: Koin | 方案C: 手写 Dagger |
| --- | --- | --- | --- | --- |
| 编译期开销 | 15% | 差（+8s） | 优（0s） | 中（+5s） |
| 运行时性能 | 10% | 优 | 良 | 优 |
| 编译期校验能力 | 20% | 优 | 差 | 优 |
| 学习成本 | 15% | 中 | 低 | 中 |
| 官方支持 | 20% | 优 | 良 | 良 |
| 多模块支持 | 20% | 优 | 良 | 差 |
| **加权总分** | 100% | **8.0** | **6.5** | **7.2** |

推荐：方案A（Hilt）。理由：官方支持与编译期校验权重最高；
虽有 8s 编译开销，但可通过 CI 分级缓存缓解。
```

**关键点**：

- **权重来自团队现状**，不是通用模板。团队小就降低"学习成本"权重，团队大就提高"多人协作一致性"权重。
- **保留落选方案的得分**，不要为了让自己方案胜出而把别的方案写得极差——资深面试官和同事一眼能看出来。
- **明确写出缓解措施**："虽然 +8s，但通过 CI 分级缓存 + 只在 CI 全量编译解决"。

### 5. 设计评审的流程与角色

```text
 ① 作者自评        ② 预审(1-2人)         ③ 正式评审              ④ 落地跟踪
 作者写方案   →   找 1-2 位相关同事   →  正式会议：           →  纪要 + Action Item
 走查一遍逻辑      过一遍方案          30min 讲方案            责任到人 + 时间点
                   提前收集反对意见      40min 讨论             下次评审会检查
                                   10min 结论与分工
```

**角色分工**：

- **Author**：讲方案、回答问题、记录结论。
- **Reviewer**：**提前读文档**并提前给意见（会上读文档是最糟的评审方式）。
- **Facilitator / 主持人**（Leader 岗必备）：控制时间、防止跑题、把"这个我喜欢"引向"我们担心的是什么"。
- **Decision Maker**：最终拍板的人。

**评审前必须做的三件事**：

1. **提前至少 1 天发出文档**。会上现读文档的评审，等于浪费所有人的时间。
2. **作者自己先过一遍"我哪里没想清楚"**，标出来邀请大家重点看——这会显著提升评审质量（心理学上的"预先示弱"反而增加被采纳概率）。
3. **提前收集反对意见**：私下问最可能反对的人，让他把反对意见提前提出来，避免会上无人反对、散会后一堆私下抱怨。

### 6. 常见争议的处理方式

| 争议类型 | 错误处理 | 正确处理 |
| --- | --- | --- |
| "我觉得方案太复杂" | 争论谁更聪明 | "我们评估过复杂度成本：A 方案多写 300 行代码，但减少 2 个运行时崩溃点的排查路径" |
| "以前不是这么做的" | "那是因为以前情况不同" | "对，当时是 X 约束，现在这个约束变了，所以这次调整" |
| 各方都有道理 | 各让一步，做个折中 | "我们能不能先做个 PoC 用真实数据验证一下？周三前给结论" |
| 无人反对但也没人认同 | 直接通过 | "谁愿意牵头实现第一个里程碑？"——沉默即是不认可 |
| 争论超过 15 分钟 | 现场辩论 | "记为 Action Item，指定 owner，X 日前给结论，下次评审直接进入结论" |

**核心心法**：

> **技术争议用数据裁决，偏好之争用实验裁决，无解之争用"谁先做"裁决。**
> 永远不要让会议室变成辩论赛——要么 30 分钟内收敛，要么转化为一个有 owner 和 deadline 的 Action Item。

### 7. 评审的产出物

1. **评审纪要**：结论（通过/修改后通过/不通过）+ 待办事项清单 + 决策要点。
2. **方案文档更新**：把评审意见吸收进去，版本号 +1。
3. **ADR**（当决策具有长期影响时）：见 [[../技术文档与知识沉淀/ADR架构决策记录]]。
4. **Action Item 跟踪**：责任到人 + 时间点，纳入下一次评审的检查项。

**最容易被忽略的是第 4 项**。没有跟踪的 Action Item 等于没开这个会。

### 4. 一个真实的"非目标"与"回滚"写法（面试可讲）

```markdown
## 非目标
1. **不重构网络层**——本次只解决启动期初始化，网络层重构会引入额外风险，另立 ADR。
2. **不要求业务方立即迁移**——新框架提供 Adapter 兼容老的 `initXxx()` 写法，
   存量初始化全部迁完预计需要 2 个版本，本次只保证新写法可用。

## 回滚
新增远端配置开关 `startup_new_framework_enabled`（默认 true）：
- 关闭后走老初始化路径，新框架不生效；
- 灰度期间监控启动耗时与崩溃率，若 P90 上升 > 15% 或崩溃率上升 > 0.05%，
  自动关闭开关并通知值班群。
```

## 常见问题 / 面试要点

**读者问：技术方案文档要写多详细？会不会写完代码都变了？**

**AI答：**

1. **详细度标准**：**详到"另一个人能照着实现，且实现出来和你的预期一致"**。
   - 够用的标准：接口签名、关键数据结构、时序、异常分支、边界条件都有交代。
   - 不够：只画一张架构图 + 几句业务描述。
2. **关于"写完代码都变了"**：
   - **会变很正常，而且应该变**——方案的价值在于**提前暴露问题**，如果一次过稿反而说明没认真想。
   - **但要区分两类改动**：
     - **实现细节调整**（变量名、内部算法）→ 改文档即可，甚至不用改。
     - **结构性调整**（模块划分、接口形态、依赖方向变了）→ **说明方案评审漏掉了东西**，要回头补 ADR 或更新方案，并复盘为什么评审没发现。
   - **经验法则**：如果方案在评审通过后**大改**，通常不是"开发理解错了"，而是**方案写得不够具体**，把不确定性留给了开发。
3. **控制篇幅**：Android 团队的一份方案控制在 **5-15 页**比较健康。超过 20 页通常意味着拆分不够，或者混入了不该在这份文档里的内容（比如详细接口文档应该用 OpenAPI/KDoc 单独维护）。
4. **面试话术**："我的判断标准是'实现者不需要再来问我'。如果实现时还要问问题，那要么是我没写清楚，要么是我不该一个人写方案。我见过方案 30 页、结果开发推翻重来的，根因就是把所有技术选型细节都堆在一起，没有区分'必须现在决定的'和'可以开发时再定的'。"

---

**读者问：评审会上没人提意见，方案就这么通过了，是不是说明方案没问题？**

**AI答：**

1. **不是**。沉默往往意味着三种情况：
   - **没读**（会前没时间看）→ 流程问题：文档要提前发，且会前 30 分钟不许现读。
   - **读不懂** → 表达问题：方案写得只有作者能懂。
   - **不敢提**（尤其 senior 提 junior 的方案、或者 boss 在场）→ 氛围问题：这是最危险的一种。
2. **怎么破**：
   - **设"提问优先"环节**：主持人事先声明"方案人先讲 10 分钟，之后所有人必须至少提一个问题（包括方案人自问）"。
   - **指定角色负责挑刺**：评审时安排一位"唱反调"角色（红队），专门负责找方案的漏洞，即使没有真实问题也要提出"我最担心什么"。
   - **匿名评审**：提前收集书面意见（Google 式的 Reviewer 匿名打分，能显著提高负面意见比例）。
   - **换时间/换形式**：如果面对面压力大，改为异步书面评审 + 30 分钟讨论。
3. **判断方案是否真被认可**：**看 Action Item 而不是看有没有人反对**。如果会上"一致通过"但没人愿意牵头第一个里程碑，那就是不认可。
4. **面试话术**："我特别关注评审的'沉默'问题。我们的做法是评审前先让参与者匿名写三个'我最担心的地方'，然后方案人先回答这些担心，再开始讨论。实践下来能挖出很多当面不会提的问题。"

---

**读者问：作为开发/技术负责人，怎么推动一场有效的技术评审？**

**AI答：**

1. **会前（最重要，决定评审质量）**：
   - **提前 1-2 天发文档**，明确请大家**提前阅读并把意见写在文档评论里**（而不是会上口头说）。
   - **私下预沟通**：找 1-2 个最可能持反对意见的人单独聊，把反对意见提前挖出来，避免会上僵持。
   - **作者自我暴露盲区**：在文档开头写"我特别不确定的是 X 和 Y，希望重点看"。这会显著提高评审的信息量。
   - **准备 3 分钟版本**：能在 3 分钟内讲清核心，说明你没把问题复杂化。
2. **会中**：
   - **先讲目标和非目标**，避免范围蔓延。
   - **主动讲方案对比与取舍**，不要等别人问"为什么不用 X"。
   - **把分歧显性化**："我理解大家担心的是 A，你有不同看法吗？"——沉默往往不是同意，是没被点名。
   - **控制时长**：每个议题最多 10 分钟，超时就转化为 Action Item。
   - **区分"阻塞项"和"建议"**：只有真正阻塞的才要求改，避免"什么都改一遍"导致方案永远定不下来。
3. **会后（最容易被忽略）**：
   - **当天发纪要**：结论 + Action Item + 责任人 + deadline。口头共识不算共识。
   - **更新方案文档**并标注版本。
   - **把长期影响的决策写成 ADR**（见 [[../技术文档与知识沉淀/ADR架构决策记录]]）。
   - **下次评审先检查上次的 Action Item**——这是让"评审"变成"闭环"的关键。
4. **Leader 视角的额外动作**：
   - **保护提出异议的人**，公开表扬挑刺的行为，让"唱反调"变成安全的。
   - **不要在方案人还在讲的时候打断提问**，会让人不敢充分准备。
   - **你的角色是收敛，不是裁决**——除非有明显的技术风险，否则尊重方案人的判断。
5. **面试话术**："我推动评审的三个关键动作是：会前私下找最可能反对的人聊一遍、把分歧显性化点名确认、会后当天发纪要并把 Action Item 挂到下次评审。坦白说，我最看重的产出不是'通过了'，而是 Action Item 是否被闭环——那才是评审真正在起作用。"

**读者问：方案被评审打回，怎么处理？**

**AI答：**

1. **先分清打回原因**：
   - **方案本身有缺陷**（漏了边界条件、影响面评估不全）→ 这是正常且有价值的，**改方案，不要辩解**。
   - **需求理解有偏差**（大家基于不同的需求理解在讨论）→ 这是最危险的情况，要**回头对齐需求**，而不是改方案去迎合。
   - **方向性争议**（认为该用另一种技术路线）→ 需要回到决策矩阵和 ADR 层面讨论，甚至可能推翻整个方案。
2. **正确反应**：
   - **不要在会上争辩**。先记录所有意见，判断哪些是"必须改"（blocking）、哪些是"建议"、哪些是"我不喜欢"。
   - **区分 blocking 和 preference** 是核心能力。**因为"我不喜欢 Room"而不改方案**是任性的；**因为"这里没考虑多进程写冲突"而改方案**是专业的。
   - **给出回应时间**：告诉评审人"我 X 日前给出修改版"，不要让讨论悬空。
   - **被反复打回 2 次以上**时，应该重新审视方案方向，或者引入第三方视角（找架构师/更资深的人预审）。
3. **重新提交时**：
   - **在文档里逐条列出对意见的处理**（接受/部分接受/不接受+理由），这让评审人看到意见被认真对待。
   - **不接受的要给理由**，尤其是 blocking 意见不接受时。
4. **面试话术**："被评审打回时我先做一件事：把意见分类成'必须改'和'我不太喜欢'。前者一定改，后者我会解释为什么保留——但不会因为对方不喜欢就改，因为那样方案就没有主人了。如果两次被同一类意见打回，说明是我的方案方向有问题，我会推倒重来。"

**读者问：面试中怎么体现"能写技术方案"的能力？**

**AI答：**

1. **准备一个你主导过的、有架构分量的方案**，用 **STAR + 量化** 讲：
   - **S/T**：什么背景、你要解决什么问题（要具体到业务影响）。
   - **A**：你评估了几个方案、维度是什么、结论是什么（**这里是展示决策能力的地方**）。
   - **R**：结果如何（量化）。
2. **模板**：
   ```text
   "我们的启动耗时 P90 是 2.1 秒，直接影响了新用户次日留存。
    我提了三个方案：全异步化、惰性加载、以及按优先级调度的启动任务框架。
    评估维度是：首屏可用时间、崩溃风险、SDK 兼容性和改造成本。
    最后选了按优先级调度，因为另外两个方案要么改造成本太高，要么会引入初始化时序问题。
    灰度一周后，P90 降到 1.05 秒，启动期崩溃率从 0.8% 降到 0.15%。
    同时我写了一份 ADR 记录这个决策和它的代价——SDK 初始化全部串行化后，
    我们不得不放弃了一个依赖早期初始化的实验功能。"
   ```
3. **必须能讲出"代价"**。只讲收益的方案是宣传稿；能讲出"这个方案让我们放弃了什么"的回答，才显得真实可信。
4. **能讲出方案"没做什么"（非目标）**：这是资深工程师的标志。比如"这次明确没有重构网络层，因为网络层的问题会用另一个方案解决，两件事混在一起会让风险不可控"。
5. **避坑**：不要讲"我写了个方案文档"这种没有信息量的描述，一定要讲到**决策和权衡**。

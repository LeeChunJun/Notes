# 技术债务识别与偿还

## 一句话定义

技术债务是"**当前代码实现中，为了短期速度而透支的未来开发成本**"；管理它分两步——**先用数据把它量化出来**（否则它永远排在功能需求后面），**再用一个可控的节奏偿还它**（否则它会一次性引爆）。

## 核心原理

### 1. 三类技术债务（Ward Cunningham 的经典分类）

| 类型 | 定义 | 特征 | 处理策略 |
| --- | --- | --- | --- |
| **审慎的债务**（Prudent） | **明知代价**但为短期速度主动借入 | 有意识、有计划、有还款窗口 | **正常偿还**，按计划还 |
| **鲁莽的债务**（Reckless） | 未来再重构就来不及了（"先凑合，以后再说"） | 无计划、无意识、利息在快速累积 | **最高优先级立即处理** |
| **意外的债务**（Inadvertent） | 环境变化导致原本合理的实现变得不合理 | 无意识、事后才发现 | **重新评估**，可能变成机会 |

**关键判断**：

- **审慎的债务**是**工程决策**，不是失败。例如"为了这个月的发布，先把支付逻辑硬编码，下个迭代抽象"——只要真的还了，它就是合理的。
- **鲁莽的债务**是最贵的，因为它的**利息以指数增长**：一个被 copy 了 50 次的坏设计，改动成本会随复制次数增长。
- **意外的债务**最容易被忽略：比如原本单机调用 Service 的代码，在引入多进程后变得不安全；原本单机同步的数据库，在引入多线程后出现竞态。**环境变了，债就产生了**。

### 2. "利息"模型：为什么债务会自己长大

```text
债务本金：改造这些代码所需的工时
债务利息：每单位时间因为债务导致的额外成本

利息来源：
  ├─ 每次新功能要在"坏"的地基上盖楼 → 越盖越难拆
  ├─ 每次改动都要理解"为什么这么写" → 认知成本累积
  ├─ 坏代码吸引更多坏代码（破窗效应）→ 熵增
  ├─ 新人踩坑 → 缺陷与返工
  └─ 编译慢、测试慢 → 全员每天损失
```

**一个具体例子**：

```kotlin
// 第 1 天（审慎）：为了赶进度，直接在 Activity 里请求网络
class OrderActivity : AppCompatActivity() {
    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        Thread {
            val order = Api.getOrder(orderId)
            runOnUiThread { binding.tvOrder.text = order.title }
        }.start()
    }
}

// 3 个月后：需求要加"下拉刷新"、"离线缓存"、"重试"、��"登录态过期处理"
// → 同一段代码被复制到 4 个页面
// → 每次都要改 4 处，其中 1 处经常漏改 → 线上事故
```

**利息的体现**：改动从"改 1 处"变成"改 4 处"，且**因为漏改产生缺陷**——缺陷的成本远高于重构成本。

### 3. 量化：从"感觉代码很烂"到"这里有 47 万"

**主观感受不能推动排期，数字可以。**

| 维度 | 指标 | 采集方式 | 说明 |
| --- | --- | --- | --- |
| **复杂度** | 圈复杂度（CC）、认知复杂度 | SonarQube / detekt / PMD | 单个函数 CC > 15 视为高风险 |
| **重复率** | 重复代码行占比 | SonarQube（Duplicated Lines） | > 5% 需要关注 |
| **可维护性** | Maintainability Rating | SonarQube | A-E 五档 |
| **测试覆盖** | 行覆盖率 / 分支覆盖率 | JaCoCo | 核心模块低于 60% 是红线 |
| **构建效率** | 全量编译时长 | CI 统计 | 超过 10 分钟会抑制重构意愿 |
| **缺陷密度** | 千行代码缺陷数 | Jira / Sonar | 缺陷集中的模块即债务热点 |
| **变更成本** | 某模块的"改动耗时中位数" | Git + Jira 关联分析 | **最真实的指标** |
| **耦合度** | 模块间依赖数 | ArchUnit / jdeps | 循环依赖是债务的信号 |
| **遗留代码** | 近 6 个月未变更的文件数 | git log | 冻结代码也是风险 |
| **文档缺失** | 无 README / 无注释的公共 API | 自定义脚本 | 影响上手成本 |

**最被低估但最有说服力的指标**：**模块的实际改动耗时**。

> 如果 A 模块的每次改动中位数是 0.5 天，而 B 模块是 4 天，那么 B 模块就有 8 倍于 A 的"债务利息"。这个数字比任何代码质量工具的评分都有说服力，因为它直接换算成了**业务成本**。

**计算"债务利息总额"给老板看**：

```text
年利息 = Σ(每个热点模块的月均改动次数 × 每次多花的时间) × 12

例：3 个热点模块，月均改动 20 次，每次多花 2 小时
年利息 = 3 × 20 × 2h × 12 = 1440 小时 ≈ 3 个人月 ≈ 30 万人民币
一次性重构成本 = 15 人日 ≈ 3 万

结论：再拖 1 个月，利息就超过了重构成本。
```

**这个换算方式是说服管理层最有效的手段**——它把技术话题翻译成了钱。

### 4. 识别手段：怎么找到热点

```text
                    ┌─────────────────────────┐
                    │   技术债务热点识别        │
                    └────────────┬────────────┘
         ┌───────────────┬───────┴───────┬────────────────┐
         ▼               ▼               ▼                ▼
    静态分析         动态指标         历史考古          人的直觉
  SonarQube/       崩溃率/ANR       git log/blame     技术债
  detekt/PMD      改 动 耗 时       "这块为什么      专项会
  复杂度/重复率    圈复杂度热点      这么写"          (债务盘点)
```

**四种手段要结合**：

1. **静态分析**：SonarQube 的 "Hotspots"（SonarQube 4.6+）专门标记"**修改风险高但还没人动过**"的代码——这是最有价值的清单。
2. **动态指标**：线上崩溃堆栈的 Top N 函数，往往就是复杂度最高的地方。
3. **历史考古**：`git log -p <file>` 看一个文件被改了多少次、改动是否总在"打补丁"。**改动次数多且总在同一处打补丁 = 典型的鲁莽债务**。
4. **人的直觉**：**技术债专项会**（Tech Debt Workshop）让团队成员匿名列出"你最不想碰的代码"。这个清单往往和静态分析高度重合，而且**更容易推动行动**（因为是团队自己的判断，不是工具给的评分）。

**黄金技巧：把静态工具的 Hotspot 清单和"大家最不想碰的清单"取交集**，这个交集就是优先偿还目标——既有客观数据支撑，又有团队共识。

### 5. 偿还策略

#### 策略一：绞杀者模式（Strangler Fig Pattern）

**核心思想**：不要重写整个模块，而是**在它周围一圈一圈地建新实现，逐步把流量切过去，最后把老代码拔掉**。

```text
阶段 1: 新建 OrderRepository（新实现），老 Activity 仍调老逻辑
阶段 2: 路由层按开关/百分比把 10% 流量导向新实现
阶段 3: 逐步放量 10% → 50% → 100%，监控指标对比
阶段 4: 稳定运行 2 个版本后，删除老实现
```

**优点**：每一步都可上线、可回滚、风险可控。
**缺点**：需要长期维护新旧两套（这本身也是债）。

#### 策略二：并行改造（Feature Flag / Strangler at Edge）

用功能开关控制新旧逻辑：

```kotlin
class PaymentHandler(
    private val newImpl: NewPaymentProcessor,
    private val oldImpl: LegacyPaymentProcessor,
) {
    suspend fun pay(order: Order): Result {
        return if (FeatureFlags.useNewPayment) {
            newImpl.pay(order)      // 新实现
        } else {
            oldImpl.pay(order)      // 老实现
        }
    }
}
```

**关键**：`FeatureFlags` 必须能**远端下发**（见 [[../../08-企业级工程与运维/日志与监控/远端配置]]），出事 1 分钟内能关掉。

#### 策略三：逐步替换（Branch by Abstraction）

不想双线运行时的替代方案：

```
第 1 步: 在老实现外包一层接口（不改变内部逻辑）
第 2 步: 把所有调用方改为依赖接口
第 3 步: 在接口后面换成新实现（老实现代码删除）
```

**优点**：不需要双线运行，不需要开关。
**缺点**：中间态需要老实现能被接口完全覆盖。

#### 策略四：预算化偿还（20% 规则 / Debt Budget）

**核心思想**：把技术债当作**固定成本**，而不是"等有空再还"。

- **20% 规则**：每个迭代固定拿出 20% 的容量做技术债偿还（不接新需求）。
- **Debt Budget**（Martin Fowler）：把偿还时间**记入预算**，和其他需求**竞争排期**。想加功能？可以，但要同时说明它会推迟多少债务偿还。
- **收益可视化**：每期公开"已偿还债务 X 小时 / 累计 Y"。

**关键**：技术债偿还**必须进入迭代计划**，而不是"利用空闲时间"。**空闲时间永远不存在。**

### 6. 优先级排序：影响 × 成本矩阵

```text
              偿还成本低
                  │
     ┌────────────┴────────────┐
     │                         │
  高 │   ① 立即偿还            │  ② 计划偿还
 影  │   (Hotspot + 高频改动)  │  (有影响但改动少)
 响  │   例：Activity 里的网络请求│  例：重复的工具类
     │                         │
     ├─────────────────────────┤
     │                         │
  低 │   ③ 顺手清理            │  ④ 暂不处理
 影  │   (改这块时顺带改)      │  (记录在案，不投入)
 响  │   例：局部命名混乱      │  例：老模块的注释格式
     │                         │
     └─────────────────────────┘
                  │
              偿还成本高
```

**但真正的排序依据是"利息"**：

```text
优先级 = 影响面 × 改动频率 × (修复的确定性 - 实施风险)
```

**最高优先级永远是**：**线上正在崩溃 / 正在出事故的热点**。技术债偿还的第一优先级永远是**止血**，不是优化。

### 7. 推动偿还：怎么说服老板

**四种有效策略**：

1. **用钱说话**：把利息换算成人月成本（见上文）。"这个模块每年多花 3 个人月。"
2. **用事故说话**：把技术债与线上故障关联。"过去 6 个月 12 个 P1 事故，其中 8 个的根因指向同一个模块。这个模块去年欠了 200 小时的债。"
3. **用对比说话**：找一个**已经偿还过的模块**做前后对比。"订单模块我们花 10 天重构后，改动耗时从 3 天降到 0.5 天，此后半年改了 15 次，节省约 37 天。"
4. **用渐进降低风险说服**：不要一次申请 3 个月重构，先做**一个 3 天的试点**，拿到数据后再申请。

**关键话术**：不要把技术债说成"代码不优雅"（老板听不懂），要说成"**我们每接一个需求都要多花 X 天，一年下来是 Y 个人月**"。

### 8. 反模式

| 反模式 | 表现 | 后果 |
| --- | --- | --- |
| **永远"有空再说"** | 每次排期都被功能需求挤掉 | 债务利息持续累积，最终大爆炸 |
| **大爆炸重写** | 停掉新功能 3 个月全面重写 | 通常失败率高，业务方失去信任 |
| **无记录的债务** | 没人知道欠了多少、在哪 | 靠记忆管理，遗忘即失控 |
| **只清理代码格式** | 用格式化工具"偿还债务" | 债务是**结构问题**，不是格式问题 |
| **追求零债务** | 要求所有指标满分 | 过度工程，团队丧失交付能力 |
| **技术债专项月** | 一年一次集中还债 | 债务在专项月之间疯狂累积 |
| **归咎个人** | "这是某某当时写烂的" | 破坏信任，无复盘价值 |

### 2. 债务热点的量化脚本

```bash
#!/usr/bin/env bash
# scripts/tech-debt-hotspots.sh —— 用 git 历史找出"改动频繁且总在打补丁"的热点文件
set -euo pipefail

SINCE="${1:-6.months}"

echo "== 改动次数 Top 30 =="
git log --since="$SINCE" --name-only --pretty=format: \
  | grep -E '\.(kt|java)$' \
  | sort | uniq -c | sort -rn | head -30

echo
echo "== 冲突/回滚痕迹最多的文件（补丁倾向）=="
git log --since="$SINCE" --grep='Revert\|revert\|fix\|Fix\|hotfix\|HOTFIX' \
  --name-only --pretty=format: \
  | grep -E '\.(kt|java)$' | sort | uniq -c | sort -rn | head -20

echo
echo "== 近 6 个月未变更但仍在编译的模块（冻结区）=="
find . -name '*.kt' -not -path '*/build/*' -newermt "$(date -d '-6 months' +%Y-%m-%d)" | \
  sed 's|/[^/]*$||' | sort -u | head -20
```

### 3. 债务改造前后的对比度量脚本

```kotlin
// scripts/ModuleChangeCost.kt —— 用 git 历史估算模块的"改动成本"
// 思路：同一模块每次改动的提交数越多、平均 diff 越大 → 改动成本越高

data class ModuleStat(
    val module: String,
    val commitCount: Int,
    val avgFilesPerCommit: Double,
    val conflictCount: Int,
    val revertCount: Int,
)

object ChangeCostAnalyzer {
    fun analyze(repoRoot: String, since: String = "6.months"): List<ModuleStat> {
        // 实际实现可调用 git log --numstat 并按路径前缀聚合
        val commits = runCatching {
            ProcessBuilder(
                "git", "log", "--since=$since", "--numstat", "--pretty=format:%H"
            ).directory(File(repoRoot)).redirectErrorStream(true).start()
        }.getOrElse { return emptyList() }

        val output = commits.inputStream.bufferedReader().readText()
        return output
            .split("\n\n")
            .filter { it.isNotBlank() }
            .map { block ->
                val files = block.lines().drop(1).filter { it.contains('\t') }
                ModuleStat(
                    module = files.map { it.substringBefore('\t').substringBeforeLast('/') }
                        .groupingBy { it }.eachCount().maxByOrNull { it.value }?.key ?: "unknown",
                    commitCount = 1,
                    avgFilesPerCommit = files.size.toDouble(),
                    conflictCount = 0,
                    revertCount = 0,
                )
            }
            .groupBy { it.module }
            .map { (m, list) ->
                m.copy(
                    commitCount = list.size,
                    avgFilesPerCommit = list.map { it.avgFilesPerCommit }.average(),
                )
            }
            .sortedByDescending { it.commitCount }
    }
}
```

### 4. 绞杀者模式的实施骨架

```kotlin
// 阶段 1：为老实现包一层接口（不改动内部逻辑）
interface OrderRepository {
    suspend fun getOrder(id: String): Order
}

// 阶段 2：老实现适配到接口
class LegacyOrderRepository @Inject constructor(
    private val api: LegacyOrderApi,
) : OrderRepository {
    override suspend fun getOrder(id: String): Order = api.fetch(id).toOrder()
}

// 阶段 3：新实现（绞杀者）
class NewOrderRepository @Inject constructor(
    private val dao: OrderDao,
    private val api: OrderApi,
) : OrderRepository {
    override suspend fun getOrder(id: String): Order {
        // 本地优先 + 网络刷新
        val cached = dao.get(id)
        val fresh = api.get(id).also { dao.upsert(it) }
        return fresh.copy(fromCache = cached != null)
    }
}

// 阶段 4：路由层按远端开关切流
@Singleton
class OrderRepositoryRouter @Inject constructor(
    private val newImpl: NewOrderRepository,
    private val legacyImpl: LegacyOrderRepository,
    private val config: FeatureFlags,
) : OrderRepository {
    override suspend fun getOrder(id: String): Order =
        if (config.useNewOrderRepo) newImpl.getOrder(id) else legacyImpl.getOrder(id)
}
```

### 5. 一次偿还的完整记录（用于汇报与 ADR）

```markdown
## 技术债偿还报告：Order 模块

**周期**：2026-03-01 ~ 2026-03-12（10 工作日）
**关联债务**：TD-001, TD-003
**负责人**：@张三

### 改造范围
1. 抽出 `OrderRepository` 接口，4 个页面的网络请求统一走 Repository
2. 引入统一的超时/重试/错误映射策略（`core/net`）

4. 移除 4 处重复的轮询/倒计时实现

### 量化效果（改造前 6 个月 vs 改造后 6 个月）

| 指标 | 改造前 | 改造后 | 变化 |
| --- | --- | --- | --- |
| 月均改动次数 | 20 | 23 | +15% |

| 该模块相关线上缺陷 | 12 起 | 3 起 | **-75%** |
| 崩溃率（订单模块） | 0.31% | 0.09% | **-71%** |

- 结论：**投入产出比约 1:40**

### 遗留
- `legacy/OrderActivity` 将在下个版本随老业务流程下线时删除（计划 2026-05）
```

## 常见问题 / 面试要点

**读者问：什么是技术债务？怎么判断我们项目里的技术债？**

**AI答：**

1. **定义**：技术债务是"**为了短期交付速度而做出的、未来需要额外付出代价才能消除的技术决策的累积**"。关键是它必须**与速度有关**——为了长期收益主动做的复杂设计（如过早优化、多层抽象）**不是**技术债务，是投资。
2. **三类**（Ward Cunningham）：
   - **审慎的债务**：明知代价、主动借入、有还款计划 → **这是工程决策，不是失败**。
   - **鲁棒的债务**："先凑合，以后再说"，无意识、无计划 → **最危险**。
   - **意外的债务**：环境变化（多进程、多线程、团队扩张）让原本合理的实现变得不合理 → **最容易被忽略**。
3. **判断方法**：
   - **静态**：SonarQube / detekt 的复杂度、重复率、维护性评分。
   - **动态**：某模块的改动耗时中位数、缺陷密度、崩溃堆栈 Top N。
   - **历史**：`git log` 看某文件被反复打补丁。
   - **人的直觉**：技术债专项会，团队成员列出"最不想碰的代码"。
4. **最实用的单一指标**：**"某模块每次改动多花多少时间"**。它把技术问题直接翻译成了业务成本，最能推动行动。
5. **面试话术**："我用三个信号判断是不是技术债：改这块要多花时间、改这块容易出 bug、新人接手会反复问'为什么这么写'。第三个信号最重要，因为它反映的是**认知负担**，而认知负担才是技术债真正的成本。"

---

**读者问：技术债怎么量化？怎么才能说服老板投入资源去重构？**

**AI答：**

1. **量化的核心：换算成业务成本，不能停留在代码质量评分。**
   - **公式**：`年利息 = Σ(模块月均改动次数 × 单次多花时间) × 12`
   - **例**：3 个热点模块，月均改 20 次，每次多花 2 小时 → 年利息 1440 小时 ≈ **3 个人月**。
   - **重构成本**：15 人日 ≈ 3 万。**结论：拖一个月利息就超过重构成本。**
2. **补充量化维度**（做成一页看板）：
   - 复杂度：圈复杂度、认知复杂度、重复代码率
   - 测试覆盖：核心模块行/分支覆盖率
   - 构建效率：全量编译时长、CI 队列等待
   - 缺陷密度：千行代码缺陷数、该模块线上事故数
   - 耦合度：模块间依赖与循环依赖数
   - **变更成本：模块改动耗时中位数（最有说服力）**
3. **说服策略（按有效性排序）**：
   - **用钱说话**：把利息换算成人月成本。
   - **用事故说话**："过去 6 个月 12 个 P1，8 个根因指向同一模块。"
   - **用对比说话**：找一个已偿还的模块做前后对比（"改动耗时从 3 天降到 0.5 天"）。
   - **用试点说话**：先申请 3 天做试点，拿到数据再申请正式排期。
4. **关键话术转换**：
   - ❌ "这段代码很烂，应该重构。"
   - ✅ "订单模块每次需求改动要多花 2 天，一年 20 次需求，合计 40 人日。这 40 人日本可以做 3 个版本的迭代。"
5. **不要一次申请大排期**：先做**一个模块的试点**，拿到"改动耗时 -75%、缺陷 -75%"的数据，再用这个数据推动全面偿还。**一个成功案例比十次论证更有力。**
6. **面试话术**："我发现技术债的沟通有个关键点：不要谈代码质量指标，老板听不懂也不在乎。要谈'每次改动多花几天，一年多少次'。我们用这个方法成功推动了一次偿还——改造后月均改动次数反而上升了 15%（说明大家更敢改了），但单次成本降了 75%，年化节省 414 人日。"

---

**读者问：技术债应该什么时候还？怎么安排排期？**

**AI答：**

1. **三条偿还时机**：
   - **立刻还（止血）**：线上正在崩溃/出事故的热点 —— **第一优先级永远是止血，不是优化**。
   - **计划还（排期）**：高频改动区的结构性债务 —— 纳入迭代，占用固定额度。
   - **顺手还（搭车）**：改动某块代码时，顺带清理局部问题 —— 边际成本最低的方式。
2. **排期机制**：
   - **20% 规则**：每个迭代固定 20% 容量做技术债。
   - **Debt Budget**：把偿还工时记入预算，和新需求**竞争排期**——想加功能？可以，但要说明它会推迟多少偿还。
   - **专项迭代**：每季度 1 个技术债迭代（但不能只有专项，债务会在专项之间疯狂累积）。
   - **关键**：偿还**必须进迭代计划**。"有空就做"= 永远不做。
3. **偿还策略选择**：
   | 场景 | 策略 |
   | --- | --- |
   | 遗留模块要整体换掉 | **绞杀者模式**（一圈圈切流量，最后拔掉） |
   | 需要灰度、可随时回滚 | **并行改造 + Feature Flag** |
   | 小范围重构、不想双线运行 | **Branch by Abstraction**（包接口 → 换实现） |
   | 老代码即将随版本下线 | **不要还**（记录在案，等它自然死亡） |
4. **最大的风险**：**大爆炸重写**。停掉 3 个月业务全面重写，通常结局是：业务方失去信任 → 新旧系统数据不一致 → 上线延期 → 重写失败。**绞杀者模式**虽然慢，但是每一步可上线、可回滚。
5. **面试话术**："我用一个原则判断要不要还：**这块代码还在高频改吗？改的人多吗？** 如果还在被频繁修改，那就值得优先还；如果已经半年没人动过、且计划随老版本下线，那就不值得投入——技术债有时候的正确答案是'让它死'。"

---

**读者问：重构和技术债有什么区别？什么是"过度重构"？**

**AI答：**

1. **区别**：
   - **重构**：**不改变外部可观察行为**，只改善内部结构。
   - **技术债偿还**：可能**改变外部行为**（比如把 4 个页面的接口统一成 1 个，接口变了）。
   - 所以"偿还技术债"经常不是纯粹的重构，它包含**行为变更**，风险更高，需要测试与灰度。
2. **过度重构的信号**：
   - 重构后**业务代码行数没减少甚至变多**（抽象层越加越多）。
   - 出现了**只有它自己用的接口/基类**（为抽象而抽象）。
   - **一个类只有一个实现且没有测试**，为它建接口是为了测试而测试（应该直接测实现）。
   - **新人需要读更多代码才能理解**——抽象增加了认知负担而不是减少。
   - 重构期间**没有任何可交付的业务价值**产生，业务方连续两个迭代看不到东西，信任就开始流失。
3. **判断抽象是否值得**（"Rule of Three"）：
   - **第一次**出现相似代码 → 直接复制，或加个小工具函数。
   - **第二次**出现 → 提取公共方法。
   - **第三次**出现 → 才考虑抽象成接口/基类。
   - 原因：前两次时你**还不知道**真正的共性是什么，过早抽象往往抽错了维度。
4. **Android 领域的常见过度设计**：
   - 为每个 Activity 建一个 BaseActivity，最后所有 Activity 都继承它，且基类里塞满了与业务无关的工具方法。
   - 为"以后可能要换数据源"而在每个 Repository 上包一层接口，实际只有一个实现。
   - 自研一套 DI/网络/图片库，最后维护成本远超直接用官方库。
5. **面试话术**："我判断重构值不值得的标准是：**重构后新人理解这块代码的时间是否变短**。如果只是文件变多了、层数变深了，但理解成本没降，那这不是重构，是把复杂度搬了个地方。我们团队有一条规矩：非静态的公共接口至少要有两个实现或两个真实调用场景，否则不进主干。"

---

**读者问：技术债怎么在团队里推动？团队成员不配合怎么办？**

**AI答：**

1. **先解决"认知差"**：大部分不配合不是因为懒，而是**没意识到技术债的存在和代价**。
   - 让具体的人**亲自感受**：安排一个改动频繁的模块由新人来改，现场计时。**亲身经历比任何说服都有效。**
   - 用**数据**而非形容："这个模块上次改动花了 4 天"比"这个模块很乱"有用一百倍。
2. **不要让人"额外"还债**：
   - 偿还工作必须**进入迭代计划、占用正式工时**，而不是"在功能需求之外挤时间"。后者永远被挤掉。
   - **认领制**：让团队成员**自己认领**想还的债（通常是他们最痛的），而不是指派。**自己提的债，才有动力还完。**
3. **降低偿还的门槛**：
   - 把大债**拆成可独立交付的小块**（每次 3-5 天），让人看到进度。
   - 优先还**"天天被碰到"**的债，收益体感最强。
4. **建立正反馈**：
   - **公开成果**：每期公示"本期偿还 X 小时，热点模块改动耗时 -30%"。
   - **把偿还结果和业务指标挂钩**（构建时长、需求交付周期、事故数），让技术工作被业务看见。
5. **处理"不配合"的两种情况**：
   - **认知问题** → 用上面的方式解决。
   - **优先级问题**（ leader 认为技术债不重要）→ **不要技术层面硬争**，而是找到业务痛点（需求交付慢、线上事故多、招人难）把它翻译成业务语言。技术债务很少是因为工程师懒而积累的，通常是因为**业务永远更急**——那就要在**排期机制**上解决，而不是在个人层面解决。
6. **Leader 视角**：**技术债的偿还本质上是"你作为 leader 如何分配团队的注意力"**。如果每个迭代都是 100% 业务需求，那技术债永远不会被偿还，而且团队会慢慢失去成长，最终竞争力下降。**留出 15-20% 是必须付的成本，不是浪费。**
7. **面试话术**："推动技术债偿还我踩过最大的坑是：把它当成额外工作。后来改成在迭代计划里明确划出 20% 的额度，并且让团队成员自己认领他们最痛的模块，效果完全不一样——认领的债，还款率接近 100%。"

---

**读者问：技术债和"代码写得烂"、"历史遗留问题"是一回事吗？**

**AI答：**

1. **不是一回事，这三个概念常被混用，但处理方式完全不同**：

| 说法 | 真实含义 | 处理方式 |
| --- | --- | --- |
| **技术债** | **为短期速度主动透支的未来成本**（有意识、有代价） | 排期偿还 |
| **代码写得烂** | 代码质量问题，**不一定有未来成本**（可能只是不符合你的审美） | 顺手改，别当债 |
| **历史遗留问题** | **中性描述**，指"以前留下的" | 先判断它是不是债 |

2. **判别标准只有一个：它有"利息"吗？**
   - **有利息** → 是技术债，必须管理。利息 = **每次改动这个模块要多花的时间 + 它贡献的线上事故数**。
   - **无利息** → 只是"不好看"，不值得专门排期。
   - **例子**：
     - "这个类 800 行、圈复杂度 40" —— 如果**没人改它**，无利息，不是债；如果它**每月被改 5 次**，那就有 5 次/月 × 每次多花 2 小时的利息，**是债**。
     - "命名用拼音" —— 无利息，不是债。
     - "支付逻辑直接写在 Activity 里，4 个页面各抄一份" —— 利息极高（漏改 → 事故），**是债**。

3. **"历史遗留"是个中性词，不该用来推卸责任**：
   - "这是历史遗留问题" 在团队里常被用作"我不想改"的托词。
   - 正确说法："这个模块改动成本高（具体数字），我在 P2 队列，Q3 偿还"——**承认它、排期它**。
   - **如果一个模块永远挂着"历史遗留"的标签，说明的是治理机制失效，不是历史的问题。**

4. **不是债的情况，用别的机制处理**（别占人工排期）：
   - **格式问题** → ktlint / Spotless **自动修复**。
   - **Lint 能查的问题** → 配 CI 卡点。
   - **注释缺失** → 靠 Code Review 要求。

5. **一个实用判断**：**"如果这个模块明天就要下线，还值不值得还？"**
   - 不值得 → 不要投入，记一笔账，等它自然死亡。
   - 值得 → 纳入偿还排期。

6. **面试话术**："我不接受'历史遗留'这个说法当理由。我会先算这个模块的利息——月均改动次数乘以每次多花的时间，以及它贡献了多少线上事故。有利息就是债，进排期还；没利息的只是代码质量问题，靠 lint 和格式化工具自动处理。如果一个模块永远挂着'历史遗留'的标签，说明的是我们的治理机制出了问题，不是历史的问题。"

# 状态管理

## 一句话定义

Compose 的状态管理就是回答三个问题：**状态存在哪里**（`remember` / `rememberSaveable` / `ViewModel`）、**谁读谁写**（状态提升）、**副作用在哪执行**（`LaunchedEffect` / `SideEffect` / `DisposableEffect`）。核心原则是：**状态向下流动、事件向上流动**，UI 只是状态的纯函数渲染结果。

## 核心原理

### 1. 状态 vs 事件

| 概念 | 定义 | 例子 | 特征 |
| --- | --- | --- | --- |
| **状态（State）** | 描述"**现在是什么样**" | 文本框内容、加载中、错误信息、选中项 | **可重复观察、可重放**；界面直接由它渲染 |
| **事件（Event）** | 描述"**发生了什么**" | 点击了提交、显示一次 Toast、导航到下一页 | **一次性消费**；不能靠"再渲染一次"复现 |

**错误做法：把事件塞进状态**。

```kotlin
// ❌ 旋转屏幕后 Toast 会再弹一次；重组也可能重复触发
data class UiState(
    val showToast: Boolean = false,
    val message: String = ""
)
```

**正确做法：事件走独立的通道**。

```kotlin
// ✅ 事件用 Channel / SharedFlow，一次性消费
class MyViewModel {
    private val _events = Channel<MyEvent>(Channel.BUFFERED)
    val events = _events.receiveAsFlow()

    fun onSubmit() {
        viewModelScope.launch { _events.send(MyEvent.ShowToast("提交成功")) }
    }
}

sealed interface MyEvent {
    data class ShowToast(val message: String) : MyEvent
    data object NavigateBack : MyEvent
}
```

**判断口诀**：
- 状态 → 用 `State` / `StateFlow` / `MutableState`；
- 事件 → 用 `Channel` / `SharedFlow`，且**必须一次性消费**。

### 2. 状态提升（State Hoisting）

**定义**：把状态从子 composable "提到"更高的、可复用的层级，使子 composable 变成**无状态（stateless）**的纯渲染函数。

```text
状态提升前（有状态）                    状态提升后（无状态）
─────────────────────                  ─────────────────────
@Composable                            @Composable
fun Counter() {                        fun Counter(count: Int, onPlus: () -> Unit) {
    var count by remember { 0 }            Text("Count: $count")
    Text("Count: $count")                 Button(onClick = onPlus) { Text("+") }
    Button(onClick = { count++ }) {      }
        Text("+")                     }
}
```

**提升后的三个好处**：
1. **可复用**：同一个无状态 composable 可以在多处使用不同状态。
2. **可测试**：预览和测试时直接传值，不需要模拟交互。
3. **单一真相源**：状态只有一份，避免"局部状态和全局状态不一致"。

**配套原则**（官方三原则）：
1. **状态提升到最接近使用它的地方**（不是越高越好）。
2. **状态应该只有一个来源**（single source of truth）。
3. **状态尽可能对使用者不可见**，通过回调暴露修改入口。

### 3. 状态的存放位置对比

```text
┌────────────────────────────────────────────────────────────────┐
│  remember          → 内存，配置变更丢失，进程死亡丢失            │
│  rememberSaveable → 内存 + SavedState，配置变更保留              │
│  ViewModel        → 内存 + 配置变更保留，进程死亡也丢失（除非 SavedStateHandle）│
│  DataStore/Room   → 磁盘，永久保留                              │
└────────────────────────────────────────────────────────────────┘
```

| API | 生命周期 | 适用场景 |
| --- | --- | --- |
| `remember { }` | 组合存续期间 | 纯 UI 状态：展开/收起、动画进度、临时筛选条件 |
| `rememberSaveable { }` | 组合存续 + 配置变更（通过 `SavedStateRegistry`） | 需要在旋转后保留的：滚动位置、Tab 索引、输入框内容 |
| `ViewModel` | Activity/Fragment 生命周期 | 业务状态：列表数据、加载状态、网络请求 |
| `rememberCoroutineScope` | 组合存续 | 绑定组合生命周期的协程作用域 |

### 4. remember 与 rememberSaveable

```kotlin
// remember：只在组合存续期间保留，旋转屏幕后重新执行 → 值丢失
val scrollPosition = remember { mutableIntStateOf(0) }

// rememberSaveable：通过 SaveableStateRegistry 保存，旋转屏幕后恢复
val scrollPosition = rememberSaveable { mutableIntStateOf(0) }
```

**`rememberSaveable` 的工作原理**：

```text
Composition 结束
   │
   ├─ 遍历所有 rememberSaveable 的槽位
   ├─ 用 Saver 把值转换成可序列化的类型（Bundle 能存的类型）
   └─ 存入 Activity/Fragment 的 savedInstanceState

进程/Activity 重建
   │
   ├─ 从 savedInstanceState 取出
   ├─ 用 Saver 反序列化
   └─ 放回 rememberSaveable 的槽位
```

**支持的类型**：基本类型、`String`、`Parcelable`、`Serializable`、`Bundle`、`SparseArray`、以及任何实现了 `Saver` 的类型。

**自定义 Saver**：

```kotlin
// 保存复杂对象
val user = rememberSaveable(
    stateSaver = UserSaver   // 或 userSaver = User::Saver
) { mutableStateOf(User(1, "Tom")) }

// 或者用 listSaver
val users = rememberSaveable(saver = listSaver(
    save = { listOf(it.id, it.name) },
    restore = { User(it[0] as Int, it[1] as String) }
)) { mutableStateOf(listOf<User>()) }
```

**常见坑**：
1. `rememberSaveable` 的值必须**能被 Saver 序列化**。放一个 `View` 或 `Bitmap` 进去会崩（`IllegalArgumentException: Cannot save ...`）。
2. `rememberSaveable` **不保存大数据**：`savedInstanceState` 有大小限制（Binder 事务约 1MB），超出会 `TransactionTooLargeException`。
3. `rememberSaveable` 的 **key 变化会丢失旧值**（重建了槽位）。

### 5. `remember` 的 key 机制

```kotlin
// 无 key：只要位置不变，值就一直复用
val a = remember { compute() }

// 带 key：key 变化时丢弃旧值，重新计算
val b = remember(userId) { compute(userId) }

// 多个 key
val c = remember(userId, filter) { compute(userId, filter) }
```

**key 的典型用途**：
```kotlin
// 场景：搜索词变化时重置分页
val page by remember(query) { mutableStateOf(1) }

// 场景：用户切换时重建整个表单
key(userId) {
    UserForm(userId = userId)
}
```

**`key()` composable vs `remember(key)` 的区别**：

| | `remember(key) { }` | `key(key) { }` |
| --- | --- | --- |
| 作用 | key 变则**重新计算值** | key 变则**整个子树被重建**（状态全部重置） |
| 影响范围 | 只影响这一个槽位 | 影响所有子节点的 `remember` / 状态 |
| 典型用途 | 缓存重算 | 切换用户/页面时重置全部状态 |

### 6. 快照系统（Snapshot）与状态一致性

```text
Compose 状态存储在 Snapshot 中：

  GlobalSnapshot
    ├─ SnapshotStateList<T>
    ├─ SnapshotStateMap<K, V>
    └─ MutableState<T>
```

**快照解决的问题**：

1. **一致读**：一次读取中，即使其他线程修改了状态，你看到的是**同一时刻的一致视图**。
2. **无锁并发**：读不需要加锁。
3. **写冲突合并**：
   ```kotlin
   // 两个线程同时读-改-写
   val list = remember { mutableStateListOf<Int>() }
   // Snapshot.apply { list.add(1) }  → 在快照内修改，最后一次性提交
   ```
4. **嵌套快照**：`Snapshot.takeNestedSnapshot()`。

**线程规则**：

| 操作 | 线程要求 |
| --- | --- |
| 读 `state.value` | 任意线程（返回快照中的值） |
| 写 `state.value = x` | 任意线程安全，但**读-改-写**需要原子性 |
| `mutableStateListOf.add/remove` | 任意线程安全 |
| `LaunchedEffect` / `rememberCoroutineScope` | **主线程**（`Dispatchers.Main.immediate`） |

**常见坑**：

```kotlin
// ❌ 后台线程直接改 Compose 状态 → 可能导致"快照冲突"或状态不一致
GlobalScope.launch(Dispatchers.IO) {
    delay(1000)
    count = 1     // 虽然不崩，但不推荐
}

// ✅ 用 withContext 回主线程
viewModelScope.launch {
    val data = withContext(Dispatchers.IO) { repository.load() }
    state = data
}
```

### 7. 四种副作用 API

| API | 触发时机 | 生命周期绑定 | 典型用途 |
| --- | --- | --- | --- |
| `LaunchedEffect(key1, key2)` | 进入组合时启动协程；**key 变化时取消旧协程并重启** | 组合存续 | 加载数据、订阅 Flow、播放动画 |
| `SideEffect` | **每次成功重组后**执行 | 无（每次都执行） | 发送埋点、同步非 Compose 状态 |
| `DisposableEffect(key)` | 进入组合时执行；**key 变化或离开组合时**清理 | 组合存续 | 注册/反注册监听、`remember` 释放资源 |
| `produceState` | 类似 `LaunchedEffect`，但产生一个 `State` | 组合存续 | 快速把 Flow 转成状态 |

**`LaunchedEffect` 的 key 怎么选**（高频面试点）：

```kotlin
// 1. 只在进入时执行一次 → Unit
LaunchedEffect(Unit) { viewModel.refresh() }

// 2. 参数变化时重启 → 用参数本身做 key
LaunchedEffect(userId) { loadUser(userId) }

// 3. 多个依赖 → 全部列出
LaunchedEffect(userId, filter) { load(userId, filter) }

// 4. 永远不重启 → 空 key 列表（但一般不需要）
LaunchedEffect(Unit) { while (true) { delay(1000); tick() } }
```

**key 选择的三条原则**：
1. **只列真正影响协程逻辑的依赖**。多列一个无关的 key → 协程被频繁重启（如网络请求被重复触发）。
2. **不要把"每次重组都变的对象"作为 key**（如 `mutableStateOf` 本身）→ 无限重启循环。
3. **key 变化时旧协程会被取消** → 取消是"协作式"的，CPU 密集的循环需要自己检查 `isActive` 或用 `ensureActive()`。

**`SideEffect` 的正确用法**：

```kotlin
// ❌ 错误：在 composable 体里直接做副作用 → 每次重组都做，且可能做多次
Text("count: $count")

// ✅ 正确：SideEffect 在重组成功提交后执行一次
SideEffect {
    analyticsTracker.log("ScreenShown", mapOf("count" to count))
}
```

> **注意**：`SideEffect` 在**每次重组后**都会执行（不是每次"值变化"）。如果只想在值变化时执行，需要自己比较。

**`DisposableEffect` 的正确用法**：

```kotlin
// 释放资源
val context = LocalContext.current
DisposableEffect(Unit) {
    val listener = SensorManager.registerListener(...)
    onDispose {
        SensorManager.unregisterListener(listener)   // 必须清理
    }
}
```

**`rememberCoroutineScope` vs `LaunchedEffect`**：

| | `rememberCoroutineScope` | `LaunchedEffect` |
| --- | --- | --- |
| 触发 | 需要时手动 `scope.launch {}` | 进入组合自动启动 |
| 取消时机 | 组合销毁时自动取消 | 组合销毁或 key 变化时取消 |
| 适合 | **事件回调**（点击、滑动） | **被动订阅 / 加载数据** |
| 典型坑 | 在 composable 体里直接 `launch` → 每次重组都重启任务 | 忘记写 key → 只执行一次 |

```kotlin
// ❌ 常见错误：每次重组都重新发起请求
@Composable
fun Screen(vm: ViewModel) {
    val scope = rememberCoroutineScope()
    scope.launch { vm.load() }        // 每次重组都执行！
}

// ✅ 用 LaunchedEffect
@Composable
fun Screen(vm: ViewModel) {
    LaunchedEffect(Unit) { vm.load() }
}
```

### 8. 状态容器：ViewModel + collectAsStateWithLifecycle

```text
ViewModel（业务状态，配置变更保留）
      │ StateFlow
      ▼
collectAsStateWithLifecycle()   ← 生命周期感知：STARTED 才收集，STOPPED 取消
      │ State<T>
      ▼
by 委托读取 → 触发重组
```

**`collectAsState()` vs `collectAsStateWithLifecycle()`**：

| | `collectAsState` | `collectAsStateWithLifecycle` |
| --- | --- | --- |
| 生命周期感知 | ❌ 组合存续就收集 | ✅ 只在 STARTED+ 收集 |
| 后台时 | 仍在上游收集，可能浪费资源 | 自动取消收集 |
| 推荐 | 几乎不用 | ✅ **默认推荐** |

**依赖**：

```kotlin
implementation("androidx.lifecycle:lifecycle-runtime-compose:2.8.0")
```

**完整示例**：

```kotlin
class UserViewModel(
    private val repository: UserRepository,
    private val savedStateHandle: SavedStateHandle
) : ViewModel() {

    // 业务状态
    private val _uiState = MutableStateFlow(UserUiState())
    val uiState: StateFlow<UserUiState> = _uiState.asStateFlow()

    // 需要跨进程恢复的少量状态（如搜索词）交给 SavedStateHandle
    val query: StateFlow<String> = savedStateHandle.getStateFlow("query", "")

    private val _events = Channel<UserEvent>(Channel.BUFFERED)
    val events: Flow<UserEvent> = _events.receiveAsFlow()

    fun onQueryChanged(q: String) {
        savedStateHandle["query"] = q
    }

    fun refresh() {
        viewModelScope.launch {
            _uiState.update { it.copy(loading = true, error = null) }
            runCatching { repository.load() }
                .onSuccess { list -> _uiState.update { it.copy(loading = false, users = list)) }
                .onFailure { e -> _uiState.update { it.copy(loading = false, error = e.message) } }
        }
    }

    fun consumeEvent() {
        viewModelScope.launch { _events.send(UserEvent.ShowToast("已提交")) }
    }
}
```

```kotlin
@Composable
fun UserScreen(viewModel: UserViewModel = hiltViewModel()) {
    val state by viewModel.uiState.collectAsStateWithLifecycle()
    val query by viewModel.query.collectAsStateWithLifecycle()

    // 一次性事件
    LaunchedEffect(Unit) {
        viewModel.events.collect { event ->
            when (event) {
                is UserEvent.ShowToast -> Toast.makeText(context, event.message, Toast.LENGTH_SHORT).show()
                is UserEvent.NavigateBack -> navController.popBackStack()
            }
        }
    }

    Column {
        OutlinedTextField(
            value = query,
            onValueChange = viewModel::onQueryChanged,
            label = { Text("搜索") }
        )
        when {
            state.loading -> CircularProgressIndicator()
            state.error != null -> Text("错误：${state.error}")
            else -> LazyColumn {
                items(state.users, key = { it.id }) { UserRow(it) }
            }
        }
    }
}
```

### 9. 状态管理的完整决策树

```text
这个状态需要保留多久？
  │
  ├─ 只在当前页面内、旋转也无所谓
  │     └─ remember
  │
  ├─ 旋转屏幕后要保留，但不值得写业务逻辑
  │     └─ rememberSaveable
  │
  ├─ 旋转屏幕要保留 + 涉及业务逻辑 + 需要发起网络请求
  │     └─ ViewModel (+ SavedStateHandle 存少量关键状态)
  │
  └─ 永久保留（草稿、缓存）
        └─ DataStore / Room
```

```kotlin
fun SearchBar(

@Composable
fun SearchScreen() {

    val scope = rememberCoroutineScope()

            loading = false

        SearchBar(
            query = query,
            onQueryChange = { query = it },
            onSearch = { scope.launch { /* ... */ } }
        )
        if (loading) CircularProgressIndicator()
    }
}
```

### 2. 四种副作用 API 的对照示例

```kotlin
@Composable
fun SideEffectDemo(userId: String) {
    val context = LocalContext.current

    // 1. LaunchedEffect：进入组合启动协程，key 变化时重启
    LaunchedEffect(userId) {
        Log.d("Demo", "加载用户 $userId")
        delay(1000)
        Log.d("Demo", "加载完成")
    }

    // 2. SideEffect：每次重组成功提交后执行一次
    val counter = remember { mutableIntStateOf(0) }
    SideEffect {
        counter.value++                 // 每次重组 +1（注意：会触发新的重组，要小心）
        Log.d("Demo", "重组完成，count=${counter.value}")
    }

    // 3. DisposableEffect：进入时注册，离开时清理
    DisposableEffect(userId) {
        val listener = object : View.OnAttachStateChangeListener {
            override fun onViewAttachedToWindow(v: View) {}
            override fun onViewDetachedFromWindow(v: View) {}
        }
        // 注册
        onDispose {
            // 清理（必须执行，否则泄漏）
            Log.d("Demo", "清理 $userId 的资源")
        }
    }

    // 4. produceState：把 Flow 转成 State
    val user by produceState<User?>(initialValue = null, userId) {
        value = repository.getUser(userId)
    }

    Text(user?.name ?: "加载中…")
}
```

### 4. 事件通道（Channel / SharedFlow）完整示例

```kotlin
// ViewModel：区分状态与事件
class CheckoutViewModel : ViewModel() {

    // 状态：界面渲染用
    private val _uiState = MutableStateFlow(CheckoutUiState())
    val uiState: StateFlow<CheckoutUiState> = _uiState.asStateFlow()

    // 事件：一次性消费
    private val _events = MutableSharedFlow<CheckoutEvent>(extraBufferCapacity = 1)
    val events: SharedFlow<CheckoutEvent> = _events.asSharedFlow()

    fun submit() {
        viewModelScope.launch {
            _uiState.update { it.copy(submitting = true) }
            runCatching { repository.pay() }
                .onSuccess { _events.emit(CheckoutEvent.NavigateToSuccess) }   // 一次性
                .onFailure { _uiState.update { it.copy(submitting = false, error = "支付失败") } }
        }
    }
}

sealed interface CheckoutEvent {
    data object NavigateToSuccess : CheckoutEvent
    data class ShowMessage(val text: String) : CheckoutEvent
}

// Compose 侧消费
@Composable
fun CheckoutScreen(vm: CheckoutViewModel = hiltViewModel()) {
    val state by vm.uiState.collectAsStateWithLifecycle()
    val navController = LocalNavController.current

    LaunchedEffect(Unit) {
        vm.events.collect { event ->
            when (event) {
                is CheckoutEvent.NavigateToSuccess -> navController.navigate("success")
                is CheckoutEvent.ShowMessage -> snackbarHostState.showSnackbar(event.text)
            }
        }
    }

    Button(onClick = vm::submit, enabled = !state.submitting) {
        Text("提交")
    }
}
```

### 6. `mutableStateListOf` 与不可变集合

```kotlin
@Composable
fun TagEditor() {
    // 快照感知列表：add/remove 会自动触发重组
    val tags = remember { mutableStateListOf("Android", "Kotlin") }
    var input by remember { mutableStateOf("") }

    Column {
        tags.forEach { tag ->
            Row {
                Text(tag)
                IconButton(onClick = { tags.remove(tag) }) {
                    Icon(Icons.Default.Close, contentDescription = "删除")
                }
            }
        }
        OutlinedTextField(
            value = input,
            onValueChange = { input = it },
            trailingIcon = {
                IconButton(onClick = {
                    if (input.isNotBlank()) {
                        tags.add(input)      // 直接改列表，UI 自动更新
                        input = ""
                    }
                }) { Icon(Icons.Default.Add, contentDescription = "添加") }
            }
        )
    }
}
```

## 常见问题 / 面试要点

**读者问：`remember` 和 `rememberSaveable` 有什么区别？什么时候用哪个？**

**AI答：**

1. **核心区别**：
   - `remember`：**只在组合存续期间**保留值。Activity 重建（旋转）→ 组合销毁重建 → 值丢失。
   - `rememberSaveable`：额外通过 `SavedStateRegistry` 把值序列化进 `savedInstanceState`，**配置变更后恢复**。
2. **实现机制**：`rememberSaveable` 内部用 `Saver` 把值转成 `Bundle` 可存类型（`Parcelable` / `Serializable` / 基本类型），存入 Activity 的 `savedInstanceState`；重建时反向恢复。
3. **选择原则**：
   | 场景 | 用哪个 |
   | --- | --- |
   | 展开/收起状态、动画进度、临时筛选 | `remember` |
   | 滚动位置、Tab 索引、输入框文字、开关状态 | `rememberSaveable` |
   | 列表数据、加载状态、任何涉及网络请求 | `ViewModel` |
   | 用户草稿、长期偏好 | `DataStore` |
4. **坑**：
   - `rememberSaveable` 只能存**可序列化**的类型；存 `View` / `Bitmap` 会崩。
   - `savedInstanceState` 有大小限制（Binder 事务 ~1MB），别存大列表。
   - `rememberSaveable` 的 **key 变化会导致值重置**（槽位重建）。
5. **面试话术**："**`remember` 管『本次会话』，`rememberSaveable` 管『配置变更』，`ViewModel` 管『业务逻辑与生命周期』，`DataStore` 管『持久化』。四层，职责不要混。**"

---

**读者问：状态提升（State Hoisting）是什么？为什么要做？**

**AI答：**

1. **定义**：把状态从子 composable 中移出，提到调用方（父级）持有，子 composable 通过**参数接收状态**、通过**回调上抛事件**，变成**无状态（stateless）**的纯函数。
2. **三个好处**：
   - **可复用**：同一个子组件在不同上下文用不同状态。
   - **可测试 / 可预览**：`@Preview` 直接传固定值即可。
   - **单一真相源**：状态只有一份，不会出现"局部和全局不一致"。
3. **官方三原则**：
   - 状态提升到**最接近使用点**的地方（不是越高越好）。
   - 状态应有**唯一来源**。
   - 状态应**对使用者隐藏**，通过回调暴露修改入口（`value` + `onValueChange`）。
4. **反面例子**：
   ```kotlin
   // ❌ 状态藏在子组件里，父级无法控制
   @Composable fun Counter() {
       var count by remember { mutableIntStateOf(0) }
       Text("$count")
   }
   ```
5. **面试话术**："**状态提升不是为了『把状态放得越高越牛』，而是让 UI 变成纯函数：`UI = f(state, events)`。**"

---

**读者问：`derivedStateOf` 什么时候用？和 `remember` 有什么区别？**

**AI答：**

1. **本质区别**：
   - `remember`：**缓存值**，跨重组复用同一份数据；写什么读什么。
   - `derivedStateOf`：**缓存派生值**，只有当"真正被读取的源状态"变化时才重新计算。
2. **独特价值：把"重组"降级为"重新求值"**。
   ```kotlin
   // ❌ 滚动时每秒几十次重组
   val showFab = listState.firstVisibleItemIndex > 0
   if (showFab) FloatingActionButton(...)

   // ✅ 只有布尔值翻转时才重组
   val showFab by remember { derivedStateOf { listState.firstVisibleItemIndex > 0 } }
   ```
3. **判断标准**：
   - 源状态变化**频繁**（滚动、动画、传感器），
   - 派生结果变化**稀疏**（布尔、枚举、字符串），
   → 用 `derivedStateOf`。
4. **注意**：
   - `derivedStateOf` 内的读取也会建立依赖，源变化会触发**重新求值**（但不一定重组）。
   - 要和 `remember` 配合，否则每次重组都新建对象，缓存失效。
   - Compose 1.7+ 推荐 `rememberDerivedStateOf`（Compose-aware 版本）。
   - 简单派生直接内联计算，**不要滥用**（它有额外开销）。
5. **面试话术**："**`derivedStateOf` 解决的是『源变化频繁、结果变化稀疏』的场景，把重组变成重新求值。**"

---

**读者问：`LaunchedEffect` 的 key 应该怎么选？key 写错会怎样？**

**AI答：**

1. **语义**：`LaunchedEffect(key1, key2, ...)` 在进入组合时启动协程；**当任意 key 变化时，旧的协程被取消，新的协程启动**。
2. **key 选择三原则**：
   - **只列真正影响协程逻辑的依赖**。多列一个 → 协程频繁重启（如网络请求被反复触发）。
   - **不要放"每次重组都变"的对象**（如 `mutableStateOf` 的委托本身、每次新建的 lambda）→ 无限重启循环。
   - **key 变化 = 逻辑重跑**，所以要问自己"这个数据变了，我需要重新加载吗？"
3. **典型写法**：
   ```kotlin
   LaunchedEffect(Unit) { vm.refresh() }            // 只在进入时跑一次
   LaunchedEffect(userId) { vm.load(userId) }        // userId 变则重载
   LaunchedEffect(query) { search(query) }            // 搜索词变化（可配合防抖）
   LaunchedEffect(lifecycle) { /* 订阅直到销毁 */ }
   ```
4. **key 写错的两种典型后果**：
   - **漏写 key** → 协程只执行一次，参数变化后不更新 → **Bug**。
   - **多写 key** → 协程被频繁重启 → 重复请求 + 闪烁 → **性能问题**。
5. **取消是协作式的**：CPU 密集循环需要在循环体里检查 `currentCoroutineContext().isActive` 或调用 `ensureActive()`，否则取消不生效。
6. **面试话术**："**`LaunchedEffect` 的 key 就是『这段副作用依赖哪些输入』的声明，写多了是重复执行，写少了是数据不更新。**"

---

**读者问：`rememberCoroutineScope` 和 `LaunchedEffect` 有什么区别？什么时候用哪个？**

**AI答：**

1. **触发方式**：
   - `LaunchedEffect`：**自动**在进入组合时启动协程。
   - `rememberCoroutineScope`：返回一个**手动触发**的作用域，需要你 `scope.launch {}`。
2. **取消时机**：两者都在**组合销毁时**自动取消所有子协程（避免泄漏）。
3. **使用场景**：
   | 场景 | 用哪个 |
   | --- | --- |
   | 加载数据、订阅 Flow、播放动画 | `LaunchedEffect` |
   | 点击按钮后发起操作 | `rememberCoroutineScope` |
   | 滚动到底加载更多 | `rememberCoroutineScope`（在 `LaunchedEffect` 中绑定 `snapshotFlow` 收集） |
4. **典型错误**：
   ```kotlin
   // ❌ 在 composable 体里直接 launch → 每次重组都重启任务
   @Composable fun Screen() {
       val scope = rememberCoroutineScope()
       scope.launch { vm.load() }
   }
   ```
   正确：数据加载用 `LaunchedEffect(Unit) { vm.load() }`；事件回调里才用 `scope.launch`。
5. **另一个差异**：`rememberCoroutineScope` 的 dispatcher 是 `Dispatchers.Main.immediate`（立即执行，不排队），`LaunchedEffect` 默认也是 Main。
6. **面试话术**："**`LaunchedEffect` 管『被动订阅』，`rememberCoroutineScope` 管『主动触发』。前者自动启动，后者手动 launch，但两者都随组合销毁而取消。**"

---

**读者问：状态和事件在 Compose 里应该怎么区分？为什么事件不能放进状态？**

**AI答：**

1. **定义**：
   - **状态**：描述"现在是什么样"，需要被**持续观察**（`State` / `StateFlow`）。
   - **事件**：描述"发生了什么"，需要被**消费一次**（`Channel` / `SharedFlow`）。
2. **为什么事件不能进状态**：
   - 状态是**可重放**的：旋转屏幕、重组、甚至 `collectAsState` 重新收集，都会把最新值再发一次 → Toast 再弹一次、导航再执行一次。
   - 事件必须**一次性消费**，消费后"消失"。
3. **正确方案**：
   ```kotlin
   private val _events = Channel<MyEvent>(Channel.BUFFERED)
   val events = _events.receiveAsFlow()
   ```
   - `Channel`：**每个事件只被一个收集者收到一次**（适合"事件由某个界面处理"）。
   - `SharedFlow`：**广播**给所有收集者（适合多个观察者都要知道，如"播放/暂停"这类状态广播）。
4. **Channel vs SharedFlow**：
   | | `Channel` | `SharedFlow` |
   | --- | --- | --- |
   | 分发 | 单消费者语义（多个收集者会瓜分事件） | 广播 |
   | 粘性 | 缓冲/`CONFLATED` 时保留 | `replay` 缓存 |
   | 适合 | 一次性通知（导航、Toast） | 状态广播、持续监听 |
5. **面试话术**："**状态是『现在是什么』，事件是『刚刚发生了什么』。状态可以重复读，事件只能读一次。**"

---

**读者问：Compose 的状态在多线程下安全吗？快照系统解决了什么问题？**

**AI答：**

1. **快照系统解决的问题**：
   - **一致性读**：一次读取中即使其他线程在写，你看到的仍是**同一时刻的一致快照**。
   - **无锁并发**：读不需要加锁（Copy-on-Write + 版本号）。
   - **写冲突合并**：写操作先在**私有快照**中进行，最后 `apply` 到全局快照时做冲突解决，避免"读-改-写"丢更新。
2. **线程安全边界**：
   - 读 `state.value`：任意线程安全。
   - 写 `state.value = x`：**单次写**线程安全；但"读-改-写"（如 `count.value = count.value + 1`）**不是原子的**，需要 `Snapshot.withMutableSnapshot {}` 或在主线程操作。
3. **推荐实践**：
   ```kotlin
   // 后台计算 → 回主线程更新 UI 状态
   viewModelScope.launch {
       val data = withContext(Dispatchers.IO) { repo.load() }
       _uiState.value = data
   }
   ```
4. **`mutableStateListOf` 的并发写**：同样是快照语义，`add`/`remove` 安全，但"检查再修改"模式要小心。
5. **面试话术**："**快照系统让 Compose 状态『读无锁、写隔离、最终一致』。多线程写的正确姿势是：后台算数据，主线程写状态。**"

---

**读者问：`SideEffect`、`LaunchedEffect`、`DisposableEffect`、`produceState` 分别什么时候用？**

**AI答：**

1. **`LaunchedEffect(key)`**：**进入组合自动启动**协程；key 变化时**取消旧协程 + 重启**。
   - 用于：加载数据、订阅 Flow、播放动画、无限循环。
2. **`SideEffect`**：**每次重组成功后**执行一次（不取消）。
   - 用于：埋点上报、把状态同步给非 Compose 的系统（如 `View`）。
   - ⚠️ 它**每次重组都执行**，不是"值变化时执行"。若只想在变化时执行，要自己比较。
3. **`DisposableEffect(key)`**：进入组合时执行一次；**key 变化或离开组合时**执行 `onDispose` 清理。
   - 用于：注册/反注册监听、订阅/退订、持有需要 `release()` 的资源。
4. **`produceState(initialValue, key)`**：本质是 `LaunchedEffect` + `mutableStateOf` 的语法糖，把异步结果暴露为状态。
   ```kotlin
   val user by produceState<User?>(null, userId) { value = repo.get(userId) }
   ```
5. **`rememberCoroutineScope`**：手动触发的作用域（配合事件回调）。
6. **判断口诀**：
   ```text
   要跑协程 → LaunchedEffect
   要在重组后做点事 → SideEffect
   要注册需要清理的东西 → DisposableEffect
   要把异步结果变成 State → produceState
   要在事件里触发 → rememberCoroutineScope
   ```
7. **面试话术**：**"这五个 API 覆盖了 Compose 副作用的全部场景，关键是记住每个的『触发时机』和『取消时机』。**"

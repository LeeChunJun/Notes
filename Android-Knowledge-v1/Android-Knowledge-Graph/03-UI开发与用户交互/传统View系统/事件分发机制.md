# 事件分发机制

## 一句话定义

Android 的触摸事件分发是一条**自上而下的责任链**：`dispatchTouchEvent` 决定"事件给谁"，`onInterceptTouchEvent` 决定"要不要拦截"，`onTouchEvent` 决定"要不要消费"。父容器一旦拦截，子 View 会收到一个 `ACTION_CANCEL`，从而中断正在进行的交互序列。

## 核心原理

### 1. 三个方法的职责

```text
                ACTION_DOWN
                     │
                     ▼
        ┌────────────────────────────┐
        │ ViewGroup.dispatchTouchEvent│
        └────────────────────────────┘
                     │
       ┌─────────────┴─────────────┐
       ▼                           ▼
 onInterceptTouchEvent        （不拦截，遍历子 View）
   返回 true → 事件全部留给自身     │
       │                          ▼
       │              ┌────────────────────────┐
       │              │ child.dispatchTouchEvent│
       │              └────────────────────────┘
       │                          │
       │              ┌───────────┴───────────┐
       │              ▼                       ▼
       │      child.onInterceptTouchEvent   child.onTouchEvent
       │              （View 无子 View，      返回 true → 消费
       │                默认 false）              │
       │                                          ▼
       │                                 事件结束（不传给兄弟）
       ▼
  自己处理：onTouchEvent
```

| 方法 | 所属 | 责任 | 典型返回值 |
| --- | --- | --- | --- |
| `dispatchTouchEvent` | View / ViewGroup | **分发入口**。ViewGroup 负责在子 View 中找"能处理该事件的子 View"；View 的实现最终调用自己的 `onTouchEvent` | View：直接返回 `onTouchEvent` 结果；ViewGroup：true/false 表示"是否有人在后续 MOVE 中还需要处理" |
| `onInterceptTouchEvent` | **只有 ViewGroup** | 是否拦截事件不再传给子 View | `true` = 拦截；`false` = 继续分发给子 View |
| `onTouchEvent` | View / ViewGroup | 是否消费这个事件 | `true` = 消费（后续 MOVE/UP 继续发给我）；`false` = 不消费（后续 MOVE/UP 可能发给兄弟 View） |

### 2. MotionEvent 的事件序列

```text
一次完整的手势序列：

ACTION_DOWN          (0)   —— 必须有，且总是第一个
   ↓ 用户手指移动
ACTION_MOVE          (1)   —— 一个 DOWN 后可能有 0 个或多个 MOVE
   ↓
ACTION_UP            (2)   —— 手势正常结束
   或
ACTION_CANCEL        (3)   —— 被父容器抢走 / 窗口失焦 / 手指被系统接管
   或
ACTION_POINTER_DOWN  (5)   —— 第二根手指按下
ACTION_POINTER_UP    (6)   —— 最后一根手指抬起
```

`MotionEvent` 的重要属性：

| 属性 | 说明 |
| --- | --- |
| `getAction()` | 返回 action，**注意多指事件的 action 包含指针索引**（`action & ACTION_POINTER_INDEX_MASK`） |
| `getActionMasked()` | **去掉指针索引**，推荐的取值方式 |
| `getX()/getY()` | 相对于**接收该事件 View** 的坐标 |
| `getRawX()/getRawY()` | 屏幕坐标 |
| `getEventTime()` | 事件产生的时间（up-time ms） |
| `getDownTime()` | `ACTION_DOWN` 的时间 |
| `getPointerCount()` | 触摸点数量 |

> 面试点：`getX()` 是相对坐标，会随 View 自身移动而变化；做跟随手指的效果要用 `getRawX()` 减去 View 初始屏幕位置。

### 3. ViewGroup.dispatchTouchEvent 的核心逻辑

```text
dispatchTouchEvent(ev):
  │
  ├─ ACTION_DOWN:
  │    ├─ 记录 mFirstTouchTarget = null，清空 touch targets 列表
  │    ├─ 清空 mGroupFlags 中的 FLAG_DISALLOW_INTERCEPT（每次 DOWN 都要重置）
  │    └─ 判断是否需要拦截：
  │         if (mGroupFlags & FLAG_DISALLOW_INTERCEPT) == 0 && disallowInterceptIntercept) {
  │             intercepted = onInterceptTouchEvent(ev);
  │         } else {
  │             intercepted = false;      // 子 View 要求"别拦截我"
  │         }
  │
  ├─ ACTION_DOWN 或 intercepted:
  │    ├─ 如果 intercepted → 走 mFirstTouchTarget == null 的分支
  │    │    → 自己的 onTouchEvent 处理（同时给子 View 发 ACTION_CANCEL）
  │    └─ 否则遍历子 View 找 target：
  │         for (child in children) {
  │             if (dispatchTransformedTouchEvent(ev, false, child, ...)) {
  │                 mFirstTouchTarget = child; break;   // 找到了
  │             }
  │         }
  │
  ├─ ACTION_MOVE:
  │    ├─ 若已找到 target → 转交 target 处理（target 内部可能再调用自己的 onIntercept）
  │    └─ 若 target 不再处理（返回 false）→ 清除 target，回到"自己处理"
  │
  ├─ ACTION_UP / CANCEL:
  │    └─ 结束手势，清理 touch targets
```

**`dispatchTransformedTouchEvent` 的关键动作**：当 ViewGroup 拦截时，它会向所有子 View 派发 `ACTION_CANCEL`：

```java
private boolean dispatchTransformedTouchEvent(MotionEvent event, boolean cancel,
        View child, long eventTime) {
    ...
    if (cancel) {
        // 已被拦截 → 给子 View 发 CANCEL，告诉它"中断了"
        event.setAction(MotionEvent.ACTION_CANCEL);
        canceled = true;
    }
    ...
}
```

### 4. ACTION_CANCEL 的产生时机

这是**必考题**。`ACTION_CANCEL` 表示"**手势被强行打断**"，常见触发场景：

| 场景 | 说明 |
| --- | --- |
| **父容器中途拦截** | `onInterceptTouchEvent` 在 MOVE 阶段返回 `true`，子 View 之前已收到 DOWN，此时必须收到 CANCEL 以终止内部状态（如 ScrollView 的 fling、按钮的按压态） |
| **子 View 拒绝消费（DOWN 返回 false）** | 父容器把事件交给下一个兄弟 View，被跳过的兄弟会收到 CANCEL |
| **View 移出窗口 / 被移除** | `ViewGroup` 在 `removeView` 或 `detach` 时向子 View 派发 CANCEL |
| **窗口失去焦点** | `onWindowFocusChanged` 变化，系统派发 CANCEL |
| **系统手势接管** | 屏幕边缘的返回手势、下拉通知栏、多任务手势抢占 |
| **父 View 的 `onTouchEvent` 处理了 DOWN 且后续兄弟也要处理** | 兄弟 View 收到 CANCEL |

> 面试话术：**"CANCEL 的语义是『你之前收到的 DOWN 作废了，撤销所有按压/滑动状态』。"** 因此所有自定义控件都必须在 `onTouchEvent` 中处理 CANCEL，否则会残留高亮、卡在滑动状态。

### 5. 消费与不消费：兄弟 View 的竞争

```text
父 ViewGroup 有两个兄弟：A（Button）、B（ImageView）

DOWN 到达：
  A.dispatchTouchEvent → A.onTouchEvent → 返回 true（可点击）
      → ViewGroup 找到 target = A，中止遍历
  → B 根本没收到 DOWN

MOVE 到达：
  → 依然发给 A
  → A.onTouchEvent 返回 false（如手指移出按钮范围）
      → ViewGroup 清除 mFirstTouchTarget
      → 后续 MOVE/UP 走 ViewGroup 自己的 onTouchEvent
```

`View.onTouchEvent` 的默认实现要点：

```java
public boolean onTouchEvent(MotionEvent event) {
    // 1. 可点击/可长按 → 消费
    if (clickable || longClickable) {
        // 处理 pressed 状态、performClick 等
        return true;
    }
    // 2. 否则不消费
    return false;
}
```

> **重要推论**：`View` 默认 `clickable = false`。所以如果你自定义 View 想响应点击，**必须 `setClickable(true)` 或 `setOnClickListener`**，否则 `onTouchEvent` 永远返回 false，点击无效。这是最经典的"自定义 View 点击没反应"的原因。

### 6. 滑动冲突的两种解决方案

**方案 A：父容器拦截（`onInterceptTouchEvent`）**

```java
public class MyScrollLayout extends ViewGroup {
    private boolean isDragging = false;

    @Override
    public boolean onInterceptTouchEvent(MotionEvent ev) {
        switch (ev.getActionMasked()) {
            case MotionEvent.ACTION_DOWN:
                isDragging = false;
                break;
            case MotionEvent.ACTION_MOVE:
                // 水平位移大于垂直位移且超过阈值 → 认为用户想横向滑动，拦截
                float dx = Math.abs(ev.getX() - ev.getDownX());
                float dy = Math.abs(ev.getY() - ev.getDownY());
                if (dx > dy && dx > touchSlop) {
                    isDragging = true;
                    return true;    // 拦截 → 子 View 收到 CANCEL
                }
                break;
        }
        return false;
    }
}
```

**方案 B：子 View 请求父容器不要拦截（`requestDisallowInterceptTouchEvent`）**

```java
public class HorizontalPager extends View {
    @Override
    public boolean onTouchEvent(MotionEvent ev) {
        switch (ev.getActionMasked()) {
            case MotionEvent.ACTION_DOWN:
                // 告诉父容器：这一串手势是我的，别拦截
                getParent().requestDisallowInterceptTouchEvent(true);
                break;
            case MotionEvent.ACTION_UP:
            case MotionEvent.ACTION_CANCEL:
                // 手势结束，恢复父容器的拦截能力
                getParent().requestDisallowInterceptTouchEvent(false);
                break;
        }
        return true;
    }
}
```

**`requestDisallowInterceptTouchEvent(true)` 的内部效果**：

```text
ViewGroup.dispatchTouchEvent:
  if ((mGroupFlags & FLAG_DISALLOW_INTERCEPT) == 0
      && disallowInterceptIntercept(ev)) {
      intercepted = onInterceptTouchEvent(ev);
  }
```

它给 ViewGroup 设置 `FLAG_DISALLOW_INTERCEPT`，在**下一次 DOWN 之前**都跳过 `onInterceptTouchEvent`。

> **重要限制**：这个标记**在每次 `ACTION_DOWN` 时会被清除**（`clearTouchTargets` / `resetTouchState` 逻辑）。所以只能在 DOWN 之后请求。

**两种方案的对比**：

| 维度 | 父拦截 | 子请求不拦截 |
| --- | --- | --- |
| 决策方 | 父容器 | 子 View |
| 触发时机 | MOVE 阶段可动态改变 | DOWN 时申请，整串手势有效 |
| 灵活性 | 高（可根据手势方向动态切换） | 低 |
| 常见使用 | ViewPager / ScrollView 与子控件共存 | 横向滑动列表嵌入竖向 ScrollView |

**横向 ViewPager 嵌在竖向 ScrollView 里的经典解法**：

```java
// 竖向父容器
@Override
public boolean onInterceptTouchEvent(MotionEvent ev) {
    // 只有当子内容是横向可滑动时才不拦截，否则拦截（保证竖向滚动）
    return !childCanScrollHorizontally;
}
```

### 7. 内部滑动的三件套

| 工具 | 作用 | 关键 API |
| --- | --- | --- |
| `Scroller` / `OverScroller` | 计算滚动位移 | `computeScrollOffset()` 返回是否还在滚动；配合 `scrollTo`/`overScrollBy` 使用 |
| `VelocityTracker` | 追踪手指速度 | `addMovement(ev)` → `computeCurrentVelocity(1000)` → `getXVelocity()` |
| `GestureDetector` | 把原始事件翻译成手势语义 | `onDown` `onFling` `onScroll` `onSingleTapUp` `onLongPress` |

**`GestureDetector.SimpleOnGestureListener` 关键回调语义**：

```text
onDown           —— 手指按下，几乎所有手势的前提；返回 true 表示"我关心后续事件"
onSingleTapUp   —— 单击（抬手时未超过移动阈值、未超时）
onSingleTapConfirmed —— 单击确认（等到 ACTION_UP 后）
onDoubleTap     —— 双击
onFling(e1, e2, velocityX, velocityY) —— 快速甩动，用 velocity 判断惯性滚动
onScroll(e1, e2, distanceX, distanceY) —— 拖动
onLongPress     —— 长按
```

**`VelocityTracker` 的正确用法**：

```java
private VelocityTracker mVelocityTracker;

@Override
public boolean onTouchEvent(MotionEvent event) {
    if (mVelocityTracker == null) {
        mVelocityTracker = VelocityTracker.obtain();
    }
    mVelocityTracker.addMovement(event);
    switch (event.getActionMasked()) {
        case MotionEvent.ACTION_UP:
            mVelocityTracker.computeCurrentVelocity(1000);  // 单位：px/s
            float velocityX = mVelocityTracker.getXVelocity();
            float velocityY = mVelocityTracker.getYVelocity();
            if (Math.abs(velocityX) > mMinimumFlingVelocity) {
                fling(velocityX);
            }
            mVelocityTracker.recycle();      // 必须回收，否则泄漏
            mVelocityTracker = null;
            break;
    }
    return true;
}
```

> 常见坑：① `VelocityTracker` 不回收 → 内存泄漏；② `computeCurrentVelocity` 不传单位 → 默认是 1（单位/毫秒），数值含义完全不同；③ `onFling` 的速度为**像素/秒**。

**`Scroller` 的标准用法**（ fling 惯性滚动）：

```java
private final OverScroller scroller = new OverScroller(context);

private void fling(float velocityX) {
    scroller.fling(
        getScrollX(), getScrollY(),
        (int) velocityX, 0,
        0, getWidth() - getWidth(),     // minX, maxX
        0, 0,                            // minY, maxY
        0, 0);                          // overX, overY
    invalidate();
}

@Override
public void computeScroll() {
    if (scroller.computeScrollOffset()) {
        scrollTo(scroller.getCurrX(), scroller.getCurrY());
        postInvalidateOnAnimation();     // 下一帧继续
    }
}
```

### 8. 事件分发与绘制流程的关系

```text
输入阶段（Choreographer CALLBACK_INPUT）
   InputStage → ViewRootImpl.dispatchInputEvent
       → ViewGroup.dispatchTouchEvent → onInterceptTouchEvent → onTouchEvent
            └─ 手指移动 → 消费后调用 scrollTo() / invalidate()
                                    │
绘制阶段（Choreographer CALLBACK_TRAVERSAL）
   ViewRootImpl.performTraversals
       → measure / layout / draw
```

**关键点**：
- 事件分发发生在**输入阶段**，早于绘制阶段。
- 事件处理中调用 `scrollTo()` 会触发 `requestLayout()`（因为 `scrollTo` 内部走 `computeScroll` 逻辑会 `invalidate`）。
- 一次手势会产生多个 `ACTION_MOVE`，每个 MOVE 都可能引发一次 `invalidate` → 一次 `performDraw`。**这就是滑动掉帧的根源**。

## 代码示例

### 1. 完整的事件分发骨架（自定义 ViewGroup）

```java
public class DragLayout extends ViewGroup {

    private static final int SLOP = 8;
    private float downX, downY;
    private boolean isDragging = false;

    @Override
    public boolean onInterceptTouchEvent(MotionEvent ev) {
        switch (ev.getActionMasked()) {
            case MotionEvent.ACTION_DOWN:
                downX = ev.getX();
                downY = ev.getY();
                isDragging = false;
                return false;                      // 先不拦，让子 View 收到 DOWN
            case MotionEvent.ACTION_MOVE:
                float dx = ev.getX() - downX;
                float dy = ev.getY() - downY;
                if (Math.abs(dx) > SLOP || Math.abs(dy) > SLOP) {
                    isDragging = true;
                    return true;                   // 拦截 → 子 View 收到 CANCEL
                }
                return false;
            case MotionEvent.ACTION_UP:
            case MotionEvent.ACTION_CANCEL:
                isDragging = false;
                return false;
        }
        return false;
    }

    @Override
    public boolean onTouchEvent(MotionEvent event) {
        switch (event.getActionMasked()) {
            case MotionEvent.ACTION_DOWN:
                return true;                      // 声明"我也能处理"，后续 MOVE 才会送到这
            case MotionEvent.ACTION_MOVE:
                if (isDragging) {
                    scrollTo((int) (getScrollX() - (event.getX() - downX)), getScrollY());
                    downX = event.getX();
                    downY = event.getY();
                }
                return true;
            case MotionEvent.ACTION_UP:
            case MotionEvent.ACTION_CANCEL:         // 必须处理 CANCEL，清理状态
                isDragging = false;
                performClick();                    // 触发 click 回调
                return true;
        }
        return super.onTouchEvent(event);
    }

    @Override
    public boolean performClick() {
        super.performClick();
        // 业务：通知外部
        return true;
    }
}
```

### 2. 用 GestureDetector + VelocityTracker 实现可拖动的自定义 View

```java
public class SwipeCardView extends View {

    private final GestureDetector detector;
    private final OverScroller scroller = new OverScroller(getContext());
    private VelocityTracker velocityTracker;
    private float downX;
    private int direction = 0;    // 0 无, 1 左滑, 2 右滑

    public SwipeCardView(Context context, AttributeSet attrs) {
        super(context, attrs);
        detector = new GestureDetector(context, new SimpleOnGestureListener() {
            @Override
            public boolean onDown(MotionEvent e) {
                downX = e.getX();
                direction = 0;
                return true;
            }

            @Override
            public boolean onScroll(MotionEvent e1, MotionEvent e2, float dx, float dy) {
                if (e2.getX() - downX < -SLOP) direction = 1;
                else if (e2.getX() - downX > SLOP) direction = 2;
                translationX = e2.getX() - downX;   // 直接改属性，触发重绘
                return true;
            }

            @Override
            public boolean onFling(MotionEvent e1, MotionEvent e2, float vx, float vy) {
                if (Math.abs(vx) > mMinFlingVelocity) {
                    scroller.fling((int) translationX, 0, (int) vx, 0,
                            Integer.MIN_VALUE, Integer.MAX_VALUE, 0, 0);
                    invalidate();
                }
                return true;
            }
        });
        detector.setOnDoubleTapListener(new SimpleOnGestureListener() {
            @Override public boolean onSingleTapConfirmed(MotionEvent e) {
                performClick();    // 单击
                return true;
            }
        });
        setClickable(true);        // 关键：让默认 onTouchEvent 会消费事件
    }

    @Override
    public boolean onTouchEvent(MotionEvent event) {
        if (velocityTracker == null) velocityTracker = VelocityTracker.obtain();
        velocityTracker.addMovement(event);
        boolean handled = detector.onTouchEvent(event);

        switch (event.getActionMasked()) {
            case MotionEvent.ACTION_UP:
            case MotionEvent.ACTION_CANCEL:
                velocityTracker.computeCurrentVelocity(1000);
                mMinFlingVelocity = Math.max(
                        velocityTracker.getXVelocity(),
                        velocityTracker.getYVelocity());
                velocityTracker.recycle();
                velocityTracker = null;
                break;
        }
        return handled || super.onTouchEvent(event);
    }

    @Override
    public void computeScroll() {
        if (scroller.computeScrollOffset()) {
            translationX = scroller.getCurrX();
            postInvalidateOnAnimation();
        }
    }
}
```

### 3. 子 View 请求父容器不要拦截（横向滚动嵌竖向滚动）

```java
public class HorizontalListView extends ViewGroup {

    private final VelocityTracker tracker = VelocityTracker.obtain();

    @Override
    public boolean onInterceptTouchEvent(MotionEvent ev) {
        // 父容器只关心横向手势
        if (ev.getActionMasked() == MotionEvent.ACTION_MOVE) {
            float dx = Math.abs(ev.getX() - ev.getDownX());
            float dy = Math.abs(ev.getY() - ev.getDownY());
            return dx > dy && dx > touchSlop;
        }
        return false;
    }

    @Override
    public boolean onTouchEvent(MotionEvent event) {
        tracker.addMovement(event);
        switch (event.getActionMasked()) {
            case MotionEvent.ACTION_DOWN:
                // 关键：告诉父容器，这一串手势不要拦截（否则父 ScrollView 抢走）
                getParent().requestDisallowInterceptTouchEvent(true);
                return true;
            case MotionEvent.ACTION_UP:
            case MotionEvent.ACTION_CANCEL:
                getParent().requestDisallowInterceptTouchEvent(false);
                tracker.clear();
                return true;
        }
        return super.onTouchEvent(event);
    }
}
```

### 4. Compose 中的对应写法（对比参考）

```kotlin
@Composable
fun SwipeBox(modifier: Modifier = Modifier, onSwiped: () -> Unit) {
    // Compose 里没有"事件分发链"，只有 Modifier 链：事件按 Modifier 链自上而下传递
    val offsetX = remember { Animatable(0f) }
    val scope = rememberCoroutineScope()

    Box(
        modifier = modifier
            .pointerInput(Unit) {                       // key 决定何时重启手势检测
                detectDragGestures(
                    onDrag = { change, dragAmount ->
                        change.consume()                 // 消费掉，防止父级也响应
                        scope.launch { offsetX.snapTo(offsetX.value + dragAmount.x) }
                    },
                    onDragEnd = {
                        if (kotlin.math.abs(offsetX.value) > 300f) {
                            scope.launch { offsetX.animateTo(if (offsetX.value > 0) 1000f else -1000f) }
                            onSwiped()
                        } else {
                            scope.launch { offsetX.animateTo(0f) }
                        }
                    }
                )
            }
            .offset { IntOffset(offsetX.value.roundToInt(), 0) }
    ) { /* ... */ }
}
```

> 对比要点：Compose **没有 ViewGroup 那种"拦截/消费"二选一**，而是用 `Modifier` 链 + `change.consume()` 表示消费；`pointerInput` 的 `key` 变化会重启手势检测协程。

## 常见问题 / 面试要点

**读者问：为什么会出现 `ACTION_CANCEL`？它和 `ACTION_UP` 有什么区别？**

**AI答：**

1. **语义区别**：
   - `ACTION_UP`：**手势正常结束**，手指离开屏幕。
   - `ACTION_CANCEL`：**手势被强行打断**，"你之前收到的 DOWN 作废了，请撤销所有状态"。
2. **产生的 6 大场景**：
   - **父容器中途拦截**（最常见）：`onInterceptTouchEvent` 在 MOVE 返回 `true`，子 View 必须收到 CANCEL 才能结束按压态/停止 fling。
   - 子 View 在 DOWN 时返回 `false` 不消费，父容器把事件交给兄弟 View，此时被跳过的兄弟会收到 CANCEL。
   - View 被 `removeView` 或 `detach`。
   - 窗口失去焦点（来了电话、弹出对话框）。
   - **系统边缘手势抢占**（返回手势、下拉通知栏、多任务）。
   - 父 View 的 `onTouchEvent` 消费了事件，其他子 View 收到 CANCEL。
3. **不处理 CANCEL 的后果**：按钮按下后移出屏幕外再回来 → 按压高亮卡住；ScrollView 的 fling 停不下来；自定义 View 的 `isPressed` 永远为 true。
4. **面试话术**："**CANCEL 是 Android 事件系统给被抢占方的一个『善后通知』，任何处理 DOWN 的地方都必须处理 CANCEL。**"

---

**读者问：`dispatchTouchEvent`、`onInterceptTouchEvent`、`onTouchEvent` 分别是谁的？返回 true / false 分别意味着什么？**

**AI答：**

1. **归属**：
   - `dispatchTouchEvent`：**View 和 ViewGroup 都有**。View 的实现是 `return onTouchEvent(event)`；ViewGroup 的实现负责在子 View 中寻找处理者。
   - `onInterceptTouchEvent`：**只有 ViewGroup 有**（View 没有子 View，无需拦截）。默认返回 `false`。
   - `onTouchEvent`：**View 和 ViewGroup 都有**。ViewGroup 若不拦截，通常由 `super.onTouchEvent()` 处理（返回 `clickable`）。
2. **返回值的含义**：
   - `dispatchTouchEvent` 返回 **true**：表示"**这个事件已经被消费（或我关心后续事件）**"。ViewGroup 返回 true 意味着它记住了 `mFirstTouchTarget`，后续 MOVE/UP 会继续沿这条链分发。
   - `onInterceptTouchEvent` 返回 **true**：表示"**我拦截，不再传给子 View**"。此时子 View 会收到 CANCEL。
   - `onTouchEvent` 返回 **true**：表示"**我消费了**"，后续同序列的 MOVE/UP 都会发给我。返回 false 则事件可能转交给父容器或兄弟 View。
3. **分发顺序（自上而下）**：
   ```text
   父.dispatchTouchEvent
     → 父.onInterceptTouchEvent   （返回 true 则中断向下分发）
     → 子.dispatchTouchEvent
          → 子.onInterceptTouchEvent
          → 子.onTouchEvent
     → 父.onTouchEvent            （没有子 View 消费时兜底）
   ```
4. **面试话术**：一句话——"**dispatch 是分发的决定者，intercept 是拦截权，touch 是消费权；消费了 DOWN 才有资格收到后续 MOVE/UP。**"

---

**读者问：父 View 的 `onTouchEvent` 返回 `false` 会发生什么？**

**AI答：**

1. **DOWN 阶段**：如果没有任何子 View 消费（所有子 View 的 `onTouchEvent` 都返回 false），事件最终落到父 View 的 `onTouchEvent`。
2. **父 View 返回 false**：
   - 整个 ViewGroup 的 `dispatchTouchEvent` 返回 **false**。
   - 事件继续**向上冒泡**给父 View 的父容器（如果当前 ViewGroup 是子 View）。最终如果根 View 也不消费，这一串手势就"无人处理"，系统不再派发后续的 MOVE/UP。
   - 效果就是：这次点击**没有任何反应**（没有 ripple、没有 pressed 状态、不会触发 `performClick`）。
3. **常见踩坑**：
   - 自定义 ViewGroup 忘了实现 `onTouchEvent` 的 `ACTION_DOWN` 分支返回 true → 整个 ViewGroup 完全不能点。
   - 自定义 View 忘了 `setClickable(true)` → 默认 `onTouchEvent` 返回 false → 点击无效。
   - `onTouchEvent` 返回 true 但没调用 `performClick()` → `OnClickListener` 不触发、无障碍（Accessibility）事件缺失。
4. **正确姿势**：
   ```java
   @Override
   public boolean onTouchEvent(MotionEvent event) {
       if (event.getActionMasked() == MotionEvent.ACTION_DOWN) {
           return true;   // 必须消费 DOWN，才能收到后续 MOVE/UP
       }
       ...
       return super.onTouchEvent(event);
   }
   ```

**读者问：`requestDisallowInterceptTouchEvent` 到底做了什么？为什么必须在 `ACTION_DOWN` 里调用？**

**AI答：**

1. **内部机制**：`View.requestDisallowInterceptTouchEvent(true)` 会调用 `parent.requestDisallowInterceptTouchEvent(true)` 沿父链冒泡，最终由 `ViewGroup` 设置 `FLAG_DISALLOW_INTERCEPT` 标记。
2. **效果**：`ViewGroup.dispatchTouchEvent` 中的判断变为：
   ```java
   if ((mGroupFlags & FLAG_DISALLOW_INTERCEPT) == 0 && disallowInterceptIntercept(ev)) {
       intercepted = onInterceptTouchEvent(ev);
   } else {
       intercepted = false;    // 跳过拦截，直接给子 View
   }
   ```
   即**在标记生效期间，父容器不再调用 `onInterceptTouchEvent`**。
3. **为什么必须在 DOWN 调用**：`ViewGroup` 在每次 `ACTION_DOWN` 开始时会执行 `resetTouchState` / `clearGroupTouchFlag(FLAG_DISALLOW_INTERCEPT)`，**清除该标记**。所以标记的有效期是"**从 DOWN 到下一次 DOWN**"。
4. **典型用法**：
   - 横向滑动列表嵌在竖向 `ScrollView` 中 → DOWN 时 `requestDisallowInterceptTouchEvent(true)`，防止父 ScrollView 抢走横向手势。
   - 列表项中的横向滑动控件（like 按钮滑动）→ 主动"锁"住手势。
5. **必须记得恢复**：在 `ACTION_UP` / `ACTION_CANCEL` 时调用 `requestDisallowInterceptTouchEvent(false)`，否则后续手势父容器将永远无法拦截。
6. **与 `onInterceptTouchEvent` 的选择**：
   - 父拦截：**动态**，可在 MOVE 阶段根据方向切换（ViewPager 常用）。
   - 子请求：**静态**，整串手势一票否决（横向列表常用）。

**读者问：滑动冲突（横向 ViewPager 和竖向 ScrollView）有哪些解决方案？**

**AI答：**

1. **方案一：父容器 `onInterceptTouchEvent` 判断方向**（最通用）。
   ```java
   @Override
   public boolean onInterceptTouchEvent(MotionEvent ev) {
       if (ev.getActionMasked() == MotionEvent.ACTION_MOVE) {
           float dx = Math.abs(ev.getX() - ev.getDownX());
           float dy = Math.abs(ev.getY() - ev.getDownY());
           if (dx > dy) return true;    // 横向意图 → 父容器拦截
       }
       return false;
   }
   ```
   配套：子 View 收到 CANCEL 后要清理自身状态。
2. **方案二：子 View `requestDisallowInterceptTouchEvent(true)`**（子 View 主动锁定）。
3. **方案三：嵌套滚动（NestedScrolling）**——Android 5.0+ 提供的标准解法：
   - `NestedScrollingChild`（如 `RecyclerView`）实现 `onNestedPreScroll` / `onNestedScroll`；
   - `NestedScrollingParent`（自定义容器）实现 `onNestedPreScroll` / `onNestedScroll` / `onNestedFling` / `onNestedPreFling`；
   - 好处：父子**同时**参与滚动，能自然地"先滚动完父再滚子"，无需互相打断。
4. **方案四：使用 `ViewPager2` + `NestedScrollView`**，官方已处理冲突（`ViewPager2` 用 `RecyclerView` 实现）。
5. **方案五（Compose）**：用 `Modifier.nestedScroll` 配合 `NestedScrollConnection`，父级声明 `onPreScroll` 消费剩余 delta。
6. **面试话术**：先讲方向判断（最常见），再讲 `requestDisallowInterceptTouchEvent`（子主动），最后提 **NestedScrolling 是官方推荐**，能避免"手势被抢断"的突兀感。

**读者问：`VelocityTracker` 有什么坑？`GestureDetector` 的 `onFling` 速度单位是什么？**

**AI答：**

1. **`VelocityTracker` 的 4 个坑**：
   - **必须 recycle**：`VelocityTracker.obtain()` 是池化的，用完 `recycle()`，否则内存泄漏 + 复用串数据。
   - **必须 `addMovement`**：不调 `addMovement` 则速度恒为 0。
   - **必须先 `computeCurrentVelocity(1000)`** 才能取速度，单位是 **px/秒**；不传参数则默认单位是 1（即 px/毫秒），数值会差 1000 倍。
   - **多指事件**：`getXVelocity()` 默认取第 0 个指针，多指场景要用 `getXVelocity(pointerIndex)`。
2. **`GestureDetector` 的关键语义**：
   - `onDown` **必须返回 true**，否则后续的 `onScroll` / `onFling` 等回调不会触发（Detector 用 `onDown` 的返回值决定是否继续处理）。
   - `onFling` 的 `velocityX/velocityY` 单位是 **px/秒**，是手指在 UP 前的瞬时速度。
   - `onSingleTapUp` 在 UP 时立刻回调；`onSingleTapConfirmed` 会等到确认无双击后（延迟 ~300ms）才回调。**单击业务通常用 `onSingleTapConfirmed`**。
   - `onLongPress` 需要 `setIsLongpressEnabled(true)`（默认开启）。
3. **面试话术**："**`GestureDetector` 是把原始 MotionEvent 翻译成语义手势的翻译器，`VelocityTracker` 是它的测速仪；两者配合才能做出顺滑的 fling。**"

**读者问：自定义 View 的点击没反应是什么原因？**

**AI答：**

按排查顺序：

1. **没有 `setClickable(true)`**：`View.onTouchEvent` 默认实现是
   ```java
   if (clickable || longClickable) { ... return true; }
   return false;
   ```
   自定义 View 默认 `clickable = false` → `onTouchEvent` 返回 false → 事件无人消费。**这是 90% 的原因**。
2. **重写了 `onTouchEvent` 但 DOWN 分支没返回 true** → 收不到后续事件。
3. **重写了 `onTouchEvent` 但没调用 `performClick()`** → `setOnClickListener` 不触发，同时无障碍服务读不到点击事件（TalkBack 无响应）。
4. **父容器拦截了事件**：检查父 `onInterceptTouchEvent` 是否误返回 true。
5. **View 被 `setEnabled(false)` 或 `setVisibility(GONE)`**。
6. **触摸区域太小**：即使可点击，命中区域不足也点不到；可用 `TouchDelegate` 扩大热区。
7. **正确写法**：
   ```java
   @Override
   public boolean onTouchEvent(MotionEvent event) {
       switch (event.getActionMasked()) {
           case MotionEvent.ACTION_DOWN:
               setPressed(true);
               invalidate();
               return true;
           case MotionEvent.ACTION_UP:
               setPressed(false);
               invalidate();
               if (isClickable()) performClick();   // 触发 OnClickListener
               return true;
           case MotionEvent.ACTION_CANCEL:
               setPressed(false);
               invalidate();
               return true;
       }
       return super.onTouchEvent(event);
   }
   ```

**读者问：Compose 里有没有类似 ViewGroup 的事件分发和拦截机制？**

**AI答：**

1. **没有拦截机制**。Compose 的事件在 **Modifier 链** 上传播（`pointerInput`），不是父子 View 的责任链。
2. **消费机制不同**：Compose 用 `change.consume()` 显式"消费" delta。被消费后，外层 Modifier 不会收到该 delta，但**外层仍然会收到事件**（区别于 View 的"消费即夺走"）。
3. **顺序**：`Modifier.padding().clickable()` 中，`clickable` 比 `padding` 更靠近内容，事件先到 `clickable`；但 `Modifier.clickable().padding()` 则相反。**Modifier 顺序影响事件处理顺序**（与 View 相反）。
4. **重启机制**：`pointerInput(key1, key2)` 的 key 变化时，旧协程被取消、新的手势检测协程启动。key 通常传"手势依赖的状态"。
5. **对比**：
   | 维度 | View | Compose |
   | --- | --- | --- |
   | 分发 | 父 → 子 的责任链 | Modifier 链 |
   | 拦截 | `onInterceptTouchEvent` | 无；用 `consume()` 部分消费 |
   | 手势识别 | `GestureDetector` | `detectDragGestures` / `detectTapGestures` |
   | 速度 | `VelocityTracker` | `VelocityTracker`（`androidx.compose.ui.input.pointer.util.VelocityTracker`） |

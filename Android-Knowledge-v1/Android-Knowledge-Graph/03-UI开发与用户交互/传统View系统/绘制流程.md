# 绘制流程

## 一句话定义

Android 的 View 绘制是一条**自上而下的树形流水线**：`measure` 量出每个 View 有多大、`layout` 决定每个 View 摆在哪个位置、`draw` 把内容画到 Canvas 上。这个过程由 `ViewRootImpl.performTraversals()` 驱动，一次遍历可能只执行 `draw`（轻量重绘），也可能执行完整的 `measure + layout + draw`（尺寸变化或 `requestLayout`）。

## 核心原理

### 1. 三段式绘制总览

```
┌───────────────────────────────────────────────────────────────┐
│                    ViewRootImpl.performTraversals()            │
│                                                               │
│   performMeasure()      performLayout()       performDraw()   │
│        │                      │                     │        │
│        ▼                      ▼                     ▼        │
│   ┌─────────┐           ┌─────────┐           ┌─────────┐    │
│   │ measure │           │  layout │           │  draw   │    │
│   │  量大小  │           │ 定位置  │           │  画内容  │    │
│   └─────────┘           └─────────┘           └─────────┘    │
│        │                      │                     │        │
│   自顶向下传约束            自顶向下传位置            自顶向下画  │
│   自底向上回尺寸            自底向上回尺寸            逐个 drawChild│
└───────────────────────────────────────────────────────────────┘
```

关键方向性区别（**面试常考的第一个坑**）：

| 阶段 | 尺寸/位置的数据流向 | 谁调用 `onMeasure`/`onLayout`/`onDraw` |
| --- | --- | --- |
| measure | **父 → 子**传 `MeasureSpec`；**子 → 父**回 `measuredDimension` | 父 ViewGroup 调用子 View 的 `onMeasure` |
| layout | **父 → 子**传 `left/top/right/bottom` | 父 ViewGroup 调用子 View 的 `onLayout` |
| draw | **父 → 子**画（`dispatchDraw` → `drawChild`） | 父 ViewGroup 调 `child.draw(canvas)` |

> 结论：**measure 和 layout 都是"父问子、父定、子答"，只有 draw 是"父画子的内容"**。

### 2. measure 阶段与 MeasureSpec

`MeasureSpec` 是一个 32 位 int，高 2 位存 `mode`，低 30 位存 `size`：

```text
 31        30 29                                        0
┌────────────┬────────────────────────────────────────────┐
│   mode     │                  size                     │
│  2 bits    │                 30 bits                   │
└────────────┴────────────────────────────────────────────┘

mode:
  UNSPECIFIED = 0b00  // 0x00000000 父不约束，子想多大就多大
  EXACTLY     = 0b01  // 0x40000000 父指定精确尺寸，子必须等于 size
  AT_MOST     = 0b10  // 0x80000000 父给上限，子不能超过 size
```

`MeasureSpec` 的组合规则：

```text
makeMeasureSpec(size, mode) = (size & 0x3fffffff) | (mode << 30)

getMode(spec)  = spec & 0xc0000000
getSize(spec)  = spec & 0x3fffffff
```

**谁生成 MeasureSpec？**

- 父容器调用 `measureChildWithMargins` 时构造。
- `ViewGroup.measureChild`（有 margin / `LayoutParams`）→ `measureChildWithMargins` → 对 child 调用 `child.measure(getChildMeasureSpec(...), heightMeasureSpec)`。
- `getChildMeasureSpec(parentSpec, padding, childDimension)` 的推导规则：

| 父 Spec mode | 子 LayoutParams | 传给子的 mode |
| --- | --- | --- |
| EXACTLY | MATCH_PARENT(-1) | EXACTLY，size = 父可用空间 |
| EXACTLY | WRAP_CONTENT(-2) | AT_MOST，size = 父可用空间 |
| EXACTLY | 固定 dp | EXACTLY，size = 固定值 |
| AT_MOST | MATCH_PARENT | AT_MOST，size = 父上限 |
| AT_MOST | WRAP_CONTENT | AT_MOST，size = 父上限 |
| AT_MOST | 固定 dp | EXACTLY，size = 固定值 |
| UNSPECIFIED | 任意 | UNSPECIFIED（或固定值→EXACTLY） |

**`View.onMeasure` 的默认实现**：

```java
protected void onMeasure(int widthMeasureSpec, int heightMeasureSpec) {
    setMeasuredDimension(
        getDefaultSize(getSuggestedMinimumWidth(), widthMeasureSpec),
        getDefaultSize(getSuggestedMinimumHeight(), heightMeasureSpec)
    );
}

public static int getDefaultSize(int size, int measureSpec) {
    int specMode = MeasureSpec.getMode(measureSpec);
    int specSize = MeasureSpec.getSize(measureSpec);
    switch (specMode) {
        case MeasureSpec.AT_MOST:
        case MeasureSpec.EXACTLY:
            return specSize;          // 有约束就用约束
        case MeasureSpec.UNSPECIFIED:
        default:
            return size;               // 无约束用建议最小尺寸
    }
}
```

注意 `AT_MOST` 分支里 `getDefaultSize` **直接返回 specSize**，而不是 `min(suggested, specSize)` —— 这就是为什么自定义 View 默认实现下 `wrap_content` 会"撑满父容器"。

**优化 `onMeasure` 的正确写法**：

```java
int width = resolveSizeAndState(suggestedMinimumWidth, widthMeasureSpec, 0);
int height = resolveSizeAndState(suggestedMinimumHeight, heightMeasureSpec, 0);
setMeasuredDimension(width, height);
```

`resolveSize` 的逻辑才是"正确"的：

```text
EXACTLY  -> specSize
AT_MOST  -> min(suggestedSize, specSize)   // WRAP_CONTENT 才不会撑满
UNSPECIFIED -> suggestedSize
```

**`measureChildren` 与 `measureChild` 的区别**：

- `measureChildren(widthSpec, heightSpec)`：遍历所有子 View，**用同一组 Spec** 给每个子 View（忽略各自的 LayoutParams），子 View 数量多时效率低。
- `measureChildWithMargins(child, parentWidthSpec, widthUsed, parentHeightSpec, heightUsed)`：为每个子 View 单独按其 `LayoutParams` 计算 Spec，**正确但更耗**。
- `ViewGroup.measureChildWithMargins` 默认实现：`getChildMeasureSpec(parentSpec, padding + margins + used, child.layoutParams.<width|height>)`。

### 3. layout 阶段

```java
// View
public void layout(int l, int t, int r, int b) {
    boolean changed = (mPrivateFlags3 & PFLAG3_MEASURE_NEEDED_BEFORE_LAYOUT) != 0;
    if (changed || (l != mLeft || t != mTop || r != mRight || b != mBottom)) {
        changed = true;
        onLayout(changed, l, t, r, b);   // 交给子类实现
        ...
    }
}
```

`View.onLayout` 的默认实现是 `setFrame(l, t, r, b)` —— 即**只记录位置，不摆放任何子 View**。

`ViewGroup.onLayout` 的默认实现是空方法，必须由子类实现。典型实现：

```java
@Override
protected void onLayout(boolean changed, int l, int t, int r, int b) {
    for (int i = 0, count = getChildCount(); i < count; i++) {
        final View child = getChildAt(i);
        if (child.getVisibility() == GONE) continue;   // 跳过 GONE
        final LayoutParams lp = (LayoutParams) child.getLayoutParams();
        final int left = l + lp.leftMargin;
        final int top = t + lp.topMargin;
        final int childWidth = child.getMeasuredWidth();
        final int childHeight = child.getMeasuredHeight();
        child.layout(left, top, left + childWidth, top + childHeight);
    }
}
```

`layout()` 的作用：
1. 调用 `onLayout`，让父类把自己的子 View 摆放好。
2. 在 `setFrame` 中记录 `mLeft/mTop/mRight/mBottom`（**最终位置**）与 `mScrollX/mScrollY`。
3. `mPrivateFlags3 &= ~PFLAG3_MEASURE_NEEDED_BEFORE_LAYOUT`，清除"需要重新测量"的标记。
4. 触发 `onSizeChanged`（尺寸变化时）。

> 面试点：`getLeft()/getTop()` 返回的是**父容器坐标系**下的位置；`getX()/getY()` = `getLeft() + translationX`，`getTranslationX()` 是动画位移。三个概念混用是新手最常犯的错。

### 4. draw 阶段

```java
// View.draw(Canvas) 的骨架（Android 源码精简）
public void draw(Canvas canvas) {
    int saveCount;
    // 1. 绘制背景（background drawable）
    if (mBackground != null) {
        ...
    }
    // 2. onDraw：绘制内容（子类重写点）
    onDraw(canvas);
    // 3. dispatchDraw：绘制子 View
    dispatchDraw(canvas);
    // 4. 绘制装饰（foreground / scrollbars）
    ...
}
```

`ViewGroup.dispatchDraw`：

```java
protected void dispatchDraw(Canvas canvas) {
    final int count = getChildCount();
    for (int i = 0; i < count; i++) {
        final View child = getChildAt(i);
        if ((child.mPrivateFlags & PFLAG_DRAWN) != PFLAG_DRAWN) {
            // 尚未被绘制过 → 先测一次
            more = measureChildForAccessibility(...);
        }
        if (more) { ... }
        if (!child.hasIdentityMatrix() ...) { child.draw(canvas, this); }
    }
}
```

`ViewGroup.drawChild` 的核心：**先算 `child` 是否完全落在自己的可见区域内（clip）**，如果完全不可见且没有动画，直接跳过绘制（这就是 `clipChildren`/`clipToPadding` 的性能意义）。

```text
View.draw(canvas)
 ├─ 背景 drawable
 ├─ onDraw(canvas)            ← 你重写这里画内容
 ├─ dispatchDraw(canvas)      ← ViewGroup 遍历子 View 调 child.draw()
 │    └─ drawChild → child.draw(canvas, this)
 ├─ foreground
 └─ scrollbar / 装饰
```

**硬件加速下的差异**：API 21+ 默认硬件加速，`onDraw` 中的绘制指令会被录制进 **DisplayList**（`RecordingCanvas`），再由 RenderThread 一次性提交给 GPU。`Canvas.drawBitmap` 等命令**不会立即执行**，而是延迟执行。副作用：
- `canvas.getMatrix()` / `getTextBounds` 等查询类 API 在硬件加速下会抛 `IllegalArgumentException`（部分 API 被禁用）。
- `Picture` / `Canvas` 截图需要 `setLayerType(LAYER_TYPE_SOFTWARE, null)` 或用 `PixelCopy`。

### 5. requestLayout vs invalidate

这是**本主题最高频的面试题**。

| 对比项 | `requestLayout()` | `invalidate()` |
| --- | --- | --- |
| 作用 | 标记"尺寸可能变了"，需要**重新测量 + 重新布局 + 重新绘制** | 只标记"内容变了"，**只重新绘制** |
| 触发条件 | 子 View 的尺寸约束发生变化（`LayoutParams` 变化、依赖父容器尺寸） | 只是内容/颜色/文字变化，尺寸不变 |
| 内部实现 | `PFLAG_FORCE_LAYOUT` 标记 → 下一帧执行 `performMeasure` + `performLayout` | `PFLAG_DIRTY` / `PFLAG_INVALIDATE` 标记 → 下一帧只执行 `performDraw` |
| 代价 | 高（整棵树重新测量） | 低（只重绘） |
| 典型调用 | `setText` 导致 `TextView` 尺寸可能变（其实 `TextView` 用的是 `requestLayout`） | `setTextColor`、`setImageBitmap`、自定义 View 中属性变化但尺寸不变 |

```text
requestLayout()
   │
   ├─ View.requestLayout()  → setPFLAG_LAYOUT_REQUIRED
   │     └─ 若未在布局中，requestLayout 会向上冒泡到 ViewRootImpl
   └─ ViewRootImpl.requestLayout()
         └─ mLayoutRequested = true
               └─ scheduleTraversals() → mTraversalScheduled = true
                     └─ Choreographer.postCallback(CALLBACK_TRAVERSAL, mTraversalRunnable)

下一帧 performTraversals():
   if (mLayoutRequested) {
       performMeasure();     // → measure → onMeasure
       performLayout();      // → layout → onLayout
       mLayoutRequested = false;
   }
   performDraw();            // → draw
```

> **一个高频追问**：为什么 `requestLayout` 有时"没生效"？
> 答案：① 在 `layout` 过程中调用 `requestLayout` 会被忽略（`isInLayout()` 判断）；② 若 `View` 尚未 attach 到 window，`requestLayout` 只是打标记，等到 attach 后才处理；③ `requestLayout` **不会跨过 ViewGroup 的 `onMeasure` 重新测量兄弟节点**——如果子 View 的尺寸依赖父容器给的约束，`requestLayout` 后 `measureChild` 才会重新给 Spec。

### 6. ViewRootImpl 的调度：performTraversals

```text
Choreographer.doFrame()
   │
   ├─ doCallbacks(CALLBACK_INPUT)          ← 处理输入事件
   ├─ doCallbacks(CALLBACK_ANIMATION)      ← 动画
   ├─ doCallbacks(CALLBACK_TRAVERSAL)      ← mTraversalRunnable
   │     └─ ViewRootImpl.performTraversals()
   │           ├─ performMeasure()   → mMeasuredWidth/Height
   │           ├─ performLayout()    → mLayoutRequested = false
   │           └─ performDraw()      → scheduleTraversals → mTraversalScheduled = false
   ├─ doCallbacks(CALLBACK_COMMIT)         ← RenderThread 同步
   └─ mLastFrameTimeNanos = frameTimeNanos
```

`performTraversals()` 的核心判断：

```text
boolean performTraversals() {
    ...
    boolean isLayoutRequested = mLayoutRequested;   // requestLayout 标记
    boolean isTraversalScheduled = mTraversalScheduled; // invalidate 标记
    ...
    if (mFirst || isLayoutRequested || ...) {
        performMeasure();     // 1
        performLayout();      // 2
    }
    ...
    performDraw();            // 3
    ...
}
```

**`measureHierarchy` 与"为什么一次 requestLayout 会引发两遍 measure"**：
`ViewRootImpl.measureHierarchy()` 在 `performMeasure()` 内部被调用，它对** DecorView → ContentView → 整棵子树**做一次"是否需要重新测量"的协商；如果发现某层需要重测，会调用 `measureChildWithMargins` 递归下去，导致**外层测量一次、内层又测一次**。这就是 Android 中"嵌套层级越深，measure 成本呈指数级上升"的根源，也是 `ConstraintLayout` 存在的意义。

### 7. 从 setContentView 到第一帧的完整链路

```text
Activity.onCreate()
   └─ setContentView(layoutRes)
        ├─ mWindow.setContentView(layoutRes)
        │     └─ PhoneWindow.setContentView
        │           ├─ installDecor()                    ← 创建 DecorView
        │           │     ├─ generateDecor()              ← 创建 DecorView（ActionBar 容器）
        │           │     └─ mDecor = ...
        │           └─ mContentParent = mDecor.findViewById(android.R.id.content)
        │                 └─ LayoutInflater.inflate(layoutRes, mContentParent)
        │                       └─ 创建 ContentView（我们的布局根节点）
        └─ mWindow.getWindowManager().addView(mDecor, mWindow.getAttributes())
              └─ WindowManagerImpl.addView
                    └─ mViewRoot = new ViewRootImpl(view.getContext())
                    └─ mViewRoot.setView(view, params)
                          └─ requestLayout() → scheduleTraversals()

下一帧：
Choreographer.doFrame
   └─ ViewRootImpl.performTraversals()
         ├─ measureHierarchy() → performMeasure()   （第一次测量）
         ├─ performLayout()
         └─ performDraw()                             ← 第一帧渲染
```

**DecorView 的结构**（不同版本略有差异）：

```text
PhoneWindow
 └─ DecorView (FrameLayout)
      ├─ [ActionBar 区域] (ActionBarOverlayLayout)
      │    └─ 内容容器 (contentParent)
      │         └─ 你的布局根 View
      ├─ 状态栏背景 (可选)
      └─ 导航栏背景 (可选)
```

> 面试点：**`getWindow().getDecorView().findViewById(android.R.id.content)`** 拿到的是承载你布局的容器；`setContentView` 会把 DecorView 加到 WindowManager，此后系统才有了 ViewRootImpl。

### 8. 传统 View 与 Compose 绘制流程对比

| 维度 | 传统 View | Jetpack Compose |
| --- | --- | --- |
| 单位 | View 节点树 | Compose 节点树（`LayoutNode`） |
| 测量 | `measure`/`onMeasure`（自定尺寸） | `MeasurePolicy.measure`（`SubcomposeMeasureScope`） |
| 布局 | `layout`/`onLayout`（定位置） | `place`/`Placeable.place`（绝对定位） |
| 绘制 | `draw`/`onDraw`（`Canvas` 指令） | `DrawScope`（`Canvas` 指令） |
| 触发 | `requestLayout` / `invalidate` | 状态变更 → **重组** → 重新布局/绘制 |
| GPU 提交 | `DisplayList` → RenderThread | `RenderNode` → RenderThread |
| 失效粒度 | 整棵子树（invalidate 可带矩形） | **可跳过**（`@Stable` + 未读状态不变） |

## 代码示例

### 1. 标准自定义 View 的 measure/layout/draw 全实现

```java
public class RingProgressView extends View {

    private final Paint ringPaint = new Paint(Paint.ANTI_ALIAS_FLAG);
    private final Paint textPaint = new Paint(Paint.ANTI_ALIAS_FLAG);
    private float progress = 0f;                 // 业务状态：0~1
    private final RectF arcRect = new RectF();

    // 构造器链：Context / AttributeSet / defStyleAttr
    public RingProgressView(Context context) { this(context, null); }
    public RingProgressView(Context context, AttributeSet attrs) {
        this(context, attrs, 0);
    }
    public RingProgressView(Context context, AttributeSet attrs, int defStyleAttr) {
        super(context, attrs, defStyleAttr);
        ringPaint.setStyle(Paint.Style.STROKE);
        ringPaint.setStrokeWidth(8f);
        textPaint.setTextAlign(Paint.Align.CENTER);
        textPaint.setTextSize(32f);
    }

    /** 业务状态变更：只影响内容，不影响尺寸 → invalidate 即可 */
    public void setProgress(float progress) {
        this.progress = progress;
        invalidate();          // 只重绘，不重新测量与布局
    }

    @Override
    protected void onMeasure(int widthMeasureSpec, int heightMeasureSpec) {
        // 1. 依据约束计算期望尺寸（支持 wrap_content）
        int desired = dpToPx(120);   // 期望 120dp
        int width = resolveSize(desired, widthMeasureSpec);
        int height = resolveSize(desired, heightMeasureSpec);
        // 2. 保证宽高一致（正圆）
        int size = Math.min(width, height);
        setMeasuredDimension(size, size);
    }

    @Override
    protected void onLayout(boolean changed, int l, int t, int r, int b) {
        // View 无子 View，onLayout 默认只 setFrame，通常无需重写
    }

    @Override
    protected void onDraw(Canvas canvas) {
        super.onDraw(canvas);       // 会绘制 background
        int w = getWidth(), h = getHeight();
        float cx = w / 2f, cy = h / 2f;
        float radius = Math.min(w, h) / 2f - ringPaint.getStrokeWidth();

        // 预计算 RectF，避免在 onDraw 里 new 对象（造成 GC 抖动）
        arcRect.set(cx - radius, cy - radius, cx + radius, cy + radius);

        canvas.drawCircle(cx, cy, radius, ringPaint);   // 底圈
        canvas.drawArc(arcRect, -90f, 360f * progress, false, ringPaint);
        canvas.drawText(String.format("%.0f%%", progress * 100),
                cx, cy - (textPaint.ascent() + textPaint.descent()) / 2f, textPaint);
    }
}
```

### 2. 自定义 ViewGroup：手动测量与摆放

```java
public class FlowLayout extends ViewGroup {

    public FlowLayout(Context context, AttributeSet attrs) { super(context, attrs); }

    /** measure：先问每个孩子想要多大，再按行分配 */
    @Override
    protected void onMeasure(int widthMeasureSpec, int heightMeasureSpec) {
        int widthMode = MeasureSpec.getMode(widthMeasureSpec);
        int widthSize = MeasureSpec.getSize(widthMeasureSpec);
        int availableWidth = widthSize - getPaddingLeft() - getPaddingRight();

        int childWidth = 0, childHeight = 0, lineHeight = 0;
        int totalWidth = 0, totalHeight = 0;

        // 逐个测量：让每个子 View 拿到自己的 MeasureSpec
        measureChildWithMargins(child, 0, 0, 0, 0) 伪代码 → 实际见下
        for (int i = 0; i < getChildCount(); i++) {
            final View child = getChildAt(i);
            if (child.getVisibility() == GONE) continue;
            measureChildWithMargins(child, 0, 0, widthMeasureSpec, 0);
            final LayoutParams lp = (LayoutParams) child.getLayoutParams();
            childWidth = child.getMeasuredWidth() + lp.leftMargin + lp.rightMargin;
            childHeight = child.getMeasuredHeight() + lp.topMargin + lp.bottomMargin;

            if (childWidth > availableWidth) {           // 换行
                totalWidth = Math.max(totalWidth, childWidth);
                totalHeight += lineHeight;
                lineHeight = childHeight;
                childWidth = childWidth;                 // 新行第一个孩子
            } else {
                childWidth += childWidth;                // 同行累加（注意命名易混）
                lineHeight = Math.max(lineHeight, childHeight);
            }
        }
        totalHeight += lineHeight;

        int w = resolveSize(totalWidth + getPaddingLeft() + getPaddingRight(), widthMeasureSpec);
        int h = resolveSize(totalHeight + getPaddingTop() + getPaddingBottom(), heightMeasureSpec);
        setMeasuredDimension(w, h);
    }

    /** layout：把测量好的孩子摆到具体坐标 */
    @Override
    protected void onLayout(boolean changed, int l, int t, int r, int b) {
        int x = getPaddingLeft(), y = getPaddingTop();
        int lineHeight = 0;
        for (int i = 0; i < getChildCount(); i++) {
            final View child = getChildAt(i);
            if (child.getVisibility() == GONE) continue;
            final LayoutParams lp = (LayoutParams) child.getLayoutParams();
            if (x + child.getMeasuredWidth() > r - getPaddingRight()) {
                x = getPaddingLeft();
                y += lineHeight;
                lineHeight = 0;
            }
            child.layout(x + lp.leftMargin, y + lp.topMargin,
                         x + lp.leftMargin + child.getMeasuredWidth(),
                         y + lp.topMargin + child.getMeasuredHeight());
            x += child.getMeasuredWidth() + lp.leftMargin + lp.rightMargin;
            lineHeight = Math.max(lineHeight, child.getMeasuredHeight() + lp.topMargin + lp.bottomMargin);
        }
    }

    /** 必须提供 LayoutParams，否则 inflate 会抛异常 */
    @Override
    public LayoutParams generateLayoutParams(AttributeSet attrs) {
        return new MarginLayoutParams(getContext(), attrs);
    }
    @Override
    protected LayoutParams generateDefaultLayoutParams() {
        return new MarginLayoutParams(LayoutParams.MATCH_PARENT, LayoutParams.WRAP_CONTENT);
    }
    @Override
    protected boolean checkLayoutParams(LayoutParams p) {
        return p instanceof MarginLayoutParams;
    }
}
```

### 3. requestLayout / invalidate 的正确使用场景

```java
public class BadgeView extends ViewGroup {

    private int count = 0;

    /** 数字变化可能导致 badge 尺寸变化 → 需要 requestLayout */
    public void setCount(int count) {
        if (this.count == count) return;
        this.count = count;
        requestLayout();      // 尺寸可能变 → 重新测量 + 布局 + 绘制
        invalidate();         // 同时请求重绘（requestLayout 已含，这里显式写更保险）
    }

    /** 颜色变化不影响尺寸 → 只 invalidate */
    public void setBadgeColor(int color) {
        badgePaint.setColor(color);
        invalidate();          // 只重绘
    }
}
```

### 4. 用 `Choreographer` 观察绘制节奏（排查掉帧）

```java
public class FrameWatcher implements Choreographer.FrameCallback {

    private long lastFrameNanos = 0;
    private final Choreographer choreographer = Choreographer.getInstance();

    public void start() {
        lastFrameNanos = 0;
        choreographer.postFrameCallback(this);
    }

    @Override
    public void doFrame(long frameTimeNanos) {
        if (lastFrameNanos != 0) {
            long frameMs = (frameTimeNanos - lastFrameNanos) / 1_000_000L;
            if (frameMs > 16) {
                Log.w("FrameWatcher", "掉帧：本次耗时 " + frameMs + "ms");
            }
        }
        lastFrameNanos = frameTimeNanos;
        choreographer.postFrameCallback(this);   // 继续监听
    }
}
```

## 常见问题 / 面试要点

**读者问：`requestLayout()` 和 `invalidate()` 到底有什么区别？什么时候用哪个？**

**AI答：**

1. **本质区别**：
   - `requestLayout()` = "**我的大小可能变了**" → 下一帧走 `performMeasure()` + `performLayout()` + `performDraw()`。**只影响自己的子树**。
   - `invalidate()` = "**我的内容变了，但大小没变**" → 下一帧只走 `performDraw()`。
2. **内部标记不同**：
   - `requestLayout()` → `View.setPFLAG_LAYOUT_REQUIRED` → 沿父链向上冒泡到 `ViewRootImpl` → `mLayoutRequested = true`。
   - `invalidate()` → `View.setPFLAG_DIRTY` + `setPFLAG_INVALIDATE` → 逐级向父 `invalidateChild()` 冒泡 → `ViewRootImpl.scheduleTraversals()` → `mTraversalScheduled = true`。
3. **能否只 invalidate 不 requestLayout？** 可以，但前提是**尺寸确实没变**。如果你在 `onDraw` 里根据某个状态改变了内容宽度却只调 `invalidate()`，会出现"画出来了但布局位置是旧的"，视觉上就是错位。
4. **能否只 requestLayout 不 invalidate？** 可以，`requestLayout` 最终也会触发 draw。但 `requestLayout` 成本高得多，能用 `invalidate` 就别用 `requestLayout`。
5. **一句话口诀**：**尺寸变了 → `requestLayout`；只是颜色、文字、图片、进度变了 → `invalidate`**。
6. **追问：为什么 `TextView.setText()` 内部用的是 `requestLayout()` 而不是 `invalidate()`？** 因为文字变长后 TextView 的宽高可能变化，需要重新测量与布局，否则会截断。
7. **追问：为什么 `requestLayout` 在 `layout()` 过程中调用会无效？** `View.layout()` 里有 `isInLayout()` 检查，`ViewGroup.setFrame` 期间若再次 `requestLayout` 会打上 `PFLAG3_MEASURE_NEEDED_BEFORE_LAYOUT`，延迟到下一帧处理。

**读者问：`MeasureSpec` 的三个 mode 分别是什么？父容器是怎么决定给子 View 传哪个 mode 的？**

**AI答：**

1. **三个 mode**：
   - `MeasureSpec.EXACTLY`（`0x40000000`）：父容器给出**精确尺寸**，子 View 必须按此尺寸绘制（`MATCH_PARENT` 或固定 dp）。
   - `MeasureSpec.AT_MOST`（`0x80000000`）：父容器给出**上限**，子 View 不得超过（典型是 `WRAP_CONTENT`）。
   - `MeasureSpec.UNSPECIFIED`（`0x00000000`）：父容器**不约束**，子 View 想多大就多大（典型是 `ScrollView` 的纵向子 View）。
2. **Spec 的组成**：32 位 int，高 2 位是 mode，低 30 位是 size。`makeMeasureSpec(size, mode)` = `(size & 0x3fffffff) | (mode << 30)`。
3. **父容器的推导规则**（`ViewGroup.getChildMeasureSpec`）：
   - 父 EXACTLY + 子 MATCH_PARENT → 子 EXACTLY，size = 父可用空间。
   - 父 EXACTLY + 子 WRAP_CONTENT → 子 AT_MOST，size = 父可用空间。
   - 父 AT_MOST + 子 MATCH_PARENT → 子 AT_MOST，size = 父上限。
   - 父 AT_MOST + 子 WRAP_CONTENT → 子 AT_MOST，size = 父上限。
   - 父 UNSPECIFIED + 子固定值 → 子 EXACTLY；+ 子 MATCH_PARENT/WRAP_CONTENT → 子 UNSPECIFIED。
   - 任何情况 + 子固定 dp → 子 EXACTLY，size = 固定值。
4. **面试话术**：可以背一句口诀——"**父给死，子随死；父给上限，子可以小但不能大；父不管，子自由**"。

---

**读者问：为什么自定义 View 的 `onMeasure` 里不能写死尺寸？该怎么正确处理 `wrap_content`？**

**AI答：**

1. **写死的后果**：
   - 父容器给 `EXACTLY`（比如 `match_parent`）时，写死尺寸 → View 尺寸与父容器不符 → 布局错位、内容被裁剪。
   - 用户开启"显示大小/字体放大"或不同屏幕密度时，固定 px 尺寸完全不可用。
   - 父容器给 `AT_MOST` 时，写死尺寸可能比父容器还大 → 溢出。
2. **正确做法**：
   ```java
   int desired = dpToPx(120);                        // 期望尺寸
   int width = resolveSize(desired, widthMeasureSpec); // EXACTLY→specSize; AT_MOST→min(desired,specSize); UNSPEC→desired
   setMeasuredDimension(width, height);
   ```
   `resolveSize()` 就是 `View.getDefaultSize()` 的修正版（`AT_MOST` 时取 `min` 而不是直接返回 `specSize`）。
3. **额外建议**：`View` 默认的 `onMeasure` 用 `getSuggestedMinimumWidth()`，它返回 `mMinimumWidth`（`minWidth` 属性）与背景图固有宽度的较大者。想让 `wrap_content` 生效，通常需要：
   - 在 `onMeasure` 里覆写并使用 `resolveSize`；
   - 或提供 `setMeasuredDimension` 的正确实现；
   - 若 View 需要内容驱动尺寸（如文本、图片），必须在 `onMeasure` 里考虑内容。
4. **追问：什么时候必须重写 `onMeasure`？** 当 View 的**尺寸不由父容器决定、也不固定**，而是"由内容决定且有自己的规则"时（如圆形进度条正方形、聊天气泡最大宽度 80%、自定义雷达图）。

---

**读者问：从 `setContentView` 到界面显示第一帧，中间经历了什么？**

**AI答：**

1. **主线程链路**：
   - `Activity.setContentView` → `PhoneWindow.setContentView` → `installDecor()`（创建 `DecorView` + `contentParent`）→ `LayoutInflater.inflate` 解析 XML 生成 View 树 → `mWindowManager.addView(mDecor, attrs)`。
   - `WindowManagerImpl.addView` → `new ViewRootImpl(context)` → `mViewRoot.setView(view, params)` → `requestLayout()` → `scheduleTraversals()` → `Choreographer.postCallback(CALLBACK_TRAVERSAL, ...)`。
2. **下一帧（VSync 到来）**：
   - `Choreographer.doFrame` → 输入事件回调 → 动画回调 → `CALLBACK_TRAVERSAL` 回调 → `ViewRootImpl.performTraversals()`。
   - `performTraversals()` → `measureHierarchy()` → `performMeasure()` → `measure` → `onMeasure` → `performLayout()` → `layout` → `onLayout` → `performDraw()` → `draw` → `onDraw`/`dispatchDraw`。
   - 绘制指令被记录进 `DisplayList`（硬件加速），`RenderThread` 在 `CALLBACK_COMMIT` 阶段同步并提交给 GPU → 真正显示到屏幕。
3. **关键点**：**`setContentView` 本身不绘制**，它只是"把 View 挂上去 + 预约一帧"。真正绘制发生在 Choreographer 的下一帧。
4. **面试话术**：很多人以为 `setContentView` 是同步渲染，其实它是**异步提交 + 下一帧渲染**。这也解释了为什么 `setContentView` 之后立即 `view.getWidth()` 得到的是 0 —— 此时还没 measure。

---

**读者问：为什么嵌套的 `LinearLayout` 会让测量次数变多？`ConstraintLayout` 是怎么解决的？**

**AI答：**

1. **测量次数翻倍的原因**：Android 的测量是"父问子"。`ViewRootImpl.measureHierarchy()` 先对 DecorView 测一次，得到宽高后**再拿这个结果**去测 ContentView —— 这就是第一层"翻倍"。如果 ContentView 内部还有 `LinearLayout`，`LinearLayout.onMeasure` 又要拿自己的 Spec 去测每个孩子，而 `LinearLayout` 内部还会先做一次 `measureVertical`/`measureHorizontal` 的估算，等拿到孩子尺寸后再用精确尺寸 **重测一遍**孩子 —— 这是第二层翻倍。
2. **为什么 LinearLayout 要测两遍**：因为 `weight` 的存在——只有在知道所有孩子尺寸后才能计算剩余空间，而孩子可能又依赖这个剩余空间（`layout_weight` + `match_parent` 组合）。为了正确性必须二次测量。
3. **指数级增长的代价**：嵌套 N 层，每层 2 次测量，最坏是 `2^N` 量级。层级 5~6 层、列表项里再嵌几层，在低端机上 measure 就能占到一帧预算（16ms）的很大比例。
4. **ConstraintLayout 的解法**：
   - 所有子 View **在一次测量中全部测量完**（平铺，无层层传递）；
   - 依赖关系通过**约束求解器**计算：先测量无依赖的，再按依赖拓扑序传播，必要时第二轮修正，但典型情况 1~2 轮搞定，而不是每层 2 轮。
   - 层级从 N 降到 1，测量成本从 `2^N` 降到接近 `O(N)`。
5. **面试话术**："**层级越深，measure 越贵；ConstraintLayout 把树拍平，用约束求解代替递归测量。**"

---

**读者问：硬件加速对绘制流程有什么影响？为什么 `canvas.getMatrix()` 会崩？**

**AI答：**

1. **原理**：API 21+ 默认硬件加速。`onDraw` 中的绘制命令不再**立即**由 CPU 执行，而是被 `RecordingCanvas` 录制成 **DisplayList**（一份绘制指令列表），在 `doFrame` 的 `CALLBACK_COMMIT` 阶段由 `RenderThread` 同步、交给 GPU 执行。
2. **好处**：CPU 只负责"录制"，GPU 负责"执行"，两者并行；同一 View 的多个 DisplayList 可共享 Shader/纹理。
3. **副作用（面试追问点）**：
   - **查询类 API 不可用**：`canvas.getMatrix()`、`canvas.getClipBounds()`、`canvas.getTextBounds()`、`canvas.getDrawFilter()` 在硬件加速下抛 `IllegalArgumentException: Method ... is not supported in hardware accelerated canvas`（部分被禁用）。
   - `Bitmap` 直接 `canvas.drawBitmap(bitmap, srcRect, dstRect, paint)` 是"贴图"操作，不支持 `Matrix` 之外的复杂变换（`save/rotate/scale` 组合是支持的）。
   - `Picture` 与 `View` 的截图：`View.draw(canvas)` 在硬件加速下只返回 DisplayList，需要 `PixelCopy` 或 `setLayerType(LAYER_TYPE_SOFTWARE)`。
4. **何时关闭硬件加速**：需要 `clipPath` 抗锯齿、离屏渲染、`saveLayer` 复杂合成时，可以对该 View 设置 `setLayerType(View.LAYER_TYPE_SOFTWARE, null)`，但会引入位图缓存与内存开销，**不要全局关闭**。
5. **面试话术**："**硬件加速下 Canvas 是录制器不是渲染器；查询类 API 失效，因此要避免在 `onDraw` 中做大量 `getTextBounds` 等测量**。"

---

**读者问：`View` 的 `getLeft()`、`getX()`、`getTranslationX()` 有什么区别？**

**AI答：**

1. `getLeft()/getTop()/getRight()/getBottom()`：**父容器坐标系**下的绝对位置，由 `layout()` 中的 `setFrame()` 写入。**不随动画变化**。
2. `getX()/getY()` = `getLeft() + getTranslationX()`（`getY()` 同理），**包含动画位移**。
3. `getTranslationX()/getTranslationY()`：**动画位移量**，属性动画修改的就是它，`getX()` 会跟着变。
4. `getScrollX()/getScrollY()`：滚动偏移量。
5. **常见坑**：
   - 用 `getLeft()` 做点击区域判断 → 动画中会算错；应该用 `getX()` 或 `getHitRect()`。
   - 父容器滚动后，儿子的 `getLeft()` 仍以父容器为坐标系，不受父 `scrollX` 影响。
   - `getGlobalVisibleRect()` / `getLocationOnScreen()` 才是屏幕坐标。
6. **面试话术**：记住一句话——"**`left/top` 是布局结果，`translation` 是动画结果，`x/y` 是两者之和**"。

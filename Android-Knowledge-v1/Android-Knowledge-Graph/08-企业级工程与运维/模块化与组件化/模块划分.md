# 模块划分

## 一句话定义

模块化是把一个巨大的 Gradle 工程**按职责边界切分成多个可独立构建、独立测试、独立发布的单元**，从而让编译变快、依赖可控、团队可并行。组件化（插件化）则是在此之上再加一层：**让业务模块在运行期可插拔**，做到真正的"动态组装"。

面试开场：**"模块化解决的是'依赖治理与编译效率'，组件化解决的是'业务隔离与动态化'。前者是工程组织问题，后者是运行时架构问题——它们的代价差了一个数量级。"**

## 核心原理

### 1. 模块化 vs 组件化（插件化）

| 维度 | 模块化（Modularization） | 组件化 / 插件化（Pluginization） |
| --- | --- | --- |
| **本质** | 构建期切分（Gradle module） | 运行期切分（可动态加载的 APK/DEX） |
| **编译期** | 每个模块独立编译为 AAR | 同上 |
| **运行期** | 全部代码静态打包进主 APK | 部分模块可作为独立 APK 动态加载 |
| **依赖方式** | `implementation project(...)` 编译期依赖 | 通过路由 + 接口 + 反射/类加载通信 |
| **类加载** | 单一 ClassLoader | 需要自定义 ClassLoader 与路由表 |
| **单独调试** | 可以（模块可作为 application 变体） | 可以（宿主壳工程） |
| **独立发布** | 不可以（最终合成一个 APK） | 可以（插件包可单独下发） |
| **包体影响** | 无（代码总量不变） | 宿主变小，插件按需下载 |
| **技术成本** | 低（主要是 Gradle 配置） | 高（自研 ClassLoader、路由、资源重定向） |
| **适合场景** | 中大型项目、需要并行协作 | 超大型项目、需要热更新/插件化生态 |
| **主要收益** | 编译提速、依赖清晰、并行开发 | 业务隔离、动态化、减少安装包 |

> **关键澄清**：国内很多团队把"组件化"当作"模块化"的同义词使用，面试时应该主动区分这个概念，并说明自己理解的差异——这是资深候选人的信号。

### 2. 分层模型

标准的 Android 模块分层：

```
┌───────────────────────────────────────────────────────────────┐
│  app（应用壳 / Application Module）                            │
│  职责：Application、MainActivity、路由注册、DI 根、主题、启动流程 │
│  依赖：可以依赖 feature、core-*                                 │
│  特点：唯一被"打包"的模块，applicationId / 签名 / 渠道在这里配置 │
└──────────────────────────┬────────────────────────────────────┘
                           │ 依赖所有 feature
┌──────────────────────────▼────────────────────────────────────┐
│  feature/*（业务功能模块，按业务域划分）                        │
│  feature-login / feature-profile / feature-order ...            │
│  职责：一个完整业务闭环（UI + ViewModel + 数据访问）            │
│  依赖：只能依赖 core-*，feature 之间【不允许】直接依赖           │
│  特点：可独立调试、可以被单独团队负责、可被 Feature Flag 关闭   │
└──────────────────────────┬────────────────────────────────────┘
                           │
┌──────────────────────────▼────────────────────────────────────┐
│  core-*（基础能力模块，技术维度划分）                          │
│  core-ui（通用 UI 组件、主题、扩展函数）                         │
│  core-network（OkHttp、Retrofit、拦截器、序列化）                 │
│  core-database（Room、DataStore、迁移）                         │
│  core-common（工具类、通用 Model、Result 封装）                 │
│  core-analytics（埋点、监控、日志）                              │
│  core-designsystem（设计系统：颜色、排版、Shape）                │
└──────────────────────────┬────────────────────────────────────┘
                           │
┌──────────────────────────▼────────────────────────────────────┐
│  build-logic（构建逻辑模块，included build）                    │
│  职责：Convention Plugin、依赖版本管理、构建工具                 │
│  特点：不参与 App 打包，独立于业务演进                          │
└───────────────────────────────────────────────────────────────┘
```

**为什么 core 按技术维度、feature 按业务维度划分**：

- **feature 按业务**：因为业务边界 = 需求边界 = 团队边界 = 发布单元边界，三者对齐。
- **core 按技术**：因为技术能力被多个 feature 复用，按业务拆 core 会导致 `core-login-ui`、`core-order-ui` 这种爆炸，且难以统一设计规范。

### 3. 模块类型

| 类型 | 产物 | 典型用途 | 注意 |
| --- | --- | --- | --- |
| **Android Library**（`com.android.library`） | AAR | 有 UI 或依赖 Android 框架的模块 | 必须设置 `namespace`，不再用 `package` |
| **Kotlin/JVM**（`org.jetbrains.kotlin.jvm`） | JAR | 纯 Kotlin 逻辑（工具类、算法、DTO） | **可在 JVM 上直接跑单测，速度极快** |
| **Dynamic Feature**（`com.android.dynamic-feature`） | 独立 APK/feature APK | Play Feature Delivery 按需下载 | 只能有**一个** dynamic feature，且依赖 `base` 模块 |
| **Test Module**（`com.android.test`） | 测试 APK | 独立的 instrumentation test | 独立于 app 的测试模块 |
| **Included Build**（`build-logic`） | 插件 jar | 构建逻辑 | 用 `includeBuild` 引入 |
| **Pure Kotlin Multiplatform** | 多平台产物 | 跨端共享逻辑 | 见第 9 部分 |

**关键建议：把能下沉为 Kotlin/JVM 的模块尽量下沉**。

```kotlin
// core-common 用 Kotlin/JVM 模块：单测无需 Robolectric，秒级完成
// core-network 用 Kotlin/JVM 模块：只依赖 Retrofit/OkHttp 等纯 JVM 库
// 只有真正需要 Context / 资源 / 生命周期的东西才放在 Android Library
```

好处：
1. **单测快 10 倍以上**（不需要 Android 运行时）。
2. **更少的后台线程限制**（Android Library 有 `consumerProguardFiles`、资源合并等额外约束）。
3. **更容易被其他平台复用**。

### 4. 依赖原则

#### 4.1 单向依赖铁律

```
app ──▶ feature-* ──▶ core-* ──▶ （第三方库）
  │          │           │
  └──────────┴───────────┘
     都不允许反向依赖
```

| 规则 | 说明 | 强制手段 |
| --- | --- | --- |
| **单向依赖** | 下层绝不依赖上层 | 自定义 Lint 规则（见 [[../代码规范与质量/Lint与静态检查]]） |
| **feature 之间不直接依赖** | 通过路由通信 | 自定义 Lint 规则 + 架构评审 |
| **core 之间不互相依赖** | 或只允许极小的公共层 | 约定 + Code Owner |
| **app 不写业务逻辑** | app 只做组装 | 人工 Review + 自定义 Lint |
| **依赖用 `implementation` 不用 `api`** | 避免传递依赖污染 | 约定 + `api` 使用审计 |

#### 4.2 feature 之间如何通信

这是组件化最核心的设计决策。四种方案的取舍：

| 方案 | 机制 | 优点 | 缺点 | 适用 |
| --- | --- | --- | --- | --- |
| **A. 路由跳转** | 通过路由框架传 ID，跳转后目标自己查数据 | 解耦最彻底 | 无法直接传对象、无法同步拿结果 | 跨业务模块的页面跳转 |
| **B. 共享 core 中的 Repository** | 都依赖 `core-data`，Repository 内用 `Hilt` 多绑定或 `ServiceLoader` | 类型安全、能共享缓存 | 需要在 core 中声明接口，实现由 feature 提供（需依赖倒置） | 跨模块的数据共享 |
| **C. 依赖倒置（接口下沉）** | 把接口放 `core-api`，实现在 feature，用 DI 注入 | 类型安全、可编译期检查 | core 需要知道"有哪些实现"（用 Multibinding 解决） | 需要回调/结果回传 |
| **D. 事件总线** | 全局 EventBus | 简单 | 隐式依赖、难追踪、易内存泄漏 | 慎用，只用于"埋点/通知"这类广播 |

**推荐的组合**：

```kotlin
// 方案 B + C 的标准实现：接口下沉 + Hilt 多绑定

// ── core-api 模块：只定义接口，不依赖任何 feature ──
package com.example.core.api

interface UserRepository {
    fun observeUser(userId: String): Flow<User?>
    suspend fun refresh(userId: String): Result<User>
}

// ── feature-profile 模块：提供实现 ──
package com.example.feature.profile.data

@Singleton
class RemoteUserRepository @Inject constructor(
    private val api: UserApi
) : UserRepository {
    override fun observeUser(userId: String): Flow<User?> = flow {
        emit(api.fetch(userId))
    }
    override suspend fun refresh(userId: String): Result<User> = runCatching {
        api.fetch(userId)
    }
}

// ── core-di 模块：用 Hilt Multibinding 聚合所有实现 ──
@Module
@InstallIn(SingletonComponent::class)
abstract class RepositoryModule {

    // 同一个接口可以有多个实现，按 @Key 区分
    @Binds
    @IntoSet
    @Key("remote")
    abstract fun bindRemote(impl: RemoteUserRepository): UserRepository

    @Binds
    @IntoSet
    @Key("cache")
    abstract fun bindCache(impl: CachedUserRepository): UserRepository
}
```

**feature 之间跳转用路由**（见 [[路由框架]]）：

```kotlin
// feature-order 需要跳转 feature-profile
// 只能传 ID，不能直接引用 ProfileActivity（否则产生模块依赖）
router.navigate(
    path = "/profile/detail",
    args = mapOf("userId" to userId)
)
```

#### 4.3 依赖可见性的选择：`api` vs `implementation`

```kotlin
// core-network/build.gradle.kts
dependencies {
    // ❌ api：OkHttp 会被传递给所有下游，使用方可以直接用 OkHttp
    //    → 换版本时所有下游都要跟着改，且失去了封装
    api("com.squareup.okhttp3:okhttp:4.12.0")

    // ✅ implementation：只在 core-network 内部可见
    implementation("com.squareup.okhttp3:okhttp:4.12.0")
    // 但对外暴露的类型必须用 api
    api("com.squareup.retrofit2:retrofit:2.11.0")   // 拦截器接口是公开 API 的一部分
}
```

**判断标准**：**如果下游代码需要引用这个依赖的类，那它就是 `api`；否则一律 `implementation`**。

#### 5.2 Convention Plugin

把重复的 Gradle 配置抽到 `build-logic`，让每个模块只写"差异部分"。

```kotlin
// build-logic/convention/build.gradle.kts
plugins {
    `kotlin-dsl`
}
group = "com.example.buildlogic"

java {
    sourceCompatibility = JavaVersion.VERSION_17
    targetCompatibility = JavaVersion.VERSION_17
}

dependencies {
    compileOnly(libs.android.gradlePlugin)
    compileOnly(libs.kotlin.gradlePlugin)
    compileOnly(libs.ksp.gradlePlugin)
}

gradlePlugin {
    plugins {
        register("androidApplication") {
            id = "myapp.android.application"
            implementationClass = "AndroidApplicationConventionPlugin"
        }
        register("androidLibrary") {
            id = "myapp.android.library"
            implementationClass = "AndroidLibraryConventionPlugin"
        }
        register("androidCompose") {
            id = "myapp.android.compose"
            implementationClass = "AndroidComposeConventionPlugin"
        }
    }
}
```

```kotlin
// build-logic/convention/src/main/kotlin/AndroidLibraryConventionPlugin.kt
class AndroidLibraryConventionPlugin : Plugin<Project> {
    override fun apply(target: Project) = with(target) {
        pluginManager.apply("com.android.library")
        pluginManager.apply("org.jetbrains.kotlin.android")

        extensions.configure<LibraryExtension> {
            namespace = "com.example.${project.path.removePrefix(":").replace(':', '.')}"

            compileSdk = 35
            defaultConfig {
                minSdk = 24
                consumerProguardFiles("consumer-rules.pro")
            }
            compileOptions {
                sourceCompatibility = JavaVersion.VERSION_17
                targetCompatibility = JavaVersion.VERSION_17
            }
            kotlinOptions {
                jvmTarget = "17"
                freeCompilerArgs += listOf("-opt-in=kotlin.RequiresOptIn")
            }
            buildFeatures {
                viewBinding = true
                buildConfig = true
            }
            testOptions {
                unitTests.isIncludeAndroidResources = true
                unitTests.isReturnDefaultValues = true
            }
            packaging {
                resources.excludes += setOf(
                    "/META-INF/{AL2.0,LGPL2.1}",
                    "META-INF/LICENSE.md",
                    "META-INF/LICENSE-notice.md"
                )
            }
        }
    }
}
```

### 6. 资源合并与命名空间

#### 6.1 namespace 的作用

Android Gradle Plugin 8.0 起，`namespace` **取代**了 `package` 属性：

```kotlin
// feature/profile/build.gradle.kts
android {
    namespace = "com.example.feature.profile"   // R 类与 BuildConfig 的包名
    // 不再需要在 AndroidManifest.xml 里写 package
}
```

| 属性 | AGP < 7.3 | AGP ≥ 7.3 | AGP ≥ 8.0 |
| --- | --- | --- | --- |
| `namespace` | ❌ | ✔（新写法） | ✔（**必填**） |
| Manifest `package` | ✔ | ✔（与 namespace 需一致） | ❌ **移除** |
| `R` 类包名 | Manifest package | `namespace` | `namespace` |
| `BuildConfig` 包名 | Manifest package | `namespace` | `namespace` |

#### 6.2 资源合并冲突

资源合并发生在 app 模块打包时，规则：

```
优先级：app 模块 > 依赖库（直接依赖 > 传递依赖，后者优先）
```

**冲突场景与解法**：

```kotlin
// 场景：两个库都定义了 app_name
// app/src/main/res/values/strings.xml
<resources>
    <string name="app_name">我的应用</string>   <!-- app 模块优先级最高，会覆盖库里的 -->
</resources>
```

**解法一：app 模块覆盖**（最常用）。App 级资源覆盖库级资源是 Android 的标准机制，用于"换肤/多品牌"。

**解法二：使用限定符区分**，避免同名：

```xml
<!-- core-ui/src/main/res/values/strings.xml -->
<resources>
    <string name="common_confirm">确定</string>
</resources>

<!-- feature-profile/src/main/res/values/strings.xml -->
<resources>
    <string name="profile_confirm">确定</string>   <!-- 加模块前缀避免同名 -->
</resources>
```

**解法三：`tools:override` / `tools:replace`**（在 `res/values/strings.xml` 的 `<resources>` 上）：

```xml
<resources xmlns:tools="http://schemas.android.com/tools"
    tools:override="true">
    <string name="app_name">我的应用</string>
</resources>
```

> **重要提醒**：资源名在**最终 APK 里是全局的**（所有库的资源被合并进同一个 `R` 表的 `resources.arsc`），所以**跨模块的同名资源会冲突**，即使它们在不同的包里。这是"资源全局性"与"R 类包名隔离"的**不一致性**，是模块化最常见的坑之一。

**规避策略**：
1. **所有资源名加模块前缀**：`profile_xxx`、`order_xxx`、`common_xxx`。
2. 用 `lint` 规则 `ResourceName` / 自定义规则检查命名规范。
3. 在 CI 里检查 `aapt dump resources` 或合并后的 `R.txt` 是否有重复项。

### 7. 独立调试（模块作为宿主）

模块化最实用的收益之一：**feature 模块可以单独运行**，不需要启动整个 App。

```kotlin
// feature/profile/build.gradle.kts
plugins {
    id("myapp.android.library")
    id("com.android.application")   // ⚠️ 同时应用 library 和 application 是不允许的
}
```

**正确做法：使用 `debug` 源集 + `applicationId` 变体**，或者更常用的"**宿主壳模块**"方案：

```kotlin
// feature/profile/src/debug/AndroidManifest.xml
<manifest xmlns:android="http://schemas.android.com/apk/res/android">
    <application android:theme="@style/Theme.ProfileDebug" />
</manifest>
```

```kotlin
// 方案二：debug 变体把库变成应用（Gradle 的 library 插件支持 debug variant 转 application）
// feature/profile/build.gradle.kts
android {
    buildTypes {
        debug {
            // 让 library 的 debug variant 变成可安装的应用
        }
    }
}
```

```kotlin
// 方案三（推荐，业界主流）：在 app 模块中用 productFlavor 或动态模块切换
// app/build.gradle.kts
android {
    flavorDimensions += "module"
    productFlavors {
        full {
            dimension = "module"
        }
        profileOnly {
            dimension = "module"
            applicationIdSuffix = ".profile"
            // 只包含 profile 相关模块
        }
    }
}
```

**另一种更实用的方案**——**路由跳转到指定模块启动**：

```kotlin
// app 中加一个调试入口
if (BuildConfig.DEBUG) {
    // 启动时根据参数决定跳转到哪个 feature
    val startPage = intent.getStringExtra("start_page") ?: "home"
    router.navigate(startPage)
}
```

```bash
# adb 直接启动指定页面
adb shell am start -n com.example.app/.MainActivity --es start_page "/profile/detail" --es userId "123"
```

### 8. 何时该拆 / 何时是过度设计

**拆模块的信号**（满足 2 条以上可以考虑）：

| 信号 | 量化 |
| --- | --- |
| 编译慢 | 全量构建 > 5 分钟，改一行代码要等很久 |
| 合并冲突频繁 | 同一目录每周多次冲突 |
| 职责混杂 | 一个类/目录承担 3 种以上职责 |
| 团队并行 | 多团队改同一模块，PR 互相阻塞 |
| 复用需求 | 同一段代码在 3 个以上地方复制 |
| 独立演进 | 某部分功能有独立的发布节奏（如运营活动模块） |

**过度设计的信号**：

| 信号 | 问题 |
| --- | --- |
| 模块数量 > 业务复杂度 | 一个简单 App 拆出 20 个模块 |
| 每个模块只有 1~2 个类 | "为了模块化而模块化"，配置成本 > 收益 |
| 模块之间频繁互相依赖 | 拆了但没解决依赖问题，反而增加了协调成本 |
| 跨模块调用需要"绕" | 简单的调用被迫走接口下沉 + 多绑定 |
| 编译反而更慢 | 过多模块 + 每个模块单独配置 → 配置阶段开销大 |
| 新人 2 周还搞不清结构 | 认知负担剧增 |

**模块数量经验值**：

| 项目规模 | 建议模块数 | 说明 |
| --- | --- | --- |
| 单人 / 3 人以内 | 3~5 个 | app + 1~2 个 core + 1~2 个 feature |
| 5~15 人 | 10~25 个 | 按业务域拆 feature，core 按技术拆 |
| 15 人以上 | 25~60 个 | 需要考虑多 team 归属、多 App 复用 |
| 50 人以上 | 需要组件化/插件化评估 | 或考虑多仓库/多 App 架构 |

**拆分的优先级**（按收益排序）：

```
1. 先把 app 里的 "上帝类" 拆成包/类（不改模块）
   ↓  成本最低，收益立竿见影
2. 把与业务无关的基础设施下沉到 core-*（Kotlin/JVM 模块）
   ↓  单测提速、依赖收敛
3. 把最大的 2~3 个业务域独立成 feature 模块
   ↓  编译并行度提升
4. 按团队边界继续细分
   ↓
5. 最后才考虑组件化/插件化
```

### 4. 自定义 Lint 规则守护依赖方向

```kotlin
// lint-rules/src/main/kotlin/FeatureDependencyDetector.kt
package com.example.lint

import com.android.tools.lint.detector.api.*
import com.intellij.psi.PsiFile
import org.jetbrains.uast.UElement
import org.jetbrains.uast.UCallExpression

/**
 * 禁止 feature 模块之间直接依赖。
 */
class FeatureDependencyDetector : Detector(), SourceCodeScanner {

    override fun getApplicableUastTypes(): List<Class<out UElement>> =
        listOf(UCallExpression::class.java)

    override fun createUastHandler(context: JavaContext): UElementHandler =
        object : UElementHandler() {
            override fun visitCallExpression(node: UCallExpression) {
                val file: PsiFile = node.sourcePsi?.containingFile ?: return
                if (!file.name.endsWith(".gradle.kts")) return

                val target = node.sourcePsi?.text ?: return
                // 匹配 project(":feature:xxx")
                if (!target.contains("project(\":feature:")) return

                val gradleText = file.text
                // 判断是否在 dependencies 块内的 implementation/api
                val isDirectDep = gradleText.contains("implementation(project(\":feature:") ||
                        gradleText.contains("api(project(\":feature:")

                if (isDirectDep) {
                    context.report(
                        Incident(
                            message = """
                                feature 模块之间不允许直接依赖。
                                当前依赖：$target
                                请通过 core 模块的接口 + 路由通信解耦。
                            """.trimIndent(),
                            location = context.getLocation(node.sourcePsi),
                            issue = ISSUE
                        )
                    )
                }
            }
        }

    companion object {
        @JvmField
        val ISSUE: Issue = Issue.create(
            id = "FeatureDirectDependency",
            briefDescription = "feature 模块直接依赖其他 feature 模块",
            explanation = """
                组件化架构要求 feature 之间保持独立。
                直接依赖会导致编译耦合、无法独立发布与调试。
                请将公共接口下沉到 core-* 模块，或通过路由通信。
            """.trimIndent(),
            category = Category.CORRECTNESS,
            priority = 8,
            severity = Severity.ERROR,
            implementation = Implementation(
                FeatureDependencyDetector::class.java,
                Scope.JAVA_FILE_SCOPE
            )
        )
    }
}
```

## 常见问题 / 面试要点

**读者问：模块化拆分到什么粒度合适？一个 App 拆多少模块合适？**

**AI答：**

1. **判断标准不是数量，而是"边界是否清晰"**。每个模块应该能回答三个问题：
   - **它负责什么**（一句话能说清职责）？
   - **它对外暴露什么**（只有 public API，其余全是 internal）？
   - **谁可以依赖它**（有明确的依赖规则）？
   如果这三个问题答不上来，说明这个模块不该存在。
2. **经验数量参考**：
   - 3 人以下团队：**3~5 个模块**（app + 1~2 core + 1~2 feature）。
   - 5~15 人：**10~25 个**（每个业务域一个 feature）。
   - 15 人以上：**25~60 个**，需要考虑团队归属与 Code Owner。
3. **粒度的下界（太细的信号）**：
   - 一个模块只有 1~2 个类。
   - 模块之间为了一个工具函数也要绕一圈。
   - 配置成本（build.gradle.kts + proguard + 测试）超过收益。
4. **粒度的上界（太粗的信号）**：
   - 全量编译 > 5 分钟。
   - 同一目录每周多次合并冲突。
   - 一个模块承担多个不相关业务（改支付要动搜索模块的编译）。
5. **推荐的拆分节奏**：
   - **不要一次性大拆**：先按业务域粗拆（3~5 个 feature），跑两个迭代观察，再逐步细分。
   - **优先拆"最痛"的地方**：编译最慢的、冲突最多的、职责最混杂的。
   - **保留一个"垃圾回收"机制**：每季度 review 一次模块列表，合并没有存在价值的模块。

---

**读者问：feature 模块之间怎么通信？直接依赖行不行？**

**AI答：**

1. **直接依赖的三个问题**：
   - **编译耦合**：`feature-order` 依赖 `feature-profile`，则 profile 改动会触发 order 重新编译，编译时间线性增长。
   - **无法独立发布/独立调试**：组件化的核心价值被破坏。
   - **责任边界模糊**：两个团队同时改两个模块，PR 互相阻塞（见 [[../代码规范与质量/Git工作流]]）。
2. **标准方案（按场景选）**：

| 场景 | 方案 | 示例 |
| --- | --- | --- |
| **页面跳转** | **路由**（传 ID，目标自己查数据） | `router.navigate("/profile/detail", args)` |
| **需要传复杂对象** | 接口下沉到 `core-api`，用 `@Parcelize` 或 ID + 查询 | `ProfileData` 接口下沉 |
| **需要拿返回值** | 路由结果回传 API（`navigateForResult`） | `router.navigateForResult(...).await()` |
| **需要共享数据** | 共享 Repository（实现放 core 或通过多绑定） | `UserRepository` |
| **全局广播**（慎用） | 共享 Flow/EventBus | `AppEventBus` |

3. **"接口下沉"的正确做法**（避免 core 依赖 feature）：
   ```
   core-api/          ← 定义接口（不依赖任何 feature）
       UserRepository.kt
   feature-profile/   ← 提供实现，依赖 core-api
       RemoteUserRepository.kt
   core-di/ 或 core-di 聚合各实现的 @Binds
   ```
   **关键**：`core` 模块的 `build.gradle.kts` 里**不能出现任何 `project(":feature:...")`**，否则依赖倒置失败。
4. **常见反模式**：
   - ❌ 为了"方便"在 core 里写 `implementation(project(":feature:xxx"))` → core 变成垃圾场。
   - ❌ 用 `companion object` + 全局单例在模块间传数据 → 隐式依赖，测试困难。
   - ❌ 用反射直接拿别的模块的 Activity → 绕过路由，破坏可维护性。
5. **面试话术**："模块间通信我遵循两条：**数据流向下走**（接口下沉 + 依赖倒置），**控制流向上走**（路由 + ID 传参）。这样 feature 保持零横向依赖。"

---

**读者问：模块化一定能加速编译吗？为什么有的团队拆完反而更慢？**

**AI答：**

1. **模块化加速编译的三个机制**：
   - **增量编译**：改 `feature-a` 只重编 `feature-a` 及其下游，单模块变更从 3 分钟降到 10 秒。
   - **并行执行**：Gradle 并行编译无依赖关系的模块（`org.gradle.parallel=true`），CPU 多核直接线性加速。
   - **按需构建**：`feature-a` 的测试不需要构建 `feature-b`。
2. **反而更慢的四个原因**：
   - **❌ 配置阶段开销大**：每个模块都有 `build.gradle.kts` + `apply(from=...)` + 依赖解析。20 个模块 × 3 秒配置 = 60 秒，比不拆还慢。
     - **解法**：用 **Convention Plugin** 把配置收敛（一个插件应用 = 一次类加载），开启**配置缓存**。
   - **❌ 没有开并行**：`org.gradle.parallel=false`（默认在某些场景），模块只是被拆开，没有并行。
   - **❌ 每个模块都开一堆功能**：每个模块都开 `viewBinding` + `buildConfig` + `compose` + `kapt`，各自的代码生成开销累加。
     - **解法**：下沉到能共用的地方（比如都用 KSP 统一处理）。
   - **❌ 依赖被重复解析**：每个模块独立解析依赖树，重复下载元数据。
     - **解法**：确保只有一个 `repositories` 声明点（`RepositoriesMode.FAIL_ON_PROJECT_REPOS`），依赖缓存共享。
3. **关键指标与观测**：
   - **配置阶段耗时** vs **执行阶段耗时**（`--profile` 报告）。
   - 如果配置阶段 > 30%，**优先优化配置**（Convention Plugin + 配置缓存），而不是加机器。
4. **实测经验**：一个 300 模块的 Android 项目，从单模块迁移到模块化 + Convention Plugin + 配置缓存，全量构建从 8 分钟降到 2 分 30 秒。**其中配置缓存贡献了约一半**。

---

**读者问：Version Catalog 和 Convention Plugin 分别解决什么问题？能不能不用？**

**AI答：**

1. **Version Catalog 解决"依赖声明的重复与版本漂移"**：
   - **问题**：20 个模块各自写 `implementation("androidx.core:core-ktx:1.13.1")`，升级要改 20 处，还可能漏。
   - **Catalog 的价值**：集中管理、类型安全（写错库名编译失败）、支持 Bundle（BOM）、支持版本引用（`version.ref`）。
   - **能不能不用**：可以，但多模块项目里收益很大。**单模块小项目可不用。**
   - **进阶能力**：
     - **版本对齐**：普通 TOML 不支持，需要 `libs.versions.toml` + Renovate/Bot 插件做版本升级 PR。
     - **BOM 统一版本**：`platform(libs.androidx.compose.bom)` 一次性对齐整个 Compose 生态的版本，避免版本冲突。
2. **Convention Plugin 解决"构建配置的重复"**：
   - **问题**：每个模块重复写 `compileSdk`、`minSdk`、`jvmTarget`、`viewBinding`、`packaging` 排除项……30 行 × 30 个模块 = 900 行重复，且新人不知道该填什么。
   - **Plugin 的价值**：**约定优于配置**——只写差异（`namespace`、依赖），其余由插件统一。新人不需要知道 Android 工程的最佳实践，只需要知道"这个模块要什么能力"。
   - **额外能力**：插件里可以做**校验**（如"core 模块不允许依赖 feature 模块"直接抛异常，比 Lint 更早失败）。
3. **两者配合的效果**：
   ```
   build-logic/convention/     ← 统一"怎么做"（配置）
   gradle/libs.versions.toml   ← 统一"用什么"（版本）
   模块的 build.gradle.kts      ← 只声明"我是什么"（差异）
   ```
4. **迁移建议**：
   - **Version Catalog**：AGP 7.4+ / Gradle 7.6+ 稳定支持，迁移成本低，**优先做**。
   - **Convention Plugin**：需要搭 `includeBuild` 目录结构，前期投入 1~2 天，但收益长期化。**在模块数超过 10 个后再做**。
   - **迁移顺序**：先 Version Catalog（快赢）→ 再 Convention Plugin（慢赢但更彻底）。

---

**读者问：什么是组件化（插件化）？和模块化的实现差异在哪？**

**AI答：**

1. **模块化**：编译期切分，模块产物是 AAR，最终合成一个 APK。**代码全都在包里**。
2. **组件化/插件化**：运行期切分，业务模块可以是**独立的 APK**，运行时由宿主动态加载。
3. **实现差异的核心：ClassLoader**：
   - Android 的默认 ClassLoader（`PathClassLoader`）按顺序加载 classes.dex。
   - 插件化需要**自定义 ClassLoader**（如 `DelegateClassLoader`），把插件 APK 的 dex 插入到**父 ClassLoader 之前**，保证宿主找不到的类由插件提供。
   - **还要处理**：资源加载（`Resources` 与 `AssetManager` 的合并）、`Context` 传递、`Activity` 的生命周期与 `Instrumentation` 替换、`Provider` 的动态注册。
4. **四大核心问题**（这是回答此题的骨架）：
   | 问题 | 解决方案 |
   | --- | --- |
   | **类加载** | 自定义 ClassLoader + dex 插到最前 |
   | **资源加载** | 资源重定向（hook `AssetManager` 的 `addAssetPath`） |
   | **通信** | 路由 + 接口下沉 + Binder/AIDL |
   | **生命周期/上下文** | 插件 Context 包装 + `ActivityThread`/`Instrumentation` Hook |
5. **收益**：
   - 业务模块可独立发版（配合动态化，见 [[../热修复与动态化]]）。
   - 减少首屏安装包（按需下载）。
   - 业务彻底隔离（一个模块崩溃不影响其他）。
6. **成本与风险**：
   - **技术成本极高**：需要 Hook Android 框架内部 API，随 Android 版本升级而失效。
   - **兼容性差**：Android 8 之后 `PackageManager` 行为变化、Android 10 限制跨进程访问、Android 11+ 限制 `requestLegacyExternalStorage` 等。
   - **商店政策风险**：Google Play 对动态下载代码（Dynamic Code Loading）有明确限制，除非是解释器或不含违规功能的自更新机制。
   - **审核风险**：国内商店对插件化普遍敏感。
7. **面试结论**：
   > "组件化解决的是业务隔离与动态化，技术代价是对 Android 框架内部机制的侵入。我个人的判断是：**除非有明确的动态化需求（如游戏 DSL、运营活动），否则模块化 + Feature Flag + 远端配置 + 热修复的组合，能以 10% 的成本拿到 90% 的收益。**"

---

**读者问：资源冲突怎么处理？`namespace` 到底解决什么问题？**

**AI答：**

1. **`namespace` 解决的是"R 类包名隔离"，不是"资源隔离"**——这是最容易误解的点。
   - **namespace 决定**：`R` 类和 `BuildConfig` 类生成在哪个包下。比如 `feature/profile` 的 `namespace = "com.example.feature.profile"` → `com.example.feature.profile.R`。
   - **namespace 不解决**：资源名冲突。因为所有库的资源最终被合并进主 APK 的**同一个 `resources.arsc`**，资源名是**全局唯一**的。
2. **资源合并规则**：
   ```
   app 模块资源  >  依赖库资源（直接依赖 > 传递依赖）
   ```
   - app 模块可以**覆盖**库里的同名资源——这是 Android 官方的"多品牌换肤"机制。
   - 两个**平级的库**（都是 app 的直接依赖）定义同名资源 → **编译期报错**：`Duplicate resources`。
3. **解决方案**：
   - **方案一：加模块前缀**（推荐）：`profile_title`、`order_price`、`common_confirm`。可以在 Lint 里用自定义规则强制检查。
   - **方案二：app 模块覆盖**：在 `app/src/main/res/values/strings.xml` 定义同名资源覆盖掉库的。
   - **方案三：命名空间化资源目录**（AGP 8.x 引入的非传递 R 类）：
     ```kotlin
     android {
         // 每个库生成自己的 R 类，资源引用需带模块名
         android.nonTransitiveRClass = true
     }
     ```
     这解决了 **R 类引用**的传递依赖问题，但**资源名本身仍然全局唯一**（同名依然冲突）。
4. **还要注意的其他资源冲突源**：
   - **`AndroidManifest` 合并**：库里的 `<application>` 属性、`<activity>` 会被合并；`android:name` 冲突、`tools:replace` 缺失。
   - **`proguard-rules.pro`**：库的规则文件与 app 的合并，顺序有讲究。
   - **assets / res/raw 目录**：同名文件冲突。
5. **预防策略**：
   - 在项目根目录放一份**资源命名约定文档**，并用自定义 Lint 规则强制检查。
   - CI 里检查合并后的 `R.txt` 是否有重复条目。

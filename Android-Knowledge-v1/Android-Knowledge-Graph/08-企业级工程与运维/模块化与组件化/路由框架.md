# 路由框架

## 一句话定义

路由框架是组件化架构的**"交通枢纽"**：它把"跳转到某个页面"从"直接 new 一个 Activity 并 startActivity"抽象为"**用字符串路径 + 参数**发起跳转"，从而让调用方**不依赖目标模块的编译产物**。同时它还承担**拦截（登录、维护页、降级）、结果回传、外部 URL 处理**等横切能力。

面试开场：**"路由的价值不是'跳转方便'，而是'解耦'——它让 A 模块调用 B 模块时，编译期完全不需要知道 B 的存在。代价是失去了编译期类型安全，所以必须用好参数校验和兜底。"**

## 核心原理

### 1. 路由要解决的四个职责

```
┌────────────────────────────────────────────────────────────────┐
│  ① 页面标识（Addressing）                                        │
│     用字符串路径 "/profile/detail" 唯一标识一个页面                │
│     → 映射到具体的 Activity / Composable                         │
├────────────────────────────────────────────────────────────────┤
│  ② 参数传递（Parameter Passing）                                  │
│     Bundle / 序列化对象 / Query 参数                               │
│     → 目标页面自行解析与类型转换                                   │
├────────────────────────────────────────────────────────────────┤
│  ③ 拦截（Interception）                                          │
│     跳转前的统一检查：未登录拦截、维护页拦截、开关拦截、AB 拦截     │
│     → 拦截器按优先级链式执行                                       │
├────────────────────────────────────────────────────────────────┤
│  ④ 结果回传（Result）                                             │
│     跳转时发起一个"请求"，目标页面返回结果给发起方                │
│     → 类似 Activity Result API，但跨模块可用                       │
└────────────────────────────────────────────────────────────────┘
```

### 2. 原生方案：Intent + Navigation Component

#### 2.1 Intent 方案

```kotlin
// 直接启动
startActivity(Intent(this, UserProfileActivity::class.java).apply {
    putExtra("user_id", userId)
})

// 隐式 Intent（通过 action + category，系统按匹配规则解析）
val intent = Intent("com.example.app.action.VIEW_PROFILE").apply {
    putExtra("user_id", userId)
    setPackage(packageName)   // 限定包名，避免被其他 App 抢
}
startActivity(intent)
```

**原生方案的问题**：
- **编译期耦合**：`UserProfileActivity::class.java` 直接引用了目标模块的类，产生模块依赖。
- **参数无类型约束**：传错 key 编译不报错，运行时 `getStringExtra("userId")` 返回 null。
- **无法统一拦截**：每个跳转点都要自己写登录检查。

#### 2.2 Navigation Component 方案

```kotlin
// res/navigation/nav_graph.xml
<?xml version="1.0" encoding="utf-8"?>
<navigation xmlns:android="http://schemas.android.com/apk/res/android"
    xmlns:app="http://schemas.android.com/apk/res-auto"
    android:id="@+id/nav_graph"
    app:startDestination="@id/homeFragment">

    <fragment
        android:id="@+id/homeFragment"
        android:name="com.example.feature.home.HomeFragment"
        android:label="@string/home_title">
        <action
            android:id="@+id/action_home_to_profile"
            app:destination="@id/profileFragment" />
    </fragment>

    <fragment
        android:id="@+id/profileFragment"
        android:name="com.example.feature.profile.ProfileFragment">
        <!-- Safe Args：生成类型安全的参数类 -->
        <argument
            android:name="userId"
            app:argType="string" />
    </fragment>
</navigation>
```

```kotlin
// 使用 Safe Args（编译期生成强类型参数）
val args = ProfileFragmentArgs.builder()
    .setUserId(userId)
    .build()

findNavController().navigate(R.id.action_home_to_profile, args)
```

**Navigation Component 的能力**：
- **可视化编辑导航图**（Android Studio 的 Nav Graph Editor）。
- **Safe Args**：编译期生成类型安全的参数类（通过 `androidx.navigation.safeargs` 插件）。
- **Deep Link**：自动解析 `https://example.com/profile/123` → 目标页面。
- **多返回栈**（Navigation 2.4+ 的 `NavBackStackEntry` 与 `saveState/restoreState`）。
- **动画**：转场动画集中配置。

**局限**：
- 导航图是 XML，**集中在一个模块**（通常在 app 或 navigation 模块），这在组件化下有矛盾——各 feature 的页面分散在不同模块，导航图却要在一处。
- **Deep Link 的处理与外部 URL 安全**需要自己实现。

### 3. ARouter 的思想：注解 + 路由表

ARouter（阿里巴巴开源）是国内组件化路由的代表，其核心思想对业界影响深远。

#### 3.1 注解声明

```kotlin
// ── 定义路由服务接口 ──
interface IUserRouter {
    fun openUserProfile(userId: String)
}

// ── 路由注解 ──
@Target(AnnotationTarget.CLASS)
@Retention(AnnotationRetention.RUNTIME)
annotation class RouterUri(
    val path: String,          // 路由路径
    val group: String = "",    // 分组（用于按模块查找）
    val name: String = "",     // 页面名称
    val extra: String = "",    // 额外参数
    val priority: Int = 0      // 优先级
)

@RouterUri(path = "/profile/detail", group = "profile")
class ProfileDetailActivity : AppCompatActivity(), IUserRouter {

    override fun openUserProfile(userId: String) {
        // ...
    }
}
```

#### 3.2 APT 生成路由表

```
编译期（APT / Annotation Processor）
  扫描所有带 @RouterUri 的类
      ↓
  生成三个文件
      ↓
  1. XxxRouterGroup.java    —— 分组索引：group → 该组所有路由
  2. XxxRouterTable.java    —— 路由表：path → Class<?>
  3. Xxx$$Autowired.java    —— 依赖注入：把接口实现注入到目标

运行期
  RouteService（由 APT 生成的类）→ 内存中的 HashMap<path, Class>
```

生成的路由表大致如下：

```java
// APT 生成：com.example.router.generated.RouteTable
public class RouteTable {
    public static final Map<String, Class<?>> ROUTE_TABLE = new HashMap<>();

    static {
        ROUTE_TABLE.put("/profile/detail", ProfileDetailActivity.class);
        ROUTE_TABLE.put("/order/list", OrderListActivity.class);
        ROUTE_TABLE.put("/home/main", HomeActivity.class);
    }
}
```

**关键点**：路由表是**编译期生成**的，运行期查 HashMap，**O(1) 查找，零反射开销**（首次解析后可以缓存 Method）。

#### 3.3 运行时调用

```kotlin
// ARouter 的调用形式
ARouter.getInstance()
    .build("/profile/detail")
    .withString("user_id", userId)
    .navigation(this)
```

**ARouter 的完整能力矩阵**：

| 能力 | 说明 |
| --- | --- |
| 路由映射 | path → Activity/Fragment |
| 参数传递 | `withString`、`withInt`、`withBundle`、自定义 Parcelable |
| 拦截器 | `IRouterInterceptor` 链式执行，优先级排序 |
| 自定义拦截器 | 登录检查、维护页、降级、埋点 |
| IProvider 服务 | 不依赖 Activity 的服务（类似 DI 的跨模块服务调用） |
| 自动注入 | APT 生成的 `$$Autowired` 实现参数自动注入 |
| URI 映射 | 支持 `://` scheme 的外部 URL |
| Action | 支持类似 `router://` 的伪协议 |
| 降级策略 | 目标不存在时的兜底页面 |
| 混淆 | 通过 ProGuard 规则保持路由表类名 |

### 4. 组件化路由：类加载与插件化

真正的组件化/插件化场景下，目标页面在**另一个 APK** 里，路由需要处理**类加载**问题。

```
┌─────────────────────────────────────────────────────────────┐
│  宿主 APK（Stub / 壳）                                        │
│  ┌───────────────────────────────────────────────────────┐  │
│  │ RouteTable (编译期生成，但只包含宿主内的页面)            │  │
│  │   "/home/main" → HomeActivity                        │  │
│  └───────────────────────────────────────────────────────┘  │
│                          ↓ 找不到                              │
│  ┌───────────────────────────────────────────────────────┐  │
│  │ DelegateClassLoader（自定义 ClassLoader）                │  │
│  │   1. 优先在自己加载的 dex 中查找                        │  │
│  │   2. 找不到再委托给父 ClassLoader                      │  │
│  │   → 插件 APK 的 dex 被插入到最前面                      │  │
│  └───────────────────────────────────────────────────────┘  │
│                          ↓ 找到                                │
│  ┌───────────────────────────────────────────────────────┐  │
│  │ 插件 APK（业务模块，独立签名、独立下发）                  │  │
│  │   ProfileDetailActivity                               │  │
│  └───────────────────────────────────────────────────────┘  │
└─────────────────────────────────────────────────────────────┘
```

**插件路由的实现要点**：

```kotlin
/**
 * 插件 ClassLoader：把插件 dex 插入到父加载器之前。
 *
 * 查找顺序：插件 dex → 宿主 dex → 系统的 PathClassLoader
 */
class PluginClassLoader(
    private val pluginDexPath: String,
    parent: ClassLoader
) : PathClassLoader(pluginDexPath, parent) {

    override fun loadClass(name: String, resolve: Boolean): Class<*> {
        // 1. 先在插件中查找（findClass 会触发 dex 加载）
        return try {
            findClass(name)
        } catch (e: ClassNotFoundException) {
            // 2. 找不到则委托给父加载器（宿主 + 系统）
            super.loadClass(name, resolve)
        }
    }
}
```

**但只有 ClassLoader 是不够的**，组件化路由还要解决：

| 问题 | 解决方案 |
| --- | --- |
| **类加载** | 自定义 ClassLoader + dex 插到最前 |
| **资源加载** | hook `AssetManager.addAssetPath`，让插件资源进入宿主 `Resources` |
| **Activity 启动** | hook `Instrumentation`（`execStartActivity`），把目标 Activity 替换为插件的 Stub Activity |
| **Context 传递** | 用 `ContextWrapper` 包装插件 Context（正确的 `resources` + `assets`） |
| **Provider 动态注册** | 插件的 ContentProvider 需在 `attachBaseContext` 阶段手动注册 |
| **路由表合并** | 宿主路由表 + 各插件路由表，通过 `IProvider` 聚合 |

**插件路由的接口聚合机制**（IProvider）：

```kotlin
// 插件通过实现 IProvider 并在 manifest 中声明，由宿主扫描合并
interface IProvider {
    fun init(context: Context)
}

// 插件中的实现
class ProfileRouteProvider : IProvider {
    override fun init(context: Context) {
        // 把插件的路由注册到全局路由表
        RouteTable.register(
            "/profile/detail",
            ProfileDetailActivity::class.java
        )
    }
}
```

**这个机制的本质**：宿主在启动时扫描所有已安装/已下载的插件 APK，读取其 `AndroidManifest.xml`，找到声明了 `IProvider` 的类（通过约定：类名固定为 `com.xxx.IProvider` 或在 manifest 中用 meta-data 声明），反射实例化并调用 `init`。

### 5. 拦截器机制

拦截器是路由框架的**横切能力载体**，也是路由框架相对于 `Intent` 的最大增量价值。

```kotlin
/** 路由拦截器接口 */
interface RouteInterceptor {
    /** 优先级，数值越大越先执行 */
    val priority: Int get() = 0

    /**
     * @return true 表示继续执行后续拦截与跳转；false 表示中断
     */
    fun intercept(request: RouteRequest, chain: InterceptorChain): Boolean
}

/** 拦截器链 */
class InterceptorChain(
    private val interceptors: List<RouteInterceptor>
) {
    private var index = 0

    fun proceed(request: RouteRequest): Boolean {
        while (index < interceptors.size) {
            val interceptor = interceptors[index++]
            if (!interceptor.intercept(request, this)) {
                return false   // 拦截，中断链路
            }
        }
        return true   // 全部通过
    }
}
```

**常见拦截器类型**：

| 拦截器 | 逻辑 | 优先级 |
| --- | --- | --- |
| **登录拦截** | 未登录 → 跳转登录页，登录成功后回到原页面 | 高（100） |
| **维护拦截** | 服务端下发维护状态 → 跳维护页 | 最高（200） |
| **降级拦截** | 目标模块被远程禁用（Feature Flag） → 跳降级页 | 高（150） |
| **实名/权限拦截** | 需要实名认证 → 跳认证页 | 90 |
| **AB 实验拦截** | 当前用户不在实验组 → 跳默认实现 | 50 |
| **埋点拦截** | 记录页面曝光 PV | 低（10） |
| **性能拦截** | 记录跳转耗时 | 低（10） |

```kotlin
/** 登录拦截器实现 */
class LoginInterceptor : RouteInterceptor {
    override val priority = 100

    override fun intercept(request: RouteRequest, chain: InterceptorChain): Boolean {
        val needLogin = request.extras.getBoolean(EXTRA_NEED_LOGIN, false)
        if (!needLogin || UserSession.isLoggedIn) {
            return chain.proceed(request)   // 放行
        }

        // 需要登录：保存原始请求，登录成功后恢复
        PendingRequestStore.save(request)
        LoginActivity.start(request.context)
        return false   // 中断本次跳转
    }
}
```

### 6. 与 Navigation Compose 的配合

Jetpack Compose 项目里，Navigation Compose 是官方方案，但要与"字符串路径路由"结合，需要做一层适配。

```kotlin
/**
 * Compose 路由注册表：把字符串路径映射到 Composable。
 *
 * 每个 feature 模块在初始化时注册自己的页面，
 * app 模块在启动时统一构建 NavHost。
 */
object ComposeRouteRegistry {

    private val routes = mutableMapOf<String, @Composable (NavBackStackEntry) -> Unit>()

    /** 注册一个 Compose 页面 */
    fun register(path: String, content: @Composable (NavBackStackEntry) -> Unit) {
        require(path.startsWith("/")) { "路由路径必须以 / 开头: $path" }
        check(path !in routes) { "路由重复注册: $path" }
        routes[path] = content
    }

    /** 构建 NavHost：把注册的页面挂到 NavHost 上 */
    @Composable
    fun BuildNavHost(navController: NavHostController, startDestination: String) {
        NavHost(navController = navController, startDestination = startDestination) {
            routes.forEach { (path, content) ->
                composable(
                    route = path,
                    arguments = listOf(
                        navArgument("userId") {
                            type = NavType.StringType
                            nullable = true
                            defaultValue = null
                        }
                    )
                ) { entry ->
                    content(entry)
                }
            }
        }
    }
}
```

```kotlin
// ── feature/profile 模块内注册自己的页面 ──
@Composable
fun ProfileRoutes() {
    ComposeRouteRegistry.register("/profile/detail") { entry ->
        val userId = entry.arguments?.getString("userId")
        ProfileDetailScreen(userId = userId)
    }
}
```

```kotlin
// ── app 模块统一组装 ──
@Composable
fun AppNavHost(navController: NavHostController = rememberNavController()) {
    // 触发各 feature 的注册（通过反射或显式调用）
    ProfileRoutes()
    OrderRoutes()
    HomeRoutes()

    ComposeRouteRegistry.BuildNavHost(navController, startDestination = "/home/main")
}
```

**用 Compose 的 Navigation 还是字符串路由？取舍**：

| 方案 | 优点 | 缺点 |
| --- | --- | --- |
| **纯 Navigation Compose** | 官方支持、类型安全（参数类）、动画开箱即用、动画与转场完善 | 导航图集中在一处，组件化下所有 feature 的页面都要被 app 引用（产生依赖） |
| **纯字符串路由** | 完全解耦、支持外部 URL、易做拦截 | 类型不安全、动画要自己实现、Deep Link 要自己解析 |
| **混合（推荐）** | 字符串路径作为**外部标识**（Deep Link、埋点、拦截），内部用 Navigation Compose 的类型安全参数 | 需要一层适配，初期成本稍高 |

**推荐的混合方案**：

```kotlin
// 统一入口：业务代码只认字符串路径
object AppRouter {
    fun navigate(context: Context, path: String, args: Map<String, String> = emptyMap()) {
        // 1. 执行拦截器链
        // 2. 构造 NavDeepLink 或直接 navigate(route = path)
        // 3. 结果回调
    }
}
```

### 7. Deep Link 与外部 URL 处理

```kotlin
/** 处理来自外部（浏览器、短信、其他 App）的 URL */
class DeepLinkHandler {

    /**
     * 解析外部 URL，映射到内部路由。
     *
     * 安全要点：外部 URL 是不可信输入，必须：
     * 1. 白名单校验 host
     * 2. 参数类型与长度校验
     * 3. 不允许跳转到内部管理/调试页面
     */
    fun resolve(url: String): RouteRequest? {
        val uri = Uri.parse(url)
        if (uri.scheme != "https" && uri.scheme != "myapp") return null

        // host 白名单
        if (uri.host !in ALLOWED_HOSTS) return null

        // 路径映射：https://example.com/profile/123 → /profile/detail
        val path = when (val segments = uri.pathSegments) {
            listOf("profile", id) -> "/profile/detail"
            listOf("order", id) -> "/order/detail"
            else -> return null
        }

        // 参数白名单与校验
        val args = buildMap {
            segments.getOrNull(1)?.let { put("id", it.take(64)) }   // 长度限制
        }

        return RouteRequest(path = path, extras = args.toBundle(), needLogin = true)
    }
}
```

**安全红线**：
- **绝不信任外部 URL 的任何部分**。
- **禁止通过外部 URL 跳转到内部管理页、调试页、导出数据页**（这些页面要有额外鉴权）。
- **参数必须做类型与长度校验**，防止 SQL 注入、路径穿越、OOM（超大参数）。
- **敏感操作需要二次确认**（如"通过链接直接下单/支付"必须弹窗确认）。

### 8. 路由性能优化

| 优化点 | 做法 | 收益 |
| --- | --- | --- |
| **路由表查找** | HashMap 而非遍历扫描 | O(1) vs O(n) |
| **参数反射** | APT 生成类型安全的 setter，避免反射 | 反射单次 ~1μs，高频跳转可省 |
| **缓存 path → Activity 映射** | 静态缓存，避免每次解析 | 减少字符串处理 |
| **拦截器链缓存** | 拦截器列表构建一次 | 避免每次遍历 DI 图 |
| **懒初始化** | 只在首次导航时构建路由表 | 启动更快 |
| **主线程检查** | 路由跳转必须在主线程，非主线程用 Handler 投递 | 避免 `CalledFromWrongThreadException` |

```kotlin
/** 高性能路由：编译期生成映射 + 缓存 */
object FastRouter {

    /** APT 生成的映射表：path → 类 */
    private val routeMap: Map<String, Class<out Activity>> by lazy {
        RouteTableGenerator.ROUTE_TABLE
    }

    fun navigate(context: Context, path: String, args: Bundle? = null) {
        val target = routeMap[path]
            ?: throw RouteNotFoundException("未找到路由: $path")
        val intent = Intent(context, target).apply {
            args?.let { putExtras(it) }
            addFlags(Intent.FLAG_ACTIVITY_NEW_TASK)
        }
        context.startActivity(intent)
    }
}
```

## 代码示例

### 1. 路由框架核心实现

```kotlin
package com.example.router

import android.content.Context
import android.os.Bundle

/** 路由请求 */
data class RouteRequest(
    val path: String,
    val extras: Bundle = Bundle(),
    val needLogin: Boolean = false,
    val interceptors: List<RouteInterceptor> = emptyList(),
    internal var resultCallback: ((Bundle?) -> Unit)? = null
)

/** 拦截器接口 */
interface RouteInterceptor {
    val priority: Int get() = 0
    fun intercept(request: RouteRequest, chain: InterceptorChain): Boolean
}

/** 拦截器链 */
class InterceptorChain(private val interceptors: List<RouteInterceptor>) {
    private var index = 0

    fun proceed(request: RouteRequest): Boolean {
        while (index < interceptors.size) {
            if (!interceptors[index++].intercept(request, this)) return false
        }
        return true
    }
}

/** 路由表：编译期由 APT 生成 */
interface RouteTable {
    /** path → 目标 Activity 类 */
    val table: Map<String, Class<out android.app.Activity>>

    /** 需要跳转前执行的自定义逻辑（如埋点） */
    fun prepare(context: Context, request: RouteRequest): Boolean = true
}

/**
 * 路由器：统一入口。
 *
 * 职责：
 * 1. 拦截器链执行
 * 2. 路由表查找
 * 3. 参数校验
 * 4. 跳转执行
 */
object Router {

    /** 全局路由表（由 APT 生成类注入） */
    @Volatile
    private var routeTable: RouteTable? = null

    /** 全局拦截器（由 DI 注入） */
    @Volatile
    private var interceptors: List<RouteInterceptor> = emptyList()

    fun install(table: RouteTable, interceptors: List<RouteInterceptor>) {
        this.routeTable = table
        this.interceptors = interceptors.sortedByDescending { it.priority }
    }

    /** 发起跳转 */
    fun navigate(
        context: Context,
        path: String,
        args: Bundle = Bundle(),
        needLogin: Boolean = false
    ) {
        navigateForResult(context, path, args, needLogin) { }
    }

    /** 发起跳转并等待结果 */
    fun navigateForResult(
        context: Context,
        path: String,
        args: Bundle = Bundle(),
        needLogin: Boolean = false,
        callback: (Bundle?) -> Unit
    ) {
        val request = RouteRequest(
            path = path,
            extras = args,
            needLogin = needLogin,
            interceptors = interceptors
        )
        request.resultCallback = callback

        // 1. 执行拦截器链（登录、维护、降级、AB）
        val chain = InterceptorChain(interceptors)
        if (!chain.proceed(request)) {
            // 被拦截（通常已跳转到登录页等）
            return
        }

        // 2. 查找目标
        val table = routeTable ?: error("Router 未初始化，请检查 Application 中的 install 调用")
        val target = table.table[path]
        if (target == null) {
            // 降级：跳转到兜底页
            FallbackActivity.start(context, path)
            return
        }

        // 3. 参数校验与准备
        if (!table.prepare(context, request)) return

        // 4. 执行跳转（必须在主线程）
        val intent = android.content.Intent(context, target).apply {
            putExtras(request.extras)
            addFlags(android.content.Intent.FLAG_ACTIVITY_NEW_TASK)
        }
        RouteResultRegistry.register(context, request.resultCallback)
        context.startActivity(intent)
    }
}
```

### 3. 拦截器实现

```kotlin
/** 登录拦截器 */
class LoginInterceptor : RouteInterceptor {
    override val priority = 100

    override fun intercept(request: RouteRequest, chain: InterceptorChain): Boolean {
        val needLogin = request.extras.getBoolean("need_login", false)
        if (!needLogin || SessionManager.isLoggedIn) {
            return chain.proceed(request)
        }

        // 保存原始请求，登录成功后恢复跳转
        LoginActivity.start(
            context = request.context,
            pendingPath = request.path,
            pendingArgs = request.extras
        )
        return false
    }
}

/** 维护页拦截器：服务端下发维护状态时，全局拦截 */
class MaintenanceInterceptor : RouteInterceptor {
    override val priority = 200

    override fun intercept(request: RouteRequest, chain: InterceptorChain): Boolean {
        val maintenanceInfo = RemoteConfig.maintenanceInfo
        if (maintenanceInfo == null || !maintenanceInfo.enabled) {
            return chain.proceed(request)
        }

        // 维护中的白名单页面（如公告页）可以放行
        if (request.path in maintenanceInfo.allowedPaths) {
            return chain.proceed(request)
        }

        MaintenanceActivity.start(request.context, maintenanceInfo.message)
        return false
    }
}

/** 功能开关拦截器：目标模块被远程关闭时走降级 */
class FeatureFlagInterceptor : RouteInterceptor {
    override val priority = 150

    override fun intercept(request: RouteRequest, chain: InterceptorChain): Boolean {
        val feature = FeatureFlags.pathMapping[request.path] ?: return chain.proceed(request)

        if (RemoteConfig.isFeatureEnabled(feature)) {
            return chain.proceed(request)
        }

        // 功能已关闭 → 跳降级页
        FallbackActivity.start(request.context, feature)
        return false
    }
}
```

### 5. Compose 路由注册

```kotlin
// ── core/router/src/main/kotlin/.../ComposeRoutes.kt ──
package com.example.core.router

import androidx.compose.runtime.Composable
import androidx.navigation.NavHostController
import androidx.navigation.NavType
import androidx.navigation.compose.NavHost
import androidx.navigation.compose.composable
import androidx.navigation.navArgument

/**
 * Compose 路由注册表。
 *
 * feature 模块在自己的 Application 初始化或显式调用处注册页面，
 * app 模块统一构建 NavHost。
 */
object ComposeRouteRegistry {

    private val routes = LinkedHashMap<String, @Composable (androidx.navigation.NavBackStackEntry) -> Unit>()

    fun register(
        path: String,
        content: @Composable (androidx.navigation.NavBackStackEntry) -> Unit
    ) {
        require(path.startsWith("/")) { "路由路径必须以 / 开头: $path" }
        check(routes.put(path, content) == null) { "路由重复注册: $path" }
    }

    @Composable
    fun BuildNavHost(
        navController: NavHostController,
        startDestination: String,
        defaultArgs: List<androidx.navigation.NamedNavArg> = emptyList()
    ) {
        NavHost(navController = navController, startDestination = startDestination) {
            routes.forEach { (path, content) ->
                composable(
                    route = path,
                    arguments = defaultArgs + listOf(
                        navArgument("id") {
                            type = NavType.StringType
                            nullable = true
                            defaultValue = null
                        }
                    )
                ) { entry -> content(entry) }
            }
        }
    }
}
```

## 常见问题 / 面试要点

**读者问：组件化怎么做路由？路由表是怎么生成的？**

**AI答：**

1. **路由表生成的三个阶段**：
   - **注解声明**：目标页面用 `@RouterUri(path = "/profile/detail")` 标注。
   - **编译期处理**：APT（Java）或 KSP（Kotlin）扫描所有被注解的类，生成路由表类。**运行时零反射、零扫描**，直接 `HashMap` 查找。
   - **运行时注册**：Application 启动时把生成的路由表对象交给 Router。
2. **生成的产物通常有三份**：
   - **路由表**（`path → Class`）：解决"跳到哪里"。
   - **分组索引**（`group → paths`）：解决"批量操作"（如一键注销某模块）。
   - **自动注入**（`$$Autowired`）：解决"参数自动塞进目标页面"，实现"接口 + 路由"的双重调用方式。
3. **组件化（插件化）下的额外处理**：
   - 宿主与插件各有自己的路由表，宿主在启动时**扫描已安装/已下载的插件**，通过 `IProvider` 接口聚合插件路由。
   - **ClassLoader**：插件 dex 由自定义 `ClassLoader` 加载，且要插到父加载器之前，否则宿主会先找到同名类。
   - **资源**：需要重定向 `AssetManager.addAssetPath`，把插件资源并入宿主 `Resources`。
   - **Activity 启动**：需要 hook `Instrumentation`，否则系统找不到插件的 Activity（插件 Activity 实际继承自宿主中的 Stub Activity）。
4. **方案选型**：
   - **不插件化**：直接用 Navigation Component / Navigation Compose + 少量自研封装即可，**不需要自研路由框架**。
   - **需要插件化**：用成熟方案（ARouter、ShadowHook 配套的路由、或自研），成本很高。
5. **面试话术**："路由表的核心思路是**用编译期代码生成换取运行期零反射**。注解提供声明，KSP 生成 HashMap，运行时只是查表——这比运行期扫描 + 反射快一到两个数量级。"

---

**读者问：为什么不用 Navigation Component，非要自己写路由？**

**AI答：**

1. **Navigation Component 的真实限制**：
   - **导航图集中在一处**：`nav_graph.xml` 必须在一个模块里（通常 app）。组件化下，`feature-profile` 的页面要写进 app 的导航图 → **app 依赖 feature 的具体类，破坏了"app 只做组装"的原则**。
   - **参数类型安全依赖代码生成**（Safe Args），但要求 `nav_graph.xml` 集中管理。
   - **拦截机制弱**：Navigation 没有内置的"跳转前统一拦截"点，要实现登录拦截得自己包一层。
2. **自研路由的价值**（什么时候值得）：
   - **需要跨模块跳转且不想产生依赖**。
   - **需要统一拦截**（登录、维护、降级、AB 实验）——**这是最实在的理由**。
   - **需要处理外部 URL / Deep Link**。
   - **需要路由级别的降级**（模块被禁用时跳兜底页）。
3. **但自研路由的代价**：
   - 失去类型安全（字符串 path 的错误是运行期才发现）。
   - 失去官方动画支持（Compose 里要自己接 `AnimatedContent`）。
   - 需要自己维护参数序列化、生命周期、结果回传。
4. **推荐答案（面试稳妥）**：
   > "如果只是单模块或轻量组件化，我倾向用 **Navigation Compose**，它类型安全、动画完善、官方维护。**只有在真正需要跨模块解耦 + 全局拦截 + 外部 URL 时**，才引入一层薄薄的字符串路由封装，把它作为**外部标识层**（Deep Link、埋点、拦截的 key），内部仍然走 Navigation Compose。这样既拿到解耦的好处，又不失去 Compose 的类型安全与动画。"
5. **混合方案的具体形态**：
   ```kotlin
   // 业务代码只认字符串路径
   AppRouter.navigate(context, "/profile/detail", args = mapOf("userId" to id))

   // Router 内部转换成 Navigation Compose 的调用
   navController.navigate("profile/detail?userId=$id")
   ```

---

**读者问：路由拦截器怎么设计？有哪些典型拦截场景？**

**AI答：**

1. **拦截器链的标准模式（责任链 / Chain of Responsibility）**：

```kotlin
interface RouteInterceptor {
    val priority: Int
    fun intercept(request: RouteRequest, chain: InterceptorChain): Boolean
}
```
   - **按优先级排序**（数字大的先执行）。
   - **返回 `true` = 放行**（继续链上下一个）；返回 `false` = **中断**（链路结束，不再跳转）。
   - 关键设计点：**中断后要有兜底动作**（跳登录页/维护页），不能"什么都不做"。
2. **典型场景（按优先级）**：

| 拦截器 | 优先级 | 逻辑 |
| --- | --- | --- |
| **维护页** | 200 | 服务端下发维护状态 → 全局跳维护页（带白名单） |
| **降级/功能开关** | 150 | 目标模块被远程关闭 → 跳降级页 |
| **登录** | 100 | 需要登录但未登录 → 跳登录页，登录后恢复原请求 |
| **实名/权限** | 90 | 需要实名 → 跳认证流程 |
| **AB 实验** | 50 | 当前用户不在实验组 → 跳默认实现 |
| **埋点** | 10 | 记录页面 PV（**必须在最外层**，即使被拦截也要记录尝试） |
3. **实现时的三个坑**：
   - **无限递归**：拦截器里调 `Router.navigate` 又会触发拦截器 → 需要**重入保护**（ThreadLocal 标记或"拦截器发起的跳转跳过某些拦截器"）。
   - **登录后恢复**：需要保存原始 `RouteRequest`（path + args + callback）到内存或 `SavedStateHandle`，登录成功后重新发起。
   - **拦截器依赖 Context**：拦截器里需要 Context 跳转 → 通过 `request.context` 传入，避免静态持有 Activity（防泄漏）。
4. **跨模块通信：IProvider 模式**：
   - 路由不仅能跳 Activity，还能**获取服务**：`ARouter.getInstance().navigation(service.class)`。
   - 实现方式：接口定义在 `core-api`，实现在 feature，通过 APT 生成的 `$$Autowired` 或 Hilt 多绑定注入。
   - **用途**：跨模块获取 Repository、Tracker、Config 等**无 UI 的服务**。
5. **面试话术**："拦截器的价值是把**横切关注点**从业务代码里抽出来。业务代码只需要在跳转时声明'这个页面需要登录'，登录逻辑、登录页跳转、登录后恢复全部由拦截器负责。**新增一种拦截规则时，业务代码零改动。**"

---

**读者问：Deep Link / 外部 URL 怎么处理？有什么安全风险？**

**AI答：**

1. **标准方案**：
   - **Android 原生**：`AndroidManifest` 里 `<intent-filter>` + `<data>` 声明，`autoVerify="true"` 做 App Link 验证（通过 `assetlinks.json` 校验域名归属）。
   - **路由框架**：Deep Link 拦截器解析 URL → 映射到内部路由 → 走正常拦截链（登录、埋点）。
2. **映射示例**：
   ```
   https://example.com/profile/123  →  /profile/detail?userId=123
   https://example.com/order/456    →  /order/detail?orderId=456
   myapp://scan?code=xxx             →  /scan/result?code=xxx
   ```
3. **安全风险（必须主动提，这是加分项）**：
   | 风险 | 说明 | 防御 |
   | --- | --- | --- |
   | **未授权页面访问** | 通过 URL 直接进入内部管理页/调试页 | **路径白名单**，且管理页需额外鉴权 |
   | **参数注入** | 参数被用于 SQL、文件路径、反射 | 类型 + 长度 + 白名单校验；参数化查询 |
   | **敏感操作绕过确认** | 链接直接触发支付/下单/删除 | 敏感操作强制二次确认，不接受链接直达 |
   | **开放重定向** | 参数被用于跳转外部 | 域名白名单 |
   | **XSS（WebView）** | URL 加载到 WebView | 限制可加载域名，禁止 `file://`、禁止 JS 桥暴露 |
   | **DoS** | 超大参数导致 OOM | 参数长度限制（如 64 字符） |
4. **核心原则**：
   > **外部 URL 是完全不可信输入。**它等同于用户输入，甚至比用户输入更危险——因为用户主动点击会认为"是我自己在操作"，而实际上链接可能来自第三方。
5. **实践清单**：
   - 只接受 `https`（自定义 scheme 也需防止被其他 App 抢注）。
   - **host 白名单**。
   - **路径映射显式枚举**（不用通配符）。
   - **参数类型化 + 长度限制 + 字符集限制**。
   - 敏感路径额外标记 `needLogin = true`。
   - **App Link 验证**（`assetlinks.json`）防止域名被抢注。
6. **面试话术**："Deep Link 的第一原则是**把它当成不可信输入**。我们做三件事：**host 白名单、路径显式映射、参数强校验**。另外敏感操作一定不能从链接直达，必须有确认步骤。"

---

**读者问：路由的性能问题？路由表查找会不会有开销？**

**AI答：**

1. **查找开销极小**：
   - APT 生成的路由表是 `HashMap<String, Class>` → **O(1)**，纳秒级。
   - 对比 `Intent` 方案，反射（如果有）只在首次解析，之后缓存 `Method`。
   - **一次跳转的总开销在微秒级**，相比 Activity 启动动辄几毫秒到几十毫秒，**完全可以忽略**。
2. **真正的性能问题不在路由本身，而在跳转后**：
   - Activity 创建与布局膨胀（`setContentView`）。
   - ViewModel 初始化、DI 注入、首次网络请求。
   - Compose 的首次组合（Composition）。
   - **这些才是跳转卡顿的主因**。
3. **路由自身的可优化点**：
   - **拦截器链构建**：如果每次跳转都从 DI 图拉一次拦截器列表，开销会放大 → **在初始化时构建一次并缓存**。
   - **参数反射注入**：APT 生成的 setter 避免反射；必须用反射时**缓存 Method 对象**。
   - **Bundle 序列化**：大对象参数会拖慢跳转 → **只传 ID，不传大对象**。
   - **冷启动时的路由表初始化**：路由表是 `by lazy` 的，第一次跳转会触发类加载 → 可以在 `Application.onCreate` 提前预热（非关键路径）。
4. **主线程约束**：
   - `startActivity` 必须在主线程。从后台线程调用要 `Handler(Looper.getMainLooper()).post {}`。
   - 路由框架应**主动检查 Looper** 并给出清晰错误，而不是抛 `CalledFromWrongThreadException`。
5. **编译期优化**：
   - KSP 生成的路由表是纯 Kotlin `object`，无反射、无字符串解析。
   - 开启 R8 后注意路由表类**不能被混淆移除**（加 ProGuard 规则）。
6. **结论**："路由本身不是性能瓶颈。**如果跳转卡顿，要查的是目标页面的初始化，而不是路由**。"

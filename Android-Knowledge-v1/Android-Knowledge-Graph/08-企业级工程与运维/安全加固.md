# 安全加固

## 一句话定义

安全加固是**用"抬高攻击成本、降低攻击收益"来保护客户端 App**的一整套工程手段。核心认知是：**客户端安全永远是"军备竞赛"而非"绝对防御"**——你无法阻止攻击者拿到 APK，也无法阻止他用 Frida hook 你的函数，你能做的是**让他的自动化攻击成本高到不值得做，让你的核心资产（密钥、协议、算法）在被拿到时已经过期或失效**。

面试开场：**"客户端加固的核心不是'防住'，而是'拖慢'。拖慢逆向 3 天，攻击者就会转向别的目标。但有两件事必须做到 100%：**密钥不落在客户端**、**通信必须可验证**。这两条是底线，混淆和检测只是纵深防御。"**

## 核心原理

### 1. 威胁模型：攻击者是谁

```text
┌──────────────────────────────────────────────────────────────────────┐
│  攻击者分层                                                          │
├──────────────────────────────────────────────────────────────────────┤
│  ① 普通用户（好奇党）                                                 │
│     手段：反编译看广告位、找隐藏菜单、抓包看接口                        │
│     目标：白嫖功能、拿内部资源                                          │
│     对策：基础混淆 + 接口签名 + 服务端鉴权                                │
├──────────────────────────────────────────────────────────────────────┤
│  ② 灰产 / 工作室                                                      │
│     手段：Frida / Xposed hook 改返回值、自动签到、批量刷量                │
│     目标：批量薅羊毛、伪造数据                                          │
│     对策：运行时完整性校验 + 服务端风控 + 关键逻辑上移                      │
├──────────────────────────────────────────────────────────────────────┤
│  ③ 专业逆向团队                                                      │
│     手段：脱壳、动态分析、协议还原、算法破解                              │
│     目标：仿冒 App、盗取协议、破解算法                                    │
│     对策：字符串加密 + 控制流混淆 + 协议加密 + 密钥不下发                   │
├──────────────────────────────────────────────────────────────────────┤
│  ④ 恶意攻击者                                                        │
│     手段：二次打包植入木马、Root 环境劫持、供应链投毒                      │
│     目标：盗号、盗支付、植入广告                                          │
│     对策：签名校验 + 完整性校验 + Root 检测 + 证书 Pinning                 │
└──────────────────────────────────────────────────────────────────────┘
```

**关键认知**：**服务端才是信任边界**。客户端的所有检测（Root 检测、Frida 检测、签名校验）**都是可绕过的**，它们的价值不是"阻止"，而是：
- **提高自动化脚本的成本**（黑产规模化作业的 ROI 直接归零）。
- **在发生攻击时提供证据**（服务端可以据此拒绝请求、要求二次验证）。
- **缩短攻击者的批量作业窗口**。

### 3. 进阶混淆技术

#### 3.1 名称混淆 vs 类名替换

| 技术 | 作用 | 效果 | 代价 |
| --- | --- | --- | --- |
| **名称混淆**（默认 R8） | `OrderViewModel` → `a.b.c` | 中 | 低 |
| **类名替换 / Repackage** | 所有类打包到同一包 `o` 下 | **高**（攻击者不知从哪找入口） | 中（反射/JNI 需配合） |
| **字符串加密** | 常量字符串在 DEX 中是密文，运行时解密 | **高**（`strings` 命令搜不到） | 中（需注入解密调用） |
| **控制流混淆** | 打乱 if/else、for 的控制流结构 | **高**（人工阅读成本暴涨） | **高**（可能影响性能与稳定性） |
| **方法隐藏 / 内联移除** | 把方法体搬进调用方 | 中 | 中（可能破坏反射） |
| **指令重排 / 插入垃圾指令** | 在指令流中插入无意义指令 | 中（阻碍反汇编） | 中 |

**Repackage 的规则写法**：

```proguard
# proguard-rules.pro

# ── 保留崩溃还原所需的信息 ──
-keepattributes SourceFile,LineNumberTable
# 用短文件名替换真实源文件名：保留行号（可定位），隐藏文件名（增加逆向成本）
-renamesourcefileattribute SourceFile

# ── 类名替换：把所有业务类重打包到 o 包下 ──
# 注意：必须保留 Android 框架回调（Activity/Service/Receiver 等），
#      否则系统找不到组件，会直接崩溃
-repackageclasses 'o'
-repackageclassmapping 'com.example.feature.**' 'o.f.**'
-repackageclassmapping 'com.example.core.**' 'o.c.**'

# ── 组件类保留包名（系统按 manifest 里的全限定名反射实例化）──
-keep class com.example.MainActivity { *; }
-keep class * extends android.app.Activity
-keep class * extends android.app.Service
-keep class * extends android.content.BroadcastReceiver
-keep class * extends android.app.Application
```

> ⚠️ **Repackage 的坑**：`-keep class * extends android.app.Activity` 会让所有 Activity 保留在原包下（因为包名变了系统就找不到），这反而暴露了组件位置。更好的做法是**在 manifest 里用相对路径 + 保留一条精确规则**，而不是通配保留。

#### 3.2 字符串加密的原理

```text
【未加密的 DEX】
  const-string v0, "https://api.example.com/v2/user"
  → strings classes.dex | grep api.example.com   ← 一秒定位

【加密后的 DEX】
  const/4 v0, 0x3
  invoke-static {v0}, Lcom/guard/S;->a(I)Ljava/lang/String;
  const-string v1, "Lcom/guard/S;"
  → DEX 里只有密文和索引，"api.example.com" 完全不存在
  → 运行时由 native 层的解密函数还原
```

**实现要点**：
- 解密逻辑放在 **JNI 层**（native 更难被 jadx 直接分析）。
- 使用**按需解密**：只在真正使用字符串时才解密，不做全量解密表。
- 解密结果可加**轻量混淆**（例如用时序扰动、内存分段存储）。

#### 3.3 控制流混淆的代价

控制流混淆通过**替换 if/else 为状态机、为循环插入空操作、拆分 switch 为跳转表**来实现。效果是 jadx/Ghidra 输出的代码完全不可读。

**必须知道的代价**：
- **性能损失**：主要来自**运行时解密 + 反射调用**，典型在 **3% ~ 15%**；若混淆热点路径，可能更严重。
- **稳定性风险**：反射调用会**阻碍 ART 优化**（无法内联、无法去虚拟化），极端情况下触发 `ClassNotFoundException`。
- **兼容性问题**：混淆后 QA 很难定位问题，**必须保证 crash 平台有 mapping 还原能力**（见 [[日志与监控/异常捕获]]）。
- **建议**：**只对核心算法模块混淆控制流**，不要全量混淆。策略是"**核心逻辑混淆 + 崩溃符号化兜底**"。

### 4. 防二次打包

#### 4.1 原理

二次打包（Repackaging）指攻击者用 `apktool` 反编译原包 → 修改代码 → 用自己的签名重新打包，绕过官方渠道分发。

**防御核心**：**运行时校验"当前加载的 APK 的签名"是不是我们自己的**。

```text
APK 的签名信息存在哪？
  → META-INF/*.RSA (v1) 或 APK Signing Block (v2/v3)
  → PackageManager.getPackageInfo(..., GET_SIGNING_CERTIFICATES).signingInfo
  → Android 11+：signingInfo.apkContentsSigners（当前签名者）
                signingInfo.signingCertificateHistory（签名历史，可检测降级重签）
```

#### 4.2 签名校验的三个层次

| 层次 | 检查什么 | 防住什么 | 局限 |
| --- | --- | --- | --- |
| **L1 签名存在性** | `GET_SIGNATURES` 是否为空 | 最粗糙的改包 | 攻击者可伪造一个任意签名的包 |
| **L2 签名匹配** | 签名 SHA-256 是否等于内置常量 | **99% 的二次打包** | 常量被 hook 可绕过；需在多处校验 |
| **L3 签名历史 + 完整性** | 签名历史是否只有我们、APK 摘要是否匹配 | 降级重签、替换 DEX | 需计算 APK 全文件摘要，性能开销大 |

#### 4.3 关键实现细节

- **不要在 `Application.onCreate` 里只校验一次**：攻击者可以直接跳过。应在**多个时机**校验（启动、关键页面、每次网络请求前）。
- **校验逻辑要分散**：把"校验结果"写入多个位置，攻击者必须全部 patch 才能绕过。
- **`GET_SIGNATURES` 已被废弃**：Android 9+ 对第三方应用隐藏了其他包的签名；`GET_SIGNING_CERTIFICATES`（API 28+）才是正确 API。

### 5. 防调试与防 Hook

#### 5.1 防调试的三种手段

| 手段 | 原理 | API / 路径 |
| --- | --- | --- |
| **ptrace 自附加** | `ptrace(PTRACE_TRACEME)`：如果已被调试器附加则返回失败 | NDK `ptrace` |
| **TracerPid 读取** | `/proc/self/status` 里的 `TracerPid` 字段：非 0 表示有调试器附加 | 读 `/proc/self/status` |
| **isDebuggerConnected** | 系统提供的便捷判断 | `Debug.isDebuggerConnected()` / `Debug.waitingForDebugger()` |

#### 5.2 防 Hook 的检测面

| 检测对象 | 检测原理 | 关键路径 |
| --- | --- | --- |
| **Frida** | 检测 `frida-server`/`re.frida.server` 进程、`libfrida-agent.so` 库、端口 27042、`/proc/self/maps` 中的 `frida` 字符串 | `maps` 扫描最可靠 |
| **Xposed** | 检测 `de.robv.android.xposed.installer` 包、`XposedBridge.jar` 在 classpath、`/system/framework/XposedBridge.jar` 存在、`ro.build.tags` 含 `xposed` | `/system/framework/` 扫描 |
| **通用 Hook 框架** | `maps` 中出现 `sandhook`、`epic`、`whale`、`ShadowHook`、`.so` 中包含 `hook` 字样的可疑库 | `/proc/self/maps` |
| **内存注入** | `maps` 中出现可写且匿名的匿名可执行映射 | `/proc/self/maps` 权限位 |
| **Java 层 Hook** | 反射检查关键方法的 `native` 修饰符是否被去掉 | `Method.modifiers` 位运算 |
| **重打包注入** | 检查 `ApplicationInfo.sourceDir` 与 `classLoader` 实际加载路径是否一致 | `PackageManager` 对比 |

**`/proc/self/maps` 的关键特征**：
- Frida 会把 Agent 注入到进程内存，maps 里会出现 `libfrida-agent-64.so` 这样的条目。
- 即使文件名被改，**映射的权限位**（`r-xp` 可读可执行）加上**匿名映射**（无文件路径）是重要线索。
- 也可用 `/proc/self/task/<tid>/maps` 检查其他线程的映射（Frida 有时只注入到特定线程）。

### 6. Root 检测与模拟器检测

| 检测项 | 方法 | 准确度 |
| --- | --- | --- |
| **Root 文件** | `/system/app/Superuser.apk`、`/system/xbin/su`、`/system/bin/su`、`/sbin/su`、`/su/bin/su`、Magisk 的 `/sbin/.magisk` | 低（易绕过，但成本极低值得做） |
| **Build 属性** | `Build.TAGS` 含 `test-keys`、`ro.debuggable == 1`、`ro.build.type == userdebug` | 中 |
| **Root 管理器** | 查询 `com.topjohnwu.magisk`、`eu.chainfire.supersu`、`com.koushikdutta.superbackup` 是否安装 | 中 |
| **SU 命令** | `which su` / 执行 `su -c id`（Android 9+ 返回 `Permission denied` 是正常的，要看具体行为） | 中 |
| **挂载点** | `/proc/mounts` 里 `/system` 被挂载为 overlayfs | 高 |
| **SELinux** | `getenforce` 返回 `Permissive` | 高 |
| **密钥** | 用 AndroidKeyStore 生成的密钥能否被 root 读取 | 很高 |
| **模拟器** | `Build.FINGERPRINT` 含 `generic`/`unknown`/`emulator`、`Build.HARDWARE` 含 `goldfish`/`ranchu`、`Build.MODEL` 含 `sdk`/`Emulator`、`/dev/socket/qemud`、`/dev/qemu_pipe`、`ro.hardware` 含 `ranchu`、`/sys/qemu_trace`、传感器恒定值 | 中高 |
| **模拟器网络** | 无法访问 Google Play 服务（但这在真机禁用 GMS 时也成立） | 低 |

> ⚠️ **Root 检测最大的坑**：**误伤真实用户**。很多海外用户为了玩银行 App 装了 Root，但你的 App 不是银行 App——一刀切拒绝服务会流失大量用户。**正确做法是"检测 + 记录 + 上报 + 降级"而不是"检测 + 拒绝"**：把设备标记为高风险，服务端对高风险设备收紧策略（如限制提现额度、要求二次验证），而不是客户端直接退出。

### 7. 网络层防护

#### 7.1 证书 Pinning

**原理**：客户端内置服务器证书（或公钥）的指纹，TLS 握手时校验服务端出示的证书是否匹配。

```text
【无 Pinning】
  客户端 ──TLS──→ 中间人代理（用户装了根证书）
     中间人用自签证书与客户端握手 → 客户端只检查"证书是否由系统信任的 CA 签发"
     → 握手成功，中间人看到全部明文  ← 抓包成功

【有 Pinning】
  客户端 ──TLS──→ 中间人代理
     中间人出示自签证书 → 客户端校验公钥指纹
     → 不匹配 → 握手失败 → App 报错/降级  ← 抓包失败
```

**关键实现要点**：
- **Pinning 公钥而不是证书**：CA 会轮换中间证书，Pin 证书会导致 CA 更新后全部客户端连不上；Pin 公钥（SubjectPublicKeyInfo）更稳。
- **必须 Pin 备用密钥**：万一主密钥泄露，能快速发布新 Pin。
- **配套"Pin 失败时的信任路径"**：不能直接崩，否则中间人 DoS 就能让用户完全不能用 App。Google 推荐的 `network_security_config` 支持 `pin-set` + `trust anchors`。

```xml
<!-- res/xml/network_security_config.xml -->
<network-security-config>
    <!-- 生产环境：只信任系统 CA + 固定的自有公钥 -->
    <base-config cleartextTrafficPermitted="false">
        <trust-anchors>
            <certificates src="system" />
            <!-- 备用锚点：CA 轮换时的兜底 -->
            <certificates src="@raw/backup_ca" />
        </trust-anchors>
        <pin-set expiration="2027-06-01">
            <!-- 主公钥（SHA-256 指纹） -->
            <pin digest="SHA-256">7HIpactkIAq2Y49orFOOQKurWxmmSFZhBC0QYcLywUI=</pin>
            <!-- 备用公钥：主密钥泄露时可无发版切换 -->
            <pin digest="SHA-256">FsQqRR5i8rT4rH5F5F5F5F5F5F5F5F5F5F5F5F5F5F5F5F5F5F5F5F5F5F5F5F5F5A=</pin>
        </pin-set>
    </base-config>

    <!-- 测试环境：允许抓包（仅 debug 构建引用） -->
    <debug-overrides>
        <trust-anchors>
            <certificates src="user" />
        </trust-anchors>
    </debug-overrides>
</network-security-config>
```

```xml
<!-- AndroidManifest.xml -->
<application
    android:networkSecurityConfig="@xml/network_security_config"
    android:usesCleartextTraffic="false">
```

#### 7.2 防重放

**重放攻击**：攻击者抓到一个合法请求，原封不动地重复发送（可能是一张优惠券、一次转账）。

**防御三要素**：

| 要素 | 做法 | 说明 |
| --- | --- | --- |
| **Timestamp** | 请求携带 `timestamp=1699999999000`，服务端校验与服务端时间差 < 5 分钟 | 超过窗口直接拒绝 |
| **Nonce** | 每次请求携带唯一随机串，服务端记录已用 nonce（Redis set，TTL = 窗口期） | 重复 nonce 直接拒绝 |
| **Signature** | 对 `method + path + sortedParams + timestamp + nonce` 计算 HMAC-SHA256 | 参数被改则签名失效 |

**签名参数排序必须规范化**：所有参数按 key 字典序排列，值做 URL 编码，空值也参与签名（否则 `a=1&b=` 和 `a=1&b` 签名相同，是经典漏洞）。

### 8. 混淆后崩溃的还原（retrace）

混淆让逆向变难，但代价是**线上崩溃堆栈变成 `a.b.c.a()`**。完整方案：

```text
构建期
  R8 混淆 → 生成 mapping.txt（类/方法/字段 的 混淆前后对照）
    ↓
发布期
  CI 自动上传 mapping.txt 到崩溃平台（Crashlytics / Bugly / Sentry）
  CI 同时归档到制品库（永久保存，retention 至少匹配崩溃保留期）
    ↓
崩溃期
  用户崩溃 → 堆栈 `a.b.c.a(SourceFile:42)` 上报
    ↓
  崩溃平台用对应版本的 mapping.txt 还原 → `com.example.feature.order.OrderViewModel.loadOrder(OrderViewModel.kt:42)`
```

**必须遵守的三条铁律**：
1. **mapping 文件与 APK 版本严格一一对应**，用 **Build ID** 而非版本号关联（版本号会被复用/回滚）。
2. **每次发版自动上传**，绝不能靠人手动（人一定会忘）。
3. **mapping 文件永久保存**——崩溃可能在发版半年后才被用户上报。

**本地 retrace**：

```bash
# 用 SDK 里的 retrace 还原
$ANDROID_HOME/build-tools/34.0.0/retrace \
    -m app/build/outputs/mapping/release/mapping.txt \
    < crash-stacktrace.txt

# 用 R8 jar（Gradle 缓存里）还原，支持 ProGuard 格式
java -cp r8.jar com.android.tools.r8.retrace.Retrace \
    app/build/outputs/mapping/release/mapping.txt crash.txt
```

> **面试话术补充**：混淆和"崩溃可读性"是**一对矛盾体**，我一般用 `-renamesourcefileattribute SourceFile` 做折中——保留行号（能定位到具体哪一行），但把文件名换成 `SourceFile`，攻击者拿不到"OrderViewModel.kt"这个名字，定位难度只降一点点，逆向成本却明显上升。

### 1. 完整的运行时安全检测器

```kotlin
package com.example.core.security

import android.content.Context
import android.content.pm.PackageManager
import android.os.Build
import android.os.Debug
import android.os.Process
import java.io.File

/**
 * 运行时环境检测器。
 *
 * 设计原则（非常重要）：
 * 1. **检测结果只做"标记"，不直接"拒绝服务"**——误伤真实用户的代价远大于放过少量攻击者
 * 2. 检测逻辑本身要**可被绕过也不影响安全底线**，因为真正的安全边界在服务端
 * 3. **分散校验**：结果写入多个位置，攻击者需要全部 patch 才能完全绕过
 * 4. 检测要**快**：整个检测应该在 50ms 内完成，不能拖慢启动
 */
object SecurityDetector {

    private const val TAG = "SecurityDetector"

    /** 检测结果缓存，避免重复 IO */
    private val cached = lazy { performDetection() }

    /** 检测项枚举，便于统一上报与分级处置 */
    enum class Risk {
        NORMAL,
        SUSPICIOUS,   // 疑似：不影响功能，但收紧服务端策略
        HOSTILE       // 明确恶意：拒绝敏感操作
    }

    data class Result(
        val risk: Risk,
        val reasons: List<String>,
        val environment: String
    ) {
        fun toReportMap(): Map<String, Any> = mapOf(
            "risk" to risk.name,
            "reasons" to reasons,
            "env" to environment
        )
    }

    fun detect(context: Context): Result = cached.value

    private fun performDetection(): Result {
        val reasons = mutableListOf<String>()

        // ── 1. 调试器检测 ──
        if (isDebuggerAttached()) {
            reasons += "debugger_attached"
        }

        // ── 2. Frida / Hook 框架检测 ──
        if (isFridaPresent()) {
            reasons += "frida_present"
        }
        if (isXposedPresent()) {
            reasons += "xposed_present"
        }

        // ── 3. Root 环境检测 ──
        if (isRooted()) {
            reasons += "rooted_device"
        }

        // ── 4. 模拟器检测 ──
        if (isEmulator()) {
            reasons += "emulator"
        }

        // ── 5. 重打包检测 ──
        if (isRepackaged(context)) {
            reasons += "repackaged"
        }

        val risk = when {
            reasons.contains("repackaged") || reasons.contains("debugger_attached") -> Risk.HOSTILE
            reasons.isNotEmpty() -> Risk.SUSPICIOUS
            else -> Risk.NORMAL
        }
        return Result(risk, reasons, environmentDescription())
    }

    /**
     * 调试器检测：三种方式任一命中即判定为被调试。
     */
    private fun isDebuggerAttached(): Boolean {
        // 方式一：系统 API（最简单，但可被 hook）
        if (Debug.isDebuggerConnected() || Debug.waitingForDebugger()) return true

        // 方式二：读取 /proc/self/status 的 TracerPid 字段（非 0 表示有调试器附加）
        if (readTracerPid() > 0) return true

        // 方式三：native 层 ptrace 自附加（最难绕过，但实现成本高）
        // if (NativeGuard.selfTrace()) return true

        return false
    }

    /**
     * 从 /proc/self/status 中解析 TracerPid。
     *
     * ⚠️ 这是 Android 10+ 上检测调试器最可靠的方法，
     *    比 Debug.isDebuggerConnected() 难绕过得多（后者容易被 hook）。
     */
    private fun readTracerPid(): Int {
        return try {
            File("/proc/self/status").useLines { lines ->
                lines.firstOrNull { it.startsWith("TracerPid:") }
                    ?.substringAfter(":")
                    ?.trim()
                    ?.toIntOrNull()
                    ?: 0
            }
        } catch (e: Exception) {
            // 某些 ROM 限制了 /proc 访问，读取失败不等于安全
            0
        }
    }

    /**
     * Frida 检测。
     *
     * 三条线：
     * 1. /proc/self/maps 里搜 frida 关键字（最有效，能覆盖改名的情况）
     * 2. 检查可疑的匿名可执行映射（Frida 注入的 shellcode）
     * 3. 尝试连接 Frida 默认端口 27042（会暴露自己，不建议在生产用）
     */
    private fun isFridaPresent(): Boolean {
        // 线 1：扫描内存映射
        if (scanMapsForKeywords(listOf("frida", "gadget", "re.frida"))) return true

        // 线 2：扫描其他线程的 maps（Frida 有时只注入部分线程）
        try {
            File("/proc/self/task").listFiles()?.forEach { taskDir ->
                if (scanMapsForKeywords(listOf("frida"), File(taskDir, "maps"))) return true
            }
        } catch (e: Exception) {
            // 忽略
        }

        // 线 3：检查 Frida 常见的内存路径
        val fridaPaths = listOf(
            "/data/local/tmp/frida-server",
            "/data/local/tmp/re.frida.server",
            "/data/local/tmp/frida-agent-64.so"
        )
        if (fridaPaths.any { File(it).exists() }) return true

        return false
    }

    /**
     * 扫描 /proc/self/maps（或指定的 maps 文件）中的关键字。
     *
     * ⚠️ 注意：字符串本身可能被加密/拆分。
     *    更强的做法是把关键字拆成两半拼接，运行时才组合，
     *    避免攻击者用 strings 命令在 APK 里直接搜到检测特征。
     */
    private fun scanMapsForKeywords(keywords: List<String>, mapsFile: File = File("/proc/self/maps")): Boolean {
        return try {
            mapsFile.useLines { lines ->
                lines.any { line -> keywords.any { line.contains(it, ignoreCase = true) } }
            }
        } catch (e: Exception) {
            false
        }
    }

    /**
     * Xposed 检测。
     *
     * 覆盖三类特征：
     * 1. 系统目录中的 Xposed 组件文件
     * 2. classpath 中的 XposedBridge
     * 3. 运行时被 hook 的系统方法（Method 的 native 修饰符被去掉）
     */
    private fun isXposedPresent(): Boolean {
        // 1. 文件系统特征
        val xposedPaths = listOf(
            "/system/framework/XposedBridge.jar",
            "/system/bin/app_process",
            "/system/app/Superuser.apk",
            "/system/xbin/su"
        )
        if (xposedPaths.any { File(it).exists() }) return true

        // 2. classpath 特征
        try {
            val classpath = System.getProperty("java.class.path") ?: ""
            if (classpath.contains("XposedBridge") || classpath.contains("xposed")) return true
        } catch (e: Exception) {
            // 忽略
        }

        // 3. Build 属性特征
        if (Build.TAGS?.contains("xposed") == true) return true
        if (System.getProperty("ro.xposed.version") != null) return true

        // 4. 运行时 hook 特征：检查某个系统方法的 modifiers 是否还带 native
        try {
            val method = Class.forName("android.app.ActivityThread").getDeclaredMethod("currentActivityThread")
            val modifiers = method.modifiers
            val NATIVE_MODIFIER = 0x100L   // Modifier.NATIVE
            if (modifiers and NATIVE_MODIFIER == 0L) {
                // native 方法被改成了 Java 实现 → 典型的 Xposed/其他框架 hook 特征
                return true
            }
        } catch (e: Exception) {
            // 类不存在或方法改名 → 忽略
        }

        return false
    }

    /**
     * Root 检测。
     *
     * 多信号组合：文件 + 属性 + 挂载点 + SELinux。
     * ⚠️ 任何单一信号都有大量误报，必须多信号组合，
     *    并且**不作为拒绝服务的唯一依据**。
     */
    private fun isRooted(): Boolean {
        // 信号 1：su / 管理器文件
        val suPaths = listOf(
            "/system/app/Superuser.apk",
            "/system/app/com.topjohnwu.magisk",
            "/system/xbin/su",
            "/system/bin/su",
            "/sbin/su",
            "/su/bin/su",
            "/data/local/xbin/su",
            "/data/local/bin/su",
            "/system/sd/xbin/su",
            "/system/bin/.ext/.su",
            "/sbin/.magisk"          // Magisk 隐藏 root 的挂载点
        )
        if (suPaths.any { File(it).exists() }) return true

        // 信号 2：Build 属性（userdebug/eng 版本）
        if (Build.TAGS?.contains("test-keys") == true) return true

        // 信号 3：挂载点被 overlay（Magisk 的核心特征）
        try {
            File("/proc/mounts").useLines { lines ->
                if (lines.any { it.contains("/system") && it.contains("overlay") }) return true
            }
        } catch (e: Exception) {
            // 忽略
        }

        // 信号 4：SELinux 处于 Permissive
        try {
            val process = Runtime.getRuntime().exec(arrayOf("getenforce"))
            val output = process.inputStream.bufferedReader().readText().trim()
            if (output.equals("Permissive", ignoreCase = true)) return true
        } catch (e: Exception) {
            // 多数真机没有 getenforce 工具，忽略
        }

        return false
    }

    /**
     * 模拟器检测。
     *
     * 组合多个信号，任意 N 个命中即判定。
     * ⚠️ 模拟器上做开发调试是合法需求，不要在 debug 构建里启用。
     */
    private fun isEmulator(): Boolean {
        var hits = 0
        val threshold = 2

        // 信号 1：硬件特征
        val hardware = Build.HARDWARE ?: ""
        if (hardware.contains("goldfish") || hardware.contains("ranchu")) hits++

        // 信号 2：产品特征
        val product = Build.PRODUCT ?: ""
        if (product.contains("sdk") || product.contains("emulator") || product.contains("simulator")) hits++

        // 信号 3：指纹
        val fingerprint = Build.FINGERPRINT ?: ""
        if (fingerprint.startsWith("generic") || fingerprint.contains("generic") ||
            fingerprint.contains("vbox") || fingerprint.contains("emulator")) hits++

        // 信号 4：型号
        val model = Build.MODEL ?: ""
        if (model.contains("google_sdk") || model.contains("Emulator") ||
            model.contains("Android SDK built for")) hits++

        // 信号 5：qemu 设备节点
        if (File("/dev/socket/qemud").exists() ||
            File("/dev/qemu_pipe").exists() ||
            File("/sys/qemu_trace").exists()) hits++

        // 信号 6：ro.kernel.qemu
        if (System.getProperty("ro.kernel.qemu") == "1") hits++

        return hits >= threshold
    }

    /**
     * 二次打包检测。
     *
     * 思路：对比"系统记录的安装路径"和"类加载器实际加载的路径"。
     * 二次打包后，APK 从新路径加载，但 PackageManager 里的 sourceDir 可能被改，
     * 或者签名被替换。
     */
    private fun isRepackaged(context: Context): Boolean {
        return try {
            val packageInfo = context.packageManager.getPackageInfo(
                context.packageName,
                PackageManager.GET_SIGNING_CERTIFICATES
            )

            // 检查 1：签名是否匹配我们内置的常量
            val signatures = packageInfo.signingInfo?.apkContentsSigners
            if (signatures.isNullOrEmpty()) return true

            val ourCertHash = SignatureVerifier.OUR_CERT_SHA256
            val matched = signatures.any { sig ->
                val hash = sha256(sig.toByteArray())
                hash.contentEquals(ourCertHash)
            }
            if (!matched) return true

            // 检查 2：加载路径与 sourceDir 是否一致
            val classLoaderPath = context.classLoader.toString()
            if (classLoaderPath.contains("cache") || classLoaderPath.contains("app_process")) {
                // 正常情况下 dex 在 /data/app/ 下；出现在 cache 说明被动态加载
            }
            false
        } catch (e: PackageManager.NameNotFoundException) {
            true    // 取不到包信息本身就是异常信号
        }
    }

    private fun sha256(bytes: ByteArray): ByteArray {
        val digest = java.security.MessageDigest.getInstance("SHA-256")
        return digest.digest(bytes)
    }

    private fun environmentDescription(): String {
        return "Android ${Build.VERSION.RELEASE}(API ${Build.SDK_INT}) " +
                "${Build.MANUFACTURER}/${Build.MODEL} pid=${Process.myPid()}"
    }
}
```

```kotlin
package com.example.core.security

import android.content.Context
import android.content.pm.PackageManager
import android.util.Base64
import java.security.MessageDigest

/**
 * 签名校验器。
 *
 * ⚠️ 三条工程原则：
 * 1. **不信任运行时可被 hook 的返回值**：签名结果应在多处校验，
 *    且部分校验应放在 native 层
 * 2. **常量不明文存放**：证书指纹应拆分/编码，避免被 strings 搜出
 * 3. **校验失败不直接崩**：降级到"受限模式"（禁用支付、隐藏敏感数据），
 *    避免用户被 DoS 后无法使用
 */
object SignatureVerifier {

    /**
     * 我们自己的签名证书 SHA-256 指纹（Base64）。
     *
     * ⚠️ 安全提示：直接写成明文常量，攻击者用 strings 一搜就能定位
     *    "这是签名校验的位置"，然后 patch 掉。
     *    生产环境应该：
     *    - 拆成两半拼接（运行时组合）
     *    - 放在 native 层
     *    - 或做一次简单的异或/哈希变换
     */
    private val PART_A = "MIIC5TCCAb+gAwIBAgIUJ0P"
    private val PART_B = "3kQ1x2mNv7Bs8Wc0L9rY4zE6hFjKlMnOpQrStUvWx"

    /** 期望的签名 SHA-256（运行时由两段拼出） */
    val OUR_CERT_SHA256: ByteArray by lazy {
        Base64.decode(PART_A + PART_B, Base64.DEFAULT)
    }

    /**
     * 校验当前安装包的签名。
     *
     * @return true 表示签名可信
     */
    fun verify(context: Context): Boolean {
        return try {
            val pm = context.packageManager
            val packageInfo = pm.getPackageInfo(
                context.packageName,
                PackageManager.GET_SIGNING_CERTIFICATES
            )

            // Android 9+ 用 signingInfo；低版本用 signatures
            val signatures = if (android.os.Build.VERSION.SDK_INT >= android.os.Build.VERSION_CODES.P) {
                packageInfo.signingInfo?.apkContentsSigners
            } else {
                @Suppress("DEPRECATION")
                packageInfo.signatures
            }

            if (signatures.isNullOrEmpty()) return false

            // ★ 关键：所有签名都必须匹配（主签名 + 历史签名）
            //   只检查第一个签名是不够的——攻击者可以追加一个伪造签名
            signatures.all { sig ->
                val digest = MessageDigest.getInstance("SHA-256").digest(sig.toByteArray())
                digest.contentEquals(OUR_CERT_SHA256)
            }
        } catch (e: PackageManager.NameNotFoundException) {
            false
        } catch (e: Exception) {
            false
        }
    }
}
```

### 3. 防重放与接口签名

```kotlin
package com.example.core.security

import java.security.MessageDigest
import javax.crypto.Mac
import javax.crypto.spec.SecretKeySpec

/**
 * 请求签名器：防篡改 + 防重放。
 *
 * 签名串构造规则（服务端必须完全一致）：
 *   method + "\n" + path + "\n" + timestamp + "\n" + nonce + "\n" + canonicalParams
 *
 * canonicalParams：所有业务参数按 key 字典序排列，key=value 用 & 连接，
 *   value 做 URL 编码，**空值也参与签名**（否则 a=1&b= 与 a=1&b 签名相同）
 */
class RequestSigner(private val secretProvider: () -> String) {

    /**
     * 生成签名头。
     *
     * @param nonce 必须全局唯一（建议 UUID 或 服务端下发的一次性 token）
     */
    fun sign(method: String, path: String, params: Map<String, String>): Headers {
        val timestamp = System.currentTimeMillis().toString()
        val nonce = java.util.UUID.randomUUID().toString().replace("-", "")

        val canonical = params.entries
            .sortedBy { it.key }                       // ★ 字典序排序
            .joinToString("&") { (k, v) ->
                "${urlEncode(k)}=${urlEncode(v)}"       // ★ 空值也参与
            }

        val raw = buildString {
            append(method.uppercase()).append('\n')
            append(path).append('\n')
            append(timestamp).append('\n')
            append(nonce).append('\n')
            append(canonical)
        }

        val signature = hmacSha256(raw, secretProvider())

        return Headers(
            timestamp = timestamp,
            nonce = nonce,
            signature = signature
        )
    }

    /**
     * HMAC-SHA256 签名。
     *
     * ⚠️ 关键问题：secret 不能硬编码在客户端！
     *    正确做法：secret 由服务端在用户登录/初始化时下发，
     *    并且可以随时轮换（服务端校验时同时接受新旧两个 secret）。
     */
    private fun hmacSha256(data: String, secret: String): String {
        val mac = Mac.getInstance("HmacSHA256")
        mac.init(SecretKeySpec(secret.toByteArray(), "HmacSHA256"))
        val bytes = mac.doFinal(data.toByteArray())
        return bytes.joinToString("") { "%02x".format(it) }
    }

    private fun urlEncode(value: String): String =
        java.net.URLEncoder.encode(value, "UTF-8")

    data class Headers(
        val timestamp: String,
        val nonce: String,
        val signature: String
    )
}
```

```kotlin
// 服务端（Java 示例）校验逻辑——必须与客户端完全对称
/**
 * 服务端校验步骤：
 * 1. 校验 timestamp 与服务端时间差 ≤ 5 分钟（防跨窗口重放）
 * 2. 校验 nonce 是否已使用（Redis SETNX，TTL = 5 分钟）→ 防同窗口内重放
 * 3. 用相同规则重算签名，比对签名 → 防参数篡改
 */
public boolean verifyRequest(HttpServletRequest request) {
    String timestamp = request.getHeader("X-Timestamp");
    String nonce = request.getHeader("X-Nonce");
    String signature = request.getHeader("X-Signature");

    // 1. 时间窗口
    long ts = Long.parseLong(timestamp);
    if (Math.abs(System.currentTimeMillis() - ts) > TimeUnit.MINUTES.toMillis(5)) {
        return false;   // 时间戳过期
    }

    // 2. Nonce 一次性校验（Redis SETNX 保证原子性）
    Boolean firstUse = redis.opsForValue().setIfAbsent(
        "nonce:" + nonce, "1", 5, TimeUnit.MINUTES);
    if (!Boolean.TRUE.equals(firstUse)) {
        return false;   // nonce 已被使用 → 重放
    }

    // 3. 重算签名
    String canonical = request.getParameterMap().entrySet().stream()
            .sorted(Map.Entry.comparingByKey())
            .map(e -> urlEncode(e.getKey()) + "=" +
                      urlEncode(e.getValue()[0] == null ? "" : e.getValue()[0]))
            .collect(Collectors.joining("&"));
    String raw = request.getMethod().toUpperCase() + "\n"
               + request.getRequestURI() + "\n"
               + timestamp + "\n" + nonce + "\n"
               + canonical;
    String expected = hmacSha256(raw, secret);
    return constantTimeEquals(expected, signature);
}
```

## 常见问题 / 面试要点

**读者问：客户端安全加固到底能做到什么程度？能不能做到"不被破解"？**

**AI答：**

1. **先给结论**：**客户端安全做不到"绝对防御"，只能做到"提高攻击成本 + 缩短攻击窗口 + 提供事后证据"**。任何把客户端密钥、核心算法、判定逻辑放在客户端的方案，本质上都是"延迟泄露"，不是"不泄露"。
2. **按"资产"分级加固**（这是最重要的思路）：
   | 资产 | 威胁 | 正确做法 |
   | --- | --- | --- |
   | **API 密钥 / AppSecret** | 反编译即得，直接伪造请求 | **绝对不能放客户端**。放服务端 |
   | **核心算法（推荐/风控规则）** | 被还原后可直接调用 | **上移服务端**；客户端只做展示 |
   | **通信协议** | 被抓包后伪造请求 | 请求签名 + Timestamp + Nonce + 服务端校验 |
   | **用户数据（本地缓存）** | Root 设备可直接读 | 敏感字段加密存储（密钥存 AndroidKeyStore） |
   | **防作弊（签到/抽奖）** | 脚本批量刷 | 服务端风控为主，客户端检测为辅 |
3. **面试话术**："我的原则是**三档分级**——**密钥绝不落客户端，算法尽量上移，混淆只做纵深防御**。混淆能让逆向多花 3 天，但只要有一个 API 密钥硬编码在 APK 里，攻击者根本不需要逆向，直接 `strings` 一下就能拿到。所以我会优先做**密钥托管**和**服务端校验**，混淆是第二优先级。"

---

**读者问：怎么提升逆向难度？有哪些具体手段？优先级怎么排？**

**AI答：**

1. **分层手段与性价比**：
   | 手段 | 逆向成本提升 | 实现成本 | 性能影响 | 优先级 |
   | --- | --- | --- | --- | --- |
   | **密钥托管（服务端下发）** | 极高（密钥可轮换、可短时效） | 中（需服务端配合） | 极小 | **P0** |
   | **接口签名 + 防重放** | 高（伪造请求需先破算法） | 中 | 极小 | **P0** |
   | **证书 Pinning** | 高（抓包需装用户 CA，pin 后失败） | 低（配置文件） | 极小 | **P0** |
   | **字符串加密** | 中高 | 中（需引入加固 SDK 或自研） | 小（3%~5%） | P1 |
   | **类名替换（repackage）** | 中 | **低（一条规则）** | 无 | **P1（性价比最高）** |
   | **控制流混淆** | 高（人工阅读成本暴涨） | **高（需专业方案）** | **中（3%~15%）** | P2 |
   | **防调试 / 防 Hook 检测** | 中（增加黑产成本） | 中 | 小 | P2 |
   | **Root / 模拟器检测** | 低（易绕过） | 低 | 小 | P3 |
2. **真正的性价比之王是 `-repackageclasses 'o'`**：**一行 ProGuard 规则，零性能损耗，逆向难度显著提升**。因为攻击者反编译后看到的是几百个 `o.a.b.c`，完全不知道哪个是登录逻辑、哪个是支付逻辑，只能靠**逐个点开看**或**运行时动态跟踪**——从"文本搜索"降级到"人工考古"。
3. **混淆的三个必知代价**：
   - **性能**：主要来自字符串解密的运行时开销和反射调用阻碍 ART 优化。**核心算法模块可接受 5%~10%**，全量混淆要慎。
   - **稳定性**：反射、序列化、DI 框架都可能被误伤，**必须有 mapping 还原 + 充分测试**。
   - **可调试性**：QA 报的崩溃是 `a.b.c.a()`，没有符号化流程等于盲测。
4. **面试话术**："我会**按资产分级**做加固，而不是堆检测点。P0 是密钥托管、接口签名、证书 Pinning——这三件几乎没有性能代价且收益最高；P1 是类名替换和字符串加密；控制流混淆只在核心算法上用，因为它的性能与稳定性代价最大。**检测类手段（Root/Frida）我定位为'提高黑产成本'，绝不做成拒绝服务**，否则误伤海外真实用户得不偿失。"

---

**读者问：Frida 是怎么检测的？能被绕过吗？**

**AI答：**

1. **Frida 的工作原理**（先理解原理才能设计检测）：
   - `frida-server` 以 root 权限运行在设备上；
   - 通过 **ptrace** 附加到目标进程（`PTRACE_ATTACH`）；
   - 把 `frida-agent.so` **注入**到目标进程的内存；
   - 通过 Unix Domain Socket 通信，暴露一套 JavaScript 运行时，攻击者用 JS 写 hook 脚本。
2. **检测面（按可靠性从高到低）**：
   | 检测项 | 原理 | 可靠性 | 绕过难度 |
   | --- | --- | --- | --- |
   | **扫描 `/proc/self/maps`** | 注入的 agent 库会出现在内存映射里 | **最高** | 中（改名可绕） |
   | **扫描 `/proc/self/task/*/maps`** | 覆盖只注入到部分线程的情况 | 高 | 中 |
   | **检测 `libfrida-agent.so` 文件存在** | 常见路径 `/data/local/tmp/` | 中 | 低（换路径） |
   | **`TracerPid != 0`** | frida-server 用 ptrace 附加，会留下痕迹 | **高** | 中（用注入代替 attach） |
   | **检查关键方法是否被 hook** | Java 方法的 `native` 修饰符被去掉 | 中 | 中（用 inline hook 可保留） |
   | **连接 27042 端口探测** | Frida 默认端口 | 低 | 一改就绕，且会暴露自己 |
3. **`/proc/self/maps` 检测的关键技巧**：
   - 不仅搜 `"frida"` 字符串，还要看**权限位**——攻击者改名后，映射仍然可能是**匿名可执行**（`r-xp` 且路径为空），这是强特征。
   - 检查 `maps` 的**加载顺序异常**：正常进程的映射按加载顺序排列，注入的 agent 通常出现在不合理的位置。
4. **必须承认的局限（面试加分点）**：
   - **所有客户端检测都能被绕过**。Frida 生态有大量反检测模块（`frida-hide`、`frida-gadget` 自定义名称、inline hook 替代 GOT hook 等）。
   - **对抗是持续博弈**：检测规则要定期更新。
   - **真正的防线是服务端**：服务端行为分析（调用频率、设备指纹、行为轨迹）能识别"被 hook 的 App"，因为**hook 后的 App 行为模式和人不一样**（比如签到脚本会 100% 成功）。
5. **面试话术**："Frida 检测我会做**三层**：`/proc/self/maps` 扫 `frida-agent` 关键字 + 查匿名可执行映射、`TracerPid` 判断是否被 ptrace 附加、检查关键 Java 方法的 native 修饰符是否被剥离。**但我非常清楚这些都能被绕过**——Frida 生态有现成的反检测方案。所以我把客户端检测定位为'**抬高黑产脚本的成本**'，真正的风控放在服务端：**hook 过的设备行为模式异常**（成功率 100%、无错误、操作节奏机械），服务端能识别出来。"

---

**读者问：Xposed 和 Root 检测有什么区别？Root 设备占比高不高？该不该拦？**

**AI答：**

1. **Root ≠ Xposed**：
   - **Root**：设备获得 superuser 权限，能读写其他 App 数据、装任意系统应用。可以**不用任何 hook 框架**。
   - **Xposed**：一种 Hook 框架（需 Root 或类 Xposed 的虚拟化方案如 LSPatch/VirtualApp），让**普通 App 内的方法被替换**。
   - **关系**：Xposed 通常需要 Root；但 Root 设备不一定装了 Xposed。
2. **Root 检测的多信号组合**（单一信号误报率极高）：

   | 信号 | 检查方式 | 误报场景 |
   | --- | --- | --- |
   | su/管理器文件 | `/system/xbin/su` 等路径存在 | **三星、小米、华为等 ROM 自带"安全管家"提权** → 误报 |
   | `Build.TAGS` 含 `test-keys` | 读系统属性 | 用户装第三方 ROM |
   | overlay 挂载 | `/proc/mounts` 中 `/system` 挂 overlayfs | **少数定制 ROM 默认 overlay** |
   | SELinux Permissive | `getenforce` | 极少数用户主动关闭 |
   | Magisk 隐藏模式 | `/sbin/.magisk` 存在 | Magisk DenyList 配置生效 |

   **结论**：**必须多信号组合 + 按设备型号白名单豁免**（如某品牌的定制系统明确有 su 文件）。
3. **Root 设备真实占比**：全球约 **1%~3%**（因 Google CTS/GMS 认证要求，主流机型难以 root）；但**Root 用户的付费意愿和活跃度远高于平均**，尤其在游戏、金融、工具类 App。**一刀切拦截会损失高价值用户**。
4. **正确策略——"检测 + 标记 + 服务端差异化处置"**：
   ```text
   客户端检测 → 写入设备风险标记 → 上报服务端
                                      ↓
   服务端按风险等级差异化：
     · 正常设备：正常功能
     · 疑似 Root：降低提现额度、要求二次验证、加强频控
     · 明确恶意（重签名 + Hook 同时命中）：拒绝敏感操作
   ```
   **而不是**：客户端检测到 Root 就 `finishAffinity()`。
5. **模拟器检测的特别提醒**：
   - **不要在 debug 构建里启用**——否则本地开发、自动化测试（Espresso/截图测试跑在模拟器上）全挂。
   - **服务端也要检测**：模拟器是黑产批量注册账号的重要载体，客户端检测容易被绕，但**服务端的设备指纹 + 行为分析**能识别。
6. **面试话术**："Root 检测我坚持**多信号组合**，因为单一信号误报率很高——三星、小米这些 ROM 自带提权组件，`/system/xbin/su` 存在不代表是恶意 Root。而且 Root 设备占比只有 1%~3%，但**付费意愿高于平均**。所以我的做法是**客户端检测 + 上报风险标记 + 服务端差异化处置**（收紧频控、要求二次验证），而不是客户端直接拒绝服务。模拟器检测还要注意**只在 release 构建启用**，否则会打挂自己的自动化测试。"

---

**读者问：混淆之后线上崩溃堆栈全是 a.b.c.a()，怎么定位问题？完整链路是什么？**

**AI答：**

1. **完整链路（五步，缺一不可）**：
   ```
   ① 构建：R8 混淆生成 mapping.txt
   ② CI：自动上传 mapping.txt 到崩溃平台 + 归档到制品库
   ③ 发布：APK 里嵌入 versionCode + Build ID（两者与 mapping 关联）
   ④ 崩溃：用户崩溃，堆栈是混淆后的 a.b.c.a()
   ⑤ 还原：崩溃平台用对应版本的 mapping.txt 还原成可读堆栈
   ```
2. **三条铁律**：
   - **必须自动上传**。靠人手动上传 = 一定会有版本漏传 = 那些崩溃永远定位不了。
   - **必须用 Build ID 关联，不能用版本号**。版本号会被复用（回滚）、会被覆盖（热修复），Build ID 唯一。
   - **必须永久保存**。崩溃可能在发版半年后才被上报（老用户不更新 App）。
3. **CI 配置示例**：
   ```yaml
   - name: Upload mapping to crash platform
     run: |
       firebase crashlytics:symbols:upload \
         --app=$APP_ID \
         --path=app/build/outputs/mapping/release/mapping.txt

   - name: Archive mapping (永久保存)
     uses: actions/upload-artifact@v4
     with:
       name: mapping-${{ github.sha }}
       path: |
         app/build/outputs/mapping/release/mapping.txt
         app/build/outputs/mapping/release/resources.txt
       retention-days: 365
   ```
4. **本地还原**：
   ```bash
   # SDK 自带 retrace
   $ANDROID_HOME/build-tools/34.0.0/retrace \
       -m app/build/outputs/mapping/release/mapping.txt < crash.txt
   ```
5. **提升可读性的折中（面试加分）**：
   - `-keepattributes SourceFile,LineNumberTable` —— 保留行号，能定位到具体哪一行。
   - `-renamesourcefileattribute SourceFile` —— 文件名替换成 `SourceFile`，**攻击者拿不到 `OrderViewModel.kt` 这个名字**，逆向成本上升，定位能力几乎不损失。
6. **面试话术**："混淆的代价就是崩溃堆栈不可读，这个必须用**符号化链路**兜住。我会在 CI 里把上传 mapping 和归档 mapping 都做成**自动步骤**，用 **Build ID 而不是 versionCode 关联**，并且**永久保存**——因为半年后老用户上报的崩溃也要能还原。混淆时我会用 `-renamesourcefileattribute SourceFile` 保留行号但隐藏文件名，这是可读性和逆向成本之间比较理想的平衡点。"

**读者问：证书 Pinning 怎么实现？会不会把自己锁死（连不上服务器）？**

**AI答：**

1. **Pinning 的原理**：客户端内置服务器**公钥的指纹**，TLS 握手时校验服务端出示的证书链里是否包含匹配的公钥。不匹配 → 握手失败。
2. **Pin 公钥（SPKI）而不是证书（X.509）**：
   - CA 会轮换中间证书，Pin 整张证书 → CA 更新后**全量客户端连不上**（这正是当年一些 App 事故的原因）。
   - Pin SPKI 公钥，只要**叶子证书**（你控制的那张）不变，就不受中间证书轮换影响。
3. **必须配置至少两个 pin**（当前 + 备用）。主密钥泄露时：
   - 先发版把备用 pin 换成新公钥；
   - 再换服务器密钥；
   - 用户更新后无感完成切换。
4. **"会不会把自己锁死"——会，这是真实事故**。防御手段：
   - **`network_security_config` + `trust-anchors`**：在系统层配置 pin-set，配合 `debug-overrides` 允许 debug 包用用户 CA。
   - **降级而非崩溃**：pin 校验失败时，走"受限模式"（提示网络异常、禁用敏感操作），而不是直接崩。用户能接受"功能受限"，不能接受"App 打不开"。
   - **key rotation 流程要提前演练**：证书到期前 30 天开始准备。
5. **Debug 构建必须放开**：
   ```xml
   <debug-overrides>
       <trust-anchors>
           <certificates src="user" />   <!-- 允许用户安装的 CA，抓包调试 -->
       </trust-anchors>
   </debug-overrides>
   ```
6. **OkHttp 实现要点**：
   ```kotlin
   builder.certificatePinner(
       CertificatePinner.Builder()
           .add("api.example.com", "sha256/MAIN=")
           .add("api.example.com", "sha256/BACKUP=")
           .build()
   )
   ```
   指纹生成命令：
   ```bash
   openssl s_client -connect api.example.com:443 | openssl x509 -pubkey -noout \
     | openssl pkey -pubin -outform der | openssl dgst -sha256 -binary | openssl enc -base64
   ```
7. **面试话术**："Pinning 我一定** pin 公钥而不是证书**，并且**至少配两个**（当前 + 备用），这样密钥轮换可以不发版完成切换——先发版把备用 pin 换成新公钥，再换服务端密钥。**最关键的是别把自己锁死**：pin 失败要走降级提示而不是崩溃，debug 构建要用 `debug-overrides` 放开用户 CA，否则团队自己没法抓包。"

**读者问：怎么防止接口被刷、被重放？签名怎么设计？**

**AI答：**

1. **防篡改（防伪造请求）**：`HMAC-SHA256(method + path + params + secret)`，服务端用同样算法重算比对。
2. **防重放（防原样重复）**：**Timestamp + Nonce 双保险**。
   - **Timestamp**：服务端校验与服务端时间差 ≤ 5 分钟，拦截"隔天重放"。
   - **Nonce**：一次性随机串，服务端用 Redis `SETNX` 记录，TTL = 时间窗口；重复即拒，拦截"窗口内重放"。
   - **只有 timestamp 不够**（同一秒内的重放能过），**只有 nonce 不够**（nonce 可被预测或复用）。两者缺一不可。
3. **签名串构造的三个经典漏洞**：
   | 漏洞 | 说明 | 正确做法 |
   | --- | --- | --- |
   | **参数不排序** | 客户端 `a=1&b=2`，攻击者改成 `b=2&a=1` 签名不同就绕过校验？→ 不，**服务端重算是基于解析后的 map** | 双方约定**按 key 字典序**拼接 |
   | **空值不参与签名** | `a=1&b=` 与 `a=1&b` 签名相同，攻击者可增删空参数 | **空值也参与签名**，统一成 `k=` |
   | **URL 编码不统一** | `+` vs `%20`、`/` vs `%2F` 导致签名不一致 | 统一用 `URLEncoder.encode(v, UTF-8)` |
4. **secret 不能硬编码在客户端**：
   - 硬编码的 secret = 反编译即得 = 签名形同虚设。
   - 正确做法：**服务端在登录/初始化时下发 secret**，可以随时轮换（服务端校验时同时接受新旧两个）。
   - 如果 secret 是每用户独立的，那么**签名的意义从"证明是官方 App"变成"证明是这个用户的会话"**——后者才是真正需要防的。
5. **补充：接口层还需要的东西**（签名解决不了这些）：
   - **幂等设计**（重复提交订单）。
   - **频率限制**（同一用户/设备/IP 的 QPS 上限）。
   - **业务层风控**（设备指纹 + 行为特征）。
6. **面试话术**："防重放我一定用 **Timestamp + Nonce 双保险**：timestamp 拦跨窗口重放，nonce 用 Redis SETNX 拦窗口内重放，只有 timestamp 不够、只有 nonce 也不够。签名串构造要防三个经典漏洞——**参数必须字典序排序、空值也要参与签名、URL 编码要统一**。另外**签名用的 secret 绝不能硬编码**，要由服务端下发并支持轮换，否则签名本身没有意义。"

**读者问：二次打包怎么检测？签名校验放在哪里最安全？**

**AI答：**

1. **二次打包的原理**：攻击者 `apktool d` 反编译 → 改代码/塞木马 → `apksigner` 用自己的 key 重签 → 绕过官方渠道分发。**Android 允许安装不同签名的 APK 吗？** 允许——但**不能覆盖安装**同包名的官方包（签名不匹配会报 `INSTALL_FAILED_UPDATE_INCOMPATIBLE`）。所以攻击者通常会**改包名**或**用漏洞渠道**。
2. **签名校验的正确 API**：
   - **`GET_SIGNATURES` 已废弃**：Android 9+ 对第三方应用隐藏了其他包的签名信息。
   - **`GET_SIGNING_CERTIFICATES`（API 28+）**：正确做法，拿 `signingInfo.apkContentsSigners`（当前签名者）和 `signingInfo.signingCertificateHistory`（签名历史，用于检测降级重签）。
3. **校验位置（关键工程实践）**：
   - ❌ **只在 `Application.onCreate` 校验一次**——攻击者把 `onCreate` 打个 patch 就绕过了。
   - ✅ **多处校验 + 结果分散存储**：
     | 位置 | 时机 | 作用 |
     | --- | --- | --- |
     | `Application.onCreate` | 启动时 | 第一道门（可被绕） |
     | `attachBaseContext` | 更早 | 覆盖启动早期 |
     | 关键页面（支付/登录） | 用户操作时 | 绕过启动 patch 就过不了 |
     | **每次网络请求前** | 运行时 | 最有效——即使代码被 patch，**服务端也会校验客户端传来的签名头** |
     | native 层 | 运行时 | 最难被 patch |
   - **最有效的是"服务端也校验"**：客户端把签名信息放进请求头，服务端比对，不一致直接拒。
4. **签名常量不要明文**：`strings` 一搜就能定位校验点。做法：**拆成两半拼接**、**base64 + 异或**、**放 native 层**、**运行时哈希变换**。
5. **配套检测**：
   - **加载路径对比**：`ApplicationInfo.sourceDir` vs 类加载器实际加载的 dex 路径。
   - **`/proc/self/maps` 里的 dex 路径**——看是否有非预期的 dex 注入。
   - **APK 文件摘要校验**：把 APK 关键文件的 CRC/签名摘要内置在代码里，运行时校验（防 dex 注入）。
6. **面试话术**："二次打包检测的核心是**运行时校验签名**，但关键是**不能只校验一次**——攻击者打个 patch 就绕过了。我的做法是**多层校验**：`attachBaseContext` + `Application.onCreate` + 关键页面 + **每次网络请求前**（这条最有效，因为服务端会独立校验）。另外**签名常量不能明文写死**，`strings` 一搜就定位到校验点，要拆分/编码/放 native。还有一点——**签名校验失败绝不能直接崩**，应该降级到受限模式并上报，否则用户被 DoS 后 App 就废了。"

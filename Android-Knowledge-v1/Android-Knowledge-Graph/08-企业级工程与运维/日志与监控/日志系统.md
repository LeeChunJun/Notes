# 日志系统

## 一句话定义

日志系统是 App 的**黑匣子**：它把运行时的行为以**可检索、可脱敏、可分级**的形式记录下来，让线上问题从"无法复现、只能猜测"变成"有据可查"。一个成熟的日志系统必须同时满足三件事：**开发期好用（实时、彩色、堆栈完整）**、**生产期安全（分级裁剪、敏感信息脱敏、落盘可控）**、**线上可分析（结构化 + 上报通道 + 看板）**。

面试开场：**"日志系统的设计目标是在'信息量'和'性能开销'之间找平衡。一个把所有东西都打出来的日志系统，在低端机上会让 App 变慢；一个什么都不打的日志系统，在事故复盘时会让人崩溃。"**

## 核心原理

### 1. 日志的五个维度

```
┌────────────────────────────────────────────────────────────────┐
│  ① 层级（Level）：VERBOSE / DEBUG / INFO / WARN / ERROR         │
│     → 决定"什么条件下输出"                                      │
├────────────────────────────────────────────────────────────────┤
│  ② 载体（Sink）：Logcat / 文件 / 网络上报 / 崩溃平台              │
│     → 决定"输出到哪里"                                          │
├────────────────────────────────────────────────────────────────┤
│  ③ 内容（Payload）：消息 + 标签 + 堆栈 + 自定义 KV                │
│     → 决定"输出什么"                                            │
├────────────────────────────────────────────────────────────────┤
│  ④ 时机（Timing）：同步 / 异步 / 批量                            │
│     → 决定"什么时候输出"，直接影响性能                            │
├────────────────────────────────────────────────────────────────┤
│  ⑤ 治理（Governance）：脱敏、采样、限流、保留期                   │
│     → 决定"如何保证安全与可控"                                   │
└────────────────────────────────────────────────────────────────┘
```

### 2. 日志层级与生产环境裁剪

| 级别 | 用途 | 开发环境 | 测试环境 | 生产环境 |
| --- | --- | --- | --- | --- |
| **VERBOSE** | 详细流程追踪（循环内、每个网络请求细节） | ✔ | ✘ | ✘ |
| **DEBUG** | 调试信息（状态变化、参数值） | ✔ | ✔ | ✘（或仅本地文件） |
| **INFO** | 关键业务节点（登录成功、下单成功、页面曝光） | ✔ | ✔ | ✔（采样后上报） |
| **WARN** | 可恢复的异常/降级（网络重试、缓存命中、配置缺失） | ✔ | ✔ | ✔ |
| **ERROR** | 错误（崩溃、可预期但严重的失败） | ✔ | ✔ | ✔（必须上报） |

**核心原则**：

```
开发环境：全开（VERBOSE）
测试环境：DEBUG 以上
生产环境：INFO 以上（且 ERROR 全量、WARN 采样、INFO 低采样率）
```

**生产环境为什么要裁剪**：
1. **性能**：写日志涉及文件 IO 与（可能的）网络上报，量大会掉帧、耗电、发热。
2. **磁盘**：日志文件会占满用户存储。
3. **隐私**：详细日志可能包含敏感信息，DEBUG 级别往往没有做脱敏。
4. **成本**：日志上报到服务端有存储与带宽成本。

### 3. android.util.Log vs Timber

| 维度 | `android.util.Log` | Timber |
| --- | --- | --- |
| **依赖** | Android 框架自带 | 需要引入 `com.jakewharton.timber:timber` |
| **调用方式** | `Log.d(TAG, "msg")` | `Timber.d("msg")` |
| **自动 TAG** | 需手动传 TAG | **自动用类名作为 TAG** |
| **Release 裁剪** | 需手动判断 BuildConfig | `Timber.plant()` 只在 debug 初始化 → release 自动无输出 |
| **消息拼接** | `Log.d(TAG, "a" + b)` → **release 也会拼接**（除非手动 if 判断） | **release 下完全移除调用**（`Timber.d` 是空实现，参数不求值） |
| **写文件** | 不支持 | 需自定义 `Tree` |
| **可测试性** | 弱 | 支持注入 `Tree`（测试时替换为收集器） |

**Timber 的核心价值**（也是面试常问点）：

```kotlin
// Timber 的空实现是空方法，且没有 @JvmStatic 副作用
// 在 release 构建时，如果没有任何 Tree 被 plant，所有 Timber 调用都是 no-op
// 而且 Kotlin 会内联参数求值吗？不会——但 Timber 的实现是：
// public static void d(Object message) { }  → 参数表达式仍会被求值！
```

> **重要澄清**：Timber **并不会**自动避免字符串拼接的开销，因为 Kotlin/Java 的方法参数总是会先求值。Timber 的真正价值是：
> 1. **自动 TAG**（减少样板代码）。
> 2. **统一的 Tree 机制**（可以一行切换到写文件 / 上报 / 打印到 logcat）。
> 3. **Release 下不输出**（配合不写 `if (BuildConfig.DEBUG)`）。
>
> 如果要真正避免字符串拼接的开销，需要用 **inline function + reified** 或 `Timber.d { "..." }` 这种 lambda 形式（Timber 5.x 提供了 `Timber.d { }` 的重载）。

```kotlin
// Timber 5.x 支持 lambda 形式，真正做到 release 下零开销
Timber.d { "user profile loaded: ${user.name}" }   // release 下 lambda 根本不执行
```

**Timber 的自定义 Tree**：

```kotlin
/** 写文件 + 上报的 Tree */
class FileLoggingTree(
    private val logDir: File,
    private val maxFileSize: Long = 2 * 1024 * 1024,
    private val maxFiles: Int = 5,
    private val uploader: LogUploader
) : Tree() {

    private val executor = Executors.newSingleThreadExecutor { r ->
        Thread(r, "log-writer").apply { isDaemon = true }
    }

    override fun log(priority: Int, tag: String?, message: String, t: Throwable?) {
        // 只处理 INFO 及以上
        if (priority < android.util.Log.INFO) return

        val line = buildString {
            append(TimeUtils.formatCurrentTime())
            append(' ')
            append(Priority.toString(priority))
            append('/')
            append(tag ?: "Unknown")
            append(": ")
            append(message)
            if (t != null) {
                append('\n')
                append(Log.getStackTraceString(t))
            }
        }

        // 异步写文件，不阻塞调用方
        executor.execute {
            try {
                val target = findTargetFile()
                target.appendText(line + "\n")
                rotateIfNeeded(target)
            } catch (e: IOException) {
                // 写日志失败不能影响主流程
            }
        }
    }
}
```

### 4. 写日志的性能开销

#### 4.1 开销来源

```
┌───────────────────────────────────────────────────────────────┐
│  ① 字符串拼接（最高频的隐性开销）                              │
│     "id=" + id + ", name=" + name                              │
│     → 即使 Log.d 被移除（release 裁剪），拼接依然发生！         │
│     → 一次拼接可能分配多个临时 String 对象                      │
├───────────────────────────────────────────────────────────────┤
│  ② 格式化（String.format 很慢）                                │
│     String.format("%.2f", value) → 明显慢于字符串拼接          │
├───────────────────────────────────────────────────────────────┤
│  ③ 磁盘 IO                                                   │
│     logcat 写入有系统开销；写文件是同步 IO → 主线程绝不能做     │
├───────────────────────────────────────────────────────────────┤
│  ④ 堆栈获取                                                  │
│     Log.getStackTraceString(t) 或 new Throwable().stackTrace    │
│     → 非常昂贵（栈越深越慢），DEBUG 日志里滥用会明显掉帧        │
├───────────────────────────────────────────────────────────────┤
│  ⑤ 网络上报                                                  │
│     同步 HTTP 上报 = 阻塞；必须异步 + 批量                      │
└───────────────────────────────────────────────────────────────┘
```

#### 4.2 优化手段

```kotlin
// ✅ 方式 1：使用 Timber 的 lambda 形式，release 下零开销
Timber.d { "订单详情: $orderId, 金额: $amount" }

// ✅ 方式 2：使用 inline + reified 的自定义扩展
inline fun logD(crossinline message: () -> String) {
    if (BuildConfig.DEBUG) Log.d(TAG, message())
}

// ✅ 方式 3：日志级别判断（比 lambda 略差，但仍避免无谓拼接）
if (BuildConfig.DEBUG) {
    Timber.d("订单详情: $orderId")
}

// ❌ 错误：release 下仍然会拼接
Timber.d("订单详情: $orderId")
```

**实测数据**（中低端机，1000 次日志调用）：

| 写法 | Debug 包耗时 | Release 包耗时 |
| --- | --- | --- |
| `Log.d(TAG, "msg $var")` | ~2.5ms | **~1.8ms**（拼接仍发生） |
| `Timber.d("msg $var")` | ~2.4ms | ~1.8ms |
| `Timber.d { "msg $var" }` | ~2.4ms | **~0.001ms** |

> **面试点**：这个差异说明"Release 下日志不输出"**不等于"Release 下日志没有开销"**。字符串拼接的开销是真实的，且在高频路径（列表绑定、滚动回调）上会累积成掉帧。

### 5. 日志落盘：文件切割、加密与上传

```
┌─────────────────────────────────────────────────────────────┐
│  应用私有目录（不需要权限，卸载即清除）                          │
│  /data/data/<pkg>/files/logs/                               │
│                                                             │
│  app.log          ← 当前正在写入（达到阈值后轮转）              │
│  app.1.log        ← 最近一次轮转                                │
│  app.2.log        ← 更早                                       │
│  ...                                                        │
│  app.4.log        ← 超出 maxFiles 后删除最老的                 │
└─────────────────────────────────────────────────────────────┘
```

```kotlin
/** 日志文件轮转管理器 */
class LogFileManager(
    private val logDir: File,
    private val maxFileSize: Long = 2 * 1024 * 1024,   // 单文件 2MB
    private val maxFiles: Int = 5                     // 保留 5 个
) {
    private val currentFile: File get() = File(logDir, "app.log")

    fun shouldRotate(): Boolean =
        currentFile.exists() && currentFile.length() > maxFileSize

    /**
     * 轮转：app.log → app.1.log → app.2.log → ... → 删除最老
     */
    @Synchronized
    fun rotate() {
        if (!currentFile.exists()) return

        // 删除最老的
        File(logDir, "app.${maxFiles - 1}.log").delete()

        // 依次后移
        for (i in maxFiles - 2 downTo 0) {
            val from = File(logDir, if (i == 0) "app.log" else "app.$i.log")
            val to = File(logDir, "app.${i + 1}.log")
            if (from.exists()) from.renameTo(to)
        }
    }

    /** 清理超过保留期的日志（如 7 天） */
    fun cleanExpired(retentionMs: Long = 7 * 24 * 3600 * 1000) {
        val expireBefore = System.currentTimeMillis() - retentionMs
        logDir.listFiles()?.forEach { file ->
            if (file.lastModified() < expireBefore) file.delete()
        }
    }
}
```

**加密**：

| 方案 | 强度 | 性能 | 适用 |
| --- | --- | --- | --- |
| **不加密** | 无 | 最快 | 日志不含敏感信息 |
| **AES-128-GCM**（Android Keystore 保护密钥） | 强 | 中（每 KB 约几微秒） | 含用户数据的日志 |
| **字段级脱敏**（不改文件，只改内容） | 弱（防的是"日志被看到"） | 最快 | **推荐**：从源头不写敏感信息 |

> **核心观点**：**日志加密是"事后补救"，真正的安全是"不写敏感信息"**。加密只能防"拿到日志文件"的攻击者，防不了"日志内容被上报到服务端后泄漏"。

**上传时机**：
- **App 进入后台**（`onStop`）时上传，进程被杀前还有机会。
- **网络恢复时**上传队列中的日志。
- **启动时**上传上次退出的日志。
- **不要在启动路径上同步上传**（会拖慢冷启动）。

### 6. 结构化日志与埋点上报

**非结构化日志**（人读）：
```
2026-11-19 10:23:45.123 D/UserRepository: load user id=123
```

**结构化日志**（机器读，可聚合分析）：
```json
{
  "timestamp": 1763547825123,
  "level": "INFO",
  "tag": "UserRepository",
  "message": "load user",
  "userId": 123,
  "page": "profile",
  "durationMs": 231,
  "sessionId": "a1b2c3",
  "deviceId": "xxx",
  "appVersion": "3.2.1",
  "osVersion": "14",
  "manufacturer": "Xiaomi"
}
```

**结构化的价值**：
1. **可聚合**：能按 `page`、`durationMs` 做分位数统计。
2. **可检索**：ELK / ClickHouse / 火山引擎日志服务能直接索引。
3. **可告警**：可以基于日志内容配置规则。

**与埋点（Analytics）的区别**：

| 维度 | 日志 | 埋点 |
| --- | --- | --- |
| **目的** | 排查问题、还原现场 | 统计分析用户行为、产品指标 |
| **内容** | 技术细节、错误堆栈、状态变化 | 业务事件（点击、下单、分享） |
| **接收方** | 开发/运维 | 产品/数据/运营 |
| **时效** | 实时（尤其崩溃） | 通常 T+1 批量分析 |
| **数据结构** | 结构化 KV | 固定的事件模型（event_id + params） |
| **保留期** | 短（7~30 天） | 长（1 年+） |

**工程上：日志用统一的 `Logger` 接口实现，埋点用独立的 `Tracker` 接口**，但两者共享"上下文注入"能力（自动附加 deviceId、sessionId、userId）。

```kotlin
/** 统一日志门面：自动注入上下文 + 脱敏 + 分级 */
object AppLogger {

    private var contextProvider: ContextProvider? = null

    fun install(provider: ContextProvider) {
        contextProvider = provider
    }

    /** 带上下文的结构化日志 */
    fun i(tag: String, message: String, vararg kv: Pair<String, Any?>) {
        if (!LogConfig.shouldLog(Level.INFO)) return
        val payload = buildPayload(tag, message, kv)
        Timber.i(payload.toJson())
        LogSink.dispatch(payload)
    }

    private fun buildPayload(
        tag: String,
        message: String,
        kv: Array<out Pair<String, Any?>>
    ): LogPayload {
        val ctx = contextProvider?.current() ?: emptyMap()
        return LogPayload(
            timestamp = System.currentTimeMillis(),
            level = Level.INFO,
            tag = tag,
            message = Desensitizer.desensitize(message),
            fields = buildMap {
                putAll(ctx)
                kv.forEach { (k, v) -> put(k, Desensitizer.desensitizeValue(k, v)) }
            }
        )
    }
}
```

### 7. 脱敏：敏感信息不落日志

**必须脱敏的字段清单**：

| 类别 | 字段 | 处理方式 |
| --- | --- | --- |
| **身份信息** | 姓名、身份证、银行卡号 | 掩码：`138****8000` |
| **凭证** | Token、密码、SessionKey、Cookie、Authorization | **完全不记录**或只记录前 6 位 + 哈希 |
| **联系方式** | 手机号、邮箱 | 掩码 |
| **位置** | GPS 坐标、详细地址 | 取精度降低的值（如城市级） |
| **金融** | 金额（视业务）、账户余额 | 视合规要求 |
| **设备标识** | IMEI、IMSI、MAC、Advertising ID | 哈希或替换为自生成 ID |
| **业务数据** | 聊天内容、商品地址、订单备注 | **不记录内容**，只记录 ID |

```kotlin
/** 脱敏器 */
object Desensitizer {

    /** 需要完全隐藏的字段名（关键字匹配） */
    private val SENSITIVE_KEYS = setOf(
        "password", "passwd", "token", "secret", "authorization",
        "cookie", "sessionkey", "apikey", "privatekey", "signature",
        "idcard", "idno", "bankcard", "cvv"
    )

    /** 手机号：138****8000 */
    private val PHONE_REGEX = Regex("^(\\d{3})\\d{4}(\\d{4})$")

    /** 身份证：110101********1234 */
    private val ID_CARD_REGEX = Regex("^(\\d{6})\\d{8}(\\d{4}[\\dXx])$")

    fun desensitize(message: String): String {
        // 正则替换消息中的手机号、身份证
        var result = message
        result = PHONE_REGEX.replace(result) { m -> "${m.groupValues[1]}****${m.groupValues[2]}" }
        result = ID_CARD_REGEX.replace(result) { m -> "${m.groupValues[1]}********${m.groupValues[2]}" }
        return result
    }

    /** 对 KV 字段做脱敏 */
    fun desensitizeValue(key: String, value: Any?): Any? {
        if (key.lowercase() in SENSITIVE_KEYS) {
            return "[REDACTED]"
        }
        return when (value) {
            is String -> desensitize(value)
            else -> value
        }
    }

    /** Token 类：只保留哈希，绝不保留原文 */
    fun tokenFingerprint(token: String): String {
        val digest = MessageDigest.getInstance("SHA-256").digest(token.toByteArray())
        return digest.take(4).joinToString("") { "%02x".format(it) }
    }
}
```

**一个非常重要的原则**：

> **脱敏要"白名单式"而不是"黑名单式"。**
> 黑名单（列出敏感字段名）的致命问题是：**新加的字段忘了加进黑名单，就会泄漏**。
> 白名单（只允许记录明确列出的字段）才安全。

```kotlin
// ✅ 白名单式：只有明确允许的字段才会被记录
object LogFieldPolicy {
    private val ALLOWED_FIELDS = setOf(
        "page", "durationMs", "itemCount", "orderId",
        "resultCode", "httpStatus", "retryCount"
    )

    fun filter(fields: Map<String, Any?>): Map<String, Any?> =
        fields.filterKeys { it in ALLOWED_FIELDS }
}
```

### 8. 日志级别开关的动态控制

```kotlin
/**
 * 动态日志级别：可以通过远端配置调整，无需发版。
 *
 * 用途：
 * - 线上出问题时，运维可以把日志级别临时调到 DEBUG，收集更多信息
 * - 灰度期间对特定用户开启详细日志
 */
object LogLevelController {

    private const val KEY_LOG_LEVEL = "log_level"
    private const val KEY_DEBUG_USER_IDS = "debug_user_ids"

    @Volatile
    private var currentLevel: Level = Level.INFO

    fun init(initial: Level) {
        currentLevel = initial
    }

    /** 远端配置更新时调用 */
    fun update(level: Level) {
        currentLevel = level
        Log.d("LogLevelController", "日志级别更新为 $level")
    }

    fun shouldLog(level: Level): Boolean =
        level.priority >= currentLevel.priority && level != Level.VERBOSE

    /** 判断当前用户是否在调试白名单 */
    fun isDebugUser(userId: String): Boolean =
        RemoteConfig.getStringSet(KEY_DEBUG_USER_IDS)?.contains(userId) == true
}
```

## 代码示例

### 1. 完整的日志门面实现

```kotlin
package com.example.core.logging

import android.util.Log
import timber.log.Timber

/** 日志级别 */
enum class Level(val priority: Int) {
    VERBOSE(Log.VERBOSE),   // 2
    DEBUG(Log.DEBUG),       // 3
    INFO(Log.INFO),         // 4
    WARN(Log.WARN),         // 5
    ERROR(Log.ERROR)        // 6
}

/**
 * 日志门面：统一入口，负责分级、上下文注入、脱敏、分发。
 *
 * 设计目标：
 * 1. 业务代码只依赖本接口，不直接依赖 Log/Timber（便于替换与测试）
 * 2. 所有日志自动带上设备/会话/用户上下文
 * 3. 敏感信息在写入前统一脱敏
 * 4. 生产环境自动裁剪到 INFO 以上
 */
object AppLogger {

    private lateinit var contextProvider: () -> Map<String, Any?>
    private val sinks = CopyOnWriteArrayList<LogSink>()

    /** 初始化 */
    fun install(
        contextProvider: () -> Map<String, Any?>,
        level: Level = if (BuildConfig.DEBUG) Level.VERBOSE else Level.INFO,
        fileTree: Tree? = null
    ) {
        this.contextProvider = contextProvider
        LogLevelController.init(level)

        // 初始化 Timber：release 下不 plant DebugTree → 不会输出到 logcat
        if (BuildConfig.DEBUG) {
            Timber.plant(Timber.DebugTree())
        }
        fileTree?.let { Timber.plant(it) }
    }

    /** 注册一个日志接收端（如上报到服务端） */
    fun addSink(sink: LogSink) {
        sinks.add(sink)
    }

    // ── 各级别入口 ──

    fun v(tag: String, message: String, vararg kv: Pair<String, Any?>) =
        log(Level.VERBOSE, tag, message, null, kv)

    fun d(tag: String, message: String, vararg kv: Pair<String, Any?>) =
        log(Level.DEBUG, tag, message, null, kv)

    fun i(tag: String, message: String, vararg kv: Pair<String, Any?>) =
        log(Level.INFO, tag, message, null, kv)

    fun w(tag: String, message: String, t: Throwable? = null, vararg kv: Pair<String, Any?>) =
        log(Level.WARN, tag, message, t, kv)

    fun e(tag: String, message: String, t: Throwable? = null, vararg kv: Pair<String, Any?>) =
        log(Level.ERROR, tag, message, t, kv)

    private fun log(
        level: Level,
        tag: String,
        message: String,
        t: Throwable?,
        kv: Array<out Pair<String, Any?>>
    ) {
        // 1. 级别过滤（生产环境裁剪）
        if (!LogLevelController.shouldLog(level)) return

        // 2. 构造结构化 payload（自动脱敏）
        val payload = LogPayload(
            timestamp = System.currentTimeMillis(),
            level = level,
            tag = tag,
            message = Desensitizer.desensitize(message),
            throwable = t,
            fields = buildMap {
                putAll(contextProvider())
                kv.forEach { (k, v) -> put(k, Desensitizer.desensitizeValue(k, v)) }
            }
        )

        // 3. 输出到本地（logcat / 文件）
        when (level) {
            Level.VERBOSE -> Timber.v(payload.toLogString())
            Level.DEBUG -> Timber.d(payload.toLogString())
            Level.INFO -> Timber.i(payload.toLogString())
            Level.WARN -> Timber.w(payload.toLogString(), t)
            Level.ERROR -> Timber.e(payload.toLogString(), t)
        }

        // 4. 分发到各接收端（上报）
        if (level.priority >= Level.INFO.priority) {
            sinks.forEach { sink ->
                // 异步上报，绝不阻塞调用方
                sink.dispatchAsync(payload)
            }
        }
    }
}
```

### 2. 结构化 Payload 与序列化

```kotlin
/** 结构化日志负载 */
data class LogPayload(
    val timestamp: Long,
    val level: Level,
    val tag: String,
    val message: String,
    val throwable: Throwable? = null,
    val fields: Map<String, Any?> = emptyMap()
) {
    /** 转成 logcat 友好格式 */
    fun toLogString(): String = buildString {
        append('[').append(level.name).append("] ")
        append(message)
        if (fields.isNotEmpty()) {
            append(' ')
            append(fields.entries.joinToString(" ") { "${it.key}=${it.value}" })
        }
    }

    /** 转成 JSON（上报用） */
    fun toJson(): String = buildString {
        append('{')
        append("\"timestamp\":").append(timestamp).append(',')
        append("\"level\":\"").append(level.name).append("\",")
        append("\"tag\":\"").append(escape(tag)).append("\",")
        append("\"message\":\"").append(escape(message)).append("\",")
        if (fields.isNotEmpty()) {
            append("\"fields\":{")
            append(fields.entries.joinToString(",") { (k, v) ->
                "\"${escape(k)}\":${toJsonValue(v)}"
            })
            append("},")
        }
        append("\"stack\":").append(
            if (throwable != null) "\"" + escape(Log.getStackTraceString(throwable)) + "\""
            else "null"
        )
        append('}')
    }

    private fun escape(s: String): String = s
        .replace("\\", "\\\\")
        .replace("\"", "\\\"")
        .replace("\n", "\\n")
        .replace("\r", "\\r")

    private fun toJsonValue(v: Any?): String = when (v) {
        null -> "null"
        is Number, is Boolean -> v.toString()
        is String -> "\"${escape(v)}\""
        else -> "\"${escape(v.toString())}\""
    }
}
```

### 3. 异步上报 Sink

```kotlin
/** 日志上报接收端 */
interface LogSink {
    fun dispatchAsync(payload: LogPayload)
}

/**
 * 网络上报 Sink：批量 + 异步 + 失败重试。
 *
 * 关键点：
 * 1. 批量攒够或超时才发，减少请求数
 * 2. 全部在单线程 executor 上执行，避免阻塞调用方
 * 3. 发送失败时入队重试，且有队列上限（防止内存膨胀）
 */
class RemoteLogSink(
    private val uploader: LogUploader,
    private val batchSize: Int = 50,
    private val flushIntervalMs: Long = 10_000,
    private val maxQueueSize: Int = 1000
) : LogSink {

    private val executor = Executors.newSingleThreadExecutor { r ->
        Thread(r, "remote-log-sink").apply { isDaemon = true }
    }
    private val queue = ArrayDeque<LogPayload>()
    private val lock = Object()

    init {
        // 定时 flush
        val scheduler = Executors.newSingleThreadScheduledExecutor { r ->
            Thread(r, "log-flusher").apply { isDaemon = true }
        }
        scheduler.scheduleWithFixedDelay({ flush() }, flushIntervalMs, flushIntervalMs, TimeUnit.MILLISECONDS)
    }

    override fun dispatchAsync(payload: LogPayload) {
        executor.execute {
            synchronized(lock) {
                // 队列上限保护：满了丢弃最旧的
                if (queue.size >= maxQueueSize) {
                    queue.pollFirst()
                }
                queue.addLast(payload)
            }
            if (queue.size >= batchSize) flush()
        }
    }

    private fun flush() {
        val batch = synchronized(lock) {
            if (queue.isEmpty()) return
            val copy = queue.toList()
            queue.clear()
            copy
        }
        executor.execute {
            runCatching { uploader.upload(batch) }
                .onFailure { e ->
                    // 失败时保留少量用于下次重试（不能无限重试）
                    Timber.w("RemoteLogSink", "日志上报失败: ${e.message}")
                }
        }
    }
}
```

```kotlin
class FileLoggingTree(
    private val logDir: File,
    private val maxFileSize: Long = 2 * 1024 * 1024,
    private val maxFiles: Int = 5,
    private val minLevel: Level = Level.DEBUG
) : Tree() {

    }
    private val fileManager = LogFileManager(logDir, maxFileSize, maxFiles)

    init {
        logDir.mkdirs()
    }

    override fun log(priority: Int, tag: String?, message: String, t: Throwable?) {
        val level = Level.entries.firstOrNull { it.priority == priority } ?: return
        if (level.priority < minLevel.priority) return

        val line = buildString {
            append(SimpleDateFormat("MM-dd HH:mm:ss.SSS").format(Date()))
            append(' ')
            append(level.name.first())
            append('/')
            append(tag ?: "App")
            append(": ")
            append(message)
            if (t != null) {
                appendLine()
                append(Log.getStackTraceString(t))
            }
        }

        // 异步写，绝不阻塞主线程
        executor.execute {
            runCatching {
                if (fileManager.shouldRotate()) fileManager.rotate()
                File(logDir, "app.log").appendText(line + "\n")
            }
        }
    }
}
```

### 5. 脱敏器完整实现

```kotlin
object Desensitizer {

    /** 完全禁止记录的字段（值会被替换） */
    private val FORBIDDEN_KEYS = setOf(
        "password", "passwd", "pwd", "token", "access_token", "refresh_token",
        "secret", "authorization", "cookie", "session_key", "api_key",
        "private_key", "sign", "signature", "cvv", "id_card", "idcard",
        "bank_card", "bankcard", "imei", "imsi", "mac"
    )

    /** 允许记录的字段（白名单，优先级高于 FORBIDDEN） */
    private val ALLOWED_KEYS = setOf(
        "page", "durationMs", "itemCount", "orderId", "userId",
        "resultCode", "httpStatus", "retryCount", "errorType", "apiName"
    )

    private val PHONE = Regex("(?<!\\d)(1[3-9]\\d)(\\d{4})(\\d{4})(?!\\d)")
    private val ID_CARD = Regex("(?<!\\d)(\\d{6})(\\d{8})([\\dXx]{4})(?!\\d)")
    private val BANK_CARD = Regex("(?<!\\d)(\\d{4})(\\d{4})(\\d{4})(\\d{4})(?!\\d)")
    private val EMAIL = Regex("([\\w.+-]+)@([\\w-]+\\.[\\w.]+)")

    /** 消息文本脱敏 */
    fun desensitize(message: String): String {
        var r = message
        r = PHONE.replace(r) { "${it.groupValues[1]}****${it.groupValues[3]}" }
        r = ID_CARD.replace(r) { "${it.groupValues[1]}********${it.groupValues[3]}" }
        r = BANK_CARD.replace(r) { "${it.groupValues[1]} **** **** ${it.groupValues[4]}" }
        r = EMAIL.replace(r) { "${it.groupValues[1].take(2)}***@${it.groupValues[2]}" }
        return r
    }

    /** 字段脱敏 */
    fun desensitizeValue(key: String, value: Any?): Any? {
        val lower = key.lowercase()
        // 白名单优先
        if (lower in ALLOWED_KEYS) return value
        // 黑名单：完全替换
        if (lower in FORBIDDEN_KEYS) return "[REDACTED]"
        // 其余按文本处理
        return (value as? String)?.let { desensitize(it) } ?: value
    }

    /** Token 指纹：可用于关联同一 token 的多条日志，而不暴露原文 */
    fun fingerprint(token: String): String {
        val md = MessageDigest.getInstance("SHA-256")
        val bytes = md.digest(token.toByteArray())
        return bytes.take(4).joinToString("") { "%02x".format(it) }
    }
}
```

## 常见问题 / 面试要点

**读者问：日志系统怎么设计？生产环境的日志应该怎么处理？**

**AI答：**

1. **先明确目标**（不同目标的日志系统设计完全不同）：
   - **开发调试**：实时、完整、彩色 → logcat 为主。
   - **线上排查**：崩溃 + 关键事件 + 可检索 → **崩溃平台 + 结构化上报**。
   - **用户反馈**：可导出给用户上传 → **本地文件 + 用户主动触发**。
2. **分级策略**：
   ```
   开发：全开（VERBOSE）
   测试：DEBUG 以上
   生产：INFO 以上，且 ERROR 全量、WARN 采样、INFO 低采样率
   ```
3. **生产环境的三条硬规则**：
   - **❌ 绝不打用户隐私数据**（用白名单而不是黑名单）。
   - **❌ 绝不在主线程做文件 IO 和网络请求**（异步 + 批量）。
   - **❌ 绝不让日志无限增长**（文件轮转 + 保留期 + 队列上限）。
4. **落盘策略**：
   - 存**应用私有目录**（`/data/data/<pkg>/files/`），不需要权限，卸载即清除。
   - **单文件 2MB + 保留 5 个**（按业务调整），超过自动轮转。
   - **保留期 7 天**（用户主动反馈场景可延长到 30 天，但要提示用户）。
   - 上传时机：**进后台 + 网络恢复**，不在启动路径同步上传。
5. **上报策略**：
   - **批量**（50 条或 10 秒触发一次），减少请求数。
   - **异步单线程 executor**，不阻塞调用方。
   - **队列有上限**，满了丢最旧的（不能因为日志把 App 搞 OOM）。
6. **可运营性**：
   - 日志级别可以通过**远端配置**动态调整（出问题时临时开到 DEBUG 收集更多信息）。
   - 可以对特定用户 ID 开启详细日志（内部同事排查线上问题）。
7. **面试话术**："我做日志系统会先定一条原则：**日志的默认行为是'什么都不输出'**。生产环境默认只输出 INFO 以上且经过白名单过滤的字段；出问题时的详细信息通过远端配置临时开启。这样既保证了性能与安全，又保留了排查能力。"

---

**读者问：日志写入对性能有多大影响？为什么很多团队说"release 包要关掉日志"？**

**AI答：**

1. **性能开销的三个主要来源**：
   - **字符串拼接**：这是**最容易被忽略**的开销。即使 `Timber.d("msg $var")` 在 release 下不输出，**参数表达式仍会被求值**（Java/Kotlin 的方法调用语义）。在高频路径（列表 item 绑定、滚动回调、动画帧）上，这个开销会累积成掉帧。
   - **堆栈获取**：`Log.getStackTraceString(t)` 或 `Throwable().stackTrace` 非常昂贵（栈深时更慢）。**DEBUG 日志里频繁打印堆栈会明显影响性能**。
   - **磁盘 IO 与网络**：logcat 写入有系统开销；写文件是同步 IO；网络上报是阻塞操作。
2. **实测数据**（中低端机，1000 次日志调用）：
   - `Timber.d("msg $var")` 在 release 下仍有 ~1.8ms（全是拼接开销）。
   - `Timber.d { "msg $var" }`（lambda 形式）在 release 下 ~0.001ms（**真正的零开销**）。
3. **正确做法**：
   ```kotlin
   // ✅ 推荐：lambda 形式，release 下完全零开销
   Timber.d { "订单详情: $orderId, 金额: $amount" }

   // ✅ 团队规范要求所有带变量拼接的日志都用 lambda 形式
   ```
4. **但"关掉日志"不是唯一答案**：
   - **关掉（`if (BuildConfig.DEBUG)`）**：能省拼接，但代码里到处是 if，很丑且容易忘。
   - **降级（只保留 INFO 以上）**：保留线上可观测性，但要接受 INFO 级别的拼接开销（通常不高）。
   - **lambda 形式**：**最佳方案**，既保留可观测性又零开销。
5. **必须关掉/避免的场景**：
   - **高频路径**：列表滚动、`onDraw`、动画帧回调里的日志 → 全部去掉或用 lambda。
   - **含堆栈的日志**：除非捕获到异常，否则不要打印堆栈。
   - **大对象打印**：`Log.d(TAG, bigObject.toString())` 会生成巨大的字符串。
6. **面试话术**："release 包关日志的价值不只是 IO，而是**避免字符串拼接这种'看起来无害'的开销**。但更现代的做法是用 Timber 5 的 lambda 形式，这样在 release 下连参数求值都省了，同时保留了线上 INFO 级别的可观测性。**我的规范是：高频路径一律 lambda 形式，禁止在 release 打堆栈。**"

---

**读者问：日志脱敏怎么做才安全？黑名单够用吗？**

**AI答：**

1. **黑名单不够用，这是安全设计上的根本缺陷**：
   - **人会忘**：新增了一个 `userRealName` 字段，没加进黑名单 → 泄漏。
   - **别名难覆盖**：`pwd`、`passWord`、`passwd`、`user_pwd`……枚举不完。
   - **嵌套结构**：Map/List 里的敏感字段更难覆盖。
2. **正确做法：白名单（默认拒绝）**：
   ```kotlin
   // 只有明确列出的字段才允许被记录
   private val ALLOWED_KEYS = setOf(
       "page", "durationMs", "itemCount", "orderId",
       "resultCode", "httpStatus", "retryCount", "errorType"
   )
   ```
   - 新字段默认**不记录**，要记录必须显式加入白名单 → **新增字段时会触发一次"要不要记录"的思考**，这正是安全设计想要的。
3. **多层防护**：
   - **第 1 层（源头）**：不把敏感信息传进日志 API（Kotlin 的 `String` 类型系统帮不了忙，但 Code Review 能查）。
   - **第 2 层（脱敏）**：统一 `Desensitizer`，正则替换手机号、身份证、银行卡、邮箱。
   - **第 3 层（黑名单兜底）**：对已知敏感 key 做完全替换 `[REDACTED]`。
   - **第 4 层（传输）**：HTTPS + 服务端再脱敏一次。
4. **Token 类要特别处理**：
   - **绝不记录原文**。如果需要关联同一 token 的多条日志，记录**哈希指纹**（SHA-256 前 4 字节）：
     ```kotlin
     fun fingerprint(token: String) = MessageDigest.getInstance("SHA-256")
         .digest(token.toByteArray()).take(4).joinToString("") { "%02x".format(it) }
     ```
   - 这样一个 token 的多条日志可以关联，但无法反推 token 本身。
5. **注意事项**：
   - **正则脱敏有误判**：手机号正则可能误伤订单号。**关键字段应该走结构化字段脱敏，而不是靠正则扫全文**。
   - **异常堆栈里也可能有敏感信息**：`IllegalArgumentException("token=abc123")` → 堆栈里的 message 也要脱敏。
   - **URL 里的 query 参数**：`https://api.com/user?token=xxx` → 记录 URL 时要剥离 query 或脱敏其中的敏感参数。
6. **合规视角**：
   - 中国的《个人信息保护法》（PIPL）与《数据安全法》对日志中的个人信息有明确要求。
   - **Google Play** 与国内商店对隐私合规的检查越来越严，**日志中记录个人信息可能导致审核不通过或下架**。
7. **面试话术**："脱敏我坚持**白名单**而不是黑名单。黑名单的问题是**新加的字段一定会漏**，而漏一次就是数据事故。白名单的代价是每次加字段要想一下，这个思考成本是可以接受的。"

---

**读者问：日志和埋点有什么区别？什么时候用哪个？**

**AI答：**

1. **本质区别**：
   - **日志（Log）**：面向**开发者**的**技术性记录**，目的是"还原现场、定位问题"。内容是状态变化、错误详情、耗时。
   - **埋点（Analytics/Tracking）**：面向**产品与数据**的**业务性记录**，目的是"衡量行为、分析漏斗"。内容是点击、曝光、下单、分享。
2. **对比**：

| 维度 | 日志 | 埋点 |
| --- | --- | --- |
| **受众** | 开发、运维 | 产品、运营、数据分析师 |
| **内容** | 技术细节、堆栈、状态 | 业务事件、参数 |
| **结构** | 灵活 KV | 固定事件模型（event + params） |
| **时效** | 实时（尤其崩溃） | 通常 T+1 或准实时 |
| **保留期** | 短（7~30 天） | 长（1 年+） |
| **失败容忍** | 丢失可接受 | **不可丢失**（影响指标准确性） |
| **合规要求** | 高（含技术细节易含隐私） | 高（涉及用户行为） |
| **量级** | 万~十万/天/用户 | 十万~百万/天/用户（事件更多） |

3. **举例说明区别**：
   - 日志：`"加载用户信息失败, userId=123, cause=timeout"` → **给开发看**。
   - 埋点：`event="user_profile_load", params={result="fail", duration_ms=3000}` → **给数据分析师看**。
4. **工程上怎么组织**：
   - **两个独立接口**：`AppLogger`（日志）与 `AppTracker`（埋点），不要混用。
   - **共享上下文**：都自动附加 `deviceId`、`sessionId`、`userId`、`appVersion`。
   - **共享可靠性策略**：埋点需要**本地持久化队列 + 失败重试**（不能丢），日志不需要。
5. **容易犯的错**：
   - ❌ **用日志代替埋点**：日志会被级别裁剪和采样，导致数据不准；且没有可靠投递保证。
   - ❌ **用埋点做错误监控**：埋点的字段模型太固定，堆栈信息放不进去，排查价值低。
   - ❌ **埋点里塞太多参数**：上报量大、存储成本高，还容易夹带敏感信息。
6. **面试话术**："日志和埋点是**两套服务、两个受众、两套可靠性要求**。日志是尽力而为（丢了就丢了），埋点是必须送达（要做本地队列和重试）。工程上我把它们分成两个独立的门面，但共享设备/会话上下文注入。"

---

**读者问：日志文件会占满用户存储吗？怎么控制？日志文件需要加密吗？**

**AI答：**

1. **会占满，需要多层控制**：
   - **单文件上限**：2MB（可按业务调）。
   - **文件数量**：保留 5 个（当前 + 4 个历史）→ **总量上限 ~10MB**。
   - **保留期**：7 天（用户反馈场景可到 30 天，但要告知用户）。
   - **主动清理**：App 启动时检查并删除过期文件（用户可能几个月没打开 App）。
   - **空间检查**：写入前检查 `logDir.usableSpace`，不足时丢弃或删除最老的。
2. **存储位置选择**：

| 位置 | 权限 | 卸载清除 | 推荐 |
| --- | --- | --- | --- |
| `context.filesDir/logs` | 私有，无需权限 | ✔ | **✔ 首选** |
| `context.getExternalFilesDir()` | 私有，无需权限 | ✔ | 大文件（但用户可访问） |
| `Environment.getExternalStorageDirectory()` | **需要 WRITE_EXTERNAL_STORAGE** | ✔ | ❌ Android 10+ 不可用 |
| `sdcard/Android/data/<pkg>/` | 私有 | ✔ | 不推荐（分屏/多用户下不可靠） |

3. **加密的必要性与局限**：
   - **日志本身不含敏感信息时，不需要加密**——**最好的保护是不写**。
   - **含敏感信息时**：用 **AES-128-GCM** 加密文件，**密钥存放在 Android Keystore**（硬件安全区 TEE/StrongBox），App 进程能拿到密钥但**导出不了**（root/调试器之外无法提取）。
   - **加密解决不了什么**：
     - ❌ 防不住**上报到服务端后**的泄漏（日志内容在服务端是明文，需要服务端再脱敏）。
     - ❌ 防不住**运行时内存中的明文**（加密文件在写入前是明文）。
     - ❌ 增加 IO 开销与复杂度（每条日志一次加密 → 批量加密更好）。
   - **更好的组合**：**字段级脱敏（源头）+ 文件加密（传输/存储）**。
4. **一个实用建议**：日志文件**不要直接给用户**。如果需要用户反馈日志，提供"**一键生成日志包（脱敏 + 压缩 + 有效期 7 天）**"的流程，而不是暴露文件路径。
5. **面试话术**："日志存储我用**私有目录 + 单文件 2MB + 保留 5 个 + 7 天保留期**。加密方面我的观点是：**加密是补救，源头不写才是根治**。如果确实含敏感信息，我会用 Keystore 保护密钥做 AES-GCM 加密，同时明确告诉团队它防不住服务端泄漏。"

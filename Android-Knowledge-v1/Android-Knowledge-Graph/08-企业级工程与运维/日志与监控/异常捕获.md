# 异常捕获

## 一句话定义

异常捕获体系是 App 的**"急诊室"**：它保证任何未被业务代码处理的异常，都能在**进程死亡之前**被截获、记录、上报，从而把"用户看到闪退 + 未知原因"变成"我们有完整堆栈、有设备信息、有发生次数"。完整的异常捕获需要覆盖四层：**Java 层未捕获异常**、**协程未捕获异常**、**Native 层崩溃**、**ANR**。

面试开场：**"异常捕获的核心思路是'**在最后一刻兜住它**'。业务代码的 try-catch 是局部防御，而全局兜底机制保证的是'**没有任何一条路径能让异常逃逸到系统**'。"**

## 核心原理

### 1. Java/Kotlin 异常体系

```
                    java.lang.Throwable
                    （所有异常的根，可被 catch(Throwable) 捕获）
                            │
              ┌─────────────┴─────────────┐
              │                           │
       java.lang.Error            java.lang.Exception
       （JVM 层面的严重错误）       （程序可预期的异常）
              │                           │
    ┌─────────┼─────────┐      ┌────────┼────────┐
    │         │         │      │        │        │
OutOfMemory  StackOverflow  VirtualMachineError  │        │
Error        Error                            │        │
                                       │        │        │
                     ┌─────────────────┴──┐  RuntimeException  IOException
                     │                    │  （非受检异常）    （受检异常）
              SQLException             ArithmeticException
                                          NumberFormatException
                                          NullPointerException
                                          IndexOutOfBoundsException
                                          ClassCastException
```

**关键分类**：

| 类别 | 是否受检（编译器强制 catch） | 能否恢复 | 处理方式 |
| --- | --- | --- | --- |
| **受检异常（Checked）** | ✔ 必须处理或声明抛出 | 通常可恢复 | `try/catch` 或声明 `throws` |
| **非受检异常（Unchecked）** | ✘ 可不处理 | 通常表示程序缺陷 | 尽量修复根因；全局兜底 |
| **Error** | ✘ | **不可恢复** | 通常只能让进程崩溃（`OutOfMemoryError` 等） |

**Kotlin 没有受检异常**：

```kotlin
// Java 中必须处理
try {
    riskyOperation()
} catch (e: IOException) {
    // 必须
}

// Kotlin 中不需要强制处理（但仍会抛）
try {
    riskyOperation()
} catch (e: IOException) {
    // 可选
}
```

**Kotlin 的取舍**：Kotlin 设计者认为受检异常在实践中价值不大（大部分时候都会 catch），且与其他 JVM 语言（Groovy、Scala、Clojure）不一致。代价是**失去了编译期的"你必须处理这个异常"提示**，需要靠团队规范来保证。

**实践建议**：Kotlin 项目里仍然应该**在文档和 Review 中明确"会抛什么异常"**，尤其是对外 API 和 Repository 层。

### 2. 未捕获异常的处理机制

#### 2.1 Thread.setDefaultUncaughtExceptionHandler

```text
异常抛出 → 栈展开（寻找匹配的 catch）→ 未找到
    ↓
当前线程的 UncaughtExceptionHandler（默认是 ThreadGroup）
    ↓
如果 handler 自己抛异常 → 进程终止（Android 会打印 "FATAL EXCEPTION" 并杀掉进程）
    ↓
进程死亡，App 退出
```

```kotlin
/**
 * 全局异常处理器。
 *
 * 职责：
 * 1. 记录崩溃信息（堆栈、线程、设备信息、内存信息）
 * 2. 上报到崩溃平台
 * 3. 落盘一份崩溃日志（供下次启动时上传）
 * 4. 交还给默认 handler，让系统按正常流程杀掉进程
 *
 * ⚠️ 关键：一定要调用 delegate?.uncaughtException()，
 *    否则进程不会退出，会处于"卡死但没死"的状态（更糟）。
 */
class CrashHandler : Thread.UncaughtExceptionHandler {

    private val defaultHandler: Thread.UncaughtExceptionHandler? =
        Thread.getDefaultUncaughtExceptionHandler()

    override fun uncaughtException(thread: Thread, throwable: Throwable) {
        try {
            // 1. 收集崩溃信息
            val crashInfo = CrashInfoCollector.collect(thread, throwable)

            // 2. 落盘（同步写，保证进程被杀前写完）
            CrashLogStore.write(crashInfo)

            // 3. 上报（同步，必须在进程死亡前完成）
            CrashReporter.report(crashInfo)

            // 4. 交还默认处理器（Android 会打印并杀掉进程）
            defaultHandler?.uncaughtException(thread, throwable)
        } catch (e: Throwable) {
            // 兜底：即使收集信息失败，也必须让进程正常退出
            defaultHandler?.uncaughtException(thread, throwable)
        }
    }
}
```

```kotlin
// Application 中安装（必须在 Application.onCreate 的最早期）
class MyApplication : Application() {
    override fun onCreate() {
        super.onCreate()
        // 注意：onCreate 里不要做太多耗时操作，否则会拖慢启动
        Thread.setDefaultUncaughtExceptionHandler(CrashHandler())
    }
}
```

**安装的时机问题**：

- **`Application.onCreate` 中安装**：能捕获之后的所有崩溃，但**捕获不到 Application.onCreate 本身早期**的崩溃（更早的崩溃由系统处理，表现为"启动即闪退"）。
- **更早的时机**：`ContentProvider.onCreate` 比 `Application.onCreate` 更早（系统先创建 Provider 再调 Application.onCreate）→ 可以在 `ContentProvider` 里安装以覆盖更多场景。
- **最彻底**：`attachBaseContext` 是 Application 生命周期中最早的回调。

```kotlin
/** 用 ContentProvider 提前安装异常处理器（覆盖更早的崩溃） */
class CrashInitProvider : ContentProvider() {
    override fun onCreate(): Boolean {
        Thread.setDefaultUncaughtExceptionHandler(CrashHandler())
        return true
    }
    // ... 其他空实现
}
```

```xml
<!-- AndroidManifest.xml -->
<provider
    android:name=".CrashInitProvider"
    android:authorities="${applicationId}.crashinit"
    android:exported="false"
    android:initOrder="9999" />
```

#### 2.2 协程异常处理

协程的异常处理**与线程不同**，这是最容易出错的地方。

```kotlin
// ❌ 错误：launch 中的异常不会传播到 CoroutineExceptionHandler
//    因为 launch 用的是 SupervisorJob + CoroutineExceptionHandler 的组合，
//    但如果异常发生在子协程中且没有 supervisor 语义，行为不同
scope.launch {
    throw IllegalStateException("boom")
}
// 结果：异常会走 CoroutineExceptionHandler（如果 launch 的 context 里有）

// ✅ 结构化并发：父协程会因子协程失败而失败
scope.launch {
    coroutineScope {          // 或 supervisorScope
        launch { throw RuntimeException("child failed") }
        // 异常会向上传播，取消兄弟协程，并最终抛给 CoroutineExceptionHandler
    }
}
```

**核心规则**：

| 协程构建器 | 异常传播 | 说明 |
| --- | --- | --- |
| `launch` | 异常抛给 **`CoroutineExceptionHandler`**（若有）；无 handler 则走 `Thread.UncaughtExceptionHandler` | 异常不会传播给调用方（因为 launch 返回 Job，不阻塞） |
| `async` | 异常在 **`await()` 时**抛出 | 若不 await，异常会被吞掉（但会记录到 CoroutineExceptionHandler） |
| `supervisorScope` | 子协程失败**不影响**兄弟协程 | 每个子协程的异常独立处理 |
| `coroutineScope` | 子协程失败**取消整个作用域** | 异常在 scope 结束时抛给调用方 |

```kotlin
/**
 * 协程异常处理器。
 *
 * 注意：CoroutineExceptionHandler 只能捕获 "根协程" 的未处理异常，
 * 对于结构化并发中的子协程异常，需要用 supervisorScope 或在子协程内部处理。
 */
class AppCoroutineExceptionHandler : CoroutineExceptionHandler {
    override fun handleException(context: CoroutineContext, exception: Throwable) {
        // 1. 记录
        AppLogger.e("Coroutine", "协程未捕获异常", exception)

        // 2. 判断是否是 CancellationException（协程取消是正常流程，不算错误）
        if (exception is CancellationException) {
            AppLogger.d("Coroutine", "协程被取消（正常流程）")
            return
        }

        // 3. 上报崩溃
        CrashReporter.reportCoroutineException(exception, context)
    }
}
```

```kotlin
// 全局安装
val appScope = CoroutineScope(
    SupervisorJob() + Dispatchers.Default + AppCoroutineExceptionHandler()
)

// 或者在 Application 中设置（不推荐，会影响所有新建协程）
// 但可以通过自定义 Scope 工厂
```

**必须过滤 `CancellationException`**：

```kotlin
override fun handleException(context: CoroutineContext, exception: Throwable) {
    // CancellationException 表示协程被主动取消（用户离开页面、scope 销毁），
    // 这是正常流程，不应该当成崩溃上报，否则会产生大量噪音
    if (exception is CancellationException) return
    // 真正的异常
    report(exception)
}
```

> **这是面试高频考点**：为什么协程异常处理器里要 `if (e is CancellationException) return`？因为结构化并发中 `viewModelScope` 被取消时，`onCleared()` 会取消所有子协程，这些取消会抛出 `CancellationException`。不上报的话，**每次用户离开页面都会产生一条"崩溃"**，噪音极大。

### 4. Native 崩溃收集与符号还原

#### 4.1 Native 崩溃的原理

Native 层崩溃通常是**信号（Signal）**导致的：

| 信号 | 含义 | 常见原因 |
| --- | --- | --- |
| **SIGSEGV** | 段错误（非法内存访问） | 空指针解引用、数组越界 |
| **SIGABRT** | 进程主动终止 | `assert` 失败、C++ 异常未捕获、`std::terminate` |
| **SIGBUS** | 总线错误 | 未对齐的内存访问 |
| **SIGFPE** | 算术异常 | 除零 |
| **SIGILL** | 非法指令 | CPU 指令集不兼容（如在旧设备上执行 ARMv8 指令） |

**信号处理机制**：

```
Native 代码崩溃
    ↓
内核向进程发送信号
    ↓
OS 层的 signal handler（通常是 debuggerd）
    ↓
读取进程内存：线程栈、寄存器、内存映射
    ↓
生成 tombstone（崩溃转储）
    ↓
写入 /data/tombstones/tombstone_XX
    ↓
如果 App 有 Native 崩溃捕获 SDK（注册了自己的 signal handler）
    → SDK 拦截信号，读取堆栈，上报
```

#### 4.2 采集方式

```kotlin
/**
 * Native 崩溃信号捕获。
 *
 * 原理：Android 的 native 崩溃最终由系统处理并生成 tombstone。
 * SDK 通过注册自己的信号处理器（sigaction）拦截信号，
 * 在 handler 里读取当前线程的栈信息，然后上报。
 *
 * ⚠️ 注意：signal handler 里只能调用 async-signal-safe 的函数，
 *    不能做文件 IO、网络请求、内存分配（很多实现用 sigaltstack 独立栈）。
 */
class NativeCrashHandler {

    companion object {
        // 需要捕获的信号
        private val CRASH_SIGNALS = intArrayOf(
            Signal.SIGSEGV, Signal.SIGABRT, Signal.SIGBUS,
            Signal.SIGFPE, Signal.SIGILL, Signal.SIGTRAP
        )

        private val handlers = SparseArray<SignalHandler>()

        fun install() {
            for (signum in CRASH_SIGNALS) {
                val oldHandler = Signal.handle(signum) { signal, info ->
                    // 在这里收集 native 堆栈
                    val stack = NativeStackTrace.collect()
                    val info = NativeCrashInfo(
                        signal = signal,
                        stack = stack,
                        threadName = Thread.currentThread().name,
                        appVersion = BuildConfig.VERSION_NAME
                    )
                    // 写入本地文件（异步，避免在 signal handler 里做复杂操作）
                    NativeCrashStore.write(info)
                    // 交还原来的 handler，让系统正常处理
                    oldHandler?.handle(signal, info)
                }
                handlers.put(signum, oldHandler)
            }
        }
    }
}
```

#### 4.3 符号还原（Native）

Native 崩溃的堆栈里是**地址**（如 `0x0000007a1b2c3d4`），需要用**符号表（symbol / unstripped so）**还原成函数名和源码行号。

```
崩溃上报：native crash 堆栈 + so 文件的 Build ID
    ↓ 服务端
用 Build ID 找到对应的符号文件（upload-symbols 时上传的）
    ↓
addr2line / atos 还原 → 函数名 + 文件:行号
```

**上传符号文件的流程**：

```bash
# 提取未 strip 的 so（构建时保留符号）
./gradlew :app:assembleRelease

# NDK 项目：符号在 intermediates/stripped_native_libs（stripped）和
#           intermediates/cxx（unstripped）
# 通常从 build/intermediates/cxx/{abi}/**/obj/ 找 unstripped 版本

# 用 llvm-nm / llvm-addr2line 手动还原
$NDK/toolchains/llvm/prebuilt/linux-x86_64/bin/llvm-addr2line \
    -C -f -e libnative.so 0x0000007a1b2c3d4
# 输出：/path/to/native.cpp:42
#       (anonymous namespace)::parseData(unsigned char const*, int)

# 使用 Crashlytics 的符号上传
firebase crashlytics:symbols:upload \
    --app=com.example.myapp \
    --path=app/build/intermediates/stripped_native_libs/release/out/lib/arm64-v8a \
    --debug-symbol-ids-directory=app/build/intermediates/cxx/release/*/obj

# Bugly 的符号上传
python bugly-symbols.py \
    --appid <appid> \
    --appversion 3.2.1 \
    --symbol-dir app/build/intermediates/stripped_native_libs/release/out/lib
```

**关键点**：
- **每个发版都必须上传符号**，否则线上 Native 崩溃只有地址，无法定位。
- **符号文件必须与 APK 版本严格对应**（用 Build ID 校验，不要用文件名）。
- **符号文件要长期保存**（崩溃可能在几个月后才被用户上报）。

### 5. ANR 监控与看门狗

#### 5.1 ANR 的产生机制

```
主线程消息队列（MessageQueue）长时间无法取出消息
    ↓
超过阈值（前台 5s / 后台 10s）
    ↓
系统弹出"App 无响应"对话框
    ↓
用户选择"等待"或"关闭应用"
```

**触发 ANR 的常见原因**：
- 主线程做磁盘 IO（读文件、SharedPreferences 首次加载、数据库查询）。
- 主线程做网络请求（**明确禁止**）。
- 主线程做复杂计算/大量内存分配（GC 压力大）。
- 主线程死锁（ synchronized 竞争、Binder 阻塞）。
- 主线程等待锁（`CountDownLatch.await()` 在主线程）。
- **主线程被非主线程持有的锁阻塞**。

**注意**：**ANR 不一定会杀进程**。用户点"等待"后 App 可能继续运行，但**后续的 ANR 会持续上报**。

#### 5.2 主线程看门狗（Watchdog）

```kotlin
/**
 * 主线程卡顿看门狗。
 *
 * 原理：
 * 1. 在主线程的 MessageQueue 里放一个"心跳 Runnable"
 * 2. 后台线程定期检查"心跳是否被更新"
 * 3. 如果超过阈值没更新，说明主线程被阻塞 → 主动抓取主线程堆栈并上报
 *
 * ⚠️ 关键：抓取堆栈必须在【另一个线程】做，
 *    因为主线程此时已经卡住，自己抓不到自己。
 */
class MainThreadWatchdog(
    private val thresholdMs: Long = 5000,
    private val checkIntervalMs: Long = 1000
) {

    private val mainHandler = Handler(Looper.getMainLooper())
    private val watchdogThread = HandlerThread("watchdog").apply { start() }
    private val handler = Handler(watchdogThread.looper)

    /** 心跳时间戳：主线程每次执行心跳 Runnable 时更新 */
    @Volatile
    private var lastHeartbeat = 0L

    /** 卡顿次数，用于去重（同一处卡顿只报一次） */
    private val reportedStacks = LruCache<String, Long>(20)

    private val heartbeat = object : Runnable {
        override fun run() {
            lastHeartbeat = System.currentTimeMillis()
            mainHandler.postDelayed(this, HEARTBEAT_INTERVAL_MS)
        }
    }

    fun start() {
        lastHeartbeat = System.currentTimeMillis()
        mainHandler.post(heartbeat)

        handler.postDelayed(checkTask, checkIntervalMs)
    }

    private val checkTask = object : Runnable {
        override fun run() {
            val blockedFor = System.currentTimeMillis() - lastHeartbeat

            if (blockedFor > thresholdMs) {
                reportAnr(blockedFor)
            }
            handler.postDelayed(this, checkIntervalMs)
        }
    }

    /** 抓取主线程堆栈并上报 */
    private fun reportAnr(blockedFor: Long) {
        // ★ 必须在 watchdog 线程执行（主线程已经卡住了）
        val mainThread = Looper.getMainLooper().thread
        val stackTrace = mainThread.stackTrace

        // 关键：定位"真正卡住的位置"——主线程当前正在执行的栈顶
        val topFrames = stackTrace.take(30)

        // 去重：相同堆栈 30 秒内不重复上报
        val fingerprint = topFrames.joinToString("|") { "${it.className}.${it.methodName}" }
        val lastReport = reportedStacks.get(fingerprint)
        val now = System.currentTimeMillis()
        if (lastReport != null && now - lastReport < DEDUP_INTERVAL_MS) return
        reportedStacks.put(fingerprint, now)

        val anrInfo = AnrInfo(
            blockedDurationMs = blockedFor,
            stackTrace = topFrames.joinToString("\n") { "\tat $it" },
            threadName = mainThread.name,
            deviceInfo = DeviceInfoCollector.collect()
        )
        CrashReporter.reportAnr(anrInfo)
    }

    companion object {
        private const val HEARTBEAT_INTERVAL_MS = 1000L
        private const val DEDUP_INTERVAL_MS = 30_000L
    }
}
```

#### 5.3 更精准的卡顿检测

**心跳法**的局限：只能知道"卡了"，不知道"卡在哪"，而且粒度是秒级。

**更现代的方案 —— `Choreographer` + `Looper.setMessageLogging`**：

```kotlin
/**
 * 基于 Choreographer 的掉帧/卡顿检测。
 *
 * Choreographer.postFrameCallback 在每一帧（vsync）时回调，
 * 如果两次回调的时间间隔远超 16.67ms，说明这一帧超时了。
 * 用它可以精确到"哪一帧卡了多久"。
 */
class FrameMetricsMonitor(
    private val onJank: (frameDurationMs: Long, droppedFrames: Int) -> Unit
) : Choreographer.FrameCallback {

    private var lastFrameTime = 0L

    override fun doFrame(frameTimeNanos: Long) {
        if (lastFrameTime != 0L) {
            val durationMs = (frameTimeNanos - lastFrameTime) / 1_000_000
            // 超过 3 帧（50ms）视为明显卡顿
            if (durationMs > 50) {
                val dropped = (durationMs / 16.67f).toInt() - 1
                onJank(durationMs, dropped)
            }
        }
        lastFrameTime = frameTimeNanos
        Choreographer.getInstance().postFrameCallback(this)
    }

    fun start() {
        lastFrameTime = 0L
        Choreographer.getInstance().postFrameCallback(this)
    }
}
```

#### 6.1 R8/ProGuard 的 mapping 文件


| **usage.txt** | 被移除的类/方法 | 排查反射问题 |
| **seeds.txt / configuration.txt** | 保留的类与配置 | 调试 |

### 7. 主动异常上报

```kotlin
/**
 * 主动异常上报：捕获"可预期但需要关注"的错误。
 *
 * 与崩溃的区别：
 * - 崩溃：App 无法继续，用户感知强
 * - 主动上报：App 继续运行，但某项功能失败（如某个接口连续失败）
 *
 * 主动上报的价值：可以在**不影响用户**的前提下收集到大量异常信息。
 */
object ErrorReporter {

    /** 上报业务异常（带业务上下文） */
    fun reportBusinessError(
        errorType: String,
        message: String,
        cause: Throwable? = null,
        extra: Map<String, Any?> = emptyMap()
    ) {
        val payload = ErrorPayload(
            type = errorType,
            message = message,
            stackTrace = cause?.let { Log.getStackTraceString(it) },
            level = ErrorLevel.RECOVERABLE,
            extra = extra + deviceContext()
        )
        // 异步上报
        CrashReporter.reportError(payload)
    }

    /** 在关键流程处使用 try-catch + 上报 */
    fun <T> withErrorReport(
        errorType: String,
        block: () -> T
    ): Result<T> = try {
        Result.success(block())
    } catch (e: CancellationException) {
        throw e   // 协程取消不当作错误
    } catch (e: Throwable) {
        reportBusinessError(errorType, e.message ?: "unknown", e)
        Result.failure(e)
    }
}
```

### 8. 崩溃上报的字段设计

```kotlin
/**
 * 崩溃信息收集器。
 *
 * 收集原则：
 * 1. 只收集"定位问题必需"的信息，不要什么都收（隐私 + 体积）
 * 2. 采集必须快速（崩溃时进程随时可能被杀）
 * 3. 敏感信息必须脱敏
 */
object CrashInfoCollector {

    fun collect(thread: Thread, throwable: Throwable): CrashInfo {
        return CrashInfo(
            // 基本信息
            timestamp = System.currentTimeMillis(),
            threadName = thread.name,
            threadId = thread.id,
            isMainThread = thread === Looper.getMainLooper().thread,

            // 异常信息

            stackTrace = Log.getStackTraceString(throwable),
            causeChain = buildCauseChain(throwable),

            // 设备信息
            deviceModel = Build.MODEL,
            manufacturer = Build.MANUFACTURER,
            osVersion = Build.VERSION.RELEASE,
            sdkInt = Build.VERSION.SDK_INT,
            abi = Build.SUPPORTED_ABIS.firstOrNull(),

            // 内存信息（排查 OOM 必需）
            javaHeapUsed = Runtime.getRuntime().totalMemory() - Runtime.getRuntime().freeMemory(),
            javaHeapMax = Runtime.getRuntime().maxMemory(),
            nativeHeap = Debug.getNativeHeapAllocatedSize(),
            availableMemory = ActivityManager.MemoryInfo().let {
                ActivityManager.getSystemService(ACTIVITY_SERVICE).getMemoryInfo(it)
                it.availMem
            },

            // 进程信息
            totalMemory = ActivityManager.MemoryInfo().let {
                ActivityManager.getSystemService(ACTIVITY_SERVICE).getMemoryInfo(it)
                it.totalMem
            },
            lowMemory = ActivityManager.MemoryInfo().let {
                ActivityManager.getSystemService(ACTIVITY_SERVICE).getMemoryInfo(it)
                it.lowMemory
            },

            // 进程状态
            isLowRamDevice = ActivityManager.isLowRamDevice(),
            processName = getCurrentProcessName(),

            // 前后台状态
            appState = AppStateTracker.currentState,

            // 当前页面（从路由栈获取）
            currentRoute = CurrentRouteTracker.currentRoute,

            // 网络状态
            networkType = NetworkStateTracker.currentType,

            // 最近日志（关键！崩溃前的上下文）
            recentLogs = RecentLogBuffer.snapshot(50)
        )
    }

    /** 构建 cause chain（异常链），还原完整的因果关系 */
    private fun buildCauseChain(throwable: Throwable): List<String> {
        val chain = mutableListOf<String>()
        var current: Throwable? = throwable
        var depth = 0
        while (current != null && depth < 10) {   // 防止循环引用导致无限循环
            chain += "${current.javaClass.name}: ${current.message}"
            current = current.cause
            depth++
        }
        return chain
    }
}
```

### 1. 完整的崩溃处理器

```kotlin
package com.example.core.crash

import android.app.ActivityManager
import android.content.Context
import android.os.Build
import android.os.Debug
import android.os.Looper
import android.util.Log
import com.example.core.logging.AppLogger
import java.io.File
import java.io.FileOutputStream
import java.io.PrintWriter
import java.io.StringWriter
import java.util.concurrent.atomic.AtomicBoolean

/**
 * 全局崩溃处理器。
 *
 * 工作流程：
 * 1. 捕获未捕获异常
 * 2. 收集崩溃信息（含最近日志上下文）
 * 3. 同步写入本地文件（进程随时可能被杀，必须同步）
 * 4. 同步上报到崩溃平台（带重试）
 * 5. 交还默认 handler，让系统正常结束进程
 */
class CrashHandler(
    private val appContext: Context,
    private val reporter: CrashReporter
) : Thread.UncaughtExceptionHandler {

    private val defaultHandler: Thread.UncaughtExceptionHandler? =
        Thread.getDefaultUncaughtExceptionHandler()

    /** 防止重复处理（嵌套异常时） */
    private val isHandling = AtomicBoolean(false)

    override fun uncaughtException(thread: Thread, throwable: Throwable) {
        if (!isHandling.compareAndSet(false, true)) {
            // 已经在处理中，直接交还
            defaultHandler?.uncaughtException(thread, throwable)
            return
        }

        try {
            val crashInfo = CrashInfoCollector.collect(thread, throwable)

            // 1. 写本地文件（同步，保证不丢）
            runCatching { writeLocalLog(crashInfo) }

            // 2. 上报（同步，最多等 3 秒）
            runCatching { reporter.reportBlocking(crashInfo, timeoutMs = 3000) }

            // 3. 交还默认 handler（系统会打印堆栈并结束进程）
            defaultHandler?.uncaughtException(thread, throwable)
        } catch (t: Throwable) {
            // 兜底：无论如何都要让进程退出
            defaultHandler?.uncaughtException(thread, throwable)
        }
    }

    private fun writeLocalLog(crashInfo: CrashInfo) {
        val dir = File(appContext.filesDir, "crash")
        dir.mkdirs()
        val file = File(dir, "crash-${crashInfo.timestamp}.txt")
        FileOutputStream(file).use { fos ->
            PrintWriter(fos).use { pw ->
                pw.println("timestamp: ${crashInfo.timestamp}")
                pw.println("thread: ${crashInfo.threadName} (main=${crashInfo.isMainThread})")
                pw.println("exception: ${crashInfo.exceptionClass}")
                pw.println("message: ${crashInfo.message}")
                pw.println("device: ${crashInfo.manufacturer} ${crashInfo.deviceModel}")
                pw.println("os: Android ${crashInfo.osVersion} (API ${crashInfo.sdkInt})")
                pw.println("memory: java=${crashInfo.javaHeapUsed / 1024 / 1024}MB/" +
                        "${crashInfo.javaHeapMax / 1024 / 1024}MB native=${crashInfo.nativeHeap / 1024 / 1024}MB")
                pw.println("state: ${crashInfo.appState}, route: ${crashInfo.currentRoute}")
                pw.println("--- stack ---")
                pw.println(crashInfo.stackTrace)
                pw.println("--- recent logs ---")
                crashInfo.recentLogs.forEach { pw.println(it) }
            }
        }
        // 清理超过 7 天的崩溃日志
        dir.listFiles()?.forEach { f ->
            if (System.currentTimeMillis() - f.lastModified() > 7 * 24 * 3600 * 1000L) {
                f.delete()
            }
        }
    }
}
```

```kotlin
package com.example.core.crash

import kotlinx.coroutines.CancellationException
import kotlinx.coroutines.CoroutineExceptionHandler
import kotlinx.coroutines.CoroutineScope
import kotlinx.coroutines.Dispatchers
import kotlinx.coroutines.SupervisorJob
import kotlinx.coroutines.launch
import kotlin.coroutines.CoroutineContext

/**
 * 协程全局异常处理器。
 *
 * ⚠️ 三个关键点：
 * 1. 必须过滤 CancellationException（协程取消是正常流程）
 * 2. 只对根协程生效；子协程异常要靠结构化并发传播
 * 3. 应该用独立的 SupervisorJob scope，而不是修改全局 Dispatchers
 */
class AppCoroutineExceptionHandler : CoroutineExceptionHandler {

    override fun handleException(context: CoroutineContext, exception: Throwable) {
        // ★ 过滤协程取消：用户离开页面时 viewModelScope 取消会抛 CancellationException，
        //   如果不上报，每次页面销毁都会产生一条"崩溃"，噪音极大
        if (exception is CancellationException) {
            AppLogger.d(TAG, "协程正常取消: ${exception.message}")
            return
        }

        AppLogger.e(TAG, "协程未捕获异常", exception)

        // 上报崩溃
        CrashReporter.reportAsync(
            CrashInfo(
                timestamp = System.currentTimeMillis(),
                exceptionClass = exception.javaClass.name,
                message = exception.message ?: "",
                stackTrace = android.util.Log.getStackTraceString(exception),
                isMainThread = false,
                threadName = Thread.currentThread().name,
                coroutineContext = context.toString()
            )
        )
    }

    companion object {
        private const val TAG = "CoroutineException"
    }
}

/** 应用级协程作用域：后台任务的容器 */
val ApplicationScope: CoroutineScope by lazy {
    CoroutineScope(
        SupervisorJob() +                      // ★ SupervisorJob：一个子任务失败不影响其他
            Dispatchers.Default +              // 后台线程池
            AppCoroutineExceptionHandler()     // 全局异常处理
    )
}

/** 正确使用结构化并发 */
suspend fun loadDataSafely(): Result<Data> = coroutineScope {

    val userDeferred = async { userRepository.getUser() }
    val configDeferred = async { configRepository.getConfig() }
```

### 3. 主线程看门狗（ANR 检测）

```kotlin
package com.example.core.crash

import android.os.Handler
import android.os.HandlerThread
import android.os.Looper
import android.util.LruCache
import com.example.core.logging.AppLogger

/**
 * 主线程卡顿（ANR）看门狗。
 *
 * 工作原理：
 * 1. 主线程的 MessageQueue 里跑一个心跳 Runnable，每秒更新一次时间戳
 * 2. 后台线程每秒检查一次时间戳
 * 3. 超过阈值未更新 → 主线程被阻塞 → 在后台线程抓取主线程堆栈并上报
 */
class MainThreadWatchdog(
    private val thresholdMs: Long = 5000L,
    private val checkIntervalMs: Long = 1000L,
    private val onAnr: (AnrInfo) -> Unit
) {

    private val mainHandler = Handler(Looper.getMainLooper())
    private val watchdogThread = HandlerThread("anr-watchdog").apply { start() }
    private val watchdogHandler = Handler(watchdogThread.looper)

    @Volatile
    private var lastHeartbeat = 0L

    @Volatile
    private var running = false

    /** 堆栈指纹去重：同一处卡顿不重复上报 */
    private val reported = LruCache<String, Long>(32)

    private val heartbeat = object : Runnable {
        override fun run() {
            lastHeartbeat = System.currentTimeMillis()
            if (running) mainHandler.postDelayed(this, HEARTBEAT_INTERVAL_MS)
        }
    }

    private val checkTask = object : Runnable {
        override fun run() {
            val blockedFor = System.currentTimeMillis() - lastHeartbeat
            if (blockedFor >= thresholdMs) {
                captureAndReport(blockedFor)
            }
            if (running) watchdogHandler.postDelayed(this, checkIntervalMs)
        }
    }

    fun start() {
        if (running) return
        running = true
        lastHeartbeat = System.currentTimeMillis()
        mainHandler.post(heartbeat)
        watchdogHandler.postDelayed(checkTask, checkIntervalMs)
    }

    fun stop() {
        running = false
        mainHandler.removeCallbacks(heartbeat)
        watchdogHandler.removeCallbacks(checkTask)
    }

    private fun captureAndReport(blockedFor: Long) {
        // ★ 必须在 watchdog 线程（主线程已卡住，无法自己抓自己）
        val mainThread = Looper.getMainLooper().thread
        val frames = mainThread.stackTrace

        // 定位真正卡住的位置：栈顶第一个非系统帧
        val appFrame = frames.firstOrNull { frame ->
            frame.className.startsWith("com.example")
        }
        val fingerprint = appFrame?.let { "${it.className}.${it.methodName}:${it.lineNumber}" }
            ?: frames.take(3).joinToString("|")

        // 去重：30 秒内相同位置只报一次
        val now = System.currentTimeMillis()
        val last = reported.get(fingerprint)
        if (last != null && now - last < DEDUP_INTERVAL_MS) return
        reported.put(fingerprint, now)

        val info = AnrInfo(
            blockedDurationMs = blockedFor,
            stackTrace = frames.joinToString("\n") { "\tat $it" },
            blockedAt = appFrame?.let { "${it.className}.${it.methodName}(${it.fileName}:${it.lineNumber})" },
            threadName = mainThread.name,
            timestamp = now
        )
        AppLogger.e(TAG, "检测到主线程卡顿 ${blockedFor}ms @ ${info.blockedAt}")
        onAnr(info)
    }

    companion object {
        private const val TAG = "ANRWatchdog"
        private const val DEDUP_INTERVAL_MS = 30_000L
    }
}
```

```kotlin
/**

            javaHeapMax = runtime.maxMemory(),

            networkType = NetworkStateTracker.currentType.name,
            orientation = context.resources.configuration.orientation,

            // 崩溃前的日志上下文（非常关键）
            recentLogs = RecentLogBuffer.snapshot(MAX_RECENT_LOGS)
        )
    }

    /**
     * 构建异常链。
     *
     * ⚠️ 必须限制深度：某些异常（如自定义的重试异常）可能形成 cause 循环引用，
     *    直接遍历会栈溢出或死循环。
     */
    private fun buildCauseChain(throwable: Throwable): List<String> {
        val chain = mutableListOf<String>()
        val visited = mutableSetOf<Throwable>()
        var current: Throwable? = throwable
        var depth = 0

        while (current != null && depth < MAX_CAUSE_DEPTH) {
            // 循环引用检测
            if (!visited.add(current)) break
            chain += "${current.javaClass.simpleName}: ${current.message}"
            current = current.cause
            depth++
        }
        return chain
    }

    private const val MAX_CAUSE_DEPTH = 10
    private const val MAX_RECENT_LOGS = 50
}
```

### 5. 最近日志环形缓冲区

```kotlin
package com.example.core.crash

/**
 * 最近日志的环形缓冲区。
 *
 * 目的：崩溃时能知道"崩溃前发生了什么"，
 * 这是定位问题的关键上下文（尤其是异步/并发场景）。
 */
object RecentLogBuffer {

    private const val CAPACITY = 100

    private val buffer = arrayOfNulls<String>(CAPACITY)
    private var index = 0
    private val count = AtomicInteger(0)

    /** 记录一条日志（由日志系统调用） */
    fun add(line: String) {
        synchronized(buffer) {
            buffer[index] = line
            index = (index + 1) % CAPACITY
            if (count.get() < CAPACITY) count.incrementAndGet()
        }
    }

    /** 取出最近的 N 条（按时间顺序） */
    fun snapshot(n: Int = 50): List<String> {
        synchronized(buffer) {
            val size = minOf(n, count.get())
            if (size == 0) return emptyList()
            val result = ArrayList<String>(size)
            // 从最旧的一条开始
            val start = (index - size + CAPACITY) % CAPACITY
            for (i in 0 until size) {
                buffer[(start + i) % CAPACITY]?.let { result.add(it) }
            }
            return result
        }
    }

    fun clear() {
        synchronized(buffer) {
            buffer.fill(null)
            index = 0
            count.set(0)
        }
    }
}
```

```proguard
# ── 崩溃还原所需 ──
# 保留行号与源文件信息（还原堆栈时需要）
-keepattributes SourceFile,LineNumberTable
# 混淆文件名（保留行号但隐藏真实文件名，平衡可读性与逆向成本）
-renamesourcefileattribute SourceFile

# ── 崩溃 SDK 需要的 ──
-keep class com.example.core.crash.** { *; }
-keep class com.example.crashlib.** { *; }
-dontwarn com.example.crashlib.**

# ── 反射相关 ──
# 使用反射的类需要保留成员（注意：保留太多会削弱混淆效果）
-keepclassmembers class * {
    @com.example.core.annotation.ReflectionInject <methods>;
}
-keep class com.example.core.annotation.ReflectionInject

# ── Kotlin ──
-dontwarn kotlinx.coroutines.**
-keepclassmembers class kotlinx.coroutines.** { volatile <fields>; }

# ── 排除警告 ──
-dontwarn javax.annotation.**
-dontwarn org.slf4j.**
```

## 常见问题 / 面试要点

**读者问：怎么全局捕获未捕获异常？有哪些坑？**

**AI答：**

1. **实现方式**：`Thread.setDefaultUncaughtExceptionHandler(CrashHandler())`，在 `Application.onCreate`（或更早的 `ContentProvider.onCreate`）中安装。
2. **五个必知的坑**：

| 坑 | 说明 | 解决 |
| --- | --- | --- |
| **必须交还默认 handler** | 不调用 `defaultHandler?.uncaughtException()` → **进程不会退出**，App 处于"半死"状态（界面卡住但进程在），更糟 | 一定要调用 |
| **处理时间不能太长** | 系统给崩溃处理的时间有限（约 5 秒后会 ANR）；网络上报超时要有上限 | 上报超时设 3 秒；或者先落盘、退出前异步上报 |
| **只覆盖安装之后的崩溃** | `Application.onCreate` 之前的崩溃捕获不到 | 用 `ContentProvider.onCreate` 或 `attachBaseContext` 更早安装 |
| **协程异常不一定会到 Handler** | `launch` 的异常走 `CoroutineExceptionHandler`；`async` 的异常在 `await()` 时抛，不 await 就被吞 | 见下文 |
| **Native 崩溃不走这个机制** | 信号不是 Java 异常 | 需要 Native 崩溃捕获 SDK |

3. **协程异常的三条规则（面试高频）**：
   - `launch` 的未捕获异常 → 交给 `CoroutineExceptionHandler`（若未安装则交给线程的 `UncaughtExceptionHandler`）。
   - `async` 的异常在 `await()` 时抛出；如果**从不 await**，异常会被 `CoroutineExceptionHandler` 记录（Android 上还会导致进程崩溃）。
   - 结构化并发中，子协程的异常会**取消父协程和兄弟协程**，最终冒泡到根协程。
4. **必须过滤 `CancellationException`**：
   ```kotlin
   override fun handleException(context: CoroutineContext, exception: Throwable) {
       if (exception is CancellationException) return   // ★ 协程取消是正常流程
       report(exception)
   }
   ```
   **不加这行会怎样**：`viewModelScope` 在 `onCleared()` 时取消所有子协程 → 抛出 `CancellationException` → 每次用户离开页面都会上报一条"崩溃" → **崩溃率数据完全失真**，真正的崩溃被淹没。
5. **收集什么信息**（多不少）：
   - **必须**：时间戳、异常类与消息、完整堆栈（含 cause chain）、线程名、是否主线程。
   - **强烈建议**：设备型号、系统版本、内存使用（OOM 排查必备）、前后台状态、当前页面（路由）、网络类型。
   - **强烈建议**：**崩溃前最近的日志**（环形缓冲）——这是定位"为什么崩"的黄金线索。
   - **不要**：用户姓名、手机号等可识别信息（脱敏后也不必要）。
6. **面试话术**："全局捕获用 `setDefaultUncaughtExceptionHandler`，但有三个必须说出的细节：**一定要交还默认 handler 让进程正常退出**；**上报要有超时**（崩溃时系统只给几秒）；**协程要单独处理并过滤 `CancellationException`**，否则崩溃率数据会被页面销毁的噪音污染。"

**读者问：ANR 怎么监控？原理是什么？**

**AI答：**

1. **ANR 的系统判定**：
   - **前台 Service/Activity**：主线程 5 秒无响应 → ANR。
   - **后台 Service**：10 秒无响应 → ANR。
   - **BroadcastReceiver**：10 秒。
   - **Input 事件**：5 秒无响应。
   - **系统弹出对话框**，用户可选"等待"或"关闭"。注意**用户点等待后进程不会死**，ANR 会持续上报。
2. **应用侧监控的原理**：**主线程心跳法**。
   ```
   主线程：每秒往 MessageQueue 里 post 一个心跳 Runnable，执行时更新时间戳
   后台线程：每秒检查时间戳
   超时未更新 → 主线程被阻塞 → 在【后台线程】抓主线程堆栈并上报
   ```
3. **关键细节**：
   - **必须用另一个线程抓堆栈**：主线程卡住时自己抓不到自己（会永久阻塞）。
   - **堆栈要定位到"卡在哪"**：主线程的栈顶可能是 `Looper.loop()`（正常状态），真正的线索是**栈中第一个属于业务代码的帧**。
   - **要去重**：同一个位置每 30 秒只报一次，否则一个死循环会刷爆监控。
4. **Android 11+ 的官方方案**：`FrameMetrics` + `Window.addOnFrameMetricsAvailableListener`，能拿到每一帧的详细分解（UI 线程耗时、RenderThread 耗时、GPU 耗时），比心跳法精确得多。
   - **API 30 以下**需要用 `Choreographer.postFrameCallback` 自己计算帧间隔。
   - 更早的方案是 `Debug.threadCpuTimeNanos` 或 systrace。
5. **现代 APM 产品的做法**：
   - **多信号交叉**：心跳（是否卡）+ 堆栈快照（卡在哪）+ 系统 ANR 事件（`ApplicationExitInfo`，API 30+）。
   - **`ApplicationExitInfo`**：Android 11+ 提供了 `ActivityManager.getHistoricalProcessExitReasons()`，能拿到**系统判定的 ANR 原因和 trace 文件路径**——这是最权威的数据源（但只能查历史，需要权限）。
6. **排查 ANR 的常见根因**：
   | 根因 | 例子 |
   | --- | --- |
   | **主线程 IO** | 读数据库、`SharedPreferences.getX()` 首次加载（会等磁盘） |
   | **主线程网络** | 明确禁止 |
   | **锁竞争** | 主线程 `synchronized` 被后台线程持有 |
   | **Binder 阻塞** | 主线程调用跨进程 Binder（另一个进程卡住） |
   | **大量分配 → GC** | 主线程创建大量对象 |
   | **死循环** | 逻辑 bug |
   | **等待信号量** | `CountDownLatch.await()` 在主线程 |
7. **面试话术**："ANR 监控我用**主线程心跳 + 后台线程抓堆栈**。关键是**必须在另一个线程抓堆栈**（主线程已经卡住了），以及**定位到栈中第一个业务代码帧**（栈顶是 `Looper.loop()` 没有意义）。Android 11+ 我会优先用 `FrameMetrics` 和 `ApplicationExitInfo` 拿更精确的数据。"

**读者问：混淆后的崩溃堆栈怎么还原？mapping 文件怎么管理？**

**AI答：**

1. **还原原理**：R8 混淆时生成 **mapping.txt**，记录"混淆前的类/方法/字段名 → 混淆后的名称"以及行号映射。崩溃平台用 `retrace` 工具反向还原。
2. **还原命令**：
   ```bash
   # retrace 随 R8 一起分发，在 build-tools 里
   $ANDROID_HOME/build-tools/34.0.0/retrace -m mapping.txt < crash.txt

   # 或用 retrace.sh
   retrace.sh -m app/build/outputs/mapping/release/mapping.txt crash.txt
   ```
3. **mapping 文件的管理（最容易出事的环节）**：
   - **每次发版自动上传**到崩溃平台（Bugly/Crashlytics 都有脚本或插件）。
   - **长期归档**（至少 1 年，与崩溃数据保留期匹配）——**崩溃可能在 3 个月后才被用户上报**。
   - **用 Build ID 而不是版本号关联**：版本号可能被复用（不同分支都用 `1.0.0`），Build ID 是唯一的。
   - **保留 SourceFile 与 LineNumberTable**：否则还原出来的堆栈只有行号没有文件名。
4. **Native 崩溃的还原（不同机制）**：
   - Native 堆栈是**地址**，需要**符号文件（unstripped .so）**。
   - 用 `llvm-addr2line` 手动还原：
     ```bash
     llvm-addr2line -C -f -e libnative.so 0x7a1b2c3d4
     ```
   - 也需要**每次发版上传符号文件**（CI 中自动执行）。
5. **常见问题**：
   - **❌ mapping 文件没上传** → 线上堆栈全是 `a.b.c.a()`，完全无法定位。**这是最常见的事故**。
   - **❌ mapping 与 APK 版本不匹配** → 还原出来的行号是错的（更隐蔽，更糟糕）。
   - **❌ 混淆后没有保留必要注解** → 反射失效、Room/Hilt 序列化失败。
6. **CI 自动化示例**：
   ```yaml
   - name: Upload mapping
     run: |
       firebase crashlytics:symbols:upload \
         --app=$APP_ID \
         --path=app/build/outputs/mapping/release/mapping.txt
       # 同时归档到制品库
   - uses: actions/upload-artifact@v4
     with:
       name: mapping-release
       path: app/build/outputs/mapping/release/mapping.txt
       retention-days: 365
   ```
7. **面试话术**："混淆堆栈还原依赖 **mapping 文件**。工程上有三条铁律：**每次发版自动上传**（人工上传必然会漏）、**长期归档至少一年**、**用 Build ID 关联而不是版本号**。另外 Native 崩溃要单独上传符号文件——这两套机制不能混为一谈。"

**读者问：Native 崩溃（NDK 层）怎么收集？和 Java 崩溃有什么区别？**

**AI答：**

1. **本质区别**：

| 维度 | Java 崩溃 | Native 崩溃 |
| --- | --- | --- |
| **机制** | JVM 抛异常 | 操作系统发**信号（Signal）** |
| **入口** | `UncaughtExceptionHandler` | `sigaction` 信号处理器 |
| **堆栈** | Java 栈帧（可读） | **地址**（需要符号化） |
| **还原** | mapping.txt | 符号文件（unstripped .so） |
| **常见原因** | 空指针、越界、类型转换 | 内存越界、野指针、栈溢出、ABI 不兼容 |
| **归属** | 全部业务代码 | 主要是三方 SDK（NDK 库） |

2. **Native 崩溃的常见信号**：
   - `SIGSEGV`（段错误）：最常见，空指针解引用、缓冲区溢出。
   - `SIGABRT`：`assert` 失败、C++ 异常未捕获、`std::terminate`。
   - `SIGBUS`：未对齐访问。
   - `SIGFPE`：除零。
   - `SIGILL`：**CPU 指令集不兼容**——比如在只支持 ARMv7 的设备上执行 ARMv8 指令（这是一个非常典型的线上事故来源）。
3. **收集机制**：
   - **Android 系统本身**会生成 tombstone（`/data/tombstones/`），但**普通 App 读不到**（需要系统权限）。
   - **崩溃 SDK 的做法**：注册自己的信号处理器（`sigaction`），在 handler 里用 `sigaltstack`（独立栈，避免栈溢出时 handler 也崩）读取当前线程的栈，然后上报。
   - **hook 的方式**：`Signal.handle` / 反射 `libc` 的 `sigaction`。
4. **符号还原流程**：
   ```
   崩溃上报：native 堆栈地址 + so 的 Build ID
      ↓ 服务端匹配符号文件
   llvm-addr2line / llvm-symbolizer 还原
      ↓
   函数名 + 源文件:行号
   ```
5. **符号文件的上传（CI 必须自动化）**：
   ```bash
   # 找到 unstripped 的 so（构建产物中 stripped 和 unstripped 都有）
   find app/build/intermediates/cxx -name "*.so" -path "*arm64-v8a*"

   # 上传（Crashlytics）
   firebase crashlytics:symbols:upload \
     --app=com.example.myapp \
     --path=app/build/intermediates/stripped_native_libs/release/out/lib/arm64-v8a \
     --debug-symbol-ids-directory=app/build/intermediates/cxx/release/*/obj
   ```
6. **ABIs 的注意事项**：
   - 出包时可能同时包含 `armeabi-v7a`、`arm64-v8a`、`x86_64`。
   - **符号文件必须与 so 的架构对应**，且必须**按 ABI 分目录**上传。
   - 64 位设备上 **不能用 32 位的 so**（Android 5.0 之后不支持）。
7. **预防优于捕获**：
   - **ABI 兼容性**：用 `abiFilters` 精确控制打哪些架构（减小包体 + 避免兼容问题）。
   - **内存安全**：用 ASan（`-fsanitize=address`）在 debug 包检测内存错误。
   - **NDK 的 minSdk 限制**：某些 NDK 版本要求 minSdk ≥ 21。
8. **面试话术**："Native 崩溃和 Java 崩溃是两套机制：Java 靠 `UncaughtExceptionHandler`，Native 靠**信号处理器**；Java 靠 mapping.txt 还原，Native 靠**符号文件**还原。工程上最常见的坑是**符号文件没在 CI 里自动上传**——我会在流水线里强制这一步。"

**读者问：主动上报和崩溃上报有什么区别？什么时候用主动上报？**

**AI答：**

1. **本质区别**：

| 维度 | 崩溃上报 | 主动上报（可恢复异常） |
| --- | --- | --- |
| **触发时机** | 异常逃逸到顶层，进程即将死亡 | 业务代码 catch 后显式上报 |
| **用户感知** | 强（闪退） | 弱（功能不可用但 App 能用） |
| **数据量** | 少（千分之几） | 多（可能占日志的 90%） |
| **排查价值** | 定位"为什么崩" | 定位"哪个功能在失败" |
| **处理优先级** | P0（阻断发布） | P1/P2（按影响面） |

2. **主动上报的价值**：
   - **灰度期的"隐形问题"**：功能不出错但**结果不对**（比如推送没收到、支付成功但订单没更新）——这类问题**不会崩溃**，只能靠主动上报发现。
   - **降级路径的可见性**：网络失败走了缓存、重试、fallback —— 这些如果完全静默，用户投诉时你完全不知道发生过。
   - **聚合统计**：可以统计"某接口失败率 0.3%"，而不是"某接口崩溃了 3 次"。
3. **设计要点**：
   - **必须有业务上下文**：`errorType`（错误分类）、`errorCode`、`apiName`、`orderId`、`retryCount`、`fallbackUsed`。
   - **必须可聚合**：错误类型应该是**有限枚举**，不是自由文本。
   - **必须有去重与采样**：同一个错误反复上报会淹没监控。
   - **不影响主流程**：上报必须异步且失败不影响业务。
4. **典型代码位置**：
   ```kotlin
   // 网络层：重试后仍失败
   if (retryCount >= MAX_RETRY) {
       ErrorReporter.reportBusinessError(
           errorType = "network_failure",
           message = "request failed after retries",
           extra = mapOf("apiName" to apiName, "retryCount" to retryCount)
       )
   }

   // 数据层：使用了降级数据
   val data = withFallback(cacheData) {
       ErrorReporter.reportBusinessError("fallback_used", "using cached data",
           extra = mapOf("source" to "cache"))
       cacheData
   }
   ```
5. **注意事项**：
   - **不要用主动上报代替日志**：主动上报是聚合数据，日志是详细上下文，两者互补。
   - **不要上报高频错误**：一个每秒钟失败 100 次的接口会刷爆上报通道 → 必须采样 + 限流。
   - **错误分类要稳定**：`errorType` 应该是常量枚举，方便做趋势看板。
6. **面试话术**："主动上报解决的是**'不崩溃但出错'**的问题。比如支付成功了但订单没更新——它不会产生 Crash，但如果不主动上报，你在监控上完全看不到。我的做法是在**网络层（重试耗尽）、数据层（走了 fallback）、关键业务流程（状态不一致）**这三个位置埋主动上报点，并且用**有限枚举的错误类型 + 采样 + 去重**来控制量。"

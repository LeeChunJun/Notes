# 性能监控

## 一句话定义

性能监控（APM, Application Performance Monitoring）是**在线上真实设备上，持续采集 App 的性能指标并形成可观测、可告警的数据体系**。它与本地 Profiler 的本质区别在于：Profiler 是"**给一台设备做体检**"，APM 是"**给百万台设备做体检并统计出群体规律**"——目标不是找到"那一帧慢在哪"，而是回答"**多少比例的用户正在经历卡顿？是哪个版本开始的？**"。

面试开场：**"线上性能监控的价值在于'发现趋势'和'定位版本'。Crash 能告诉你哪里坏了，但性能退化往往是渐进的——用户不会立刻投诉，他们只是慢慢卸载。"**

## 核心原理

### 1. APM 的采集维度全景

```
┌─────────────────────────────────────────────────────────────────────┐
│  ① 启动性能                                                          │
│     ├─ 冷启动（TTID: Time To Initial Display）                        │
│     ├─ 热启动 / 热恢复                                                │
│     └─ 首帧（TTFD: Time To First Draw）                               │
├─────────────────────────────────────────────────────────────────────┤
│  ② 流畅性                                                            │
│     ├─ 帧率（FPS）、掉帧率、卡顿率                                     │
│     ├─ 慢帧 / 冻结帧（Frozen Frame）                                   │
│     └─ 页面渲染耗时（首屏到可交互）                                    │
├─────────────────────────────────────────────────────────────────────┤
│  ③ 稳定性                                                            │
│     ├─ 崩溃率（Crash Rate）、ANR 率                                   │
│     ├─ Java 异常、未捕获异常                                          │
│     └─ Native 崩溃                                                    │
├─────────────────────────────────────────────────────────────────────┤
│  ④ 资源                                                              │
│     ├─ 内存（Java Heap / Native Heap / PSS）                          │
│     ├─ CPU 使用率                                                      │
│     ├─ 磁盘 IO                                                        │
│     └─ 电量与温度                                                      │
├─────────────────────────────────────────────────────────────────────┤
│  ⑤ 网络                                                              │
│     ├─ 请求成功率、耗时分布（P50/P90/P99）                             │
│     ├─ DNS / TLS / TTFB / 下载各阶段耗时                               │
│     └─ 流量消耗                                                       │
└─────────────────────────────────────────────────────────────────────┘
```

### 2. 核心指标与行业基准

Google 的 [Android Vitals](https://developer.android.com/topic/performance/vitals) 定义了官方基准，是行业通用语言：

| 指标 | 定义 | 良好阈值 | 较差阈值 |
| --- | --- | --- | --- |
| **启动耗时（TTID）** | 用户点击到首帧绘制完成 | ≤ 2s | > 5s |
| **慢帧（Slow Frame）** | 帧耗时 > 16.67ms 但 < 700ms | 帧率 ≥ 60fps | — |
| **冻结帧（Frozen Frame）** | 帧耗时 ≥ 700ms | 0 个 | > 0 个 |
| **ANR 率** | 用户遇到 ANR 的会话比例 | ≤ 0.47% | > 8% |
| **崩溃率** | 崩溃会话 / 总会话 | ≤ 0.47% | > 1.09% |
| **用户感知崩溃率** | 排除后台崩溃后的比例 | ≤ 0.09% | > 0.47% |

**重要说明**：这些阈值是 Google 依据"**达到该水平的 App 在 Play 商店的评分和留存表现更好**"的统计得出的，不是拍脑袋。面试时能引用这个来源会加分。

### 3. 启动耗时的线上统计

#### 3.1 三个关键时间点

```
    用户点击图标
        │
        │ ← ① 进程创建（Process Start）
        ▼
    Application.attachBaseContext()
        │
        │ ← ② Application.onCreate()
        ▼
    Activity.onCreate()
        │
        │ ← ③ 首帧绘制完成（First Frame / TTID）
        ▼
    用户可交互（TTFD，通常紧随首帧）

冷启动总耗时 = ③ - ①
```

#### 3.2 关键实现：首帧时间戳的获取

```kotlin
/**
 * 启动耗时监控。
 *
 * 关键点：
 * 1. 进程启动时间戳必须在 Application 之前获取（用 API 24+ 的 Process.getStartUptimeMillis）
 * 2. 首帧时间用 ViewTreeObserver.OnDrawListener 或 reportFullyDrawn 近似
 */
object StartupTracker {

    /** 进程启动时刻（SystemClock.uptimeMillis 基准） */
    private var processStartUptime: Long = 0L

    /** 首帧绘制完成时刻 */
    @Volatile
    private var firstFrameUptime: Long = 0L

    /** 是否是冷启动（进程之前不存在） */
    @Volatile
    private var isColdStart: Boolean = false

    fun onProcessCreate() {
        processStartUptime = if (Build.VERSION.SDK_INT >= Build.VERSION_CODES.N) {
            // ★ API 24+：系统直接提供进程启动时间，最准确
            Process.getStartUptimeMillis()
        } else {
            // 低版本兜底：Application.attachBaseContext 的时间（略晚于真实启动）
            SystemClock.uptimeMillis()
        }
    }

    /**
     * 注册首帧回调。
     *
     * 注意：必须在 Activity 的 onCreate 之后（此时 View 树已创建）。
     */
    fun registerFirstFrameCallback(activity: Activity, onFirstFrame: () -> Unit) {
        val decorView = activity.window.decorView
        decorView.viewTreeObserver.addOnDrawListener(
            object : ViewTreeObserver.OnDrawListener {
                override fun onDraw() {
                    if (firstFrameUptime == 0L) {
                        firstFrameUptime = SystemClock.uptimeMillis()
                        decorView.viewTreeObserver.removeOnDrawListener(this)
                        onFirstFrame()
                    }
                }
            }
        )
    }

    /** 计算并上报启动指标 */
    fun reportStartup(activity: Activity, isColdStart: Boolean) {
        registerFirstFrameCallback(activity) {
            val ttid = firstFrameUptime - processStartUptime
            val ttf = SystemClock.uptimeMillis() - processStartUptime

            StartupMetrics(
                coldStart = isColdStart,
                ttidMs = ttid,                     // Time To Initial Display
                totalStartupMs = ttf,
                appInitMs = AppInitTracker.getCost(),
                deviceModel = Build.MODEL,
                osVersion = Build.VERSION.RELEASE,
                abi = Build.SUPPORTED_ABIS.first()
            ).also { StartupReporter.report(it) }
        }
    }
}
```

#### 3.3 冷启动 vs 热启动的区分

```kotlin
/** 冷热启动判定 */
object ColdStartDetector {

    private var isColdStart = true

    /**
     * 判断依据：进程是否为新建。
     * ActivityManager.getRunningAppProcesses 的 importance 判断不够准确，
     * 更可靠的方式是记录进程内的静态标记。
     */
    fun markColdStart() {
        isColdStart = true
    }

    fun isColdStart(): Boolean = isColdStart

    /** Activity 首次 onCreate 后置为 false（同一进程内后续启动都是热启动） */
    fun markFirstActivityCreated() {
        isColdStart = false
    }

    /** 热启动耗时（从 onCreate 到首帧） */
    fun reportHotStart(activity: Activity) {
        if (isColdStart()) return
        val start = SystemClock.uptimeMillis()
        StartupTracker.reportStartup(activity, isColdStart = false)
    }
}
```

#### 3.4 冷启动优化的观测：分段耗时

**只看总耗时是不够的**，要知道慢在哪一段：

```kotlin
/** 分段启动耗时采集 */
class StartupPhaseTracker {

    private val marks = LinkedHashMap<String, Long>()

    fun mark(phase: String) {
        marks[phase] = SystemClock.uptimeMillis()
    }

    /** 生成各阶段耗时报告 */
    fun report(): List<PhaseCost> {
        val result = mutableListOf<PhaseCost>()
        var previous = 0L
        for ((name, time) in marks) {
            result.add(PhaseCost(phase = name, costMs = time - previous))
            previous = time
        }
        return result
    }
}
```

```kotlin
// Application 中打点
class MyApplication : Application() {
    private val tracker = StartupPhaseTracker()

    override fun attachBaseContext(base: Context) {
        tracker.mark("attachBaseContext")
        super.attachBaseContext(base)
    }

    override fun onCreate() {
        tracker.mark("application.onCreate")
        super.onCreate()

        // 初始化分阶段打点
        tracker.mark("init-third-party")
        initThirdPartySdk()
        tracker.mark("init-hilt")
        initHilt()
        tracker.mark("init-routes")
        RouteRegistry.registerAll()
        tracker.mark("done")
    }
}
```

**典型分段耗时分布（冷启动 2.5s 的例子）**：

| 阶段 | 耗时 | 优化手段 |
| --- | --- | --- |
| 进程创建 → attachBaseContext | 200ms | 减少 MultiDex（用 Native MultiDex）、优化 so 加载 |
| Application.onCreate 第三方 SDK 初始化 | 800ms | **延迟初始化**（用完再 init）、异步初始化 |
| Hilt / DI 初始化 | 300ms | 延迟到首次使用、减少 eager 的 `@Inject` |
| 首屏 Activity 创建 + inflate | 500ms | ViewBinding 代替反射、减少布局层级、AsyncLayoutInflater |
| 首帧绘制 | 400ms | 减少首屏工作量、数据本地缓存优先 |

### 4. 掉帧与卡顿采集

#### 4.1 Choreographer 方案（兼容所有版本）

```kotlin
/**
 * 基于 Choreographer 的掉帧检测。
 *
 * 原理：Choreographer.postFrameCallback 在每一帧的 vsync 时回调。
 * 两次回调的时间间隔 = 该帧的实际耗时。
 * 理想是 16.67ms（60fps）；> 50ms 视为明显卡顿。
 */
class JankDetector(
    private val onJank: (JankInfo) -> Unit,
    private val slowThresholdMs: Long = 50L,
    private val frozenThresholdMs: Long = 700L
) : Choreographer.FrameCallback {

    private var lastFrameNanos = 0L
    private var running = false

    override fun doFrame(frameTimeNanos: Long) {
        if (lastFrameNanos != 0L) {
            val frameDurationMs = (frameTimeNanos - lastFrameNanos) / 1_000_000

            if (frameDurationMs >= slowThresholdMs) {
                val droppedFrames = (frameDurationMs / 16.67f).toInt() - 1
                onJank(
                    JankInfo(
                        durationMs = frameDurationMs,
                        droppedFrames = droppedFrames,
                        isFrozen = frameDurationMs >= frozenThresholdMs,
                        timestamp = System.currentTimeMillis()
                    )
                )
            }
        }
        lastFrameNanos = frameTimeNanos
        if (running) Choreographer.getInstance().postFrameCallback(this)
    }

    fun start() {
        if (running) return
        running = true
        lastFrameNanos = 0L
        Choreographer.getInstance().postFrameCallback(this)
    }

    fun stop() {
        running = false
        Choreographer.getInstance().removeFrameCallback(this)
    }
}
```

**局限**：只能告诉你"卡了"，不能告诉你"卡在哪"。要定位到具体方法，需要在卡顿发生时抓主线程堆栈。

#### 4.2 FrameMetrics 方案（Android 11+）

```kotlin
/**
 * Android 11+ 官方帧指标采集。
 *
 * FrameMetrics 能拿到每帧的完整分解：
 * - TOTAL_DURATION：整帧耗时
 * - UI_THREAD_DURATION：主线程耗时
 * - RENDER_THREAD_DURATION：RenderThread 耗时
 * - GPU_DURATION：GPU 耗时
 * - COMMAND_ISSUE_DURATION：命令提交耗时
 *
 * 这能直接区分"是主线程慢"还是"是渲染慢"，是定位卡顿根因的关键。
 */
@RequiresApi(Build.VERSION_CODES.R)
class FrameMetricsCollector(
    private val onFrameMetrics: (FrameMetrics) -> Unit
) {

    private val handler = Handler(Looper.getMainLooper())
    private var attachedWindows = mutableSetOf<Window>()

    private val listener = Window.OnFrameMetricsAvailableListener { _, metrics, _ ->
        onFrameMetrics(metrics)
    }

    fun attach(window: Window) {
        window.addOnFrameMetricsAvailableListener(listener, handler)
        attachedWindows.add(window)
    }

    fun detachAll() {
        attachedWindows.forEach { it.removeOnFrameMetricsAvailableListener(listener) }
        attachedWindows.clear()
    }

    companion object {
        /** 提取关键指标 */
        fun extract(metrics: FrameMetrics): FrameBreakdown {
            val total = metrics.getMetric(FrameMetrics.TOTAL_DURATION) / 1_000_000f
            val uiThread = metrics.getMetric(FrameMetrics.UI_THREAD_DURATION) / 1_000_000f
            val renderThread = metrics.getMetric(FrameMetrics.RENDER_THREAD_DURATION) / 1_000_000f
            val gpu = metrics.getMetric(FrameMetrics.GPU_DURATION) / 1_000_000f
            return FrameBreakdown(total, uiThread, renderThread, gpu)
        }
    }
}
```

#### 4.3 卡顿时的堆栈采集

```kotlin
/**
 * 卡顿快照采集：在卡顿发生时抓主线程堆栈。
 *
 * 与 ANR 看门狗同样的思路，但阈值更低（卡顿 50ms 就抓）。
 */
class JankStackCollector {

    private val watchdogThread = HandlerThread("jank-collector").apply { start() }
    private val handler = Handler(watchdogThread.looper)

    fun capture(blockedForMs: Long, callback: (List<StackTraceElement>) -> Unit) {
        handler.post {
            val mainThread = Looper.getMainLooper().thread
            val frames = mainThread.stackTrace
            // 定位业务代码帧（跳过系统帧）
            val appFrames = frames.filter {
                it.className.startsWith("com.example") ||
                    it.className.startsWith("androidx")
            }
            callback(appFrames.ifEmpty { frames.take(20) })
        }
    }
}
```

### 5. 网络监控

```kotlin
/**
 * 网络请求埋点：通过 OkHttp Interceptor 采集。
 *
 * 采集维度：
 * - 总耗时、成功/失败状态码、异常类型
 * - DNS / TLS / 连接 / 首字节 / 下载 各阶段耗时（API 24+ 有 EventListener）
 */
class NetworkMetricsInterceptor : Interceptor {

    override fun intercept(chain: Interceptor.Chain): Response {
        val request = chain.request()
        val start = System.nanoTime()

        try {
            val response = chain.proceed(request)
            val durationMs = (System.nanoTime() - start) / 1_000_000
            NetworkReporter.report(
                NetworkMetric(
                    url = request.url.redact(),       // ★ 脱敏：去掉 query 中的 token
                    method = request.method,
                    durationMs = durationMs,
                    statusCode = response.code,
                    success = response.isSuccessful,
                    requestSize = request.body?.contentLength() ?: 0,
                    responseSize = response.body?.contentLength() ?: 0
                )
            )
            return response
        } catch (e: IOException) {
            val durationMs = (System.nanoTime() - start) / 1_000_000
            NetworkReporter.report(
                NetworkMetric(
                    url = request.url.redact(),
                    method = request.method,
                    durationMs = durationMs,
                    statusCode = -1,
                    success = false,
                    errorType = e.javaClass.simpleName
                )
            )
            throw e
        }
    }
}
```

**分阶段耗时采集（OkHttp EventListener，API 24+ / OkHttp 4.x）**：

```kotlin
class NetworkPhaseEventListener : EventListener() {

    private var callStartNanos = 0L
    private var dnsStart = 0L
    private var dnsEnd = 0L
    private var connectStart = 0L
    private var connectEnd = 0L
    private var tlsStart = 0L
    private var tlsEnd = 0L

    override fun callStart(call: Call) { callStartNanos = System.nanoTime() }

    override fun dnsStart(call: Call, domainName: String) { dnsStart = System.nanoTime() }
    override fun dnsEnd(call: Call, domainName: String, inetAddressList: List<InetAddress>) {
        dnsEnd = System.nanoTime()
    }

    override fun connectStart(call: Call, inetSocketAddress: InetSocketAddress, proxy: Proxy) {
        connectStart = System.nanoTime()
    }
    override fun connectEnd(call: Call, inetSocketAddress: InetSocketAddress, proxy: Proxy, protocol: Protocol?) {
        connectEnd = System.nanoTime()
    }

    override fun secureConnectStart(call: Call) { tlsStart = System.nanoTime() }
    override fun secureConnectEnd(call: Call, handshake: Handshake?) { tlsEnd = System.nanoTime() }

    override fun callEnd(call: Call) {
        val now = System.nanoTime()
        NetworkReporter.reportPhase(
            NetworkPhases(
                totalMs = (now - callStartNanos) / 1_000_000,
                dnsMs = if (dnsEnd > 0) (dnsEnd - dnsStart) / 1_000_000 else 0,
                connectMs = if (connectEnd > 0) (connectEnd - connectStart) / 1_000_000 else 0,
                tlsMs = if (tlsEnd > 0) (tlsEnd - tlsStart) / 1_000_000 else 0
            )
        )
    }
}
```

### 6. 内存与 CPU 采集

```kotlin
/**
 * 内存指标采集器。
 *
 * 采集时机：低频（不要每秒都读，会产生开销），建议 5~10 秒一次，
 * 或者在关键生命周期节点（onTrimMemory、onPause）。
 */
class MemoryMetricsCollector(
    private val context: Context,
    private val onSample: (MemoryMetric) -> Unit
) {

    private val activityManager =
        context.getSystemService(Context.ACTIVITY_SERVICE) as ActivityManager
    private val runtime = Runtime.getRuntime()
    private var lastJavaHeap = 0L

    /** 由 Application 注册，在 onTrimMemory 与周期性采样中调用 */
    fun sample() {
        val javaUsed = runtime.totalMemory() - runtime.freeMemory()
        val javaMax = runtime.maxMemory()
        val nativeAllocated = Debug.getNativeHeapAllocatedSize()
        val nativeTotal = Debug.getNativeHeapSize()

        val memInfo = ActivityManager.MemoryInfo()
        activityManager.getMemoryInfo(memInfo)

        val metric = MemoryMetric(
            timestamp = System.currentTimeMillis(),
            javaHeapUsed = javaUsed,
            javaHeapMax = javaMax,
            javaHeapGrowth = javaUsed - lastJavaHeap,
            nativeHeapAllocated = nativeAllocated,
            nativeHeapTotal = nativeTotal,
            systemAvailable = memInfo.availMem,
            systemTotal = memInfo.totalMem,
            isLowMemory = memInfo.lowMemory,
            pssKb = Debug.getPss()            // ★ PSS 比 Java heap 更能反映真实内存占用
        )
        lastJavaHeap = javaUsed
        onSample(metric)
    }

    /** 监听内存压力 */
    fun registerTrimMemoryListener(callback: (level: Int) -> Unit) {
        // 在 Application.onTrimMemory 中调用
        callback(0)
    }
}
```

**PSS vs Java Heap 的区别**（面试可能追问）：

- **Java Heap**：只是 Dalvik/ART 管理的堆，**不包含** native 内存（Bitmap、SO 库、DirectBuffer）、**不包含** mmap 的资源文件。
- **PSS（Proportional Set Size）**：把进程的内存按比例分摊给系统，**更接近系统视角的真实占用**。`adb shell dumpsys meminfo <pkg>` 看到的就是它。
- **结论**：**监控内存必须看 PSS**，只看 Java Heap 会漏掉 Bitmap 和 native 库的大头。

### 7. 采样策略

**为什么必须采样**：

```
假设：100 万 DAU
  - 每个会话采集 60 个性能指标点
  - 每次上报 500 字节
  → 每天 100万 × 60 × 500B = 30 GB/天
  → 存储成本与带宽成本都不可接受
```

**采样策略设计**：

| 指标类型 | 采样率 | 理由 |
| --- | --- | --- |
| **崩溃 / ANR** | **100%** | 极低频、极重要，绝不能采样 |
| **严重卡顿（冻结帧）** | 100% | 低频且关键 |
| **启动耗时** | **100%**（或按用户抽样） | 每个会话一次，量可控 |
| **普通掉帧** | 10%~30% | 量较大 |
| **网络请求指标** | 1%~5%（失败请求 100%） | 量极大；失败的必须全量 |
| **内存快照** | 1%~5% | 量较大 |
| **CPU 使用率** | 1% | 量较大且信息密度低 |
| **详细堆栈（卡顿快照）** | **卡顿事件的 1%~10%** | 单次数据量大（堆栈可能几十 KB） |

**采样实现的两种策略**：

```kotlin
/** 策略 1：客户端固定采样（简单，但可能不均匀） */
object Sampler {
    fun shouldSample(rate: Double): Boolean = Random.nextDouble() < rate
}

/** 策略 2：服务端按会话抽样（更均衡，推荐） */
// 客户端上报 sessionId，服务端决定这个会话是否采全量数据
// 优点：同一会话的数据是完整的，可以关联分析；且无需客户端判断
```

**策略 3：按设备/用户哈希采样（避免随机波动）**：

```kotlin
/**
 * 确定性采样：同一个用户/设备的采样结果稳定。
 *
 * 好处：
 * 1. 数据分布更均匀（不是随机波动）
 * 2. 同一个用户的多次会话行为一致，可以做趋势分析
 */
object DeterministicSampler {

    /**
     * @param key 通常用 deviceId 或 userId
     * @param rate 采样率，如 0.05 表示 5%
     */
    fun shouldSample(key: String, rate: Double): Boolean {
        // 取 MD5 前 4 字节当作 32 位整数，映射到 [0, 1)
        val hash = MessageDigest.getInstance("MD5").digest(key.toByteArray())
        val bucket = ((hash[0].toInt() and 0xFF) shl 24 or
                (hash[1].toInt() and 0xFF) shl 16 or
                (hash[2].toInt() and 0xFF) shl 8 or
                (hash[3].toInt() and 0xFF)) and 0xFFFFFFFFL
        val normalized = bucket.toDouble() / 0xFFFFFFFFL
        return normalized < rate
    }
}
```

**重要原则**：

> **采样必须与"重要度"绑定，而不能只看"频率"。**
> 崩溃、ANR、冻结帧这类"低频高价值"的事件**永远不采样**；
> 网络请求、内存快照这类"高频低单价"的指标才采样。
> 这是 APM 系统的基本设计原则。

### 8. 自研 vs 第三方 APM

| 方案 | 代表 | 优点 | 缺点 |
| --- | --- | --- | --- |
| **第三方 SaaS** | Firebase Performance Monitoring、Datadog、New Relic、火山引擎 APM、阿里云移动监控 | 开箱即用、看板完善、跨端支持 | 数据出境合规问题、定制受限、按量付费成本 |
| **自研** | 大型公司自建 | 完全可控、可深度定制、与内部系统打通 | 成本高（需要 2~5 人年）、周期长、稳定性要自己保证 |
| **混合** | 自研采集 + 第三方看板/存储 | 兼顾 | 集成复杂度 |

**自研的最小可行架构**：

```
┌──────────────────────────────────────────────────────────┐
│  Client SDK（Android）                                     │
│  ├─ 采集层：启动/帧率/网络/内存/崩溃                        │
│  ├─ 采样层：按指标类型应用不同采样率                        │
│  ├─ 缓冲层：本地持久化队列（进程被杀不丢）                   │
│  └─ 上报层：批量 + 压缩 + 失败重试                        │
└───────────────────────┬──────────────────────────────────┘
                        │ HTTPS + protobuf/gzip
                        ▼
┌──────────────────────────────────────────────────────────┐
│  Server                                                     │
│  ├─ 接入层：鉴权、限流、协议解析                           │
│  ├─ 存储层：ClickHouse（指标）/ HBase（明细）/ ES（日志）    │
│  ├─ 计算层：实时聚合（P99 指标）+ 离线分析                  │
│  └─ 应用层：看板（Grafana）+ 告警（Prometheus/AlertManager）│
└──────────────────────────────────────────────────────────┘
```

**技术选型建议（指标存储）**：

| 方案 | 适用 | 说明 |
| --- | --- | --- |
| **Prometheus + Grafana** | 指标（Counter/Gauge/Histogram） | 生态好，但高基数标签（userId）会成为灾难 |
| **ClickHouse** | 海量时序明细分析 | **APM 明细数据的最佳选择**，压缩比高、聚合快 |
| **InfluxDB** | 时序 | 简单，但写入性能与基数控制弱于 ClickHouse |
| **Sentry** | 崩溃 + 性能一体 | 错误追踪体验好，自建也可以（开源） |

**关键指标**：P99 延迟不适合存在 Prometheus 里（高基数），更适合存在 ClickHouse 里做实时聚合。

#### 9.1 看板设计的三层结构

#### 9.2 告警策略

```yaml
# 告警规则示例（Prometheus 风格）
groups:
  - name: app-health
    rules:
      # 崩溃率突增（相比基线翻倍）
      - alert: CrashRateSpike
        expr: |
          sum(rate(app_crashes_total[15m])) by (version)
          / sum(rate(app_sessions_total[15m])) by (version) > 0.01
        for: 10m
        labels:
          severity: critical
        annotations:
          summary: "崩溃率超过 1%（版本 {{ $labels.version }}）"
          description: "过去 15 分钟崩溃率为 {{ $value | humanizePercentage }}，已自动暂停该版本的灰度发布"

      # 启动耗时劣化（相比上一版本增加 20%）
      - alert: StartupDegradation
        expr: |
          histogram_quantile(0.9, sum(rate(app_startup_duration_ms_bucket[1h])) by (le, version))
          > histogram_quantile(0.9, sum(rate(app_startup_duration_ms_bucket[1h])) by (le, baseline_version))) * 1.2
        for: 30m
        labels:
          severity: warning

      # ANR 率突增
      - alert: AnrRateHigh
        expr: |
          sum(rate(app_anrs_total[10m])) / sum(rate(app_sessions_total[10m])) > 0.01
        for: 5m
        labels:
          severity: critical
```

**告警设计的四个原则**：

1. **告警必须可执行**：每条告警要能回答"收到后该做什么"。
2. **告警要有归属**：每条告警指定责任团队与处理文档链接。
3. **避免告警疲劳**：一天超过 10 条的告警等于没有告警。
4. **分级**：P0（阻断发版，需要立即响应）/ P1（当天处理）/ P2（进 backlog）。
5. **与灰度联动**：崩溃率超阈值时**自动暂停灰度**（见 [[../灰度发布与监控]]）。

### 10. 性能数据的隐私与合规

- **设备标识**：用自生成的 `installationId`（首次启动生成并存储），**不用 IMEI/IMSI/MAC**（法律上已被禁止采集）。
- **位置信息**：不上报 GPS 坐标。
- **用户标识**：用 `userId` 的哈希，且提供"退出登录时清除"的能力。
- **合规**：符合《个人信息保护法》与 GDPR 的最小化原则。

```kotlin
package com.example.core.apm

/**
 * APM 客户端门面：统一采集 + 采样 + 缓冲 + 上报。
 */
object PerformanceMonitor {

    private val collectors = mutableListOf<MetricsCollector>()
    private lateinit var reporter: MetricsReporter
    private lateinit var sampler: PerformanceSampler

    fun install(
        reporter: MetricsReporter,
        sampler: PerformanceSampler
    ) {
        this.reporter = reporter
        this.sampler = sampler
    }

    fun addCollector(collector: MetricsCollector) {
        collectors.add(collector)
    }

    /** 采集一个性能事件（自动采样 + 缓冲） */
    fun track(event: PerformanceEvent) {
        if (!sampler.shouldCollect(event)) return
        collectors.forEach { it.collect(event) }
    }

    /** 周期性采集（内存、CPU） */
    fun startPeriodicSampling(intervalMs: Long = 30_000) {
        collectors.filterIsInstance<PeriodicCollector>().forEach { it.start(intervalMs) }
    }
}

sealed interface PerformanceEvent {
    val timestamp: Long get() = System.currentTimeMillis()

    data class Startup(val metrics: StartupMetrics) : PerformanceEvent
    data class Jank(val info: JankInfo) : PerformanceEvent
    data class Network(val metric: NetworkMetric) : PerformanceEvent
    data class Memory(val metric: MemoryMetric) : PerformanceEvent
    data class Anr(val info: AnrInfo) : PerformanceEvent
}

/** 采集器接口 */
interface MetricsCollector {
    fun collect(event: PerformanceEvent)
}

/** 周期采集器 */
interface PeriodicCollector : MetricsCollector {
```

### 3. 采样策略实现

```kotlin
package com.example.core.apm

import java.security.MessageDigest
import kotlin.random.Random

/**
 * 性能数据采样器。
 *
 * 核心原则：
 * 1. 崩溃 / ANR / 冻结帧 → 100%（低频高价值）
 * 2. 网络 / 内存 / CPU → 低采样率（高频低单价）
 * 3. 采样必须"确定性"（同一用户稳定命中），避免数据波动
 */
class PerformanceSampler(
    /** 客户端固定采样率（作为服务端末端的兜底） */
    private val fallbackRates: Map<MetricType, Double>
) {

    private val deterministicSampler = DeterministicSampler()

    fun shouldCollect(event: PerformanceEvent): Boolean {
        val type = event.type()
        // ★ 关键事件永不采样
        if (type in ALWAYS_COLLECT) return true

        val rate = fallbackRates[type] ?: DEFAULT_RATE
        return deterministicSampler.shouldSample(sampleKey(), rate)
    }

    /** 采样键：优先用 userId（没有则用 installationId） */
    private fun sampleKey(): String =
        SessionManager.currentUserId() ?: SessionManager.installationId()

    private companion object {
        val ALWAYS_COLLECT = setOf(
            MetricType.CRASH,
            MetricType.ANR,
            MetricType.FROZEN_FRAME
        )
        const val DEFAULT_RATE = 0.05
    }
}

/** 指标类型 */
enum class MetricType {
    CRASH, ANR, FROZEN_FRAME, SLOW_FRAME,
    STARTUP, NETWORK, MEMORY, CPU, DETAILED_STACK
}

/**
 * 确定性采样器：同一 key 的采样结果稳定。
 *
 * 使用 MD5 哈希映射到 [0, 1) 区间，保证数据分布均匀
 * （纯随机采样在用户量小的时候波动很大）。
 */
object DeterministicSampler {

    fun shouldSample(key: String, rate: Double): Boolean {
        if (rate >= 1.0) return true
        if (rate <= 0.0) return false

        val digest = MessageDigest.getInstance("MD5").digest(key.toByteArray())
        val value = ((digest[0].toInt() and 0xFF) shl 24) or
                ((digest[1].toInt() and 0xFF) shl 16) or
                ((digest[2].toInt() and 0xFF) shl 8) or
                (digest[3].toInt() and 0xFF)
        val normalized = (value.toLong() and 0xFFFFFFFFL).toDouble() / 0xFFFFFFFFL
        return normalized < rate
    }
}
```

### 4. 本地缓冲与批量上报

```kotlin
package com.example.core.apm

import java.io.File
import java.util.concurrent.LinkedBlockingQueue
import java.util.concurrent.TimeUnit

/**
 * 性能数据上报器：本地缓冲 + 批量 + 失败重试。
 *
 * 为什么要本地缓冲：
 * 1. 网络不可用时不丢数据
 * 2. 进程被杀时不丢数据（下次启动继续上传）
 * 3. 批量上传减少请求数
 */
class BufferedMetricsReporter(
    private val context: android.content.Context,
    private val uploader: MetricsUploader,
    private val batchSize: Int = 50,
    private val flushIntervalMs: Long = 60_000
) : MetricsReporter {

    private val queue = LinkedBlockingQueue<MetricsRecord>(MAX_QUEUE_SIZE)
    private val storageFile = File(context.filesDir, "apm/metrics.buffer")
    private val executor = java.util.concurrent.Executors.newSingleThreadExecutor { r ->
        Thread(r, "apm-reporter").apply { isDaemon = true }
    }

    init {
        // 启动时把上次未上传的数据读回来
        executor.execute { restoreFromDisk() }
        // 定时 flush
        val scheduler = java.util.concurrent.Executors.newSingleThreadScheduledExecutor { r ->
            Thread(r, "apm-flusher").apply { isDaemon = true }
        }
        scheduler.scheduleWithFixedDelay(
            { flush() }, flushIntervalMs, flushIntervalMs, TimeUnit.MILLISECONDS
        )
    }

    override fun report(record: MetricsRecord) {
        // 队列满时丢弃最旧的（性能数据可以丢，崩溃数据不行）
        if (queue.size >= MAX_QUEUE_SIZE) queue.poll()
        queue.offer(record)
        if (queue.size >= batchSize) flush()
    }

    private fun flush() {
        val batch = mutableListOf<MetricsRecord>()
        queue.drainTo(batch, batchSize)
        if (batch.isEmpty()) return

        executor.execute {
            runCatching { uploader.upload(batch) }
                .onSuccess { }
                .onFailure {
                    // 失败则写回磁盘，下次启动再试
                    persistToDisk(batch)
                }
        }
    }

    private fun persistToDisk(records: List<MetricsRecord>) {
        runCatching {
            storageFile.parentFile?.mkdirs()
            storageFile.appendText(records.joinToString("\n") { it.toJson() } + "\n")
        }
    }

    private fun restoreFromDisk() {
        runCatching {
            if (!storageFile.exists()) return
            storageFile.readLines().filter { it.isNotBlank() }.forEach { line ->
                queue.offer(MetricsRecord.fromJson(line))
            }
            storageFile.delete()
        }
    }

    companion object {
        private const val MAX_QUEUE_SIZE = 2000
    }
}
```

### 5. 启动优化的完整实践

```kotlin
package com.example.core.startup

/**
 * 延迟初始化框架：把非首屏必需的初始化推迟到真正需要时。
 *
 * 常见做法：
 * 1. 主线程只初始化"首屏必需"的部分
 * 2. 其他 SDK 用 IdleHandler / 协程后台线程初始化
 * 3. 极关键的（如路由表）可以放子线程但要同步等待
 */
class LazyInitializer(private val app: android.app.Application) {

    private val pendingTasks = mutableListOf<() -> Unit>()
    private val lock = Any()

    /** 注册延迟任务 */
    fun defer(name: String, task: () -> Unit) {
        synchronized(lock) { pendingTasks.add(task) }
    }

    /** 在主线程空闲时执行（Android 的 IdleHandler） */
    fun runWhenIdle() {
        val handler = android.os.Handler(android.os.Looper.getMainLooper())
        handler.post {
            android.os.MessageQueue.IdleHandler {
                val tasks = synchronized(lock) { pendingTasks.toList().also { pendingTasks.clear() } }
                tasks.forEach { runCatching { it() } }
                false   // 返回 false 表示不重复执行
            }
        }
    }

    /** 在子线程执行（不阻塞启动） */
    fun runInBackground(tasks: List<() -> Unit>) {
        Thread({
            tasks.forEach { runCatching { it() } }
        }, "lazy-init").apply { isDaemon = true }.start()
    }
}
```

```kotlin
class MyApplication : Application() {

    private val lazyInit by lazy { LazyInitializer(this) }

    override fun onCreate() {

        // ===== 首屏必需的同步初始化 =====

        ))

        // 主线程空闲后执行剩余任务
        lazyInit.runWhenIdle()
    }
}
```

## 常见问题 / 面试要点

**读者问：线上怎么监控 App 性能？采集多少用户数据合适？**

**AI答：**

1. **采集什么（按优先级）**：
   - **P0（必做）**：崩溃率、ANR 率、启动耗时（TTID）。这三个是**用户感知最直接**的，也是 Google Vitals 的核心。
   - **P1（重要）**：掉帧率/卡顿率、网络成功率与耗时分布、内存（PSS）。
   - **P2（可选）**：CPU 占用、流量、磁盘 IO、电池温度。
2. **采样率怎么定（这是核心问题）**：
   - **原则：按"事件重要度"分级采样，不按"频率"一刀切。**
   - **崩溃 / ANR / 冻结帧（≥700ms）→ 100% 采集**。这些事件量本来就小（崩溃率通常 0.1%~1%），全量采集的成本可以忽略，且**一条都不能丢**。
   - **启动耗时 → 100%**（每会话一次，量可控）。启动是用户感知最强的指标。
   - **普通掉帧 → 10%~30%**。量较大但信息密度高。
   - **网络请求指标 → 1%~5%**，但**失败的请求 100%**（失败率低，且失败样本比成功样本有价值得多）。
   - **内存 / CPU → 1%~5%**。
   - **详细堆栈快照 → 卡顿事件的 1%~10%**（单次数据量大）。
3. **用什么方式采样**：
   - **推荐"服务端按会话抽样"**：客户端把 sessionId 一起上报，**服务端决定是否采全量**。好处是①同一会话的数据完整可关联；②不需要客户端做判断逻辑；③可以随时调整采样率而不发版。
   - **客户端固定采样**作为兜底。
   - **采样必须确定性**（同一用户稳定命中），用 `MD5(userId) % 10000 < rate * 10000` 这类哈希分桶，避免纯随机的分布波动。
4. **量级估算**（面试常考）：
   ```
   100 万 DAU，日活用户平均 3 个会话
   启动指标：300 万条 × 200B = 600 MB/天
   掉帧（30% 采样）：假设每会话 20 次卡顿 → 300万 × 20 × 30% = 1800万条 → 太大了
   → 所以掉帧必须低采样 + 客户端先聚合（只上报"卡顿次数"而不是每次卡顿明细）
   ```
   **关键技巧**：**客户端先聚合再上报**。比如"每个会话只上报卡顿总次数 + 最严重的一次的堆栈"，数据量能降两个数量级，信息量几乎不损失。
5. **面试话术**："我的采样原则是**低频高价值的事件 100% 采集，高频低单价的事件低采样 + 客户端聚合**。启动和崩溃必须全量；掉帧和内存要采样，并且客户端先做会话级聚合再上报——这样能把数据量降两个数量级，同时保留关键信息。"

---

**读者问：启动耗时怎么优化？怎么定位启动慢在哪？**

**AI答：**

1. **先分清冷启动和热启动**：
   - **冷启动**：进程不存在 → Application 创建 → Activity 创建 → 首帧。
   - **热启动**：进程存在 → Activity 重建（`onRestart` → `onStart` → `onResume`）。
   - **热恢复**：进程被系统回收但任务栈保留 → 从 `onCreate` 重来（Android 10+ 后台启动限制会让 App 冷启动）。
2. **冷启动的四个耗时来源**：
   | 阶段 | 典型耗时 | 优化方向 |
   | --- | --- | --- |
   | **进程创建 → attachBaseContext** | 100~300ms | MultiDex（用 Native MultiDex）、减少 so 库数量、优化 `dexopt` |
   | **Application.onCreate** | 300~1500ms | **第三方 SDK 延迟初始化**、异步初始化、减少静态初始化 |
   | **Activity 创建 + 布局膨胀** | 200~500ms | ViewBinding（代替反射 findViewById）、减少布局层级、AsyncLayoutInflater |
   | **首帧绘制** | 100~500ms | 减少首屏 UI 复杂度、数据先渲染骨架再填充 |
3. **定位手段**：
   - **分段打点**：`attachBaseContext` / `onCreate` / 每个 SDK 初始化 / `Activity.onCreate` / 首帧。用 `SystemClock.uptimeMillis()` 打点，生成耗时分布。
   - **Traceview / Perfetto / systrace**：看主线程时间线。
   - **Android Studio Profiler 的 Startup Inspector**：录制启动过程，看每个阶段的耗时与调用栈。
   - **线上 APM**：收集 TTID 分布 + 分段耗时，**这是唯一能看到真实设备分布的方式**。
4. **核心优化手段**：
   - **延迟初始化**（最大的收益点）：
     ```kotlin
     // ❌ 所有 SDK 都在 onCreate 同步初始化
     override fun onCreate() {
         AnalyticsSDK.init(this)
         PushSDK.init(this)
         ShareSDK.init(this)
         MapSDK.init(this)
         // ... 一堆
     }

     // ✅ 首屏必需的同步做，其余延后
     override fun onCreate() {
         // 必需：日志、崩溃上报、路由
         StartupTracker.onProcessCreate()
         // 其余：主线程空闲时 或 子线程
         lazyInit.defer("analytics") { AnalyticsSDK.init(this) }
         lazyInit.runInBackground(listOf({ MapSDK.init(this) }))
     }
     ```
   - **首屏数据本地优先**：先渲染本地缓存/骨架屏，**不等网络**。
   - **减少布局层级**：ConstraintLayout 替代多层 LinearLayout；Compose 下减少不必要的重组。
   - **ViewBinding**：`ActivityMainBinding.inflate()` 比 `findViewById` 快。
   - **App Bundle 优化**：按语言/密度拆分 APK（见 [[../构建与打包优化/构建加速]]）。
5. **效果指标**：Google Vitals 的启动耗时"良好"标准是 **TTID ≤ 2s**（用户点击到首帧）。国内大厂的目标通常是 **P90 ≤ 1.5s**。
6. **面试话术**："启动优化我的思路是**先分段打点定位，再对症下药**。经验上 60% 以上的启动时间花在 `Application.onCreate` 里的第三方 SDK 初始化上，所以**延迟初始化**是收益最大的手段。其次是首屏不要等网络。衡量指标用 TTID 的 P90，而不是平均值——平均值会被低端机拉高但用户体感差的是 P90。"

**读者问：怎么线上监控掉帧/卡顿？采样率怎么定？会不会影响性能？**

**AI答：**

1. **检测原理**：
   - **Choreographer.postFrameCallback**：每帧回调，计算两次间隔。> 50ms = 慢帧，≥ 700ms = 冻结帧。**兼容所有版本**。
   - **FrameMetrics（Android 11+）**：官方 API，能拿到每帧的分解（UI 线程 / RenderThread / GPU），**能直接定位瓶颈**。
   - **主线程堆栈快照**：卡顿发生时在后台线程抓主线程栈，定位"卡在哪"。
2. **怎么定位"卡在哪"（关键）**：
   - 卡顿发生时**主线程被阻塞**，抓堆栈要在**另一个线程**做。
   - 抓到的栈顶可能是 `Looper.loop()`（正常），要**定位栈中第一个业务代码帧**。
   - **Android 11+ 建议用 `ApplicationExitInfo`**：系统判定的 ANR 有官方的 trace 文件（需要 `GET_TASKS` 权限，是系统签名权限，普通 App 拿不到全部，但可以通过 `adb` 在测试设备上取）。
3. **采样率**：
   - **卡顿事件本身**：建议 **100% 计数 + 低比例采堆栈**。
     - 计数（"这个会话卡了 37 次"）→ 100% 上报，数据量小。
     - 堆栈（"这 37 次里最严重的 3 次的堆栈"）→ 客户端只保留最严重的 N 次，或按 10% 采样。
   - **这是最重要的优化技巧**：**客户端先聚合**。
4. **性能影响**：
   - `Choreographer.postFrameCallback` 本身开销极小（每帧一次回调）。
   - **抓堆栈才是开销大的操作**（约 1~5ms），所以必须：
     - 只在超过阈值时才抓。
     - 在后台线程抓（不阻塞主线程）。
     - **去重**（同一堆栈 30 秒内不重复抓）。
   - 上报走异步队列，批量发送。
5. **帧率 vs 卡顿率的口径**：
   - **FPS 平均值**意义不大（用户感知的是"最低帧率"和"卡顿次数"）。
   - 更好的指标：**"慢帧率"**（帧耗时 > 50ms 的帧占比）和**"冻结帧率"**。
   - Google Vitals 的定义就是**慢帧占比**和**冻结帧占比**，不是 FPS。
6. **面试话术**："掉帧监控我用 `Choreographer` 做通用检测，Android 11+ 用 `FrameMetrics` 拿帧分解来定位瓶颈是主线程还是渲染还是 GPU。采样上我坚持**客户端先聚合**：卡顿次数 100% 上报，堆栈只上报最严重的几次或按比例采样——这样数据量能降两个数量级。抓堆栈一定要在后台线程做，并且做去重，否则监控本身就会造成卡顿。"

**读者问：自研 APM 和用第三方 SDK 怎么选？**

**AI答：**

1. **选型维度**：

| 维度 | 自研 | 第三方 |
| --- | --- | --- |
| **开发成本** | 高（2~5 人年：客户端 SDK + 接入层 + 存储 + 看板 + 告警 + 值班） | 低（接入即可） |
| **定制能力** | 完全可控 | 受限于 SDK 提供的指标 |
| **数据合规** | 数据不出境（重要！） | 需评估数据出境（Google Analytics 在国内不合规） |
| **稳定性责任** | 自己扛 | 厂商扛 |
| **成本结构** | 固定人力成本 | 按量付费（DAU 大时很贵） |
| **跨端支持** | 需自己做 | 通常支持 iOS/小程序/Web |
| **上手速度** | 慢（3~6 个月） | 快（1 周） |

2. **决策建议**：
   - **DAU < 50 万、没有出海业务** → **用第三方**（Firebase/火山引擎 APM/阿里云移动监控）。自研的 ROI 算不过来。
   - **DAU > 500 万、有出海合规要求、需要与内部系统深度打通** → **自研或混合**。
   - **中间状态** → **混合**：客户端自研采集（灵活），存储与看板用 ClickHouse + Grafana（成本低）。
3. **自研的最小可行团队与周期**：
   - **2~3 人**：客户端 SDK + 简单上报 + ClickHouse 存储 + Grafana 看板。**约 2~3 个月**。
   - **完整版**（含告警、实时聚合、多端）：**4~6 人 × 6 个月**。
4. **无论选哪个，这三件事都要做**：
   - **统一的数据模型**（不要各家 SDK 各自定义字段）。
   - **统一的采样策略**。
   - **统一的告警与发布流程联动**（见 [[../灰度发布与监控]]）。
5. **面试话术**："我的判断标准是**规模 + 合规**。50 万 DAU 以内用第三方，500 万以上或涉及数据出境合规就值得自研。自研最大的坑不是技术，而是**它是一个长期运维的基建**——看板没人维护、告警没人看、数据质量慢慢腐烂。所以如果决定自研，我会优先保证'**崩溃率 + 启动耗时 + ANR**'这三件事的看板足够好，再逐步加维度。"

**读者问：APM 采集的数据会不会有隐私风险？指标怎么设计才不泄露用户信息？**

**AI答：**

1. **原则：最小化采集 + 假名化 + 可删除**。
2. **绝对不能采集的**：
   - **IMEI / IMSI / MAC / Android ID**（法律上已被禁止采集——IMEI 是设备唯一标识，Google Play 与国内商店都会检查）。
   - **精确 GPS 坐标**。
   - **真实姓名、身份证、银行卡**。
   - **聊天内容、相册内容**。
3. **应该使用的替代标识**：
   - **installationId**：首次启动时用 `UUID.randomUUID()` 生成，存 SharedPreferences，卸载即清除。**这是安装级标识，不是设备级**。
   - **sessionId**：每次冷启动生成一个新的 UUID，30 分钟无操作视为新会话。
   - **userId（哈希后）**：如果需要关联到用户，用 `SHA-256(userId + 盐)`，且提供"退出登录即清除"的逻辑。
4. **URL 脱敏（高频遗漏点）**：
   ```kotlin
   /** HTTP URL 里的 query 参数常常带 token、用户 ID */
   fun HttpUrl.redact(): String {
       val query = queryParameterNames.fold(queryParameterNames.size) { acc, _ -> acc }
       // 保留路径，移除全部 query
       return "$scheme://$host:$port$encodedPath?<redacted>"
   }
   ```
   **更好的做法**：把 API 路径映射为**业务名**上报（`/api/v1/user/profile` → `user.profile`），既脱敏又便于聚合分析。
5. **聚合而非明细**：
   - 上报"设备型号 + OS 版本 + 启动耗时"是聚合数据，**不构成个人信息**。
   - 上报"某用户看了某条内容"就可能构成个人信息 → **埋点要有明确的目的与最小字段**。
6. **合规动作**：
   - **隐私政策**要说明采集哪些数据、用途、保留期。
   - **数据保留期**：性能明细数据保留 30~90 天，聚合数据保留 1 年。
   - **用户可见**：提供"清除我的数据"的入口。
   - **数据存储地**：国内业务的数据必须存在境内（这是自研相对第三方最大的优势）。
7. **面试话术**："APM 的隐私风险主要来自**'标识 + 明细'的组合**。我的设计是：**只用 installationId 和 sessionId，不用任何设备硬件标识**；URL 上报前映射成业务名而不是原始路径；用户相关字段全部哈希；性能明细 30 天过期、聚合数据 1 年。国内业务还有一条硬约束——**数据必须存境内**，这也是我们选择自研存储的原因之一。"

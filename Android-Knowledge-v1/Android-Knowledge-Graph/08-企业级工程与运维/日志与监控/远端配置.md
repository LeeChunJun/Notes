# 远端配置

## 一句话定义

远端配置（Remote Config）是一套"**服务端下发配置、客户端动态读取**"的基础设施，让运营和开发能在**不发版**的情况下调整 App 的行为——开关、参数、文案、阈值、兜底策略。它是灰度发布、功能开关（Feature Flag）、A/B 实验、线上降级、紧急止血的**公共底座**。

面试开场：**"远端配置的价值是'**把发版从唯一手段变成最后手段**'。当一个功能出了问题，你能秒级关掉它，而不用等应用商店审核——这是线上事故处理里最重要的能力。"**

## 核心原理

### 1. 远端配置要解决的问题

```
传统发布流程的问题：
  代码改动 → 打包 → 审核（数小时~数天）→ 上架 → 用户升级（数小时~数周）→ 生效
  总延迟：3 天 ~ 4 周

远端配置：
  服务端改配置 → 客户端下次拉取生效
  总延迟：秒级 ~ 分钟级（取决于拉取时机）
```

**能做什么**：

| 场景 | 例子 | 效果 |
| --- | --- | --- |
| **功能开关** | 新功能一键关闭 | 出问题时秒级止血 |
| **参数调整** | 首页推荐条数从 5 改成 3 | 不用发版 |
| **文案下发** | 活动 banner 文案 | 运营改文案不发版 |
| **降级策略** | 接口超时改成走缓存、关闭第三方 SDK | 第三方服务挂了时的兜底 |
| **限流阈值** | 限流阈值动态调整 | 应对突发流量 |
| **环境切换** | 指向预发环境 | 测试 |
| **A/B 实验分组** | 实验参数 + 分组 | 实验 |
| **强制升级提示** | 最低版本号 | 老版本强制提示升级 |
| **服务器时间校准** | 时间偏移 | 修正本地时间不准 |

**不能做什么（边界）**：

- ❌ **不能改变代码逻辑结构**（配置不是代码）。
- ❌ **不能替代热修复**（见 [[../热修复与动态化]]）——配置改不了已经打包的字节码。
- ❌ **不能下发敏感密钥**（客户端能解密的密钥等于没有密钥；见后文安全章节）。
- ❌ **不能保证实时**（受拉取时机限制）。

### 3. 核心设计：默认值、缓存、兜底

**这是远端配置最关键的三件套**，任何一条做不到，这个系统就不可靠：

#### 3.1 默认值（Default Value）——代码里的兜底

```kotlin
// ✅ 正确：每个配置项都有代码内的默认值
object ConfigKeys {
    const val HOME_RECOMMEND_COUNT = "home_recommend_count"
    const val PAYMENT_TIMEOUT_SECONDS = "payment_timeout_seconds"
    const val NEW_CHECKOUT_ENABLED = "new_checkout_enabled"
    const val MAINTENANCE_MODE = "maintenance_mode"
    const val HOME_BANNER_TEXT = "home_banner_text"
}

/** 读取入口 */
class RemoteConfig(private val store: ConfigStore) {

    fun getInt(key: String, default: Int): Int = store.getInt(key, default)

    fun getString(key: String, default: String): String = store.getString(key, default)

    fun getBoolean(key: String, default: Boolean): Boolean = store.getBoolean(key, default)

    /** 复杂配置：JSON 反序列化，失败时用默认 */
    inline fun <reified T> getObject(key: String, default: T): T {
        val json = store.getString(key, "") ?: return default
        if (json.isBlank()) return default
        return runCatching { Json.decodeFromString<T>(json) }.getOrDefault(default)
    }
}
```

**为什么默认值必须写在代码里**：
1. **首次安装**时还没拉过配置 → 只有默认值。
2. **拉取失败**时（断网、服务端故障）→ 只能用默认值。
3. **配置被删除**时 → 回落到默认值。
4. **新版本发布后**，老版本 App 没有新配置项 → 用默认值（**向后兼容的关键**）。

> **重要原则**：**默认值要保守**。默认开启新功能 = 风险；默认关闭新功能 = 安全。同理，默认超时时间要保守（宁可保守也不要让线上请求堆积）。

#### 3.2 本地缓存——稳定性的保证

```kotlin
/**
 * 配置存储：内存快照 + DataStore 持久化。
 *
 * 读路径：内存 → DataStore（同步缓存）→ 默认值
 * ★ 全程不做网络 IO，永远不会阻塞业务
 */
class ConfigStore(private val dataStore: DataStore<Preferences>) {

    /** 内存快照：所有读取都走这里（纳秒级，无 IO） */
    @Volatile
    private var snapshot: ConfigSnapshot = ConfigSnapshot.EMPTY

    /** 初始化：从本地持久化加载到内存 */
    suspend fun restore() {
        snapshot = dataStore.readConfigSnapshot() ?: ConfigSnapshot.EMPTY
    }

    /** 获取当前快照（同步） */
    fun current(): ConfigSnapshot = snapshot

    /**
     * 应用新配置：先写磁盘，再更新内存。
     *
     * 顺序很重要：先落盘（保证一致性），再更新内存（保证可见性）。
     */
    suspend fun apply(newSnapshot: ConfigSnapshot) {
        dataStore.writeConfigSnapshot(newSnapshot)
        snapshot = newSnapshot
        notifyListeners(newSnapshot)
    }

    // 类型安全的读取
    fun getInt(key: String, default: Int): Int = snapshot.ints[key] ?: default
    fun getString(key: String, default: String): String = snapshot.strings[key] ?: default
    fun getBoolean(key: String, default: Boolean): Boolean = snapshot.booleans[key] ?: default
    fun getLong(key: String, default: Long): Long = snapshot.longs[key] ?: default
}
```

**为什么必须有本地缓存**：
- 用户在**弱网/断网/地铁/电梯**里打开 App，必须能正常工作。
- 配置服务挂了不能让整个 App 不可用——**配置服务是"增强"不是"依赖"**。
- 冷启动时如果每次都等网络，用户会看到白屏或功能不可用。

#### 3.3 兜底策略——降级链路

```
读取配置的优先级：
  ① 内存中的最新快照（可能来自刚才的拉取）
  ② 本地持久化的最后一次成功配置（离线可用）
  ③ 代码内的默认值（首次安装 / 配置从未成功拉取过）
```

### 4. 拉取时机（Trigger）

| 时机 | 说明 | 优点 | 缺点 |
| --- | --- | --- | --- |
| **冷启动时** | Application 中异步拉取 | 保证首屏之后配置是最新的 | 首屏用的是默认值/缓存 |
| **每次进入前台** | `onStart` / `ProcessLifecycleOwner` | 用户活跃时配置最新 | 频繁切前台会拉很多次 |
| **定时轮询** | 每 30 分钟 / 1 小时 | 覆盖后台场景 | 耗电、耗流量 |
| **收到推送时** | 推送消息里带配置版本号，App 被唤起时检查 | **最实时**，且不额外耗电 | 需要推送通道 |
| **手动刷新** | 用户下拉刷新 | 用户可感知 | 依赖用户操作 |
| **关键路径按需** | 进入支付页时才拉 | 按需 | 延迟 |

**推荐的组合**：

```kotlin
/**
 * 拉取时机协调器。
 *
 * 策略：
 * 1. 冷启动：延迟到首帧之后拉（不阻塞启动）
 * 2. 每次进入前台：如果距上次拉取超过 N 分钟才拉
 * 3. 关键业务节点（支付、下单）：同步检查版本号
 * 4. 推送唤醒：收到推送立即检查
 */
class ConfigFetchCoordinator(
    private val api: ConfigApi,
    private val store: ConfigStore,
    private val minIntervalMs: Long = 5 * 60 * 1000
) {

    private val lastFetchTime = AtomicLong(0)
    private val fetching = AtomicBoolean(false)

    /** 应用启动后调用：延迟拉取，不阻塞冷启动 */
    fun scheduleStartupFetch() {
        // 延迟到首帧之后 + 一个小延时，避开启动高峰
        mainHandler.postDelayed({ fetch(force = false) }, 3000)
    }

    /** 进入前台时调用 */
    fun onForeground() {
        fetch(force = false)
    }

    /** 关键路径调用：检查是否有新版本（只传版本号，流量小） */
    suspend fun checkForUpdate(): Boolean {
        val remoteVersion = api.fetchVersion()
        return if (remoteVersion > store.current().version) {
            fetch(force = true)
            true
        } else {
            false
        }
    }

    /** 推送回调：立即拉取 */
    fun onPushReceived() {
        fetch(force = true)
    }

    private fun fetch(force: Boolean) {
        val now = System.currentTimeMillis()
        if (!force && now - lastFetchTime.get() < minIntervalMs) return
        if (!fetching.compareAndSet(false, true)) return   // 防止并发

        scope.launch {
            try {
                val result = api.fetchConfig(environment(), appVersion(), deviceId())
                lastFetchTime.set(now)

                // 校验签名
                if (!SignatureVerifier.verify(result.payload, result.signature)) {
                    AppLogger.w("RemoteConfig", "配置签名校验失败，忽略本次更新")
                    return@launch
                }

                // 校验版本
                if (result.version <= store.current().version) return@launch

                // 应用
                store.apply(ConfigSnapshot.from(result))
                AppLogger.i("RemoteConfig", "配置已更新 v${result.version}")
            } catch (e: Exception) {
                // ★ 拉取失败不影响 App 运行，继续用缓存
                AppLogger.w("RemoteConfig", "配置拉取失败: ${e.message}")
            } finally {
                fetching.set(false)
            }
        }
    }
}
```

### 5. 配置项类型与建模

```kotlin
/**
 * 配置快照：强类型的配置集合。
 *
 * 设计要点：
 * 1. 一次性把所有配置解析成强类型对象（避免每次读都解析 JSON）
 * 2. 解析失败的项回落到默认值，不影响其他项
 * 3. 提供版本号，用于判断是否需要更新
 */
data class ConfigSnapshot(
    val version: Long,
    val fetchedAt: Long,
    val strings: Map<String, String> = emptyMap(),
    val ints: Map<String, Int> = emptyMap(),
    val longs: Map<String, Long> = emptyMap(),
    val doubles: Map<String, Double> = emptyMap(),
    val booleans: Map<String, Boolean> = emptyMap(),
    val jsonObjects: Map<String, String> = emptyMap()   // 复杂对象保留 JSON 字符串，按需解析
) {
    companion object {
        val EMPTY = ConfigSnapshot(version = 0, fetchedAt = 0)

        /** 从服务端返回的 JSON 解析 */
        fun from(response: ConfigResponse): ConfigSnapshot {
            val root = runCatching { Json.parseToJsonElement(response.payload).jsonObject }
                .getOrElse { return EMPTY }

            return ConfigSnapshot(
                version = response.version,
                fetchedAt = System.currentTimeMillis(),
                strings = root["strings"]?.toStringMap() ?: emptyMap(),
                ints = root["ints"]?.toIntMap() ?: emptyMap(),
                longs = root["longs"]?.toLongMap() ?: emptyMap(),
                doubles = root["doubles"]?.toDoubleMap() ?: emptyMap(),
                booleans = root["booleans"]?.toBooleanMap() ?: emptyMap(),
                jsonObjects = root["objects"]?.toStringMap() ?: emptyMap()
            )
        }
    }
}
```

**配置项分类与最佳实践**：

| 类型 | 例子 | 注意事项 |
| --- | --- | --- |
| **开关（Boolean）** | `new_checkout_enabled` | **默认 false**（新功能默认关闭） |
| **数值参数（Int/Long/Double）** | `home_recommend_count = 5` | 要做**范围校验**（服务端配错值不能让 App 崩） |
| **文案（String）** | `home_banner_text = "双十一大促"` | 支持**占位符**（`"欢迎 %s"`） |
| **URL** | `fallback_api_base = "https://..."` | 必须是**白名单域名**，防止被下发恶意地址 |
| **JSON 对象** | `home_sections = [...]` | 要有**schema 校验**和默认值 |
| **枚举** | `pay_channel = "alipay"` | 用 `enum class` + `runCatching` 解析 |
| **多语言** | `i18n.banner.zh = "..."` | 客户端按语言取，缺失回落默认语言 |

**配置校验（必须有）**：

```kotlin
/** 配置项的取值范围约束 */
data class ConfigConstraint(
    val minValue: Long? = null,
    val maxValue: Long? = null,
    val allowedValues: Set<String>? = null
)

/**
 * 配置校验器：服务端配错值时不能让客户端崩溃。
 */
class ConfigValidator(private val constraints: Map<String, ConfigConstraint>) {

    fun validate(snapshot: ConfigSnapshot): ConfigSnapshot {
        val validInts = snapshot.ints.mapValues { (key, value) ->
            val c = constraints[key] ?: return@mapValues value
            val min = c.minValue?.toInt()
            val max = c.maxValue?.toInt()
            if ((min != null && value < min) || (max != null && value > max)) {
                AppLogger.w("ConfigValidator", "配置 $key=$value 超出范围 [$min, $max]，已忽略")
                min ?: 0
            } else {
                value
            }
        }
        return snapshot.copy(ints = validInts)
    }
}
```

### 6. 灰度与分桶

**分桶（Bucketing）**：把用户按某个 key 的哈希分成 N 桶，每个配置项指定对哪些桶生效。

```kotlin
/**
 * 分桶器：决定当前用户是否在目标分组中。
 *
 * 关键：用【用户 ID】而不是【设备 ID】做哈希
 * - 换设备后用户体验一致
 * - 同一用户在同一实验中始终在同一个组（实验有效性的前提）
 */
class BucketAllocator(private val totalBuckets: Int = 1000) {

    /**
     * @param userId 用户标识（未登录时用安装 ID）
     * @param experimentKey 实验/配置标识（不同配置独立分桶）
     * @return 桶号 [0, totalBuckets)
     */
    fun bucketOf(userId: String, experimentKey: String): Int {
        val hash = MessageDigest.getInstance("MD5")
            .digest("$experimentKey:$userId".toByteArray())
        val value = ((hash[0].toInt() and 0xFF) shl 24) or
                ((hash[1].toInt() and 0xFF) shl 16) or
                ((hash[2].toInt() and 0xFF) shl 8) or
                (hash[3].toInt() and 0xFF)
        return ((value.toLong() and 0xFFFFFFFFL) % totalBuckets).toInt()
    }

    /** 判断用户是否在指定百分比分组内 */
    fun isInGroup(userId: String, experimentKey: String, percentage: Int): Boolean {
        require(percentage in 0..100) { "百分比必须在 0~100 之间" }
        return bucketOf(userId, experimentKey) < totalBuckets * percentage / 100
    }
}
```

### 7. 配置变更的响应（Listener）

```kotlin
/**
 * 配置变更监听器：让业务模块在配置更新后立即响应。
 *
 * 典型用途：
 * - 主题色变更 → 刷新 UI
 * - 降级策略变更 → 切换网络实现
 * - 第三方 SDK 开关变更 → 启停 SDK
 */
class ConfigChangeNotifier {

    private val listeners = CopyOnWriteArrayList<Pair<String, (ConfigSnapshot) -> Unit>>()

    /** 注册监听（指定关心的 key，null 表示全部） */
    fun register(keys: Set<String>?, callback: (ConfigSnapshot) -> Unit) {
        listeners.add(keys to callback)
    }

    /** 配置更新时通知 */
    fun notifyChanged(old: ConfigSnapshot, new: ConfigSnapshot) {
        listeners.forEach { (keys, callback) ->
            if (keys == null) {
                callback(new)
                return@forEach
            }
            // 只通知关心的 key 有变化的监听器
            val changed = keys.any { key ->
                old.stringValue(key) != new.stringValue(key)
            }
            if (changed) callback(new)
        }
    }

    private fun ConfigSnapshot.stringValue(key: String): Any? =
        strings[key] ?: ints[key] ?: longs[key] ?: doubles[key] ?: booleans[key] ?: jsonObjects[key]
}
```

**注意事项**：
- **回调可能在任意线程执行**（拉取在后台线程）→ 需要 UI 更新的必须切回主线程。
- **回调里不要做耗时操作**（会拖慢拉取流程）。
- **回调异常要吞掉**（一个监听器出错不能影响其他监听器）。

### 8. 安全：签名校验与防篡改

**威胁模型**：如果配置接口走明文 HTTP，或者不校验内容，攻击者（中间人）可以下发恶意配置：
- 把支付接口地址改成自己的服务器（**中间人攻击**）。
- 把某个开关打开，触发有漏洞的功能路径。
- 下发超大字符串导致 OOM。

**防御措施**：

```kotlin
/**
 * 配置签名校验。
 *
 * 方案：服务端用私钥对配置内容签名，客户端用内置公钥验证。
 * 攻击者即使劫持了网络，也无法伪造合法签名。
 */
object SignatureVerifier {

    /** 内置在客户端的公钥（Base64 编码的 X.509 公钥） */
    private const val PUBLIC_KEY_BASE64 = "MIIBIjANBgkqhkiG9w0BAQEFAAOCAQ8AMIIBCgKCAQEA..."

    fun verify(payload: String, signature: String): Boolean {
        return runCatching {
            val keyBytes = Base64.decode(PUBLIC_KEY_BASE64, Base64.DEFAULT)
            val publicKey = KeyFactory.getInstance("RSA")
                .generatePublic(X509EncodedKeySpec(keyBytes))

            val verifier = Signature.getInstance("SHA256withRSA")
            verifier.initVerify(publicKey)
            verifier.update(payload.toByteArray(Charsets.UTF_8))

            val sigBytes = Base64.decode(signature, Base64.DEFAULT)
            verifier.verify(sigBytes)
        }.getOrDefault(false)
    }
}
```

**其他安全措施**：

| 措施 | 说明 |
| --- | --- |
| **强制 HTTPS** | 接口必须 TLS，且**校验证书**（不要用 `TrustAllCerts`） |
| **证书 Pinning** | 防止中间人用自签证书（见 [[../安全加固]]） |
| **URL 白名单** | 下发的 URL 必须属于自有域名列表 |
| **数值范围校验** | 服务端配错值不能让客户端崩 |
| **配置项变更审计** | 谁在什么时候改了什么，必须留日志 |
| **权限控制** | 不同角色能改的配置范围不同（开发能改开关，运营只能改文案） |
| **不要下发密钥** | 客户端能解出来的密钥 = 没有密钥。见下 |
| **敏感配置不落地** | 敏感配置只放内存，不写 DataStore |

**关于下发密钥的说明**：

> **远端配置不能用来安全地分发密钥。** 因为客户端必须内置解密密钥，攻击者逆向 App 就能拿到。正确的做法是：
> - 密钥在**服务端**保存，客户端通过**认证接口**换取**短期 token**（如 15 分钟有效）。
> - 远端配置只下发**非敏感的策略参数**（如"token 有效期 900 秒"）。
> - **短时效 + 服务端可撤销** > 试图通过配置下发密钥来保密。

### 9. 第三方方案对比

| 方案 | 特点 | 适用 |
| --- | --- | --- |
| **Firebase Remote Config** | 与 Firebase 生态深度集成；实时推送；A/B 实验；条件定向；免费额度 | 海外产品、用 Firebase |
| **Firebase App Hosting / Cloud Functions** | 与上述配套 | — |
| **Apollo / GraphQL + 自建** | 配置作为 GraphQL 查询 | 需要与后端一体 |
| **火山引擎 RemoteConfig**（字节） | 国内合规、低延迟、灰度能力强 | 国内产品 |
| **阿里云移动推送 + 远程配置** | 阿里生态 | 阿里云用户 |
| **腾讯 Bugly / 灯塔** | 部分提供配置能力 | 腾讯生态 |
| **自建** | 完全可控、与内部系统打通 | 大型公司、有合规要求 |

**自建 vs 第三方**：

| 维度 | 自建 | 第三方 |
| --- | --- | --- |
| **成本** | 2~3 人 × 1~2 个月（最小可用） | 低 |
| **控制力** | 完全可控（分桶逻辑、灰度规则） | 受限于平台能力 |
| **合规** | 数据不出境 | 需评估 |
| **功能丰富度** | 需自己做（分桶、审批、审计） | 完善（可视化控制台、A/B、审计） |
| **可靠性** | 自己做（但只做配置，可用性要求低于核心服务） | 厂商保障 |

**建议**：**用第三方的控制台 + 自建的下发接口**是常见的折中——控制台（配置编辑、审批、灰度）用第三方的，数据面（下发 API）自建，保证延迟与合规。

### 10. 与 Feature Flag 的关系

**远端配置 ⊃ Feature Flag**：Feature Flag 是一种特殊的远端配置项（布尔型 + 分组）。

```kotlin
/**
 * 功能开关：远端配置之上的语义化封装。
 *
 * 好处：
 * 1. 业务代码读起来语义清晰（FeatureFlags.isNewCheckoutEnabled()）
 * 2. 开关与代码解耦，可以随时新增而不需要改代码结构
 * 3. 统一管理开关的元信息（负责人、依赖关系、到期日）
 */
class FeatureFlags(private val config: RemoteConfig, private val buckets: BucketAllocator) {

    fun isEnabled(feature: String, userId: String? = null): Boolean {
        // 1. 检查开关是否过期（防止临时开关被遗忘）
        if (isExpired(feature)) {
            AppLogger.w("FeatureFlags", "开关 $feature 已过期，按默认关闭处理")
            return false
        }
        // 2. 读配置（默认关闭）
        val enabled = config.getBoolean(feature, false)
        if (!enabled) return false
        // 3. 如果是灰度开关，检查用户是否在分组内
        val rolloutPercentage = config.getInt("${feature}_rollout_percentage", 100)
        if (rolloutPercentage >= 100) return true
        return userId != null && buckets.isInGroup(userId, feature, rolloutPercentage)
    }
}
```

**开关的治理（非常重要））**：

```kotlin
/** 开关元信息：过期自动关闭 */
data class FeatureFlagMeta(
    val key: String,
    val owner: String,          // 负责人
    val createdAt: Long,
    val expireAt: Long?,        // 过期时间
    val dependencies: List<String> = emptyList()   // 依赖的其他开关
)

class FeatureFlagRegistry {
    private val metas = ConcurrentHashMap<String, FeatureFlagMeta>()

    fun isExpired(feature: String): Boolean {
        val meta = metas[feature] ?: return false
        val expireAt = meta.expireAt ?: return false
        return System.currentTimeMillis() > expireAt
    }

    /** 依赖检查：一个开关依赖的开关没开时，它也不能开 */
    fun canEnable(feature: String): Boolean {
        val meta = metas[feature] ?: return true
        return meta.dependencies.all { isEnabled(it) }
    }
}
```

**临时开关必须设过期时间**——否则会积累成"开关地狱"：没人知道哪些开关还在用，删掉一个可能引发线上事故。

### 1. 完整的远端配置客户端

```kotlin
package com.example.core.config

import android.content.Context
import androidx.datastore.preferences.core.*
import androidx.datastore.preferences.preferencesDataStore
import kotlinx.coroutines.flow.first
import kotlinx.coroutines.flow.map
import kotlinx.serialization.json.Json

private val Context.configDataStore by preferencesDataStore(name = "remote_config")

/**
 * 远端配置客户端。
 *
 * 设计原则：
 * 1. 读永远不阻塞（走内存快照）
 * 2. 拉取永远不失败 App（异常全部兜住，继续用缓存）
 * 3. 默认值永远在代码里（首次安装/从未拉取成功时的兜底）
 * 4. 内容必须验签（防篡改）
 */
class RemoteConfigClient(
    private val context: Context,
    private val api: ConfigApi,
    private val notifier: ConfigChangeNotifier,
    private val validator: ConfigValidator = ConfigValidator(emptyMap())
) {

    private val dataStore = context.configDataStore

    /** 内存快照（所有读取的来源） */
    @Volatile
    private var snapshot: ConfigSnapshot = ConfigSnapshot.EMPTY

    /** 是否初始化完成 */
    private val initialized = CompletableDeferred<Unit>()

    suspend fun initialize() {
        // 1. 从本地恢复（保证首次读取就有值）
        snapshot = dataStore.data.map { it.toSnapshot() }.first() ?: ConfigSnapshot.EMPTY
        initialized.complete(Unit)
    }

    // ── 读取 API（同步，永不阻塞）──

    fun getBoolean(key: String, default: Boolean): Boolean = snapshot.booleans[key] ?: default
    fun getInt(key: String, default: Int): Int = snapshot.ints[key] ?: default
    fun getLong(key: String, default: Long): Long = snapshot.longs[key] ?: default
    fun getDouble(key: String, default: Double): Double = snapshot.doubles[key] ?: default
    fun getString(key: String, default: String): String = snapshot.strings[key] ?: default

    /** 复杂对象 */
    inline fun <reified T> getObject(key: String, default: T): T {
        val json = getString(key, "")
        if (json.isBlank()) return default
        return runCatching { Json.decodeFromString<T>(json) }.getOrElse {
            AppLogger.w("RemoteConfig", "配置 $key 解析失败，使用默认值")
            default
        }
    }

    /** 当前版本号 */
    fun version(): Long = snapshot.version

    // ── 拉取 ──

    /**
     * 拉取并应用配置。
     *
     * @param force true 表示忽略最小间隔限制，强制拉取
     * @return 是否真的更新了
     */
    suspend fun fetch(force: Boolean = false): Boolean {
        initialized.await()
        return try {
            val response = api.fetchConfig(
                environment = AppEnv.current(),
                appVersion = BuildConfig.VERSION_NAME,
                buildNumber = BuildConfig.VERSION_CODE,
                deviceId = DeviceInfo.installationId()
            )

            // 1. 验签（防止中间人篡改）
            if (!SignatureVerifier.verify(response.payload, response.signature)) {
                AppLogger.w("RemoteConfig", "配置签名校验失败，拒绝本次更新")
                return false
            }

            // 2. 版本检查
            if (response.version <= snapshot.version) {
                return false
            }

            // 3. 解析 + 校验
            val newSnapshot = ConfigSnapshot.from(response)
            val validated = validator.validate(newSnapshot)

            // 4. 落盘（先写磁盘保证一致性）
            persist(validated)

            // 5. 更新内存 + 通知
            val old = snapshot
            snapshot = validated
            notifier.notifyChanged(old, validated)

            AppLogger.i("RemoteConfig", "配置已更新 v${old.version} -> v${validated.version}")
            true
        } catch (e: Exception) {
            // ★ 拉取失败不影响 App，继续用缓存和默认值
            AppLogger.w("RemoteConfig", "配置拉取失败: ${e.message}")
            false
        }
    }

    private suspend fun persist(snapshot: ConfigSnapshot) {
        dataStore.edit { prefs ->
            prefs[longKey(KEY_VERSION)] = snapshot.version
            prefs[longKey(KEY_FETCHED_AT)] = snapshot.fetchedAt
            prefs[stringKey(KEY_STRINGS)] = Json.encodeToString(snapshot.strings)
            prefs[stringKey(KEY_INTS)] = Json.encodeToString(snapshot.ints)
            prefs[stringKey(KEY_BOOLEANS)] = Json.encodeToString(snapshot.booleans)
            prefs[stringKey(KEY_LONGS)] = Json.encodeToString(snapshot.longs)
            prefs[stringKey(KEY_DOUBLES)] = Json.encodeToString(snapshot.doubles)
        }
    }
}
```

### 3. 分桶与规则应用

```kotlin
package com.example.core.config

/**
 * 规则应用器：把服务端的"规则"应用到基础配置上。
 *
 * 规则优先级（数值越大越优先）：
 *   100 用户白名单 > 90 指定用户 > 50 地域/版本 > 10 分桶 > 0 全局
 */
class RuleApplier(private val buckets: BucketAllocator) {

    /**
     * @param base 基础配置（全局值）
     * @param rules 服务端下发的规则列表
     * @param userId 当前用户 ID
     * @return 应用规则后的最终配置
     */
    fun apply(
        base: ConfigSnapshot,
        rules: List<ConfigRule>,
        userId: String?,
        region: String?,
        osVersion: Int
    ): ConfigSnapshot {
        // 按优先级升序排列，后面的（优先级高的）覆盖前面的
        val sorted = rules.sortedBy { it.priority }

        val result = base.copy(
            strings = base.strings.toMutableMap(),
            ints = base.ints.toMutableMap(),
            booleans = base.booleans.toMutableMap(),
            longs = base.longs.toMutableMap(),
            doubles = base.doubles.toMutableMap()
        )

        for (rule in sorted) {
            if (!matches(rule, userId, region, osVersion)) continue

            when (rule.type) {
                ConfigType.STRING -> result.strings[rule.key] = rule.stringValue.orEmpty()
                ConfigType.INT -> rule.intValue?.let { result.ints[rule.key] = it }
                ConfigType.LONG -> rule.longValue?.let { result.longs[rule.key] = it }
                ConfigType.DOUBLE -> rule.doubleValue?.let { result.doubles[rule.key] = it }
                ConfigType.BOOLEAN -> rule.booleanValue?.let { result.booleans[rule.key] = it }
            }
        }
        return result
    }

    private fun matches(
        rule: ConfigRule,
        userId: String?,
        region: String?,
        osVersion: Int
    ): Boolean = when (rule.scope) {
        Scope.GLOBAL -> true

        Scope.USER_WHITELIST ->
            userId != null && userId in rule.userIds

        Scope.BUCKET -> {
            if (userId == null) return false
            val start = rule.bucketRange?.getOrNull(0) ?: 0
            val end = rule.bucketRange?.getOrNull(1) ?: 0
            val bucket = buckets.bucketOf(userId, rule.experimentKey ?: rule.key)
            bucket in start until end
        }

        Scope.REGION -> region != null && region in rule.regions

        Scope.OS_VERSION ->
            osVersion >= (rule.minOsVersion ?: 0) &&
                    osVersion <= (rule.maxOsVersion ?: Int.MAX_VALUE)

        Scope.APP_VERSION -> {
            val current = BuildConfig.VERSION_CODE
            current >= (rule.minAppVersion ?: 0) &&
                    current <= (rule.maxAppVersion ?: Int.MAX_VALUE)
        }
    }
}
```

### 6. CI 中的配置校验脚本

```bash
#!/usr/bin/env bash
# scripts/validate-config.sh —— 校验远端配置的合法性
set -euo pipefail

CONFIG_FILE="${1:-config/remote-config.json}"

echo "🔍 校验配置: $CONFIG_FILE"

# 1. JSON 语法检查
if ! jq empty "$CONFIG_FILE" 2>/dev/null; then
  echo "❌ JSON 语法错误"
  exit 1
fi

# 2. 检查是否有缺少默认值的配置项
MISSING=$(jq -r '
  .items[]
  | select(.default == null)
  | .key' "$CONFIG_FILE" 2>/dev/null || true)

if [ -n "$MISSING" ]; then
  echo "❌ 以下配置项缺少默认值（会导致首次安装行为不确定）："
  echo "$MISSING"
  exit 1
fi

# 3. 检查数值是否在合理范围
OUT_OF_RANGE=$(jq -r '
  .items[]
  | select(.type == "int")
  | select(.value != null)
  | select(.value < (.min // 0) or .value > (.max // 999999))
  | "\(.key)=\(.value)"' "$CONFIG_FILE" 2>/dev/null || true)

if [ -n "$OUT_OF_RANGE" ]; then
  echo "❌ 以下配置值超出范围："
  echo "$OUT_OF_RANGE"
  exit 1
fi

# 4. 检查功能开关默认值（新功能必须默认 false）
BAD_SWITCH=$(jq -r '
  .items[]
  | select(.type == "boolean")
  | select(.default == true)
  | .key' "$CONFIG_FILE" 2>/dev/null || true)

if [ -n "$BAD_SWITCH" ]; then
  echo "⚠️  以下开关默认值为 true，请确认是有意为之（新功能建议默认 false）："
  echo "$BAD_SWITCH"
fi

echo "✅ 配置校验通过"
```

## 常见问题 / 面试要点

**读者问：远端配置怎么做？配置拉不到怎么办？**

**AI答：**

1. **整体架构（三层）**：
   - **客户端**：内存快照（读）+ 本地持久化（缓存）+ 网络拉取（写）。
   - **服务端**：配置管理后台 + 存储 + 下发 API（含分桶规则）。
   - **触发时机**：冷启动后延迟拉取 + 每次进前台（限频）+ 推送唤醒 + 关键路径按需。
2. **"拉不到怎么办"的完整答案（这是核心）**：
   - **① 永远有本地缓存**：上次成功拉到的配置存在 DataStore，**断网也能用**。
   - **② 永远有代码默认值**：首次安装、配置从未成功拉取、配置被删除 → 用代码里的默认值。**默认值必须保守**（新功能默认 false）。
   - **③ 拉取失败静默降级**：拉取失败不弹 Toast、不阻塞启动、不影响任何功能，只是"配置还是老的"。
   - **④ 版本号机制**：只有 `remoteVersion > localVersion` 才应用，避免重复处理。
   - **⑤ 读取永不阻塞**：所有读取走内存快照（纳秒级），**绝不在读路径上做网络请求**。
   - **⑥ 拉取有超时**：网络超时设 3~5 秒，不能让配置拖慢 App。
3. **优先级链**（必须背下来）：
   ```
   内存最新快照 → 本地持久化缓存 → 代码默认值
   ```
4. **关键实现细节**：
   - **落盘顺序**：先写磁盘，再更新内存（保证一致性）。
   - **拉取去重**：并发拉取用 `AtomicBoolean` 防止重复请求。
   - **限频**：最小间隔（如 5 分钟），防止频繁切前台导致请求风暴。
   - **不阻塞冷启动**：延迟到首帧之后拉。
5. **面试话术**："远端配置的核心不是'能下发'，而是'**下发失败时系统仍然完整可用**'。我的设计是三级兜底：**内存快照 → 本地缓存 → 代码默认值**，所有读取走内存快照永不阻塞，所有拉取失败静默降级。默认值的原则是保守——新功能默认关闭。"

**读者问：远端配置和 Feature Flag、A/B 实验是什么关系？**

**AI答：**

1. **三者是层层递进的关系**：

```
远端配置（Remote Config）
  └── 配置分发的基础设施：存储、下发、缓存、灰度、分桶
        │
        ├── Feature Flag（功能开关）
        │     布尔型配置的语义化封装 + 灰度比例 + 过期管理
        │
        └── A/B 实验
              在 Feature Flag 之上叠加"分组 + 指标统计 + 实验结论"
```

2. **Feature Flag 是远端配置的语义化层**：
   - 远端配置给的是 `"new_checkout_enabled": true`。
   - Feature Flag 给的是 `FeatureFlags.isEnabled("new_checkout", userId)`，内部处理**灰度比例**、**依赖关系**、**过期自动关闭**、**埋点**。
   - **关键价值**：业务代码读起来语义清晰，且开关的生命周期被治理（防止"开关地狱"）。
3. **A/B 实验是 Feature Flag + 统计**：
   - 底层还是"按用户哈希分桶 + 下发不同配置"。
   - 额外需要：**实验指标上报**（对照组 vs 实验组的核心指标对比）、**实验平台**、**显著性检验**。
   - **A/B 实验的技术核心是"分流一致性"**：同一个用户在不同设备、不同时间必须落在同一组（这决定了必须用 `hash(userId + experimentKey)` 而不是随机数）。
4. **三者的实现差异**：

| 维度 | 远端配置 | Feature Flag | A/B 实验 |
| --- | --- | --- | --- |
| **配置形态** | 任意类型 | 布尔 + 灰度比例 | 多组 + 参数 |
| **分流** | 全局或简单规则 | 按用户哈希 | 按用户哈希（必须稳定） |
| **统计** | 无 | 可选（开关曝光） | 必须（核心指标） |
| **生命周期** | 长期 | 有过期时间 | 有实验周期（到期自动结束） |
| **治理** | 权限、审计 | 负责人、过期清理 | 实验平台管理 |

5. **重要的工程细节**：
   - **A/B 实验必须保证分组稳定**：用 `MD5(userId + experimentId)`，而不是 `random()`。
   - **必须用 userId 而不是 deviceId**：换设备后用户仍在同一组（否则实验数据失真）。
   - **实验参数与实验分组要分离**：分组 ID 和参数绑定，避免"用户看到分组 A 但拿到 B 的参数"。
   - **Feature Flag 要有依赖关系**：如果 B 功能依赖 A 功能，A 没开时 B 也不能开。
6. **面试话术**："我的理解是**远端配置是基础设施，Feature Flag 是语义层，A/B 实验是统计层**。技术上它们共用同一套分桶机制（`hash(userId + key)`），保证分流稳定。工程上最大的差异是**生命周期治理**：远端配置是长期的，Feature Flag 必须有负责人和过期时间，A/B 实验必须有结束日期——否则会积累成无法维护的'开关地狱'。"

**读者问：远端配置的安全性怎么保证？能不能下发密钥？**

**AI答：**

1. **威胁模型**（配置通道面临的攻击）：
   - **中间人攻击**：篡改下发的配置（把 API 地址改成攻击者的服务器、打开有漏洞的开关）。
   - **服务端被攻破**：配置被恶意修改。
   - **客户端被篡改**：本地缓存被改。
   - **越权操作**：内部人员改了不该改的配置。
2. **防御措施**：

| 措施 | 做法 | 防什么 |
| --- | --- | --- |
| **强制 HTTPS + 证书校验** | 不要用 `TrustAllCerts` | 基础传输安全 |
| **证书 Pinning** | 固定服务端证书或公钥 | 中间人（见 [[../安全加固]]） |
| **内容签名（RSA/ECDSA）** | 服务端私钥签名 payload，客户端内置公钥验签 | **内容篡改（核心）** |
| **URL 白名单** | 下发的 URL 必须属于自有域名 | 劫持到攻击者服务器 |
| **取值范围校验** | 服务端配错值不能让客户端崩 | 配置错误 |
| **权限与审批** | 谁能改哪些配置；关键配置需审批 | 内部越权 |
| **变更审计** | 谁在何时改了什么（全量日志） | 追责与回滚 |
| **服务端签名密钥保护** | 私钥放 KMS，不落明文 | 服务端被入侵 |

3. **签名方案的设计**：
   ```
   服务端：payload = 配置JSON
           signature = RSA-SHA256(payload, 私钥)
           下发 { payload, signature }

   客户端：用内置公钥验证 signature 与 payload 的匹配
           验证失败 → 拒绝本次更新（继续用缓存）
   ```
   **注意**：公钥内置在 App 里，攻击者可以替换公钥来绕过验签——**所以还需要 APK 自身的完整性保护**（签名校验，见 [[../安全加固]]）。**纵深防御**，没有单点失效。
4. **能不能下发密钥？（重点）**：
   - **❌ 不能安全地分发密钥。** 客户端必须内置解密能力，逆向就能拿到密钥。**能解密的密钥等于没有密钥**。
   - **正确做法**：
     - 密钥保存在**服务端**，客户端通过**认证接口**换取**短期 token**（如 15 分钟有效、绑定设备、可撤销）。
     - 远端配置只下发**非敏感的策略参数**（如"token 有效期 = 900 秒"、"接口重试次数 = 3"）。
     - 敏感业务参数走**带签名的请求**（服务端校验），而不是明文下发到客户端。
   - **一个反例**：用远端配置下发"某接口的 AES 密钥"，然后客户端用它加密请求体 → **攻击者抓包拿到密钥**，所有加密形同虚设。
5. **客户端缓存被篡改的风险**：
   - 本地缓存被改（Root 设备）→ 客户端应该校验**本地缓存的完整性**（用与服务端相同的签名机制：本地存的配置也带签名，启动时验签）。
   - 这是一个容易忽略的点：**内存里的值可以信任，磁盘上的值要验签**。
6. **敏感配置不落地**：
   - 真正敏感的配置（哪怕是短期的）**只放内存，不写 DataStore**，App 重启后重新拉取。
7. **面试话术**："远端配置的安全核心是**内容签名**——服务端用私钥签名，客户端用内置公钥验签，防止中间人篡改。但这还不够，因为公钥本身可以被替换，所以要配合 APK 完整性校验做纵深防御。至于密钥下发，**我的答案是不能**——客户端能解密的密钥就等于公开密钥，正确的做法是服务端保存密钥、客户端换短效 token，远端配置只下发非敏感的策略参数。"

**读者问：远端配置怎么保证实时性？会不会有"配置延迟"导致的问题？**

**AI答：**

1. **实时性的构成**：
   ```
   总延迟 = 服务端生效延迟 + 客户端感知延迟
          = 配置编辑到发布的时间 + 拉取时机决定的等待时间
   ```
2. **各环节的延迟**：

| 环节 | 延迟 | 优化手段 |
| --- | --- | --- |
| 服务端编辑 → 发布 | 秒级 | 控制台一键发布 |
| 发布 → 客户端下次拉取 | **这是主要延迟** | 见下方拉取时机策略 |
| 拉取 → 应用生效 | 毫秒级 | 内存快照即时更新 |
3. **拉取时机策略（决定感知延迟）**：

| 策略 | 感知延迟 | 适用场景 |
| --- | --- | --- |
| **冷启动后拉取** | 用户下次打开 App 时 | 大部分场景足够 |
| **进前台拉取** | 切回前台时 | 日常使用 |
| **定时轮询（后台）** | ≤ 轮询间隔 | 长时间后台运行 |
| **推送唤醒拉取** | 秒级 | **最实时**，且不额外耗电 |
| **关键路径同步检查** | 用户操作时 | 支付、下单等关键流程 |

4. **推荐的组合方案**：
   ```
   ① 冷启动后延迟 3~5 秒拉取（不阻塞启动）
   ② 每次进前台：如果距上次 > 5 分钟则拉取
   ③ 推送消息里带配置版本号 → 收到推送立即检查并拉取（最实时）
   ④ 支付/下单等关键路径：调用 checkForUpdate()（只传版本号，流量极小）
   ```
5. **"配置延迟"带来的真实风险（这是关键思考）**：

   | 风险 | 场景 | 缓解 |
   | --- | --- | --- |
   | **开关没及时关闭** | 功能出问题，配置已发布但客户端没拉取 | 关键开关用**推送唤醒**；灰度期用**短轮询间隔** |
   | **新旧逻辑不一致** | 服务端已按新配置返回数据，客户端还是旧逻辑 | **服务端与客户端配置版本要协同**（服务端接口也返回版本号，客户端发现不一致时提示更新） |
   | **紧急止血延迟** | 事故发生，配置关了但用户还遇到 | 兜底：**其他止损手段**（热修复、下架、强制升级提示） |
   | **配置风暴** | 频繁修改导致频繁拉取 | 服务端加"变更冷却期"；客户端限频 |

6. **重要的架构原则**：
   > **远端配置是"增强"，不是"依赖"。它的实时性永远不如代码本身可靠。**
   > 所以**关键的安全保障不能只靠远端配置**——要有第二道防线（热修复、强制升级、服务端校验）。

7. **一个实用技巧：配置版本协同**：
   ```kotlin
   /**
    * 服务端接口返回时也带上"期望的客户端配置版本"。
    * 客户端发现服务端期望的版本比自己新 → 触发拉取 + 提示用户重启。
    */
   data class ApiResponse<T>(
       val data: T,
       val expectedConfigVersion: Long? = null
   )

   // 拦截器中检查
   class ConfigVersionInterceptor : Interceptor {
       override fun intercept(chain: Interceptor.Chain): Response {
           val response = chain.proceed(chain.request())
           val expected = response.headers["X-Config-Version"]?.toLongOrNull()
           if (expected != null && expected > remoteConfig.version()) {
               // 服务端已经用了新配置，客户端需要更新
               scope.launch { remoteConfig.fetch(force = true) }
           }
           return response
       }
   }
   ```
8. **面试话术**："实时性取决于拉取时机。我的方案是**冷启动延迟拉取 + 进前台限频拉取 + 推送唤醒立即拉取 + 关键路径按需检查**这四层组合。最优的实时性来自**推送唤醒**，因为它既实时又不额外耗电。但我要强调一点：**远端配置是增强不是依赖**，关键保障必须有第二道防线——因为配置永远可能拉不到，或者用户根本不再打开这个 App。"

**读者问：远端配置在下发时机和缓存策略上具体怎么设计？首次启动没有缓存、离线、配置服务挂了分别怎么兜？**

**AI答：**

1. **拉取必须"异步 + 不阻塞 + 有上限"**。三件事同时成立才算合格：
   - **不阻塞首屏**：冷启动时**先渲染本地快照，首帧之后**再拉取（`Handler.postDelayed` 或 `ProcessLifecycleOwner` 观察者里触发），**绝不能在 `Application.onCreate` 里同步等网络**——那会直接拖慢冷启动指标。
   - **必须有超时**：配置接口设 3~5 秒超时，**配置拉不到不能影响任何业务请求**（两条链路独立，不能共用同一个 OkHttpClient 的默认超时策略）。
   - **必须限频 + 去重**：`AtomicBoolean` 防并发重复拉取，最小间隔（5 分钟）防止频繁切前台造成请求风暴。
2. **缓存分三层，各司其职**：
   ```
   ① 内存快照（@Volatile）  → 纳秒级读，所有业务读取走这里
   ② DataStore 持久化缓存  → 跨进程重启存活，离线可用
   ③ 代码内默认值          → 首次安装 / 从未拉取成功 / 配置被删除
   ```
   **关键**：读取路径上**一次网络 IO 都不能有**。业务代码拿到的是同步的 `getBoolean(key, default)`，它只读内存。
3. **首次启动（没有任何缓存）怎么办**：
   - 只能**用代码默认值**。所以默认值必须**在代码里写死且保守**：新功能开关默认 `false`、数值有范围保护（`coerceIn`）、文案有兜底串。
   - **首屏不能用"加载配置中"的空态挡住用户**——正确做法是"**先用默认值渲染，等配置到了再刷新**"（这就是为什么配置变更要支持 Listener 通知）。
   - **面试要点**：首次启动的默认值决定了"新装用户第一次看到什么"，这是**产品决策**，不是技术细节；默认值写错＝新装用户全部命中错误路径。
4. **离线 / 弱网怎么办**：
   - 直接**用上一次的持久化缓存**；没有缓存就用默认值。**全程不弹错误提示、不阻塞、不重试到成功为止**。
   - **必须区分两类失败**：
     - **可重试失败**（网络超时、5xx）→ 退避重试（指数退避 + 上限次数），**但只能在下次触发时机重来**，不要死循环。
     - **不可重试失败**（4xx、参数非法、客户端版本不支持）→ **直接放弃本次拉取**，等下次触发，避免无意义重试。
   - **弱网下要额外注意**：超时时间不能太长（用户已经感知到"卡"），宁可"这次没拉到、下次再说"。
5. **配置服务挂了怎么办（降级链路）**：
   - 客户端侧：**继续用缓存和默认值**，App **必须完整可用**——这是"配置服务是增强、不是依赖"的直接体现。
   - 服务端侧：下发接口要做**多副本 + 降级副本**；更稳的做法是**服务端把最近一版配置全量缓存在 CDN/边缘节点**，客户端拉不到 API 时可以退而拉一个静态 JSON 兜底。
   - **监控是必须的**：配置拉取成功率、失败原因分布、客户端配置版本与服务端当前版本的**版本差**——如果大量客户端停留在旧版本，说明拉取链路出问题了。**"配置下发失败"必须是告警项，而不是等用户投诉才发现。**
6. **缓存写入的顺序与一致性**：
   - **先写磁盘，再更新内存**（`DataStore.writeConfigSnapshot()` → `snapshot = newSnapshot`）：先落盘保证进程被杀后仍能恢复一致状态，再更新内存保证可见性。顺序反了会出现"内存新、磁盘旧"，重启后配置回退。
   - **写入要原子**：整份快照一次性序列化写入，**不要按 key 分多次写**（否则中途崩溃会产生"半新半旧"的混合配置）。
   - **版本号单调递增**：只有 `remoteVersion > localVersion` 才应用 → 天然幂等，重复拉取不会造成状态抖动。
7. **配置更新的"生效边界"（最容易踩的坑）**：
   - **不是所有配置都能"热生效"**：改**开关**（影响后续逻辑分支）通常可以即时生效；改**文案/数值参数**在下次进入页面时生效就很自然。
   - **有些配置必须重启才生效**（如改变初始化顺序、改变资源加载路径）→ 所以配置项要**声明生效时机**，否则会出现"运营改了配置但用户说没变化"的客诉。
   - **运行中的实例状态不会回滚**：配置更新不会让已经创建的对象"变身"，需要业务代码自己监听并重建（如切换网络实现、重建主题）。
8. **一个务实的"配置 TTL"设计**：给每个配置项加 **`effectiveUntil`（有效期）**——超过有效期**自动回落到默认值**，避免一份半年前的配置长期生效（比如某个降级开关只应该在事故期间打开，忘了关就是长期降级 → 用户体验反而更差）。
9. **面试话术**："**拉取策略是'异步不阻塞 + 超时 + 限频去重'，缓存是'内存快照 → DataStore 持久化 → 代码默认值'三级，读路径永不碰网络。** 首次启动只有默认值，所以默认值必须保守（新功能默认关闭）；离线直接用上次缓存；配置服务挂了客户端必须完整可用、服务端要有降级副本。工程上我会强调三件事：**落盘先于更新内存**（避免重启回退）、**版本号单调递增**（幂等）、**拉取失败率要进监控告警**（配置不生效是静默故障，最容易漏）。最后一条边界是：**有些配置必须重启才生效**，所以配置项要显式声明生效时机，否则运营改了用户却说没变化。**"

# 灰度发布与监控

## 一句话定义

灰度发布（Canary Release / Gradual Rollout）是**先让一小部分真实用户使用新版本，在真实流量下验证指标达标后再逐步扩大范围，最终全量**的发布方式。它的存在理由是：**任何离线测试都无法覆盖真实设备的真实网络、真实数据、真实并发**，所以最后一道防线必须是"真实用户 + 自动化监控 + 快速回滚"。而**功能开关（Feature Flag）** 是灰度的孪生兄弟——它让"发布代码"和"启用功能"解耦，使得**回滚不需要重新发版**。

面试开场：**"灰度的本质是'**用小流量换取确定性**'。1% 灰度跑 48 小时，如果 Crash 率相对基线上涨超过阈值就自动回滚——这比任何测试报告都有说服力，因为它是真实数据。而功能开关让这个'回滚'的动作从'重新发版等审核'变成'改一个配置，30 秒生效'。"**

## 核心原理

### 1. 为什么要灰度：移动端的约束

```text
┌────────────────────────────────────────────────────────────────────────┐
│  移动端发布的三个硬约束（Web/后端没有）                                  │
├────────────────────────────────────────────────────────────────────────┤
│  ① 回滚慢                                                                │
│     Play 商店的"回滚"= 提交一个新版本 + 重新审核（小时到天级）             │
│     → 已升级的用户在坏版本上停留的时间不可控                                │
│     → 所以必须靠【功能开关】和【热修复】来止损                             │
├────────────────────────────────────────────────────────────────────────┤
│  ② 设备碎片化                                                            │
│     厂商 ROM、系统版本、屏幕尺寸、CPU 架构差异巨大                          │
│     → 你的开发机永远测不全                                                 │
├────────────────────────────────────────────────────────────────────────┤
│  ③ 分发不可控                                                          │
│     用户会停留在旧版本上几个月（有的甚至不更新）                            │
│     → 新旧版本会【长期共存】，接口必须向后兼容                              │
└────────────────────────────────────────────────────────────────────────┘
```

**由此推出灰度的三大作用**：
1. **控制爆炸半径**：出问题只影响 1% 用户，而不是 100%。
2. **获取真实数据**：用线上真实设备矩阵验证，而不是靠模拟器。
3. **支撑快速回滚**：发现问题后能立刻停止扩大范围。

### 2. 灰度策略的分桶方式

| 分桶维度 | 说明 | 适用场景 |
| --- | --- | --- |
| **设备 ID hash** | `hash(设备ID + 盐) % 10000` 决定桶号，取前 N 个桶为灰度组 | **最常用**，覆盖随机、无偏 |
| **用户 ID hash** | `hash(userId + 盐) % 100` | 需登录的 App，按用户而非设备分桶 |
| **白名单** | 内部员工、测试账号、指定设备 ID 强制进灰度组 | **内测阶段**，必须与百分比策略叠加 |
| **地域 / 国家** | 按国家/地区分批（如先发东南亚再发欧洲） | 规避区域合规、多语言问题 |
| **系统版本** | Android 10+ 先发，Android 9 稍后 | 规避特定系统版本的兼容问题 |
| **设备型号 / 厂商** | 先发主流机型，避开问题机型 | 已知某厂商 ROM 有兼容问题 |
| **渠道** | 先内部渠道，再应用商店 | 商店审核周期长的场景 |
| **网络类型** | 4G/5G 先发，WiFi 稍后 | 弱网场景有风险时 |

**⚠️ 分桶必须"稳定 + 无偏"**：
- **稳定**：同一设备/用户**永远落在同一个桶**（否则用户会在新旧体验间反复横跳，投诉不断）。
- **无偏**：分桶哈希必须**与设备属性无关**（否则可能恰好把某厂商某系统版本的用户全分到一组，对比数据失真）。
- **加盐**：用固定盐值（不要用会变的值），避免攻击者预测分桶。

### 3. 阶段划分

```text
┌────────────┬───────────┬──────────────┬───────────┬──────────────────┐
│ 阶段       │ 流量比例   │ 观察时长      │ 参与者    │ 通过标准          │
├────────────┼───────────┼──────────────┼───────────┼──────────────────┤
│ 开发自测   │ 开发者本人 │ 持续         │ 内部      │ 功能正确          │
│ 内测       │ 1%        │ 1~2 天       │ 内部员工  │ 无 P0/P1 崩溃     │
│ 灰度一     │ 5%        │ 24~48 小时   │ 种子用户  │ Crash 率不劣化    │
│ 灰度二     │ 20%       │ 24~48 小时   │ 扩大      │ Crash/ANR/启动达标 │
│ 灰度三     │ 50%       │ 24~48 小时   │ 半数      │ 业务指标正向      │
│ 全量       │ 100%      │ 持续观察 7 天 │ 全部      │ 无异常            │
└────────────┴───────────┴──────────────┴───────────┴──────────────────┘

★ 每一阶段都必须"用数据决定是否进入下一阶段"，而不是"到时间了就进"。
★ 任一阶段不达标 → 立即停止扩大（不必回滚，见 §7 熔断）
```

**观察时长的选择**：
- **至少覆盖一个"日周期"**：因为很多问题只在特定时段出现（如早高峰的并发问题、凌晨的定时任务冲突）。
- **必须覆盖"周末"**：Android 的用户活跃度在周末和工作日差异很大，很多崩溃只在低版本设备的特定操作路径上。
- **建议 48 小时起**：24 小时往往只覆盖了一个使用模式。

### 4. A/B 测试原理与分流一致性

#### 4.1 A/B 与灰度的区别

| 维度 | **灰度发布** | **A/B 测试** |
| --- | --- | --- |
| **目的** | **验证"新版本没毛病"**（稳定性） | **验证"新方案更好"**（业务效果） |
| **成功标准** | Crash 率、ANR 率、启动耗时 | 转化率、留存、客单价 |
| **对比对象** | 新版本 vs **旧版本（基线）** | 方案 A vs 方案 B（**平权**） |
| **失败处理** | 立即回滚 | 保留原方案 |

> **关键**：灰度是"**新 vs 旧**"（有先后关系），A/B 是"**A vs B**"（平权同时进行）。**灰度期不要用业务指标做决策**——因为新用户群和老用户群本身就有差异（先升级的用户往往更活跃），业务指标的差异不是新版本带来的。

#### 4.2 分流一致性（Sharding Consistency）

这是 A/B 实验最容易出错的地方：

```text
❌ 错误做法：客户端自己随机
   if (Random.nextInt(100) < 50) showVariantA() else showVariantB()
   → 用户每次启动可能看到不同版本 → 数据完全不可信

❌ 错误做法：按安装时间分桶
   → 新装用户全在 B 组、老用户全在 A 组 → 两组用户画像完全不同

✅ 正确做法：服务端分桶 + 本地缓存
   ① 首次启动 → 请求服务端 → 服务端按【稳定 ID】计算分组
   ② 服务端把分组结果【持久化到客户端】
   ③ 后续启动读本地缓存，不再请求
```

**分流必须"稳定"的四个层次**：

| 层次 | 要求 | 实现 |
| --- | --- | --- |
| **① 用户级稳定** | 同一用户永远在同一组 | 服务端用 `userId` 计算 + 客户端持久化 |
| **② 跨端一致** | 同一用户在不同设备（手机/平板）同组 | 服务端计算（不是客户端） |
| **③ 跨会话稳定** | 杀进程重开不变 | 持久化到本地（SharedPreferences / DataStore） |
| **④ 分流无偏** | 各组的用户画像基本一致 | 哈希 + 盐 + 校验分布 |

**稳定 ID 的选择**：

| 候选 ID | 优点 | 缺点 |
| --- | --- | --- |
| **设备 ID（ANDROID_ID）** | 无需登录 | **重置工厂设置会变**；部分 ROM 在 Android 8+ 每用户不同；多用户设备不共享 |
| **自生成 UUID（存 DataStore）** | 稳定可控 | 卸载重装会丢 |
| **用户 ID（登录后）** | **最稳定**，跨端一致 | 未登录用户无法分组 → 需先登录或用设备 ID 兜底 |
| **账号体系 + 设备指纹 组合** | 最完善 | 实现复杂 |

**实践推荐**：**登录后用 userId（服务端计算），未登录用设备 ID（客户端计算 + 持久化）**。登录时把设备组的分组"继承"到用户组。

### 5. 功能开关（Feature Flag）

#### 5.1 Feature Flag 的四种类型

| 类型 | 生命周期 | 例子 | 清理要求 |
| --- | --- | --- | --- |
| **发布开关（Release Flag）** | 临时（1~2 个版本） | "新版首页" | **必须清理**，否则变成"僵尸开关" |
| **实验开关（Experiment Flag）** | 临时（几周） | "新按钮颜色 A/B" | 必须清理 |
| **运营开关（Ops Flag）** | 长期 | "活动入口显示/隐藏" | 定期清理 |
| **Kill Switch（熔断开关）** | 长期 | "支付功能总开关" | **永远保留** |

#### 5.2 开关的实现层级

```text
┌────────────────────────────────────────────────────────────────────────┐
│  ① 云端开关（Firebase Remote Config / 自研配置中心）                     │
│     特点：可实时下发，无需发版；弱网时需要本地缓存兜底                      │
│     适用：运营开关、实验开关、Kill Switch                                │
├────────────────────────────────────────────────────────────────────────┤
│  ② 构建期开关（BuildConfig / productFlavor）                           │
│     特点：编译期确定，代码可被 R8 完全裁剪（包体更小、无法被绕过）           │
│     适用：渠道差异、永久性功能差异                                       │
├────────────────────────────────────────────────────────────────────────┤
│  ③ 本地开关（DataStore / SharedPreferences）                            │
│     特点：极快、可离线；但无法远程变更                                    │
│     适用：用户个人设置、A/B 分组缓存                                     │
└────────────────────────────────────────────────────────────────────────┘
```

**实战推荐**：**"云端开关 + 本地缓存 + 硬编码兜底值"**三层结构。
- 云端拉取成功 → 用云端值（实时生效）。
- 云端拉取失败 / 未拉到 → 用本地缓存值。
- 首次启动、缓存都没有 → 用**代码里写死的默认值**（通常是最安全的旧行为）。

> **面试话术**："Feature Flag 我会**分四类管理**：**发布开关、实验开关、运营开关、Kill Switch**。前两类**必须在上线后 1~2 个版本内清理掉**，否则半年后没人知道这个开关是干什么的，改代码时不敢删——这就是'**僵尸开关**'。实现上我用**云端下发 + 本地缓存 + 硬编码兜底值**三层：云端实时生效，弱网用缓存，首次启动用代码里的安全默认值。**兜底值一定要是'保守行为'**——新功能没拉到配置时，宁可不显示也不要出错。"

#### 5.3 开关的下发与客户端设计

```text
【App 启动】
  ① 读本地缓存的开关配置（DataStore，毫秒级）
  ② 立即按缓存值渲染首屏（不等待网络）
  ③ 后台异步请求最新配置
  ④ 拉到新配置 → 校验合法性 → 写入缓存 → 通知需要刷新的地方
  ⑤ 下次冷启动生效（或对"可热切换"的开关立即生效）
```

**关键设计点**：
- **首屏绝不能等网络**——这是启动耗时的大忌。
- **配置要有 schema 版本号和合法性校验**：服务端下发了格式错误的配置，客户端必须能识别并丢弃，而不是崩溃。
- **开关的"值"要能表达灰度维度**：不只是 `true/false`，还可以是 `{ enabled: true, rolloutPercentage: 5 }`。

### 6. 灰度期监控指标

```text
┌────────────────────────────────────────────────────────────────────────┐
│  ① 稳定性指标（最重要，优先级最高）                                      │
│     ├─ Crash 率（用户感知崩溃率 / 会话崩溃率）                           │
│     ├─ ANR 率                                                          │
│     ├─ Java 异常率（未崩溃但被捕获的异常）                                │
│     └─ Native 崩溃率                                                    │
├────────────────────────────────────────────────────────────────────────┤
│  ② 性能指标                                                            │
│     ├─ 冷启动耗时 P50 / P90 / P99（TTID）                               │
│     ├─ 首屏渲染耗时                                                       │
│     ├─ 帧率 / 卡顿率 / 冻结帧率                                          │
│     ├─ 内存峰值 / OOM 率                                                 │
│     └─ 包体大小（下载完成率受此影响）                                      │
├────────────────────────────────────────────────────────────────────────┤
│  ③ 网络指标                                                            │
│     ├─ 请求成功率 / 失败率（按接口维度）                                   │
│     ├─ 请求耗时 P95                                                     │
│     ├─ 流量消耗（4G 用户尤其敏感）                                        │
│     └─ 超时率                                                            │
├────────────────────────────────────────────────────────────────────────┤
│  ④ 业务指标（灰度期的参考项，决策要看趋势而非绝对值）                       │
│     ├─ 核心流程转化率（下单、支付、发布）                                  │
│     ├─ DAU / 新增用户 / 留存                                             │
│     ├─ 客单价 / ARPU                                                     │
│     └─ 卸载率（★ 最灵敏的负面信号）                                       │
├────────────────────────────────────────────────────────────────────────┤
│  ⑤ 体验指标                                                            │
│     ├─ 卸载率                                                            │
│     ├─ 应用商店评分变化                                                   │
│     └─ 用户反馈量（客服工单、舆情）                                        │
└────────────────────────────────────────────────────────────────────────┘
```

**核心指标阈值参考**（基于 Google Android Vitals，见 [[日志与监控/性能监控]]）：

| 指标 | 良好 | 可接受 | 必须回滚 |
| --- | --- | --- | --- |
| **Crash 率（会话）** | < 0.10% | < 0.47% | > 1.09% |
| **用户感知 Crash 率** | < 0.09% | < 0.47% | > 0.47% |
| **ANR 率** | < 0.47% | < 8% | > 8% |
| **启动耗时 P90** | < 2s | < 5s | > 5s |

> ⚠️ **阈值不能直接抄**，要用**灰度组 vs 基线组的相对变化**来判定。绝对值 0.5% 的崩溃率，如果基线组本来就是 0.48%，那灰度组是正常的；如果基线组是 0.05%，那灰度组就是灾难。

### 7. 崩溃率对比（灰度组 vs 基线组）

这是灰度决策的**核心算法**：

```text
【分组定义】
  灰度组：分桶命中灰度的设备
  基线组：同一时间窗口内，分桶未命中灰度的设备（★ 不是"上一版本用户"）

【为什么基线组要同期】
  旧版本用户和灰度组用户画像不同（活跃度、网络、设备档次都不同）
  → 必须用【同一时刻】的未灰度用户作对照，才能排除"时间因素"和"用户差异"

【对比公式】
  相对劣化率 = (灰度组 Crash 率 - 基线组 Crash 率) / 基线组 Crash 率

【判定】
  相对劣化率 > 20%  且  绝对差值 > 0.05%  →  告警
  相对劣化率 > 50%  且  灰度组 Crash 率 > 0.5%  →  自动熔断
```

**为什么必须"绝对差值 + 相对变化"两个条件同时满足**：
- **只看相对变化**：基线组 Crash 率是 0.01% 时，灰度组 0.011% 相对劣化 10%——但绝对只多了 0.001%，用户完全无感，**误报**。
- **只看绝对差值**：基线组 1.0%（本来就有问题）、灰度组 1.1%，绝对差 0.1% 看着大——但那是**存量问题**，不是新版本引入的，**误报**。

**统计显著性**：灰度 1% 流量下，Crash 率只有 0.1% 时，1 万台设备只有 10 次崩溃——**样本量太小，噪声很大**。所以：
- 灰度早期用**绝对差值 + 人工判断**。
- 灰度扩大后（≥20%）用**统计检验**（双比例检验 / 卡方检验）。
- 或者用 **Crash Free Sessions / Crash Free Users** 这类指标（Google Play Console 用的是这个）。

**"Crash Free Users"（无崩溃用户占比）**比"Crash 率"更常用：
```text
Crash Free Users = 1 - (崩溃用户数 / 活跃用户数)
Crash Free Sessions = 1 - (崩溃会话数 / 总会话数)
```
Google Play 的门槛是 **Crash Free Users ≥ 99.8%** 才能进入 production（这是硬性条件）。

### 8. 自动熔断与回滚

```text
┌────────────────────────────────────────────────────────────────────────┐
│  监控数据（每 5~15 分钟聚合一次）                                        │
│       │                                                                 │
│       ▼                                                                 │
│  ① 计算灰度组 vs 基线组的指标差异                                          │
│       │                                                                 │
│       ▼                                                                 │
│  ② 阈值判定（多信号：Crash 率 / ANR 率 / 启动耗时 / 卸载率）               │
│       │                                                                 │
│       ├── 未达标 ──→ 继续观察                                              │
│       │                                                                 │
│       ├── 预警（黄）──→ 通知群，人工介入                                    │
│       │                                                                 │
│       └── 熔断（红）──→ ③ 自动执行止损动作                                  │
│                            │                                             │
│                            ├─ 动作 A：关闭功能开关（秒级，无需发版）★首选       │
│                            ├─ 动作 B：暂停灰度扩大（灰度组保持在当前比例）        │
│                            ├─ 动作 C：热修复下发（需审核，小时级）                │
│                            └─ 动作 D：Play 分阶段发布回滚（已装用户无效）         │
└────────────────────────────────────────────────────────────────────────┘
```

**四种止损动作的对比（这是最重要的认知）**：

| 动作 | 生效时间 | 影响范围 | 依赖 | 适用 |
| --- | --- | --- | --- | --- |
| **A. 关闭功能开关** | **秒~分钟** | 只影响新功能 | 远端配置 | **首选**：功能级问题 |
| **B. 暂停灰度扩大** | 秒 | 只影响新用户 | 运维操作 | 灰度阶段发现轻度问题 |
| **C. 热修复** | **小时~天**（审核） | 已安装用户 | 修复包 + 审核 | 代码级问题，必须修 |
| **D. Play 回滚** | **小时~天** | **只影响未升级用户** | 重新提交审核 | **几乎无效**（已升级的用户拿不到旧版） |

> **核心结论（面试必答）**：**"Play 的回滚不是真正的回滚"**。Play Console 的"回滚到上一版本"实际上是**提交一个新版本（内容是老版本）**，需要重新审核；而已经升级的用户**不会收到这个包**（Play 只向"选择自动更新且应用低于目标版本"的用户推送）。所以**真正的止损手段是功能开关和热修复**，必须提前准备好。
>
> 更进一步：**Google Play 的"暂停分阶段发布（Pause rollout）"** 是唯一能立即停止新用户升级的操作，但它**不能降级已安装用户**。

### 9. 灰度与 A/B 实验的指标体系对比

```text
【灰度发布】看的是"没出事"
  基线 = 同期未灰度用户
  指标 = Crash 率 / ANR 率 / 启动耗时 / 包体 / 卸载率
  判定 = 相对劣化在阈值内 → 扩大范围
  失败 = 立即停止扩大 + 关闭开关 + 修复

【A/B 实验】看的是"更好"
  基线 = 对照组（同时在线）
  指标 = 转化率 / 留存 / 客单价
  判定 = 统计显著（p < 0.05）且效应量足够大 → 全量采用
  失败 = 保留原方案
```

**混用是常见错误**：
- 用灰度期的业务指标做决策 → **新老用户画像差异导致误判**。
- 用 A/B 实验的统计显著性做灰度决策 → **灰度组的 Crash 率天然受"用户画像"影响**，不是版本造成的。
- **正确的分工**：灰度期用**稳定性和性能指标**把关（硬性门槛），业务指标只做**趋势观察**；A/B 实验用**业务指标**决策。

### 1. 灰度分桶服务（服务端）

```java
package com.example.release.service;

import java.nio.charset.StandardCharsets;
import java.security.MessageDigest;
import java.security.NoSuchAlgorithmException;

/**
 * 灰度分桶服务。
 *
 * 设计原则：
 * 1. 【稳定】：同一 stableId 永远落在同一个桶
 * 2. 【无偏】：哈希只依赖 stableId + 盐，与设备属性无关
 * 3. 【可解释】：能从桶号反推配置，方便排查
 * 4. 【可扩展】：支持多维度叠加（地域 × 机型 × 百分比）
 */
public class GrayReleaseService {

    /**
     * 固定盐值。
     *
     * ⚠️ 必须是【固定】的：盐变了会导致所有用户重新分桶，
     *    正在灰度的用户会被打乱，体验割裂。
     * ⚠️ 应该是【保密】的：公开了盐，攻击者可预测分桶做定向规避。
     */
    private static final String SALT = "gr-2024-release-v1";

    /** 分桶总数：用 10000 而不是 100，便于表达 0.01% 粒度 */
    private static final int TOTAL_BUCKETS = 10_000;

    /**
     * 计算分桶号。
     *
     * @param stableId 稳定标识：优先用 userId，未登录用设备稳定 ID
     * @return 桶号 [0, 10000)
     */
    public int bucketOf(String stableId) {
        // 使用 SHA-256 的前 8 字节做无符号整数
        long hash = sha256ToLong(SALT + ":" + stableId);
        return (int) Math.floorMod(hash, (long) TOTAL_BUCKETS);
    }

    /**
     * 判断用户是否命中灰度。
     *
     * @param rolloutPercentage 灰度比例，0~100（支持小数）
     */
    public boolean isInRollout(String stableId, double rolloutPercentage) {
        int threshold = (int) Math.round(rolloutPercentage / 100.0 * TOTAL_BUCKETS);
        return bucketOf(stableId) < threshold;
    }

    /**
     * 白名单强制命中（内测阶段必须叠加在百分比策略之上）。
     */
    public boolean isInRollout(String stableId, double rolloutPercentage,
                                java.util.Set<String> whitelist) {
        if (whitelist.contains(stableId)) {
            return true;
        }
        return isInRollout(stableId, rolloutPercentage);
    }

    /**
     * 多维度组合灰度：先按地域筛，再按机型筛，最后按百分比分桶。
     */
    public boolean isInRollout(GrayRequest request) {
        // 维度 1：地域
        if (request.getAllowedRegions() != null
                && !request.getAllowedRegions().isEmpty()
                && !request.getAllowedRegions().contains(request.getRegion())) {
            return false;
        }
        // 维度 2：系统版本下限
        if (request.getMinOsVersion() > 0 && request.getOsVersion() < request.getMinOsVersion()) {
            return false;
        }
        // 维度 3：设备型号排除（规避问题机型）
        if (request.getExcludedModels().contains(request.getDeviceModel())) {
            return false;
        }
        // 维度 4：百分比分桶
        return isInRollout(request.getStableId(), request.getRolloutPercentage(),
                request.getWhitelist());
    }

    private static long sha256ToLong(String input) {
        try {
            MessageDigest digest = MessageDigest.getInstance("SHA-256");
            byte[] hash = digest.digest(input.getBytes(StandardCharsets.UTF_8));
            // 取前 8 字节拼成 long（保证非负）
            long value = 0;
            for (int i = 0; i < 8; i++) {
                value = (value << 8) | (hash[i] & 0xFFL);
            }
            return value & Long.MAX_VALUE;
        } catch (NoSuchAlgorithmException e) {
            throw new IllegalStateException("SHA-256 not available", e);
        }
    }
}
```

### 2. 客户端功能开关 SDK

```kotlin
package com.example.core.feature

import android.content.Context
import androidx.datastore.preferences.core.edit
import androidx.datastore.preferences.core.stringPreferencesKey
import androidx.datastore.preferences.preferencesDataStore
import kotlinx.coroutines.CoroutineScope
import kotlinx.coroutines.flow.first
import kotlinx.coroutines.launch
import kotlinx.serialization.json.Json
import kotlinx.serialization.json.JsonObject
import kotlinx.serialization.json.jsonPrimitive

private val Context.featureStore by preferencesDataStore(name = "feature_config")

/**
 * 功能开关 SDK。
 *
 * 核心设计：
 * 1. 【三级兜底】：云端值 → 本地缓存 → 代码硬编码默认值
 *    任何一层失败都能得到一个【安全的行为】
 * 2. 【首屏不等网络】：启动时同步读缓存（DataStore 很快），异步刷新云端
 * 3. 【配置校验】：云端下发的配置必须先校验，非法就丢弃
 * 4. 【可观测】：开关的命中率、异常率都要上报
 */
class FeatureFlagManager(
    private val context: Context,
    private val scope: CoroutineScope,
    private val remoteSource: RemoteConfigSource,
    private val reporter: FeatureFlagReporter
) {

    private val json = Json { ignoreUnknownKeys = true }

    /** 内存缓存：首屏同步读取，避免每次 get 都走磁盘 */
    @Volatile
    private var memoryCache: Map<String, FeatureConfig> = emptyMap()

    /**
     * 启动时调用：读取本地缓存（同步可用）+ 后台刷新云端。
     */
    suspend fun initialize() {
        // 1. 读本地缓存（DataStore 首次读取约几毫秒）
        val cachedJson = context.featureStore.data.first()[KEY_CONFIG_JSON]
        if (cachedJson != null) {
            memoryCache = parseSafely(cachedJson)
        }

        // 2. 后台刷新云端
        scope.launch {
            runCatching {
                val remote = remoteSource.fetch()
                val parsed = parseSafely(remote)
                if (parsed.isNotEmpty()) {
                    memoryCache = parsed
                    // 持久化，下次冷启动直接可用
                    context.featureStore.edit { it[KEY_CONFIG_JSON] = remote }
                    reporter.onConfigUpdated(parsed)
                }
            }.onFailure {
                // ★ 拉取失败不是错误：用缓存/默认值继续跑，不能影响启动
                reporter.onFetchFailed(it)
            }
        }
    }

    /**
     * 获取开关值。
     *
     * @param defaultValue 代码里的兜底默认值，★ 必须是【保守/安全】的行为
     */
    fun isEnabled(key: String, defaultValue: Boolean = false): Boolean {
        val config = memoryCache[key] ?: return defaultValue
        return config.enabled
    }

    /**
     * 获取带灰度比例的开关（客户端二次分桶）。
     *
     * ⚠️ 服务端已经分过桶时，直接用服务端的结论；
     *    这里的客户端分桶是【兜底】方案（服务端不可用时）。
     */
    fun isEnabledWithRollout(
        key: String,
        stableId: String,
        defaultValue: Boolean = false
    ): Boolean {
        val config = memoryCache[key] ?: return defaultValue
        if (!config.enabled) return false

        // 客户端分桶：与服务端算法保持一致（同样的盐、同样的桶数）
        val bucket = ClientGrayBucketer.bucketOf(stableId)
        val threshold = (config.rolloutPercentage / 100.0 * ClientGrayBucketer.TOTAL_BUCKETS).toInt()
        return bucket < threshold
    }

    /**
     * 解析云端配置，非法配置直接丢弃（不能因为配置错误让 App 崩溃）。
     */
    private fun parseSafely(raw: String): Map<String, FeatureConfig> {
        return try {
            val root = json.parseToJsonElement(raw).jsonObject
            val configs = root["features"]?.jsonObject?.mapValues { (_, element) ->
                val obj = element.jsonObject
                FeatureConfig(
                    enabled = obj["enabled"]?.jsonPrimitive?.content?.toBoolean() ?: false,
                    rolloutPercentage = obj["rollout"]?.jsonPrimitive?.content?.toDoubleOrNull() ?: 0.0,
                    expireAt = obj["expireAt"]?.jsonPrimitive?.content?.toLongOrNull() ?: 0L
                )
            } ?: emptyMap()

            // ★ 校验：过期配置视为关闭（防止服务端忘记关开关）
            val now = System.currentTimeMillis()
            configs.filterValues { it.expireAt == 0L || it.expireAt > now }
        } catch (e: Exception) {
            emptyMap()   // 解析失败 → 用空配置 → 全部走默认值
        }
    }

    data class FeatureConfig(
        val enabled: Boolean,
        val rolloutPercentage: Double,
        val expireAt: Long
    )

    companion object {
        private val KEY_CONFIG_JSON = stringPreferencesKey("feature_config_json")
    }
}

/**
 * 客户端分桶器（与服务端算法严格一致）。
 */
object ClientGrayBucketer {
    const val TOTAL_BUCKETS = 10_000
    private const val SALT = "gr-2024-release-v1"

    fun bucketOf(stableId: String): Int {
        val digest = java.security.MessageDigest.getInstance("SHA-256")
            .digest("$SALT:$stableId".toByteArray())
        var value = 0L
        for (i in 0 until 8) {
            value = (value shl 8) or (digest[i].toLong() and 0xFFL)
        }
        return (value and Long.MAX_VALUE).toInt() % TOTAL_BUCKETS
    }
}
```

### 4. 灰度指标对比与熔断判定（服务端）

```java
package com.example.release.service;

import java.util.List;
import java.util.Map;

/**
 * 灰度监控与自动熔断。
 *
 * 核心算法：灰度组 vs 【同期基线组】的相对劣化判定。
 */
public class GrayMonitorService {

    /** 熔断配置 */
    public static class CircuitBreakerConfig {
        /**
         * 相对劣化阈值（%）：灰度组指标比基线组劣化超过这个比例就告警
         */
        public double relativeDegradationThreshold = 20.0;

        /**
         * 绝对差值阈值（百分点）：防止基线组极低时相对变化被放大
         */
        public double absoluteDiffThreshold = 0.05;

        /**
         * 自动熔断的相对劣化阈值（更严格）
         */
        public double autoRollbackRelativeThreshold = 50.0;

        /**
         * 自动熔断的绝对 Crash 率下限（灰度组自身不能太差）
         */
        public double autoRollbackAbsoluteRate = 0.005;

        /** 最小样本量：样本不足时不做自动判定（噪声太大） */
        public long minSampleSize = 10_000;

        /** 判定周期（分钟） */
        public int evaluationIntervalMinutes = 15;
    }

    /**
     * 一次评估的结果。
     */
    public static class EvaluationResult {
        private boolean healthy;
        private boolean shouldRollback;
        private String reason;
        private Map<String, MetricComparison> comparisons;

        // getters / setters
        }

    public static class MetricComparison {
        private String metricName;
        private double rolloutValue;
        private double baselineValue;
        private double absoluteDiff;
        private double relativeDegradation;   // %
        private boolean passed;

        // getters / setters
    }

    /**
     * 执行一次灰度评估。
     *
     * @param rolloutStats  灰度组统计（来自 APM）
     * @param baselineStats 基线组统计（★ 同期、同指标、非灰度设备）
     */
    public EvaluationResult evaluate(
            String releaseId,
            Map<String, Double> rolloutStats,
            Map<String, Double> baselineStats,
            long rolloutSampleSize,
            long baselineSampleSize,
            CircuitBreakerConfig config) {

        EvaluationResult result = new EvaluationResult();
        result.setHealthy(true);
        result.setShouldRollback(false);

        // ★ 样本量不足 → 不做自动判定，只做监控
        if (rolloutSampleSize < config.getMinSampleSize()
                || baselineSampleSize < config.getMinSampleSize()) {
            result.setReason("样本量不足（灰度组=" + rolloutSampleSize
                    + ", 基线组=" + baselineSampleSize + "），仅监控不判定");
            return result;
        }

        Map<String, MetricComparison> comparisons = new java.util.HashMap<>();
        boolean shouldRollback = false;
        boolean healthy = true;
        StringBuilder reason = new StringBuilder();

        for (String metric : rolloutStats.keySet()) {
            Double rolloutValue = rolloutStats.get(metric);
            Double baselineValue = baselineStats.get(metric);

            // ★ 关键：基线组为 0 时不做相对计算（除零），只看绝对差值
            if (rolloutValue == null || baselineValue == null) continue;

            double absDiff = rolloutValue - baselineValue;
            double relative = (baselineValue == 0.0)
                    ? (absDiff > 0 ? Double.POSITIVE_INFINITY : 0.0)
                    : (absDiff / baselineValue) * 100.0;

            MetricComparison cmp = new MetricComparison();
            cmp.setMetricName(metric);
            cmp.setRolloutValue(rolloutValue);
            cmp.setBaselineValue(baselineValue);
            cmp.setAbsoluteDiff(absDiff);
            cmp.setRelativeDegradation(relative);

            // ★ 双条件判定：相对劣化 + 绝对差值 同时超阈值
            boolean relativeExceeded = relative > config.getRelativeDegradationThreshold();
            boolean absoluteExceeded = absDiff > config.getAbsoluteDiffThreshold();
            cmp.setPassed(!(relativeExceeded && absoluteExceeded));

            if (!cmp.isPassed()) {
                healthy = false;
                reason.append(String.format(
                        "[%s 劣化] 灰度组=%.4f%%, 基线组=%.4f%%, 相对=%+.1f%%, 绝对=%+.4f%%; ",
                        metric, rolloutValue, baselineValue, relative, absDiff));

                // 自动熔断：更严格的双条件
                boolean rollbackRelative = relative > config.getAutoRollbackRelativeThreshold();
                boolean rollbackAbsolute = rolloutValue > config.getAutoRollbackAbsoluteRate();
                if (rollbackRelative && rollbackAbsolute) {
                    shouldRollback = true;
                }
            }
            comparisons.put(metric, cmp);
        }

        result.setComparisons(comparisons);
        result.setHealthy(healthy);
        result.setShouldRollback(shouldRollback);
        result.setReason(reason.length() > 0 ? reason.toString() : "全部指标正常");
        return result;
    }
}
```

### 5. 熔断执行器

```java
package com.example.release.service;

import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.springframework.scheduling.annotation.Scheduled;
import org.springframework.stereotype.Component;

import java.util.List;

/**
 * 熔断执行器：定时评估灰度指标，达标则自动执行止损。
 */
@Component
public class CircuitBreakerExecutor {

    private static final Logger log = LoggerFactory.getLogger(CircuitBreakerExecutor.class);

    private final GrayMonitorService monitorService;
    private final RemoteConfigService remoteConfigService;   // 功能开关服务
    private final AlertService alertService;                  // 告警（企微/邮件）
    private final ActiveReleaseRepository releaseRepository;  // 活跃发布记录

    /**
     * 每 15 分钟评估一次所有进行中的灰度发布。
     */
    @Scheduled(fixedDelay = 15 * 60 * 1000)
    public void evaluateAllActiveReleases() {
        List<ActiveRelease> activeReleases = releaseRepository.findAllActive();
        for (ActiveRelease release : activeReleases) {
            try {
                evaluateOne(release);
            } catch (Exception e) {
                log.error("评估灰度发布失败: releaseId={}", release.getReleaseId(), e);
            }
        }
    }

    private void evaluateOne(ActiveRelease release) {
        // 1. 拉取两组的指标（灰度组 + 同期基线组）
        MetricsSnapshot rollout = apmClient.query(release.getReleaseId(), true);
        MetricsSnapshot baseline = apmClient.query(release.getReleaseId(), false);

        // 2. 判定
        GrayMonitorService.EvaluationResult result = monitorService.evaluate(
                release.getReleaseId(),
                rollout.getCrashRate(), rollout.getAnrRate(), rollout.getStartupP90(),
                baseline.getCrashRate(), baseline.getAnrRate(), baseline.getStartupP90(),
                rollout.getSessionCount(), baseline.getSessionCount(),
                release.getCircuitBreakerConfig()
        );

        // 3. 健康 → 记录，可能推进到下一阶段
        if (result.isHealthy()) {
            releaseRepository.recordHealthyCheck(release.getReleaseId());
            // ★ 推进阶段也应该由数据驱动，而不是定时器
            if (shouldAdvanceStage(release, result)) {
                advanceStage(release);
            }
            return;
        }

        // 4. 不健康 → 告警
        alertService.sendGrayAlert(release, result);

        // 5. ★ 自动熔断：执行止损动作
        if (result.isShouldRollback()) {
            executeRollback(release, result);
        } else {
            // 仅预警：暂停扩大范围，但保留当前灰度
            releaseRepository.pauseExpansion(release.getReleaseId());
            log.warn("灰度预警，已暂停扩大范围: releaseId={}, reason={}",
                    release.getReleaseId(), result.getReason());
        }
    }

    /**
     * 执行止损动作（按优先级）。
     */
    private void executeRollback(ActiveRelease release, GrayMonitorService.EvaluationResult result) {
        String releaseId = release.getReleaseId();

        // 动作 A（首选，秒级生效）：关闭功能开关
        // ★ 只有当问题可以通过关闭功能规避时才执行
        if (isFeatureToggleable(release)) {
            boolean success = remoteConfigService.disableFeature(
                    release.getFeatureKey(), release.getTargetRatio(),
                    "auto_circuit_breaker:" + result.getReason());
            if (success) {
                log.error("★ 自动熔断：已关闭功能开关 featureKey={}, releaseId={}",
                        release.getFeatureKey(), releaseId);
                releaseRepository.markRolledBack(releaseId, "feature_disabled");
                alertService.sendRollbackNotice(release, result);
                return;
            }
        }

        // 动作 B：暂停灰度扩大（已安装用户不受影响，作为次优）
        releaseRepository.pauseExpansion(releaseId);
        log.error("★ 自动熔断：已暂停灰度扩大 releaseId={}", releaseId);

        // 动作 C（人工）：触发热修复流程
        // Play 的回滚对已升级用户无效，所以必须走热修复
        hotfixService.createTask(release, result.getReason());

        alertService.sendRollbackNotice(release, result);
    }

    /**
     * 判断该发布是否可以通过关闭功能开关来规避问题。
     *
     * ⚠️ 不是所有问题都能靠开关规避：
     *    - 新代码引入的崩溃（即使功能关闭，代码路径可能仍被执行）→ 需要热修复
     *    - 性能退化（全局性的）→ 通常无法靠开关规避
     */
    private boolean isFeatureToggleable(ActiveRelease release) {
        return release.getIssueType() == IssueType.FEATURE_SPECIFIC
                && release.getFeatureKey() != null;
    }
}
```

## 常见问题 / 面试要点

**读者问：灰度发布怎么做？分桶怎么设计？**

**AI答：**

1. **分桶的四个要求**：
   - **稳定**：同一设备/用户永远在同一桶（否则用户反复横跳，投诉不断）。
   - **无偏**：哈希只依赖稳定 ID + 固定盐，**与设备属性无关**（否则可能恰好把某厂商某系统版本的用户全分到一组，对比数据失真）。
   - **可解释**：能从桶号反推配置，方便排查"为什么这个用户看到了新功能"。
   - **可叠加**：白名单 + 地域 + 系统版本 + 百分比，AND 关系。
2. **分桶算法**：`bucket = SHA256(盐 + ":" + stableId) % 10000`，灰度比例 5% 就是 `bucket < 500`。
   - **用 10000 而不是 100**：支持 0.01% 粒度（先放 10 台设备验证）。
   - **盐必须固定且保密**：变了会重新分桶（正在灰度的用户被打乱），公开了会被预测。
3. **稳定 ID 的选择**（分层降级）：
   - **登录后用 userId**（最稳定，跨设备一致）——最佳。
   - **未登录用自生成 UUID 持久化到 DataStore**（卸载重装会丢，但干净）。
   - **ANDROID_ID 只作兜底**（Android 8+ 按用户+按签名生成，重置工厂设置会变）。
   - **注意**：登录时要把"设备组的分组"继承到"用户组"，否则登录前后用户会"换组"。
4. **谁来做分桶**：
   - **服务端分桶 + 结果持久化到客户端**（推荐）——跨端一致、可控。
   - **客户端分桶**（兜底）——服务端不可用时用，但算法必须与服务端**完全一致**（同样的盐、同样的桶数、同样的哈希）。
5. **多维度组合**：地域（先东南亚再欧洲）、系统版本（Android 10+ 先发）、机型（避开问题机型）、渠道。
6. **面试话术**："灰度分桶我会保证四点：**稳定、无偏、可解释、可叠加**。算法是 `SHA256(固定盐 + 稳定ID) % 10000`，用 10000 而不是 100 是为了支持 0.01% 粒度。**盐必须固定且保密**——固定是为了不重新洗牌，保密是为了不被预测。稳定 ID 分层选：**登录用 userId，未登录用持久化的 UUID，ANDROID_ID 只兜底**。而且我会**优先服务端分桶**，客户端分桶只作兜底算法，**两边算法必须严格一致**，否则同一个人在两端看到不同版本，实验数据就废了。"

**读者问：灰度期间看什么指标？怎么判断能不能扩大灰度范围？**

**AI答：**

1. **指标分四类，优先级从高到低**：
   | 类别 | 指标 | 为什么 |
   | --- | --- | --- |
   | **稳定性（最高）** | Crash 率、ANR 率、Java 异常率、Native 崩溃率 | 出问题直接是 P0 |
   | **性能** | 冷启动 P50/P90/P99、首屏、帧率、OOM 率、包体 | 劣化会被用户感知 |
   | **网络** | 请求成功率、耗时 P95、流量、4G 超时率 | 网络问题在灰度期最容易被放大 |
   | **业务（参考）** | 转化率、留存、卸载率 | ⚠️ **只看趋势，不做决策依据** |
2. **⚠️ 灰度期不要用业务指标做决策**。原因：**灰度组和基线组的用户画像天然不同**（先升级的用户往往更活跃、更愿意尝鲜），业务指标的差异**不是新版本造成的**。业务指标要靠 A/B 实验（平权分流）来评估。
3. **判定必须用"灰度组 vs 同期基线组"**：
   - **基线组必须是同期同指标的非灰度用户**，不能是"上一版本的历史数据"——否则混入了时间因素和用户差异。
   - **判定公式**：`相对劣化 = (灰度组 - 基线组) / 基线组`。
4. **必须"相对变化 + 绝对差值"双条件**（这是最容易被追问的点）：
   - **只看相对**：基线组 0.01%、灰度组 0.011% → 相对劣化 10%，但绝对只多 0.001%，用户完全无感，**误报**。
   - **只看绝对**：基线组本来就 1.0%（存量问题）、灰度组 1.1% → 看着差很多，但**不是新版本引入的**，**误报**。
   - **两个都超才告警**，能大幅降低误报率。
5. **样本量与统计显著性**：灰度 1% 时，Crash 率 0.1% 意味着 1 万台设备只有 10 次崩溃——**噪声极大**。所以早期靠绝对差值 + 人工判断，扩大到 ≥20% 后再用统计检验。Google Play 用的是 **Crash Free Users**（≥99.8% 才能进 production），比 Crash 率更好用。
6. **观察时长**：至少覆盖**一个完整日周期 + 周末**。很多问题只在特定时段出现。
7. **面试话术**："灰度期我会按**稳定性 > 性能 > 网络 > 业务**的优先级看指标。**稳定性是硬门槛**，Crash 率和 ANR 率必须不劣化；业务指标**只看趋势不做决策**，因为灰度组和基线组的用户画像本来就不一样，差异不是新版本造成的。判定上我一定用**同期基线组**做对照，而且是**相对劣化 + 绝对差值双条件**——只看相对会误报（基线极低时）、只看绝对也会误报（存量问题）。另外灰度早期样本量小，我用绝对差值加人工判断，扩大到 20% 以上才上统计检验。"

**读者问：灰度期间出现 Crash 怎么处理？怎么回滚？**

**AI答：**

1. **先说结论**：**"Play 的回滚不是真正的回滚"**——这是本题的核心。
   - Play Console 的"回滚到上一版本"实际是**提交一个新版本（内容是老版本）**，需要重新审核（小时到天级）。
   - **已经升级的用户收不到这个包**——Play 只向"低于目标版本"的用户推送。
   - 所以 **Play 的回滚只能防止坏版本扩散，不能修复已受影响的用户**。
2. **四种止损动作的时效与适用**：
   | 动作 | 生效时间 | 适用 | 依赖 |
   | --- | --- | --- | --- |
   | **A. 关闭功能开关** | **秒~分钟** | 功能级问题 | 远端配置（必须事先准备好开关） |
   | **B. 暂停灰度扩大** | 秒 | 轻度问题 | 运维操作。**Play 的"暂停分阶段发布"是唯一能立即停止新用户升级的操作** |
   | **C. 热修复** | 小时~天 | 代码级问题，必须修 | 修复包 + 审核流程 |
   | **D. Play 回滚** | 小时~天 | 阻止扩散 | 重新审核 |
5. **Crash 发生时的处置流程**：
   ```
   ① 告警（5~15 分钟内发现）
      → 立即暂停扩大范围（动作 B，秒级）
   ② 定位（30 分钟内）
      → 看崩溃平台：新增崩溃 Issue？堆栈？集中在哪个版本/机型/OS？
      → 判断是"功能相关"还是"全局性"
   ③ 决策
      · 功能相关 → 关闭功能开关（动作 A，秒级止损）
      · 全局性 / 开关无法规避 → 必须热修复（动作 C）
   ④ 复盘
      → 为什么测试没发现？为什么灰度没拦住？门禁要补什么？
   ```
6. **判断"能否靠关开关止损"的关键**：
   - **能**：新功能自身的崩溃（关闭功能后代码路径不再执行）。
   - **不能**：**新代码引入的公共路径问题**（比如改了一个公共工具类，即使功能关闭，别的功能也会崩）、**性能退化**（全局性的）。
   - **所以架构上要"功能隔离"**：新功能的代码路径尽量独立，出问题能"关掉一条路"而不是"炸掉整个 App"。
7. **预防比止损重要**：
   - **灰度前**：崩溃率基线要清楚（当前基线是多少？）。
   - **灰度中**：自动熔断（阈值 + 动作 A/B 自动执行）。
   - **发版前**：必须准备**功能开关**和**热修复包**的能力，否则出事只能干等审核。
8. **面试话术**："我会先强调一个认知：**Play 的回滚不是真回滚**——它本质是提交一个新版本要重新审核，而且**已经升级的用户收不到**，所以只能防扩散不能止损。真正的止损顺序是：**先暂停灰度扩大（秒级）→ 判断能否靠功能开关规避（能就关开关，秒级）→ 不能就热修复**。Play 回滚是最差选项。另外我会强调**架构上要让新功能代码路径独立**，因为只有这样才能'关掉一条路'而不是'炸掉整个 App'。防患于未然的做法是**灰度期做自动熔断**，阈值到了自动执行暂停/关开关。"

**读者问：A/B 测试怎么保证分流的一致性？和灰度有什么区别？**

**AI答：**

1. **灰度 vs A/B 的本质区别**：
   | | **灰度** | **A/B** |
   | --- | --- | --- |
   | 目的 | 验证"没出事" | 验证"更好" |
   | 对照 | **同期未灰度用户** | **同期对照组（平权）** |
   | 指标 | Crash/ANR/启动耗时 | 转化率/留存/客单价 |
   | 决策 | 阈值内就扩大 | 统计显著才全量 |
   | **失败处理** | 停止扩大 + 回滚 | 保留原方案 |
   - **一句话**：灰度是"**新 vs 旧**"（有时间差），A/B 是"**A vs B**"（平权同时）。
2. **分流一致性的四个层次**：
   - **① 用户级稳定**：同一用户永远同组 → 用 `userId` 计算 + 结果持久化。
   - **② 跨端一致**：手机和平板同组 → **必须服务端计算**（客户端算不出来）。
   - **③ 跨会话稳定**：杀进程重开不变 → 持久化到 DataStore。
   - **④ 无偏**：各组用户画像基本一致 → 哈希 + 盐 + **定期校验分布**（上报各组的机型/OS 分布，抽样对比）。
3. **三个经典错误**：
   - **客户端随机**：`Random.nextInt(100) < 50` → 每次启动可能变 → **数据完全不可信**。
   - **按安装时间分桶**：新装用户全在 B 组、老用户全在 A 组 → **两组画像完全不同**。
   - **登录时重新分桶**：登录前后分组变化 → 用户"换组" → 归因错误。正确做法是**登录时继承设备组的分组**。
4. **统计显著性的正确做法**：
   - **样本量估算**：先算"最小可检测效应（MDE）"和所需样本量，**不要拍脑袋定流量**。
   - **显著性检验**：双比例检验（z 检验）或卡方检验，**p < 0.05**。
   - **同时看效应量**：p < 0.05 但效应量只有 0.1%，**业务上无意义**，不要全量。
   - **多重比较校正**：同时跑 10 个实验时，用 Bonferroni 或 BH 校正，否则假阳性率飙升。
   - **不中途窥视**：频繁看结果并提前停止 → 显著率虚高（"peeking" 问题），应预先定好样本量和观察时长。
5. **A/B 实验的平台选择**：
   - **Firebase Remote Config + Analytics**：Google 生态首选，与 GA4 打通。
   - **自研实验平台**：需要分流、埋点、统计三大件。
   - **第三方**：GrowthBook、Optimizely、Amplitude Experiment。
6. **面试话术**："灰度和 A/B 的本质区别是**对照组的含义不同**：灰度是'新 vs 同期旧'，A/B 是'A vs B 平权'。分流一致性我要保证四层：**用户级稳定、跨端一致、跨会话稳定、无偏**。所以我**优先服务端分桶 + 结果持久化到客户端**。三个经典错误是：**客户端随机**（每次启动变）、**按安装时间分桶**（画像不同）、**登录时重新分桶**（用户换组）。统计上我会**先算样本量再定流量**，用双比例检验，同时看效应量——p<0.05 但效应量 0.1% 业务上没意义。灰度期我会**明确不用业务指标做决策**，因为新老用户画像差异不是版本造成的。"

**读者问：功能开关怎么设计？怎么防止开关变成"僵尸开关"？**

**AI答：**

1. **开关分四类**：
   | 类型 | 生命周期 | 例子 | 清理 |
   | --- | --- | --- | --- |
   | **发布开关** | 1~2 个版本 | "新版首页" | **必须清理** |
   | **实验开关** | 几周 | "按钮颜色 A/B" | 必须清理 |
   | **运营开关** | 长期 | "活动入口" | 定期清理 |
   | **Kill Switch** | 长期 | "支付总开关" | **永久保留** |
2. **"僵尸开关"的危害**（这是问题的本质）：
   - 代码里积累几百个开关，**没人知道哪个还有效**。
   - 半年后看到 `if (featureFlags.isEnabled("xxx"))`，**不敢删**——因为不知道谁在依赖。
   - 新人接手要逐个排查，**认知负担极大**。
   - **开关本身成为 bug 来源**：一个默认开着的旧开关，可能在新版本里意外启用老逻辑。
3. **防僵尸的四个机制**：
   - **① 集中管理 + 统一 key 常量**：所有开关 key 定义在一个 `FeatureFlags` 对象里，全局可搜索。
   - **② 登记清理计划**：每个开关创建时必须填"计划移除的版本号"，用 `CLEANUP_TRACKER` 跟踪。
   - **③ 发布流程卡点**：每个版本发布前，扫一遍 `CLEANUP_TRACKER`，到期的开关**必须删或续期**。
   - **④ 过期自动失效**：配置带 `expireAt`，过期视为关闭（防止服务端忘关）。
4. **三级兜底设计**（保证任何一层失败都有安全行为）：
   ```
   云端值（实时生效）
     ↓ 拉取失败 / 未拉到
   本地缓存值（DataStore，启动时同步读）
     ↓ 首次启动 / 缓存损坏
   代码硬编码默认值 ★ 必须是【保守行为】
   ```
   - **默认值必须是"旧行为"**：新功能没拉到配置时，宁可不显示也不要出错。
5. **首屏不等网络**：启动时**同步读本地缓存**（DataStore 几毫秒），**异步刷新云端**。这是启动耗时的大忌——功能开关绝不能成为启动阻塞点。
6. **配置校验**：云端下发可能格式错误，客户端必须能识别并**丢弃**，而不是崩溃。
7. **可观测性**：每个开关的**命中率、异常率**都要上报。否则你不知道这个开关到底有没有用户在走。
8. **面试话术**："功能开关我会**分四类管理**：发布开关、实验开关、运营开关、Kill Switch。前两类**必须在上线后一两个版本内清理**，否则就是'**僵尸开关**'——几百个开关没人知道哪个有效，改代码时不敢删，新人接手负担极大。防僵尸我会做四件事：**集中管理 key、创建时登记清理版本、发布流程卡点核对、配置带过期时间自动失效**。技术上必须**三级兜底**：云端 → 本地缓存 → 代码硬编码默认值，而且**默认值一定是保守的旧行为**。另外有个坑是**首屏绝不能等网络**——开关拉取只能异步，否则直接拖垮启动耗时。"

---

**读者问：灰度和热修复是什么关系？有了热修复还需要灰度吗？**

**AI答：**

1. **两者解决不同的问题，是互补关系**：
   | | **灰度** | **热修复** |
   | --- | --- | --- |
   | 解决什么 | **扩散控制**（不让问题波及全量） | **修复速度**（问题发生后快速止损） |
   | 时间尺度 | 发版前（预防） | 发版后（补救） |
   | 前提 | 新包还没发出去 | 新包已发出去了 |
2. **为什么有热修复还需要灰度**：
   - **热修复不能覆盖所有场景**：资源修复（布局/文案/图片）可以改；**代码修复受限于 ClassLoader 机制**（方法数限制、类结构变更无法热修）。
   - **热修复有审核延迟**：国内渠道的热修复包通常要 1~3 天审核（虽然可以走"静默下发 + 延迟生效"绕过，但有合规风险）。
   - **热修复是"补救"，灰度是"预防"**。**灰度能把问题挡在 1% 用户，热修复是等 1% 用户已经受害之后的补救**。
   - **热修复本身也需要灰度**：热修复包推给 100% 用户，如果补丁本身有 bug，影响面更大。**热修复包也要先灰度 1%**。
3. **完整的发布体系**（面试可以画这张图）：
   ```
   代码变更
     ↓
   CI 流水线（Lint → 单测 → 集成测试 → 构建）  ← [[../CI-CD/流水线设计]]
     ↓
   内测（功能开关 + 白名单）
     ↓
   灰度 1% → 5% → 20% → 50% → 100%      ← 本篇
     ↓  指标异常
   熔断：关开关（秒级）/ 暂停扩大 / 热修复
     ↓
   全量 + 持续监控（APM）
     ↓
   发现线上问题 → 热修复（小时~天）         ← [[热修复与动态化]]
     ↓
   下一个版本把热修复的改动合入主干（避免累积漂移）
   ```
4. **热修复代码要"合回主干"**：热修复包里的 patch 文件如果不合并回源码，下个版本会把这些改动**丢掉**，导致"修了两次"。这是热修复流程里最常见的疏漏。
5. **灰度 + 开关 + 热修复合起来的止损时间线**：
   - **T+0**：发布新版本。
   - **T+15分钟**：熔断系统检测到 Crash 率异常 → **自动暂停扩大**。
   - **T+30分钟**：人工确认问题范围 → 若可关开关，**关开关（秒级生效）**。
   - **T+2小时**：热修复包开发 + 自测 + 灰度。
   - **T+1~3天**：热修复审核通过 → 推送 → **热修复包自身也先灰度 1%**。
   - **T+7天**：全量热修复 + 把 patch 合回主干。
6. **面试话术**："灰度和热修复是**互补**的，不是替代关系。**灰度解决'扩散控制'——把问题挡在 1% 用户；热修复解决'修复速度'——问题发生后快速止损**。而且**热修复不能覆盖所有场景**（代码结构变更、Native、资源改不了），加上审核延迟 1~3 天，所以不能指望热修复来兜底所有情况。更重要的是**热修复包自己也要灰度**——推给 100% 用户如果有 bug 影响面更大。还有个容易漏的点：**热修复的改动必须合回主干**，否则下个版本这些改动就丢了，等于修了两次。"

**读者问：灰度期间怎么验证"分桶是无偏的"？如果分桶有问题，监控数据还能信吗？**

**AI答：**

1. **分桶无偏是所有灰度结论的前提**。如果灰度组恰好聚集了某厂商、某系统版本、某网络类型的用户，那"灰度组 Crash 率更高"可能**完全是用户画像造成的**，与新版本无关。**整个灰度决策就建立在沙子上。**
2. **必须主动校验的三组分布**：
   | 维度 | 为什么重要 |
   | --- | --- |
   | **设备档次**（高/中/低端） | 低端机内存小、CPU 弱，新版本更容易 OOM / 卡顿 |
   | **系统版本 / 厂商** | 某厂商 ROM 的兼容问题是常见崩溃来源 |
   | **网络类型 / 地域** | 弱网区域请求失败率高，会拉低成功率类指标 |
   - **校验方法**：分组上报各维度分布 → 服务端做**两组分布的差异检验**（卡方检验或直接看比例差）。
   - **判定标准**：某维度在灰度组的占比与基线组差异 **< 5 个百分点**算通过；超过则说明分桶或用户画像有偏，**需要把该维度加入分桶条件**。
3. **⚠️ 一个隐蔽的偏差源："先升级的用户"本身就不是随机样本**：
   - 灰度阶段用户是**主动或被动先升级**的那批人——可能更活跃（新功能尝鲜）、也可能更保守（系统提示才更新）。
   - **这会导致即使哈希完全均匀，灰度组和基线组的"活跃度"仍然不同**。
   - **缓解**：除了"百分比分桶"，再叠加一层**活跃度分层**（按历史活跃度把用户分成高/中/低层，每层内部再按 hash 分桶），保证两组的活跃度分布一致。
   - **或者**：把灰度扩展到 20% 以上，让"先升级"的用户占比稀释，画像差异变小。
4. **另一个隐蔽的偏差源：指标本身的统计性质**：
   - **Crash 率是"用户数"或"会话数"的函数**。灰度组用户如果启动次数更多（活跃度高），**会话数自然更多**，Crash 率的分母口径要统一。
   - **⚠️ 常见错误**：灰度组用"会话崩溃率"、基线组用"用户崩溃率" → **口径不一致，比出来的差异全是假的**。
   - **原则**：两个组必须用**完全相同的指标定义、相同的统计窗口、相同的数据延迟过滤规则**。
5. **上线前的"分桶自检"**：
   - 在**灰度还没开始前**，用**纯哈希分组**跑一次模拟（不发新版本），对比两组的机型/系统/地域分布。
   - **这一步能提前发现哈希分布不均的问题**（比如某些 stableId 前缀导致桶位偏移），成本极低。
6. **面试话术**："分桶无偏是灰度结论的前提——如果灰度组恰好聚集了低端机或某个厂商的用户，那 Crash 率更高可能完全是画像造成的。所以我会**主动校验三组分布：设备档次、系统版本/厂商、网络地域**，看两组差异是否小于 5 个百分点。还有个很隐蔽的偏差源是：**'先升级的用户'本身就不是随机样本**——他们可能更活跃，这会导致即使哈希完全均匀，两组的活跃度分布仍然不同，缓解办法是**先按活跃度分层、再在层内按 hash 分桶**。另外要特别注意**指标口径必须完全一致**，最常见的翻车是灰度组算会话崩溃率、基线组算用户崩溃率，比出来的差异全是假的。最后我会在**灰度开始前做一次纯哈希的分布自检**，成本极低但能提前发现哈希分布不均的问题。"

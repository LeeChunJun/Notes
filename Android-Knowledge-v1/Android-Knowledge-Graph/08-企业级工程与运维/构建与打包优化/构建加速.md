# 构建加速

## 一句话定义

构建加速是通过**减少不必要的计算、复用已完成的计算、并行化独立计算**这三件事，把"从代码变更到可安装 APK"的时间压到最短。它不只是"加机器"——**配置阶段的浪费、无效的缓存失效、串行执行的任务**，才是构建慢的主因。

面试开场：**"构建优化第一步永远是'测量'。我会先用 `--profile` 把时间拆成配置阶段和执行阶段，再看任务级的耗时排行——80% 的项目里，配置阶段占 30% 以上，这部分是最容易拿到的收益。"**

## 核心原理

### 1. 构建耗时的四个来源

```
┌────────────────────────────────────────────────────────────────────┐
│ ① 配置阶段（Configuration）                                         │
│    解析 build.gradle.kts、执行脚本、解析依赖、创建任务对象            │
│    特点：不需要改一行代码也会全量重来                                │
│    典型耗时：30% ~ 60%（多模块项目更严重）                          │
├────────────────────────────────────────────────────────────────────┤
│ ② 依赖下载与解析（Dependency Resolution）                            │
│    网络下载、Maven 元数据、POM 解析、版本冲突仲裁                    │
│    典型耗时：首次 5~10 分钟，之后靠缓存                              │
├────────────────────────────────────────────────────────────────────┤
│ ③ 任务执行（Execution）                                             │
│    资源处理、Kotlin 编译、Java 编译、dex、合并、打包                  │
│    特点：可通过增量 + 缓存 + 并行优化                                │
├────────────────────────────────────────────────────────────────────┤
│ ④ 增量失效（Invalidation）                                          │
│    改了 A 却重编了 B —— 依赖声明不精确、api/implementation 用错       │
│    典型耗时：占比最大，也最容易被忽视                                 │
└────────────────────────────────────────────────────────────────────┘
```

### 2. Gradle 构建生命周期

```
┌─ 配置阶段（Configuration Phase）─────────────────────────────┐
│  settings.gradle.kts  →  解析插件  →  解析依赖  →  执行脚本  │
│  →  创建 Task 对象（此时任务还没执行）                          │
│  ★ 这阶段的产物是一棵"任务执行图"                               │
├──────────────────────────────────────────────────────────────┤
│  执行阶段（Execution Phase）─────────────────────────────────┤
│  按依赖关系拓扑排序 → 并行执行独立任务                          │
│  compileKotlin → processResources → mergeDex → package        │
└──────────────────────────────────────────────────────────────┘
```

**关键认知**：**配置阶段和执行阶段是两个独立的世界**。配置阶段创建的 Task 对象是**执行阶段的输入**。这决定了两个重要优化方向：

- **配置缓存（Configuration Cache）**：把"配置阶段的产物"（任务图 + 配置结果）**序列化缓存**下来，下次直接用，跳过整个配置阶段。
- **Convention Plugin**：减少配置阶段的脚本执行量（少解析、少执行）。

### 3. 配置缓存（Configuration Cache）

#### 3.1 原理

```
【第一次构建】
  配置阶段：执行所有 build.gradle.kts  →  生成 Task 图 + 属性
  执行阶段：执行任务
  ★ 配置阶段结束时，把"任务图 + 所有可序列化状态"存入
    .gradle/configuration-cache/<hash>/entry.bin

【第二次构建（输入未变）】
  1. 计算当前构建的"指纹"（输入文件哈希 + 环境变量 + Gradle 属性...）
  2. 指纹命中 → 直接反序列化任务图
  3. 跳过整个配置阶段，直接执行任务
```

**命中条件**（任何一项变了就失效）：
- 构建脚本或任何 buildSrc / included build 的源码变化。
- `gradle.properties` 中的属性变化。
- 环境变量变化（**必须显式声明**，见下）。
- 命令行参数变化。
- **文件系统上被读取的文件**变化（如 `local.properties`）。

#### 3.2 配置

```properties
# gradle.properties
org.gradle.configuration-cache=true
org.gradle.configuration-cache.problems=warn    # 配置问题只警告不失败（迁移期）

# 并行执行
org.gradle.parallel=true

# 构建缓存
org.gradle.caching=true

# JVM 参数（CI 上很关键）
org.gradle.jvmargs=-Xmx4g -XX:MaxMetaspaceSize=1g -Dfile.encoding=UTF-8

# 守护进程
org.gradle.daemon=true

# 按需配置（ incubating，Gradle 8.x）
org.gradle.configureondemand=true

# Kotlin 编译执行策略
kotlin.compiler.execution.strategy=in-process    # 或 daemon / out-of-process
```

```kotlin
// build.gradle.kts：声明哪些系统属性影响构建，避免配置缓存频繁失效
// 必须在 build 脚本顶层（不能用 providers.gradleProperty 惰性读取）
val myApiUrl: String by settings
```

```groovy
// 对于读取系统属性/环境的场景，用 Provider API（可被配置缓存正确追踪）
// build.gradle.kts
val apiUrl: String = providers.gradleProperty("apiUrl").getOrElse("https://default.api")
```

#### 3.3 配置缓存的常见问题

| 问题 | 原因 | 解决方案 |
| --- | --- | --- |
| `invocation of 'Task.project' at execution time is unsupported` | 在执行阶段访问了 `project` | 提前在配置阶段取值，或用 Provider |
| 读取了 `System.getenv()` / `System.getProperty()` | 不被追踪 | 用 `providers.environmentVariable()` / `providers.gradleProperty()` |
| 自定义 Task 持有 `Project` 引用 | Project 不可序列化 | 用 `@Inject` 注入 `ObjectFactory`/`Provider` |
| 配置缓存每次都失效 | 有文件在配置阶段被读取且频繁变化 | 检查 `local.properties`、构建时间戳类文件 |
| `Configuration cache entry discarded` | 配置阶段有未声明的副作用 | 看警告日志定位 |

```kotlin
// ❌ 错误写法：自定义 Task 持有 Project
abstract class MyTask : DefaultTask() {
    @get:Input
    val someValue: String = project.findProperty("key") as String   // 执行期访问 project
}

// ✅ 正确写法：用 Provider 惰性求值
abstract class MyTask : DefaultTask() {
    @get:Input
    abstract val someValue: Property<String>   // 由 Gradle 在配置阶段注入
}
```

#### 3.4 效果

```
配置缓存关闭：单模块项目配置 ~4s，多模块（40 个）项目配置 ~25s
配置缓存开启：命中时配置 ~0.3s
全量构建时间：8min → 3.5min（其中配置阶段节省 25s，任务执行也因输入不变而命中缓存）
```

### 4. Build Cache（构建缓存）

与配置缓存不同，**Build Cache 缓存的是"任务执行结果"**。

```
Task 输入（inputs） ──┐
                      ├──→ 哈希 = Cache Key
Task 输出（outputs） ──┘

  命中缓存 → 直接恢复输出文件，跳过任务执行
  未命中   → 正常执行，把输出存入缓存
```

```properties
org.gradle.caching=true
```

```kotlin
// 自定义任务参与缓存的条件（缺一不可）
abstract class GenerateResourcesTask : DefaultTask() {

    // 输入：变了则缓存失效
    @get:Input
    abstract val sourceFile: RegularFileProperty

    @get:Input
    abstract val version: Property<String>

    // 输出：缓存命中时会被恢复
    @get:OutputDirectory
    abstract val outputDir: DirectoryProperty

    @get:CacheableTask
    abstract val taskAction: WorkAction<GenerateResourcesTask>
}
```

**注意**：**不是所有任务都可缓存**。AGP 中可缓存的典型任务：`compileKotlin`（部分）、`processResources`、`mergeResources`、`mergeExtDex`、`processManifest`。**不可缓存的**：`packageRelease`（签名）、`lint`（依赖分析状态）、`dexBuilder`。

**CI 中的缓存策略**：缓存 `~/.gradle/caches/build-cache-1`（跨机器共享构建结果）+ `~/.gradle/caches/modules-2`（依赖）+ `~/.gradle/caches/transforms-3`（AGP 的资源/dex 转换结果，**最容易被忽略但收益很大**）。

```yaml
# GitHub Actions 缓存示例
- uses: actions/cache@v4
  with:
    path: |
      ~/.gradle/caches/build-cache-1
      ~/.gradle/caches/modules-2
      ~/.gradle/caches/transforms-3
      ~/.gradle/caches/8.7
    key: gradle-${{ runner.os }}-${{ hashFiles('**/*.gradle.kts', 'gradle/libs.versions.toml') }}
    restore-keys: |
      gradle-${{ runner.os }}-
```

### 5. 并行执行

```properties
org.gradle.parallel=true
```

**并行生效的条件**：**任务之间没有依赖关系**。Gradle 会根据任务的 `inputs`/`outputs` 自动推断依赖。

```kotlin
// ❌ 破坏并行：手动 dependsOn 了不必要的依赖
tasks.named("preBuild").configure {
    dependsOn("generateAllResources")   // 强制所有资源任务串行
}

// ✅ 依赖应该按需声明（Gradle 会自动推导）
dependencies {
    implementation(project(":core:network"))   // 自动产生 "app 编译依赖 core:network 编译"
}
```

**影响并行的常见"隐形依赖"**：
- **共享输出目录**：两个任务写同一个目录 → Gradle 会警告并串行化。
- **全局状态**：`buildDir` 被多个任务写入。
- **同一个 sourceSet 被多个变体使用**。
- **AGP 的 `preBuild` 任务**：某些 AGP 版本会引入全局依赖。

### 6. 依赖管理优化

#### 6.1 版本统一与约束

```kotlin
// build.gradle.kts（根项目）：统一管理版本，避免各处硬编码
plugins {
    alias(libs.plugins.android.application) apply false
    alias(libs.plugins.kotlin.android) apply false
}
```

```toml
# gradle/libs.versions.toml
[versions]
androidxCore = "1.13.1"
lifecycle = "2.8.6"
coroutines = "1.8.1"

[libraries]
androidx-core-ktx = { group = "androidx.core", name = "core-ktx", version.ref = "androidxCore" }
androidx-lifecycle-runtime = { group = "androidx.lifecycle", name = "lifecycle-runtime-ktx", version.ref = "lifecycle" }
kotlinx-coroutines-core = { group = "org.jetbrains.kotlinx", name = "kotlinx-coroutines-core", version.ref = "coroutines" }
```

#### 6.2 避免动态版本

```kotlin
// ❌ 动态版本：每次构建都可能去网络检查最新版本
implementation("com.squareup.okhttp3:okhttp:+")
implementation("com.squareup.okhttp3:okhttp:4.+")

// ❌ SNAPSHOT：每次都检查远程仓库，且不可复现
implementation("com.example:library:1.0-SNAPSHOT")

// ✅ 固定版本
implementation("com.squareup.okhttp3:okhttp:4.12.0")
```

**动态版本的三重危害**：
1. **构建不可复现**（同一份代码今天和明天构建出不同结果）。
2. **每次构建都要访问网络**（检查最新版本）→ 慢且离线不可用。
3. **可能引入破坏性变更**（自动升级到不兼容版本）。

#### 6.3 依赖锁

```kotlin
// settings.gradle.kts
dependencyResolutionManagement {
    repositoriesMode.set(RepositoriesMode.FAIL_ON_PROJECT_REPOS)
    repositories { google(); mavenCentral() }
    // 启用依赖锁
    dependencyLocking { lockAllConfigurations() }
}
```

```bash
# 生成锁文件
./gradlew dependencies --write-locks

# 验证锁文件
./gradlew dependencies --write-locks    # CI 中会校验锁文件一致性
```

**依赖锁的作用**：锁定**传递依赖**的确切版本，防止某个库升级时传递依赖版本漂移。

### 7. KSP vs kapt 性能对比

这是 Gradle 8.x 时代最值得做的构建优化之一。

```
┌─────────────────────────────────────────────────────────────────────┐
│  kapt（Kotlin Annotation Processing Tool）                           │
│                                                                     │
│  Kotlin 源码 ──▶ 生成 Java Stub ──▶ javac 编译 Stub ──▶ 跑 APT       │
│                                              │                      │
│                                              └──▶ 生成 Kotlin 代码    │
│                                                                     │
│  问题：                                                             │
│  ① 多一次 javac 编译（Stub 编译）                                    │
│  ② 只处理 Java 源（Kotlin 源需要先转 Stub）                          │
│  ③ 增量构建不可靠：改一个 Kotlin 文件可能重新处理全部               │
│  ④ 与 Kotlin 编译器版本强耦合（kapt 版本要对应）                      │
└─────────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────────┐
│  KSP（Kotlin Symbol Processing）                                    │
│                                                                     │
│  Kotlin 源码 ──▶ KSP 插件（同一编译器内）──▶ 直接读 Kotlin 符号      │
│                                                                     │
│  优势：                                                             │
│  ① 无 Stub 编译步骤 → 通常快 2~10 倍                                │
│  ② 直接处理 Kotlin 符号（类型信息更精确）                            │
│  ③ 真正的增量处理 → 只处理受影响的文件                              │
│  ④ 与 Kotlin 编译器同版本发布，版本问题少                            │
└─────────────────────────────────────────────────────────────────────┘
```

**实测数据（典型中大型项目）**：

| 场景 | kapt | KSP | 提升 |
| --- | --- | --- | --- |
| Room（数据库） | 25s | 6s | **4x** |
| Hilt（DI） | 40s | 12s | **3.3x** |
| Glide / Moshi | 15s | 4s | **3.7x** |
| 全量冷构建 | 6min | 3min | **2x** |

```kotlin
// 迁移方式：plugin + dependency 同时替换
plugins {
    id("com.google.devtools.ksp") version "2.0.20-1.0.25"
    // 移除 id("kotlin-kapt")
}

dependencies {
    // 移除 kapt("androidx.room:room-compiler")
    ksp("androidx.room:room-compiler")            // Room 官方支持 KSP
    ksp("com.google.dagger:hilt-android-compiler") // Hilt 官方支持 KSP（2.48+）
}
```

**KSP 的限制**：
- **不能处理 Java 源码**（只能处理 Kotlin）。如果有大量 Java 代码需要注解处理，混合使用。
- **KAPT 的部分第三方库还没迁移**（需要检查）。
- **不能与某些编译器插件共存**（如旧的 `kotlin-parcelize` 无问题，但 `dagger-compiler` 的某些老特性要验证）。

### 8. 增量编译与编译期优化

#### 8.1 增量编译的失效传播

```
修改 feature/order/src/.../OrderViewModel.kt
    ↓
OrderViewModel.kt 重编译
    ↓
谁依赖 OrderViewModel？
    ├─ 同模块内引用它的类 → 重编译
    ├─ feature-order 的其他类 → 重编译
    └─ app 模块（如果引用了 OrderViewModel）→ 重编译
```

**关键**：**`api` 依赖会把"编译期"依赖传染出去**，`implementation` 则只在运行时传递。

```kotlin
// ❌ 用 api 会让编译期依赖扩散到所有下游
api(project(":core:network"))   // 下游模块编译时需要 core-network 的传递依赖

// ✅ implementation 只在运行时传递，编译期隔离
implementation(project(":core:network"))
```

#### 8.2 编译期优化

```kotlin
// build.gradle.kts：关闭不需要的编译任务
android {
    buildFeatures {
        buildConfig = false        // 不需要 BuildConfig 就关掉
        aidl = false                // 不需要 AIDL 就关掉
        renderScript = false
        resValues = false
        shaders = false
    }

    // 关闭不需要的 variant（大幅减少构建任务数）
    androidComponents {
        beforeVariants { variant ->
            // 关闭所有 debug variant 的单元测试
            if (variant.buildType == "debug") {
                variant.enableUnitTest = false
                variant.enableAndroidTest = false
            }
        }
    }

    // 资源优化
    androidResources {
        noCompress += listOf("ttf", "otf", "webp")   // 已压缩的资源不再压缩，减小包体
    }
}
```

```kotlin
// Kotlin 编译选项
kotlin {
    compilerOptions {
        // 增量编译（默认开启，K1 时代不稳定，K2 已稳定）
        incremental = true
        // 自由编译器参数
        freeCompilerArgs.addAll(
            "-opt-in=kotlin.RequiresOptIn",
            "-Xjvm-default=all"
        )
    }
}
```

**Kotlin 编译器的性能选项**：

| 选项 | 作用 | 注意 |
| --- | --- | --- |
| `kotlin.incremental.useClasspathSnapshot` | 使用 classpath 快照，编译更快 | Gradle 8.x 默认开启 |
| `kotlin.compiler.execution.strategy=in-process` | 编译在 Gradle 进程内，避免启动 Kotlin 守护进程 | 内存压力小，适合 CI |
| `kotlin.compiler.execution.strategy=daemon` | 独立守护进程 | 本地开发更快 |
| `kotlin.incremental.useClasspathSnapshot=false` | 排查增量编译不生效的问题 | 排查时用 |

### 9. 分析工具

#### 9.1 --profile 生成 HTML 报告

```bash
# 生成构建报告
./gradlew assembleRelease --profile

# 报告位置
# build/reports/profile/profile-<timestamp>.html
```

**报告能看出什么**：
- **Total Build Time** 与 **Startup Time**（配置阶段耗时）。
- **Task Execution**：每个任务的耗时条形图，按时间排序。
- **Build Cache**：哪些任务命中了缓存（绿色标记）。
- **Configuration**：配置阶段的耗时分布。

#### 9.2 Build Scan（Gradle Enterprise / Develocity）

```properties
# gradle.properties
develocity.scan.enabled=true
develocity.scan.build-cache.enabled=true
```

```bash
# 本地或 CI 中发布扫描
./gradlew build --scan
```

**Build Scan 提供的能力**：
- **构建耗时趋势图**：能发现"这个任务从上周开始变慢了"。
- **配置缓存命中率**。
- **构建缓存命中率**。
- **问题定位**："60% 的构建时间花在 `compileKotlin` 上，因为每次都全量编译（增量失效）"。
- **CI 性能分析**：找出哪条流水线最慢。

#### 9.3 Build Analyzer（Android Studio 内置）

```bash
# 生成构建分析报告（需要 AGP 8.x）
./gradlew :app:assembleRelease --build-analyzer
# 报告：app/build/reports/build-analyzer/
```

**Build Analyzer 能分析**：
- **Project Overhead**：Gradle 配置 + 插件加载的开销（纯浪费）。
- **Gradle Configuration**：每个模块的配置耗时。
- **Tasks**：任务耗时排行。
- **Dependency Resolution**：依赖解析耗时。
- **Kotlin Compilation**：增量编译是否生效、哪些文件被全量重编。
- **AGP Tasks**：资源处理、dex 等的耗时。

#### 9.4 其他诊断命令

```bash
# 只跑配置阶段，输出配置耗时
```

### 10. 多渠道打包优化


```kotlin
        // 内部渠道不需要 benchmark 变体

        }
```

### 5. 自定义缓存友好的任务

```kotlin
// 抽象任务：正确的 inputs/outputs 声明是缓存生效的前提
abstract class GenerateVersionInfoTask : DefaultTask() {

    @get:Input
    abstract val versionCode: Property<Int>

    @get:Input
    abstract val versionName: Property<String>

    @get:Input
    abstract val buildTime: Property<String>   // 必须是输入的一部分，否则缓存会复用旧结果

    @get:OutputFile
    abstract val outputFile: RegularFileProperty

    @get:CacheableTask
    abstract val generateAction: WorkAction<GenerateVersionInfoTask>
}

// 注册
tasks.register<GenerateVersionInfoTask>("generateVersionInfo") {
    group = "build"
    description = "生成版本信息文件"
    versionCode.set(project.findProperty("versionCode") as? Int ?: 1)
    versionName.set(project.findProperty("versionName") as? String ?: "1.0.0")
    buildTime.set(providers.provider { getCurrentTimestamp() })   // Provider 保证可追踪
    outputFile.set(layout.buildDirectory.file("generated/version-info.properties"))

    generateAction {
        val file = outputFile.get().asFile
        file.parentFile.mkdirs()
        file.writeText(
            """
            VERSION_CODE=${versionCode.get()}
            VERSION_NAME=${versionName.get()}
            BUILD_TIME=${buildTime.get()}
            """.trimIndent()
        )
    }
}
```

## 常见问题 / 面试要点

**读者问：Gradle 构建慢怎么优化？给你一个项目你怎么定位？**

**AI答：**

1. **第一步：测量（不做这一步就是瞎优化）**：
   ```bash
   ./gradlew assembleDebug --profile
   ./gradlew assembleDebug --build-analyzer    # AGP 8.x
   ```
   关注三个数字：
   - **Total Build Time**（总耗时）
   - **Startup / Configuration Time**（配置阶段耗时）
   - **Task Execution Time**（执行阶段耗时）
2. **第二步：分诊（按瓶颈类型对症下药）**：

| 现象 | 诊断 | 处方 |
| --- | --- | --- |
| **配置阶段 > 30%** | Build Analyzer 的 Project Overhead | **配置缓存** + **Convention Plugin** + 减少变体 |
| **依赖解析慢** | Build Analyzer 的 Dependency Resolution | 固定版本、**依赖锁**、统一仓库声明、CI 缓存 `modules-2` |
| **单模块编译慢** | Task 排行里 `compileKotlin` 靠前 | **KSP 替代 kapt**、增量编译、拆分模块 |
| **全量重编** | Build Analyzer 的 Kotlin Compilation 显示非增量 | 检查 `api` 依赖、修正任务依赖声明 |
| **dex/合并慢** | `mergeExtDex` / `dexBuilder` 靠前 | 开启 **R8 增量**、减少方法数、`multiDex` 优化 |
| **资源处理慢** | `processDebugResources` 靠前 | 减少资源数量、`shrinkResources`、检查超大图�� |
| **每次都变慢** | Build Scan 的趋势图 | 找引入回归的提交 |

3. **第三步：优先级排序（ROI 从高到低）**：
   ```
   1. 配置缓存开启          → 立刻见效，零风险
   2. KSP 替代 kapt        → 30%+ 提升，一次性投入
   3. Convention Plugin     → 减少配置阶段 + 统一规范
   4. CI 缓存配置           → CI 从 20min → 5min
   5. 减少变体数量          → 避免构建不需要的组合
   6. 修 api/implementation → 恢复增量编译
   7. 拆分超大模块          → 并行度提升
   8. 升级硬件              → 最后手段（线性收益，最贵）
   ```
4. **面试话术**："我的原则是**先测量、再分诊、后优化**。构建慢有四种不同的成因，优化手段完全不同。我通常先看配置阶段占比——如果超过 30%，那就先开配置缓存和 Convention Plugin，这两件事的投入产出比最高。"

---

**读者问：配置缓存（Configuration Cache）是什么原理？为什么不是默认开启？**

**AI答：**

1. **原理**：
   - Gradle 的构建分**配置阶段**（执行 build 脚本，生成任务图）和**执行阶段**（跑任务）。
   - 配置阶段结束后，Gradle 把**任务图 + 所有配置结果**序列化到 `.gradle/configuration-cache/`。
   - 下次构建时，先计算当前构建的**指纹**（所有输入文件哈希 + 环境变量 + 命令行参数 + Gradle 属性）。**指纹一致 → 直接反序列化，跳过整个配置阶段。**
   - 指纹不一致 → 配置缓存失效，重新执行配置阶段并更新缓存。
2. **为什么不是默认开启**：
   - **构建脚本可能有隐式副作用**：读环境变量、读任意文件、访问网络、修改系统状态。这些行为**无法被 Gradle 追踪**，缓存后行为会改变。
   - **第三方插件不兼容**：很多老插件在执行阶段访问 `project`，这在配置缓存下是非法的。
   - **Gradle 的策略**：先用 `problems=warn` 让用户看到所有不兼容点，改完再切到 `fail`。
3. **迁移建议**：
   ```properties
   org.gradle.configuration-cache=true
   org.gradle.configuration-cache.problems=warn   # 先警告
   ```
   - 逐个修复警告里报出的问题。
   - 全部修复后改成 `problems=fail`，防止新代码引入破坏。
4. **三个高频不兼容点与改法**：

| 问题 | 改法 |
| --- | --- |
| 执行阶段访问 `project` | 提前在配置阶段取值，或用 `Provider` 惰性求值 |
| 读 `System.getenv()` | 用 `providers.environmentVariable("KEY")` |
| 自定义 Task 持有 `Project` 引用 | 用 `@get:Input abstract val x: Property<T>` |

5. **与 Build Cache 的区别（高频追问）**：
   - **配置缓存**：缓存**配置阶段的结果**（任务图），跳过"描述要做什么"。
   - **构建缓存**：缓存**任务执行的结果**（输出文件），跳过"做"。
   - **两者可叠加**：配置缓存命中后，如果某个任务的输入也没变，还会命中构建缓存 → 整个构建瞬间完成。
6. **效果数据**：40 模块项目，配置阶段 25s → 0.3s；配合构建缓存，重复构建可从 3min 降到 20s 内。

---

**读者问：KSP 和 kapt 有什么区别？为什么 KSP 更快？**

**AI答：**

1. **kapt 的工作流程（多一步）**：
   ```
   Kotlin 源码
      ↓ kotlinc 编译
   生成 Java Stub（.java 文件）
      ↓ javac 编译 Stub        ← 额外的一次 Java 编译
   在 Stub 上运行 APT
      ↓
   生成 Java/Kotlin 代码
      ↓ 最终编译
   ```
   **额外成本**：① 一次完整 javac 编译；② Stub 与真实代码可能不一致（Kotlin 与 Java 的类型差异导致注解处理器看到的信息失真）；③ 增量处理不可靠。
2. **KSP 的工作流程**：
   ```
   Kotlin 源码
      ↓ KSP 插件（集成在 kotlinc 内部）
   直接读取 Kotlin 符号（SourceFiles / Resolver）
      ↓
   生成代码
      ↓ 编译
   ```
   **省掉了整个 Stub 编译环节**，且拿到的是**真实的 Kotlin 类型信息**。
3. **提速原因总结**：
   - 少了 javac 编译（省 30%~50% 时间）。
   - **真正的增量**：KSP 知道哪个文件被改了，只处理受影响的符号；kapt 常常需要全量重处理。
   - 更精确的类型信息 → 生成的代码更准确 → 减少后续编译错误与重试。
4. **实测数据**（大型项目）：Room 编译从 25s → 6s；Hilt 从 40s → 12s；整体构建时间下降 30%~50%。
5. **迁移注意**：
   - **Room 2.6+** 官方支持 KSP。
   - **Hilt 2.48+** 官方支持 KSP（用 `hilt-android-compiler` 的 KSP 变体）。
   - **Glide 4.16+**、**Moshi 1.15+**、**Room**、**Hilt**、**DataStore** 都已支持。
   - **仍需 kapt 的**：老版本第三方库、或处理 Java 源码的处理器。
   - **Dagger/Hilt 与 KSP 的差异**：Dagger 早期用 kapt 是因为需要处理 Java；现在 Dagger 官方也提供 KSP 支持，但 **Hilt 的聚合依赖（AggregatedDeps）处理**曾有过问题，升级时需要验证。
6. **面试话术**："KSP 的核心优势是**去掉了 Stub 编译这一层**，同时因为它运行在 Kotlin 编译器内部，能拿到精确的 Kotlin 类型信息。这带来两个直接收益：**快**（通常 2~4 倍）和**准**（生成的代码更可靠）。Kotlin 2.0 之后我建议所有新项目默认用 KSP。"

---

**读者问：CI 上的构建怎么加速？和本地优化有什么不同？**

**AI答：**

1. **CI 与本地的核心差异**：
   - **没有 Gradle Daemon 复用**：每次 CI 跑都是全新的 JVM → 启动开销 + 无法复用内存中的状态。
   - **没有本地缓存**：除非显式配置 CI 缓存。
   - **机器配置可能更低**（GitHub Actions 标准 runner 是 4 核 16GB）。
   - **磁盘 IO 较慢**（临时目录）。
2. **CI 专属优化清单**：

| 优化项 | 做法 | 收益 |
| --- | --- | --- |
| **依赖缓存** | 缓存 `~/.gradle/caches/modules-2` | 巨大（首次 5min → 10s） |
| **构建缓存** | 缓存 `~/.gradle/caches/build-cache-1` | 巨大 |
| **转换缓存** | 缓存 `~/.gradle/caches/transforms-3`（AGP 资源/dex 转换） | 很大（常被忽略） |
| **Gradle 发行版缓存** | 缓存 `~/.gradle/wrapper/dists` | 中 |
| **配置缓存** | `org.gradle.configuration-cache=true` | 大（CI 上尤其明显，因为每次都是冷启动） |
| **按需配置** | `org.gradle.configureondemand=true` | 中 |
| **只构建需要的** | `assembleAppstoreRelease` 而非 `assemble` | 大 |
| **增量构建** | 检出后先构建一次，后续步骤复用 | 大（适合多阶段流水线） |
| **并行 Job** | lint / test / build 拆成并行 Job | 大 |
| **受影响范围** | 只构建/测试受变更影响的模块 | 最大 |
3. **Gradle 官方 Action 的缓存**：

```yaml
- uses: gradle/actions/setup-gradle@v3
  with:
    cache-read-only: ${{ github.event_name == 'pull_request' }}
    cache-write-only: ${{ github.event_name != 'pull_request' }}
```
> `setup-gradle` 会自动处理 Gradle 用户 home 的缓存、Daemon 复用、Build Scan 上传等。
4. **受影响范围检测（最高 ROI）**：
   ```bash
   # 找出变更涉及的模块
   CHANGED_MODULES=$(git diff --name-only origin/main...HEAD \
     | grep '/build.gradle.kts$' | sed 's|/build.gradle.kts||' | sort -u)

   # 加上所有依赖这些模块的模块（反向依赖）
   AFFECTED=""
   for m in $CHANGED_MODULES; do
     DEPS=$(grep -rl "project(\"$m\")" --include="build.gradle.kts" . \
       | sed 's|/build.gradle.kts||')
     AFFECTED="$AFFECTED $DEPS"
   done

   # 只测试这些模块
   ./gradlew ${AFFECTED// /:test} --continue
   ```
5. **别忘了 JVM 参数**：CI 上 `org.gradle.jvmargs` 默认只有 512MB 或 1GB，**Kotlin 编译很容易 OOM**。显式设置 `-Xmx3g` 是最容易被忽略的 CI 优化。
6. **面试话术**："CI 加速的核心是**缓存**和**范围裁剪**。缓存要缓存对的东西——除了常见的 `modules-2`，**`transforms-3` 和 `build-cache-1` 才是真正的大头**。范围裁剪要靠依赖图算出受影响模块，这一步能省掉 70% 的构建时间。"

**读者问：什么是增量编译？为什么改了代码会全量重编？**

**AI答：**

1. **增量编译的原理**：
   - Kotlin 编译器为每个源文件生成**增量缓存**（在 `build/kotlin/compile<Variant>Kotlin/` 下），记录该文件的 ABI（公开 API 的签名）、依赖的类信息、源码哈希。
   - 下次编译时对比：
     - **源码哈希变了** → 该文件必须重编。
     - **源码没变，但依赖的 ABI 变了** → 该文件重编。
     - **都没变** → **跳过**（这就是增量编译带来的秒级体验）。
2. **为什么会退化成全量**：
   - **`api` 依赖扩散**：`feature-a` 用 `api(project(":core-x"))`，则 `core-x` 的公开 ABI 变化会传染给所有依赖方。
   - **KAPT 参与**：kapt 的增量处理不可靠，改一个文件可能触发全量重新处理（**这是 KSP 更快的原因之一**）。
   - **ABI 不稳定**：如果一个类的 public 方法签名经常变（哪怕实现没变），ABI 哈希也会变 → 下游重编。
   - **非确定性源码**：构建脚本里生成带时间戳的代码（除非正确声明为 `@Input`）。
   - **多模块混编**：Java + Kotlin 混用时，Java 源变化会导致 Kotlin 重编（Java ABI 影响）。
   - **`buildDir` 被外部工具写入**。
3. **诊断方法**：
   ```bash
   # Build Analyzer 的 Kotlin Compilation 面板：能看到是否有非增量行为
   ./gradlew :app:compileDebugKotlin --build-analyzer

   # 强制关闭增量，验证是否是增量导致的诡异问题
   kotlin.incremental=false
   ```
4. **优化方向**：
   - **正确使用 `implementation` 而非 `api`**（把依赖限制在模块内）。
   - **保持 ABI 稳定**：对外接口少改，内部实现随便改。
   - **迁移 KSP**。
   - **拆分模块**（缩小 ABI 影响面）。
5. **面试话术**："增量编译失效的根因几乎都是**依赖声明过宽**。`api` 和 `implementation` 的区别不只是'能不能用'，它直接决定了编译依赖的传播边界。**把 `api` 收紧到最小，是提升增量编译命中率最有效的一招。**"

---

**读者问：构建优化有没有什么"反模式"？哪些优化看起来有用其实有害？**

**AI答：**

1. **❌ 无脑加内存/加 CPU**：线性收益且成本高。**应该先消除浪费**——配置阶段的 25 秒加再多核也不会消失。
2. **❌ 关闭增量编译"求稳定"**：牺牲了最大的收益（几秒 → 几分钟），且掩盖了真正的问题（依赖声明过宽）。
3. **❌ 滥用 `dependsOn`**：手动加依赖会破坏 Gradle 的并行推断，把本可并行的任务强制串行。**依赖应该由 `inputs/outputs` 自动推导**。
4. **❌ 用 `doLast` 做真正的逻辑**：绕过了 Gradle 的输入输出追踪 → **缓存完全失效**，且增量构建也会重跑。
5. **❌ 把业务逻辑写在 build 脚本里**：Groovy/Kotlin DSL 在配置阶段执行，逻辑越复杂配置越慢，且难以测试。应下沉到 Convention Plugin 或用类型安全的 API。
6. **❌ 为了"快"而牺牲可复现性**：
   - 用动态版本（`+`）→ 每次可能拉不同版本。
   - 用 SNAPSHOT → 不可复现。
   - 把 `buildTime` 之类的动态值塞进生成代码却不声明为输入 → 缓存返回旧值。
7. **❌ 忽略 CI 与本地的差异**：本地开了配置缓存就以为万事大吉，CI 上没开 → CI 依然慢。**两边的 `gradle.properties` 应该尽量一致**（CI 可以额外覆盖）。
8. **❌ 只优化单次构建，忽视日常构建**：用户每天跑几十次增量构建，**优化增量比优化全量更有价值**。
9. **❌ 迷信配置缓存**：它有明确的前提（构建脚本纯函数化）。**如果配置阶段有副作用，缓存命中反而会导致诡异 bug**。要先修好再开。

# 编码规范

## 一句话定义

编码规范是把"**个人习惯**"升级为"**团队共识**"的一组可机器校验的约定。它解决的核心问题是：多人协作时，代码风格差异会淹没业务差异，让 Review 的人把注意力浪费在括号和命名上，最终导致代码质量下降、合并冲突激增、代码库认知成本飙升。

面试开场可以这样说：**"规范的价值不在于整齐，而在于把人的注意力从'怎么写'转移到'写什么'。凡是能被工具自动检查的规则，都不应该占用 Review 的人力。"**

## 核心原理

### 1. 规范的三层落地形态

```
┌──────────────────────────────────────────────────────────┐
│  L1  人读层：文档 + Code Review + 结对编程                 │
│      作用：表达意图、传递上下文、纠正设计                    │
├──────────────────────────────────────────────────────────┤
│  L2  机器层：ktlint / detekt / Android Lint / EditorConfig │
│      作用：把可机器判定的问题在提交前/构建前拦截             │
├──────────────────────────────────────────────────────────┤
│  L3  工具链层：IDEA 格式模板 + Git Hooks + IDE 插件         │
│      作用：让"符合规范"成为默认值而非需要主动争取的目标       │
└──────────────────────────────────────────────────────────┘
```

**关键判断**：任何一条规范，如果**无法被机器判定**，就不要把它当成"红线"，否则 Review 阶段会变成口水战。真正值得写进规范文档的应该是**设计约束**（依赖方向、模块边界、异常处理策略），风格问题交给工具。

### 2. Kotlin 官方代码风格基线

Kotlin 官方在 [Kotlin Coding Conventions](https://kotlinlang.org/docs/coding-conventions.html) 中给出了完整风格，IntelliJ IDEA 默认模板（Kotlin style）与之对齐。要点：

| 类别 | 规范 | 示例 |
| --- | --- | --- |
| 缩进 | 4 空格 | 不用 Tab |
| 行宽 | 120 字符（官方原文 120，部分项目设 100） | 长表达式换行 |
| 大括号 | K&R，左大括号同行 | `fun f() {` |
| 命名 | UpperCamelCase 类/接口/枚举；lowerCamelCase 函数/变量；常量 SCREAMING_SNAKE_CASE | `UserRepository` / `loadUser()` / `MAX_RETRY` |
| 修饰符顺序 | `public/protected/private > internal > abstract/open > override > final > lateinit > const > suspend` | `private suspend fun load()` |
| 空安全 | 优先使用 `?.` `?:` `!!`（后者慎用） | `val name = user?.name ?: "未知"` |
| 表达式体 | 单表达式函数用 `=` 表达式体 | `fun name() = "x"` |
| 遍历 | 优先 `forEach`/`map`/`filter` 而非 `for` 循环 | — |
| 可见性 | 明确标注，不依赖默认 | `internal class Foo` |

### 3. Android 特有命名约定

这是 Android 项目最容易出错的部分，因为资源命名直接参与 **R 类生成** 与 **aapt 编译**。

#### 3.1 资源命名：`<type>_<qualifier>` 格式

规则是 **type 前缀 + 语义描述 + qualifier 后缀**，qualifier 顺序由 Android 框架规定，不能随意排列：

```
✅ ic_launcher_round          图标 + 圆角限定
✅ btn_submit_enabled         按钮 + 状态
✅ txt_user_name              文本 + 语义
✅ layout_activity_main       布局 + 所属界面
✅ drawable_bg_card_corner    图片 + 语义 + 限定

❌ submitButton              大驼峰，aapt 只允许小写
❌ activity_main.xml         缺少 type 前缀，语义不清
❌ iconRound                大写字母
```

合法的 qualifier 顺序（**必须按此顺序**）：`mcc/mnc` → `locale` → `layoutDirection` → `smallestWidth` → `availableWidth/Height` → `screenSize` → `screenAspect` → `round` → `wideColorGamut` → `hdr` → `orientation` → `uiMode` → `night` → `density` → `touchscreen` → `keyboard` → ...

> 面试点：把 `night` 写成 `night_v26` 之前要先确认 **v26 是版本限定（API level）**，它必须放在**所有配置限定符之前**：`drawable-v26/ic_launcher.xml` 是对的，`drawable-night-v26` 也是对的，但 `drawable-v26-night` 是错的。

#### 3.2 ViewBinding 命名规则

ViewBinding 类名由布局文件名自动推导：去掉下划线、首字母大写、去掉 `layout_` 前缀。

| 布局文件 | 生成类名 |
| --- | --- |
| `activity_main.xml` | `ActivityMainBinding` |
| `fragment_user_list.xml` | `FragmentUserListBinding` |
| `item_product.xml` | `ItemProductBinding` |
| `view_empty_state.xml` | `ViewEmptyStateBinding` |

因此**布局文件名本身就是一种命名规范**：必须能反推出 Binding 类名，也必须能反推出这个布局属于哪个界面。

#### 3.3 Kotlin 类命名约定

| 类型 | 约定 | 示例 |
| --- | --- | --- |
| Activity | 业务名 + `Activity` | `UserProfileActivity` |
| Fragment | 业务名 + `Fragment` | `UserProfileFragment` |
| ViewModel | 业务名 + `ViewModel` | `UserProfileViewModel` |
| Repository | 业务名 + `Repository` | `UserRepository` |
| Adapter | 业务名 + `Adapter` | `ProductAdapter` |
| Compose 页面 | 页面名 + `Screen`，函数为 `XxxRoute` | `HomeScreen` / `HomeRoute` |
| UseCase | 动宾结构 + `UseCase` | `LoadUserProfileUseCase` |
| 扩展函数 | 接收者语义 + 动作 | `String.toDisplayName()` |

### 4. 常见反模式

| 反模式 | 症状 | 危害 | 治理手段 |
| --- | --- | --- | --- |
| **上帝类（God Class）** | 单文件 > 1000 行，承担网络/存储/UI/业务 | 编译慢、无法测试、合并冲突高发 | 按职责拆分，detekt `TooManyFunctions` / `LargeClass` 拦截 |
| **上帝方法** | 单方法 > 80 行、多层嵌套 if | 圈复杂度飙升，改动易漏分支 | 提取函数 + `ComplexMethod` 规则 |
| **魔法值** | `if (type == 3)`、`dp(16)`、`0.75f` | 无法追溯含义，改一处漏三处 | 常量/枚举/`@IntDef` |
| **嵌套过深** | 4 层以上 if/for | 可读性崩溃 | 卫语句 + 提前 return + `when` 替代 if-else 链 |
| **滥用扩展函数** | 给所有类型都加扩展，`fun Any.toStringOrEmpty()` | 污染全局命名空间、可读性下降、隐式行为 | 只对**高频通用**操作扩展 |
| **过度抽象** | 为一个实现建接口 + 工厂 + Builder | 阅读成本 > 收益 | YAGNI，等第二个实现出现再抽象 |
| **过度封装（Under-encapsulation）** | 字段全 public var | 状态可被任意篡改，无法保证不变量 | `private set` + 状态容器 |
| **注释复述代码** | `// 给 m 设置值` | 噪音，维护成本 | 注释写"为什么"不写"是什么" |
| **吞异常** | `catch (e: Exception) {}` | 静默失败，线上问题无法定位 | 至少上报或 rethrow |

### 5. 注释规范与 KDoc

**KDoc 是 Kotlin 的官方文档注释**，格式为 `/** ... */`，支持 Markdown 与 `@` 标签，支持 Dokka 生成文档站点。

```kotlin
/**
 * 用户仓库，负责用户数据的远程获取与本地缓存协调。
 *
 * 线程安全：所有公开方法均可在任意线程调用，内部使用 [Mutex] 保护缓存写入。
 *
 * @property cache 本地缓存实现，进程内单例
 * @property remoteApi 远程数据源，不做本地缓存
 * @since 1.2.0
 */
class UserRepository(
    private val cache: UserCache,
    private val remoteApi: UserApi
) {
    /**
     * 加载指定用户。
     *
     * 优先读缓存，缓存未命中时请求网络并回填。
     *
     * @param userId 用户唯一标识
     * @return 用户信息；用户不存在时返回 `null`
     * @throws IOException 网络异常且缓存无数据时抛出
     */
    suspend fun loadUser(userId: String): User? { /* ... */ }
}
```

注释的分类原则：

| 类型 | 写什么 | 例子 |
| --- | --- | --- |
| **文件头注释** | 版权、作者、文件职责概览 | Apache License 头 |
| **KDoc** | 公开 API 的契约：参数、返回值、异常、线程模型 | `/** ... @param ... @throws ... */` |
| **行内注释** | "为什么这么做"，尤其是反直觉的决策 | `// 这里不能用 lazy，因为跨进程会重建` |
| **TODO** | 待办，必须带负责人与 issue 链接 | `// TODO(zhangsan): 迁移到新 API，see #1234` |

> 反例：`// 设置 loading 为 true`（复述代码）
> 正例：`// 先置位再请求，避免用户重复点击造成并发下单`

### 6. API 设计规范（对外 SDK vs 对内接口）

对外 SDK 与内部代码的要求完全不同：

| 维度 | 对外 SDK | 对内接口 |
| --- | --- | --- |
| 兼容性 | **必须**二进制兼容，只能增不能删不能改签名 | 可以自由修改 |
| 异常 | 对外抛出的异常类型需稳定，必要时 catch 并转成 SDK 自定义异常 | 内部随意 |
| 日志 | 使用 SDK 自己的 `Logger` 接口，避免直接依赖 `android.util.Log`（便于宿主屏蔽） | 直接 `Log` 即可 |
| 依赖 | 零传递依赖（不引入 OkHttp/RxJava 等），或以 `compileOnly` + 可选集成 | 随便用 |
| 混淆 | 需提供 `consumer-rules.pro` 保留 public API | 无需 |
| 文档 | 每个 public 元素必须有 KDoc | 关键类即可 |
| 线程 | 明确标注回调在哪个线程 | 团队内部约定 |

**对外 SDK 的兼容性铁律**：

```kotlin
// ❌ 危险：修改已有 public 方法的参数 → 破坏二进制兼容
fun submit(order: Order)

// ✅ 安全：新增重载，保留原方法
@Deprecated("Use submit(order, callback)", level = DeprecationLevel.WARNING)
fun submit(order: Order) = submit(order, null)

// ✅ 更安全：新增参数必须给默认值（对 Kotlin 源码兼容）
fun submit(order: Order, callback: Callback? = null)
```

### 7. 团队规范落地：约定优于配置

**约定优于配置（Convention over Configuration）** 的核心思想是：**与其让每个模块写配置，不如提供一个已经配好的默认实现**。在 Android 中，这由 **Convention Plugin** 承载。

```kotlin
// build-logic/convention/src/main/kotlin/AndroidLibraryConventionPlugin.kt
class AndroidLibraryConventionPlugin : Plugin<Project> {
    override fun apply(target: Project) = with(target) {
        pluginManager.apply("com.android.library")
        pluginManager.apply("org.jetbrains.kotlin.android")

        extensions.configure<LibraryExtension> {
            // 统一 targetSdk / minSdk，模块不再各自声明
            compileSdk = 35
            defaultConfig { minSdk = 24 }
            // 统一开启 ViewBinding，模块不再重复配置
            buildFeatures { viewBinding = true }
            compileOptions {
                sourceCompatibility = JavaVersion.VERSION_17
                targetCompatibility = JavaVersion.VERSION_17
            }
            // 统一测试选项
            testOptions { unitTests.isIncludeAndroidResources = true }
        }
    }
}
```

三层落地组合拳：

```
┌──────────────────────────────────────────────────────┐
│ EditorConfig：编辑器层（缩进/换行/字符集）             │
│   root=true                                          │
│   [*.{kt,kts}] indent_size=4 end_of_line=lf          │
├──────────────────────────────────────────────────────┤
│ ktlint / Spotless：格式层（import 顺序、缩进、换行）   │
├──────────────────────────────────────────────────────┤
│ detekt：语义层（复杂度、过长函数、命名、魔法值）        │
└──────────────────────────────────────────────────────┘
```

### 8. Legacy 代码治理策略

存量代码治理最忌讳"推倒重来"。可落地的路径：

1. **建立基线（Baseline）**：先用 detekt 生成 baseline 文件，把存量问题"冻结"，保证新代码不新增问题。
2. **增量修复**：约定"**改到哪、修到哪**"——本次 PR 触及的文件，其触发的告警必须修掉，baseline 自动收缩。
3. **按目录设卡点**：核心新模块（如 `feature/*`）开启严格规则，老模块（`legacy/*`）保持宽松。
4. **热点治理**：用静态分析工具（如 `scopt`、SonarQube）找出复杂度最高的 Top 20 文件，排期专项重构。
5. **禁止新增**：在 CI 里对新增代码单独跑严格规则（基于 diff 检测），实现"新代码高标准、老代码不倒退"。

### 2. 用 `@IntDef` 消除魔法值

```kotlin
import androidx.annotation.IntDef

/** 支付方式 */
@IntDef(
    PaymentMethod.ALIPAY,
    PaymentMethod.WECHAT,
    PaymentMethod.BALANCE,
    PaymentMethod.UNKNOWN
)
@Retention(AnnotationRetention.SOURCE)
annotation class PaymentMethod {
    companion object {
        const val ALIPAY = 1
        const val WECHAT = 2
        const val BALANCE = 3
        const val UNKNOWN = 0
    }
}

/**
 * 发起支付。
 *
 * @param method 支付方式，只允许传入 [PaymentMethod] 中定义的值
 */
fun pay(@PaymentMethod method: Int, amount: Long) {
    when (method) {
        PaymentMethod.ALIPAY -> AlipayClient().pay(amount)
        PaymentMethod.WECHAT -> WeChatClient().pay(amount)
        PaymentMethod.BALANCE -> balanceDeduct(amount)
        else -> error("不支持的支付方式: $method")
    }
}
```

> `@IntDef` 让编译器在**编译期**就拒绝传入非法值，比运行期 `when` 分支优雅得多。这是"把运行时校验前移到编译期"的典型案例。

### 3. 消除深层嵌套：卫语句 + sealed interface

```kotlin
// ❌ 反模式：4 层嵌套 + 魔法值
fun handle(type: Int, data: Any?, user: User?) {
    if (type == 1) {
        if (data != null) {
            if (user != null) {
                if (user.isVip) {
                    doVip(data)
                }
            }
        }
    }
}

// ✅ 正确写法：卫语句提前 return + 枚举替代魔法值
enum class DataType { ORDER, COUPON, NONE }

sealed interface HandleResult {
    data class Success(val message: String) : HandleResult
    data object Skipped : HandleResult
    data class Error(val reason: String) : HandleResult
}

fun handle(type: DataType, data: Any?, user: User?): HandleResult {
    if (data == null) return HandleResult.Error("数据为空")
    if (user == null) return HandleResult.Error("用户未登录")
    if (!user.isVip) return HandleResult.Skipped

    return when (type) {
        DataType.ORDER -> HandleResult.Success("处理订单: $data")
        DataType.COUPON -> HandleResult.Success("处理券: $data")
        DataType.NONE -> HandleResult.Skipped
    }
}
```

## 常见问题 / 面试要点

**读者问：你怎么评价一个团队的代码规范水平？看你接手项目时先看什么？**

**AI答：**

1. **先看"机器可执行性"**：有没有 `.editorconfig`、`detekt.yml`、`ktlint` 配置？这些配置**是否被 CI 强制执行**（能不能在 CI 里直接跳过）？一份写在 Confluence 上没人看的规范文档，价值为零。
2. **看模块边界**：依赖是单向的吗？`feature` 模块会不会互相 `implementation`？这是规范里最难用工具检查的部分，也是最值钱的。
3. **看提交历史的一致性**：随机抽 10 个最近提交，看命名风格、提交信息格式、是否混杂了格式化提交（`format` / `style` 类提交多说明规范没落到工具上）。
4. **看遗留代码的处理方式**：是否存在"新代码写得很好，老代码全是坑"的双标现场？有没有 baseline 机制？说明团队懂"增量治理"。
5. **看异常与日志的处理惯例**：是吞掉还是上报？错误码是否统一？安全相关的敏感数据有没有脱敏？

> 面试话术：**"我看规范不看文档看三样东西：CI 里跑不跑的检查、模块之间的依赖方向、以及最近三个月的提交风格。"**

---

**读者问：规范文档应该写多详细？怎么防止文档过期？**

**AI答：**

1. **分层写，不要写成一本手册**：
   - **必须写**（人工 Review 保证）：模块依赖方向、命名语义、异常处理策略、数据流约定、提交信息规范、Review 流程。
   - **不要写**（交给工具）：缩进、大括号、import 顺序、行尾空格——写进文档只会浪费维护成本且与工具输出不一致。
2. **与代码同源**：规范文档放仓库 `docs/` 目录并随代码一起 Review、一起版本化；不要放在 Confluence 那种独立系统里，否则 PR 里改了规范没人同步。
3. **防过期机制**：
   - 文档末尾标注"最后更新时间 + 负责人"。
   - 规范变更必须以 PR 形式提交，和代码变更一起被 Review。
   - 每月（或每个迭代）设一个"文档巡检"任务，只检查与最近代码变更相关的部分。
   - 规范用**可执行的测试**表达：`detekt` 规则本身就是规范的"可执行版本"。
4. **判断文档是否有效的标准**：**新人照着它写代码，CR 时不会被提风格意见**。达不到这个标准，说明写得太虚或太长。

---

**读者问：ktlint、detekt、Android Lint 三者的分工是什么？可以只用 detekt 吗？**

**AI答：**

1. **ktlint** = **格式警察**。只管"长什么样"：缩进、换行、import 顺序、命名驼峰、末尾逗号、禁止通配符 import。**不做语义分析**，不管"写得对不对"。
2. **detekt** = **语义警察**。基于 Kotlin PSI 做静态分析，管"写得好不好"：复杂度、过长函数/类、魔法值、命名、返回块数量、潜在 Bug（`UnusedPrivateMember`、`EqualsWithHashCodeExist`）、空安全违规（`UnsafeCallOnNullableType`）。
3. **Android Lint** = **Android 领域专家**。基于 UAST + Android SDK 知识，能发现只有 Android 才有的问题：`HardcodedText`（硬编码文案）、`WrongThread`、`Recycle`、`MissingPermission`、`ObsoleteSdkInt`、`UnusedResources`、`StaticFieldLeak`。
4. **能不能只用 detekt？** 技术上可以覆盖 80% 的格式与语义问题，但会**丢掉 Android 特有的静态检查**（比如 `@SuppressLint("StaticFieldLeak")` 这类只有 Lint 认识）。**推荐三者叠加**：Spotless(ktlint) 管格式 → detekt 管语义 → Android Lint 管 Android 专项 → CI 全部跑。
5. **职责重叠时的取舍**：命名规范 ktlint 和 detekt 都有，**以 detekt 为准**（可配置、可 baseline），关掉 ktlint 的 `function-naming` 等重复规则。

---

**读者问：抽象和扩展函数什么时候该用，什么时候是过度设计？**

**AI答：**

1. **扩展函数的适用场景**（三个同时满足）：
   - **高频**：每个文件至少用 5 次以上。
   - **无上下文依赖**：不需要访问私有成员，不需要 Context。
   - **语义明确**：`String.toDisplayName()` 一眼能懂。
2. **不适合扩展函数的情况**：
   - 需要访问宿主类的私有状态 → 应该做成成员函数。
   - 只有 1~2 处使用 → 写成函数就够。
   - 需要 override 行为（多态）→ Kotlin 扩展是静态派发，无法多态，应定义为接口。
   - 扩展了 `Any` / `Unit` / 基础类型 → 污染全局命名空间，调用方 `import` 时容易冲突。
3. **过度抽象的判断标准**：
   - 为**只有一个实现**的类定义接口 + 工厂 + Builder → 典型 YAGNI。
   - "为了可测试而抽象"是合理的，但**不要为了可测试把所有东西都包一层接口**：真正的解耦点在于**依赖外部资源**（网络、存储、时间、随机数），这些抽象是值得的。
4. **原则**：**抽象要在第二个实现出现时才抽**。但对**边界**（网络、存储、时钟）应**从第一天就抽象**，因为它们天然会有 Fake 实现。
5. **Kotlin 特有优势**：扩展函数让"在不修改原类的前提下加方法"，对**无法修改的类**（第三方库、系统类）非常合适，且比工具类（`StringUtils`）更符合面向对象直觉。

---

**读者问：KDoc 写在什么粒度？每个 public 都要写吗？**

**AI答：**

1. **必须写 KDoc 的**：
   - 所有 `public` / `protected` 的类、接口、函数、属性（尤其是 **对外 SDK**）。
   - 任何有**非显然契约**的东西：线程安全性、是否阻塞、是否可能抛异常、返回值是否可能为 null、幂等性。
   - 复杂算法、兼容处理、临时方案（写清"为什么这么写"和"什么时候可以删掉"）。
2. **不必写的**：一眼可见的自解释代码（`fun getName() = name`）、getter/setter（Kotlin 生成的属性默认就有文档）。
3. **KDoc 的关键标签**：

   | 标签 | 用途 |
   | --- | --- |
   | `@param` | 参数说明，含取值范围、单位、是否可空 |
   | `@return` | 返回值语义（注意区分"空集合"和"null"） |
   | `@throws` | 声明的异常 |
   | `@property` | 主构造函数属性的说明 |
   | `@sample` | 代码示例，Dokka 会渲染 |
   | `@see` | 交叉引用 |
   | `@since` | 引入版本 |

4. **一个高质量 KDoc 的判断**：**能让调用者不读实现就正确使用它**。特别要写清楚**副作用**（这个函数会不会发网络请求？会不会改数据库？会不会切线程？）——这是 KDoc 最常缺失也最重要的部分。

---

**读者问：对外 SDK 怎么做版本管理和兼容性保障？**

**AI答：**

1. **API 兼容性检查工具**：
   - **binary-compatibility-validator**（Kotlin 官方）：生成 `api/*.api` 快照文件，CI 中对比，破坏性变更直接卡住 PR。
   - **Metalava**：Google 出品，适合 Android 库，能生成 API 文本文件。
   - **japicmp** / **revapi**：JVM 通用。
2. **破坏性变更的定义**：删除 public 元素、修改方法签名、修改父类/接口、降低可见性、改变异常行为、修改常量值（对 Kotlin 来说是破坏的）。
3. **语义化版本（SemVer）**：
   - `MAJOR.MINOR.PATCH`：`MAJOR` = 破坏性变更，`MINOR` = 向后兼容的新增，`PATCH` = 修复。
   - Android 库更常见的约定：`x.y.z` 中 `z` 用构建号，`x.y` 对应 API 变更。
4. **灰度与兼容矩阵**：
   - 提供 `@Experimental` / `@RequiresApi` 注解。
   - 高破坏性变更用 **Beta 阶段** + **Deprecated 过渡期**（至少一个小版本），而不是直接删。
5. **Consumer ProGuard Rules**：对外 SDK 必须提供 `consumer-rules.pro`，告诉 R8 哪些类/成员不能混淆，否则使用方的混淆会导致 SDK 反射失效。

---

**读者问：怎么治理遗留（legacy）代码？直接重写还是渐进改造？**

**AI答：**

1. **不要重写**。重写（rewrite）失败率极高，且会丢掉大量隐含的业务规则。行业经验数据（Clayton Christensen / Code Complete 的研究）都指向：**渐进式重构（refactoring）优于重写**。
2. **可落地的四步法**：
   - **第一步：量化**。用 `scopt` / SonarQube / detekt baseline 统计问题分布，找出复杂度最高的 Top N 文件，而不是"全都要改"。
   - **第二步：设卡点**。用 baseline 冻结存量，新增代码零容忍（CI 卡点），实现"不倒退"。
   - **第三步：增量修复**。约定"改到哪修到哪"——任何 PR 触及的文件，其新触发的告警必须修掉，baseline 条目随之减少，形成正循环。
   - **第四步：专项攻坚**。排期 2 周一次，每次治理 3~5 个核心文件，配测试保驾。
3. **测试是前提**：改老代码前先补**特征测试（characterization test）**，锁定当前行为，避免重构引入隐性回归。这是 Martin Fowler 在 *Refactoring* 中反复强调的。
4. **架构隔离**：老代码用 `Anti-Corruption Layer`（防腐层）包起来，新代码不直接调用老代码，逐步替换。
5. **面试话术**：**"治理 legacy 代码的三个抓手是：量化、卡点、增量。我的目标是让 baseline 只会变小不会变大。"**

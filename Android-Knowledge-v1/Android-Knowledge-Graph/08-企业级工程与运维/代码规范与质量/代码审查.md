# 代码审查

## 一句话定义

Code Review（CR）本质上是**用群体的集体经验，对单个提交做一次多视角的"设计对话"**，目的是在代码进入主干之前发现缺陷、传播知识、统一设计。关键不是"挑刺"，而是**在合适的成本下最大化缺陷发现率，同时最小化对人际关系的伤害**。

面试开场：**"Review 的产出不是'通过/不通过'这个状态，而是三样东西：缺陷被拦下、知识被传播、设计被统一。三者缺一，Review 就是形式主义。"**

## 核心原理

### 1. Review 的三个目标与成本

```
┌──────────────────┬──────────────────────────────────┬──────────────────┐
│ 目标              │ 具体形态                          │ 失败表现          │
├──────────────────┼──────────────────────────────────┼──────────────────┤
│ ① 拦截缺陷        │ 逻辑错误、边界遗漏、并发问题、     │ 线上 Crash/ANR   │
│                  │ 内存泄漏、安全漏洞                │                  │
├──────────────────┼──────────────────────────────────┼──────────────────┤
│ ② 传播知识        │ 让新人知道"为什么这样写"、        │ 只有老人能维护   │
│                  │ 熟悉模块的历史与坑                │ 关键模块         │
├──────────────────┼──────────────────────────────────┼──────────────────┤
│ ③ 统一设计        │ 分层是否一致、命名是否一致、      │ 架构逐渐腐化     │
│                  │ 新方案是否违背既有约定            │ （架构腐化）     │
└──────────────────┴──────────────────────────────────┴──────────────────┘

成本：Reviewer 的时间 + Author 的等待 + 返工成本
```

**关键判断**：CR 的**最大价值其实是②和③**，而不是①。缺陷大部分应该由测试、Lint、类型系统拦截；如果一个 bug 能轻易通过 Review，那它更可能来自**没被测到的场景**或**需求本身没想清楚**。所以好的团队会**把 Review 的重心往设计讨论上挪**。

### 2. Review 前的准备：看 diff 之前先看什么

一个只盯着 diff 逐行的 Reviewer，效率极低。正确顺序是：

```
┌─ Step 1  建立上下文 ────────────────────────────────────┐
│  · PR 描述：这次改什么、为什么、影响范围                   │
│  · 关联 Issue / 需求文档 / 设计方案                        │
│  · 变更规模：文件数、行数、模块                            │
└───────────────────────────────────────────────────────┘
┌─ Step 2  看整体结构 ────────────────────────────────────┐
│  · 先看目录树变化、模块划分变化                            │
│  · 新增了哪些类、删除了哪些类、依赖关系是否变化            │
│  · 与主干的设计是否一致                                    │
└───────────────────────────────────────────────────────┘
┌─ Step 3  逐文件细看 ────────────────────────────────────┐
│  · 按"逻辑 → 边界 → 性能 → 安全 → 可维护性"顺序          │
│  · 关注新增行（+），而非删除行                             │
└───────────────────────────────────────────────────────┘
┌─ Step 4  全局回看 ──────────────────────────────────────┐
│  · 这次改动对其它模块/调用方的影响                          │
│  · 有没有遗漏的调用点、测试、文档、配置                     │
└───────────────────────────────────────────────────────┘
```

### 3. 审查清单（Checklist）

这是 Review 质量的决定性因素。没有清单，Reviewer 的关注点会被"代码风格"和"自己最熟悉的模块"占据。

#### 3.1 正确性

| 检查项 | 典型问题 |
| --- | --- |
| 逻辑是否正确 | 分支是否穷尽、`when` 是否缺 `else` |
| 空安全 | `!!` 的使用是否安全、`?.` 链是否会 NPE |
| 边界条件 | 空集合、0、负数、超长字符串、最大值溢出 |
| 集合操作 | `ConcurrentModificationException`、遍历中修改 |
| 协程 | 是否在正确的 scope、是否取消、是否用 `Dispatchers.IO` 做 IO |
| 生命周期 | 是否持有 Activity/View、回调是否在销毁后触发 |
| 线程安全 | 共享可变状态是否有同步、`@Volatile` 是否需要 |
| 资源释放 | `Cursor`、`InputStream`、注册/反注册是否配对 |

#### 3.2 性能

| 检查项 | 典型问题 |
| --- | --- |
| 主线程 IO | 网络、磁盘读写是否在主线程 |
| 内存 | 大对象常驻、`Bitmap` 是否可回收、列表是否全量加载 |
| 布局 | 深层嵌套、过度绘制（`overdraw`）、`include` 权重 |
| 对象分配 | 循环中创建对象、`String` 频繁拼接 |
| 冷启动 | Application 中初始化了什么、是否可延迟 |
| 列表 | 是否用 DiffUtil/Compose 差分、是否 `notifyDataSetChanged` |

#### 3.3 安全与隐私

| 检查项 | 典型问题 |
| --- | --- |
| 数据存储 | 敏感信息是否明文写入 SharedPreferences/文件 |
| 传输 | 是否明文 HTTP、是否信任所有证书 |
| 日志 | 是否打印了手机号、Token、身份证、密码 |
| 权限 | 是否申请了不必要的权限、是否用 `READ_EXTERNAL_STORAGE` 全量 |
| 组件暴露 | `exported=true` 是否必要、是否缺少 `permission` 保护 |
| 输入校验 | WebView 的 `addJavascriptInterface`、Intent 来自外部时的参数校验 |
| WebView | `setAllowFileAccess`、`setAllowUniversalAccessFromFileURLs` |

#### 3.4 可维护性与设计

| 检查项 | 典型问题 |
| --- | --- |
| 分层 | UI 里有没有写业务逻辑、Repository 有没有碰 UI |
| 命名 | 是否与既有命名体系冲突、是否表意准确 |
| 抽象 | 是否重复实现、是否有不必要的间接层 |
| 兼容 | 是否有 `Build.VERSION` 判断遗漏、是否有降级路径 |
| 依赖 | 是否引入了不该引入的库、是否有循环依赖 |
| 注释 | 复杂逻辑是否解释了"为什么" |
| 测试 | 关键逻辑与 bug 修复是否有对应测试 |

### 4. 评论分级体系

**分级是 Review 最重要的沟通机制**。不分级会导致："一个拼写错误"和"架构方向错了"在同一个评论列表里，作者无法判断优先级，最终要么全改（浪费）要么全不改（危险）。

| 级别 | 标记 | 含义 | 作者必须做 |
| --- | --- | --- | --- |
| **Blocking** | `🔴` / `must` | 必须修改才能合并 | 必须改或明确说明不改的理由 |
| **Suggestion** | `🟡` / `suggestion` | 建议改，不改也能合 | 可以接受并说明理由 |
| **Question** | `🔵` / `question` | 提问，需求不明确时 | 必须回复 |
| **Nit** | `⚪` / `nit` | 吹毛求疵（命名/格式） | 随意，最好由工具处理 |

**一个实用的编码方式**——用 commit message 前缀实现"机器可读的分级"：

```text
# PR 评论中的前缀约定
blocking: 这里在主线程做了网络请求，必须移到 Dispatchers.IO
suggestion: 建议把 if-else 链改成 when，可读性更好
question: 这个阈值 0.75 是业务给定的还是拍脑袋？
nit: import 顺序反了（不过 ktlint 会自动修）
```

或使用 **Conventional Comments** 规范：

```text
praise: 这里的抽象很到位
nitpick: 变量名 data 可以更具体些
issue: 存在并发写风险
question: 为什么不复用已有的 CacheManager?
blocking: 必须处理空指针
suggestion: 建议补充单元测试
```

> **工具支持**：Reviewable、Graphite、Phabricator、GitHub 的 `.github/reviewable.yml`（配置评论模板）、以及各类 CR 机器人，都支持这种标记体系。

### 5. 建设性反馈的句式

**核心原则：把"人"和"事"分开**。评价代码，不评价人。

```
❌ 差句式（攻击性 / 无信息量 / 无替代方案）
   "这里写得太烂了。"
   "又是这种写法？"
   "为什么要这么写？"
   "你根本没考虑过性能吧。"

✅ 好句式（事实 + 影响 + 建议）
   "这里在主线程直接做了一次数据库查询（Room 的 query 是同步的），
    在低端机上会导致列表首帧多出 200~400ms。
    建议改成 suspend 函数并在 Repository 层切到 Dispatchers.IO，
    ViewModel 里用 viewModelScope.launch 调用。"

✅ 更好句式（事实 + 影响 + 建议 + 意图确认）
   "这里用 SharedPreferences 存 Token，我理解是为了避免引入 DataStore 的依赖。
    但 SharedPreferences 的 apply() 是异步落盘的，用户在极短时间内杀进程有丢失风险，
    而且明文存储有安全审计问题。
    建议改用 DataStore + EncryptedSharedPreferences / 或直接放 KeyStore，
    如果依赖敏感，我们可以先只在 core-network 模块引入。"
```

**句式模板**：

```
【事实】我看到什么（客观描述代码）
  ↓
【影响】这会导致什么（对用户/系统/团队的实际后果）
  ↓
【建议】我建议怎么做（具体的、可执行的方案，最好带代码片段）
  ↓
【开放】如果有隐含考虑请说明（"如果是因为 X 那没问题"）
```

### 6. 大 PR 的拆分

一个 3000 行的 PR 是 Review 的噩梦，作者累、Reviewer 更累。

**拆分维度**（按推荐顺序）：

| 方式 | 说明 | 优点 | 注意 |
| --- | --- | --- | --- |
| **纯机械重构** | 先只做移动/改名/格式化，无逻辑变化 | Reviewer 只需确认"没改逻辑" | 用独立 commit，便于 `git revert` |
| **新旧并行** | 新增实现但暂不接线，验证后再切换 | 每步都可独立验证 | 会有短暂的双份代码 |
| **按层拆** | 先加接口+实现，再改调用方 | 每层职责清晰 | 调用方改动量大时不适合 |
| **按模块拆** | 按 feature/模块拆成多个 PR | 边界清晰 | 需要约定依赖顺序 |
| **按文件拆** | 最后一个手段 | 机械 | 会产生大量分支冲突 |

**"新代码先行"（Expand-Migrate-Contract）模式**是现代大型改造的标准做法：

```
PR 1: 引入新接口与新实现（不接线）        ← 可独立合并，无风险
PR 2: 把调用方迁移到新接口（可分多次）    ← 每个模块一个 PR
PR 3: 移除旧实现与兼容层                 ← 确认无调用方后删除
```

**关键纪律**：每个 PR 必须**可独立构建、可独立发布、可独立回滚**。中途任何一步出问题，都不应该让主干处于不可用状态。

### 7. Review 的度量

不要用"Review 数量"或"评论数"当 KPI，那会激励刷评论。真正有意义的是：

| 指标 | 含义 | 注意点 |
| --- | --- | --- |
| **缺陷逃逸率** | 线上问题中本应在 CR 阶段发现的占比 | 需要事故复盘归因 |
| **Review 时长** | PR 从提交到首次有效反馈的时间 | 关注 P50 和 P90，不看均值 |
| **返工率** | 需要 3 轮以上 Review 才通过的 PR 占比 | 反映需求清晰度与作者水平 |
| **首轮通过率** | 一次 Review 就通过的占比 | 反映规范清晰度 |
| **响应时间** | Reviewer 的平均响应时长 | 团队健康度指标 |
| **知识扩散** | 模块的 Bus factor（多少人能维护） | 定性评估 |

> **反模式**：把"Review 通过速度"作为个人 KPI → 演变成橡皮图章审批。应该考核的是**缺陷拦截质量**和**知识扩散**。

### 8. 团队机制设计

| 机制 | 作用 | 注意 |
| --- | --- | --- |
| **CODEOWNERS** | 指定目录的必审人 | 配合 PR 自动指派 Reviewer |
| **至少 2 人批准** | 防止单人犯错 | 小团队可降低到 1 人 + 自动检查 |
| **作者不得自审** | 基本原则 | 紧急 hotfix 可豁免但需事后补审 |
| **24 小时首响 SLA** | 防止 PR 腐烂 | 超过 1 天作者可以 @ 催办 |
| **每日 Review 时间** | 固定时间集中 Review | 减少打断成本 |
| **结对 Review** | 新人 + 老手共同 Review | 知识传递效率最高 |
| **架构评审** | 涉及架构的变更需架构组评审 | 与普通 CR 分开，走设计评审流程 |

### 3. 用 GitHub API 做自动化审查检查

```yaml
# .github/workflows/pr-quality.yml
name: PR 质量检查

on:
  pull_request:
    types: [opened, synchronize, reopened]

jobs:
  size-check:
    name: "PR 规模检查"
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with: { fetch-depth: 0 }
      - name: "检查变更规模，超过 800 行需拆分"
        run: |
          BASE=${{ github.event.pull_request.base.sha }}
          HEAD=${{ github.event.pull_request.head.sha }}
          LINES=$(git diff --numstat "$BASE" "$HEAD" | awk '{a+=$1; d+=$2} END {print a+d}')
          echo "变更行数: $LINES"
          if [ "$LINES" -gt 800 ]; then
            echo "::error::PR 过大（$LINES 行），请按 https://wiki.internal/pr-split 拆分后重提"
            exit 1
          fi

  comment-template:
    name: "评论分级模板"
    runs-on: ubuntu-latest
    steps:
      - uses: actions/github-script@v7
        with:
          script: |
            const body = `### Review 指南
请使用以下前缀标注评论，以便作者判断优先级：

| 前缀 | 含义 | 是否必须处理 |
| --- | --- | --- |
| \`blocking:\` | 必须修改才能合并 | ✅ |
| \`suggestion:\` | 建议修改 | ❌ |
| \`question:\` | 需要作者澄清 | ❓ |
| \`nit:\` | 细节，可选 | ⭐ |

格式要求：**事实 → 影响 → 建议**。
`;
            await github.rest.issues.createComment({
              owner: context.repo.owner,
              repo: context.repo.repo,
              issue_number: context.issue.number,
              body: body
            });
```

### 4. 结构化的 Review 记录（ADR 式）

```markdown
<!-- docs/reviews/2026-11-19-user-cache-review.md -->
# CR 记录：用户缓存模块重构

- **PR**：[#456](https://github.com/org/repo/pull/456)
- **Reviewer**：@zhaoliu
- **日期**：2026-11-19
- **结论**：Request Changes → Approved（第二轮）

## 关键讨论点

### 1. 缓存失效策略（已达成一致）
- **作者初版**：LRU + 固定 TTL
- **Reviewer 意见**（suggestion）：用户信息变更后 5 分钟内仍返回旧值，
  会导致"我改了昵称但没生效"的客诉。建议改为**写操作主动失效 + 读操作 TTL 兜底**。
- **结论**：采纳。写路径调用 `cache.invalidate(userId)`，TTL 从 5 分钟降到 60 秒。

### 2. 线程安全（blocking）
- **问题**：`ConcurrentHashMap` 的 `computeIfAbsent` 中执行了可能阻塞的磁盘读，
  高并发下会锁住 bin，拖慢整个 map。
- **结论**：改为**先 get，miss 再异步加载并 putIfAbsent**，避免在锁内做 IO。

### 3. 接口抽象（question）
- 作者抽出 `UserCache` 接口但目前只有一个实现。
- **讨论**：这是为测试预留的边界（合理）还是过早抽象？
- **结论**：保留接口，但明确记录理由是**可测试性**，不是"将来会有多种实现"。
  写入代码注释，避免后人误以为要扩展。

## 遗留问题
- [ ] TODO(作者)：为 `DiskUserCache` 补充单测，deadline: 下个迭代
```

### 5. Review 时常用的辅助命令

```bash
# 只看新增行（忽略删除行），减少噪音
git diff -U0 origin/main...HEAD | grep -E '^\+' | grep -v '^+++'

# 按文件统计改动量，快速定位大改动文件
git diff --stat origin/main...HEAD

# 看某个文件的完整改动上下文
git diff -w --ignore-blank-lines origin/main...HEAD -- path/to/File.kt

# 查找新增的魔法数字与 TODO
git diff origin/main...HEAD | grep -nE '^\+.*(TODO|FIXME|XXX|HACK)'

# 检查是否遗留调试日志
git diff origin/main...HEAD | grep -nE '^\+.*(Log\.[dviw]|System\.out|printStackTrace)'

# 检查是否新增了 @Suppress 抑制（滥用风险）
git diff origin/main...HEAD | grep -nE '^\+.*@Suppress'

# 查看本地未推送的提交
git log --oneline origin/main..HEAD

# 检查提交信息是否符合 Conventional Commits
git log --format='%s' origin/main..HEAD | grep -vE '^(feat|fix|docs|style|refactor|perf|test|build|ci|chore|revert)(\(.+\))?!?: .+'
```

## 常见问题 / 面试要点

**读者问：CR 提了问题作者不改，Reviewer 怎么办？**

**AI答：**

1. **先确认是"沟通问题"还是"共识问题"**。大多数情况是前者：作者没看懂评论的严重性，或者评论写得太"模糊"（"这里不太好"）。
2. **升级路径**：
   - **第一次**：私聊（IM）沟通，确认是否理解。**不要在 PR 里吵**。
   - **第二次**：在 PR 里明确标记 `blocking:`，并**给出具体替代方案和理由**，把"我觉得"变成"我建议 A 而不是 B，因为 C"。
   - **第三次仍未改**：**不要无限僵持**。用团队流程解决：
     - 若 PR 有明确阻塞项 → **close 掉 PR**，作者重新拆分或重写。
     - 若只是偏好差异 → **降级为 suggestion**，明确"这条我不坚持，作者可自行决定"。
     - 若是架构分歧 → **升级为设计评审**，由架构负责人拍板并记录到 ADR（架构决策记录）。
3. **Reviewer 的义务**：如果作者坚持不改，**Reviewer 应当 allow**（不阻塞合并），除非确实是明确的 bug 或安全问题。强行阻塞会让团队的信任崩塌，也会让 Reviewer 变成"流程闸门"而非"同行帮助"。
4. **反模式**：
   - ❌ 用 `Request Changes` 表达个人偏好 → 工具语义被稀释，真正阻塞时也没人当回事。
   - ❌ 无限期挂起 PR → 作者的上下文已经丢失，review 成本翻倍。
   - ❌ 在公开评论区争论风格 → 升级为线下沟通 + 结论回帖。
5. **预防优于治疗**：
   - **前置对齐**：开 PR 前先发方案（哪怕 3 行字），避免"实现完了才发现方向不对"。
   - **明确团队约定**：哪些是硬性规范（工具可查），哪些是偏好（可讨论）。
   - **Owner 制度**：关键模块的 owner 对架构一致性有最终解释权，流程上提前写清。

**读者问：怎么写一条高质量的 CR 评论？**

**AI答：**

1. **结构**："事实 → 影响 → 建议 → 开放性结尾"，一段话讲清。
2. **给上下文**：不要假设对方知道你在想什么。评论里要包含**必要的代码位置**（类名 + 方法名）和**背景知识**（为什么你关心这个）。
3. **给可执行方案**：最好直接贴代码片段或链接到官方文档。举例：

```text
blocking: `refreshUser()` 在主线程调用了 `api.getUser()`（Retrofit 的同步方法）。

这段代码会在弱网下阻塞 UI 线程最长 10s，直接触发 ANR。
建议改成 suspend + Retrofit 的挂起函数，ViewModel 里用 viewModelScope.launch：

    suspend fun refreshUser(): User = api.getUser(id)

或在 Repository 层用 withContext(Dispatchers.IO) 包一层。

参考：https://developer.android.com/topic/architecture/additional-recommendations
```

4. **区分事实与偏好**：用不同前缀（`blocking` / `suggestion` / `nit`），让作者知道哪些是必须改的。
5. **避免"你"**：写"这段代码"而不是"你写的代码"。研究（Google 的 Developer Productivity Research）显示指向"人"的措辞会显著降低后续修改意愿。
6. **多问少判**：不确定对方意图时用 `question:`，而不是直接断言错误。低成本地问一句，比高成本地吵一架划算。
7. **正向反馈**：好的代码也应该被明确表扬（`praise:`）。全是负面评论的 PR，作者下次会抵触 Review，甚至拆小 PR 规避。

> **面试话术**："我 Review 时的原则是：每条评论都要包含**可执行的下一步**。如果我说不出该怎么改，那说明我还没理解清楚，那就不该评论。"

**读者问：大项目的 PR 应该控制在多大？怎么拆分？**

**AI答：**

1. **经验数字**：
   - **≤ 400 行变更**：理想状态，一次 Review 20~30 分钟。
   - **400~800 行**：可接受，但需要分文件多次评审。
   - **> 800 行**：应该拆分。可以直接在 CI 里加卡点（本次给的 workflow 就是这么做的）。
   - **> 2000 行**：几乎必然有问题，通常是"重构 + 功能变更"混在一起了。
2. **拆分的三个维度**（优先顺序）：
   - **按"性质"拆**：机械重构（移动/改名）与逻辑变更分开。重构 PR 的 Review 只需确认"逻辑等价"，成本极低。
   - **按"边界"拆**：按模块/调用方拆，每个 PR 影响面小。
   - **按"步骤"拆**：用 Expand-Migrate-Contract 模式。
3. **拆分时的纪律**：
   - **每个 PR 必须独立可编译、可测试、可发布**。
   - **不允许"中间态不可用"**：比如"先删掉旧接口，再改所有调用方"这种顺序是错的，应该反过来。
   - **避免长时间半成品分支**：分支存活超过 3 天就要考虑重新整理，否则 merge 冲突成本指数上升。
4. **给作者的建议**：
   - 开工前先发一条"我打算这样拆"的评论，和 Reviewer 对齐拆法，避免拆了对方不认。
   - 用 `git rebase -i` 把逻辑相关的 commit 压成一个，保持每个 commit 可编译（**bisect-friendly**）。这对二分定位 bug 至关重要。

---

**读者问：Review 时应该重点看 diff 吗？只看 diff 有什么风险？**

**AI答：**

1. **只看 diff 的三个盲区**：
   - **上下文缺失**：diff 看不到调用方。改了方法签名，diff 里只有签名变化，但真正的问题在 10 个调用方。
   - **隐含约定缺失**：看不到"这个模块规定所有 IO 必须在 Repository 层""这个类必须主线程访问"——这些是**不在代码里、只在文档/口头里**的约定。
   - **意图缺失**：看不到作者为什么这么改，也就无法判断改动是否解决了正确的问题。
2. **推荐的审查动作**：
   - 先读 PR 描述 + 关联 Issue。
   - 用 IDE 的 "Find Usages"（AS 里 `⌘+F7`）看被改方法的调用方。
   - 看类的完整实现而不是 diff 片段，理解它现在承担了哪些职责。
   - 对新增的 public API，确认是否需要更新文档与调用方。
3. **特别容易被忽略的检查项**：
   - **调用方是否都改了**：改了签名但漏改调用方 → 编译错误（能发现）；改了语义但漏改调用方 → **逻辑 bug（发现不了）**。这是最危险的一类。
   - **新增的权限/依赖是否在 manifest 声明**。
   - **是否需要数据迁移**（数据库 schema 变更）。
   - **是否影响 App Store / Play 上架合规**（隐私政策、权限说明）。
4. **一句话总结**：**diff 告诉你"改了什么"，但 Review 要回答的是"改得对不对"**——后者需要 diff 之外的信息。

---

**读者问：Review 该关注业务逻辑吗？还是只看技术实现？**

**AI答：**

1. **理想状态是都关注**，但现实是分工的：
   - **业务/产品**关注：功能是否满足需求、边界场景（空态、错误态、超长文本、多语言）、文案是否准确。
   - **资深开发**关注：技术实现、架构一致性、性能、安全。
   - **QA**关注：测试用例、回归范围。
2. **资深开发必须关注业务**，理由：
   - 业务代码里藏着最贵的 bug——**需求理解偏差**。技术再完美，实现的不是想要的东西也没意义。
   - 例子："这个列表只显示前 10 条"如果没说清是"每页 10 条"还是"总共 10 条"，技术 Review 100 次也发现不了。
3. **但要有边界**：Review 时不要替产品做决策。
   - 好的做法：`question: 这里的"最多 5 条"是指每页 5 条还是总共 5 条？我按每页理解写的，如果是后者需要服务端配合。`
   - 差的做法：`这里应该是每页 5 条，你写错了。`
4. **提效手段**：需求/设计文档在 PR 之前评审（见 [[../文档与协作]]），Review 阶段就能聚焦实现。

---

**读者问：Code Review 的收益到底有多少？怎么说服团队投入？**

**AI答：**

1. **可量化的收益**：
   - **缺陷拦截**：业界普遍经验是 Code Review 能拦截相当比例的缺陷（不同研究差异大）。更可靠的数据是 Code Complete 与 Google's Developer Productivity Research：引入 CR 后，缺陷率显著下降、交付周期缩短。
   - **知识扩散**：Bus factor 提升是更长期的收益。新人通过 Review 老代码学到的架构意图，往往比看文档学到的更多。
   - **一致性**：避免"每个模块一种写法"，长期降低维护成本。
2. **不能量化的收益**：
   - **团队共识**：对架构方向的集体认同，减少后续扯皮。
   - **心理安全**：Review 是暴露问题最安全的时刻。
3. **成本与收益的平衡**：
   - **成本**是 Reviewer 的时间（可能是 Author 的 2~3 倍）。
   - **收益是长期的**（缺陷成本在生产环境是 Review 成本的 10~100 倍：一条线上 Crash 的排查成本可能超过 100 小时的 Review）。
   - **关键判断**：**Review 的 ROI 取决于缺陷逃逸率**。如果你的测试覆盖率低，Review 是最后一道防线，ROI 高；如果测试完善，Review 的 ROI 更多体现在知识扩散上。
4. **说服团队的策略**：
   - 不要用"规范要求"这种理由，用**实际事故案例**："上个月那个线上问题，事后复盘发现是两个人都没注意到这个边界——如果当时有第二个人 Review，2 小时就能发现。"
   - 把"Review 找出的问题数"记录下来并可视化，让贡献可见。
   - 保护 Reviewer 的时间：把 Review 作为**优先级最高的工作**，不允许被其他任务随时打断。

---

**读者问：AI 时代，Code Review 还有价值吗？**

**AI答：**

1. **AI 擅长的部分**（可以自动化）：
   - **风格与格式问题** → 已被 Lint/detekt 覆盖。
   - **明显的 bug 模式**：空指针、边界遗漏、资源泄漏、并发问题 → AI 能给出不错的初筛。
   - **重复代码、过度抽象** → AI 有一定判断力。
   - **生成单测、生成文档、生成 commit message**。
2. **AI 不擅长 / 有风险的部分**：
   - **业务意图**：AI 看不到组织上下文，不知道"这个字段为什么允许为空"。
   - **架构一致性**：AI 不知道"我们三个月前决定所有 IO 必须在 Repository 层"。
   - **隐性风险**：如"这个改动会让运营的某个看板口径变掉"。
   - **过度自信**：AI 会给出一段看起来对的代码，但可能是错的，且 Review 者容易放松警惕（**Automation Bias**，自动化偏见）。
3. **AI 的最佳定位**：
   - **第一遍过滤**：AI 先扫一遍，生成"待确认清单"，人类 Reviewer 聚焦高风险处 → **人类注意力从 100% 投入变成 30% 投入但覆盖度更高**。
   - **自动化执行**：自动生成单测、自动补 KDoc、自动检查一致性。
   - **不能替代的**：架构决策、风险判断、人的最终签字。
4. **实践建议**：
   - 在 PR 里挂 AI Review 机器人（CodeRabbit、Greptel、Codium 等），输出"可疑点"供人参考。
   - **明确责任**：AI 的评论不作为审批依据，最终责任人仍是人。
   - **保护质量信号**：不要因为"AI 已经 Review 过了"而降低人的审查强度。历史上自动化检查引入后，人工检查强度往往下降，但自动化检查的覆盖面小于人的直觉。
5. **面试话术**："我认为 AI 让 Review 从'逐行挑错'转向'设计审查'。机器负责确定性，人负责判断力。这恰恰是 CR 应该演进的方向。"

# 流水线设计

## 一句话定义

CI/CD 流水线是把"**代码变更 → 可交付制品**"这条路径上所有重复、易错、依赖人工记忆的动作，**固化成一条每次提交都自动执行、可审计、可回滚的自动化流水线**。它的核心价值不是"快"，而是"**让错误在代价最低的地方暴露**"——把编译错误拦在 PR 阶段、把 Lint 拦在合并阶段、把 Crash 拦在灰度阶段，而不是都拦在用户手机上。

面试开场：**"流水线设计的本质是'**分层设防 + 快速反馈**'。便宜的检查放前面（秒级），昂贵的检查放后面（分钟级）。一个 PR 打开 20 分钟后才知道编译不过，开发者早就去干别的了，反馈的价值就衰减了。"**

## 核心原理

### 1. CI/CD 的概念边界

```text
┌──────────────────────────────────────────────────────────────────────┐
│  CI（Continuous Integration，持续集成）                                 │
│  目标：每次代码变更都自动验证                                         │
│  动作：拉代码 → 装依赖 → 编译 → Lint → 单测 → 集成测试 → 产出报告      │
│  触发：push / PR / 定时                                                │
├──────────────────────────────────────────────────────────────────────┤
│  CD（Continuous Delivery / Deployment）                                │
│  目标：把通过验证的制品自动交付到用户                                   │
│  动作：打包 → 签名 → 上传商店 → 灰度 → 全量                            │
│  关键区别：Delivery（交付到环境，人工点发布）vs Deployment（全自动）      │
└──────────────────────────────────────────────────────────────────────┘
```

**移动端的特殊性**（这是与后端 CI/CD 最大的差异，也是面试的加分点）：

| 差异点 | 后端 CI/CD | Android CI/CD |
| --- | --- | --- |
| **制品形态** | 容器镜像 / jar | **APK / AAB**（平台强制 AAB） |
| **分发方式** | 推送到服务器即刻生效 | **必须过应用商店审核**（Google Play 通常数小时到数天） |
| **回滚方式** | 切镜像 tag，秒级 | **商店回滚通常要重新审核**；因此**必须靠热修复和功能开关** |
| **签名** | 无 | **必须有 keystore，且密钥管理是核心安全问题** |
| **多渠道多 ABI** | 无 | 需要出 4 个 ABI × N 个渠道的产物 |
| **构建环境** | 容器，标准化 | **JDK/AGP/SDK 版本敏感**，需要固定镜像 |
| **发布节奏** | 随时发布 | 受商店审核约束，通常 1~2 周一次 |

> **核心结论**：因为**商店审核导致回滚极慢**，所以 Android 侧的 CI/CD 真正的价值不在"更快发布"，而在"**更早发现问题 + 更快灰度 + 可热修复**"。这直接引出了本部分的两篇核心笔记：[[../灰度发布与监控]] 与 [[../热修复与动态化]]。

### 2. 三大 CI 平台对比

| 维度 | **GitHub Actions** | **GitLab CI** | **Jenkins** |
| --- | --- | --- | --- |
| **部署形态** | 云端（SaaS） | 云端 / 自建 | 自建为主（也支持云） |
| **配置方式** | `.github/workflows/*.yml` | `.gitlab-ci.yml` | `Jenkinsfile`（Groovy） |
| **与代码托管** | 与 GitHub 深度绑定 | 与 GitLab 深度绑定 | 独立，支持任意 Git |
| **免费额度** | 公共仓库无限；私有仓库 2000 分钟/月 | 自建无限 | 自建无限（需付服务器成本） |
| **Runner** | GitHub 托管 / 自建 | GitLab 托管 / 自建 | **完全自建**（需装 Android SDK） |
| **生态** | Action 市场，极其丰富 | 内置 Registry、Package、Security | 插件最多但维护参差、插件依赖地狱 |
| **Android 生态** | `gradle/actions/setup-gradle`、`nttld/setup-ndk` | 官方 Android 模板 | 需自己配 SDK/NDK/模拟器 |
| **缓存** | `actions/cache` / `setup-gradle` 内置 | `cache` 关键字 | 需装 Cache 插件 |
| **密钥管理** | Secrets + OIDC | CI/CD Variables + Masked Variables | Credentials + Vault |
| **学习曲线** | 低（YAML + Action 组合） | 中 | **高（Jenkinsfile 是 Groovy，调试困难）** |
| **适合场景** | **开源 / 中小团队 / 想快速起步** | 已用 GitLab 的团队 | **企业内部 / 有定制化需求 / 合规要求** |

**选型建议（面试话术）**：
> "如果是**新项目或者中小团队**，我推荐 **GitHub Actions**——`setup-gradle` action 开箱即用地处理了 JDK/缓存，`gradle/actions` 还内置了 Build Scan，配置量最小。如果是**公司已有 GitLab**，就用 GitLab CI，MR 流水线是天然集成的。如果是**大型企业**（有多环境隔离、审批流、审计要求、需要接内部制品库），用 **Jenkins**——它的优势是**自定义能力最强、可以复用现有的运维体系**（K8s、Vault、制品库），劣势是维护成本高、插件版本地狱、以及 **Jenkinsfile 的 Groovy 调试对 Android 团队并不友好**。"

### 3. 流水线阶段划分（分层设防）

```text
┌────────────────────────────────────────────────────────────────────────┐
│  PR 阶段（秒~分钟级）—— 目标是"最快给出反馈"                            │
│  ┌──────────────────────────────────────────────────────────────────┐  │
│  │ ① Lint + 静态检查     ~30s   ← 便宜、快、拦住低级错误               │  │
│  │ ② 单元测试            ~1min  ← 纯 JVM，秒级反馈                    │  │
│  │ ③ 编译检查（assembleDebug） ~2min ← 编译错误在这里拦              │  │
│  └──────────────────────────────────────────────────────────────────┘  │
├────────────────────────────────────────────────────────────────────────┤
│  Merge / Nightly 阶段（分钟级）—— 目标是"深度验证"                       │
│  ┌──────────────────────────────────────────────────────────────────┐  │
│  │ ④ 集成测试 / UI 测试   ~10min  ← 模拟器或真机农场                  │  │
│  │ ⑤ 覆盖率检查 + 质量门禁  ~instant                               │  │
│  │ ⑥ 依赖漏洞扫描 (SCA)   ~2min                                   │  │
│  │ ⑦ APK 构建 + 混淆      ~5min                                   │  │
│  │ ⑧ APK 体积检查 + 签名   ~1min                                   │  │
│  └──────────────────────────────────────────────────────────────────┘  │
├────────────────────────────────────────────────────────────────────────┤
│  Release 阶段（tag 触发）—— 目标是"可交付"                              │
│  ┌──────────────────────────────────────────────────────────────────┐  │
│  │ ⑨ 构建 Release AAB（多渠道 × 多 ABI）                            │  │
│  │ ⑩ 上传 mapping.txt / symbols 到崩溃平台                          │  │
│  │ ⑪ 签名 + 上传 Play Console（internal → closed → production）     │  │
│  │ ⑫ 创建 Git tag + GitHub Release                                │  │
│  └──────────────────────────────────────────────────────────────────┘  │
└────────────────────────────────────────────────────────────────────────┘
```

**核心原则：**

1. **便宜的检查放前面**。Lint（30s）必须排在 UI 测试（10min）前面。顺序反了，开发者要等 10 分钟才知道自己少了个分号。
2. **失败的阶段必须阻断后续**（fail-fast）。但**关键路径上的非阻断项可以并行**。
3. **每个阶段独立可重跑**。不要一个大 job 跑完所有事——挂了就全部重跑。
4. **PR 阶段用 `Debug` 变体，Release 阶段用 `Release` 变体**。Release 有混淆、签名、压缩，耗时和内存占用都高得多。

### 4. 缓存策略

Android 构建的缓存分四层，**每一层都值得单独配置**：

| 缓存层 | 内容 | 失效条件 | 典型收益 |
| --- | --- | --- | --- |
| **① 依赖缓存** | `~/.gradle/caches/modules-2`（Maven 依赖） | 依赖版本变更 | **最大（首省 3~5 分钟）** |
| **② 构建缓存** | `~/.gradle/caches/build-cache-1`（任务输出） | 任务输入变化 | 大（命中即跳过整个任务） |
| **③ 配置缓存** | `.gradle/configuration-cache` | 构建脚本变化 | 配置阶段从 60s → 5s |
| **④ Kotlin 增量缓存** | `build/kotlin/` | 源文件变化 | 中 |

**关键点**：
- **缓存 key 必须包含"影响结果的输入"**。最经典的坑：缓存 key 只用了 `hashFiles('**/*.gradle')`，结果**依赖版本变了但缓存没失效**，构建出了**用旧依赖的新包**——线上事故。
- 正确做法：key 里包含 `gradle-wrapper.properties` + `**/*.gradle.kts` + `gradle.properties` + **锁定的依赖版本文件**。
- **缓存命中率的观测**：`gradle-build-action` 会输出 `Cache restored from key: ...` 的日志。

```yaml
# GitHub Actions：使用官方 setup-gradle action（自动处理依赖缓存 + 构建缓存）
- name: Setup Gradle
  uses: gradle/actions/setup-gradle@v4
  with:
    cache-read-only: ${{ github.ref != 'refs/heads/main' }}   # ★ PR 只读缓存，避免污染
    cache-write-only: ${{ github.ref == 'refs/heads/main' }}  # ★ 只在主干写缓存
    gradle-home-cache-cleanup: true

- name: Build with build cache
  run: ./gradlew :app:assembleRelease --build-cache
```

**缓存写入策略的关键决策**：
- **PR（PR 流水线）**：**只读缓存**（`cache-read-only: true`）——PR 的构建产物是不可信的（可能来自 fork），不应该写进共享缓存污染别人。
- **主干 / Release**：**独占写缓存**。
- **缓存大小上限**：GitHub Actions 单个缓存上限 10GB，超出会保存失败，需要定期清理。

### 5. 密钥管理

#### 5.1 三种方案对比

| 方案 | 原理 | 优点 | 缺点 | 适用 |
| --- | --- | --- | --- | --- |
| **静态 Secrets** | 平台存密钥，CI 注入为环境变量 | 简单 | **长期有效**，泄露后难察觉；无法审计使用 | 小团队、非敏感配置 |
| **OIDC 联邦身份** | CI 用短期身份令牌向云厂商换取**临时凭据**（AWS STS / GCP SA / Azure） | **无需存密钥**、凭据自动过期、**每次使用有审计日志** | 需要配置信任策略（一次性成本） | **推荐：云上构建** |
| **Vault / KMS** | 从密钥管理系统动态取密钥 | 密钥可轮换、精细权限、完整审计 | 引入额外组件与网络依赖 | 大型企业、金融 |

#### 5.2 OIDC 的工作原理（面试高频）

```text
传统方式：
  CI 平台存一份 AK/SK（长期有效）
    → 泄露后攻击者可以随时使用，CI 平台日志也看不出来

OIDC 方式：
  ① CI 平台（GitHub Actions）用 OIDC Provider 生成一个短期 JWT
     payload 里包含：仓库名、分支、workflow 名、actor、ref
     ★ 这些信息是【由 CI 平台签名的】，云厂商可以验证签名，
       并通过 trust policy 限制"只有 main 分支的 deploy workflow 能换取凭据"
  ② CI 用这个 JWT 调用云厂商的 STS（AssumeRoleWithWebIdentity）
  ③ 云厂商验证 JWT 签名 + trust policy → 返回【临时凭据】（15 分钟过期）
  ④ CI 用临时凭据访问 S3 / Play Console
     → 凭据过期后自动失效，无需任何清理
```

**OIDC 的四大优势**：
1. **仓库里没有密钥**（拉代码的人拿不到云权限）。
2. **凭据自动过期**（泄露窗口从"永久"缩短到"15 分钟"）。
3. **完整审计**（云厂商侧有谁在什么时间用什么身份换了凭据的日志）。
4. **权限可精确到分支**（PR 分支的 workflow 根本换不到生产凭据）。

```yaml
# .github/workflows/release.yml：使用 OIDC 换取 GCP 短期凭据
permissions:
  contents: read
  id-token: write          # ★ 申请 OIDC token 的权限

steps:
  - name: Authenticate to Google Cloud
    uses: google-github-actions/auth@v2
    with:
      workload_identity_provider: ${{ secrets.GCP_WIF_PROVIDER }}
      service_account: ${{ secrets.GCP_SERVICE_ACCOUNT }}

  - name: Upload to Play Console
    env:
      # GOOGLE_APPLICATION_CREDENTIALS 已由上一步注入为临时凭据
      SERVICE_ACCOUNT_JSON: ${{ secrets.PLAY_SERVICE_ACCOUNT }}
    run: ./gradlew publishReleaseBundle
```

#### 5.3 密钥管理的红线

| 红线 | 说明 |
| --- | --- |
| **密钥绝不进 Git** | keystore 文件、密码、服务端密钥一律进 Secrets 或 Vault |
| **`local.properties` 不入库** | 必须在 `.gitignore` 里 |
| **日志脱敏** | `echo "::add-mask::$SECRET"` 或平台自动 mask；注意 `set -x` 会打印 |
| **密钥要能轮换** | 泄露后必须能快速换掉；keystore 轮换需要重签所有包（存量用户要更新） |
| **第三方 Action 要审计** | `uses: someone/action@v1` 会拿到你的 Secrets；用官方 Action 或固定 commit SHA |
| **Fork PR 不能拿到密钥** | 外部贡献者的 PR 不应触发任何带密钥的 job |

### 6. 制品管理与版本号规范

#### 6.1 版本号的三段式

```text
versionName = "3.8.2"        用户可见：主版本.次版本.修订号
versionCode = 30802          整数，必须单调递增：主版本×10000 + 次版本×100 + 修订号
buildNumber = "3812"         CI 每次构建自增（用于区分同版本的不同构建）
```

| 位 | 含义 | 什么时候加 |
| --- | --- | --- |
| **主版本** | 不兼容的 API 变更或大重构 | 大版本发布 |
| **次版本** | 新增功能，向后兼容 | 常规功能迭代 |
| **修订号** | Bug 修复 | 补丁版本 |

**规则**：
- **`versionCode` 必须严格单调递增**，且**大于商店上已发布的任何版本**——否则上传会被 Google Play 拒绝（`INSTALL_FAILED_VERSION_DOWNGRADE`）。
- **同一次 CI 构建内，所有渠道的 versionCode 必须唯一**，否则多渠道上传会冲突。

#### 6.2 制品类型

| 制品 | 说明 | 用途 |
| --- | --- | --- |
| **AAB（Android App Bundle）** | Play 商店强制要求 | **正式分发**（Play 按设备下发最优 ABI 和语言） |
| **APK（Universal）** | 含所有 ABI | 内部测试、企业分发、第三方商店 |
| **APK（按 ABI 拆分）** | 每个 ABI 一个 | 内测分发（减小体积）、下载性能优化 |
| **mapping.txt** | 混淆映射 | **崩溃还原**（永久保存） |
| **symbols（Native）** | Native 符号表 | Native 崩溃还原（永久保存） |
| **Build Scan** | Gradle 构建性能报告 | 构建优化分析 |

**⚠️ 常见陷阱**：
- **用 APK 上传 Play 是错的**（Play 要求 AAB）。
- **AAB 里没有 mapping.txt**——必须**单独上传**到崩溃平台，否则线上崩溃无法还原。
- **AAB 的 ABI 分发是 Play 做的**，`splits` 配置对 Play 分发无效（只影响直接分发 APK）。

### 7. 质量门禁

**质量门禁（Quality Gate）= 在流水线的关键节点设置"不通过就阻断"的条件。**

| 门禁点 | 检查项 | 阻断策略 |
| --- | --- | --- |
| **PR → Main** | Lint 有 error | **阻断合并** |
| **PR → Main** | 单元测试全绿 | **阻断合并** |
| **PR → Main** | 编译通过 | **阻断合并** |
| **PR → Main** | 依赖漏洞（高危） | 阻断或需审批 |
| **PR → Main** | 新增代码覆盖率 ≥ 阈值 | 阻断或警告 |
| **Main → Release** | 集成测试通过 | 阻断发版 |
| **Release** | APK 体积增长 < 阈值 | 阻断 |
| **Release** | 混淆 + 签名 + mapping 上传成功 | 阻断 |

**门禁设计的两个原则**：
1. **门禁要少而准**。门禁太多 → 开发者习惯性"绕过"（加 `--continue`、加 `//noinspection`）→ 门禁失效。**一个从不误报的门禁才有价值。**
2. **区分"阻断"和"警告"**。新增覆盖率下降 0.5% 可以是警告；**新增代码零覆盖且是核心模块**才应该阻断。

**分支保护（Branch Protection）** 是门禁的落地方式：

```yaml
# .github/branch-protection.json（用 gh api 或 Probot 同步到 GitHub）
{
  "required_status_checks": {
    "strict": true,
    "contexts": [
      "lint",
      "unit-test",
      "assemble-debug",
      "detekt"
    ]
  },
  "enforce_admins": true,
  "required_pull_request_reviews": {
    "required_approving_review_count": 2,
    "dismiss_stale_reviews": true
  },
  "required_linear_history": true,
  "restrictions": {
    "users": [],
    "teams": ["mobile-core"]
  }
}
```

### 8. 自动化测试在流水线中的位置

```text
┌───────────────────────────────────────────────────────────────────────┐
│  测试金字塔                                                            │
│                                                                       │
│                        ╱╲          端到端 / UI 测试                    │
│                       ╱  ╲         （慢、贵、覆盖少）                   │
│                      ╱    ╲        放在 Nightly / Release             │
│                     ╱──────╲                                          │
│                    ╱        ╲     集成测试（Robolectric / 真机）       │
│                   ╱          ╲    放在 Main 合并后                      │
│                  ╱────────────╲                                       │
│                 ╱              ╲  单元测试（纯 JVM）                     │
│                ╱                ╲ 放在每个 PR ★                          │
│               ╱__________________╲                                     │
└───────────────────────────────────────────────────────────────────────┘
```

| 测试类型 | 工具 | 运行时长 | 放在哪 |
| --- | --- | --- | --- |
| **单元测试** | JUnit5 + MockK + Turbine | 秒~分钟 | **每个 PR** |
| **Robolectric 测试** | Robolectric | 分钟 | 每个 PR（可选） |
| **Compose UI 测试** | ComposeTestRule | 分钟 | Main 合并后 |
| **Espresso / 真机 UI 测试** | Espresso / UIAutomator | 10~30min | **Nightly** |
| **截图回归测试** | Paparazzi / Roborazzi | 分钟 | Main 合并后 |
| **Monkey / 稳定性测试** | 随机操作 | 小时 | **Nightly** |
| **性能基准测试** | Macrobenchmark | 10~30min | Nightly |
| **线上监控** | APM / 崩溃平台 | 持续 | **线上（灰度期）** |

**真机农场（Device Farm）**：
- 常见方案：**Firebase Test Lab**（Google 出品，按分钟计费）、**AWS Device Farm**、**自建（STF/OpenSTF）**。
- **Android 模拟器 vs 真机**：模拟器便宜并行，但**性能数据不可信**、相机/传感器/推送行为不同。真机农场用于最终验证。

**关键原则**：**单元测试在 PR 阶段，UI 测试在主干，线上监控兜底**。三层形成一个"金字塔"，任何一层漏了都会在更贵的地方暴露。

### 9. 签名与上传到 Play Console

#### 9.1 Play Console API 上传流程

```text
① 构建 AAB
   ↓
② 用 Service Account JSON + JWT（OAuth2）换取 access token
   POST https://oauth2.googleapis.com/token
     grant_type=urn:ietf:params:oauth:grant-type:jwt-bearer
     assertion=<Service Account 签名的 JWT>
   ↓
③ 创建 Release（指定 track：internal / alpha / beta / production）
   POST https://androidpublisher.googleapis.com/androidpublisher/v3/applications/{pkg}/edits
   ↓
④ 上传 AAB
   POST .../edits/{editId}/bundles
   ↓
⑤ 提交 edit（生效）
   POST .../edits/{editId}:commit
```

**Track（发布轨道）的含义**：

| Track | 用户范围 | 用途 |
| --- | --- | --- |
| **internal** | 最多 100 名测试者 | 内部测试、日常验证 |
| **alpha（closed testing）** | 封闭测试，可指定名单 | **灰度发布**、A/B 测试 |
| **beta（open testing）** | 公开测试 | 公测、收集反馈 |
| **production** | 全量 | 正式发布 |

> **重要**：Google Play 现在要求**新 App 必须先通过封闭测试（closed testing）满 12 天、20 名测试者**，才能申请 production。这是 Play 的政策变化，也是面试可以聊的一点。

#### 9.2 Play App Signing（应用签名密钥 vs 上传密钥）

```text
【传统模式】
  上传密钥（upload key）──签名──→ APK/AAB ──上传──→ Play
                                                      ↓
                                          Play 用【应用签名密钥】重新签名 ──→ 用户下载

【Play App Signing（推荐）】
  上传密钥 ──签名──→ AAB ──上传──→ Play
                              ↓
                     Play 用【应用签名密钥】重新签名 → 分发给用户

  ★ 好处：上传密钥泄露可以【直接重置】而不影响已上架应用的【应用签名密钥】
          → 用户不需要卸载重装 App（更新时签名不一致会被拒绝）
```

**三个密钥的区别（高频考点）**：

| 密钥 | 用途 | 能否重置 | 重置影响 |
| --- | --- | --- | --- |
| **Upload Key（上传密钥）** | 签名后上传到 Play | ✅ **可在 Play Console 重置** | 无影响（Play 会重签） |
| **App Signing Key（应用签名密钥）** | Play 分发给用户时签名 | ❌ **不可重置** | 需联系 Google 支持 |
| **Keystore（本地仓库）** | 存放上述密钥的容器 | 需自己备份 | 丢失 = 上传密钥丢失（但可重置） |

      - name: Setup JDK 17

        with:

          name: test-reports

            app/build/reports/tests/
            app/build/reports/lint-results-debug.html
          retention-days: 7

  # Job 2：构建（需要 quality 通过）
  # ══════════════════════════════════════════════════════════════

    name: Build AAB
    needs: quality
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0         # ★ 完整历史，用于计算版本号和 changelog

        with:
          distribution: temurin

          echo "$KEYSTORE_B64" | base64 -d > /tmp/release.keystore
          ./gradlew :app:bundleRelease \
            -Pandroid.injected.signing.store.file=/tmp/release.keystore \
            -Pandroid.injected.signing.store.password="${{ secrets.ANDROID_KEYSTORE_PASSWORD }}" \
            -Pandroid.injected.signing.key.alias="${{ secrets.ANDROID_KEY_ALIAS }}" \
            -Pandroid.injected.signing.key.password="${{ secrets.ANDROID_KEY_PASSWORD }}" \
            -PversionCode=${{ steps.version.outputs.version_code }} \
            -PversionName=${{ steps.version.outputs.version_name }}

      - name: Upload AAB + mapping
        uses: actions/upload-artifact@v4
        with:
          name: app-bundle-${{ steps.version.outputs.version_code }}
          path: |
            app/build/outputs/bundle/release/app-release.aab
            app/build/outputs/mapping/release/mapping.txt   # ★ 必须一起归档
          retention-days: 90

  # ══════════════════════════════════════════════════════════════
  release:
    name: Publish to Play
    needs: build
    if: startsWith(github.ref, 'refs/tags/')
    runs-on: ubuntu-latest
    permissions:
      contents: read
      id-token: write          # ★ OIDC
    environment:
      name: production
      url: https://play.google.com/console
    steps:
      - uses: actions/checkout@v4

      - name: Auth to GCP (OIDC → 临时凭据)
        uses: google-github-actions/auth@v2
        with:
          workload_identity_provider: ${{ secrets.GCP_WIF_PROVIDER }}
          service_account: ${{ secrets.GCP_SERVICE_ACCOUNT }}

      - name: Download artifacts
        uses: actions/download-artifact@v4
        with:
          name: app-bundle-${{ steps.version.outputs.version_code }}
          path: dist

      - name: Upload to Play (internal track)
        env:
          SERVICE_ACCOUNT_JSON: ${{ secrets.PLAY_SERVICE_ACCOUNT }}
        run: |
          ./gradlew publishReleaseBundle -Ptrack=internal

      - name: Notify Slack
        if: always()
        uses: slackapi/slack-github-action@v1
        with:
          payload: |
            {
              "text": "🚀 发布完成：${{ github.ref_name }} → Play internal track"

### 1. 版本号自动化（Gradle）

```kotlin
// build.gradle.kts（根目录或 app 模块）
import java.text.SimpleDateFormat
import java.util.Properties

/**
 * 版本号自动化。
 *
 * 设计要点：
 * 1. versionCode 必须【严格单调递增】且大于商店已发布版本
 * 2. CI 构建用【CI 提供】的值；本地构建用【git 描述】兜底
 * 3. 同一 versionCode 下的多渠道构建，追加渠道偏移量保证唯一
 */

val gitCommitCount: Int = runCatching {
    // git rev-list --count HEAD：提交总数，单调递增
    providers.exec {
        commandLine("git", "rev-list", "--count", "HEAD")
    }.standardOutput.asText.get().trim().toInt()
}.getOrDefault(0)

val gitDescribe: String = runCatching {
    providers.exec {
        commandLine("git", "describe", "--tags", "--abbrev=0")
    }.standardOutput.asText.get().trim()
}.getOrDefault("v0.0.0")

val versionNameBase = gitDescribe.removePrefix("v")   // 如 "3.8.2"
val versionCodeBase = versionNameBase.split(".").let { parts ->
    val major = parts.getOrNull(0)?.toIntOrNull() ?: 0
    val minor = parts.getOrNull(1)?.toIntOrNull() ?: 0
    val patch = parts.getOrNull(2)?.toIntOrNull() ?: 0
    major * 10000 + minor * 100 + patch
}

// CI 注入优先（CI 上更可靠，不依赖 git 仓库状态）
val ciVersionCode = providers.gradleProperty("versionCode").orNull?.toIntOrNull()
val ciVersionName = providers.gradleProperty("versionName").orNull

// 渠道偏移：同一 versionCode 下不同渠道用不同 offset，保证唯一
val channelOffset = when {
    (project.findProperty("channel") as String?) == "google" -> 0
    else -> 1
}

android {
    defaultConfig {
        applicationId = "com.example.app"

        // ★ versionCode：CI 值 > git 计算值 > 兜底
        versionCode = ciVersionCode ?: (versionCodeBase + channelOffset + gitCommitCount % 100)
        versionName = ciVersionName ?: "$versionNameBase.${gitCommitCount % 100}"

        testInstrumentationRunner = "androidx.test.runner.AndroidJUnitRunner"
    }

    buildTypes {
        debug {
            applicationIdSuffix = ".debug"
            versionNameSuffix = "-debug"
            isMinifyEnabled = false
        }
        release {
            isMinifyEnabled = true
            isShrinkResources = true
            proguardFiles(
                getDefaultProguardFile("proguard-android-optimize.txt"),
                "proguard-rules.pro"
            )
            // ★ 签名配置从 gradle 属性读，密钥内容绝不进仓库
            signingConfig = signingConfigs.getByName("release")
        }
    }

    flavorDimensions += "channel"
    productFlavors {
        create("google") {
            dimension = "channel"
            buildConfigField("String", "CHANNEL", "\"google\"")
        }
        create("huawei") {
            dimension = "channel"
            buildConfigField("String", "CHANNEL", "\"huawei\"")
        }
    }
}

// 把计算出的版本号写进 BuildConfig，方便运行时上报
buildTypes.configureEach {
    buildConfigField("String", "VERSION_NAME", "\"${project.versionName}\"")
}
```

### 4. Play Console 上传脚本

```bash
#!/usr/bin/env bash
# scripts/upload_to_play.sh
# 用法：./scripts/upload_to_play.sh app/build/outputs/bundle/release/app-release.aab internal

set -euo pipefail

AAB_PATH="${1:?用法: $0 <aab路径> <track>}"
TRACK="${2:-internal}"
SERVICE_ACCOUNT_JSON="${PLAY_SERVICE_ACCOUNT_JSON:?必须提供 Play Service Account JSON}"

# ① 生成 access token（用 Service Account 的 JWT 换 OAuth2 token）
ACCESS_TOKEN=$(echo "$SERVICE_ACCOUNT_JSON" | \
  python3 -c "
import sys, json, time, urllib.request, urllib.parse, base64, hashlib, subprocess

sa = json.load(sys.stdin)
now = int(time.time())

# 构造 JWT header
header = base64.urlsafe_b64encode(
    json.dumps({'alg':'RS256','typ':'JWT'}).encode()).rstrip(b'=')
# 构造 JWT claims：scope 决定能操作哪些 Play API
claims = base64.urlsafe_b64encode(json.dumps({
    'iss': sa['client_email'],
    'scope': 'https://www.googleapis.com/auth/androidpublisher',
    'aud': 'https://oauth2.googleapis.com/token',
    'exp': now + 3600,
    'iat': now
}).encode()).rstrip(b'=')

# 用 service account 的私钥签名
signing_input = header + b'.' + claims
with open('/tmp/sa_key.pem','w') as f:
    f.write(sa['private_key'])
sig = subprocess.run(
    ['openssl','dgst','-sha256','-sign','/tmp/sa_key.pem'],
    input=signing_input, capture_output=True).stdout
signature = base64.urlsafe_b64encode(sig).rstrip(b'=')

assertion = (header + b'.' + claims + b'.' + signature).decode()

data = urllib.parse.urlencode({
    'grant_type': 'urn:ietf:params:oauth:grant-type:jwt-bearer',
    'assertion': assertion
}).encode()

req = urllib.request.Request('https://oauth2.googleapis.com/token', data=data)
resp = json.load(urllib.request.urlopen(req))
print(resp['access_token'])
")

PACKAGE="com.example.app"
BASE_URL="https://androidpublisher.googleapis.com/androidpublisher/v3/applications/${PACKAGE}"

echo "▶ 创建 edit"
EDIT=$(curl -s -X POST "$BASE_URL/edits" \
  -H "Authorization: Bearer $ACCESS_TOKEN" \
  -H "Content-Type: application/json" | python3 -c "import sys,json;print(json.load(sys.stdin)['id'])")

echo "▶ 上传 AAB 到 track=$TRACK"
curl -s -X POST "$BASE_URL/edits/$EDIT/bundles?track=$TRACK" \
  -H "Authorization: Bearer $ACCESS_TOKEN" \
  -H "Content-Type: application/octet-stream" \
  --data-binary @"$AAB_PATH"

echo "▶ 提交 edit"
curl -s -X POST "$BASE_URL/edits/$EDIT:commit" \
  -H "Authorization: Bearer $ACCESS_TOKEN" \
  -H "Content-Type: application/json"

rm -f /tmp/sa_key.pem    # ★ 清理临时私钥
echo "✓ 上传完成：track=$TRACK"
```

#!/usr/bin/env bash
# scripts/archive_artifacts.sh —— 发版后的归档脚本
# 目的：mapping/symbols 必须与 APK 永久对应保存

set -euo pipefail

versionName=$VERSION_NAME
buildId=$BUILD_ID
gitCommit=$(git rev-parse HEAD)
gitBranch=$(git rev-parse --abbrev-ref HEAD)
buildTime=$(date -Iseconds)
aabSha256=$(sha256sum app/build/outputs/bundle/release/app-release.aab | cut -d' ' -f1)
EOF

echo "✓ 已归档到 $ARTIFACT_DIR"

## 常见问题 / 面试要点

**读者问：CI 流水线怎么设计？Android 项目应该有哪些阶段？**

**AI答：**

1. **设计的第一原则：分层设防 + 快速反馈**。便宜的检查放前面，昂贵的放后面。
2. **推荐的三段式结构**：

   | 段 | 阶段 | 时长 | 目标 |
   | --- | --- | --- | --- |
   | **PR 段** | Lint → 单元测试 → 编译检查 | 30s~3min | **最快反馈**，拦住 80% 的错误 |
   | **主干段** | 集成测试 → UI 测试 → 截图回归 → 覆盖率 → SCA → APK 构建 | 10~20min | 深度验证 |
   | **Release 段** | AAB 构建 → 签名 → mapping 上传 → Play 上传 | 5~10min | 可交付制品 |
3. **Android 特有的三个关键点**：
   - **PR 用 Debug 变体，Release 用 Release 变体**。Release 有混淆、签名、资源压缩，耗时和内存占用高得多，不能混用。
   - **AAB 和 APK 是不同的产物**：Play 只收 AAB；AAB 里**没有 mapping.txt**，必须**单独上传**到崩溃平台。
   - **mapping/symbols 必须与版本永久绑定**（用 Build ID 而非 versionCode，因为 versionCode 可能复用）。
4. **门禁的设计原则**：
   - **门禁要少而准**。门禁多了会被开发者习惯性绕过（加 `//noinspection`、用 `--continue`），一旦形成习惯门禁就形同虚设。
   - **区分阻断与警告**：Lint error 阻断；覆盖率下降 1% 警告。
5. **面试话术**："我的流水线分三段：**PR 段跑 Lint + 单测 + 编译，目标是 3 分钟内给反馈**；主干段跑 UI 测试 + 截图回归 + 依赖扫描；Release 段出 AAB 并上传 Play。Android 特有的坑我会重点提两点：**一是 mapping.txt 不在 AAB 里，必须单独上传到崩溃平台，而且要用 Build ID 关联而不是 versionCode**；**二是门禁要少而准**，一个总被绕过的门禁比没有门禁更糟。"

**读者问：CI 怎么加速？Android 构建慢有哪些优化手段？**

**AI答：**

1. **先测量再优化**：`./gradlew build --profile` 生成报告，看配置阶段 vs 执行阶段的占比，以及任务级耗时排行。
2. **按收益排序的优化清单**：

   | 手段 | 收益 | 说明 |
   | --- | --- | --- |
   | **依赖缓存** | **★★★★★** | CI 首选。`setup-gradle` action 开箱即用，首省 3~5 分钟 |
   | **配置缓存** | ★★★★★ | `org.gradle.configuration-cache=true`，配置阶段可从 60s 降到 5s |
   | **Gradle 构建缓存** | ★★★★ | `org.gradle.caching=true`，任务输入没变直接复用输出 |
   | **并行 + 隔离** | ★★★ | `org.gradle.parallel=true` + `org.gradle.workers.max`；Kotlin 编译可 `in-process` 省一次 JVM 启动 |
   | **减少模块数** | ★★★ | 模块越多配置阶段越慢；适度合并低耦合模块 |
   | **减少动态版本** | ★★★ | `implementation "com.x:lib:1.+"` 会**每次都查网络**导致缓存失效，必须用固定版本 |
   | **只构建需要的模块** | ★★★ | PR 阶段用 `assembleDebug` 而不是 `build`（后者含 lint + 所有变体 + 测试） |
   | **降低 ABI 数量** | ★★ | 本地只编一个 ABI（`-PabiFilters=arm64-v8a`），Release 才出全量 |
   | **CI Runner 规格** | ★★ | 用 4~8 核 + 16GB 内存的机器；内存不足会导致 Kotlin 编译 OOM 重试 |

3. **Android 特有的三个坑**：
   - **动态版本号**（`1.+`、`latest.release`）会让 Gradle **每次都去网络检查**，依赖缓存永远失效，必须用固定版本 + `resolutionStrategy` 锁定。
   - **Kotlin 增量编译失效**：常见原因是**在 build script 里做不稳定的配置**（如用 `System.currentTimeMillis()`、读未声明输入的外部文件）。Gradle 会给出 "Incremental compilation failed" 的警告。
   - **Configuration Cache 与不兼容写法**：某些插件（如老的 `android.enableR8.fullMode=false`、动态 `taskProvider`）不兼容，会导致缓存每次失效。
4. **CI 上的额外技巧**：
   - **`concurrency` 取消旧运行**：同一分支的新提交到达时取消旧的，省算力也避免旧产物被发布。
   - **缓存只读/只写分离**：PR 只读缓存（防止 fork 的不可信构建污染共享缓存），主干独占写。
   - **缓存 key 必须包含依赖版本**：否则"依赖升级了但用了旧缓存"，产出**用旧依赖的新包**——这是会引发线上事故的严重 bug。
5. **面试话术**："我会**先测量**再优化——`--profile` 看配置阶段和执行阶段的占比。Android 项目里收益最大的三件事是**依赖缓存、配置缓存、Gradle 构建缓存**，CI 上 `setup-gradle` action 基本一步到位。然后是三个容易踩的坑：**动态版本号会让依赖缓存永远失效**、**Kotlin 增量编译会因为 build script 里不稳定配置而失效**、**缓存 key 没包含依赖版本会导致用旧依赖产出新包，这是会出线上事故的**。还有一点 CI 特有的：**PR 的构建产物不可信，PR 流水线应该只读缓存，主干才写缓存**。"

**读者问：密钥怎么管理？为什么推荐 OIDC？**

**AI答：**

1. **三个层次的方案**：
   - **静态 Secrets**：CI 平台存密钥，注入为环境变量。简单，但**长期有效、泄露难察觉**。
   - **OIDC 联邦身份**：CI 用**短期 JWT** 向云厂商换取**临时凭据**（通常 15 分钟过期）。
   - **Vault / KMS**：动态取密钥，可轮换、精细权限、完整审计。
2. **OIDC 的工作原理**（必须能讲清楚，这是加分点）：
   ```
   ① GitHub Actions 生成 OIDC JWT，payload 含【仓库、分支、workflow、actor】
      ★ 由 GitHub 签发，云厂商可验证签名
   ② CI 用 JWT 调云厂商 STS（AssumeRoleWithWebIdentity）
   ③ 云厂商验证：JWT 签名有效 + trust policy 允许【该仓库的 main 分支】换凭据
   ④ 返回临时凭据（15 分钟过期）
   ```
4. **OIDC 的四大优势**：
   - **仓库里没有密钥**——能拉到代码的人拿不到云权限。
   - **凭据自动过期**——泄露窗口从"永久"缩到"15 分钟"。
   - **完整审计**——云厂商侧有"谁在何时用什么身份换了凭据"的日志。
   - **权限精确到分支**——PR 分支的 workflow **根本换不到**生产凭据（trust policy 里只允许 `refs/heads/main`）。
5. **密钥管理的红线**：
   - keystore / 密码 / 服务端密钥**绝不进 Git**；`local.properties` 必须 `.gitignore`。
   - **日志脱敏**：`echo "::add-mask::$SECRET"`；注意 `set -x` 和 `curl -v` 会打印。
   - **临时文件用完即删**：CI 里 `if: always() run: rm -f keystore`。
   - **第三方 Action 要审计**：`uses: someone/action@v1` 会拿到你的 Secrets；用官方 Action 或**固定 commit SHA**（tag 可被重新指向）。
   - **Fork PR 不能触发带密钥的 job**：GitHub 默认不给 fork 的 secrets，但要在 workflow 里显式约束。
6. **keystore 本身的轮换**：**上传密钥可以重置**（Play App Signing 模式下，在 Play Console 重置 upload key 即可），但**已上架应用的应用签名密钥不能重置**。所以**本地 keystore 必须做离线备份**（密码管理器 + 加密的异地备份）。
7. **面试话术**："密钥管理我会**优先用 OIDC**——CI 平台生成一个短期 JWT，云厂商验证签名和 trust policy 后返回**临时凭据**。好处是**仓库里没有密钥、凭据 15 分钟自动过期、云厂商侧有完整审计、PR 分支根本换不到生产凭据**。如果只能用静态 Secrets，我会遵守几个红线：**keystore 和密码绝不入库**、`local.properties` 加 gitignore、**临时文件用完即删**、**第三方 Action 固定 commit SHA**。另外 Play App Signing 下要记住：**上传密钥可以重置，应用签名密钥不能**，所以本地 keystore 必须离线备份。"

**读者问：版本号和制品管理怎么做？多渠道多 ABI 怎么组织？**

**AI答：**

1. **版本号三段式**：
   - `versionName = "3.8.2"`（用户可见）。
   - `versionCode = 30802`（整数，**必须严格单调递增**，且大于商店已发布版本，否则 Play 拒绝上传）。
   - `buildNumber`：CI 每次构建自增，用于区分同版本的不同构建。
2. **versionCode 计算公式**：`major × 10000 + minor × 100 + patch`，再叠加渠道偏移量（保证同 versionCode 下多渠道唯一）。
3. **CI 上 versionCode 的三种生成方式**：
   | 方式 | 公式 | 优缺点 |
   | --- | --- | --- |
   | **Git 提交数** | `git rev-list --count HEAD` | 单调递增、简单；但 **shallow clone（`fetch-depth: 1`）拿不到准确计数**，需要 `fetch-depth: 0` |
   | **时间戳** | `yyMMddHHmm` → `yymmddhhmmss` 转 int | 天然唯一、可排序；但会**导致每次构建版本号都变**，不利于测试固定版本 |
   | **CI 运行号** | `${{ github.run_number }}` | 平台保证单调递增；**但换平台（Jenkins/GitLab）要改** |
4. **多渠道多 ABI 的组织**：
   ```kotlin
   flavorDimensions += "channel"
   productFlavors {
       create("google") { dimension = "channel" }   // 依赖 google-services
       create("huawei") { dimension = "channel" }   // 依赖华为 HMS
   }
   ```
   - **渠道用 `productFlavor`**（编译期决定依赖不同 SDK），**不要用 `buildConfigField` 硬切**。
   - **ABI 用 `splits` 或 `ndk.abiFilters`**：
     ```kotlin
     splits {
         abi {
             isEnable = true
             reset()
             include("armeabi-v7a", "arm64-v8a", "x86_64")
             isUniversalApk = true     // ★ 保留一个通用包，兜底
         }
     }
     ```
   - **⚠️ 注意**：Play 分发 AAB 时，**Play 自己按设备下发最优 ABI**，`splits` 只对直接分发的 APK 生效。
5. **必须一起归档的制品**：

   | 制品 | 保存多久 | 为什么 |
   | --- | --- | --- |
   | **mapping.txt** | **永久**（≥崩溃保留期） | Java 崩溃还原；半年后老用户上报的崩溃也要能还原 |
   | **resources.txt** | 永久 | 资源问题排查 |
   | **Native symbols** | 永久 | Native 崩溃还原 |
   | **AAB** | 永久 | 复现问题、重分发 |
   | **BUILD_INFO** | 永久 | 记录 gitCommit / buildId / sha256，便于确认"这个包对应哪份 mapping" |
6. **关联必须用 Build ID 而不是 versionCode**：versionCode 可能被复用（回滚）、被覆盖（热修复），只有 Build ID 唯一。
7. **面试话术**："版本号我会用 `versionCode = major×10000 + minor×100 + patch`，**必须严格单调递增**且大于商店已发布版本，否则 Play 直接拒收。CI 上我用 `git rev-list --count HEAD` 生成，但要记得 **`fetch-depth: 0`**，否则 shallow clone 拿不到准确计数。多渠道用 `productFlavor`，ABI 用 `splits`——但要注意 **Play 发 AAB 时 ABI 分发是 Play 做的，`splits` 只对直接分发的 APK 生效**。制品方面最重要的红线是：**mapping.txt 必须和版本永久对应保存，用 Build ID 关联而不是 versionCode**，因为 versionCode 可能被复用。"

**读者问：Google Play 上传要注意什么？Play App Signing 是什么？**

**AI答：**

1. **Play App Signing（应用签名）的三段式**：
   ```
   上传密钥（upload key）──签名──→ AAB ──上传──→ Play Console
                                                      ↓
                                        Play 用【应用签名密钥】重新签名
                                                      ↓
                                                        分发给用户
   ```
   - 用户下载到的是**应用签名密钥**签名的包。
   - **上传密钥泄露可以直接在 Play Console 重置**，用户无需卸载重装（因为应用签名密钥没变）。
   - **应用签名密钥不能重置**（要联系 Google 支持）。这是整个体系中最重要的不可逆点。
2. **API 上传的四步**：
   ```
   ① Service Account JSON 签 JWT → 换 access_token
   ② POST /edits                          创建 edit
   ③ POST /edits/{id}/bundles?track=xxx   上传 bundle
   ④ POST /edits/{id}:commit              提交生效
   ```
3. **Track（发布轨道）**：
   | Track | 范围 | 用途 |
   | --- | --- | --- |
   | internal | ≤100 名测试者 | 内部测试 |
   | alpha（closed） | 封闭测试，可指定名单 | **灰度发布** |
   | beta（open） | 公开测试 | 公测 |
   | production | 全量 | 正式发布 |
4. **两个政策变化（加分点）**：
   - **新 App 必须先通过封闭测试**：20 名测试者、连续 14 天，才能申请 production 审核。首次上架要预留这个周期。
   - **Play 要求 AAB**：上传 APK 会被拒绝（仅内部测试轨道例外）。
5. **A/B 测试在 Play 上的实现**：在 Play Console 里配置 **App Bundle Explorer / 分阶段发布（staged rollout）**；真正的"实验平台"用 Firebase Remote Config + Analytics 做。
6. **发布后必须做的事**（这一步经常被忘）：
   - **上传 mapping.txt 和 Native symbols 到崩溃平台**（否则线上崩溃全是 `a.b.c`）。
   - **归档制品**到制品库。
   - **在灰度期监控指标**（见 [[../灰度发布与监控]]）。
   - **准备回滚预案**：Play 的"分阶段发布"可以**暂停推广**（不等于回滚，已安装用户仍是新版本），真正的回滚要靠**远端配置关闭功能 + 热修复**。
7. **面试话术**："Play 上传我会说三件事：**第一，Play App Signing 下有三种密钥——上传密钥、应用签名密钥、keystore，只有上传密钥能重置，应用签名密钥不能，这是不可逆的，所以本地 keystore 必须离线备份**。**第二，Play 只收 AAB，而且 AAB 里没有 mapping.txt，必须单独上传到崩溃平台**，否则线上崩溃无法还原。**第三，Play 的'回滚'其实不是真回滚**——暂停推广只能阻止新用户升级，已升级的用户还在坏版本上，所以真正的止损必须靠**远端配置关开关 + 热修复**，这也是为什么我会把灰度和热修复能力当成发版体系的一部分。"

**读者问：自动化测试在流水线里应该放在什么位置？真机农场有必要吗？**

**AI答：**

1. **按成本分层，贵的放后面**：

   | 测试类型 | 工具 | 时长 | 位置 |
   | --- | --- | --- | --- |
   | 单元测试 | JUnit5 + MockK + Turbine | 秒~分 | **每个 PR** |
   | Robolectric | Robolectric | 分 | PR 或主干 |
   | Compose UI 测试 | ComposeTestRule | 分 | 主干 |
   | 截图回归 | Paparazzi / Roborazzi | 分 | 主干 |
   | Espresso / 真机 UI | Espresso / UIAutomator | 10~30min | **Nightly** |
   | Monkey 稳定性 | 随机操作 | 小时 | **Nightly** |
   | 性能基准 | Macrobenchmark | 10~30min | Nightly |
   | 线上监控 | APM + 崩溃平台 | 持续 | **灰度期（最重要）** |
2. **为什么单元测试必须在 PR 阶段**：纯 JVM，跑得快、失败信息清晰、**定位成本低**。开发者"提交后 30 秒就知道结果"的体验，和"提交后 30 分钟"的体验，是两种完全不同的反馈文化。
3. **真机农场（Device Farm）的价值与边界**：
   - **能测什么**：真机上的权限弹窗、厂商 ROM 差异、推送、相机、传感器、安装包体（`INSTALL_FAILED_INSUFFICIENT_STORAGE`）、特定 API 级别的行为。
   - **不能测什么**：**性能数据不可信**（网络环境不真实）、用户真实行为、崩溃率（样本量太小）。
   - **方案选择**：**Firebase Test Lab**（Google 出品，按分钟计费，集成方便）/ **AWS Device Farm** / **自建 OpenSTF**（成本低但维护重）。
   - **模拟器 vs 真机**：模拟器便宜、可并行、可快照，**适合 UI 流程回归**；真机用来兜底模拟器的盲区。
4. **Mock 策略**（决定测试金字塔是否稳）：
   - **单元测试不 mock 一切**——过度 mock 会让测试通过但线上崩。原则是 **mock 边界（网络、磁盘、时间），不 mock 逻辑**。
   - 用 **Fake 而不是 Mock** 存数据库/网络（Fake 有真实行为，Mock 只验证交互）。
   - **时间必须可控**：注入 `Clock` 接口，而不是直接 `System.currentTimeMillis()`。
5. **覆盖率要看得聪明**：
   - **总覆盖率数字意义有限**，重要的是**核心模块的覆盖**和**新增代码的覆盖**。
   - CI 门禁应该卡"**新增代码覆盖率**"，而不是总覆盖率——否则老代码会把数字拉低，开发者就放弃维护了。
6. **面试话术**："我会按测试金字塔分层：**单元测试放每个 PR**（秒级反馈，定位清晰），**UI 测试和截图回归放主干**，**Monkey 和性能基准放 Nightly**，**最后是线上监控兜底**。真机农场有价值但边界很清楚——它能测**厂商 ROM 差异、权限弹窗、安装失败**这些模拟器测不了的东西，但**性能数据和崩溃率不能信**，那些必须靠线上 APM。真机方案我会优先用 **Firebase Test Lab**，集成成本最低。另外覆盖率我只卡**新增代码的覆盖率**，不卡总覆盖率——卡总覆盖率会让人放弃维护。"

**读者问：缓存策略具体怎么配？CI 缓存 key 应该包含什么？**

**AI答：**

1. **四层缓存**（前面表格已列）：**依赖缓存 → 构建缓存 → 配置缓存 → Kotlin 增量缓存**。收益从大到小。
2. **缓存 key 必须包含所有影响构建结果的输入**，这是最容易出错的地方：

   ```yaml
   # ❌ 错误：key 没包含依赖版本
   key: gradle-${{ hashFiles('**/*.gradle') }}

   # ✅ 正确：包含构建脚本 + gradle wrapper + 锁定的依赖版本
   key: gradle-${{ runner.os }}-${{ hashFiles('**/*.gradle.kts', '**/gradle-wrapper.properties', 'gradle/libs.versions.toml', 'gradle.properties') }}-${{ hashFiles('**/build.gradle.kts') }}
   ```
   - **漏了依赖版本 → 依赖升级了但缓存命中 → 产出用旧依赖的新包 → 线上事故**。这是 CI 缓存最经典也最致命的坑。
   - **漏了 `gradle.properties`** → JVM 参数变化不生效。
   - **漏了 wrapper 版本** → 换了 Gradle 版本还用旧缓存。
3. **读写分离**（防止不可信构建污染共享缓存）：
   ```yaml
   - uses: gradle/actions/setup-gradle@v4
     with:
       cache-read-only: ${{ github.event_name == 'pull_request' }}
       cache-write-only: ${{ github.event_name != 'pull_request' }}
   ```
   - **PR 流水线（包括来自 fork 的）只读缓存**。
   - **主干和 Release 独占写**。
   - 原因：PR 的构建产物来自不可信代码，写进共享缓存等于让别人投毒。
4. **缓存容量与清理**：
   - GitHub Actions 单缓存上限 **10GB**，超限会保存失败。
   - `gradle-home-cache-cleanup: true` 让 action 自动清理旧缓存。
   - **缓存超过 7 天自动过期**（GitHub 策略），主干的缓存靠每日构建刷新。
5. **Kotlin 增量缓存失效的排查**：
   - 症状：日志出现 `Incremental compilation failed: ...`。
   - 常见原因：**build script 里做了不稳定配置**（读 `System.currentTimeMillis()`、读未声明输入的外部文件、依赖顺序不确定的遍历）。
   - 解法：把这些值通过 `@Input` 显式声明，或移出配置阶段。
6. **面试话术**："缓存我会分四层：**依赖缓存（收益最大）、Gradle 构建缓存、配置缓存、Kotlin 增量缓存**。CI 上 `setup-gradle` action 基本一步到位。**但缓存 key 一定要包含依赖版本**——漏了它就会出现'依赖升级了但缓存命中、产出用旧依赖的新包'，这是能出线上事故的严重 bug。另外一个容易忽略的点是**读写分离**：PR 流水线只读缓存，因为 PR 代码不可信，主干才写。还有 **Kotlin 增量编译失效**要会排查，通常是 build script 里做了不稳定配置。"

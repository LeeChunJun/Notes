# 文档与协作

## 一句话定义

技术文档的价值不是"记录已经发生的事"，而是**让团队的知识从"某个人的脑子里"变成"团队可复用的资产"**。判断文档是否合格只有一条标准：**一个新人拿着它，能不能在不问人的情况下完成一个真实任务**。而协作流程（需求评审 → 方案评审 → 开发 → 发布 → 复盘）是文档生产的**上游**——没有结构化的协作流程，就不会有高质量的文档，因为文档只能记录下"讨论过的东西"，讨论本身才是质量的来源。

面试开场：**"文档的价值不看写得多不多，看有没有人用。我判断一份文档是否合格只有一个标准：**新同学拿着它，能不能不问我就把一个真实需求做完**。写完没人看，多半是因为写的人不明白'文档是给谁看的'——同一份技术方案，写给三个月后的自己，和写给评审的同事，结构应该完全不同。"**

## 核心原理

### 1. 文档分类：按"谁在什么时候读"划分

| 文档类型 | 读者 | 生命周期 | 核心问题 | 存放位置 |
| --- | --- | --- | --- | --- |
| **需求文档（PRD）** | 产品、开发、测试 | 版本级 | **要做什么？为什么？验收标准是什么？** | Wiki / 语雀 / Confluence |
| **技术设计文档** | 开发、Reviewer、未来维护者 | 模块/版本级 | **怎么做？为什么这么选？有什么坑？** | Wiki / PR 描述 / ADR |
| **接口文档** | 前后端、服务调用方 | 持续 | **怎么调用？参数是什么？错误码含义？** | **自动生成**（OpenAPI） |
| **部署文档** | 运维、SRE | 持续 | **怎么发布？怎么回滚？监控看哪里？** | Wiki / Runbook |
| **FAQ** | 用户、客服、一线支持 | 持续 | **常见问题怎么答？** | Wiki / 客服知识库 |
| **ADR（架构决策记录）** | **未来的所有人** | **永久** | **为什么当初这么选？** | **代码仓库内**（版本化） |
| **README** | 所有人 | 持续 | **这个项目是什么？怎么跑起来？** | **代码仓库内** |
| **Onboarding 文档** | 新人 | 持续 | **环境怎么搭？第一个任务是什么？** | Wiki |

**分类的关键洞察**：
- **按"读者"分类比按"内容"分类更有用**。同一件事，写给不同读者的**详略、语气、结构完全不同**：
  - **写给未来的自己**（ADR）：要把**权衡过程和放弃的方案**都写清楚，因为三个月后你会忘记"为什么不用 Room"。
  - **写给评审者**（设计文档）：要突出**关键决策点、风险和未决问题**，让人能聚焦讨论。
  - **写给新人**（Onboarding）：要**可执行**，每一步都能照做。
  - **写给用户**（FAQ）：要**口语化**，给结论和操作步骤，不要讲原理。
- **ADR 和 README 必须放在代码仓库里**（跟代码一起版本化），其他文档放 Wiki。

### 2. README 与架构文档的写法

#### 2.1 README 的黄金结构

```markdown
# 项目名

> 一句话说明这个项目是什么（不要超过 50 字）

[徽章：构建状态 | 版本 | 许可证 | 代码质量]

## 简介          ← 解决什么问题，2~3 段
## 快速开始      ← 5 分钟内能跑起来的最小步骤 ★
## 目录结构      ← 一眼看出模块划分
## 构建与运行    ← 完整命令 + 环境要求
## 配置          ← 环境变量 / local.properties / 密钥说明
## 测试          ← 怎么跑测试
## 贡献指南      ← 分支规范、提交规范、PR 要求
## 许可证
## 联系方式
```

**README 的三个常见错误**：
| 错误 | 为什么坏 | 正确做法 |
| --- | --- | --- |
| **开头讲历史** | 读者不关心你的产品故事，他关心"这怎么用" | 开头一句话说清"这是什么" |
| **快速开始需要问人** | 新人第一道坎就卡住，直接放弃 | 提供**完整可复制**的命令，包含依赖安装 |
| **没有目录结构** | 新人不知道从哪看起 | 加一棵目录树，标注各模块职责 |

#### 2.2 技术设计文档（方案文档）的结构

```markdown
# 【功能名】技术方案

## 背景与问题        ← 为什么现在要做这件事？痛点是什么？数据支撑
## 目标 / 非目标     ← ★ 明确"不做什么"，避免范围蔓延
## 现状分析         ← 当前实现是怎样的？痛点在哪？（附代码/截图）
## 方案设计
  - 总体架构图      ← ★ 一张图讲清整体，评审时先看这张
  - 详细设计        ← 类图 / 时序图 / 数据流
  - 关键决策点      ← ★ 每个决策写成"选项A vs 选项B vs 选C及理由"
## 影响面分析
  - 改动范围        ← 涉及哪些模块 / 多少人协作
  - 性能影响        ← 启动、内存、包体
  - 兼容性          ← 老版本 App 怎么处理？数据迁移？
  - 风险与应对      ← 风险清单 + 兜底方案（灰度/开关/回滚）
## 测试方案         ← 单测 / 集成 / 手工回归点
## 发布计划         ← 灰度策略、开关、监控指标、埋点
## 未决问题         ← ★ 列出还需要拍板的问题，评审时要收敛
## 参考资料
```

**三个最容易被忽略但最值钱的段落**：
1. **目标 / 非目标** —— "非目标"能挡住 80% 的范围蔓延。
2. **关键决策点的选项对比** —— 这是技术评审真正要讨论的内容，也是 ADR 的素材。
3. **未决问题** —— 主动暴露分歧，比假装都想清楚了更专业。

### 3. 接口文档自动化

#### 3.1 为什么必须自动化

手写接口文档的必然结果：**接口改了文档没改**。开发为了赶进度不会去改文档，文档就烂了。**唯一能长期维护的方式是"从代码生成"**。

#### 3.2 OpenAPI 规范与代码生成链路

```text
┌──────────────────────────────────────────────────────────────────────┐
│  服务端（Ktor / Spring / Swagger）                                      │
│     注解或 DSL 描述接口 → 生成 openapi.yaml / openapi.json             │
│                              ↓                                          │
│  CI 中校验：OpenAPI 变更检测（oasdiff / openapi-diff）                   │
│     ├─ 有【破坏性变更】→ 阻断合并 ★                                   │
│     └─ 无破坏性变更 → 允许合并                                           │
│                              ↓                                          │
│  客户端生成：Retrofit / OkHttp / Ktor Client                            │
│     接口定义、数据类、序列化规则全部自动生成                              │
│                              ↓                                          │
│  文档站点：Swagger UI / Redoc / Scalar（从 openapi.json 渲染）           │
└──────────────────────────────────────────────────────────────────────┘
```

**破坏性变更检测的清单**（这些是"绝对不能改"的）：

| 变更类型 | 是否破坏 | 示例 |
| --- | --- | --- |
| 删除接口 | ❌ 破坏 | 删除 `GET /api/v1/users` |
| 删除字段 | ❌ 破坏 | 从响应体移除 `user.nickname` |
| 字段改名 | ❌ 破坏 | `userName` → `username` |
| 字段类型变更 | ❌ 破坏 | `age: int` → `age: string` |
| 新增必填请求字段 | ❌ 破坏 | `POST /users` 新增必填 `phone` |
| 新增可选响应字段 | ✅ 兼容 | 响应新增 `user.avatar` |
| 新增可选请求字段 | ✅ 兼容 | 请求新增可选 `remark` |
| 新增接口 | ✅ 兼容 | — |
| 放宽校验（如 enum 加值） | ⚠️ 半兼容 | 老客户端遇到新值可能反序列化失败 |

> **重要陷阱**：**"服务端新增字段"不等于"客户端能安全处理"**。如果服务端新增了一个 enum 值，老客户端的 Kotlin data class 用 `@SerializedName` 反序列化未知枚举值时**可能崩溃**（取决于 Gson/Raw 策略）。这是"理论兼容、实际破坏"的典型。

#### 3.3 Android 端的接口文档实践

```kotlin
// 用 Retrofit + Kotlin 序列化 + KDoc 生成接口文档
interface UserApi {

    /**
     * 获取用户详情。
     *
     * @param userId 用户 ID
     * @return [UserDetail] 用户信息
     * @throws ApiException 业务异常（code != 0）
     */
    @GET("api/v1/users/{userId}")
    suspend fun getUserDetail(
        @Path("userId") userId: String
    ): ApiResponse<UserDetail>

    /**
     * 更新用户资料。
     *
     * ⚠️ 【兼容性说明】本接口在 v2.3.0 引入可选字段 [UserProfileUpdate.remark]，
     *    服务端可能返回未知的扩展字段，客户端必须容忍。
     */
    @POST("api/v1/users/profile")
    suspend fun updateProfile(
        @Body request: UserProfileUpdate
    ): ApiResponse<Unit>
}

/**
 * 用户详情。
 *
 * ⚠️ 未知字段必须忽略（服务端会灰度新增字段），
 *    所以用 `ignoreUnknownKeys = true` + 所有字段可空。
 */
@Serializable
data class UserDetail(
    val id: String,
    val nickname: String? = null,     // ★ 可空 + 默认值，容忍服务端不返回
    @SerialName("avatar_url")
    val avatarUrl: String? = null,
    val createdAt: Long? = null
)
```

```kotlin
// 客户端 JSON 配置：必须容忍未知字段
object NetworkJson {
    val instance = Json {
        ignoreUnknownKeys = true      // ★ 服务端新增字段时不崩
        explicitNulls = false
        coerceInputValues = true      // null → 默认值
        encodeDefaults = true
    }
}
```

**Android 侧的接口文档工具链**：
| 工具 | 作用 |
| --- | --- |
| **OpenAPI Generator** | 从 `openapi.yaml` 生成 Retrofit 接口 + 数据类 |
| **Swagger UI / Redoc** | 渲染接口文档站点 |
| **oasdiff / openapi-diff** | 检测破坏性变更（CI 门禁） |
| **KDoc / Dokka** | Kotlin 源码 → HTML 文档 |
| **Dokka + Compose 支持** | 生成 Compose 组件的预览文档 |

### 4. 知识库建设

#### 4.1 工具选型

| 工具 | 定位 | 优势 | 劣势 | 适合 |
| --- | --- | --- | --- | --- |
| **语雀（Yuque）** | 文档协作 | 国内访问快、**自带知识库目录树**、编辑体验好 | 私有化需付费 | **国内团队首选** |
| **Confluence** | 企业 Wiki | 与 Jira 集成、企业权限、评论与 @提及 | 学习成本高、价格贵 | **大型企业**（已有 Atlassian 生态） |
| **Notion** | 通用笔记 | 灵活、模板多、易用 | 无结构化目录、弱检索、无版本化 | 团队规模小、临时协作 |
| **GitHub / GitLab Wiki** | 仓库内文档 | **与代码一起版本化**、Review 友好 | 写长文体验差、渲染弱 | **ADR、README、模块文档** |
| **MkDocs / Docusaurus** | 静态站点 | **文档即代码**、可本地预览、可 CI 发布 | 需要写 Markdown、需维护构建 | **技术文档站** |
| **GitBook** | 文档站 | 上手快、托管服务 | 高级功能收费 | 中小团队 |

#### 4.2 知识库的信息架构

```text
知识库/
├── 📁 入门
│   ├── 新人 Onboarding（环境搭建 / 第一个任务 / 常用命令）
│   └── 术语表（Glossary）★ 消除沟通歧义
├── 📁 架构
│   ├── 系统架构图
│   ├── 模块地图（哪个模块归谁负责）
│   └── 技术栈说明
├── 📁 开发指南
│   ├── 编码规范
│   ├── Git 工作流
│   ├── 提交信息规范
│   └── 常见坑（踩坑记录）★
├── 📁 运行与运维
│   ├── 部署手册
│   ├── 监控看板与告警说明
│   ├── 应急预案（Runbook）★
│   └── 灰度与回滚流程
├── 📁 决策记录（ADR）
├── 📁 常见问题（FAQ）
└── 📁 会议纪要与复盘
```

**三个最有价值但最常被忽略的目录**：
1. **术语表（Glossary）**：一个项目里 "订单" 可能指订单实体、订单快照、订单号。**术语不统一是协作中最大的隐性成本**。
2. **踩坑记录**：把"某个方案在某个场景下会炸"写下来，避免同一个人踩两次。这是**投入产出比最高**的文档类型。
3. **Runbook（应急预案）**：出故障时，值班的人照着做就能止损。没有 Runbook 的事故响应靠"微信群里问资深同学"——人一走知识就断了。

#### 4.3 知识沉淀的机制（不只是"写文档"）

```text
┌──────────────────────────────────────────────────────────────────────┐
│  ① 触发式沉淀（事件驱动）                                              │
│     每完成一个【有技术决策】的功能 → 写一份 ADR                         │
│     每发生一次【线上事故】 → 写一份复盘报告                            │
│     ★ 关键：不是"有空写"，而是"这件事发生了就必须写"                    │
├──────────────────────────────────────────────────────────────────────┤
│  ② 评审式沉淀（流程嵌入）                                              │
│     技术方案评审 → 决策点自动提取成 ADR 草稿                           │
│     Code Review → reviewer 发现的"通用问题"沉淀进规范                  │
│     ★ 把沉淀嵌入已有流程，不新增流程（新增流程一定会被绕过）             │
├──────────────────────────────────────────────────────────────────────┤
│  ③ 定期式沉淀（时间驱动）                                              │
│     每月 / 每季度 → 清理过期文档、检查链接有效性                         │
│     每季度 → 架构文档同步（代码变了架构图也要变）                        │
│     ★ 这是"文档过期"的唯一解药——靠人自觉是不可能的                      │
└──────────────────────────────────────────────────────────────────────┘
```

### 5. 文档与代码同源

#### 5.1 三种"同源"手段

| 手段 | 原理 | 自动化程度 | 适用 |
| --- | --- | --- | --- |
| **doctoc** | 扫描 Markdown 标题，生成/更新目录 | **完全自动** | 长文档 |
| **注释生成文档** | 从 KDoc / Dokka 注释生成 API 文档 | **完全自动** | 代码 API |
| **README 生成** | 从模板 + 配置生成 README | **完全自动** | 模板化项目 |
| **代码生成接口文档** | 从 OpenAPI 生成客户端 + 文档站点 | **完全自动** | 接口契约 |
| **CI 校验一致性** | 对比代码与文档，不一致就阻断 | **半自动** | 关键文档 |

#### 5.2 doctoc 的使用

```bash
# 安装
npm install -g doctoc

# 在 Markdown 文件头部生成目录（幂等，重复执行不会产生 diff）
doctoc README.md --title "目录" --maxlevel 3

# CI 中校验：文档目录是否与实际标题一致（不一致则说明文档改了但没更新目录）
doctoc README.md --notitle > /tmp/toc.txt
git diff --exit-code README.md || {
    echo "❌ README 目录已过期，请运行 doctoc README.md 后提交"
    exit 1
}
```

#### 5.3 架构图与代码同源（进阶）

**思路**：让架构文档里的模块列表**从 Gradle 模块自动生成**，模块改名后文档自动更新。

```bash
#!/usr/bin/env bash
# scripts/generate_module_map.sh —— 自动生成模块地图，输出到架构文档
# 目的：架构文档与实际模块保持同源，避免"文档里的模块已经不存在了"

DOC="docs/architecture.md"
{
    echo "## 模块地图"
    echo ""
    echo "<!-- AUTO-GENERATED: modules. 请勿手动编辑，改为修改 scripts/generate_module_map.sh -->"
    echo ""
    echo "| 模块 | 路径 | 职责 | 负责人 |"
    echo "| --- | --- | --- | --- |"
} > /tmp/module_map.md

# 遍历所有子项目模块
find . -name "build.gradle.kts" -not -path "*/build/*" -not -path "*/.git/*" | sort | while read -r gradle_file; do
    module_path=$(dirname "$gradle_file")
    module_name=$(basename "$module_path")

    # 从 gradle 文件中提取 description（约定：每个模块写一行注释描述职责）
    description=$(grep -oP 'description\s*=\s*"\K[^"]+' "$gradle_file" 2>/dev/null || echo "-")

    # 从 CODEOWNERS 提取负责人
    owner=$(grep -E "^/${module_path}/" CODEOWNERS 2>/dev/null | awk '{print $2}' | head -1 || echo "-")

    echo "| \`$module_name\` | \`$module_path\` | $description | $owner |" >> /tmp/module_map.md
done

# 替换架构文档中的标记块
python3 - "$DOC" "/tmp/module_map.md" <<'PY'
import sys
doc_path, map_path = sys.argv[1], sys.argv[2]
with open(doc_path, encoding='utf-8') as f:
    content = f.read()
with open(map_path, encoding='utf-8') as f:
    generated = f.read()
start = "<!-- AUTO-GENERATED: modules."
if start in content:
    before = content.split(start)[0]
    after_marker = content.split(start, 1)[1].split("-->", 1)
    after = after_marker[1] if len(after_marker) > 1 else ""
    # 找到结束标记
    end = "\n<!-- /AUTO-GENERATED: modules -->"
    if end in after:
        after = after.split(end, 1)[1]
        content = before + start + generated.strip() + "\n<!-- /AUTO-GENERATED: modules -->" + after
        with open(doc_path, 'w', encoding='utf-8') as f:
            f.write(content)
        print(f"✓ 已更新 {doc_path}")
PY
```

### 6. 团队协作流程

```text
┌────────────────────────────────────────────────────────────────────────┐
│  ① 需求评审（产品主导，开发参与）                                        │
│     输入：PRD                                                          │
│     参与：产品 + 客户端 + 服务端 + 测试 + 设计                             │
│     产出：验收标准明确的需求单（含边界情况、异常流）                          │
│     关注：技术可行性评估（客户端能不能做、要多久、有什么坑）                    │
├────────────────────────────────────────────────────────────────────────┤
│  ② 方案评审（开发主导）                                                  │
│     输入：技术设计文档                                                   │
│     参与：客户端 + 服务端 + 测试 + 架构师（有争议时）                        │
│     产出：定稿的方案 + ADR 草稿                                          │
│     关注：★ 决策点的选项对比、影响面、风险与兜底                            │
│     时长：30~60 分钟，提前发文档（★ 会上不读文档）                          │

│     机制：小步提交 + 每日同步（不需要每天开大会）                            │

├────────────────────────────────────────────────────────────────────────┤
```

**协作流程的三个"反模式"**：
| 反模式 | 症状 | 危害 | 正确做法 |
| --- | --- | --- | --- |
| **会上读文档** | 评审会开 90 分钟，前 60 分钟在念文档 | 参会者无法专注讨论 | **文档提前 24 小时发出，会上只讨论决策点和未决问题** |
| **大 PR** | 单个 PR 1500 行 | Reviewer 只能"点个赞"，评审形同虚设 | **< 400 行**；超大改动拆成"重构（不改行为）" + "功能"两个 PR |
| **阻塞憋着不说** | 某人在一个技术问题上卡了 3 天 | 3 天后才发现方向错了 | **卡住超过半天就同步**，哪怕没有答案 |

### 7. 文档维护的挑战

#### 7.1 文档过期的四个原因

```text
┌──────────────────────────────────────────────────────────────────────┐
│  ① "写完就结束" —— 没有维护环节                                          │
│     代码改了，文档没改。半年后文档是"考古材料"。                          │
├──────────────────────────────────────────────────────────────────────┤
│  ② "没人读" —— 写的东西不是读者需要的                                     │
│     写成了"我的设计思路展示"，而不是"你需要的答案"。                       │
│     判据：读者看完能不能立刻行动？                                        │
├──────────────────────────────────────────────────────────────────────┤
│  ③ "重复太多" —— 同一个信息在 5 个地方                                   │
│     → 改了一处，另外四处全错 → 读者不信任文档 → 更没人读                   │
│     ★ 这是"文档不一致"最常见的成因，也是必须做"单一事实源"的原因           │
├──────────────────────────────────────────────────────────────────────┤
│  ④ "没有 owner" —— 没人负责这份文档                                     │
│     → 所有人都以为别人会更新 → 永远没人更新                              │
└──────────────────────────────────────────────────────────────────────┘
```

#### 7.2 应对策略

| 策略 | 具体做法 | 工具支持 |
| --- | --- | --- |
| **单一事实源（SSOT）** | 同一信息只在一处维护，其他地方**链接过去** | Wiki 的内部链接 |
| **代码内嵌文档** | ADR、README、模块文档**跟代码一起版本化** | Git |
| **自动生成** | 目录、API 文档、模块地图由工具生成 | doctoc / OpenAPI / 自研脚本 |
| **CI 校验** | 文档与代码不一致时阻断合并 | 脚本 + CI |
| **文档 owner 制** | 每份文档有明确负责人（CODEOWNERS） | CODEOWNERS 文件 |
| **定期清理** | 每月检查过期标记、失效链接、无 owner 文档 | 脚本 + 看板 |
| **过期标记** | 文档头部标 `最后验证时间`，超期自动提示 | `Last verified: 2026-11-19` |

### 8. 技术写作的技巧

#### 8.1 让文档有人看的六个原则

| 原则 | 说明 | 反例 → 正例 |
| --- | --- | --- |
| **① 开门见山** | 开头就给结论 | ❌"本项目历史悠久…" → ✅"一个用于管理订单的 App" |

| **⑤ 有例有反例** | 说明"应该怎么写"和"常见错误" | 只说规范不说违规样例 |
| **⑥ 注明时效** | 标注最后验证时间 | "（最后更新：2024-03）" |

### 1. ADR 模板

```markdown
# ADR-0028: 订单状态机使用单表 + 状态字段，而非多表继承

- **状态**：已接受（2026-11-19）
- **决策者**：@张三 @李四
- **相关代码**：`core-domain/src/main/kotlin/com/example/order/OrderState.kt`
- **相关设计**：[订单状态机设计](https://wiki.example.com/adr/0028)

## 背景（Context）

订单有 12 种状态流转（待支付 → 已支付 → 已发货 → 已收货 → 已完成，
以及若干逆向/异常状态）。当前实现用 `OrderBase` + 6 个子类表示不同状态，
每个子类覆盖部分方法。

问题：
1. 新增一个状态需要新增一个类 + 修改 4 个已有子类（`when` 分支散落各处）
2. 状态流转规则分散在多个类的 `override` 方法里，无法一眼看全
3. 数据库层需要多表关联查询才能拿到完整订单

## 决策（Decision）

采用 **单表 + `status` 字段 + 显式状态机（State Pattern 的表驱动变体）**：

- 订单数据存一张表 `t_order`，用 `status` 枚举字段区分
- 状态流转规则集中在一个 `OrderStateMachine` 中，以 **转移表** 声明：
  `TRANSITIONS[from][event] = to`
- 各状态的行为（允许的操作）通过 `OrderState` 接口的默认实现 + 枚举覆盖

## 考虑过的替代方案

| 方案 | 优点 | 缺点 | 为什么没选 |
| --- | --- | --- | --- |
| **A. 保持多子类继承** | 面向对象直观 | 新增状态成本高、流转规则分散、查询复杂 | 当前痛点的根源 |
| **B. 状态模式（每状态一个类）** | 行为封装好 | 仍然需要 `when` 分支做分发；类多 | 部分改善，但没解决"流转表"问题 |
| **C. 状态机库（Squirrel / Spring StateMachine）** | 功能完备 | 依赖重、学习成本高、Android 端体积与包大小不划算 | 杀鸡用牛刀 |
| **D. 单表 + 状态字段 + 转移表** | 规则集中、新增状态成本低、查询简单 | 需要手写状态机 | **✅ 选用** |

## 后果（Consequences）

**正面**：
- 新增状态从"改 4 个类"降到"加 1 个枚举值 + 加转移表条目"
- 状态流转规则可单元测试（纯函数）
- 订单查询变成单表查询，QPS 场景下 SQL 减少

**负面 / 需要注意**：
- 状态的行为通过枚举实现，**单文件会变长**（当前 380 行，需要拆分）
- 状态专属的复杂逻辑不适合放在枚举里（应下沉到独立的 handler 类）
- 存量数据需要迁移：多表 → 单表（已写迁移脚本 `V20261119__order_single_table.sql`）

**缓解措施**：
- 状态机拆成 `OrderStateMachine`（规则）+ `OrderStateHandler`（行为）两个文件
- 转移表用单元测试覆盖所有状态×事件的组合

## 复审条件

出现以下情况时重新评估本决策：
- 订单状态数量超过 30 个
- 需要按状态做不同的数据分区策略
- 需要支持"从任意状态跳转"的运营后台功能
```

### 4. 文档链接与过期检查脚本

```python
#!/usr/bin/env python3
"""
scripts/check_links.py —— 检查 Markdown 内部链接的有效性 + 找出过期文档。

用途：
1. CI 中阻断合并（链接失效说明文档已经腐烂）
2. 定期扫描（找出超过 N 天未验证的文档，输出待清理清单）
"""
import argparse
import os
import re
import sys
from datetime import datetime, timedelta
from pathlib import Path

# 匹配 Markdown 链接：[文本](路径) 和 Obsidian 风格的双链（双方括号）
LINK_PATTERN = re.compile(r'\[([^\]]*)\]\(([^)]+)\)')
WIKI_PATTERN = re.compile(r'\[\[([^\]|]+)(?:\|[^\]]+)?\]\]')
STALE_PATTERN = re.compile(r'<!--\s*last-verified:\s*(\d{4}-\d{2}-\d{2})\s*-->', re.IGNORECASE)


def collect_markdown_files(paths):
    for p in paths:
        path = Path(p)
        if path.is_file() and path.suffix == '.md':
            yield path
        elif path.is_dir():
            for md in sorted(path.rglob('*.md')):
                # 排除构建产物和依赖目录
                if not any(part in ('build', 'node_modules', '.git', 'dist')
                           for part in md.parts):
                    yield md


def check_links(files, root):
    """检查相对路径链接指向的文件是否存在。"""
    broken = []
    for md_file in files:
        content = md_file.read_text(encoding='utf-8')
        for match in LINK_PATTERN.finditer(content):
            target = match.group(2).strip()
            # 跳过外部链接、锚点、mailto
            if target.startswith(('http://', 'https://', '#', 'mailto:', 'tel:')):
                continue
            # 去掉锚点部分
            path_part = target.split('#')[0]
            if not path_part:
                continue
            resolved = (md_file.parent / path_part).resolve()
            if not resolved.exists():
                # 也可能是"目录路径"，尝试找 README
                alt = resolved / 'README.md'
                if not alt.exists():
                    line_no = content[:match.start()].count('\n') + 1
                    broken.append((md_file, line_no, target))
    return broken


def find_stale(files, days):
    """找出超过 N 天未验证的文档。"""
    threshold = datetime.now() - timedelta(days=days)
    stale = []
    for md_file in files:
        content = md_file.read_text(encoding='utf-8')
        match = STALE_PATTERN.search(content)
        if match:
            try:
                last = datetime.strptime(match.group(1), '%Y-%m-%d')
                if last < threshold:
                    stale.append((md_file, match.group(1), (datetime.now() - last).days))
            except ValueError:
                pass
        else:
            # 没有标记的也算"未知时效"，单独列出
            stale.append((md_file, None, None))
    return stale


def main():
    parser = argparse.ArgumentParser()
    parser.add_argument('paths', nargs='+', help='要扫描的路径')
    parser.add_argument('--days', type=int, default=180, help='过期天数阈值')
    parser.add_argument('--warn-only', action='store_true', help='只警告不失败')
    args = parser.parse_args()

    files = list(collect_markdown_files(args.paths))
    print(f"▶ 扫描 {len(files)} 个 Markdown 文件")

    # 1. 链接检查
    broken = check_links(files, Path.cwd())
    if broken:
        print(f"\n❌ 发现 {len(broken)} 个失效链接：")
        for md_file, line_no, target in broken:
            print(f"   {md_file}:{line_no} → {target}")
        if not args.warn_only:
            sys.exit(1)
    else:
        print("✓ 所有内部链接有效")

    # 2. 过期检查
    stale = find_stale(files, args.days)
    unknown = [s for s in stale if s[1] is None]
    expired = [s for s in stale if s[1] is not None]

    if expired:
        print(f"\n⚠ {len(expired)} 个文档超过 {args.days} 天未验证：")
        for md_file, last, age in expired:
            print(f"   {md_file}（最后验证 {last}，已 {age} 天）")

    if unknown:
        print(f"\nℹ {len(unknown)} 个文档没有 last-verified 标记")

    if expired and not args.warn_only:
        print("\n文档已过期，请验证内容后更新标记：<!-- last-verified: YYYY-MM-DD -->")
        sys.exit(1)


if __name__ == '__main__':
    main()
```

## 常见问题 / 面试要点

**读者问：技术文档怎么写才有人看？**

**AI答：**

1. **先想清楚"谁在什么时候读"**，再决定写什么。同一个功能，**写给评审者**（突出决策点、风险、未决问题）、**写给三个月后的自己**（突出权衡过程和放弃的方案）、**写给新人**（要可执行、给完整命令）——**三者的结构完全不同**。
2. **六个让文档有人看的原则**：
   | 原则 | 反例 → 正例 |
   | --- | --- |
   | **开门见山** | ❌"本项目历史悠久…" → ✅"一个用于管理订单的 App" |
   | **面向任务** | ❌"系统包含用户模块、订单模块…" → ✅"如何新增一种订单类型" |
   | **可复制粘贴** | ❌"配置好签名密钥后打包" → ✅ 完整 `keytool` 命令 |
   | **层次清晰** | 大段文字 → 分点 + 表格 |
   | **有例有反例** | 只说规范 → 给出违规样例 |
   | **注明时效** | "（最后更新：2024-03）" → `<!-- last-verified: 2026-11-19 -->` |
3. **最值钱的三个段落**（技术方案文档）：
   - **目标 / 非目标** —— "非目标"能挡住 80% 的范围蔓延。
   - **关键决策点的选项对比** —— 这才是评审要讨论的内容，也是 ADR 的素材。
   - **未决问题** —— 主动暴露分歧比假装都想清楚了更专业。
4. **常见错误**：
   - **会上读文档**（评审会 60 分钟在念 PPT）→ 文档提前 24 小时发，会上只讨论决策点。
   - **大 PR**（1500 行）→ reviewer 只能点个赞，评审形同虚设。**控制在 400 行以内**。
   - **只有"记录"没有"检索"** → 新人找不到文档等于没有。**知识库要有目录结构和搜索**。
5. **面试话术**："我判断文档有没有价值只有一个标准：**新同学拿着它能不能不问我就把一个真实任务做完**。方法上我会**先想清楚读者是谁**——同一份内容写给评审者、写给未来的自己、写给新人，结构完全不同。写文档我遵循几个原则：**开门见山、面向任务而不是面向系统结构、命令要能直接复制粘贴**。另外我觉得技术方案里最值钱的是**非目标和决策点的选项对比**，前者防止范围蔓延，后者才是评审真正该讨论的东西。"

**读者问：知识沉淀怎么做？怎么保证文档不过期？**

**AI答：**

1. **沉淀的核心是"机制"而非"意愿"**。靠"大家有空就写文档"是不可能持续的。必须把沉淀**嵌进已有的流程**：
   - **触发式**：每完成一个有技术决策的功能 → 写 ADR；每发生一次线上事故 → 写复盘。**这件事发生了就必须写**。
   - **评审式**：技术方案评审 → 决策点自动提取成 ADR 草稿；Code Review 中发现的通用问题 → 沉淀进规范。
   - **定期式**：每月清理过期文档、检查失效链接；每季度同步架构图。
   > **原则：新增流程一定会被绕过，要复用已有流程的"卡点"。**
2. **文档过期的四个原因及对策**：
   | 原因 | 对策 |
   | --- | --- |
   | **写完就结束** | 文档带 `last-verified` 标记 + 定期扫描提醒 |
   | **没人读**（不是读者需要的） | 写前先明确读者和任务 |
   | **信息重复在 5 个地方** | **单一事实源（SSOT）**：一处维护，其他地方链接过去 |
   | **没有 owner** | CODEOWNERS 指定文档负责人 |
3. **"信息重复"是最隐蔽的杀手**：同一个信息有 5 处副本 → 改了一处另外四处全错 → 读者不信任文档 → 更没人读。**这是"文档不一致"的根因，必须靠 SSOT 解决。**
4. **自动化的手段**：
   - **doctoc**：Markdown 目录自动生成，CI 校验目录是否过期。
   - **OpenAPI**：接口契约单一事实源 → 自动生成客户端 + 文档站点 + **破坏性变更检测**（`oasdiff`）。
   - **模块地图脚本**：从 Gradle 模块 + CODEOWNERS 自动生成架构文档的模块表。
   - **KDoc / Dokka**：代码注释 → API 文档。
   - **链接检查脚本**：CI 中检测失效的内部链接。
5. **工具选型**（看生态）：
   | 场景 | 推荐 |
   | --- | --- |
   | 国内团队日常协作 | **语雀**（目录树 + 编辑体验好） |
   | 大型企业 / 已用 Jira | **Confluence** |
   | **ADR、README、模块文档** | **放在代码仓库里**（跟代码版本化，Review 友好） |
   | 对外技术文档站 | **MkDocs / Docusaurus**（文档即代码） |
6. **三个最容易被忽略但价值最高的目录**：
   - **术语表（Glossary）**：一个项目里"订单"可能指实体/快照/订单号，**术语不统一是协作中最大的隐性成本**。
   - **踩坑记录**：避免同一个人踩两次坑，**投入产出比最高**。
   - **Runbook（应急预案）**：出故障时值班的人照着做就能止损，否则事故响应就变成"微信群里问资深同学"。
7. **面试话术**："知识沉淀我理解**关键是机制不是意愿**——靠'有空写文档'不可持续。我的做法是把沉淀**嵌进已有流程**：每个有技术决策的功能**必须**写 ADR，每次线上事故**必须**写复盘，Code Review 发现的通用问题沉淀进规范。**新增流程一定会被绕过，所以要复用已有卡点**。文档过期我主要靠三个手段：**单一事实源**（同一信息只在一处维护，别处链接过去）、**自动化生成**（doctoc 生成目录、OpenAPI 生成接口文档、脚本生成模块地图）、**CI 校验**（目录过期、链接失效直接阻断）。另外我觉得最被低估但价值最高的三类文档是：**术语表**（消除沟通歧义）、**踩坑记录**（避免重复踩坑）、**Runbook**（故障时照着做就能止损）。"

**读者问：接口文档怎么管理？服务端的接口改了客户端怎么知道？**

**AI答：**

1. **必须自动化的根本原因**：手写接口文档的必然结果是"**接口改了文档没改**"——开发赶进度不会去改文档。所以唯一能长期维护的方式是**从代码生成**。
2. **完整链路**：
   ```
   服务端注解/DSL → openapi.yaml
                      ↓
        ┌─────────────┼─────────────┐
        ↓             ↓             ↓
   客户端生成      文档站点      破坏性变更检测
   Retrofit      Swagger/Redoc   oasdiff（CI 门禁）
   ```
3. **破坏性变更检测（CI 门禁）**——这是最关键的机制：
   - **破坏性变更**（必须阻断）：删除接口、删除字段、字段改名、字段类型变更、新增必填请求字段。
   - **兼容变更**（允许）：新增可选字段、新增接口、删除可选请求参数。
   - **工具**：`oasdiff`（Go 写的，快）、`openapi-diff`（Java）、`buf breaking`（如果用 protobuf）。
4. **⚠️ "服务端新增字段"不等于"客户端能安全处理"**：
   - **enum 值新增**：老客户端的 Kotlin data class 反序列化未知枚举值时**可能崩溃**（取决于 Gson 的策略）。
   - **嵌套结构变更**：老客户端可能期望扁平结构。
   - **所以契约里要写明"客户端必须容忍未知字段"**，并且客户端**必须**设 `ignoreUnknownKeys = true`、**所有可选字段用 `?` + 默认值**。
5. **Android 端的具体实践**：
   ```kotlin
   // 客户端 JSON 配置：必须容忍未知字段
   val instance = Json {
       ignoreUnknownKeys = true      // ★ 服务端灰度新增字段时不崩
       coerceInputValues = true      // null → 默认值
   }
   ```
   ```kotlin
   // 数据模型：可选字段用 ? + 默认值
   @Serializable
   data class UserDetail(
       val id: String,
       val nickname: String? = null,     // ★ 容忍服务端不返回
       val level: Int? = null
   )
   ```
6. **Mock 与契约测试**：
   - **契约测试（Contract Testing）**：用 **Pact** 定义服务提供方与消费方的期望，在 CI 中验证双方一致——**能在联调前发现契约不一致**。
   - **Mock Server（WireMock / Mockoon）**：从 `openapi.yaml` 自动生成 mock，客户端可以独立开发。
7. **版本策略**：
   - **URL 版本**（`/v1/`、`/v2/`）：简单粗暴，但服务端要维护多版本。
   - **Header 版本**（`Accept: application/vnd.api.v2+json`）：更灵活，但需要网关支持。
   - **Android 侧的现实**：**大部分 App 服务端不提供多版本**，靠"新增字段 + 客户端容忍"来保证兼容。
8. **面试话术**："接口文档**必须自动化**，手写的文档一定会烂。我的链路是：**服务端注解生成 openapi.yaml，然后三路输出——生成 Retrofit 客户端、渲染文档站点、用 `oasdiff` 做破坏性变更检测**。CI 里如果有破坏性变更就直接阻断合并，这是最有效的保障。这里有个坑我会特别强调：**'服务端新增字段'不等于'客户端能安全处理'**——比如服务端新增了 enum 值，老客户端反序列化时可能直接崩，所以客户端必须配 `ignoreUnknownKeys = true`，而且**所有可选字段都要用 `?` 加默认值**。另外我们会用 **Pact 做契约测试**，在联调之前就能发现双方契约不一致。"

**读者问：团队协作流程怎么设计？评审会怎么开才有效？**

**AI答：**

1. **完整流程与每一步的产出**：
   ```
   需求评审（产品主导）→ 产出：验收标准明确的需求单
     ↓
   方案评审（开发主导）→ 产出：定稿方案 + ADR 草稿
     ↓
   开发（小步提交 + 异步同步）→ 产出：PR + 每日同步
     ↓
   Code Review（< 400 行）→ 产出：合并
     ↓
   测试 + 灰度 → 产出：监控数据
     ↓
   发布 + 复盘 → 产出：复盘报告 + Action Item
   ```
2. **评审会怎么开才有效（三个反模式）**：
   - **会上读文档** → 90 分钟里前 60 分钟在念 PPT。**文档提前 24 小时发出，会上只讨论"决策点"和"未决问题"**。
   - **没有未决问题** → 说明没准备。**方案里必须列出 2~3 个需要拍板的问题**，评审才有产出。
   - **没有决策记录** → 讨论完就忘了。**当场产出 ADR 草稿**（哪怕是结论的两句话）。
3. **方案文档的必备段落**：
   - **背景与问题**（有数据支撑）
   - **目标 / 非目标** ★（防范围蔓延）
   - **决策点的选项对比** ★（"方案 A vs B vs 选 C 及理由"）
   - **影响面**（改动范围、性能、兼容性、风险与兜底）
   - **未决问题** ★
4. **PR 规范**：
   - **< 400 行**：reviewer 的注意力是有限资源，超了就只能"点个赞"。
   - **超大改动拆分**："纯重构（不改行为）" + "功能实现" 两个 PR，先合重构再合功能——这样每个 PR 的行为变化都清晰可审。
   - **PR 描述模板**：背景 / 变更内容 / 截图（UI 改动）/ 自测清单 / 风险点。
5. **日常同步的三个原则**：
   - **小步提交 + 频繁推送**：分支活不过 3 天。长期分支必然冲突。
   - **异步优先**：能用文字说清楚的不要开会。
   - **阻塞立即暴露**：**卡住超过半天就同步**，哪怕还没有答案（"我卡住了，在试 A/B 方案"）。憋 3 天才发现方向错了，代价是 3 天。
6. **复盘的三个要点**：
   - **Blameless（对事不对人）**：不追责才能暴露真实原因。人一旦怕追责就会隐瞒，隐瞒让下次事故更容易发生。
   - **根因要挖到流程层面**：如果根因是"客户端忘了判空"，那定责到客户端就完了——**但真正的问题可能是"接口契约变更没有评审机制"**。只定责到个人，下次的漏洞还在。
   - **Action Item 必须可追踪**：有负责人、有截止日期、**有验证方式**。没有验证方式的 Action Item 三个月后 100% 没完成。
7. **面试话术**："协作流程我会分**需求评审、方案评审、开发、Code Review、测试灰度、复盘**六步。**评审会要开得有效，核心是三条：文档提前 24 小时发，会上不读文档只讨论决策点和未决问题；方案里必须列 2~3 个需要拍板的问题；当场产出 ADR 草稿**，不然讨论完就忘了。PR 我会控制在 **400 行以内**，超大改动拆成'纯重构'和'功能'两个 PR 先合重构——这样每个 PR 的行为变化都清晰可审。日常同步靠**小步提交、异步优先**，还有一条我觉得很重要：**卡住超过半天就要暴露**，哪怕还没有答案。复盘上我坚持 **Blameless**，而且**根因要挖到流程层面**——如果只定责到'某个人忘了判空'，那契约变更没评审的漏洞还在，下次还会犯。Action Item 必须有负责人、截止日期**和验证方式**，否则三个月后一定没完成。"

**读者问：ADR 是什么？什么该写 ADR？跟技术方案文档有什么区别？**

**AI答：**

1. **ADR（Architecture Decision Record，架构决策记录）**：记录**一个技术决策的上下文、选项和后果**的简短文档。
2. **与设计文档的区别**：
   | | **技术设计文档** | **ADR** |
   | --- | --- | --- |
   | **回答什么** | "**怎么做**" | "**为什么这么选**" |
   | **长度** | 几页到几十页 | **一页以内** |
   | **生命周期** | 随版本更新 | **永久**（记录历史，不修改） |
   | **读者** | 当前的实现者 | **未来的所有维护者** |
   | **数量** | 每个需求一份 | **每个决策一份**（可能一次需求产生 3 份） |
3. **什么该写 ADR（判据）**：**这个决策如果半年后有人问"为什么不用 X"，需要能查到答案。**
   - ✅ 该写：引入/替换框架、数据库选型、架构模式调整、**引入一个新的基础设施依赖**、**放弃某个方案**、**影响多模块的接口契约约定**。
   - ❌ 不该写：单个函数的实现细节、代码风格、一次性的临时方案、还没确定的事（**先写"Proposed"，定了再改"Accepted"**）。
4. **ADR 的标准结构**（Michael Nygard 的模板）：
   ```
   # ADR-NNNN: 标题（用动词描述决策，如"采用 X 而非 Y"）
   - 状态：Proposed / Accepted / Superseded by ADR-XXXX / Deprecated
   - 决策者 / 日期
   ## 背景（Context）    ← 什么约束/压力导致了需要做决策
   ## 决策（Decision）   ← 结论，一句话
   ## 考虑过的替代方案   ← ★ 表格：方案 / 优点 / 缺点 / 为什么没选
   ## 后果（Consequences）← 正面 / 负面 / 需要注意
   ## 复审条件          ← ★ 什么情况下要重新评估这个决策
   ```
5. **"考虑过的替代方案"是最有价值的部分**：
   - 它强制你**在决策时把选项摆出来**（很多决策是"没想清楚就选了默认方案"）。
   - 它让未来的维护者知道"**X 已经被考虑过了，别再提了**"——这能省下大量重复讨论。
   - **反面案例的负面后果也要写**（"我们放弃了 A，因为 A 在 X 场景下有 Y 问题"），否则半年后有人会重提 A。
6. **ADR 的存放与管理**：
   - **放在代码仓库里**（`docs/adr/`），**跟代码一起版本化**——这是它和 Wiki 文档最大的区别，也是它不容易腐烂的原因。
   - **编号递增**（ADR-0001、ADR-0002...），**永不删除、永不修改已接受的 ADR**。
   - **被取代时**：把状态改为 `Superseded by ADR-XXXX`，**保留原文**（历史是有价值的）。
7. **面试话术**："ADR 是**架构决策记录**，一页以内，回答的是'**为什么这么选**'而不是'怎么做'。它和技术方案文档的区别是：**设计文档回答'怎么做'，随版本更新；ADR 回答'为什么'，永久保留、只追加不改**。判据很简单：**如果半年后有人问'为什么不用 X'，需要能查到答案，就该写 ADR**。我认为 ADR 里最有价值的是'**考虑过的替代方案**'这个表格——它既逼我在决策时把选项摆清楚，也让未来的维护者知道'这个已经被考虑过了'，省掉重复讨论。管理上我把 ADR **放在代码仓库的 docs/adr 目录**，跟代码一起版本化，编号递增，**永不删除、永不修改**，被取代时改状态并指向新的 ADR。"

**读者问：新同学入职怎么快速上手？Onboarding 文档该怎么写？知识怎么传下去？**

**AI答：**

1. **Onboarding 的目标不是"看完所有文档"，而是"能独立完成一个真实任务"**。
   - **反面**：给一堆 Wiki 链接让新人自己看 —— 大多数人看完目录就放弃了。
   - **正面**：**第一天就能提一个 PR**，第三天能独立修复一个线上小 Bug。
2. **Onboarding 文档应该包含的四块**：
   | 模块 | 内容 | 时长 | 交付物 |
   | --- | --- | --- | --- |
   | **环境搭建** | JDK/SDK 版本、代理配置、依赖仓库账号、构建命令 | 第 1 天 | **本地能跑出 Debug 包** |
   | **系统认知** | 架构图、模块地图、关键业务流程、术语表 | 第 1~2 天 | **能画出请求链路** |
   | **第一个任务** | 一个真实的小需求（修 Bug / 加埋点 / 改文案） | 第 2~3 天 | **提第一个 PR 并被合并** |
   | **常见坑** | 踩坑记录、环境问题 FAQ | 第 3 天 | **不重复踩坑** |
   - ★ **"第一个任务"是最关键的**：真实任务会自然带出代码规范、Git 流程、CR 规范、发布流程，比"读十篇规范文档"有效得多。
3. **知识传递的三条路径**：
   - **文档**（显性知识）：**广度**好、**深度**不够、更新慢。
   - **Code Review**（隐性知识的显性化）：**深度**好。★ **Reviewer 的每一次 comment 都是一次知识传递**——尤其是"为什么这样写"而不只是"这样写不对"。
   - **结对 / 结对编程**（隐性知识）：**最高效**，但**成本最高**。
   > **组合使用**：文档负责"广度覆盖"（不遗漏），CR 负责"深度纠偏"，结对负责"最难口头说清的部分"。
4. **文档之外必须有的三个机制**：
   - **答疑渠道**：明确"卡住超过 X 分钟就问谁"（企业微信群 + 明确的 owner）。
   - **周会/同步会**：新人**必须参加**（哪怕只是听），这是了解上下文最快的渠道。
   - **"三个为什么"**：新人问的问题如果团队答不上来，说明**文档缺失** → 应该补文档，而不是只回答这一次。
5. **老员工的责任**：**每个新人入职，都应该有一位明确的"引导人（Buddy）"**。这是投入产出比最高的知识传递手段——文档可以写得再好，也替代不了一个能回答"这个模块为什么这么设计"的人。
6. **知识流失的防线**：
   - **代码里的注释**（尤其解释"为什么"而不是"是什么"）。
   - **ADR**（决策的来龙去脉）。
   - **Runbook**（事故时照着做）。
   - **结对**（把隐性知识传给下一个人）。
   - ★ **核心原则：知识只存在于人脑里，就是最大的风险资产。**
7. **面试话术**："Onboarding 我认为目标不是'看完文档'，而是'**能独立完成一个真实任务**'。所以我会分四块：**环境搭建、系统认知、第一个任务、常见坑**。其中**'第一个任务'最关键**——一个真实的小需求会自然带出代码规范、Git 流程、CR 规范，比读十篇规范文档有效得多。知识传递我走三条路径：**文档管广度**、**Code Review 管深度**（reviewer 的每一句'为什么这样写'都是一次知识传递）、**结对管最难口头说清的部分**。另外我会强调一个点：**新人问的问题如果团队答不上来，那说明文档缺失，应该补文档而不只是回答这一次**。最后每个新人我会指定一个明确的引导人，这是投入产出比最高的手段——文档写得再好，也替代不了一个能回答'这个模块为什么这么设计'的人。"

**读者问：README 和架构文档到底怎么写才有用？新人打开一个陌生项目，第一分钟该看什么？**

**AI答：**

1. **新人打开项目的第一分钟，该看到的三件事**：
   - **① 这是什么**（一句话 + 解决什么问题）。
   - **② 怎么跑起来**（能复制粘贴的命令）。
   - **③ 代码在哪**（目录树 + 模块职责）。
   > **如果 README 的第一屏没回答这三件事，新人就会去"翻代码猜结构"——这是最慢的路径。**
2. **README 的黄金结构**（按阅读顺序）：
   ```
   项目名
   → 一句话简介（≤ 50 字）
   → 徽章（构建状态 / 版本 / 许可证）
   → 简介（2~3 段：解决什么问题）
   → 快速开始（5 分钟能跑起来）★
   → 目录结构（模块 + 职责）
   → 构建与运行（完整命令 + 环境要求）
   → 配置（环境变量 / local.properties / 密钥）
   → 测试（怎么跑）
   → 贡献指南（分支规范 / 提交规范 / PR 要求）
   → 许可证 / 联系方式
   ```
3. **README 的三个经典错误**：
   | 错误 | 后果 | 正确做法 |
   | --- | --- | --- |
   | **开头讲历史与愿景** | 新人第一屏没得到任何有用信息 | 开头就给结论和用途 |
   | **"配置好签名密钥后打包"** | 新人第一道坎就卡住 → 放弃 | 给**完整可复制**的命令，含依赖安装 |
   | **没有目录结构** | 新人不知道从哪看起，漫游代码库 | 加目录树，标注每个模块的**职责**（不只是路径） |
4. **架构文档的核心是"图 + 决策"，不是"描述"**：
   - **一张总体架构图**（组件 + 依赖箭头）能顶 20 页文字。★ **评审时先看这张图**。
   - **关键链路时序图**：一个典型请求/流程的完整时序（`启动 → 首页 → 下单 → 支付`）。
   - **模块地图表**：模块 / 路径 / 职责 / 负责人（**最好自动生成**，见 §5.3）。
   - **边界与约束**：哪些模块之间**不能**直接依赖（依赖倒置规则），这一条比画图更重要。
5. **架构文档最容易过时的地方**（因此要自动生成）：
   - **模块列表** → 模块改名/新增后，文档里还是旧的 → **从 Gradle 模块自动生成**。
   - **接口清单** → 从 OpenAPI 自动生成。
   - **依赖关系** → 用工具分析实际 import 生成，而不是手画。
6. **文档的"三层粒度"策略**：
   | 层级 | 读者 | 内容 | 例子 |
   | --- | --- | --- | --- |
   | **L1 索引级**（30 秒） | 所有人 | 是什么 / 怎么跑 / 文档在哪 | README |
   | **L2 任务级**（5~30 分钟） | 要干活的人 | 如何完成某个具体任务 | "如何新增一种订单类型" |
   | **L3 原理级**（深入） | 维护者 | 为什么这么设计 / 边界情况 | ADR、架构文档 |
   > ★ **90% 的人只需要 L1 和 L2**。L3 应该存在，但**不应该挡在 L1/L2 前面**——这是"新人被文档劝退"的常见原因。
7. **面试话术**："我会区分两种文档：**README 面向'我要跑起来、我要找到代码'**，**架构文档面向'我要理解这个系统'**。README 的黄金结构我会按'**是什么 → 怎么跑 → 代码在哪 → 怎么配 → 怎么测 → 怎么贡献**'来排，并且**快速开始必须给能直接复制粘贴的完整命令**，包括依赖安装——新人第一道坎卡住就放弃了。架构文档我认为**核心是图和决策，不是文字描述**：一张总体架构图顶 20 页文字，时序图说明关键链路，边界约束（哪些模块不能直接依赖）比画图更重要。另外架构文档最容易过时的是**模块列表**，所以我会**从 Gradle 模块和 CODEOWNERS 自动生成模块地图**，CI 校验，这样模块改名了文档自动跟着变。"
